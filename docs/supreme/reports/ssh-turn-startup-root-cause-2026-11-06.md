## 真实调用链与直接原因

### 1. 同一输入重复执行两套项目准备

首次对话的 `AgentPool::acquire → create_agent → infra::create_agent_with_diagnostics_and_event_bus` 在工厂 `infra/factory.rs:674` 开始：发现项目根、发现项目 Subagent、扫描目录树、读取 gitignore、读取项目指令，随后执行 Git 状态读取并发布投影。

同一输入进入 `chat_driver.rs:2249` 后，无条件调用 `prepare_dynamic_project_context`，再次发现项目根、读取项目指令、扫描目录树、读取 gitignore、读取 Git 状态。第二份准备结果由 turn registration 保存，供模型前投影使用；没有接收或复用工厂刚准备的数据。

热会话会复用 Agent，所以第一份开销消失，但每条消息仍会支付第二份开销。这与既有报告中“首次约两段 11 秒、后续只剩第二段”的冷/热对照一致，不能把 Agent pool 的存在当作项目上下文已被复用。

### 2. 一次准备内部还会重复搜索项目根

工厂和动态准备都先调用 `utils::find_project_root_with_file_system`；指令读取经 `unified_memory::load_instruction_projection_with_file_system → InstructionProvider::load_for_file_system` 后，在 `instruction_provider.rs:47` 再调用同一搜索函数。

`utils.rs:35` 先沿所有祖先逐个检查 `.git/.hg/.svn`，找不到后再沿所有祖先逐个检查 7 个 fallback marker。每次 `exists` 最终调用 `FileSystem::metadata`。逻辑函数已统一，但执行结果没有共享，仍然重复发生网络访问。

条件计数：对 `/home/ubuntu/ssh-test`，若四级祖先都没有任何 marker，一次搜索是 `4 × (3 + 7) = 40` 次探测。动态准备做两遍是 80 次，首次输入的工厂和 driver 合计四遍，仅搜索根目录就有 160 次探测，尚未算目录树、规则、gitignore 和 Subagent。这个数量来自源码循环，不是真实服务器逐调用计数；未远程确认该目录实际 marker 分布。

不能通过只认当前目录或只认最近 manifest 降低数量：现有语义要求祖先 VCS 根优先于嵌套包目录，否则会漏掉上层 AGENTS.md。

### 3. SSH 主连接复用没有覆盖 SFTP 通道复用

`ProjectSshFileSystem::metadata/read/symlink_metadata/read_dir` 都进入 `sftp.rs:51` 的 `run`，它调用 `with_sftp`。`sftp.rs:454` 每次都 `SftpChannel::open`，执行一项文件操作后立即 `finish`。

`channel.rs:24` 每次启动系统 `ssh -s … sftp` 子进程，初始化 SFTP 客户端；`finish` 关闭客户端并等待子进程和 stderr reader。ControlMaster 复用了认证和底层 SSH 连接，但没有复用这些文件通道及其协议初始化、关闭和等待。即使每次只需约百毫秒，串行重复几十次也会变成十几秒。

`spawn_blocking` 只是把同步准备移出 Tokio 执行线程；调用方仍 await 全部结果，它不会减少网络往返或让任务更早进入模型阶段。

### 4. 全池写锁扩大慢启动的影响

`agent_pool/pool.rs:897` 在 `acquire` 一开始取得 agents 写锁，直到完整异步 `create_agent` 结束才插入实例。源码注释明确以此防止并发创建竞态。结果是一个会话的 SSH 文件准备可以阻塞同池其它会话的获取，包括已存在 Agent 的快路径。

这是可由源码确定的连带风险；当前单次“你好”没有并发证据，不能把锁竞争算成本次实测 16 秒的来源。

## 为什么会产生并漏过这样明显的问题

Git blame 将远程准备、动态准备及逐操作 SFTP 生命周期的关键实现都追溯到 `780ddd0d25c2eac5d1471cb3e5012c9d2f6b3cf9`（2026-10-26 项目工作空间集成），并非上一版删除轮数限制新引入。根目录算法此前用于本地文件，远程集成把它的文件访问替换为 SFTP，但保留了原来的串行访问粒度。

由实现和 ADR 可以支持以下工程原因，不推测作者个人动机：

1. **远程适配只保证位置与结果正确，未同时建立访问成本约束。** 本地几十次 stat 很便宜，网络文件系统的同等调用次数却很昂贵。统一 trait 没有统一成本。
2. **初始化与每条消息的新鲜上下文之间没有明确数据交接。** 工厂需要可用的初始规则；driver 需要实际 invocation 的规则。两个边界都独立全量读取，以正确性方式叠加了重复工作。
3. **物理资源结算与单次文件操作绑得过紧。** 当前方案能明确等待原通道关闭、保留未知写入状态，但以每项文件操作创建通道作为实现方式，放大了正常读取开销。结算语义本身应保留，粒度需要调整。
4. **验证覆盖了功能与生命周期，没有覆盖这条延迟链。** 已检查的适配测试包括无网络身份、错误分类、未知副作用和物理结算；现有性能基线主要测 Run 查询、GUI 数据及记忆结算，没有 SSH 提交到首个请求的预算，也没有根搜索次数或 SFTP 启动次数断言。本地/mock 绿不能发现网络往返放大。
5. **上一轮已发现延迟，但没有闭合。** `gui-feedback-2026-11-06.md:21` 明确记录两次准备和逐操作开关 SFTP，并明确本次轮数删除不包含改造。因此上一版只能交付“取消 10 轮限制”，不能作为启动性能修复的证据。

## 推荐修复路线

修复集中在 EKO 应用层；框架已有 `FileSystem` 接缝足够表达位置绑定。沿用现有 `PreparedProjectContext`、`InstructionProjectionSnapshot`、turn registration 和原连接 owner，不新增任务状态机或另一套上下文权威。

### A. 一次准入只准备一次，同一准备只解析一次根

将“实际执行位置解析 → 文件读取 → Git 读取 → 准备结果”归到一个可失败的准备过程。工厂和 driver 通过现有准备结果交接，首次输入复用相同目标、位置 revision、连接代际、cwd 和准备作用域的事实；工厂必须读取的 Subagent 定义也通过同一读取作用域获得。实际 cwd 或代际不匹配时重新准备。

指令加载器显式接收已解析的根和原 cwd，避免内部再发现一次。根与 cwd 必须分别保留：AGENTS 链和 `.eko/local.md` 使用实际 cwd，Subagent 的隔离目录不得沿用父 Agent 的快照。原始读取事实与依赖模型窗口的 prompt 裁剪分开，切模型不能复用错误 token 预算。

每条新消息仍按现有合同刷新规则；先消除同一次准入的重复读取，不引入无限期内容缓存。模型循环里的 projector 继续只重发已准备事实，不再做 I/O。

### B. 将 SFTP 生命周期提升到整次只读准备

一次准备在原连接 owner 上打开一个 SFTP 通道，根探测、目录树、gitignore、项目规则及相关定义通过同一客户端读取，全部结束后统一 close/join。可以先实现应用私有的只读作用域适配，继续喂给现有加载器；无需改框架公开文件 API 或复制加载算法。

优先采用有明确开始/结束的准备作用域，而不是先做全局永久 SFTP 池。后者会扩大重连、闲置退出、跨请求资源引用和写入结算的修改范围。只读作用域也必须保持原错误传播、请求结束确认和 host receipt，不能以丢弃 future 或本地子进程退出冒充远端停止。

### C. 减少串行远程请求，而不只减少通道创建

单次作用域内对相同路径的 metadata/缺失结果去重；将祖先 marker 按目录成批发现或有界并发，保持“所有祖先 VCS 优先，再按 fallback 优先级”的原判定。若选择 read_dir 检查 marker，必须处理“可 stat 已知名称但不可列目录”的权限差异，并保留跟随链接/非跟随链接各自的语义，不能直接互换 metadata 缓存。

指令存在性和正文读取复用同一通道；不再为一次 symlink 检查和随后 read 分别启动进程。目录树继续遵守当前深度和输出限制；大目录的完整枚举成本单列测量，不能因减少通道就宣称所有大工程都已达标。

### D. 缩短池锁范围，保持原准入权威

把慢准备移出全池写锁，对同一 conversation 协调一次创建，完成时在原锁下重新核对容量、退休/关闭、workspace/plugin/model generation 后发布。复用现有 admission 和 transition 合同，不增加独立调度器。等待者取消、创建失败和发布期间代际变化都必须有回归覆盖。

### E. 补上能阻止复发的验证

新增同一输入标识下的阶段观测：pool 等待/创建、根发现、规则、目录树、Git、SFTP 打开/关闭计数、意图分类请求、首个主请求。日志记录类型、计数、耗时与结果，不记录凭据或文件正文。

验收必须同时覆盖结构与时间：

- 无 marker 深目录、Git 根、嵌套包、AGENTS.override、规则缺失/不可读、符号链接、非 UTF-8 输入；根优先级与失败语义保持。
- 首次/后续消息、同项目多个会话、规则被外部编辑、cwd 改变、位置重绑、重连、不同隔离目录的 Subagent；不得串用快照。
- 实际完整准入路径中，同一准备不重复搜索根；准备读取的 SFTP 通道数量不随文件操作数增长；已有会话获取不被其它会话慢建实例持有全池锁阻塞。
- 可注入每次远程请求/通道启动成本的稳定测试，并统计真实请求与进程启动次数；不能只用零延迟内存文件系统，也不能只验证新 helper。
- 真实 SSH 冷/热样本分别量输入保存→准备完成、分类请求、主请求、首个事件及首 token，记录 RTT、目录规模、错误和分位数。建议初步预算：认证已就绪、固定小目录、100ms RTT 条件下，文件上下文准备 P95 ≤ 2 秒；这是待验证的验收建议，不是已测结果或任意网络下的承诺。
- 取消、断连、关闭和未知写入的既有回归必须保留；性能修复不得靠跳过必需规则、吞错或自动重放写入实现。

## 成熟实现参照与取舍

[VS Code Remote SSH 官方文档](https://code.visualstudio.com/docs/remote/ssh)把命令与扩展放在远端 Server 执行，减少本地逐项访问远端的代价。EKO 当前产品不要求部署远端 Agent/Server，因此借鉴减少跨网络碎片化工作的原则，保留本地主循环和标准 SFTP。

[GNU Emacs/TRAMP 官方源码文档的 Connection caching 节](https://raw.githubusercontent.com/emacs-mirror/emacs/master/doc/misc/tramp.texi)明确复用连接相关属性以加快初始化，并在发现远端系统变化时失效。这支持“复用必须绑定目标并有失效条件”；不据此宣称它与 EKO 的具体缓存实现相同，也不建议缓存用户凭据。

[当前 0.15.10 版 openssh-sftp-client 文档](https://docs.rs/openssh-sftp-client/0.15.10/openssh_sftp_client/)支持客户端内请求缓冲/批量 flush，同时明确取消 future 不撤回已经发送的远端操作。因此调整通道粒度可复用既有客户端，但仍须保留原物理 owner 和结果结算。

以上是修复建议，涉及准备结果交接、通道作用域和池发布并发，应在实现前明确内部契约和回归场景。当前结论是“源码根因已确认、逐操作耗时尚未实测、业务修复未实施”，没有 App、真实 SSH 修复后表现或 main CI 的通过声明。examples 与官网不因本次诊断而修改；后续若只调整应用内部实现且保持公开行为，应更新应用 ADR/运行时文档和性能验收，不发布为新框架 API。
