# Review Reporting Protocol

This protocol makes reports from different models and harnesses comparable. A
task is not complete merely because analysis prose exists. Each reviewer must
replace `<reviewer>` below with its dedicated directory; Codex uses `codex`.

## Directory Layout

```text
docs/comprehensive-review/
  README.md
  TASKS.md
  REPORTING.md
  templates/
    task-report.md
    validation-report.md
  <reviewer>/
    README.md
    reports/
      tasks/
      validations/<task-id>/
      synthesis/
```

Create report files only when their work is actually performed. Empty report
placeholders are prohibited because they make progress look more complete than
it is.

## Task Report Contract

Copy `templates/task-report.md` into
`<reviewer>/reports/tasks/<task-id>.md`. A valid report contains:

1. Task ID, title, reviewer, date, and reviewed commits.
2. Exact scope and explicit out-of-scope list.
3. Required inputs and dependency reports actually read.
4. Architecture/layering classification where relevant.
5. Current-code call graph or data-flow evidence.
6. Findings ordered by P0, P1, P2, then P3.
7. A declared validation matrix with one link per execution report.
8. Historical conclusions classified as current, fixed, stale, or regressed.
9. Coverage gaps and residual uncertainty.
10. A compact handoff for downstream tasks.

Reports must distinguish facts from recommendations. A recommendation cannot be
promoted to a finding unless a concrete negative impact is established.

## Finding Contract

Use stable IDs `<task-id>-P<priority>-<sequence>`, for example
`F-RCT-02-P1-01`. Each finding includes:

- priority and confidence (`high`, `medium`, or `low`);
- owning layer (`framework`, `application`, or `adapter`);
- affected source paths and tight line anchors;
- runtime reachability evidence;
- expected invariant and observed behavior;
- user/developer impact;
- root cause rather than only the symptom;
- recommended direction, including code that should be deleted if replaced;
- regression validation needed for a fix;
- links to all supporting validation reports.

Priority meanings:

- `P0`: data loss/corruption, secret exposure, or core path unusable.
- `P1`: concurrency/recovery error, major capability failure, or surface
  behavior that violates a product invariant.
- `P2`: duplicate authority, wrong layering, misleading public API, or material
  maintainability/performance defect.
- `P3`: localized cleanup, naming, documentation, or low-impact efficiency issue.

Do not inflate priority because code is large or complex. Do not lower priority
because a defect was generated by AI or appears old.

## Validation Report Contract

Every validation execution gets its own immutable report copied from
`templates/validation-report.md` under
`<reviewer>/reports/validations/<task-id>/`. This includes read-only validations.

Examples of one validation execution:

- tracing a request from one entry point to one terminal event;
- checking a symbol's definition, registration, and live callers;
- comparing one framework concept with its EKO adapter field by field;
- running one Cargo command;
- running one frontend test/build command;
- replaying one event fixture through multiple reducers;
- testing one crash/cancel/revision fault scenario;
- checking one external implementation against primary documentation.

A validation report records:

- repository commit(s) and dirty-state summary;
- exact command, inspection procedure, or reproducible steps;
- environment and feature flags;
- expected result before execution;
- exit code and a concise result summary;
- paths to large logs/artifacts instead of pasting them into the report;
- observed deviations;
- final status and what conclusion the result does and does not support.

New validation reports use the unambiguous `validation-v2` identity contract:

```text
<validation-key>--attempt-<NN>.md
```

The report header must contain `Schema: validation-v2`, the exact
`Validation key`, and a positive integer `Attempt`. For example,
`V01--attempt-02.md` is the second immutable attempt of `V01`, while
`V01-02--attempt-01.md` is the first attempt of the independent `V01-02`
subcase. Historical filenames remain immutable and are not retroactively
reinterpreted. Run `scripts/verify-validation-lineage.sh` before accepting new
reports; run it with `--self-test` to exercise retries and independent subcases.

If the same command is rerun after a fix or environmental change, increment the
explicit attempt number for the same validation key. Never edit an earlier
outcome from failed to passed. Corrections to factual metadata may be appended
under a dated `Correction` section.

## Validation Granularity

One report should represent one falsifiable claim or one command invocation.
Commands may be grouped only when they are an indivisible scripted scenario
with one expected terminal result. The entire submission gate is not one
validation: fmt, each Clippy configuration, tests, no-default check, feature
matrix, frontend tests, and frontend build are separate reports.

Static review tasks must declare at least these validations when applicable:

- `V01` definition and duplicate search across both repositories;
- `V02` registration and runtime reachability trace;
- `V03` invariant/edge-case inspection against tests;
- `V04` targeted executable test or compile check;
- `V05` historical-document drift check.

If a validation is not applicable, create no fake report. State why it is not
applicable in the task report's matrix.

## Completion Rule

A task may be marked `complete` only when:

- its report exists and follows the template;
- every required validation has its own report;
- every reported command has a known exit code;
- failures are recorded as findings or explicitly explained as expected;
- evidence covers definition, reachability, and behavior where those claims are
  made;
- no unresolved scope expansion remains;
- downstream handoff and stale-report triggers are recorded.

A failed validation does not prevent review completion. It prevents claiming
that the system passed and normally becomes a finding. A missing validation is
different: it leaves the task in `needs_evidence`.

## Historical Document Handling

For every historical claim used by a task, classify it as:

- `current`: code and runtime evidence still support it;
- `fixed`: the documented issue no longer exists;
- `stale`: paths or architecture changed so the claim cannot be applied;
- `regressed`: it was fixed but current code violates it again.

Never copy old findings into the new report without this classification.

## Cross-Repository Boundary Gate

Before recommending movement between repositories, the report must contain:

| Classification | Required answer |
|---|---|
| Generic mechanism | Would unrelated `echo-agent` consumers reasonably need it? |
| EKO product policy | Which local-assistant decision makes it application-specific? |
| Adapter boundary | Is conversion thin, lossless, and free of scheduling/state authority? |
| Duplicate search | What names, traits, fields, behaviors, and call paths were searched? |
| Migration deletion | Which old implementation and tests are removed when authority moves? |

Uncertain ownership defaults to the application layer. A public framework API
is retained unless framework-wide evidence shows it is obsolete or fully
replaced.

## Synthesis Rules

Phase synthesis reads completed task reports and their validation summaries. It
does not need the original review conversations. The synthesizer must:

- merge duplicate findings under one canonical ID and retain backlinks;
- resolve contradictory findings by reopening the smallest relevant validation;
- mark findings stale when reviewed commits no longer contain the evidence;
- preserve minority/uncertain conclusions as open questions rather than erasing
  them;
- avoid prescribing a second authority during staged migrations;
- give every iteration item measurable acceptance and deletion criteria.
