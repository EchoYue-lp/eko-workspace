## Claim

Every long-lived EKO interaction mode starts the common unattended services
needed for cron, background submissions/recovery, plugin monitors, and Dreaming.

## Method

For each runtime branch, trace from `src/main.rs` or `src/tauri/desktop.rs` to
the only callers of `start_task_service`, `start_scheduler_with_store`,
`PluginRuntimeService::bind_scheduler`, and `spawn_dreaming_task`. Cross-check
the pure `--channels` branch against `run_channels_mode`'s full parameter list
and body.

## Expected Result

GUI, TUI, CLI, pure channel, and CLI+channel processes all retain one scheduler
and background service; attended surfaces start Dreaming, while the long-lived
channel surface has an equivalent unattended lifecycle policy.

## Result

- Exit code: not-applicable
- Duration: not-applicable
- Summary: GUI starts TaskService, SchedulerRunner, plugin scheduler monitors,
  MCP health polling, and Dreaming. TUI starts TaskService and SchedulerRunner
  through `start_headless_services`, binds plugin monitors, and starts Dreaming
  in `run_tui`. CLI does the same and starts Dreaming in `run_repl`.
  CLI+channel inherits these services from the CLI branch. Pure channel starts
  none of TaskService, SchedulerRunner, plugin scheduler monitors, MCP health,
  or Dreaming: `src/main.rs:365` calls `run_channels_mode` directly, while the
  only headless service call is inside `run_cli_mode` at `modes.rs:83`.
- Log/artifact: task report mode matrix

## Deviations

MCP health polling currently writes GUI `AppState` projection consumed by
Tauri IPC, so its absence alone is not treated as a channel parity defect.
Scheduler/background/Dreaming are runtime capabilities and do form a defect.

## Conclusion

The claim is false. Pure channel mode is build-reachable (V04) but skips the
common unattended-service composition. Supports B-PATH-01-P1-01.

## Follow-Up

than adding another independent scheduler.
