## Claim

Every composition root that starts `SchedulerRunner` or
`BackgroundTaskService` explicitly signals those services to stop during
orderly shutdown.

## Method

Search current EKO and framework scheduler sources for all construction and
all cancellation calls involving `AppState.scheduler.cancel_token`,
`AppState.tasks.cancel_token`, `SchedulerRunner`, and `BackgroundTaskService`.
Trace shutdown blocks in GUI, TUI, CLI, and pure-channel paths.

## Expected Result

Before runtime/service owners are dropped, both service tokens are cancelled
and any owned background handles are awaited or otherwise deterministically
terminated.

## Result

- Exit code: not-applicable
- Duration: not-applicable
- Summary: `AppState` creates independent scheduler and task cancellation
  tokens at `state.rs:540-546` and passes clones into services at `:662` and
  `:692`. The only startup-level `.cancel()` calls target the separate config/
  Dreaming/MCP watcher token (`src/main.rs:336,400,445` and
  `desktop.rs:261`). No `Drop` implementation or explicit call cancels
  `scheduler.cancel_token` or `tasks.cancel_token`. `start_headless_services`
  drops its temporary `AppState` immediately after returning service Arcs, so
  no retained state object can later expose those tokens.
- Log/artifact: none

## Deviations

Process/runtime teardown eventually aborts Tokio tasks, so this does not prove
tasks survive process exit. It proves orderly service cancellation is absent
and embedded/tested shutdown cannot be awaited deterministically.

## Conclusion

The claim is false. Supports B-PATH-01-P2-03; detailed failure rollback and
cleanup semantics belong to `A-BOOT-01`.

## Follow-Up

`A-BOOT-01` should introduce or identify one retained application service
lifecycle owner and test explicit stop/join behavior.
