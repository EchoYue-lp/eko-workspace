## Claim

The two `main()` entry points (`echo-agent-cli/src/main.rs` for the
`echo-agent-cli` binary and `echo-agent-cli/src-tauri/src/main.rs` for the
`echo-agent-tauri` binary) dispatch to TUI, GUI, CLI, channels, and cron
background capabilities through a small set of `#[cfg(feature = ...)]` gates
that can be fully enumerated from the source.

## Method

Read-only static trace of every `main()` call graph and every
`#[cfg(feature = ...)]` gate on entry paths, anchored to file:line. No code
was executed; the binary was not built. Inspection procedure:

1. Read `echo-agent-cli/src/main.rs` in full (572 lines) and recorded each
   `#[cfg]` gate plus the function it brackets.
2. Read `echo-agent-cli/src-tauri/src/main.rs` in full (7 lines) and traced
   the call into `echo_agent_cli::tauri::desktop::run_desktop_entry`.
3. Read `src/tauri/desktop.rs::run_desktop_entry` (1-122) and
   `run_desktop` (124-271) to map the GUI composition sequence.
4. Read `src/cli/modes.rs` (1-235) to map `start_headless_services`,
   `run_cli_mode`, and `run_channels_mode`.
5. Grepped both `src/` trees for every `#[cfg(.*feature` occurrence to
   enumerate feature gates.

## Expected Result

Two `main()` entry points; one unified headless dispatch
(`run_tui_or_cli_entry`) covering TUI/CLI/channels via runtime flag, and one
GUI dispatch (`run_desktop_entry`); at most a handful of `#[cfg]` gates
gating whole modules or function bodies, all enumerable from the source.

## Result

- Exit code: not-applicable (static inspection only).
- Duration: not-applicable.
- Summary: confirmed. Two binaries, two `main()` functions, two feature-gated
  dispatch trees, and one shared composition root
  (`echo_agent_app_core::runtime::AgentRuntime::bootstrap`). Full call graph

### Cron reachability

There is no dedicated cron binary. Cron is reached only through the in-process
`SchedulerRunner`, which is started by:

- `AppState::start_scheduler_with_store` (`state.rs:644-675`) — called by
  `start_headless_services` (modes.rs:62, TUI+CLI) and by `desktop.rs:232`
  (GUI).
- The runner type is the framework's `echo_agent::scheduler::SchedulerRunner`
  aliased at `echo-agent-app-core/src/scheduler/runner.rs:23`. The fire
  function `build_fire_fn` (`scheduler/runner.rs:47-`) routes every cron
  fire through `launch_cron_run` (Phase 3.1 unification).

Channels-only mode (main.rs:357-405 with `run_channels` set but
`run_cli` false) does NOT call `start_headless_services`; it spawns
`cli::run_channels_mode` directly and awaits `shutdown_signal`. As a
result, in pure channels mode the in-process scheduler and
`BackgroundTaskService` are NOT started.

## Deviations

None for the claim itself. One ambiguity worth recording:

- `run_tui_or_cli_entry` is gated `any(feature = "tui", all(feature =
  "channels", not(feature = "gui")))`. With default features (`tui` on,
  `gui` off, `channels` off) the function is compiled and `main` enters
  via the `#[cfg(feature = "tui")]` branch (line 78). With
  `--features gui --no-default-features`, `main` takes the GUI-only
  shortcut at line 75 and never reaches `run_tui_or_cli_entry`. With
  `--features channels --no-default-features` (and not `tui`), the
  channels-only branch at line 83 reaches it. The three branches are
  mutually exclusive, matching the `compile_error!` guard.

## Conclusion

The entry-point call graph and feature gates are fully enumerable from the
source. Both binaries route through `echo_agent_app_core::runtime::AgentRuntime::bootstrap`
for shared composition; downstream service startup differs by mode
(see V02 and V04 for the composition and parity analysis). The claim is
supported.

This result does not prove:
- that any mode actually runs end-to-end (no compile/run was attempted);
- parity between modes (covered by V04);
- reachability of every registered IPC handler (covered by V03).
