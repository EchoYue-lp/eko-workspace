## Claim

A checkpoint returned before a file mutation preserves that file's exact prior
working-tree state and rollback is scoped to that mutation.

## Method

```text
1. Trace create_checkpoint from write_file, edit_file, and delete_file.
2. Compare the object tagged with the state being mutated.
3. Inspect rollback pathspec scope, untracked/staged handling, tag identity, and
   failure reporting.
```

## Expected Result

The checkpoint preserves dirty/staged/untracked bytes for the target, has a
collision-free identity, and restores only the intended mutation.

## Result

- Exit code: not-applicable (static Git state proof)
- Duration: approximately 4 minutes
- Summary: create_checkpoint tags only current HEAD, not working-tree or index
  state. Tags use second-resolution names. rollback_to_checkpoint runs
  `git checkout <tag> -- .`, replacing all tracked paths in the repository while
  not restoring an untracked file. Thus the advertised safety handle can omit
  the target's true prior bytes and destroy unrelated local edits.

## Conclusion

The checkpoint/rollback contract is false for ordinary dirty repositories and
rollback can cause unrelated data loss. Supports `F-EXT-02-P0-01`.

## Follow-Up

Future regression must cover dirty tracked, staged, untracked, deleted, renamed,
multiple mutations within one second, two files, and rollback of only one tool
operation.
