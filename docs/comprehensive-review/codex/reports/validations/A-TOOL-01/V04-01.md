## Claim

Task plan `allowed_tools` are validated against the selected Subagent's real executable capability.

## Method

Traced framework `task_create/task_update` through `EkoTaskToolPolicy::validate_candidate`, `TaskCapabilityCatalog`, Subagent catalog snapshots, TaskRuntime dispatch, and framework `invocation_disabled_tools`. Compared primary full-tool registration with readonly/writer Subagent construction.

## Expected Result

Validation rejects any tool absent or disabled on the selected role and distinguishes an omitted/unrestricted allowlist from an explicit empty list.

## Result

- Exit code: 0 for all inspections.
- `TaskCapabilityCatalog` stores one set copied from the main Agent's tool names and validates every task against it, independent of `agent_role`, readonly status, plan mode, sandbox removal, and Subagent-specific Browser/tool installation.
- `SubagentCatalogSnapshot` records readonly/isolation/delegation metadata but no executable tool set.
- A readonly role can therefore accept `allowed_tools: ["shell"]` because `shell` exists on the main Agent. At dispatch, the readonly Agent does not contain `shell`; framework allowlist derivation disables every tool it does contain.
- Writer roles likewise pass validation for tools hidden by their permanent plan mode.
- Existing tests cover unknown global names and task-control names, not role/tool compatibility.

## Deviations

An empty list is treated by the framework as unrestricted rather than no tools; that generic semantic is dependency-owned. The application finding is that its plan policy does not validate against the target runtime surface.

## Conclusion

Failed. Supports A-TOOL-01-P1-02.
