## Claim

SQLite operations are async-runtime safe and transaction failure always restores
the shared connection to an unambiguous usable state.

## Method

Inspect connection ownership, lock types, all database operations inside
BoxFutures, PRAGMA/busy settings, and every BEGIN/ROLLBACK/COMMIT branch.

```text
1. Compare SqliteStore Mutex<Connection> with SqliteConversationStore's mutex.
2. Trace lock acquisition to every synchronous rusqlite prepare/query/execute.
3. Trace save_messages manual transaction failure and commit branches.
4. Inspect multi-instance busy_timeout/foreign_keys settings.
```

Environment: static async/transaction state inspection; no concurrency fixture.

## Expected Result

Blocking SQLite I/O does not occupy async executor threads, and a rollback or
commit error is handled without leaving the reusable connection in an active or
unknown transaction.

## Result

- Exit code: 0 for inspection; claim failed
- Duration: not recorded
- Summary: both stores execute synchronous rusqlite work directly inside async
  trait futures while holding one connection lock. Long scans/locks therefore
  block executor threads; SqliteStore additionally uses `std::sync::Mutex`.
  SqliteConversationStore `save_messages` manually issues BEGIN/ROLLBACK/COMMIT,
  ignores every rollback result, and returns directly on COMMIT error, so the
  shared connection can remain in an unknown/active transaction for later calls.
  Conversation connections set neither busy_timeout nor an equivalent retry,
  so independently opened instances can fail immediately under write overlap.
- Log/artifact: this report

## Deviations

One connection per instance serializes its own operations and prevents internal
concurrent use of that connection. It does not solve executor blocking or
cross-instance contention.

## Conclusion

This supports F-MEM-02-P1-02 and F-MEM-02-P2-01. It does not quantify latency.

## Follow-Up

Future regression: concurrent handles plus forced insert/update/commit failures;
after every error, a new transaction and query must succeed without blocking the
runtime worker pool.
