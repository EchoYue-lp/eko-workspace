## Claim

Every plugin component category has an identifiable framework mechanism, EKO
policy owner, source identity, and live storage owner.

## Method

```text
Inspect committed echo-agent src/plugin.rs, ReactAgent Skill/Subagent/MCP
capabilities, HookSource, and plugin lifecycle types. Inspect EKO
plugin_components.rs, plugin_runtime.rs, runtime.rs, agent_pool.rs, scheduler,
LSP and surface command entry points. Classify Skills, Tools, Hooks, MCP,
Subagents, LSP, monitors, themes and output styles by owner and storage shape.
Search both repositories for parallel PluginIntegrator, PluginRuntimeService,
WiredPluginComponents, PreparedApplicationComponents, source tags and
registration/unregistration APIs.
```

## Expected Result

Generic source-scoped mechanics should remain in the framework; EKO-only
construction and presentation policy should remain in the application; an
adapter should preserve ownership without becoming a second generic registry.

## Result

- Exit code: 0
- Duration: static inspection; not timed
- Summary: framework `PluginIntegrator` owns generic Skill/Hook/MCP assembly and
  returns per-plugin receipts. EKO's single `PluginRuntimeService` owns Subagent,
  LSP, monitor, theme, output-style and lifecycle policy. ToolManager and
  HookRegistry are shared Arcs across AgentPool; SkillRegistry,
  SubagentRegistry, intent routing and context projections are per Agent.
  `PreparedApplicationComponents` carries source identity within category
  entries and is replaced as a whole generation. No second EKO plugin runtime
  owner was found.
- Log/artifact: this report

## Deviations

Framework receipt defects and application output-style propagation are already
owned by F-PLG-01 and A-PLG-01 respectively; this validation does not reopen
them.

## Conclusion

Repository layering is broadly appropriate, but the mixed shared/per-Agent
storage model requires an explicit cross-Agent generation adapter. This report
supports the ownership basis for X-PLG-01-P1-01.
