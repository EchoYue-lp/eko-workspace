## Claim

Every registered tool reaches model schema publication and execution through a
single, collision-explicit registry path.

## Method

Traced `register_all_tools`/`register_readonly_tools`, core tool registration in
`ReactAgent::new`, builder custom-tool registration, `ToolManager::get_openai_tools`,
`ToolSearchTool`, and both normal and streaming execution methods. Searched all
`.register`, `register_tools`, `add_tool`, `remove_tool`, and `replace_tool`
call sites in both repositories.

## Expected Result

Registration rejects or reports duplicate names, schema snapshots are
invalidated, and the selected definition and executable always refer to the
same explicit registration decision.

## Result

- Exit code: 0
- Duration: static inspection
- Summary: builtins are registered first, then builder custom tools call
  `add_tool`; `ToolManager::register` uses `DashMap::insert` and discards the
  replaced value. `ToolRegistrar::register` cannot report a collision.
  `ReactAgent::replace_tool` exists as the separate documented replacement API,
  but ordinary `add_tool` already performs an unreported replacement.
- Log/artifact: this report

## Deviations

The definition cache is version-invalidated on insert/removal, so the schema
does eventually reflect the last inserted implementation. The failure is the
unreported ownership/selection change, not a stale schema cache claim.

## Conclusion

The claim failed and supports F-EXT-01-P1-02. A custom or extension tool can
silently replace framework-reserved tools such as `final_answer` or
`tool_search`; the caller cannot distinguish registration from replacement.

## Follow-Up

Add static and executable regression coverage for duplicate builtin/custom/MCP
names when fixes are implemented.
