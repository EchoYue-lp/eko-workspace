## Claim

The shared `PageInfo` contract exposes `next_cursor` to the model on every
paginated tool result so later pages are reachable.

## Method

Traced `PageRequest::paginate` and `PageInfo::apply_to` through all ten static
`apply_to` call sites, representative `web_search`/`grep`/`glob` outputs, the
pipeline truncation stage, `ToolCallFailure` projection, and every live
`Message::tool_result` constructor in the ReAct paths.

## Expected Result

A truncated first page supplies an opaque continuation cursor in model-visible
content or a structured tool-result message, without requiring UI-only
metadata access.

## Result

- Exit code: 0
- Duration: static inspection
- Summary: `PageInfo::apply_to` writes `page.next_cursor` only into
  `ToolResult.metadata`. Generic collection tool output contains page items and
  counts, but not the cursor. The live pipeline returns only `ctx.output`, and
  `Message::tool_result` accepts only a text string; metadata is not projected.
  `web_search` explicitly tells the model to reuse `page.next_cursor` that the
  model never receives.
- Log/artifact: this report

## Deviations

`read_artifact` uses a separate cursor format and embeds its cursor directly in
the output notice, so complete artifact pagination is not affected by this
specific defect.

## Conclusion

The claim failed and supports F-EXT-01-P1-04. The shared pagination mechanism
can produce later pages, but its normal model consumer cannot discover the
continuation key.

## Follow-Up

Validate all paginated tools through the real model-message projection after a
single canonical page envelope is introduced.
