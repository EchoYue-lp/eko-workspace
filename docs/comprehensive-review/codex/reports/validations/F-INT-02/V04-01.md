## Claim

`SessionHandler` serializes one conversation, and reset/timeout/end callbacks occur only after owned work is cancelled or completed.

## Method

Static lock and ownership analysis of `get_or_create`, `resolve_session_dispatch`, `handle`, and `handle_stream`.

## Expected Result

Concurrent messages for one session have defined ordering; reset/timeout cannot replace or clean a handler still executing; idle sessions are eventually reclaimed with a typed end reason.

## Result

- Exit code: 0
- The per-session mutex is released after cloning the handler and before `handle`/stream consumption (`session.rs:315-337,343-382`). Multiple messages therefore execute concurrently on the same handler without session ordering.
- A reset removes the map entry and fires `on_session_end` immediately, but an in-flight call can still own the old `Arc<dyn MessageHandler>` (`session.rs:297-311`).
- Timeout similarly calls the end callback and replaces the handler while prior work may continue (`session.rs:318-337`). No cancellation token or join is owned.
- Timeout cleanup is opportunistic only on the next message; inactive sessions otherwise remain in the map, and Drop has no end notification.

## Conclusion

Failed. The map entry is synchronized, but the actual session execution lifecycle is not.

## Future Validation

Use a blocking handler to overlap messages, reset, timeout, and drop; assert ordering, cancellation/join, exactly-once end callback, and no retained idle sessions. Not run by instruction.
