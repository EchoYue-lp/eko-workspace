## Claim

Channel session and reply conversion preserves the platform conversation identity for both direct and group messages.

## Method

Trace `InboundMessage.channel_id/sender_id/chat_id/chat_type/message_id` through `SessionHandler`, the root `AgentChannelHandler`, EKO `AppChannelMessageHandler`, and QQ/Feishu outbound address selection.

## Expected Result

The canonical session key includes the conversation context needed to prevent cross-chat history reuse, and group replies target `chat_id` while direct replies target the direct peer.

## Result

- Exit code: 0
- `InboundMessage` explicitly distinguishes sender and chat IDs (`types.rs:74-90`).
- `SessionKey` and lookup use only `(channel_id, sender_id)`, ignoring `chat_id` (`session.rs:158-159,295`). The same sender in separate groups therefore shares one handler/history.
- Reset replies target `sender_id` even when `chat_type` is Group (`session.rs:306-311`).
- Root and EKO handlers also construct replies to `sender_id` (`src/channels.rs:118-123`; `cli/channels.rs:85-99,121-127`), and EKO pool/cache identity likewise excludes `chat_id` (`cli/channels.rs:65-72`).
- Concrete QQ and Feishu send adapters select a group endpoint/type but pass `OutboundMessage.to` as the group identifier, so the sender value is not a lossless group target.

## Conclusion

Failed. Group conversations can share agent context across chats and their replies/reset acknowledgements can be addressed to a user ID where a group/chat ID is required.
