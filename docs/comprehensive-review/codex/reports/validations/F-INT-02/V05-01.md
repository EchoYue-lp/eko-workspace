## Claim

QQ background receive/send tasks are owned, stopped, and observable through the plugin lifecycle.

## Method

Static task ownership and channel-closure analysis of `QqChannel::start/stop/health_check` and the gateway loop.

## Expected Result

Each spawned task has an owned handle/cancellation path; receiver closure terminates; stop awaits cleanup; repeated start cannot orphan earlier tasks; health includes all owned work.

## Result

- Exit code: 0
- The send task handle is assigned to local `_send_task` then discarded (`qq/channel.rs:105-132`).
- Its `loop { if let Some(msg) = recv().await { ... } }` has no `else`/`break`. Once all senders drop, `recv()` immediately returns `None` forever and the detached task becomes a hot CPU loop (`qq/channel.rs:108-131`).
- `stop` aborts only the gateway task, drops one sender, does not abort/await the send task, and reports success (`qq/channel.rs:198-207`).
- Repeated `start` overwrites both channel state and gateway handle without first stopping prior tasks. `health_check` observes only the latest gateway, not the sender task (`qq/channel.rs:225-239`).

## Conclusion

Failed. QQ shutdown can leave an unobservable infinite task consuming CPU, and restart/double-start can accumulate orphaned work.
