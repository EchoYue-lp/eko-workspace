## Claim

Opening a diagnostic group includes both its root trace and all child traces, so
summary status/usage and detail status/usage describe the same lifecycle facts.

## Method

```text
Compare list_diagnostic_runs grouping with load_run_diagnostics retrieval.
Use the framework RunStore contract from committed HEAD: a root Run has
parent_run_id=None and child Runs have parent_run_id=<root/business run ID>.
Trace the case where both the root and at least one child exist, then inspect
aggregate status, usage, input preview, and trace listing.
```

## Expected Result

For diagnostic ID R, detail loads R plus every run whose parent_run_id is R;
summary and detail aggregate the same member set.

## Result

- Exit code: 0
- Duration: static data-flow inspection; not timed
- Summary: listing puts the root summary in group R and each child in group R.
  Detail first loads only `list_by_parent_run(R)`; it loads R itself only when
  that child list is empty. Therefore any group with children omits the root
  trace from details while the list summary includes it. Root status, usage,
  events, input, and timing can disagree between the two projections.
- Log/artifact: this report

## Deviations

The existing parent projection test stores only two child runs and no root, so
it cannot detect this mismatch.

## Conclusion

The diagnostic membership invariant fails and supports A-OBS-01-P1-05.

## Follow-Up

Load the root independently, merge children by run ID, define deterministic
ordering, and regression-test root-only, child-only, root-plus-child, duplicate,
and partial-load cases.
