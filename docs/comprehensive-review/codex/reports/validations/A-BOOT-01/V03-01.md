## Claim

Desktop startup failures propagate to both GUI binary entry points as an error
exit and every resource started before a fallible bootstrap step is rolled
back.

## Method

Trace both GUI binary callers into `run_desktop_entry`, every fallible return
from `run_desktop`, and the ordering inside `AgentRuntime::bootstrap`. Inspect
browser defaults, prewarm behavior, explicit shutdown, `McpClient` transport
cleanup, and whether bootstrap owns a rollback guard.

```text
rg -n "run_desktop_entry|run_desktop\(\)\.await|BrowserRuntime::start|browser_runtime.shutdown|impl Drop for StdioTransport" echo-agent-cli echo-agent -g '*.rs' -g '!target/**'
```

## Expected Result

An error before Tauri begins running is logged for diagnostics, all already
started process resources are synchronously shut down, and the error remains
visible to `main` so the process exits unsuccessfully.

## Result

- Exit code: `0`
- Duration: under 1 second
- Summary: the dedicated Tauri binary returns
  `runtime.block_on(run_desktop_entry())` (`src-tauri/src/main.rs:3-5`), and the
  package-name GUI-only binary returns the same future (`src/main.rs:72-76`).
  `run_desktop_entry` logs any `run_desktop` error but unconditionally returns
  `Ok(())` (`src/tauri/desktop.rs:94-121`), so both callers report success.
  Separately, `AgentRuntime::bootstrap` starts the browser runtime at
  `runtime.rs:93-100` before the fallible agent construction at `:102-105`.
  Browser is enabled by default and immediately spawns managed-sidecar prewarm
  (`browser/config.rs:106-124`, `browser/mod.rs:66-102`). No rollback guard or
  error branch calls `BrowserRuntime::shutdown`. Its MCP stdio Drop only spawns
  another async kill/wait task (`echo-integration/src/mcp/transport/stdio.rs:
  270-280`), which is not an awaitable guarantee when the outer Tokio runtime
  is about to terminate.
- Log/artifact: none

## Deviations

No real Playwright sidecar was launched and no intentionally invalid GUI
configuration was executed, because that would mutate user runtime files and
invoke platform UI. The control-flow result and missing rollback are static
facts; whether a particular failed boot leaves a child alive depends on timing.

## Conclusion

The claim is false. Error-status suppression supports `A-BOOT-01-P1-02`.
Prewarm-before-fallibility without an awaitable rollback supports
`A-BOOT-01-P1-03`.

## Follow-Up

Make desktop logging preserve `Err`; give bootstrap an owned rollback guard or
defer prewarm until construction commits. Add an isolated child-process fixture
that forces failure after prewarm and asserts non-zero exit plus child cleanup.
