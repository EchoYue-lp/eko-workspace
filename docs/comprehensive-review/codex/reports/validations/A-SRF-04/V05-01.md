## Claim

Channel-only startup launches the same BackgroundTaskService and SchedulerRunner
as CLI/TUI so persisted background/cron automation remains live.

## Method

```text
Trace each main-mode branch into start_headless_services, start_task_service,
start_scheduler_with_store, plugin scheduler binding, run_cli_mode, and
run_channels_mode. Compare function parameters and retained service handles.
```

## Expected Result

Every long-lived headless trigger host starts/recoveries both services exactly
once and exposes the same automation management capability.

## Result

- Exit code: not-applicable
- Duration: static inspection
- Summary: TUI calls `start_headless_services` at `src/main.rs:258-275`; CLI
  calls it at `src/cli/modes.rs:83-100`. Channel-only startup directly spawns
  `run_channels_mode` at `src/main.rs:357-371`. That function receives only
  pool/config/TaskRuntimeStore/review/webhook and never starts or retains a
  BackgroundTaskService/SchedulerRunner (`src/cli/modes.rs:118-234`). It also
  has no `/cron` management command. Persisted scheduled work therefore has no
  tick loop in a channel-only process.
- Log/artifact: this report

## Deviations

When `--channels --cli` is used together, CLI happens to start the services;
the defect is the supported channel-only daemon path.

## Conclusion

The claim fails and supports A-SRF-04-P1-02. This is startup composition, not a
new scheduler authority or a duplicate of A-TSK-03 execution findings.

## Follow-Up

Use one process lifecycle owner that starts shared headless services once before
launching any CLI/channel host; test restart recovery and channel-only cron fire.
