## Claim

A group-channel message uses `chat_id` for conversation/session identity and
for its outbound destination while retaining `sender_id` as actor identity.

## Method

```text
1. Inspect InboundMessage field semantics and QQ/Feishu group construction.
2. Trace SessionHandler key creation and AppChannelMessageHandler pool/cache/
   conversation keys.
3. Trace outbound `to` into QQ group URL and Feishu receive_id_type.
4. Check tests for two chats with the same sender and group reply targets.
```

## Expected Result

The same user in two groups has two independent conversations/HITL contexts,
and a reply targets the inbound group chat ID.

## Result

- Exit code: not-applicable
- Duration: static inspection
- Summary: framework input explicitly carries `chat_id` as group ID
  (`echo-integration/src/channels/types.rs:74-90`), and QQ/Feishu populate it.
  `SessionHandler` nevertheless keys only `(channel_id,sender_id)` at
  `echo-integration/src/channels/session.rs:295`. The app repeats that key for
  AgentPool, conversation, cache, memory, TaskRuntime, and HITL at
  `src/cli/channels.rs:65-72,131-149`. All output chooses `sender_id` as `to`
  (`:85-98,:121-128,:287-291`). QQ group sends to `/v2/groups/{to}` and Feishu
  labels `to` as `chat_id`, so both need the discarded group chat ID. Existing
  tests assert only the sender-based format.
- Log/artifact: this report

## Deviations

Direct messages are unaffected because their `chat_id` equals sender identity.

## Conclusion

The claim fails and supports A-SRF-04-P1-01. Group replies can target an invalid
ID, and the same sender's group conversations share agent history, memory,
TaskRuntime identity, and pending HITL state.
