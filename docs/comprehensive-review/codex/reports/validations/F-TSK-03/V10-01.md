## Claim

Each actual retry attempt receives a distinct TaskClaim/attempt identity and is
fenced independently.

## Method

```text
Trace ManagedTaskDagController claim -> dispatch_task -> execute_selected_task ->
run_task_with_retry across a first failure and second execution; compare claim,
current_attempt, hook/event attempt, TaskExecutionResult.attempts, and resolve.
```

## Expected Result

Attempt N+1 cannot execute under attempt N's lease; durable identity and
terminal result agree on the physical attempt.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not measured
- Summary: controller creates one claim before dispatch and then ignores its
  `_claim` argument. `run_task_with_retry` may execute repeatedly while
  incrementing local `current_attempt`; no new claim is obtained between
  attempts. Resolution still fences and clears only the original claim, while
  result/hooks can report a later attempt number.
- Log/artifact: this report

## Deviations

EKO's controller requeues at a safe point and reclaims, so this finding concerns
the live generic framework TaskExecutor controller.

## Conclusion

The claim fails. Multiple possibly side-effecting executions share one durable
lease and execution identity, defeating per-attempt fencing. Supports
F-TSK-03-P1-04.

## Follow-Up

Move retry decisions to the runtime safe point or expose explicit claim renewal;
future regression must show different claim tokens for two executions.
