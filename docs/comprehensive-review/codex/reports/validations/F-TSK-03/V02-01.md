## Claim

Every claim is a unique fencing token for one physical dispatch lease, including
restart/requeue of the same task revision and attempt.

## Method

```text
1. Inspect TaskClaim fields, equality, execution_id, and all constructors.
2. Inspect EKO boot recovery/reset and claim retry_count behavior.
3. Compare old/new claims when Running -> Pending occurs without retry bump.
4. Inspect status-write fencing predicates.
```

## Expected Result

Reclaiming a task creates a token unequal to every prior dispatch token even if
revision/spec/attempt are unchanged.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not measured
- Summary: `TaskClaim` is exactly `(revision, attempt, spec_hash)` and
  `execution_id` derives from run/task plus revision/attempt. EKO boot recovery
  resets ordinary orphan Running to Pending without incrementing retry_count.
  Reclaiming the unchanged spec/revision therefore recreates an equal claim and
  equal execution_id. Status fencing compares structural equality only.
- Log/artifact: this report

## Deviations

Process restart normally kills old local futures, but delayed external/remote
dispatch completion can survive, and the public controller contract does not
restrict dispatch to process-local work.

## Conclusion

The claim fails. This is an ABA lease: a stale physical attempt can be accepted
as the newly current attempt. Supports F-TSK-03-P1-01.

## Follow-Up

Future regression with delayed old completion after restart/reclaim; it must be
Superseded even when logical retry_count did not advance.
