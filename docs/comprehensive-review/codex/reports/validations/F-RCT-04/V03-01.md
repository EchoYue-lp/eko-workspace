## Claim

Provider tool-call IDs are non-empty and unique before any event, side effect,
context insertion, or trace record is created.

## Method

```text
1. Inspect streaming delta assembly and build_tool_calls_from_map.
2. Search for empty/duplicate ID validation before run_tools dispatch.
3. Trace one empty ID through run_tools, execute_tool_with_policy, ExecuteStage,
   public events, context messages, trace, and checkpoint validation.
4. Trace two equal IDs at different provider indices through the same path.
```

## Expected Result

Invalid IDs are rejected or canonicalized once at the batch boundary and the
same canonical ID reaches every projection.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not measured
- Summary: processor entries default to empty IDs and `build_tool_calls_from_map`
  preserves them; no uniqueness check precedes dispatch. `run_tools` emits and
  stores the original ID. `ExecuteStage` independently replaces an empty local
  ID with a UUID at `pipeline.rs:475-502`, so ToolContext/trace use the generated
  ID while public ToolCall/ToolResult and message history retain empty. Equal
  non-empty IDs at different provider indices both execute. Checkpoint restore
  rejects duplicates at `state/mod.rs:194-203`.
- Log/artifact: this report

## Deviations

An empty ID is repaired only inside the per-tool pipeline, after the batch
identity has already escaped and without returning the generated ID to the
caller.

## Conclusion

The claim fails. Empty IDs split one execution across identities; duplicate IDs
can execute multiple side effects and poison recovery. Supports
F-RCT-04-P1-02.

## Follow-Up

Future regression: empty ID and two indices sharing one ID; assert zero tool
execution on duplicate and one canonical ID across event/context/trace.
