## Claim

Every checkpoint written during a tool batch is restorable and prevents replay
of already completed side effects.

## Method

```text
1. Trace assistant-with-tools insertion and per-result insertion in run_tools.
2. Enumerate save_runtime_checkpoint calls on success, error, cancel, and timeout.
3. Compare each saved message shape with AgentCheckpoint::restore_messages and
   validate_tool_message_pairing.
4. Trace resume_from_state_store and completed_tool_call_ids consumers.
```

## Expected Result

No persisted checkpoint contains an assistant call without exactly one matching
tool result; completed side effects have a durable replay guard before a batch
can be interrupted.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not measured
- Summary: `run_tools` pushes one assistant message containing all batch calls
  at lines 95-113. Error paths save immediately at 257-262 and 413-415;
  cancellation saves at 198-205, 295-300, 303-312, 330-338, and 418-422. If
  any peer remains, those checkpoints contain unmatched calls. Restore rejects
  them at `state/mod.rs:186-230`. The first guaranteed valid full-batch save is
  explicitly lines 426-429. A crash after a write completes but before that
  point has no per-call durable completion record used by resume.
- Log/artifact: this report

## Deviations

Trace records individual ToolResult events, but `resume_from_state_store` uses
checkpoint messages/completed IDs, not trace, to restore execution state.

## Conclusion

The claim fails. Mid-batch error/cancel can overwrite state with an unrestorable
checkpoint, while a crash before full completion can replay a completed
side-effecting call. Supports F-RCT-04-P1-01.

interrupt after the first completion and prove restart neither rejects the
