## Claim

A tool opting out of peer parallelism preserves its position relative to all
calls in the model-produced batch.

## Method

```text
1. Inspect Tool::allows_parallel_batch_execution contract and overrides.
2. Trace the stable provider-index order produced by build_tool_calls_from_map.
3. Trace run_tools partition and execution order for [parallel, serial,
   parallel] and [serial, parallel].
```

## Expected Result

Sequential means the call does not overlap peers and original order is honored
at dependency boundaries.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not measured
- Summary: calls start in provider-index order, but lines 115-126 partition
  them into two vectors. The entire concurrent vector executes first
  (`130-301`); serial calls execute afterward (`303-424`). Thus a serial first
  call runs after later parallel calls, and a serial middle call runs after a
  later parallel call. `task_create` and `task_update` are live examples that
  override the default true with false.
- Log/artifact: this report

## Deviations

Completion-order result insertion among calls explicitly allowed to run in
parallel is expected; this failure concerns reordering across a declared
non-parallel boundary.

## Conclusion

The claim fails. Revision/state-dependent calls can be reordered behind later
reads or writes, invalidating the meaning of the opt-out contract. Supports
F-RCT-04-P1-04.
