## Claim

The Tauri definition and ownership inventory identifies every command module,
managed state owner, setup hook, event bridge, and PTY manager without inventing
a second core service.

## Method

```text
1. Enumerate `src/tauri/commands/*.rs`, `ipc.rs`, `terminal.rs`, `state.rs`,
   `desktop.rs`, `mod.rs`, and `src-tauri` entry files.
2. Search `#[tauri::command]`, command modules, `.manage`, `.setup`, event names,
   TerminalManager, BrowserRuntime, AppState, service calls, and duplicate CRUD.
3. Search app-core/CLI/TUI for corresponding workflow, skill, worktree, browser,
   and terminal authorities.
```

## Expected Result

Commands are adapters over one `Arc<AppState>` plus genuinely desktop-local
resources; any product workflow owned only inside a command is visible.

## Result

- Exit code: 0
- Duration: static inspection
- Summary: 20 command modules plus `ipc.rs` and `terminal.rs` feed one
  `TauriState`. It owns the shared `Arc<AppState>`, shared `Arc<BrowserRuntime>`,
  and a GUI-local `TerminalManager`. Most task, workspace, analysis, memory,
  plugin, scheduler, hook, and worktree commands delegate to app-core services.
  Workflow CRUD/execution is the notable exception: `panels.rs:676-784`
  directly owns the in-memory record lifecycle, identity/timestamps, parser, and
  graph execution; no reusable application workflow service or TUI/CLI caller
  exists.
- Log/artifact: source anchors in the A-SRF-02 task report

## Deviations

The command file named `panels.rs` is a 2,000-plus-line collection of unrelated
product operations, so module boundaries alone do not establish thinness.

## Conclusion

The definition inventory is complete enough to support the layering boundary
and A-SRF-02-P2-05. It does not prove runtime registration; V02 does.

## Follow-Up

Primary review should sample one delegated command per module and the workflow
exception.
