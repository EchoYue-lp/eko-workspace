## Claim

Tauri commands remain thin, typed adapters and do not privately own a GUI-only
product workflow authority.

## Method

```text
1. Compare command bodies with app-core services and TUI/CLI call sites.
2. Trace `workflowApi` -> panel commands -> StoredWorkflow map -> framework Graph.
3. Compare Rust JSON response shapes with TypeScript WorkflowInfo and
   TerminalSession/close response types.
```

## Expected Result

Product lifecycle logic is reusable application service behavior; adapters
convert typed DTOs losslessly. GUI/TUI/CLI/channel differences are rendering,
not feature availability or a private store/executor.

## Result

- Exit code: 0
- Duration: static boundary comparison
- Summary: workflow create/delete/list/execute is entirely in Tauri
  `panels.rs:676-784`, directly mutating `AppState.history.workflows`, assigning
  identity/timestamps, parsing, and running framework Graphs. The live React
  `WorkflowPanel` reaches it, while no TUI/CLI workflow path or app-core service
  exists. The adapter also returns ad-hoc JSON inconsistent with the declared
  `WorkflowInfo`: create returns only `{success,id}` and list omits `definition`
  and `status`. Terminal endpoints similarly declare `cwd/created_at` and
  `{closed}` while Rust returns `id/pid` and `{success}`; those typed terminal
  fields are not currently consumed by the Tauri drawer.
- Log/artifact: this report

## Deviations

The terminal DTO mismatch is currently latent because the drawer uses raw
`apiInvoke` for the Tauri path and ignores responses. The workflow boundary is
live and user-facing, so it is the material finding.

## Conclusion

The claim fails and supports A-SRF-02-P2-05. It also records typed-contract debt
without promoting the currently latent terminal mismatch to a separate finding.

## Follow-Up

Move EKO workflow policy into one app-core service used by every surface; then
generate or shared-test exact request/response DTOs for workflow and terminal.
