## Claim

Tauri command state and lock/await usage does not introduce a second primary
Agent/AppState and generally releases state locks before unrelated awaits.

## Method

```text
1. Inventory `.lock().await`, `.read().await`, `.write().await`, DashMap, and
   AgentHandle read/write closures under src/tauri and src-tauri.
2. Inspect each nontrivial lock region around workspace switch, config update,
   MCP update/toggle, skill refresh, workflow execution, worktree merge, chat
   pending requests, and terminal operations.
3. Compare state.rs construction with desktop.rs service construction.
```

## Expected Result

One shared core state is managed; guards do not span arbitrary service/network/
filesystem awaits unless the lock is the intentional operation serializer.

## Result

- Exit code: 0
- Duration: static lock-region inspection
- Summary: `TauriState` wraps the desktop-created `Arc<AppState>` and
  `Arc<BrowserRuntime>` rather than constructing replacements. Configuration,
  MCP, skill, workspace, and workflow code generally scopes/drops RwLock guards
  before Agent/service awaits. Worktree merge locks intentionally span one
  `spawn_blocking` operation. PTY Mutexes protect only one writer/master/killer
  operation. Chat pending-response locking is already owned by A-HITL-01.
- Log/artifact: this report

## Deviations

layering deviation (V07), and PTY creation has an atomicity race outside Tokio
Mutex usage (V05).

## Conclusion

The shared-state and general lock/await claim passes. It supports a positive
state-owner conclusion, not lifecycle correctness of every owned resource.
