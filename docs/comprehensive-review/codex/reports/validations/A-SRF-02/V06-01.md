## Claim

The interactive terminal adapter never persists user keystrokes or pasted
credentials in diagnostic logs.

## Method

```text
1. Trace xterm onData -> UTF-8/base64 -> confirm_terminal_consent ->
   write_terminal -> decode -> tracing fields.
2. Trace GUI tracing initialization to persistent file sinks.
3. Inspect payload bounding and UTF-8 handling separately from confidentiality.
```

## Expected Result

Logs may record terminal ID, byte count, and outcome, but not content. Direct
user interaction must not be permission-gated as Agent automation.

## Result

- Exit code: not-applicable
- Duration: static data-flow inspection
- Summary: every accepted write decodes the user's exact bytes, retains the
  first 80 bytes, converts them lossily, and logs `preview = %preview` at info
  (`terminal.rs:323-355`). GUI tracing mirrors info events to append-only
  `~/.eko/logs/app.log` across restarts (`infra.rs:1592-1617,1651-1665`). A pasted
  token/password is stored verbatim up to 80 bytes; sequential keystroke records
  can reconstruct longer input. The byte bound and lossy conversion prevent
  oversized input/panic but do not protect secrecy.
- Log/artifact: this report

## Deviations

The per-session consent call is triggered automatically by the first genuine
keystroke, so it is not currently an Agent permission-mode gate. Its online-XSS
commentary is outside EKO's local threat model but is not itself the material
defect reported here.

## Conclusion

The claim fails and supports A-SRF-02-P0-01.

Delete content previews from terminal logs and validate paste and character-by-
character secret entry against captured tracing output.
