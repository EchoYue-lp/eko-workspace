## Claim

An EKO document selected for inline delivery remains available to the model
after the OpenAI-compatible adapter normalizes the message.

## Method

Trace one non-image `AttachmentRef` through
`PreparedUserTurn::build -> InputResourceRef(Inline) -> to_message ->
ContentPart::File -> OpenAiClient::normalize_messages`, and compare the final
wire-visible part with the original bytes/path/reference.

## Expected Result

The final request contains the document bytes/text or a durable model-readable
reference plus retrieval mechanism.

## Result

- Exit code: 0
- Duration: not separately measured
- Summary: short uploads are `Delivery::Inline`; `to_message` embeds base64 as
  `ContentPart::File`. The adapter decodes only an extension allowlist. Every
  other document (including PDF per its comment) becomes text containing only
  `[Attachment: name]`; neither bytes nor path survive. Existing unit test
  explicitly expects the binary name-only placeholder.
- Log/artifact: source anchors in the task report

## Deviations

This is a source-level data-flow validation because `normalize_messages` is
private. No remote model behavior is assumed.

## Conclusion

The inline-document capability invariant is false. This supports
F-LLM-02-P1-03.

## Follow-Up

Make delivery capability-aware before constructing `ContentPart::File`; retain
a retrieval reference when bytes cannot be represented by a provider.
