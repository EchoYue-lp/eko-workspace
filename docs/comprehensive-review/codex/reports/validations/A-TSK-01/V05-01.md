## Claim

The file layout has one operational authority per fact and can detect or repair a projection that is absent or stale relative to `events.jsonl`.

## Method

Trace all file read/write primitives and callers in `store.rs`, `file_store.rs`, `file_shadow.rs`, and `event_rebuild.rs`. Build the authority table from code rather than comments.

```text
rg -n "event stream is authoritative|events.*authoritative|read_plan\(|read_run_state\(|read_events\(|rewrite_plan\(|atomic_write\(|append_event_line\(" echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/{store.rs,file_store.rs,file_shadow.rs,event_rebuild.rs}
```

| Fact | Declared canonical source | Operational read source | Consistency marker |
|---|---|---|---|
| plan specification/revision | `PlanRevisionCommitted` in `events.jsonl` | `plan.json` | plan revision only |
| run and task execution | task/run events in `events.jsonl` | `run-state.json` | none linking to last event/plan revision |
| todo display metadata | task events | folded from `events.jsonl` | event order only |
| subagent attempt/result | assigned/released events | event fold / frontend projection | execution ID |

## Expected Result

Because comments declare the event stream authoritative and projections deterministic, read paths should detect missing/stale projections and rebuild from events, or transactions should make event plus all affected projections indivisible.

## Result

- Exit code: 0 for the search; claim failed by inspection
- Duration: ~10 minutes inspection
- Summary: Mutations append an fsynced event, return, then separately call `rewrite_plan`. `rewrite_plan` atomically writes each projection, but `plan.json` and `run-state.json` are separate renames. `FileTaskStore::load` directly reads projections and events; it does not invoke rebuild or compare a last-applied event sequence. `RunStateSnapshot` carries neither event sequence nor plan revision.
- Log/artifact: None.

## Deviations

Per-run locks serialize in-process writes and atomic rename prevents torn individual JSON projection files. They do not make event append plus two projection renames crash-atomic.

## Conclusion

The claim is false. A crash/error after append can leave missing, stale, or cross-revision projections that normal readers accept or treat as absent. Supports `A-TSK-01-P1-01`.
