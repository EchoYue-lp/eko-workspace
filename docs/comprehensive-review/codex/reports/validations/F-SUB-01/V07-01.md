## Claim

All public delegation entry points preserve attachment-bearing messages without
turning binary content into a text-only task.

## Method

Trace `MessageContent::Parts`, `as_text`, `filter_history`,
`with_compiled_task`, every production `DispatchRequest.message` constructor,
builtin `agent_tool`, and `execute_agent_streaming`. Inspect existing attachment
tests and comments. No fixture or test was executed.

## Expected Result

When the active user request has image/file/audio content, every supported
delegation route either forwards the original Message or rejects the operation
as unsupported.

## Result

- Exit code: 0
- Duration: static message-flow inspection
- Summary: the low-level multimodal API correctly stores `message: Some` and
  `with_compiled_task` replaces only text parts, preserving attachments. Fork
  history filtering clones a multimodal Message when it has text. However,
  builtin `agent_tool` always constructs `message: None`; Fresh is its default,
  so the active attachment is neither in inherited history nor in the dispatch
  request. The generic text-only helpers likewise set `None`. A source comment
  explicitly says end-to-end multimodal dispatch lacks an executable unit test.
- Log/artifact: this report

## Deviations

EKO TaskRuntime has a dedicated multimodal delegation method and can preserve
attachments when its caller selects that API. The finding concerns builtin
model dispatch and generic text helpers.

## Conclusion

The claim failed. Attachment preservation exists but is not part of the
primary `agent_tool` contract. Supports F-SUB-01-P1-04.

## Follow-Up

Carry the active Message in invocation context into builtin dispatch and add an
end-to-end trait-object regression case.
