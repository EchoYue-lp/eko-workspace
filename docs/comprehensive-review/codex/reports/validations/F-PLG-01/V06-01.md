## Claim

The plugin framework is a reasonable reusable public capability and EKO's live
adapter consumes it without moving product-only components into the framework.

## Method

Trace root/core exports and examples, then EKO runtime/bootstrap and GUI/TUI/CLI
plugin callers. Classify framework-owned and application-owned component types.

## Expected Result

Manifest/dependency/source ownership and lifecycle remain generic framework
mechanisms; EKO owns construction/policy for Subagents, LSP, monitors, themes
and output style and all interaction modes share one runtime service.

## Result

- Exit code: 0.
- The core registry/lifecycle and facade integrator are public, documented and
  demonstrated framework APIs. CLI non-use is not evidence for deletion.
- Skills, hooks and MCP are framework Agent components. EKO consumes resolved
  Subagent/LSP/monitor/theme/style files through `PluginRuntimeService` and does
  not put scheduler/UI policy into the framework.
- GUI, TUI and CLI paths reference one process-level PluginRuntimeService.
- EKO stages candidate application components, deactivates lifecycle callbacks,
  replaces all Agent components, and attempts whole-set restoration on failure.
- Existing dependency ordering/version checks, path traversal rejection, source
  tagged Skill unload and HookSource identity are positive controls.

## Deviations

Correct EKO compensation does not repair the weaker public framework contract
for other consumers; that distinction is captured in V04.

## Conclusion

Passed. Supports retaining the framework capability and the stated layering.
