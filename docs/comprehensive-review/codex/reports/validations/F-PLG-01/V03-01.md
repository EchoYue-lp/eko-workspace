## Claim

Plugin identity and persisted configuration remain bound to one deterministic
source across User, Project and Local scopes and after registry corruption.

## Method

Trace scope order, scan insertion keys, list/count behavior, state serialization
and state merge. Compare the documented `PluginId` format with actual keys and
inventory collision/corruption tests.

## Expected Result

Scope/source participates in stable identity or an explicit override record;
persisted config is bound to that source/version; corrupt state cannot silently
enable plugins that a user disabled.

## Result

- Exit code: 0 for static reads; source invariant failed.
- `PluginId` is documented as `name` or `name@scope` but is a String keyed only
  by manifest name. Scanning User -> Project -> Local inserts into one HashMap,
  so each later same-name entry silently replaces the earlier entry. Same-scope
  directory traversal is unsorted and also silently replaces.
- The returned discovery count increments for overwritten entries, while
  `count/list/get` see only the winner.
- `load_state` merges enabled/config by the same name into whichever scope won;
  it does not bind saved state to root, scope, version or manifest identity.
- Invalid/truncated JSON is warned and ignored. Scan defaults then remain live;
  `default_enabled: true` plugins can be re-enabled despite persisted user intent.
- No existing test covers cross-scope/same-scope duplicate names, configuration
  rebinding, corrupt state or count versus unique entries.

## Deviations

Local/project shadowing may be an intended precedence policy, but source-blind
state transfer and reported ownership are not an explicit or safe contract.

## Conclusion

Failed. Supports F-PLG-01-P1-01 and F-PLG-01-P1-06.

## Follow-Up

Use stable source-qualified identity plus a separate explicit precedence alias;
persist state against source/version and recover corruption visibly/fail closed.
