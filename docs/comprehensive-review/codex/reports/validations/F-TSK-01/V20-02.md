## Claim

The public task-tool parser must enforce the constraints advertised by its JSON schemas rather than silently changing malformed inputs into valid task graphs.

## Execution

Read-only line-numbered inspection of `echo-orchestration/src/tasks/task_tools.rs:225-619`, followed through `TaskRevisionService::create_from_tool` and `finalize_and_validate` in `revisioned.rs`.

## Result

The claim failed:

- `execution_mode` advertises only `parallel|sequential`, but any missing, non-string, or unknown value becomes `Parallel` (`task_tools.rs:419-425`).
- `max_retries` advertises an integer in `0..=10`, but negative, non-integer, too-large-for-`u32`, and absent values all become `3`; values above 10 but representable as `u32` also bypass the schema bound and can reach the validator configured independently (`task_tools.rs:544-548`).
- Every array helper filters non-string elements and returns an empty/default vector for wrong-shaped values (`task_tools.rs:590-619`). A malformed dependency list can therefore be committed as a different DAG.
- Unknown non-extension fields are ignored by the hand parser even though the advertised schema sets `additionalProperties: false` (`task_tools.rs:549-553`).

`finalize_and_validate` validates the already-normalized candidate, so it cannot recover facts discarded by parsing. Direct `Tool::execute` calls are public and are not guaranteed to have passed a provider-side schema validator.

## Impact

The schema is not the executable input contract. Invalid model/tool input may return success and persist a graph whose mode, dependencies, retry policy, or metadata differ from the caller's request.
