## Claim

The framework should expose one revisioned dynamic task graph authority, with richer task execution behavior adapting to it rather than owning a second mutable graph lifecycle.

## Execution

Read-only definition and consumer inventory across `tasks/task.rs`, `manager.rs`, `store.rs`, `executor.rs`, `revisioned.rs`, `runtime.rs`, `planning/plan_spec.rs`, facade exports, scheduler, hooks, and verifiers.

## Result

The claim failed, with an important deletion boundary:

- `TaskSpec + TaskExecution + TaskStatus`, `RevisionedTaskGraph`, and `TaskRevisionService` own immutable specs, CAS revisions, structural validation, and task relation tools.
- `ManagedTask + TaskManager + TaskStore` independently own mutable status, dependencies, persistence, pause/resume, and public one-wave execution. `TaskExecutor::execute_all` projects those records into the runtime DAG, but the legacy manager/store remain authoritatively mutable outside that projection.
- `PlanSpec` can compile to either `TaskSpec` or `ManagedTask`.
- The rich execution fields and verifier/hook/store implementations are reasonable framework capabilities and are not dead merely because a particular EKO path may not call them. The defect is parallel graph/revision/state ownership, not the existence of rich task records.

## Direction

Retain reasonable public execution policy and record capabilities, but make them consume/adapt the single revisioned task graph. State mutation, dependencies, ready frontier, and persistence identity must not remain independently authoritative in `TaskManager`/`TaskStore`.
