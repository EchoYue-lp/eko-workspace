## Claim

EKO's committed dependency feature selection does not enable or resolve SQLite,
while the independent framework retains SQLite as an optional capability.

## Method

```text
1. Inspect every CLI committed Cargo.toml for framework default-features,
   explicit features and SQLite/sqlx/rusqlite declarations.
2. Search committed CLI Cargo.lock for rusqlite/libsqlite3-sys/sqlx/sqlite
   package names.
3. Inspect framework root and echo-state manifests for default/sqlite features
   and optional dependency declarations.
```

## Expected Result

Both EKO packages use `default-features=false`, omit `sqlite`, and the committed
CLI lock resolves no SQLite package; framework definitions remain optional.

## Result

- Exit code: 0
- Duration: under one second
- Summary: CLI root selects framework features mcp/lsp/human-loop/subagent/tasks;
  app-core selects a larger explicit set, still without sqlite. Both set
  `default-features=false`; neither CLI manifest declares sqlite/rusqlite/sqlx.
  The committed CLI lock has no rusqlite, libsqlite3-sys, sqlx or sqlite package
  entry. Framework default features are empty; framework root `sqlite` forwards
  to `echo_state/sqlite` and optional bundled rusqlite; echo-state rusqlite is
  optional. Framework `full` includes sqlite, but EKO never selects `full`.
- Log/artifact: none

## Deviations

This is a committed manifest/lock proof, not a `cargo tree` execution. The live
modified CLI lock is intentionally irrelevant and excluded.

## Conclusion

The static SQLite absence invariant passes. Framework SQLite must be retained
as an independent optional implementation; CLI should continue not enabling it.
