## Question

Can representative Chat, Task, Subagent, tool, HITL, attachment, Browser/MCP,
restart, and large-output scenarios complete on applicable surfaces with
equivalent facts?

**Answer: partially — every scenario has a live code path on the surfaces that
own it, but equivalence fails on a consistent pattern of canonical P1s.** The
shared core (one `drive_chat`, one TaskRuntime store, one pool, one
`PreparedUserTurn`, one tool executor) is confirmed on all six entry classes.
The scenario matrix (V01-V46) shows: the GUI Chat scenario cannot produce
truthful terminals for error/cancel/timeout/interrupt turns; the Task
scenario cannot complete write work on any surface; the cron surface cannot
start any scenario automatically; HITL equivalence breaks on CLI (EOF
auto-approve), channel (cross-sender), and cron/background (auto-reject +
opaque escalation); Browser/MCP connect is broken or stubbed on GUI (panel +
persistence), CLI (stubs), and channel (no surface); restart continuity fails
on the CLI and channel surfaces (no conversation persistence; channels-only
services absent). Attachment, tool rendering, subagent dispatch/result, and
large-output fold/cursor pass at the code level on all applicable surfaces.
No P0-level defect is new to this task; the failures are scenario-level
syntheses of canonical findings, plus one new P2 (REPL restart continuity)
and one new P3 (frontend assistant-text has no fold/cursor — residual).

## Findings

### Q-E2E-01-P1-01: The GUI Chat scenario cannot complete with equivalent facts — error, cancel, timeout, and interrupt turns end 'completed' with wiped content or no terminal at all (synthesis of canonical A-SRF-03-P1-01/P1-02, X-EVT-01-P1-02, A-CHAT-01-P1-01)

- Priority: P1
- Confidence: high
- Layer: application (frontend reducer + adapter)
- Evidence: `web-frontend/src/hooks/chatEventHandler.ts:140-150` (error ->
  setRunStatus('failed') then finalize); `web-frontend/src/stores/chatStore.ts:
  354-362` (`finalizeAssistantMessage` unconditionally sets 'completed' and
  replaces content); `echo-agent-cli/src/tauri/commands/chat.rs:511-535`
  (interrupt early-return, no terminal for the ghost key), `:690-711`
  (TurnStatus derived from always-`Ok` drive_chat Result).
- Reachability: every GUI chat turn — success path fully wired; error/cancel/
  timeout/interrupt turns deterministically break the terminal-facts
  invariant (definition -> registration -> live caller chains in canonical
  reports; GUI is the flagship surface).
- Expected invariant: one truthful terminal per turn (completed/failed/
  cancelled/timeout); partial content survives error/cancel; interrupt leaves
  the input usable.
- Observed behavior: failed and user-cancelled turns end `runStatus
  'completed'` ("就绪") with the body replaced by `[Error] ...`; timeout has
  no typed terminal at any layer; an interrupt prompt strands the turn state
  and the input queues forever until reload.
- Impact: on the flagship surface, failure is shown as success, partial
  output is lost (and persisted wiped), and a documented user flow (message
  during a running task) makes the chat input dead; the scenario's
  "equivalent facts" clause fails on four terminal classes.
- Root cause: the frontend reducer conflates content finalization with
  terminal status and last-write-wins 'completed'; the backend interrupt
  branch returns without a lifecycle; the envelope collapses the typed
  timeout class (X-EVT-01-P1-02).
- Direction: canonical fixes first — A-SRF-03-P1-02 (split content/status;
  monotone terminal), A-SRF-03-P1-01 (roll back the optimistic turn on
  `kind:'interrupt_prompt'` or emit a terminal for the interrupted key),
  X-EVT-01-P1-02 (typed timeout terminal through the envelope + wire).
- Regression validation: the A-SRF-03 fixtures (error -> 'failed' with
  partial content; cancel -> 'cancelled' with no '[Error]' body; reload
  restores partial content; interrupt then send dispatches) plus the
  X-EVT-01-P1-02 timeout fixture.
- Validation reports: [V01-01](../validations/Q-E2E-01/V01-01.md)
