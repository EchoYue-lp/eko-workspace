## Claim

Every Tauri command is registered and reachable at runtime; every boot-time
event bridge spawns; registration and reachability are complete.

## Method

1. Counted `#[tauri::command]` annotations vs `invoke_handler` entries in
   `src/tauri/mod.rs` and checked each defined command name appears in
   `mod.rs` (registration completeness).
2. Traced the boot chain: `src-tauri/src/main.rs` -> `desktop::run_desktop_entry`
   -> `run_desktop` (desktop.rs:124-271) -> `build_tauri_app` (mod.rs:29) ->
   `.manage(TauriState)` -> `.setup(...)` x2 -> `.invoke_handler(...)` ->
   `.run(generate_context!())`.
3. Verified `Builder::setup` overwrite semantics against the vendored tauri
   2.11.2 source (`~/.cargo/registry/src/rsproxy.cn-*/tauri-2.11.2/src/app.rs`):
   `setup: SetupHook<R>` is a single non-Option Builder field (app.rs:1506);
   `pub fn setup(mut self, setup: F) -> Self { self.setup = Box::new(setup); }`
   (app.rs:1765-1769); the App takes `Some(self.setup)` (app.rs:2363) and
   `App::run` executes exactly one: `if let Some(setup) = app.setup.take() {
   (setup)(app) }` (app.rs:2522-2523).
4. Traced the two setup closures in `src/tauri/mod.rs`: first at :40-68
   (DevTools auto-open + `browser://event` forwarding loop from
   `TauriState.browser_runtime.subscribe()`), second at :311-772 (global
   shortcut + SubagentEventBus bridge persisting subagent tool executions and
   emitting `execution://event`).
5. Confirmed `browser://event` producer/consumer inventory: producer only
   `mod.rs:58` (inside the overwritten first setup); consumer
   `web-frontend/src/hooks/useBrowserEvents.ts:12` (listens and feeds
   `browserStore.ingest`); `BrowserPanel.tsx:14` mounts the hook; the browser
   view is created only by `ingest` on `session_started`/`session_updated`
   (browserStore.ts:114-131); `refreshFrame` polling requires an existing view
   (BrowserPanel.tsx:27-31). App-core browser session manager actively sends
   `BrowserEvent` into the broadcast channel (browser/session.rs:215,248,286,
   492,511).

## Expected Result

All commands registered; both setup closures execute; the browser event
stream reaches the frontend.

## Result

- Exit code: not-applicable (static trace)
- Duration: ~45 min
- Summary:
  - Registration: complete. 219 `#[tauri::command]` annotations, every
    function name appears in the single `invoke_handler` (mod.rs:69-310);
    terminal commands registered at mod.rs:304-309. No unregistered command.
  - `TauriState` managed once (mod.rs:39); the three managers
    (app_state/browser_runtime/terminal_manager) are built once in
    `TauriState::new` (state.rs:16-22).
  - **The first `.setup()` closure (mod.rs:40-68) is silently discarded.**
    Tauri's `Builder::setup` overwrites the single setup slot, and `App::run`
    executes only the last-registered closure (app.rs:2522). The second
    closure (mod.rs:311) is the one that runs (global shortcut +
    SubagentEventBus bridge). Consequences: (a) the `browser://event`
    forwarding task is never spawned — the sole producer for that channel is
    dead; the frontend listener (useBrowserEvents.ts:12) can never fire, so
    `browserStore` views are never created and the browser workspace panel is
    non-functional; (b) DevTools auto-open in debug builds never runs.
  - The SubagentEventBus bridge (second setup, mod.rs:353-768) is reachable
    and live: it subscribes to the framework event bus via
    `agent.read_async(...subagent_registry().event_bus().subscribe())`
    (mod.rs:354-358), persists tool start/finish/cancel into
    `ToolExecutionRepository` (mod.rs:416-529) and emits
    `execution://event` payloads (mod.rs:751-752).

## Deviations

The double-setup overwrite is a defect (P1-01 in the task report), not a
deviation of this validation. The claim "both setup closures execute" failed;
the claim "every command is registered" passed.

## Conclusion

Supports: complete command registration; TauriState single construction;
the second setup (shortcut + SubagentEventBus bridge) is the live boot bridge.
Proves: the first setup (browser://event bridge + DevTools) is unreachable
code at runtime, killing the documented `browser://event` contract. Static
proof only; a live GUI run would additionally confirm the panel stays empty.
