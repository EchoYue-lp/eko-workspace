## Claim

Tauri-command state/lock/await patterns are panic-safe and do not hold locks
across long awaits; command-local state is bounded; no await-order race
degrades a subsequent turn.

## Method

Static inspection of lock/await usage across `src/tauri/**`:

1. Lock inventory: `tokio::sync::{Mutex,RwLock}`, `std::sync::Mutex`
   (incl. `LazyLock` global), `DashMap` in command paths; check each guard's
   lifetime across `.await`.
2. Global state: `PENDING_RESPONSES` (chat.rs:212-213), bounded by
   request removal on response/timeout/cancel.
3. Race analysis: (a) `send_chat_message` HITL attach (chat.rs:575-582)
   vs old-turn HITL clear after Done (chat.rs:712-719), both via
   `agent_handle.write_async`; `set_human_loop_provider_preserving_approvals`
   fully replaces the provider (`echo-agent/src/agent/react/mod.rs:1617-1636`);
   (b) `TerminalManager::create` contains_key+insert (terminal.rs:216-231)
   non-atomic across concurrent commands.
4. Poison handling: `lock_std` recovers from poisoned std mutexes
   (chat.rs:1334-1339).
5. UTF-8/panic safety spot check of the touched adapter code (base64 decode,
   `chars().take`, no byte slicing of user text).

## Expected Result

No guard held across `.await` with a second lock acquisition that could
deadlock; bounded maps; no ordering race that silently swallows a user
request.

## Result

- Exit code: not-applicable (static inspection)
- Duration: ~60 min
- Summary:
  - Locks are short-lived: `mcp_config`/`app_config`/`permission_mode`/
    `tool_states` RwLocks are read-modify-dropped before awaits; the agent
    RwLock is held for whole-stream duration by design
    (`chat_driver.rs:459-460`, app-core, covered by A-CHAT-01). `lock_std`
    poison recovery prevents panics. No deadlock-shaped nesting found.
  - `PENDING_RESPONSES` entries are removed on response (`send_*_response`),
    on 300 s timeout (chat.rs:350-353, 385-388, 426-429) and on
    `cancel_pending_hitl` (chat.rs:236-257, called from `cancel_chat` and
    `cancel_task_run`/`pause_task_run`); bounded by concurrent HITL requests.
  - HITL clear race (medium confidence): the old turn emits
    `TurnStatus`+`Done` (chat.rs:709-711) and only then replaces the agent's
    HumanLoopProvider with an empty `HitlDispatcher` (chat.rs:712-719). A new
    turn for the same agent may pass the busy check (registry released at
    chat.rs:701-706), attach its own `TauriHumanLoopHandler` (chat.rs:575-582)
    and then have the old turn's clear overwrite it — the new turn's
    approval/input/selection requests then hit the empty dispatcher and time
    out at 300 s with no GUI prompt. The window is the time between Done and
    the old clear's write_async completion (auto-dispatched queued turns make
    it reachable).
  - Terminal create race (low impact): two concurrent `create_terminal` with
    the same id can both pass `contains_key` before either inserts; the loser
    is orphaned (its PTY master is dropped with the Arc, child typically dies
    via SIGHUP; its reader thread keeps running until EOF).
  - No byte-slicing/UTF-8 panic paths found in the Tauri adapter layer;
    base64 decode errors are mapped to `IpcError::Validation`; terminal
    preview uses `from_utf8_lossy` + `chars().take(80)` (terminal.rs:346-349).

## Deviations

`write_terminal` holds the session writer std-mutex guard only across a
synchronous `write_all`/`flush` (terminal.rs:173-180) — acceptable. The
HITL-clear race and terminal duplicate-id race are recorded as findings
(A-SRF-02-P3-02, A-SRF-02-P3-03).

## Conclusion

Supports: panic-safe lock usage, bounded per-command state, no deadlock
shape. Identifies two narrow races (HITL provider clear; terminal id
duplication). Does not prove runtime lock contention under load (Q-PERF-01
scope).
