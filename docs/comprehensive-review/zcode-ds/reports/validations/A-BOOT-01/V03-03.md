## Claim

Every entry point's shutdown sequence cancels background work (config watcher,
Dreaming, MCP health, task hook dispatcher, browser runtime, scheduler, task
service, PTY terminals) consistently and completely before returning.

## Expected Result

All long-lived loops are cancelled/stopped on exit; ordering is consistent
across entries; no dead cleanup API.

## Result

- Exit code: not-applicable (static trace)
- Summary:
  - Task hook dispatcher shutdown (`shutdown_hook_events`) runs on all four
    paths (TUI/CLI/channels/GUI) — consistent.
  - Browser runtime shutdown runs on all four paths — consistent.
  - Config-watcher cancellation ordering DIVERGES: GUI cancels FIRST
    (desktop.rs:261), headless cancels LAST (main.rs:336/400/445) after the
    store hook dispatcher and browser runtime are already shut down — the
    watcher remains armed during headless teardown, so a config save in that
    window can trigger a hooks reload on a partially torn-down runtime.
  - Scheduler runner and BackgroundTaskService are never stopped or cancelled
    in any entry; they are only ever killed by process exit. In the GUI the
    window-close -> process-exit window is short; in TUI/CLI the post-session
    review window is likewise short, but a cron tick during it can start a
    TaskRuntime run on a pool agent while the runtime is shutting down.
  - `TerminalManager::close_all()` (src/tauri/terminal.rs:256) is dead: live
    PTY sessions are never killed on GUI exit; children are left to the
    kernel SIGHUP when the PTY master fd closes at process exit (usually
    self-cleaning, not guaranteed for daemonized children).
  - Combined `--channels --cli` mode drops the spawned channels task without
    awaiting graceful shutdown (`manager.stop_all()` in run_channels_mode,
    modes.rs:228-232, is only reached on the channels-only path); the comment
    at main.rs:404 documents this "ends when the process exits" behavior.

## Deviations

None.

## Conclusion

Supports: hook-dispatcher and browser-runtime cleanup are consistent; three
shutdown gaps exist — config-watcher cancel ordering asymmetry (headless
cancels last), scheduler/task-service never cancelled, PTY close_all dead, and
combined-mode channels abandonment (findings A-BOOT-01-P3-01/02/03). Does not
prove the concrete fallout (e.g., cron tick during teardown), which needs a
dynamic shutdown fixture.
