## Claim

A startup failure at any composition step either fails the process with a
clear error (headless) or is reported to the crash log/dialog (GUI), and no
partially built service is left running beyond process exit.

## Method

Inspection of every `?`/`exit`/`unwrap_or`/fallback in the two composition
sequences and the GUI error wrapper.

```text
1. Headless: main.rs:60-92 (main) -> run_tui_or_cli_entry — bootstrap `?`
   (main.rs:168), conversation load `?` (203-227), run_tui `?` result,
   run_cli_mode result -> mode_error propagation (447-450), exit(1) paths
   (343-345, 351-353, 433-434)
2. GUI: desktop.rs:94-122 run_desktop_entry error -> crash log + macOS dialog;
   run_desktop `?` chain (124-271)
3. Store fallback chains: main.rs:35-57 (file -> in-memory -> None),
   state.rs:547-566 (file -> in-memory -> None), desktop.rs:174-181
   (FileStore -> InMemoryStore)
4. BrowserRuntime: bootstrap start (runtime.rs:93-99, non-failing, lazy
   client), shutdown on normal exit only (browser/mod.rs:194-206)
```

## Expected Result

Errors propagate with nonzero exit / crash log; degraded fallbacks are
logged; no service escapes process lifetime.

## Result

- Exit code: not-applicable (static inspection)
- Summary:
  - Headless: any bootstrap error propagates via `?` to `main`, which returns
    the error (nonzero exit, anyhow). Post-bootstrap failures (`run_tui`
    terminal init, REPL errors) still run the shared cleanup block
    (main.rs:329-336 TUI, 438-445 tail) before returning — cleanup is not
    skipped on UI failure.
  - GUI: `run_desktop` errors are caught at desktop.rs:94-119, written to
    crash.log, echoed to stderr, and surfaced via a native macOS dialog; the
    entry returns `Ok(())`. A GUI startup failure is therefore visible to a
    user who launched from Finder.
  - Store fallbacks are consistent: TaskRuntimeStore file -> in-memory -> None
    (both entries), each step logged (main.rs:40-48, state.rs:549-553);
    scheduler store FileStore -> InMemoryStore (desktop.rs:177-179,
    modes.rs:48-53). When the store is None, task tools are skipped with
    logs (main.rs:176, desktop.rs:200) and the app continues degraded —
    deliberate, logged fallback, not silent.
  - Rollback gap (minor, bounded by process exit): `BrowserRuntime::start` is
    non-failing and starts a lazy MCP client; if `create_agent_with_diagnostics`
    fails right after (runtime.rs:103), the runtime Arc drops WITHOUT
    `shutdown()` (which closes MCP clients/sessions). On headless the process
    exits immediately, so any connected Playwright sidecar is left to OS
    cleanup — no explicit kill. Impact limited to crash paths; recorded as
    uncertainty, not a finding.
  - GUI bootstrap failure path (desktop.rs:160 `?`) drops the browser runtime
    without shutdown as well — same bounded-rollback note.
  - `register_task_tools_on_agent`/`bind_task_execute_to_pool` are infallible
    (register.rs:45-90, 136-170); no partial-registration state is possible
    (tools registered in one `write` critical section).

## Deviations

None.

## Conclusion

Supports: startup-failure rollback is error-visible on every surface; cleanup
blocks run even when the UI step fails; the only imperfect rollback is the
dropped-without-shutdown browser runtime on failure paths, bounded by process
exit. Does not support claims about behavior after process death (e.g. sidecar
orphan reaping), which needs a dynamic test.
