## Claim

EKO tool input schemas are exactly the framework schemas plus the declared
`parallel_group` extension; `EkoTaskSpec`/`TaskPatch` map field-for-field onto
framework `TaskSpec`/`TaskSpecPatch`; every op family supported by EKO surfaces
is a subset of the framework op family with matching semantics; stale updates
are rejected; EKO deliberately disables manual progress (`set_status`) while
the framework default enables it.

## Method

1. Compare framework schema builders (`task_tools.rs:225-400`:
   `task_create_schema`, `task_update_schema`, `task_input_schema`) with
   `EkoTaskToolPolicy::task_input_schema_extensions`
   (revisioned_adapter.rs:107-112) and the extension merge loop
   (task_tools.rs:384-386).
2. Field-by-field compare `TaskSpec` (runtime.rs:179-211) vs `EkoTaskSpec`
   (types.rs:872-918) and `TaskSpecPatch` (revisioned.rs:78-91) vs `TaskPatch`
   (types.rs:1221-1258).
3. Op-family compare: framework `TaskPlanPatchInputOp` (insert/update/skip/
   reorder/set_status) vs EKO `TaskUpdateOperation` (types.rs:1256-1282) vs
   `TaskRevisionService::allow_manual_progress_updates` delegation
   (revisioned.rs:698-699) and `TaskToolPolicy` default `false`
   (revisioned.rs:275-276) vs `DefaultTaskToolPolicy::allow_manual_progress_updates
   = true` (revisioned.rs:338-339).
4. Stale-update rejection: `apply_patch_to_loaded` (revisioned.rs:944-955)
   plus store test `task_update_rejects_stale_revision_without_appending_event`
   (store.rs:3039).
5. Tool schema round trip: `plan_task_schema_keeps_generated_briefs_in_user_language`
   test (task_tools.rs:392-413) exercises `FrameworkTaskCreateTool::parameters()`
   with the EKO service.

## Expected Result

Schema = framework + `parallel_group`; all framework fields covered by EKO
DTOs; GUI/LLM op sets ⊆ framework op set; stale `base_revision` -> conflict
error, no event appended.

## Result

- Exit code: not-applicable (static inspection + existing tests)
- Duration: < 10 min
- Summary:
  - `parallel_group` is the sole EKO schema extension, merged into
    `task_create` and `task_update` task-item schemas; parser collects it into
    `TaskDraft.extensions` (task_tools.rs:549-554) and
    `EkoTaskToolPolicy::prepare_task` reads it into `EkoTaskMetadata`
    (revisioned_adapter.rs:220-235). Parity holds.
  - `EkoTaskSpec::to_task_spec` (types.rs:892-918) covers all 12 `TaskSpec`
    fields; EKO-only `domain_profile`/`parallel_group`/`sort_order` live in
    `metadata` (EkoTaskMetadata), never in generic fields.
    `TaskPatch::to_task_spec_patch` (types.rs:1236-1255) covers all 11
    `TaskSpecPatch` fields, `kind` mapped via `PlanTaskKind::to_task_kind`.
    A-TSK-01 V03-01 independently verified lossless round trip.
  - Op sets: framework `task_update` schema exposes set_status only when
    `allow_manual_progress_updates()` (task_tools.rs:309-320); EKO policy
    inherits the trait default `false`, so EKO's LLM tool never offers
    set_status and its parser rejects it (task_tools.rs:497). EKO GUI
    `TaskUpdateOperation` (types.rs:1256-1282) likewise has no SetStatus
    variant. Consistent product policy: execution status cannot be forged via
    authoring tools (matches runtime-dag-kernel-convergence.md:187 claim).
  - Stale updates rejected at service level (RevisionConflict,
    revisioned.rs:944-955) and store CAS; store test
    `task_update_rejects_stale_revision_without_appending_event` exists and
    passed in V04-04.
  - Note: F-TSK-01-P3-02/P3-03 (framework-side schema vs serde/parse drift:
    "in_progress" vs "running", lenient patch parsing) remain framework
    findings; the EKO side adds no new drift of the same class except
    `create_complex_task` fallbacks (see A-TSK-02-P3-02).
- Log/artifact: none.
