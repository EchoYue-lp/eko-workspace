## Claim

Reading a corrupt/truncated JSON store file either (a) surfaces an explicit
error, or (b) silently returns empty data — and the observed behavior per
backend is established from code and tests, with any silent-empty path that
can overwrite the corrupt file flagged as data loss.

## Method

1. Read `FileStore::new` (`echo-state/src/memory/store.rs:227-252`) and
   traced what a corrupt/truncated file produces, plus what the next
   `flush()` (`store.rs:254-278`) does to the corrupt file.
2. Read `FileConversationStore` read paths: `read_meta`
   (file_conversation.rs:100-138), `read_record` (:149-166),
   `read_all_records` (:215-241); checked its corrupt-file test
   (`corrupt_record_surfaces_as_error_not_empty`,
   file_conversation.rs:624-641).
3. Read `EmbeddingStore::with_persistence` index load
   (embedding_store.rs:107-137) and its drop-flush (:285-312).
4. Read `restore_message`/`restore_projection_meta` leniency
   (conversation.rs:169-191).
5. Checked which corrupt-handling behaviors have test coverage in the
   `echo_state` test suite (V04-01 output: file_conversation corrupt test
   present; no FileStore/EmbeddingStore corrupt test exists).

## Expected Result

FileConversationStore: explicit `MemoryError::SerializationError` (per its
module doc, file_conversation.rs:20-22) with test coverage. FileStore:
either explicit error or documented silent-empty; if silent-empty, the
overwrite-on-next-flush data-loss chain is identified.

## Result

- Exit code: not-applicable (read-only inspection; test inventory from V04-01)
- Summary:

| Backend | Corrupt file at open | Next write | Test coverage |
|---|---|---|---|
| FileConversationStore | Explicit `MemoryError::SerializationError` (file_conversation.rs:153-157, 235-237, 103-105) | write only on explicit user ops; corrupt file is never overwritten implicitly | `corrupt_record_surfaces_as_error_not_empty` (file_conversation.rs:624-641) |
| FileStore | warn + **silent empty** `HashMap::new()` (store.rs:235-238) | any `put`/`delete`/`prune_expired`/`dedup_by_content`/`flush_public` overwrites the corrupt file with the empty state (store.rs:254-278) → **permanent data loss** | none |
| EmbeddingStore index | warn + silent empty index (embedding_store.rs:117-125) | drop-flush writes the (empty) index over the corrupt file (embedding_store.rs:285-312); index is only rebuilt by new puts | none |
| restore_message (attachments_json) | garbage without `_echo_message_version` marker silently treated as legacy → `Ok(None)` (conversation.rs:176-178) — intentional, but truncation of a framework projection is indistinguishable from legacy data | n/a | projection round-trip test only (conversation.rs:206-220) |

FileConversationStore `read_meta` also reconciles `next_id` from records
(file_conversation.rs:112-136), so a corrupt `_meta.json` surfaces as an
error while a *missing* meta file is tolerated (`NotFound` → default,
:108).

## Deviations

The FileStore and EmbeddingStore silent-empty behaviors contradict the
project's own hardened pattern (FileConversationStore module doc
file_conversation.rs:20-22: "Corrupt JSON is an error... rather than
silently returning None / an empty list"); the EKO fallback guards
(desktop.rs:177-179, modes.rs:48-52, infra.rs:1332-1350) never trigger
because `FileStore::new` returns `Ok` on corrupt input.

## Conclusion

Supports: FileConversationStore corrupt handling is explicit, tested, and
safe; FileStore and EmbeddingStore index corruption is silent and leads to
overwrite of the corrupt payload (data loss). Promoted to finding
F-MEM-01-P1-01 (FileStore) and folded into F-MEM-01-P3-03 (EmbeddingStore).
Does not prove behavior for files that are valid JSON of the wrong shape
(also silent-empty for FileStore via the same `unwrap_or_else`).
