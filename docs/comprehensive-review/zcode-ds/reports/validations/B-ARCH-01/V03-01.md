## Claim

No cycle or misplaced-type pattern exists that would break the layered
architecture: (a) no sub-crate imports the facade (V01); (b) the only
cross-crate `echo_macros` consumer with a pre-existing dependency on the
root (`echo_tools`) uses only the derive macro path that resolves to
`echo_core`, while the standalone attribute macros are used only inside
`echo_agent` itself; (c) shared concept names between root and sub-crates
are re-export facades, not parallel implementations.

## Method

1. Grepped for standalone `#[tool(` attribute-macro usage across `src/` and
   `examples/`, and for `derive(Tool)` usage across `src/`, `echo-tools/src/`,
   `echo-execution/src/`.
2. Read `echo-macros/src/lib.rs:44` (`echo_agent_crate_path`) and
   `echo-macros/src/derive_tool.rs:37-62` (`resolve_echo_crate_path`) to
   compare crate-path resolution precedence.
3. Compared the module inventories of root vs sub-crates (from V02) for
   duplicate concept homes.

## Expected Result

- `#[tool(`]` attribute used only where `echo_agent` is a dependency
  (root `src/`, root `examples/`); `derive(Tool)` used by `echo_tools`.
- Attribute macros resolve `echo_agent`; derive resolves `echo_core` first.
- No concept has two independent implementations.

## Result

- Standalone `#[tool(` usage: `src/tools/mod.rs` plus examples
  (`demo03_approval`, `demo10_streaming`, `demo12_resilience`,
  `demo25_macros`, `demo45_customer_service`, `demo13_tool_execution`,
  `demo11_callbacks`, `demo17_chat`, `demo44_code_laboratory`, …) — all
  inside the `echo_agent` package, where `extern crate self as echo_agent`
  makes `crate_name("echo_agent")` resolve to `Itself`.
- `derive(Tool)` usage: zero in root `src/`; `echo-tools/src/git.rs:24` and
  `echo-tools/src/statistics.rs:22` use `#[derive(Default, echo_macros::Tool)]`
  with `#[tool(...)]` as the derive's *helper attribute* (declared at
  `echo-macros/src/lib.rs` `#[proc_macro_derive(Tool, attributes(tool, tool_param))]`),
  not the standalone attribute macro. `resolve_echo_crate_path`
  (`derive_tool.rs:37-62`) prefers `crate_name("echo_core")` and falls back
  to `echo_agent`, so echo_tools-generated code targets `::echo_core::…`.
- Resolver inconsistency confirmed: `lib.rs::echo_agent_crate_path` (used by
  `#[tool]`, `#[callback]`, `#[guard]`, `#[handler]`, `#[compressor]`,
  `#[permission_policy]`, `#[audit_logger]`) always requires the consumer to
  depend on `echo_agent`; `derive_tool.rs::resolve_echo_crate_path` requires
  `echo_core` first. A consumer depending on `echo_core` + `echo_macros` can
  use `#[derive(Tool)]` but not `#[tool]` — the two macro entry points have
  different dependency contracts. Recorded as `B-ARCH-01-P3-01`.
- Concept-home overlap check: every root/sub-crate name pair (agent, llm,
  tools, memory, retry, guard, sandbox, skills, workflow, tasks, scheduler,
  human_loop, mcp, lsp, compression, audit, tokenizer, plugin) resolves to a
  single implementation with the root side re-exporting; the only root-owned
  concepts adjacent to sub-crate concepts are `src/state/` (RuntimeStateStore
  checkpoint store) and `echo_orchestration::tasks` (TaskManager) — both
  framework-owned but semantically adjacent; whether they overlap is a
  question for `F-TSK-01`/`F-TSK-03`, not an established duplicate.
- `echo_core::agent` (9 files, 2584 lines: traits/builder/factory/critic/
  executor/reflection) vs root `src/agent` (65 files: ReAct engine +
  subagent + steer/snapshot/turn) — complementary, root re-exports core types
  (`src/agent/mod.rs:36-37,81`).

## Deviations

None.

## Conclusion

Supports: no structural cycle; macro entry points have a real but dormant
inconsistency (P3); no parallel implementations of sub-crate concepts inside
the root facade.

Does not prove: semantic equivalence of `RuntimeStateStore`/TaskNode and
`orchestration::tasks` (F-TSK-01), or that root-owned modules (evolution,
state, trace) are correctly placed for all consumers (F-API-01 / X-BND-01).
