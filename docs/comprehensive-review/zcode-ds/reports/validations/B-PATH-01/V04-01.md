## Claim

Every live entry point (TUI, GUI, CLI, channels) assembles the same set of
background services — task runtime + recovery, agent pool, config watcher,
scheduler/cron, MCP health monitoring, Dreaming/memory maintenance — and any
service present in one surface is present in all others (AGENTS.md surface
parity invariant).

## Method

1. Built a per-mode service matrix from V01/V02 evidence and the call-site
   greps below.
2. Grepped `spawn_mcp_health_check`, `spawn_dreaming_task`,
   `start_task_service`, `start_scheduler_with_store`, `spawn_config_watcher`,
   `bind_task_execute_to_pool`, `register_task_tools_on_agent`,
   `start_headless_services`, `recover_incomplete` call sites across
   `src/` and `echo-agent-app-core/src/`.
3. Compared GUI (desktop.rs) vs TUI (main.rs + tui/mod.rs) vs CLI
   (modes.rs + repl.rs) vs channels (modes.rs).

## Expected Result

- Config watcher: all modes.
- TaskRuntimeStore + recovery: all modes.
- Agent pool + cleanup monitor: all modes.
- Task service: all modes.
- Scheduler/cron: all modes.
- Dreaming: all modes (spawned with per-mode cancel token).
- MCP health check: all modes.

## Deviations

The MCP health check row is the deviation that fails this validation:
GUI-only service despite the parity invariant. Also, channels mode lacks an
explicit Dreaming spawn (lower confidence; pooled agents may run their own
memory maintenance — see Conclusion).

## Conclusion

This validation FAILS on the MCP health-monitoring row. Supports:
`B-PATH-01-P2-01` (MCP health monitoring is GUI-only). The rest of the
matrix is parity-clean, including the previously suspected Dreaming gap,
which is present in TUI/CLI/GUI.

Does not prove: whether framework-level MCP reconnect-on-use makes the
missing TUI/CLI health loop harmless (F-INT-01), or whether pooled channel
agents need an explicit Dreaming pass (A-MEM-01).
