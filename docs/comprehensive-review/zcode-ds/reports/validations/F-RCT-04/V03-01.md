## Claim

The batch invariants asked by the task card — tool-call/result pairing,
concurrent ordering, timeout versus cancel, partial-side-effect and
oversized-result fixtures — are either enforced by code, covered by tests, or
visibly absent; and the framework's only repair for broken pairing is
`sanitize_tool_call_pairing` with the exact semantics inspected.

## Method

Invariant-by-invariant static inspection against production code and existing
tests, plus a repository-wide usage count of the multi-tool mock helper.

```text
1. Pairing: count Message::tool_result pushes per batch path (tools.rs:226,252,382,408);
   check for duplicate call_id handling; check repair path
   sanitize_tool_call_pairing (echo-state/src/compression/mod.rs:1562-1718) and its
   call sites (mod.rs:848 promote_and_sanitize, :1451 prepare, :1494 fallback).
2. Concurrent ordering: context push order in the concurrent arm vs the sorted
   call order in the assistant message (processor.rs:138-163); provider serialization
   order (echo-integration/src/providers/anthropic.rs:60-90); pipeline test
   multiplexed_streams_preserve_identity_and_terminal_order (pipeline.rs:1634-1720).
3. Timeout vs cancel: per-tool timeout classification (echo-core/src/tools/mod.rs:165-198)
   vs batch timeout (tools.rs:284-292) vs cancel grace (tools.rs:176-193, 278-283);
   timeout retryability for read vs write tools (execute_tool_inner
   echo-execution/src/tools.rs:686-724).
4. Partial-side-effect fixtures: grep PartialSideEffect producers and any
   batch-level fixture; verify what the batch does with in-flight tools at timeout/cancel.

   safety and spill/truncation tests (pipeline.rs:1452-1600).
6. Fixture availability: grep usage of MockLlmClient::then_tool_calls
   (src/testing/mock_llm.rs:233) across both repositories.
```

## Expected Result

Each invariant is either enforced by code, covered by a test, or confirmed
absent with an explanation.

## Result

- Exit code: not-applicable (static inspection)
- Summary:
  - Pairing (context level): every executed tool gets exactly one
    `Message::tool_result` push on the normal path (one per completed future,
    serial and concurrent). Duplicate `call_id` across iterations is not
    detected (no dedup check in `run_tools`); provider-side duplicate-id
    rejection is possible but no fixture exists.
  - Pairing (event level): on batch timeout/cancel, in-flight calls get no
    `ToolResult`/`ToolError` event — the consumer sees `ToolCall` events
    without terminals. Additionally, `yield_event_or!` (stream_macros.rs:38-53)
    DROPS `ToolResult` events on a full buffer while the context push still
    happens (tools.rs:217-230) — event/context divergence under backpressure
    (cross-reference F-RCT-03 for the buffer-drop decision).
  - Concurrent ordering: results are pushed in `FuturesUnordered` completion
    order (tools.rs:207-240); the assistant message carries the calls sorted by
    stream index (processor.rs:141-147); providers serialize messages in
    context order with no re-sort (anthropic.rs:60-90; openai adapter has no
    tool-result ordering logic). The pipeline test
    `multiplexed_streams_preserve_identity_and_terminal_order` (pipeline.rs:1634-1720)
    asserts completion-order terminals (`["call-b","call-a"]`) — the behavior
    is enshrined by a test at the execution level, and no consumer-level test
    checks order against the assistant message. External provider constraint
    verified in V03-02.
  - Timeout vs cancel: per-tool timeout of a read-only tool is retryable
    (Timeout/Retry/None side-effect → `allows_automatic_retry` = true,
    echo-core/src/tools/mod.rs:154-163,165-198); a write tool's timeout
    becomes `PartialSideEffect` (side_effect Possible) and is NOT retried —
    correct. Batch timeout is abrupt: drops in-flight futures, sends one
    droppable `Err` event, no `ToolBatchEnd`; batch cancel is graceful
    (5 s grace, results of tools that finish during grace are still inserted,
    `ToolBatchEnd` emitted). Verified by existing test
    `cancellation_drains_running_tool_before_abandoning_turn`
    (stream_channel.rs:2041-2082) — covers cancel-with-drain; no batch-timeout
    test exists.
  - Partial-side-effect: producers exist in domain tools (echo-tools/src/files/files.rs:97,
    shell.rs:1051-1114, code.rs:390-445). The BATCH-level kill path produces no
    failure record at all for in-flight tools (no ToolError event, no
    `ToolFailure`), and the later context repair
    (`sanitize_tool_call_pairing`) either clears the orphaned calls entirely
    (mod.rs:1637-1645, "DanglingCallCleared") or inserts a placeholder
    `"[Result unavailable — tool result was removed during context compression]"`
    with name "unknown" (mod.rs:1686-1698, 1702-1714) — the attribution is
    wrong for batch kills and no partial-side-effect warning is ever given.
    `sanitize_tool_call_pairing` runs unconditionally inside
    `ContextManager::prepare` (mod.rs:1451-1453, comment "Always sanitize ...
    before sending to LLM"), which `run_compact` calls every iteration
    (phases/compact.rs:60) — so pairing is repaired before the next LLM
    request, but only via clear/placeholder, never by reordering.
  - Oversized results: `process_tool_output_for_call` (snapshot.rs:926-1060)
    is UTF-8 safe (`chars().take`), spills over `threshold_bytes` or token
    budget to artifacts with preview + `read_artifact` recovery, falls back to
    head/tail token truncation when the spill fails. Tests exist:
    `token_budget_spills_even_below_byte_threshold`,
    `truncation_stage_is_utf8_safe`, `truncation_stage_falls_back_when_spill_directory_is_unwritable`
    (pipeline.rs:1452,1501,1557). This invariant holds.
  - Fixture availability: `MockLlmClient::then_tool_calls` (src/testing/mock_llm.rs:233)
    — the multi-tool-batch mock — has ZERO usages in both repositories. Every
    existing turn test uses single-tool-call responses. No test exercises: a
    concurrent batch, mixed serial/concurrent split, batch timeout, result
    ordering, or multi-result pairing. The task card's required fixtures do
    not exist (F-RCT-04-P2-01).
  - Batch timeout arithmetic: EKO defaults (timeout 120 s, retries 2,
    retry_delay 200 ms, max_concurrency None → waves 1) give a ~360.9 s batch
    budget (run/retry.rs:69-107) — consistent with the per-tool 3-attempt
    worst case of ~360.6 s plus 250 ms grace.

## Deviations

None.

## Conclusion

Supports: pairing holds on the normal path but not on timeout/cancel at the
event level; concurrent result ordering is completion-order and never
reconciled with provider order (F-RCT-04-P1-01); timeout and cancel have
distinct semantics with the timeout signal droppable (F-RCT-04-P1-02);
batch-level kills leave no partial-side-effect record and the repair
placeholder misattributes the cause (F-RCT-04-P2-02); oversized-result
handling is correct and tested; no batch-level fixtures exist (F-RCT-04-P2-01).
