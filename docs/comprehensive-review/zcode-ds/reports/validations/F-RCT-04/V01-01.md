## Claim

There is exactly one live tool-batch execution authority in `echo-agent`, no
parallel batch machinery in `echo-agent-cli`, and no duplicated
timeout/concurrency/retry/truncation helpers that the batch path bypasses.

## Method

Repository-wide grep over both source trees (`echo-agent` all crates,
`echo-agent-cli` all crates) for the batch/execution vocabulary, then
classification of each hit as definition, registration, live caller, dead
caller, or unrelated.

```text
grep -rn --include="*.rs" -e "fn run_tools" -e "run_tools(" -e "ToolExecutionPipeline" \
     -e "execute_tool_with_policy" -e "execute_tool_feedback" -e "execute_tool(" (both repos)
grep -rn --include="*.rs" -e "MAX_CONCURRENT" -e "max_concurrency" -e "Semaphore" \
     -e "tool_timeout" -e "tokio::time::timeout" -e "allows_automatic_retry" \
     -e "retry_delay_ms" -e "truncate_tool_output" -e "spill" (echo-agent)
grep -rn "sanitize_tool_call_pairing" / "ToolBatchStart|ToolBatchEnd" (both repos + web-frontend)
```

## Expected Result

One live authority for batch execution (the `run_tools` phase); the dead
`process_steps`/`execute_tool_feedback*` path (F-RCT-02-P3-01) may exist but
must be unreachable; no batch loop in `echo-agent-cli`.

## Result

- Exit code: not-applicable (static search)
- Summary:
  - Live batch authority: `echo-agent/src/agent/react/run/phases/tools.rs:50`
    (`run_tools`), called only from `run_core_loop`
    (`echo-agent/src/agent/react/run/stream_channel.rs:660-661`). Per-tool
    execution funnels through `snapshot.rs:1189` (`execute_tool_with_policy`)
    → `ToolExecutionPipeline` (`pipeline.rs:916,1019`) → manager
    `echo-execution/src/tools.rs:591/606/618/759`.
  - Dead parallel authority: `react_loop.rs:177-502` (`process_steps`,
    `#[allow(dead_code)]`, zero callers) and `run/execution.rs:168,196,404`
    (`execute_tool_feedback_raw`, `execute_tool`, `execute_tool_feedback`,
    only dead/self callers) — matches F-RCT-02-P3-01. NOTE: the dead
    `process_steps` batch code (`react_loop.rs:240-270`) separates
    batch-timeout-exempt tools from timed peers, while the live `run_tools`
    (`tools.rs:133-139,167-175`) disables the whole-batch timer when any tool
    is exempt — a behavioral divergence between dead and live code (see
    F-RCT-04-P3-02).
  - `echo-agent-cli`: no batch loop. The only direct manager call is
    `echo-agent-app-core/src/analysis.rs:421`
    (`execute_tool_with_context("run_code", ...)`), a single-tool public-API
    consumer, not a parallel batch.
  - Concurrency: `echo-execution/src/tools.rs:18,59-61,505-511` — semaphores
    created only when `max_concurrency`/`max_read_concurrency` configured;
    `ToolExecutionConfig::default()` (`echo-core/src/tools/mod.rs:540-551`)
    has `max_concurrency: None`, `max_read_concurrency: Some(32)`.
    `run_tools` pushes the whole concurrent subset into `FuturesUnordered`
    (`tools.rs:142-160`) — no wave gating in the batch layer.
  - Timeout: two layers — per-tool `tokio::time::timeout`
    (`echo-execution/src/tools.rs:686-698,863-872`) and the batch timer
    `compute_concurrent_tool_batch_timeout` (`run/retry.rs:69-107`, consumed

    `ToolExecutionConfig.timeout_ms`.
  - Retry: single classification authority `ToolFailure::allows_automatic_retry`
    (`echo-core/src/tools/mod.rs:154-163`); consumed only at
    `echo-execution/src/tools.rs:707,885`; batch math copies the backoff

    (`echo-core/src/llm/types.rs:421-427`); pairing repair

## Deviations

None. The dead `process_steps` batch implementation is a divergence candidate
but was already flagged by F-RCT-02-P3-01; it is recorded here as behavioral
drift, not a second live authority.

## Conclusion

Supports: one live batch authority (`run_tools` → pipeline → manager), no
parallel batch machinery in the CLI, single retry-classification and
single spill/repair authorities. Does not prove: correctness of any of these
paths under concurrency/timeout/cancel — covered by V02/V03.
