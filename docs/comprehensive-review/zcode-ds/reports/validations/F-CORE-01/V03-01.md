## Claim

Identity collision/ordering semantics: `event_id` is deterministic for a
fixed identity+sequence (enabling idempotent persistence); `sequence` is
monotonic and resumable via `envelope_event_stream_after`; tool
correlation (call_id → parent_event_id) is enforced; exactly-one terminal
per stream is normalized. Edge cases: identity fallbacks and the
`parent_event_id` contract for child invocations.

## Method

1. Static inspection of `event_envelope.rs:40-194` (stable_event_id,
   envelope_event_stream_after logic) and `:197-295`
   (validate_event_trajectory).
2. `grep -rn "parent_event_id"` in framework and app-core production code
   (non-test) to find who sets it.
3. Checked the turn_id fallback path (`from_invocation`,
   event_envelope.rs:92-96) and its call sites (chat_driver:483-488 direct
   construction; subagent executor:1168 from_invocation).

## Expected Result

Deterministic event_id; monotonic resumable sequence; tool-level parent
correlation enforced; one-terminal normalization; parent_event_id set for
delegated child invocations (per its doc comment); fallback only when
identity truly unavailable.

## Result

- `stable_event_id` (`event_envelope.rs:64-84`): SHA-256 over
  schema_version + length-prefixed identity parts + sequence. Deterministic
  for the same (identity, sequence). `u64::try_from(value.len())` with
  `unwrap_or(u64::MAX)` (`:76`) is panic-safe.
- Sequence: `saturating_add(1)` (`:142`, `:181`); `envelope_event_stream_after`
  resumes from `last_persisted_sequence` (`:123-127`); test
  `resumes_after_persisted_sequence_with_stable_ids` (V04) proves
  deterministic re-creation of the same event_id at the same sequence.
- Tool correlation: ToolCall records its event_id as the parent for
  ToolResult/ToolError/ToolStream (`:143-152`); completion removes the
  entry (`:163-171`); `validate_event_trajectory` flags duplicate in-flight
  calls, orphan completions, wrong parents, unfinished calls (`:243-293`).
- One-terminal: stream ending without a terminal gets a synthetic
  `AgentEvent::Error` (`:180-191`); a second terminal event is dropped
  (test `normalizes_missing_and_duplicate_terminals`, V04).
- **`parent_event_id` for child invocations is never populated in
  production**: `EventIdentity::from_invocation` hardcodes `None`
  (`:102`); EKO `chat_driver.rs:487` hardcodes `None`; subagent executor
  uses `from_invocation` (executor.rs:1168). Only tests set it
  (`surface_contract.rs:159`). The doc comment at `event_envelope.rs:21`
  ("Parent event for a child invocation, such as a delegated subagent")
  describes a capability no production path uses. Child invocation
  association relies on run_id/execution_id instead (EKO
  `subagent_run_id = {run_id}:{task_id}:{plan_revision}:{attempt}`).
- **Turn-id fallback**: `from_invocation` falls back to a fresh
  `Uuid::new_v4()` when runtime has no turn_id/execution_id/run_id
  (`event_envelope.rs:92-96`). This makes `event_id` non-deterministic for
  that invocation and breaks the documented idempotent-persistence
  property; no doc comment warns callers that turn_id must be stable.

## Deviations

The two observations above are recorded as findings
(`F-CORE-01-P3-01` parent_event_id, `F-CORE-01-P3-02` turn_id fallback),
not deviations of this validation's primary claim.

## Conclusion

Supports: deterministic identity given stable identity+sequence; monotonic
resumable sequence; enforced tool correlation; exactly-one terminal;
robust trajectory validation. Identifies two contract-implementation gaps.

Does not prove: crash-recovery idempotency of real persistence adapters
(F-RCT-05 / A-TSK-04 own that), or that consumers honor parent_event_id
when present.

## Follow-Up

F-RCT-05 and X-EVT-01 should decide whether parent_event_id needs a
production producer; F-CORE-01-P3-02 should be fixed or documented.
