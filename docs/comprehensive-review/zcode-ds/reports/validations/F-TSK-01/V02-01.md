## Claim

`TaskStatus` has one coherent, enforced transition table; the revision
mechanism (base_revision + operations, `TaskRevisionService` +
`TaskPatchEngine`) is optimistic-concurrency correct, and stale-revision
updates are rejected at both service and store layers.

## Method

1. Read `echo-orchestration/src/tasks/runtime.rs:87-175` (TaskStatus
   definition, `can_transition_to`, `transition_to`).
2. Read `echo-orchestration/src/tasks/revisioned.rs` in full (service,
   patch engine, store trait, CAS store).
3. Read `echo-orchestration/src/tasks/task_tools.rs` parse paths.
4. Read `echo-orchestration/src/tasks/manager.rs` status mutation sites.
5. Cross-check `echo-core::error` (no panic on invalid transitions — errors
   are `Result<String, String>`).

## Expected Result

- Terminal states never accept transitions; Pending→Running gate exists;
- update of non-Pending/Blocked specs rejected; Blocked reset on update;
- stale base_revision → `TaskRevisionError::RevisionConflict` before commit,
  and store CAS independently rejects expected/current mismatch;
- revision increments exactly once per commit.

## Result

### Transition table (source of truth: `runtime.rs:128-164`)

| From | Allowed targets |
|---|---|
| Pending | Running, Cancelled, Blocked(_), Skipped, Paused(_) |
| Running | Completed, Cancelled, Failed(_), TimedOut{..}, Retrying{..}, Blocked(_), Paused(_) |
| Retrying{..} | Completed, Cancelled, Failed(_), TimedOut{..}, Retrying{..} |
| Blocked(_) | Pending, Cancelled |
| Paused(_) | Running, Cancelled |
| Completed / Failed(_) / TimedOut{..} / Skipped / Cancelled | none (terminal, `is_terminal` `:111-120`) |

- Tool-exposed manual progress subset: set_status allows only Pending /
  Running / Completed / Cancelled (`revisioned.rs:596-607`), then validates
  via `transition_to` (`:614-620`); so e.g. Pending→Completed is rejected
  (must pass through Running) — matches the evidence-based lifecycle.
- `is_running` covers Running | Retrying (`:123-125`).

### Revision / patch protocol (`revisioned.rs`)

- `TaskRevisionService` owns create/update/read (`:674-1014`); `TaskPlanPatch`
  = `base_revision + reason + operations` (`:116-121`); canonical ops
  Insert/Update/Skip/Reorder/SetStatus (`:93-113`); parsed input ops
  `TaskPlanPatchInputOp` (`:124-144`).
- `TaskPatchEngine::apply_operations` (`:476-627`): empty op list rejected
  (`:482-486`); Insert rejects duplicate id and missing `after_task_id`
  (`:496-509`); Update only on Pending|Blocked, Blocked→Pending reset +
  effects.reset_task_ids, claim cleared (`:528-546`); Skip only on
  Pending|Blocked (`:554-564`); Reorder must contain every id exactly once
  (`:569-589`); SetStatus gated by policy flag + transition_to (`:590-623`).
- `apply_spec_patch` (`:630-664`) is a pure field-overwrite of
  `TaskSpecPatch` (all Option fields, serde default).
- `apply_patch_to_loaded` (`:934-988`): `base_revision == 0` rejected
  (`:940-944`); `current.revision != patch.base_revision` →
  `RevisionConflict { expected, current }` (`:945-950`); empty reason rejected
  (`:951-955`); next revision = `current.revision.checked_add(1)` with
  overflow guard (`:964-968`); commit via `compare_and_commit`.
- Store CAS (`InMemoryRevisionedTaskStore::compare_and_commit`, `:433-463`):
  re-checks `current != expected_revision` → Conflict (`:440-444`); verifies
  `next.revision == expected_revision + 1` and rejects overflow
  (`:446-460`). So a writer that wins between service load and CAS commit is
  detected at the store boundary.
- `create_from_tool` append path (`:758-796`): requires `base_revision > 0`
  when a graph already exists, else `InvalidInput`; fresh graph commits with
  `expected_revision: None` → revision 1 (`create_prepared` `:894-918`).
- Revision conflict surfacing: `From<RevisionedTaskStoreError>` maps Conflict
  → `TaskRevisionError::RevisionConflict` (`:222-233`); tool layers render it
  as an error string (`task_tools.rs:70-77,129-137`).
- Test `stale_patch_reports_conflict` (`revisioned.rs:1085-1109`) asserts a
  base_revision=2 patch against revision-1 graph yields
  `TaskRevisionError::RevisionConflict`.

### Observed deviations (non-fatal, recorded)

1. `TaskStatus` payload equality: `Blocked("a") != Blocked("b")`; SetStatus
   no-ops only on exact equality, but still clears `claim` and pushes
   `progressed_task_ids` even for a no-op (`revisioned.rs:614-622`) — effect
   accounting slightly over-reports, claim invalidation is conservative.
2. Legacy `TaskManager` bypasses: `claim_pending_task` assigns
   `TaskStatus::Running` directly (`manager.rs:136-155`, guarded by Pending
   check), `resume_run` assigns Pending directly from Paused (`:457-465`),
   `ManagedTask::mark_started/mark_completed` assign status directly
   (`task.rs:862-874`) — the transition machine is advisory on the legacy
   rich-record path (production-unreachable, see V01).
3. `TaskGraphContext` is carried forward unchanged on patches
   (`revisioned.rs:974`) — plan-level goal/assumptions/risks are
   create-only; no documented update path.

## Conclusion

Supports: one coherent transition table with terminal-state locking;
revisioned optimistic concurrency with double-layer stale rejection
(service revision check + store CAS) and single-step revision increments;
tool manual-status path reuses the same transition machine.

Does not prove: store CAS behavior of EKO's file-backed store
(A-TSK-01 scope) beyond the adapter mapping shown in V01.
