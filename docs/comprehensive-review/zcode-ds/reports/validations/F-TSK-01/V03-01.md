## Claim

`task_create`/`task_update`/`task_list` tool schemas are consistent with the
internal parse path and with `TaskSpec`/`TaskSpecPatch`/`TaskStatus` serde
types: every schema-required field is parseable, enum values match, and the
parse path is panic-free on arbitrary input.

1. Read `echo-orchestration/src/tasks/task_tools.rs:225-400` (schema builders)
   and `:402-635` (parse functions).
2. Read `echo-orchestration/src/tasks/revisioned.rs:47-153` (`TaskDraft`,
   `TaskCreateInput`, `TaskSpecPatch`, `TaskUpdateInput`) and

   `revisioned.rs:1016-1155`).

## Expected Result

- schema property sets == parser-required/parsed field sets;
- `kind` enum == `TaskKind::from_str` values;
- serde `TaskSpecPatch` fields == schema `patch` properties;
- no unwrap/expect/indexing panic on the parse path.

## Result

- Schema generation mechanism: the three tools return hand-written
  `serde_json::Value` JSON-Schema from `parameters()` (`task_tools.rs:34-36,
  101-103,162-164`); no schemars derive is used for task tools (grep: zero
  hits in `echo-orchestration`). Round-trip is therefore schema ↔ manual
  parse (+ serde for `TaskSpecPatch`).
- `task_input_schema` properties (`:336-393`): id, title, description, kind,
  subagent, depends_on, files, allowed_tools, required_artifacts,
  execution_checks, acceptance_criteria, max_retries + policy extensions
  (EKO adds `parallel_group`, `revisioned_adapter.rs:107-112`). Required:
  `["id","title","description","kind"]`. `parse_task_draft`
  (`:527-575`) requires exactly id/title/description/kind (empty-trimmed)
  and parses all remaining fields — sets match. `TaskDraft` fields
  (`revisioned.rs:49-63`) == schema properties.
- `kind` enum (`:395-400`): implementation, debugging, verification, review,
  investigation, test_plan, summary, read_only_review — identical to
  `TaskKind::from_str` (`runtime.rs:69-85`) and to `TaskKind` serde values.
- `task_update_schema` operations oneOf: insert/update/skip/reorder +
  optional set_status (`:251-334`); parser (`:441-525`) matches all five, and
  set_status is gated by the same `allow_manual_progress_updates` flag on
  both sides (`:309`, `:497`).
- `update` patch properties (`:270-286`): title, description, kind,
  agent_role, depends_on, files, allowed_tools, required_artifacts,
  execution_checks, acceptance_criteria, max_retries == `TaskSpecPatch`
  serde fields (`revisioned.rs:77-90`); deserialized via
  `serde_json::from_value` (`task_tools.rs:486-489`).
- `set_status` enum ["pending","in_progress","completed","cancelled"]
  (`:316`) == parser mapping (`:502-509`).
- `execution_mode` enum ["parallel","sequential"] (`:245`) — parser maps
  "sequential" → Sequential and any other value → Parallel (`:419-425`).
- Panic audit of parse path (`task_tools.rs:402-620`): all access uses
  `get`/`as_*`/`ok_or_else`/`filter_map`/`unwrap_or_default`; the only
  `unwrap_or_default` (`:72`) sits behind a `base_revision.is_some()` guard;
  no unwrap/expect/indexing. `apply_operations` uses
  `index.saturating_add(1)` and `positions.get(..).copied().unwrap_or(usize::MAX)`
  (`revisioned.rs:502-509,586`). No panic candidate found.
- Existing tests: `tools_create_update_and_list_one_graph` (create→update→
  list with UTF-8 task ids, `task_tools.rs:653-691`),
  `default_schema_exposes_manual_status_updates` (`:693-697`),
  `task_create_schema_requires_one_atomic_tasks_array` (`:699-713`),
  `task_create_rejects_the_removed_singular_shape` (`:715-731`),
  `creates_and_patches_one_canonical_graph` (`revisioned.rs:1056-1083`),
  `stale_patch_reports_conflict` (`:1085-1109`).

### Observed leniencies (schema stricter than parser; non-fatal)

1. `TaskSpecPatch` has no `#[serde(deny_unknown_fields)]` — unknown `patch`
   keys are silently ignored although the schema declares
   `additionalProperties: false` (`task_tools.rs:272`).
2. `max_retries` is not clamped at parse time (schema `maximum: 10`,
   `:284`); values >10 parse and are rejected later by
   `PlanValidator::validate_task_specs` (`validator.rs:243-248`) inside
   `finalize_and_validate` (`revisioned.rs:1007-1011`) — error surfaces at
   commit time as `InvalidPatch` instead of at parse time.
3. `execution_mode` unknown values silently become Parallel instead of an
   error (`task_tools.rs:419-425`).
4. `set_status` input vocabulary `"in_progress"` (`:316,:504`) diverges from
   the output vocabulary `"running"` used by `status_name`
   (`:622-635`) and by `TaskStatus` serde (`runtime.rs:88-90`) — same state,
   two spellings.
