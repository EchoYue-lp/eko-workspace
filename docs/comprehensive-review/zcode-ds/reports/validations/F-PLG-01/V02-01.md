## Claim

Plugin registration is reachable from every EKO entry point (TUI, GUI/Tauri, CLI) through
one shared `PluginRuntimeService`, and component registration/unregistration is
source-scoped so that disable/uninstall can remove exactly the components a plugin
registered.

## Expected Result

All four entry surfaces (TUI / Tauri / CLI / startup) reach the same service instance;
every component registered during wiring has a corresponding source-scoped removal key.

## Result

- Exit code: 0 (grep/read only)
- Summary:
  - Composition root constructs the service exactly once (`runtime.rs:279-280`); TUI/CLI
    hold `Arc<PluginRuntimeService>` references; Tauri resolves it from `AppState`
    (`tauri/commands/plugins.rs:83`). No entry point builds its own registry (the
    MASTER-PLAN:1008 "each tauri command builds its own registry" gap is fixed).
  - Framework `PluginRegistry` is state-free between scans: `scan_all` clears
    `self.plugins` before re-scanning (`registry.rs:118-139`), so no accumulation across
    reloads.
  - Skills are tagged in both the tracking and the progressive shared registry
    (`capabilities.rs:719-730`), so `unregister_skills_by_source` reaches both
    (`capabilities.rs:921-923`).
  - `wire_all`'s per-plugin ownership map (`components_by_plugin`,
    `plugin.rs:269-347`) is the exact unload key set consumed by `unload_agent_components`.
  - Demo path: framework example `demo56_plugin_system.rs` exercises manifest/registry/
    dependency APIs directly (registry-level only, no agent wiring).
  - `PluginLifecycleManager::register_lifecycle` has no production caller in either repo
    (only the service API + its tests); native lifecycle callbacks are therefore a
    public framework capability not yet exercised by EKO product code.
