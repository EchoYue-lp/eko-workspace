## Claim

Manifest/path validation, dependency-graph resolution, and source-scoped registration
hold their invariants: no path escape from the plugin root, deterministic acyclic
dependency ordering with version enforcement, and unload keys that cover every
registration a plugin can create.

## Method

Static inspection of `echo-core/src/plugin/manifest.rs`, `registry.rs`, `scope.rs`,
`echo-agent/src/plugin.rs`, `capabilities.rs` (skills/unload), `hooks.rs`
(register/unregister), plus cross-repo path comparison between the runtime authority and
the EKO config-inventory listing. No source modifications.

Inspection points:
1. `PluginManifest::validate_paths` (manifest.rs:541-585): `./` prefix requirement and
   `..` rejection for every component path field.
2. `resolve_plugin_path` (registry.rs:1003-1006): `strip_prefix("./")` + `root.join`,
   safe given (1) is enforced on every entry path (scan registry.rs:204-216, install
   registry.rs:290-301, `validate_plugin_dir` registry.rs:146-181).
3. `resolve_dependencies_matching` (registry.rs:807-890): Kahn's algorithm with
   in-degree/queue sorted by name (deterministic), missing-dep, disabled-dep, semver
   version constraint (`PluginDependency::satisfies` manifest.rs:282-293), and cycle
   detection (`sorted.len() != in_degree.len()`).
4. `ensure_no_enabled_dependents` (registry.rs:508-531): disable/uninstall blocked while
   an enabled plugin depends on the target (name-only check).
5. Source-scoped registration: skill tag `plugin:{id}` applied to both registries
   (capabilities.rs:719-730), hook `HookSource::Plugin(id)` (hooks.rs:610-645), unload
   coverage in `unload_agent_components` (plugin_runtime.rs:1157-1176).
6. Scope path authority vs EKO config inventory:
   `PluginScope::resolve_dir` (scope.rs:38-50: Project -> `<root>/.echo-agent/plugins`,
   Local -> `<root>/.echo-agent/plugins.local`) versus
   `ConfigDiscovery::discover_plugin_manifests` (config_discovery.rs:325-360:
   Global -> `data_root/plugins`, Project -> `<root>/.eko/plugins`, Local never scanned).

## Expected Result

- All component paths resolve inside the plugin root; malformed manifests are skipped
  with a warning at discovery.
- Dependency resolution is deterministic, detects cycles/missing/disabled/version
  mismatches, and every enabled plugin's dependencies are enabled.
- Unload removes exactly what was registered.
- Every surface that lists plugin paths agrees with the runtime authority.

## Result

- Exit code: 0 (inspection only)
- Summary:
  1. Path validation is enforced at all three entry points; `..` and non-`./` paths
     cannot reach `resolve_components`. Deterministic.
  2. Dependency graph: deterministic (sorted queues), detects cycles (`test_circular_dependency_detected`),
     missing deps, disabled deps, and version constraints (P1 semver, `registry.rs:838-855`).
  3. Source-scoped registration: symmetric for skills/hooks/subagents/MCP; both skill
     registries carry the same tag, and `unregister_skills_by_source` removes both plus
     skill hooks and projections (capabilities.rs:915-958).
  4. DEVIATION FOUND (finding F-PLG-01-P2-01): EKO `ConfigDiscovery` scans project-scope
     plugin manifests at `<project_root>/.eko/plugins` while the runtime authority
     `PluginScope::Project` uses `<project_root>/.echo-agent/plugins`; the Local scope
     (`.echo-agent/plugins.local`) is not scanned at all. EKO's own test fixture uses
     `.echo-agent/plugins` (plugin_runtime.rs:1407), confirming the runtime convention.
     The `discover_config` Tauri command (`src/tauri/commands/config.rs:315-340`,
     registered at `src/tauri/mod.rs:99`) therefore reports manifest paths the runtime
     never scans, and omits the real project/local manifests. No frontend consumer of
     `discover_config` exists today (grep of web-frontend/src returned nothing).
  5. DEVIATION FOUND (finding F-PLG-01-P3-01): installing a plugin whose name already
     exists in another scope is allowed (`install_local` registry.rs:275-352 checks only
     `dest.exists()` inside the target scope directory); the later-scope copy silently
     shadows the earlier one in the `plugins` HashMap (`scan_scope_dir` insert
     registry.rs:235, scan order User->Project->Local registry.rs:53-55, so effective
     precedence is Local > Project > User, the reverse of the doc phrase "priority order
     (user → project → local)"); `uninstall` with `keep_data=false` removes the
     name-keyed data dir (registry.rs:429-435, 985-997), which may belong to the
     shadowed copy.
  6. DEVIATION FOUND (finding F-PLG-01-P3-03): the same data-dir path computation
     (sanitize name to `[A-Za-z0-9_-]`, join under `<base>/plugins/data/`) is implemented
     twice — `PluginEntry::data_dir_for` (registry.rs:985-997) and
     `PluginVariables::data_dir_for` (variables.rs:76-89) — a parallel implementation of
     one semantic (both currently consistent).

## Deviations

Three deviations from the expected invariant set were found; all are recorded as
findings (P2-01, P3-01, P3-03). No manifest/path escape or dependency-graph defect was
found.

## Conclusion

Supports: manifest/path validation and dependency resolution are sound and deterministic;
source-scoped registration/unregistration is symmetric; the cross-scope shadowing and
EKO listing-path divergences are the concrete defects. Does not prove: dynamic
transaction behavior of activation failure / reload / unload (V03-02) or runtime
behavior under tests (V04).
