## Claim

The plugin concept (manifest / registry / activation / unload / rollback) has exactly one
authoritative implementation per layer across both repositories: framework
(`echo-core/src/plugin/*` + facade `echo-agent/src/plugin.rs`) and EKO application
(`plugin_runtime.rs` / `plugin_components.rs`), with no parallel runtime authority and no
second lifecycle state machine.

## Method

Repository-wide grep / find over both repositories (echo-agent and echo-agent-cli), no
source modifications.

```text
grep -rln "PluginRegistry" --include="*.rs" echo-agent echo-agent-cli
grep -rln "PluginLifecycle" --include="*.rs" echo-agent echo-agent-cli
grep -rln "PluginManifest" --include="*.rs" echo-agent echo-agent-cli
grep -rln "\.echo-plugin" --include="*.rs" echo-agent echo-agent-cli
find echo-agent echo-agent-cli -name "*.rs" | grep -i plugin
grep -rn "unregister_skills_by_source" --include="*.rs" echo-agent echo-agent-cli
grep -rn "register_plugin_hooks" --include="*.rs" echo-agent echo-agent-cli
grep -rn "wire_skills\|wire_hooks\|wire_mcp" --include="*.rs" echo-agent echo-agent-cli (callers)
grep -rn "NativePlugin" --include="*.rs" echo-agent echo-agent-cli (impls/callers)
grep -rn "PluginRuntimeService" --include="*.rs" echo-agent-cli/src (entry points)
grep -rn "plugin_manifests|discover_plugin_manifests" --include="*.rs" echo-agent-cli (consumers)
```

## Expected Result

- One framework authority: `echo-core/src/plugin/{mod,manifest,registry,scope,lifecycle,
  capability,variables}.rs` + facade `echo-agent/src/plugin.rs`.
- EKO consumes the framework types only through `PluginRuntimeService` /
  `PluginIntegrator`; no hand-rolled manifest/registry/lifecycle state machine in EKO.
- Skill unload and hook unload each have one call path.
- `wire_skills`/`wire_hooks`/`wire_mcp` and `NativePlugin` have zero in-repo callers
  (retained public facade options).

## Result

- Summary:

    example + EKO `plugin_runtime.rs` / `plugin_components.rs` + CLI/Tauri command
    surfaces. No second registry implementation.
  - `PluginManifest`/`PluginLifecycle`: only `echo-core/src/plugin/*` and the facade.
  - `unregister_skills_by_source`: one definition
    (`echo-agent/src/agent/react/capabilities.rs:915`), one production caller

  - `register_plugin_hooks`: one definition (`echo-execution/src/skills/hooks.rs:610`),
    callers only in facade `plugin.rs:294,424` and tests.
  - `wire_skills`/`wire_hooks`/`wire_mcp`: zero callers anywhere in either repo
    (grep returned no matches outside their definitions).
  - `NativePlugin`: zero impls and zero callers.
  - `PluginRuntimeService` is consumed by TUI (`tui/mod.rs`, `tui/events.rs`), CLI

    surfaces; the single service instance is constructed once at
    `echo-agent-app-core/src/runtime.rs:279-280`.
  - `config_discovery.rs` scans `.echo-plugin/manifest.yaml` files into a

  - `skills_hub` (EKO skill marketplace) and `hook_config_loader` (user hook merging)
    are distinct concepts (skills, not plugins) — no semantic overlap found.
