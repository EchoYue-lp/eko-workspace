## Claim

The EKO reload transaction (`apply_candidate`) rolls back atomically on activation
failure and does not leak registrations across reload/unload; the framework
`PluginLifecycleManager` never retains a registration that blocks re-registration or
that outlives its plugin.

## Method

Static trace of `PluginRuntimeService::apply_candidate`
(`echo-agent-cli/echo-agent-app-core/src/plugin_runtime.rs:551-802`) and
`PluginLifecycleManager` (`echo-core/src/plugin/lifecycle.rs`), cross-checked against
the in-repo lifecycle tests (plugin_runtime.rs:1484-1884). No source modifications.

Inspection points:
1. Pre-flight failures (`prepare_application_components`, `validate_agent_collisions`,
   `prepare_lsp`) occur before any state mutation — candidate is a fresh registry.
2. `deactivate_all` failure path (575-588): reactivates previous set, shuts down
   replacement LSP, returns error without swapping state.
3. Monitor replacement failure path (590-604): rollback via `rollback_plugin_monitors`
   (1211-1234), reactivates previous lifecycle.
4. Component swap (`replace_agent_components`, 804-909): unload previous -> wire
   candidate; on wiring error, unloads the partially-wired candidate
   (`wiring.components_by_plugin` + `candidate_prepared`) and re-wires the previous
   registry; subagent registration failure similarly rolls back; restore errors are
   aggregated.
5. Post-swap activation failure (655-719): deactivate_all, rollback agent components and
   monitors and LSP, reactivate previous lifecycle.
6. Success path: previous LSP shut down (721), preferences persisted, PluginLoaded
   events fired (790).
7. `PluginLifecycleManager::activate` (lifecycle.rs:98-118): init exactly once, activate
   exactly once per transition; failure leaves `active=false` so retry re-activates.
8. `unregister` (lifecycle.rs:153-179): entry removed BEFORE callbacks run; a failed
   cleanup still removes the stale registration (test `failed_unregister_still_removes_stale_registration`).
9. Stale-registration scenario: `reload()` when a plugin's manifest becomes invalid —
   candidate scan skips it (registry.rs:202-216), `deactivate_all` (lifecycle.rs:137-147)
   deactivates but never removes the entry; the entry stays registered-inactive;
   `register` (lifecycle.rs:80-85) then rejects a re-registration with "Lifecycle
   callbacks already registered". Self-heals on the next reload that reactivates the
   plugin, and `uninstall` calls `lifecycle.unregister` (plugin_runtime.rs:333).

## Expected Result

- Any failure before/after the component swap leaves the live agent, registry, monitors,
  LSP manager, and lifecycle in the previous state; errors are surfaced.
- No registration survives the unload of its owning plugin.
- A failed cleanup never leaves a stale registration behind.

       `failed_real_reload_restores_previous_live_components`,
       `activation_failure_restores_previous_components_and_lifecycle`,

  9. DEVIATION FOUND (finding F-PLG-01-P3-02): a reload that drops a plugin (invalid

       but inactive; a later `register_lifecycle` for that plugin fails with "already
       registered". Severity is limited: no production caller of `register_lifecycle`
       exists in either repo (V02-01), the entry is removed on `uninstall` and
       reactivated on the next successful reload, and the error is explicit, not silent.
  10. Partial-MCP-connect cleanup verified: `wire_all` records connected servers in
       `components_by_plugin` even when a sibling server fails (plugin.rs:330-358 marks
       the plugin failed); the EKO failure path unloads `wiring.components_by_plugin`,
       so a half-connected client is disconnected during rollback — no leak.

## Deviations

## Conclusion

Supports: the reload/unload/rollback transaction is atomic and leak-free for all
component types; lifecycle callbacks are driven exactly once per transition; the only
retention anomaly is the session-scoped inactive lifecycle entry (P3-02). Does not
prove: behavior under real LLM/MCP clients (fixtures use `MockLlmClient` and a fake LSP
server) or cross-process persistence (registry state merge is unit-tested at the
framework level, V04-01).
