## Claim

Compression preserves (a) tool-call/result pairing (protocol pairs), (b)
instructions (canonical reinjection), (c) active tasks and recent evidence, (d)
recovery facts, and stays within the token window under repeated compression,
with UTF-8-safe and overflow-safe arithmetic.

## Method

Static inspection of every compressor plus the ContextManager pipeline, focused
on the five sub-claims. Files inspected (full reads): echo-state/src/compression/
`mod.rs` (2584), `compressor/{sliding_window,summary,hybrid}.rs`, `horizon.rs`,
`levels.rs`, `verifier.rs`, `invariants.rs`; echo-core/src/compression.rs;
echo-agent/src/{compression.rs,config.rs (compressor sections),memory_promoter.rs};
echo-agent/src/agent/react/{mod.rs:322-384,939,capabilities.rs:563-612};

## Expected Result

- Tool pairs contiguous after every compression + sanitize pass.
- Canonical instructions re-injected verbatim and matching current agent state.
- Protected content (EKO task brief, projections) survives compression.
- Repeated compression converges to a bounded token count <= token_limit.
- No UTF-8 byte-slice panics; no integer overflow on realistic inputs.

## Result

- Exit code: not applicable (static inspection)
- Summary of verified facts (full evidence in the task report findings):
  1. Tool pairs: the post-compression sanitizer
     (`sanitize_tool_call_pairing`, mod.rs:1562-1709) removes orphaned tool
     results, clears dangling tool_calls, and appends placeholders — correct
     for all boundary splits produced by SlidingWindow/Summary/Horizon
     (messages keep original order). EXCEPTION: AdaptiveCompressor L1 fold
     (levels.rs:392-396) inserts a `Role::User` fold-summary between an
     assistant tool_calls message and its kept tool results; the sanitizer
     never reorders, so the framework-declared contiguity invariant
     (mod.rs:1552-1557: "Every assistant message with tool_calls must be
     followed by tool messages") is violated on the adaptive path.
  2. Instructions: canonical reinjection (mod.rs:877-929) inserts the
     canonical system prompt at index 0 when absent and re-injects
     `to_reinjection_messages` (rules truncated via `chars().take(2000)`,
     echo-core/src/compression.rs:385; skill_injections dead — never emitted,
     initialized `Vec::new()` at react/mod.rs:379). `add_skill`
     (capabilities.rs:587-597) updates the live system message
     (`update_system`) but not the canonical copy — the first compression
     after `add_skill` re-inserts the stale pre-skill prompt. Independent
     confirmation of F-CTX-01-P2-02 (chains re-traced, not copied).
  3. Active tasks/recent evidence: protected markers + projection envelopes
     survive via split_protected/merge_protected (mod.rs:747-793) and the
     sanitizer leaves them untouched; EKO task brief rides the replaceable
     marker (compact_context.rs) and the runtime-recovery capsule rides
     pre-model projections (same file). `CompressionInput.current_query` —
     documented as "used to protect active task context from eviction"
     (echo-core/src/compression.rs:45) — is read by no compressor and passed
     as `None` on the live path (compact.rs:60): dead protection field.
  4. Repeated compression: (a) SlidingWindow/Summary early-return when
     `conv_msgs.len() <= window` (sliding_window.rs:48-66, summary.rs:299-317)
     regardless of tokens — compression stalls above the limit; (b) no
     post-compression token check in `prepare` (mod.rs:1317-1538) — the
     verifier's P0 check only asserts `after <= before` (verifier.rs:100-120),
     never `<= token_limit`; (c) SummaryCompressor appends a new
     Role::System summary per pass (summary.rs:346-348) and never merges or
     expires previous summaries (all system messages survive every pass,
     sliding_window.rs:41-45) — the system region grows by ~1 summary per
     compression, unbounded; (d) Horizon pre-pass is best-effort and the only
     pass that can reduce before the main compressor.
  5. Verifier fallback (mod.rs:1464-1515): on P0 fail the LLM summary is
     discarded and the ORIGINAL messages are window-cut at 40 without calling
     the memory promoter for the newly evicted set — messages in the
     [last 40 .. last 20] band are lost from both context and memory on a
     heuristic false-fail (keyword checks, verifier.rs:134-190).
  6. UTF-8 safety: `safe_truncate` (levels.rs:23-35) is char-boundary safe;
     `to_reinjection_messages` uses `chars().take`; all other truncations use
     `chars()` or `.len()` comparisons (no slicing panics). One production
     byte-slice found: `&cp.checkpoint_id[..8]` (hybrid.rs:95) — provably safe
     because `checkpoint_id` is an ASCII UUID (echo-core/src/compression.rs:122)
     but violates the repo's no-byte-slicing rule.
  7. Byte-vs-char token estimates: horizon `build_compact_summary`
     (horizon.rs:295-296) and L1 snip `char_limit = max_tokens * 4`
     (levels.rs:348) apply byte budgets to CJK content — CJK over-truncation,
     no panic; verifier keyword filter `w.len() > 3` is byte-based
     (verifier.rs:146).
  8. Overflow: all arithmetic in the compression pipeline is saturating or
     length-guarded except `target_tokens * 2` (levels.rs:226,316) — safe for
     realistic token limits, unchecked in theory.

## Deviations

No dynamic run exercised the AdaptiveCompressor fold or a repeated-compression
session end to end; provider-level rejection behavior (OpenAI contiguity) is
external and argued from the framework's own declared invariant plus provider
documentation knowledge, not executed here.

## Conclusion

P1-02 (summary accumulation), P1-03 (adaptive L1 fold breaks pairing
contiguity), P2-01 (verifier fallback discards summary and skips promotion),
P3-01 (horizon `mem::take` wipe on error), P3-03 (byte-based estimates /
byte-slice style), and the independent confirmation of F-CTX-01-P2-02 arms.
Also supports the negative claims: protected-content survival and UTF-8/overflow
safety hold (no finding).
