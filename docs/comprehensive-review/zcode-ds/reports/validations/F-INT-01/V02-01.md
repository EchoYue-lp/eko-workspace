## Claim

production entry points (definition -> registration -> live caller), and the
transport-level receive paths are wired to real consumers.

## Expected Result

Live paths: EKO startup loads `mcp.json` -> `Agent::load_mcp_from_file` ->
`McpManager::connect` -> `McpClient::new` handshake -> `McpToolAdapter`
registered into the shared `ToolManager`; GUI/TUI connect/disconnect commands
reach the same chain; the plugin integrator wires MCP per plugin. The client
receives and consumes server->client messages through `McpTransport::
notification_rx` and the 202-async-response channel.

## Deviations

practice: the notification channel (`notification_rx`) and the HTTP 202
async-response routing. Both become findings (F-INT-01-P1-01, P2-02).

## Conclusion

browser sidecar) are live. Does not support: server->client notification
consumption (absent) or HTTP async-response delivery (absent).
