## Claim

MCP transport lifecycle, schema adaptation, disconnect, reconnect, and
cancellation invariants hold under malformed/disconnected-server and edge-case
conditions, and the code is panic/UTF-8 safe per AGENTS.md.

## Method

Full reads of `echo-integration/src/mcp/transport/{stdio.rs,http.rs,sse.rs}`,
`client.rs`, `tool_adapter.rs`, `server.rs`, `config_loader.rs`; targeted grep
for panic-prone constructs (`.unwrap(`, `.expect(`, byte slicing `&s[..`,
direct indexing) inside `echo-integration/src/mcp`; comparison of declared
capabilities vs implemented handlers; check of pending-request cleanup on every
error path; UTF-8 boundary analysis of SSE chunk parsing.

## Expected Result

- No panics on malformed input (parsing uses `serde_json::from_value` with
  error mapping; `unwrap_or` fallbacks).
- Pending-request maps are cleaned on every failure path.
- Declared client capabilities have handlers.
- Cancellation reaches the server (MCP `notifications/cancelled`).
- Disconnected-server fixtures would be covered by tests (checked in V04-02:
  no client/transport/reconnect/cancellation tests exist).

## Result

- Exit code: not applicable (static inspection)
- Summary of findings:
  - Panic scan: no `.unwrap()`/`.expect()`/byte-slicing panic candidates on
    any external-input path in the MCP module. `http.rs:115-130` backoff math
    is overflow-safe (max exponent 2). `sse.rs:219-221` slices `buffer[..pos]`
    at the `\n\n` separator, which is always an ASCII boundary — safe. The
    `buffer[..pos]` / `buffer[pos+2..]` slicing cannot split UTF-8.
  - **UTF-8 chunk-split defect (SSE)**: `sse.rs:210-215` calls
    `std::str::from_utf8(&chunk)` on each network chunk; a multi-byte UTF-8
    sequence (e.g., Chinese text in a tool result) split across chunk
    boundaries fails decoding, `run_sse_loop` returns `Err`, the stream is
    torn down and reconnected with backoff (up to 5 attempts), and the
    in-flight requests hang until the 30 s timeout (`sse.rs:371-383`). Only
    `\n\n` is recognized as the event separator (`sse.rs:219`); CRLF
    servers are never parsed. (F-INT-01-P2-01)
  - **Dead 202/async path (HTTP)**: on `202 Accepted` the transport waits on
    a oneshot that nothing ever fires (`http.rs:161-179`); every such call
    fails after exactly 60 s. 200-with-SSE bodies fail JSON parsing
    (`http.rs:193-198`) even though the `Accept` header advertises
    `text/event-stream` (`http.rs:82`). (F-INT-01-P1-01)
  - **Retry-bypasses-side-effect-gate (HTTP)**: the retry loop
    (`http.rs:96-147`) re-POSTs on ambiguous failures (`is_retryable_error`
    `http.rs:251-270` matches "connection reset", "broken pipe", "eof", 5xx)
    before the framework's `ToolFailure::allows_automatic_retry` /
    side-effect classification (`echo-core/src/tools/mod.rs:154-162,165-260`)
    can gate it; a side-effecting `tools/call` that reached the server can be
    executed twice. (F-INT-01-P1-02)
  - **Declared-but-unhandled client capabilities**: `build_client_capabilities`
    declares roots.listChanged, sampling, elicitation (`client.rs:149-158`);
    no transport has a handler for server-initiated requests — stdio
    misparses them as responses and drops them (`stdio.rs:104-122`), SSE drops
    them as "unknown format" (`sse.rs:305-307`), HTTP has no inbound channel;
    `notification_rx` is never consumed. (F-INT-01-P2-02)
  - **Cancellation not implemented**: the adapter's `execute` never observes
    `ToolContext.cancel` (`tool_adapter.rs:151-204`); no `notifications/
    cancelled` is ever sent for a real cancel (the only emission,
    `http.rs:232-234` in `close()`, sends it without the spec-required
    `requestId` param); the server handler for it is a log-only no-op
    (`server.rs:306-308`). (F-INT-01-P2-03)
  - **Pending-map leaks (SSE/stdio)**: SSE `send` error paths do not remove
    the pending entry — POST failure (`sse.rs:353-358`) and 30 s timeout
    (`sse.rs:371-383`); `close()` (`sse.rs:415-421`) clears neither pending
    nor fails in-flight requests. stdio write-error returns without removing
    the entry (`stdio.rs:194-206`), bounded by the EOF drain. (folded into
    F-INT-01-P2-01/P3)
  - **Reconnect semantics (manager)**: same-name reconnect replaces the
    client (`mod.rs:73-97`) but previously returned `McpToolAdapter`s keep the
    old dead client; a failed re-connect leaves the old connection already
    destroyed. The agent-level path (`capabilities.rs:1153-1162`) handles tool
    cleanup correctly. (F-INT-01-P3-01)
  - **Server adapter lossiness**: `handle_tools_call` drops `ToolResult.data`/
    structured kind (`server.rs:446-468`); `resources/read` returns the
    placeholder text `Resource: {name}` (`server.rs:512-517`); `prompts/get`
    always returns empty messages (`server.rs:561-564`); builder silently
    overwrites duplicate tool names while advertising both
    (`server.rs:653-669`). (F-INT-01-P3-02)
  - Schema adaptation: `McpTool.input_schema` is passed through verbatim as
    `Tool::parameters()` (`tool_adapter.rs:132-134`), and `Tool::parameters()`
    becomes `McpTool.input_schema` on the server side (`server.rs:657-667`) —
    lossless JSON-Schema passthrough; MCP `annotations` map to
    `ToolRiskLevel` (`tool_adapter.rs:139-149`), aligned with the per-tool
    risk authority (F-EXT-01 direction).

## Deviations

None beyond the findings listed; the invariant "pending maps are cleaned on
every failure path" does NOT hold for SSE/stdio failure paths (leaks), and the
"declared capabilities have handlers" invariant does not hold.

## Conclusion

Supports: panic/UTF-8 safety of all parsing paths; schema passthrough is
lossless; stdio disconnect handling drains pending requests with typed errors
(-32000, `stdio.rs:129-141`). Does not support: HTTP async-response delivery,
SSE robustness on multibyte/CRLF input, cancellation propagation, or
notification consumption — each becomes a finding with V02-01 evidence.
