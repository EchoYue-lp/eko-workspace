## Claim

Definition -> registration -> dispatch reachability is one chain: loader
`discover_subagents` -> `register_default_subagents` (primary and every
pooled agent) -> framework `SubagentRegistry` + host dispatch catalog, with
the EKO catalog snapshot injected into the system prompt before build; plugin
subagents register into the same registry post-hoc; TaskRuntime reads the
registry for runtime contracts.

## Expected Result

- Every `.md` definition reaches the framework registry once per agent build;
  catalog and registry derive from the same `discovered_subagents` vector.
- Default-route validation runs before build and can fail agent creation.
- Plugin agents enter the same registry post-build; unload unregisters them
  (`unload_agent_components`, plugin_runtime.rs:1157-1174).
- Pooled agents re-run the full chain at creation time.

## Result

- Exit code: not applicable (static trace)
- Duration: ~45 min including context reads
- Summary:
  - Primary + every pooled agent run the identical discovery/validation/
    registration chain; `create_agent_with_diagnostics` is the single
    construction entry (`agent_pool.rs:850`).
  - `validate_default_subagent_routes` (`profiles.rs:139-151`) iterates all
    profiles x kinds, skips `"primary"`, errors on any missing name; wired
    with `?` at `infra.rs:249-251` -> agent creation hard-fails if a builtin
    role is missing.
  - Registration failures inside `register_default_subagents` do NOT fail
    creation: `Err(err) => tracing::warn!(...)` and the role is skipped
    (infra.rs:836-841); the catalog prompt already contains the role name.
  - Plugin registration is post-build (PluginRuntimeService::new on
    `runtime.rs:279-280`, after agent construction); reload/rollback paths
    re-register candidates or the previous set and `unload_agent_components`
    unregisters by name (plugin_runtime.rs:1157-1174 + capabilities.rs:406).
  - `from_registered` (register.rs:37/:55) runs after plugin activation in
    normal boot order (main.rs:177/desktop.rs:201), so the task capability
    catalog includes plugin roles; the build-time snapshot used by the
    system prompt and the boot-time task-tool catalog (infra.rs:509-515)
    never includes plugin roles.
  - Framework registration updates the host agent's dispatch catalog
    (capabilities.rs:377-401) but never the EKO snapshot.

## Deviations

None observed; the two catalog projections (build-time snapshot vs
`from_registered`) diverge for plugin roles — recorded as findings
A-SUB-01-P2-02/P3-01.

## Conclusion

Supports: single registration chain into one framework registry; startup
route validation wired and effective at name level; plugin path reaches the
same registry; pooled agents rebuild the chain. Does not prove: dynamic
reload (none exists — V03), or that a role skipped at registration is
rejected (it is not — P3-02).
