## Claim

The EKO file types and the framework task types round-trip field by field:
every field of the framework `Task` (`TaskSpec` + `TaskExecution` + `TaskClaim`)
is preserved through both conversion directions (`EkoTaskSpec`/`PlanTask` ->
framework, framework -> EKO), including the EKO metadata carried inside
`TaskSpec.metadata`, for every value the live paths can produce.

## Method

Static field-by-field comparison of every conversion direction, plus the
existing round-trip tests run as executable evidence:


## Expected Result

- `execution_checks`/`acceptance_criteria`/`required_artifacts` stay distinct
  fields in both directions (never flattened, no second validator);
- EKO-only fields (`domain_profile`/`parallel_group`/`sort_order`) survive the
  framework round trip through `TaskSpec.metadata` (serde JSON identical in
  both writers);
- status mapping is total over every status the live paths can produce;
- `spec.id == execution.task_id` enforced on both write and read.

## Result

- Exit code: 0 (the executable round-trip tests in V04 pass; this report is
  the static half)
- Summary:
  1. Spec fields 1:1: `id/title/description/kind/agent_role/depends_on/files/
     allowed_tools/required_artifacts/execution_checks/acceptance_criteria/
     max_retries` map one-to-one in both directions
     (`to_task_spec` types.rs:892-914, `to_task` :1117-1159, `try_from`
     :1162-1200, `load_revisioned_task_graph` store.rs:702-725).
  2. `kind` maps bijectively via `PlanTaskKind::to_task_kind`/`from_task_kind`
     (types.rs:334-358; 8 == 8 variants).
  3. EKO metadata: `EkoTaskMetadata {domain_profile, parallel_group,
     sort_order}` is serialized into `TaskSpec.metadata` by `to_task_spec`
     (types.rs:893-898) and reconstructed field-for-field by `PlanTask::try_from`
     (:1173-1174) and `compare_and_commit_revisioned_task_graph`
     (store.rs:804-814, :830). `PlanTask::to_task` builds the identical JSON
     object (:1118-1134), so `TaskSpec::stable_hash` is writer-independent.
  4. Execution fields 1:1: `task_id/status/retry_count/failure_fingerprint/
     claim` (types.rs:1081-1089, :1151-1157, store.rs:718-724). The framework
     `TaskStatus` is stored verbatim in `run-state.json` (`EkoTaskExecution
     .status` types.rs:921-929) and reconstructed on read-back; events carry
     `TodoStatus + status_detail + claim`, which the fold restores exactly
     (event_rebuild.rs; test `rebuild_reflects_task_patch` passed in V04).
  5. Status space: `TodoStatus::try_from_task_status` covers 8 of the 10
     framework states; `Retrying`/`Paused` error out (:434-437) and
     `project_task_status` collapses them to Running/Blocked (:443-456).
     Producer grep: `TaskStatus::Retrying` has ZERO construction sites in
     either repository; `TaskStatus::Paused` is constructed only in the
     production-unreachable legacy `manager.rs:446` (F-TSK-01-P3-01). So the
     mapping is total over the reachable state space; the two unrepresentable
     states are latent (A-TSK-01-P3-01).
  6. Patch ops: `TaskUpdateOperation {Insert, Update, Skip, Reorder}` maps
     onto `TaskPlanPatchOp` 1:1 (types.rs:1287-1309); `TaskPatch` has the same
     11 optional fields as `TaskSpecPatch` (types.rs:1221-1232 vs
     revisioned.rs:78-90). `SetStatus` exists only on the framework op enum
     (revisioned.rs:109-112) and is disabled in EKO
     (`EkoTaskToolPolicy` does not override `allow_manual_progress_updates`,
     framework default false, revisioned.rs:275-277).
  7. Commit round trip: `TaskGraphCommit -> PlanRevision + effects
     (skipped/reset/created task ids) -> PlanRevisionCommitted event ->
     read-back reproduces the framework snapshot` (store.rs:845-884,
     :676-749), with `spec.id == execution.task_id` enforced on both write
     (store.rs:808-813) and read (types.rs:1167-1172).

## Deviations

One silent-loss path exists on the READ side that the round-trip tests do not
cover: in `load_revisioned_task_graph`, a plan task with no entry in
`run-state.json` is silently materialized with a fabricated
`EkoTaskExecution::pending(...)` (store.rs:694-696 `unwrap_or_else`). This is
unreachable in the consistent steady state (both files are rewritten from the
same event stream) but reachable inside the plan.json-new / run-state.json-old
crash window of A-TSK-01-P2-01, where it violates losslessness by inventing
state instead of erroring or rebuilding. Recorded as finding
X-TSK-01-P3-01; the shared fix is A-TSK-01-P2-01's read-side rebuild.

## Conclusion

Supports: the conversion is thin and lossless for every field and every
status the live EKO paths can produce, in both directions; the EKO-only
metadata round-trips inside the framework extension point; there is no field
flattening that would require a second validator. It does not prove the
framework-side patch semantics (F-TSK-01/02) or executor status writes
(A-TSK-03/04) — those were consumed as dependency reports.
