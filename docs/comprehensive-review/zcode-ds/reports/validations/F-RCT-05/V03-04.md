## Claim

Corrupted or incomplete snapshots are handled without losing the canonical
conversation context: a bad checkpoint surfaces an explicit error and the
fallback preserves prior state.

## Method

Trace the two failure classes end to end:

1. Corrupt checkpoint FILE: `FileRuntimeStateStore::get_checkpoint`
   (state/file.rs:151-168) — `serde_json::from_str` error → `Err(...)`;
   caller `resume_from_state_store` propagates (react/mod.rs:1689 `?`);
   caller `restore_thread_context` (context.rs:236-249): `Err(e)` → warn
   "Failed to load RuntimeStateStore checkpoint, starting from empty context"
   → `reset_messages()` (context.rs:216-228: `ctx.clear()` + push system
   prompt + SessionStart hook).
2. Structurally-invalid checkpoint (unpaired tool calls — the mid-batch
   cancel/error case from V03-03): `restore_messages` →
   `validate_tool_message_pairing` → `Err` (state/mod.rs:157-168, 221-230) →
   same fallback as (1).
3. Missing checkpoint: `Ok(None)` → `reset_messages()` (context.rs:241-244).

Also inspect `restore_messages` error type: `ReactError::RuntimeState(
SerializationError)` (state/mod.rs:159-165, 233-237).

## Expected Result

Per the framework's own hardened-file precedent (F-MEM-01: FileConversationStore
surfaces explicit corrupt-file errors) and the AGENTS.md "prevent unintended
data loss" rule, a rejected checkpoint should (a) be surfaced loudly, and
(b) not silently discard the in-process context / prior state.

## Result

- Exit code: not-applicable (static inspection)
- Duration: ~10 min
- Summary:
  - Both failure classes follow the same path: warn! + `reset_messages()`
    (context.rs:245-248). In-process, this WIPES the full conversation
    context (all messages, plan, tool results) down to the system prompt —
    the framework explicitly replaces prior state instead of preserving it.
    After a restart the context is empty anyway, but the same wipe happens
    mid-session on the EKO path because Execute mode restores at every turn
    start (V02-01).
  - The error is a warning only (`tracing::warn!`); no error propagates to
    the caller of the turn (drive_chat sees a normal stream), so EKO surfaces
    see a "successful" turn that forgot the conversation.
  - Corrupt-file handling diverges from the hardened precedent: the file is
    not moved aside, and the next `save_checkpoint` atomically overwrites it
    (state/file.rs:170-187), destroying the only copy of the checkpoint
    (recoverable only by manual file surgery). F-MEM-01-P1-01 documented the
    same silent-overwrite class for `FileStore`; here the overwrite is
    deliberate write-ahead but the failure is silent.
  - `working_dir`/`blocked_reason`/`plan` are simply not restored on error —
    no partial hydration exists.

## Deviations

None.

## Conclusion

Supports finding F-RCT-05-P1-01 (incomplete checkpoint → full context wipe on
the very next turn; silent to the user) and F-RCT-05-P3-01 (corrupt checkpoint
file is overwritten without backup or user-visible error). The "corrupted /
incomplete snapshot handling" required validation shows the fallback is
lossy by design.
