## Claim

Every interrupt/cancel path ends at a "safe point" whose persisted checkpoint
is restorable — i.e., the checkpoint saved by each interrupt arm contains only
paired tool call/result messages.

## Method

Inventory of every checkpoint site and every interrupt path in the shared loop
(stream_channel.rs run_core_loop :494-757 and phases), then for each
interrupt arm, compare the message state at checkpoint time against the
pairing requirement of `validate_tool_message_pairing` (state/mod.rs:186-231).

Checkpoint sites:
- compact.rs:35 (every iteration, before `ContextManager::prepare`)
- tools.rs:203 (concurrent batch, cancel grace elapsed)
- tools.rs:258-262 (concurrent batch, per-tool error)
- tools.rs:296 (concurrent batch, cancel observed after drain)
- tools.rs:309 (serial batch, pre-loop cancel check)
- tools.rs:336 (serial batch, cancel grace elapsed)
- tools.rs:414 (serial batch, per-tool error)
- tools.rs:419 (serial batch, cancel observed after tool)
- tools.rs:429 (batch completion)
- tools.rs:438-440 (periodic, `react_checkpoint_interval`)
- finalize.rs:79 (tools-branch terminal), :164 (text terminal),
  :251 (max-iterations terminal)

Interrupt paths:
- cancel during think/LLM stream → `ThinkOutcome::Cancelled` → driver returns
  `Ok(())` (stream_channel.rs:605-610; think.rs:42-50) — no new checkpoint.
- cancel during tools → grace 5 s → checkpoint with reason "Tool batch
  cancelled" → `IterOutcome::Abandoned` (tools.rs:203-205, 295-300,
  309-312, 336-339, 418-423).
- tool error mid-batch → checkpoint with reason "Tool error: {fname}"
  (tools.rs:258-262, 414-415) while peer/in-flight calls may lack results.
- batch timeout → `try_send(Err)` only, no checkpoint (tools.rs:284-292);
  when the consumer drops the stream, the whole loop task is dropped with no
  checkpoint — last checkpoint is this iteration's compact (pre-batch).
- process kill at any point → last persisted checkpoint wins.

The assistant-with-tools message is pushed BEFORE any tool executes
(tools.rs:101-113), so at every cancel/error checkpoint the context contains
the full call list; calls without a pushed `Message::tool_result` are
"unpaired".

## Expected Result

All interrupt checkpoints are restorable (pairing validator passes).

## Result

- Exit code: not-applicable (static inspection; dynamic confirmation in V04-04)
- Duration: ~15 min
- Summary:
  - CLEAN sites: compact.rs:35 (only after a completed batch — all prior
    calls paired; note the *same* iteration's tools run after this checkpoint),
    tools.rs:429/:438-440 (all results pushed), finalize.rs:79/:164/:251
    (batch complete or text branch — no dangling calls).
  - POISONED sites (contain result-less assistant tool calls): tools.rs:203,
    296, 309, 336, 419 (cancel) and tools.rs:258-262, 414 (tool error) —
    in-flight concurrent tools or not-yet-run serial tools have no results at
    checkpoint time. `validate_tool_message_pairing` then rejects the whole
    checkpoint ("checkpoint has tool calls without results", state/mod.rs:221-230).
  - Cancel during think: safe (no side effects to replay; last checkpoint is
    the clean pre-think compact checkpoint).
  - The poisoned checkpoint persists beyond the interrupted turn: the next
    turn's compact checkpoint (compact.rs:35) is taken BEFORE
    `ContextManager::prepare` runs `sanitize_tool_call_pairing`, so the
    dangling calls are re-serialized into the next checkpoint too; the context
    is only sanitized after that checkpoint. Self-healing requires a second
    checkpoint after the sanitizing prepare.
  - No interrupt checkpoint is guarded by pairing validation at SAVE time —
    validation exists only on the restore side.

## Deviations

None. The poisoned-checkpoint behavior is exactly what the code produces; the
dynamic probe (V04-04) confirms it end-to-end.

## Conclusion

Supports finding F-RCT-05-P1-01: the two interrupt families the framework
explicitly checkpoints for ("Tool batch cancelled", "Tool error") write
checkpoints that `restore_messages` rejects, so resume fails exactly at the
"safe points" the design intends to be recoverable. Cancellation during
think is genuinely safe; cancellation/error during a tool batch is not.
