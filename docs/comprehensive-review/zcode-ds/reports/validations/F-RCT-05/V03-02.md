## Claim

Resume "skips completed side effects by call_id" — the mechanism documented in
MASTER-PLAN (lines 67, 96, 147, 185) — is implemented: completed tool call ids
are consumed by a resume-side skip decision.

## Method

Grep both repositories for every consumer of `completed_tool_call_ids` and for
any skip/replay-guard keyed on tool call ids in the resume path; inspect the
resume path (react/mod.rs:1680-1752) and the loop's tool execution entry
(phases/tools.rs:50-443) for any "already completed" check.

```text
grep -rn "completed_tool_call_ids" echo-agent/src
grep -rn "call_id" echo-agent/src/agent/react/mod.rs echo-agent/src/agent/react/run
grep -rn "replay\|skip\|already done\|重复执行" echo-agent/src/agent/react echo-agent/src/state
```

## Expected Result

`completed_tool_call_ids` (or an equivalent) gates re-execution on resume, so a
completed write tool is never re-issued after a checkpoint that post-dates it.

## Result

- Exit code: not-applicable (static inspection)
- Duration: ~10 min
- Summary:
  - `completed_tool_call_ids` has exactly one production consumer site,
    `resume_from_state_store`, used only for logging: a `CheckpointResumed`
    trace event (react/mod.rs:1731-1737) and a `tracing::info` line
    (:1741). No code path uses it to skip, filter, or gate anything.
  - The resume path restores the full message list verbatim
    (`set_messages`, react/mod.rs:1694). The model then "sees" completed
    results as history; there is no framework-level guarantee that the model
    will not re-issue a completed call, and no idempotency key is attached to
    the resumed context.
  - The loop's tool branch (`run_tools`) has no "already completed" check:
    every call the model emits is executed (tools.rs:130-443). The only
    protection is checkpoint freshness — if the checkpoint post-dates the
    completion, results are present and the model normally does not repeat
    them; if the checkpoint predates the completion (process killed
    mid-batch, batch-timeout channel-close drop, tools.rs:284-292 with no
    checkpoint), the completed side effect is invisible to the model and can
    be re-issued.
  - `validate_tool_message_pairing` (state/mod.rs:186-231) is the inverse
    protection: it rejects histories with *missing* results instead of
    providing partial skip (V03-04).

## Deviations

None; the claim is simply not implemented.

## Conclusion

Supports finding F-RCT-05-P2-01: the documented call_id-based completed-tool
skip does not exist; the "skip" is implicit (model-behavior-dependent) and the
validator rejects whole checkpoints instead. The framework's own test
`resume_records_checkpoint_origin_and_completed_tools_in_trace`
(stream_channel.rs:1634-1711) verifies the trace event only, not a skip
decision.
