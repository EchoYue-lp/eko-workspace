## Claim

`redact_secrets`/`contains_secrets` (echo-agent/src/security.rs) are invoked at every framework sink where tool output, tool-call args, or trace events could carry credentials, so secrets cannot reach tracing logs / persisted events via the primary paths; residual leak paths are enumerated.

## Method

1. `grep -rn "redact_secrets|scan_secrets|contains_secrets"` across `echo-agent` (excluding tests).
2. Read each call-site context: `src/tools/builtin/spawn_task.rs:155-185`, `src/trace/mod.rs:426-442` (`RunEvent::new_tool_call`), `src/agent/snapshot.rs:878-920`, `src/agent/react/run/execution.rs:221-260`, `src/agent/react/run/pipeline.rs:691-710` (OutputGuardStage), `src/agent/react/run/stream_channel.rs:120-175` (Input guard only).
3. Checked the live vs dead status of the two `check_tool_output_guard` variants (`#[allow(dead_code)]` at execution.rs:225; live call at pipeline.rs:707).
4. Checked trace-event payloads: `LlmCall` carries token counts only (`src/trace/mod.rs:252-264`); `ToolCall` args redacted at construction.
5. Grepped for raw `tracing::*` lines logging URLs/output in web fetch paths.

## Expected Result

Live redaction points: output guard stage (tool output before event/LLM), tool-call args in trace events, spawn-task stdout/stderr, snapshot tool-output truncation; no unredacted secret-bearing sink on the main path; residual paths are minor and local-only.

## Result

- Exit code: not-applicable (static inspection)
- Summary:
  - Live sinks with redaction: `pipeline.rs:707` → `snapshot.check_tool_output_guard` (`snapshot.rs:885-886` redacts before guard check); `trace/mod.rs:434` (`new_tool_call` redacts args, `pipeline.rs:480` is the live producer); `spawn_task.rs:171,175` redacts background-task stdout/stderr; `snapshot.rs:885-886` truncation path.
  - Dead duplicate: `execution.rs:225` `#[allow(dead_code)]` on `check_tool_output_guard` (same logic as the live snapshot variant) — finding F-SEC-01-P3-07.
  - `LlmCall` trace events carry no request/response payload (token aggregates only) — no leak surface.
  - Residual paths (all local-only, low impact):
    a. `echo-tools/src/web/fetch.rs:203` logs the raw URL (`tracing::info!("WebFetch: url='{}' ...")`) — a URL with embedded credentials (`https://user:pass@host/`) lands verbatim in the trace log; the "Password in URL" pattern exists in `security.rs:58` but is not applied at this site — finding F-SEC-01-P3-11.
    b. `new_tool_call` fallback `serde_json::from_str(&redacted).unwrap_or(v)` (`trace/mod.rs:439-440`) falls back to the unredacted original if redaction ever breaks JSON — replacement text is JSON-safe in practice, so the fallback is nearly unreachable.
    c. Guard LLM review (`echo-core/src/guard/llm.rs:81-90`) sends the content under review to the review LLM unredacted — by design (the review needs the content).
  - No redaction exists for model final answers on the framework side (no payload persisted in events); EKO-side sinks are out of this task's scope (A-* tasks).

## Deviations

None beyond the residual paths listed above.

## Conclusion

Supports: primary framework sinks (tool output → events/LLM, tool-call args → trace, background-task output, snapshots) are redacted; the B-DOC-01 claim that redaction's char-boundary handling is fixed is confirmed by inspection (`security.rs:113-125` boundary checks + warn-skip, never panics) and by the passing `redact_secrets` tests (V05-04). Does not prove: EKO-side sinks (chat display, file persistence) are redacted — out of scope here.
