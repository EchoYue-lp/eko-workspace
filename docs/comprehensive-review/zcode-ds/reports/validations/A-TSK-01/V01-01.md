## Claim

The task-runtime file set (`events.jsonl` / `plan.json` / `run-state.json`)
has one unambiguous authority split, and there is exactly one task model, one
structural validator, and one file store family across both repositories —
no second EKO model/validator/store and no forbidden parallel CRUD.

## Method

Definition and duplicate search across both repositories (read-only greps,
working dir `echo-agent-cli/` and `echo-agent/`):

```text
grep -rn "struct TaskPlan\|struct PlanTask\|struct TodoItem\|struct EkoTaskSpec\|enum TodoStatus\|struct TaskRun\b" echo-agent-cli/echo-agent-app-core/src/ (excluding task_runtime/)
grep -rn "todo_write\|plan_create\|plan_patch\|plan_execute" echo-agent/ echo-agent-cli/
grep -rn "struct .*Store\|impl .*Store" (task/revision store implementations both repos)
grep -rn "PlanValidator\|validate_task_snapshot\|detect_cycle\|topolog" (validator duplication, echo-agent-cli)
grep -rn "sqlite\|Sqlite\|rusqlite" echo-agent-cli/echo-agent-app-core/src/tasks/
```

Plus static inspection of the file-authority layer: `file_shadow.rs`
(append/rebuild primitives), `file_store.rs` (read API), `event_rebuild.rs`
(fold), `store.rs` (write paths), `revisioned_adapter.rs` (framework store
trait impl).

## Expected Result

- File authority: `events.jsonl` is the sole append-only write authority and
  can rebuild both projections; `plan.json` (PlanRevision spec) and
  `run-state.json` (run header + EkoTaskExecution incl. framework
  `TaskStatus`) are derived snapshots rebuilt from events on every
  projection-affecting write; reads always go through the files; no
  in-memory business state that can diverge.
- No EKO task model outside `task_runtime/`; zero definitions of
  `todo_write` / `plan_create` / `plan_patch` / `plan_execute`; zero
  EKO-owned structural DAG validator; zero SQL in app-core `tasks/`.

## Result

- Exit code: 0 (grep pipelines; zero findings in the forbidden-name search)
- Duration: ~2 min (grep + static inspection)
- Summary:
  - Authority table (verified against code):

    | File | Content | Authority role | Written by |
    |---|---|---|---|
    | `events.jsonl` | append-only `RuntimeTaskEvent` lines, per-run seq | sole write authority; rebuild source | `FileTaskShadow::append_event_line` (file_shadow.rs:118-178) |
    | `plan.json` | `PlanRevision` (envelope + `EkoTaskSpec[]` + revision) | derived projection | `FileTaskShadow::rewrite_plan` atomic rename (file_shadow.rs:208-280) |
    | `run-state.json` | `RunStateSnapshot` (`TaskRun` + `EkoTaskExecution[]`, status = framework `TaskStatus`) | derived projection | same `rewrite_plan` |

  - Every business write is `with_run_lock` -> append event -> `rewrite_plan`
    (store.rs:281-290, 302-357, 387-428, 755-885, 953-1176). Reads delegate
    to `FileTaskStore` over the shadow (store.rs:1482-1526, 1778-1808).
  - One model: framework `TaskSpec/TaskExecution/TaskStatus/TaskKind` +
    EKO `EkoTaskSpec/EkoTaskExecution/PlanTask/TodoItem/PlanRevision`; no
    EKO task types outside `task_runtime/`.
  - One structural validator: `PlanValidator::validate_task_snapshot`
    (store.rs:96-101, 921-923; revisioned_adapter.rs:284-295 delegates to
    framework service `finalize_and_validate`). EKO `TaskCapabilityCatalog`
    = capability policy only (task_tools.rs:49-81); `planner.rs` = file
    ownership policy, doc explicitly defers structural checks to
    `PlanValidator` (planner.rs:8-9).
  - Stores: framework `InMemoryRevisionedTaskStore` + legacy
    `SqliteTaskStore`/`TaskStore` (framework options, not CLI-used — see
    F-TSK-01-P3-01); EKO `TaskRuntimeStore` + `FileTaskStore` +
    `EkoRevisionedTaskStore` (thin `RevisionedTaskStore` impl with only
    `load`/`compare_and_commit`, revisioned_adapter.rs:26-56). No SQL in
    app-core `tasks/` (only retired-SQL comments).
  - Forbidden parallel CRUD: `todo_write`, `plan_create`, `plan_patch`,
    `plan_execute` have zero definitions; the only `to_task_plan_patch`
    call sites are the framework `TaskPlanPatch` protocol (types.rs:1284,
    store.rs:913, revisioned_adapter.rs:328). `TaskUpdateOperation` maps to
    framework ops Insert/Update/Skip/Reorder (no SetStatus — policy default
    `allow_manual_progress_updates=false`, revisioned.rs:275-277).
