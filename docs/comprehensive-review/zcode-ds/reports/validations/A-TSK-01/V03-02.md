## Claim

Corrupt and partial state reconstruction: (a) a torn final line in
`events.jsonl` (crash mid-append, which `append_event_line` itself documents
as possible) must not make the run unreadable — `read_events` handles it;
(b) a missing/corrupt projection (`plan.json`/`run-state.json`) must be
recoverable from the authoritative `events.jsonl` rather than bricking the run.

## Method

1. Executed reproduction of the exact `FileTaskShadow::read_events` parsing
   logic (file_shadow.rs:362-379: iterate `text.lines()`, `trim()`, skip
   empty, `serde_json::from_str`, hard error on any decode failure) against
   three fixtures — intact stream, stream with a torn partial tail line,
   stream with a trailing empty line. Scratch program `/tmp/partial_tail.rs`
   compiled with rustc + the workspace's cached serde_json rlib; behavior is
   identical to the real code because any truncated JSON line fails parsing
   regardless of the concrete struct (only the error text differs).
2. Static trace of the read paths and repair paths:
   - `read_events` (file_shadow.rs:362-379), `next_seq` (289-299),
     `rewrite_plan` (208-280), `read_plan`/`read_run_state` (339-359),
     `FileTaskStore::load` (file_store.rs:37-55), `get_run`/`get_plan`
     (store.rs:1482-1487, 1778-1782), `load_revisioned_task_graph`
     (store.rs:676-686), `recover_incomplete` (store.rs:1631-1776);
   - grep for any tail-truncation/repair logic:
     `grep -rn "truncate\|partial tail" echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/`

## Expected Result

- (a) `read_events` succeeds on a stream whose final line is torn
  (skips/repairs it), matching the code comment "A crash mid-append can at
  worst lose the last partial line — `read_events` skips empty lines and a
  future hardening pass (gate 2) will truncate a partial tail".
- (b) reads tolerate missing/corrupt projections by rebuilding from events,
  since `events.jsonl` is declared the recovery authority.

## Result

- Exit code: 0 (scratch program ran); behavior outcome: FAILED
- (a) Executed output:
  ```text
  intact: OK parsed 2 events
  partial-tail: ERROR line 3: EOF while parsing a value at line 1 column 20
  empty-tail: OK parsed 2 events
  ```
  A torn tail is NOT skipped: `read_events` returns
  `ShadowError::Decode` (file_shadow.rs:374-376). This error propagates
  through every read (`FileTaskStore::load` -> `StoreError::InvalidPlan`
  via file_store.rs:37-55 / store.rs:1486) and every write (`next_seq`
  seeds from the same failing read, file_shadow.rs:297). `recover_incomplete`
  catches the error, warns, and skips the run (store.rs:1635-1638) — the run
  stays `Running` in `run-state.json` forever and is re-detected as a zombie
  at every boot without ever being recovered. No truncation/repair exists
  anywhere in `task_runtime/` (grep: zero hits; the "gate 2" hardening pass
  is not implemented).
- (b) Static trace:
  - `rewrite_plan` writes `plan.json` and `run-state.json` as two separate
    `atomic_write`s (file_shadow.rs:267-278). A crash between the renames
    leaves plan.json new and run-state.json old/absent (or vice versa).
  - With run-state.json absent, `FileTaskStore::load` returns `Ok(None)`
    even when plan.json and events.jsonl exist (file_store.rs:50-55) →
    `get_run`/`get_plan` return `None` (run invisible); with run-state.json
    present but plan.json corrupt, `read_plan` hard-errors
    (file_shadow.rs:345-347); `load_revisioned_task_graph` errors
    `RunNotFound` when run-state.json is missing (store.rs:685-686).
  - `recover_incomplete` discovers runs only via `list_runs_in`, which reads
    `run-state.json` (file_store.rs:69-80) — an invisible run is never
    recovered. The only repair path is `rewrite_plan` on the NEXT write to
    that run; after a crash the caller is gone, so no repair ever happens.
    The run remains stuck until manual file editing.

## Deviations

Both expectations failed. The code comment in `append_event_line`
(file_shadow.rs:114-117) promises empty-line skipping plus a future
truncation pass; the empty-line half works, the truncation half does not
exist, and a torn line is a hard error rather than a tolerated loss.

## Conclusion

Supports finding A-TSK-01-P1-01 (torn tail → permanently unreadable run,
executed reproduction) and A-TSK-01-P2-01 (no read-side rebuild from the
authoritative event log; crash between the two projection renames or a
corrupt projection bricks the run). It does not quantify the probability of
a mid-append crash; the mechanism is certain from the code and the
reproduction.
