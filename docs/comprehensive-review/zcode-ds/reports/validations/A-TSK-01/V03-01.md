## Claim

Conversion between EKO file types and framework task types is thin and
lossless: field-by-field round trips for spec, execution, patch, and
plan-commit directions preserve every field on live paths.

## Method

Field-by-field static comparison of every conversion direction, plus
confirmation of the status-state space reachable on live paths:

```text
1. EkoTaskSpec <-> framework TaskSpec   (types.rs:872-915, store.rs:702-717, 815-831)
2. PlanTask <-> framework Task          (types.rs:1060-1200)
3. TaskUpdateRequest <-> TaskPlanPatch  (types.rs:1283-1317 vs revisioned.rs:94-124)
4. TaskGraphCommit -> PlanRevision + effects -> read-back graph
                                        (store.rs:755-885, event_rebuild.rs:138-205,
                                         load_revisioned_task_graph store.rs:676-749)
5. TaskStatus <-> TodoStatus + status_detail
                                        (types.rs:408-456, 1203-1216)
6. Producers of framework TaskStatus::Retrying / Paused:
   grep -rn "TaskStatus::Retrying {" echo-agent/ echo-agent-cli/
   grep -rn "TaskStatus::Paused(" echo-agent/echo-orchestration/src/
```

## Expected Result

Every EKO field maps to exactly one framework field (or EKO metadata field)
and back, including `execution_checks`/`acceptance_criteria` staying as
distinct fields (never flattened), and the status mapping is bijective for
every status the EKO write path can produce.

## Result

- Exit code: not-applicable (static)
- Summary:
  1. Spec: `id/title/description/kind/agent_role/depends_on/files/
     allowed_tools/required_artifacts/execution_checks/
     acceptance_criteria/max_retries` are 1:1; EKO-only
     `domain_profile/parallel_group/sort_order` round-trip inside
     `TaskSpec.metadata` via `EkoTaskMetadata` (serde JSON identical in
     `EkoTaskSpec::to_task_spec` and `PlanTask::to_task`).
  2. Execution: `retry_count/failure_fingerprint/claim` 1:1; status maps via
     `TodoStatus + status_detail` (8 + detail) which covers all statuses the
     EKO write path can produce (see item 6).
  3. Patch: `base_revision/reason` 1:1; Insert/Update/Skip/Reorder map to the
     framework ops; `TaskPatch` has the same 12 optional fields as
     `TaskSpecPatch`.
  4. Commit: framework `TaskGraphCommit.next` -> `PlanRevision` (specs +
     revision + envelope) + effects (`skipped_task_ids`/`reset_task_ids`)
     persisted in the event payload; read-back
     (`load_revisioned_task_graph`) reproduces the framework snapshot
     because the rebuild carries execution forward per task id and applies
     skip/reset exactly where `TaskPatchEngine` did (revisioned.rs:521-568),
     and inserts arrive Pending. `spec.id == execution.task_id` is enforced
     on both write (store.rs:808-813) and read (types.rs:1167-1172).
  5. Status: `run-state.json` stores the framework `TaskStatus` verbatim
     (serde); events carry `TodoStatus` + `status_detail` + `claim`, which
     the rebuild folds back exactly (event_rebuild.rs:214-251).
  6. Reachable status space: `TaskStatus::Retrying` has zero production
     constructors in either repository (only match arms); `TaskStatus::Paused`
     is constructed only in legacy `echo-orchestration/src/tasks/manager.rs:446`
     (production-unreachable, F-TSK-01-P3-01). EKO executor writes go
     exclusively through `TodoStatus`-typed store methods (V02-01).
     Therefore `TodoStatus::try_from_task_status`'s Err branch for
     Retrying/Paused (types.rs:434-437) is unreachable on live EKO paths.
- Existing tests exercising the round trip (all passed, see V04):
  `plan_task_round_trips_through_framework_task` (types.rs:1934-1999),
  `plan_task_status_projection_preserves_failure_detail` (2002-2040),
  `task_status_projection_preserves_cancelled_and_timed_out` (2043-2059),
  `rebuild_reflects_task_patch` (event_rebuild.rs:432-490),
  `task_update_inserts_task_and_commits_one_revision` (store.rs:2979-3018).

## Deviations

The status mapping is NOT bijective over the full framework enum: framework
`Retrying`/`Paused` have no EKO representation (`try_from_task_status` errors,
`project_task_status` collapses them to Running/Blocked). Unreachable today
but a latent lossless gap if a future framework path emits them — recorded as
finding A-TSK-01-P3-01.

## Conclusion

Supports: the adapter is thin (no patch engine, no second validator, no
state machine in `revisioned_adapter.rs`) and the conversion is lossless for
every field and every status producible on live EKO paths. It does not prove
the framework-side semantics of patch effects (F-TSK-01/02) or executor
status writes (A-TSK-03/04).
