## Claim

The workflow/pipeline API (graph, DAG, sequential/concurrent pipelines,
checkpoints, state transitions) is a coherent generic mechanism **distinct
from** the dynamic task model (`TaskSpec/TaskExecution/TaskStatus`,
`TaskRevisionService`, `RuntimeDagExecutor`): no parallel implementation of
the same semantics exists on either side, and no workflow module references
the task module (or vice versa).

## Expected Result

One authoritative workflow engine; workflow and task modules mutually
independent; no second topological sort / cycle detection / checkpoint /
pipeline authority that duplicates workflow semantics; no forbidden
`worker` terminology.

## Result

- Exit code: not-applicable (static search)
- Summary: exactly one workflow engine (echo-orchestration `workflow`
  module + root-crate facade `src/workflow/{dsl,loader}.rs` which only
  re-export / thin-build over it). **Zero** grep hits of task names inside
  `echo-orchestration/src/workflow/` and zero `workflow` hits inside
  `echo-orchestration/src/tasks/` — the two authorities are fully
  independent. The task-side DAG logic (`tasks/dag.rs`, `PlanValidator`)
  and the pipeline-side `DagWorkflow` topological sort
  (`workflow/dag.rs:334-431` Kahn + `:372-431` DFS cycle detection) are
  separate semantics: static compiled pipeline vs revisioned dynamic task
  graph; no code sharing or delegation between them. Checkpoint concepts
  are subsystem-local and mutually independent (workflow
  `CheckpointStore`, agent `snapshot.rs`, task `TaskNode` per
  F-TSK-01-P3-04, EKO run-state files) — no duplicate authority.
- EKO side: `StoredWorkflow` + Tauri `execute_workflow`
  (`echo-agent-cli/src/tauri/commands/panels.rs:746-782`) is a **thin
  adapter** that lowers the stored YAML/JSON string through the framework
  `loader::load_graph_from_yaml_str/json_str` and runs `Graph::run` — no
  second engine. `WorkflowDef`/`WorkflowStep`
  (`echo-agent-cli/echo-agent-app-core/src/state.rs:220-240`) is a parallel
  linear-step **model** with zero production users (see finding
  F-WFL-01-P3-08).
- No `worker` terminology in either workflow module.

## Deviations

None for the core claim. Naming overlap is limited to (a) `DagWorkflow`
(pipeline) vs task `DagExecutionState`/`RuntimeDagExecutor` — distinct
semantics, documented; (b) EKO `WorkflowStep`/`WorkflowDef` dead model
(P3-08).

## Conclusion

Supports: workflow and dynamic tasks are separate, coherent authorities;
no parallel implementation of workflow semantics; layering of
`src/workflow/{dsl,loader}.rs` is a correct thin root-crate facade. Does
not prove: runtime behavior correctness (V03/V04), reachability (V02).
