## Claim

All retry/backoff waits are cancellable (tokio::time, not std::thread::sleep),
retries are responsive to the run's CancellationToken, and clock usage is
monotonic where it must be.

## Method

Inspection of every wait site and its caller context:

```text
echo-core/src/retry.rs:155            tokio::time::sleep(delay).await
src/agent/react/run/retry.rs:41       tokio::time::sleep(...).await
echo-orchestration/src/tasks/executor.rs:1199-1213  tokio::select! { cancel.cancelled() / sleep }
echo-integration/.../feishu/long_poll.rs:195-205     tokio::time::sleep(jitter/backoff)
echo-integration/.../qq/channel.rs:188              tokio::time::sleep(...)
grep "select!\|cancel_token\|cancelled()" src/agent/react/run/...
grep "Instant\|SystemTime" echo-core/src/circuit_breaker.rs echo-core/src/utils/time.rs
```

## Expected Result

- No `std::thread::sleep` in any retry path.
- Retry loops either race sleeps against the cancellation token or are
  drop-cancellable with bounded wait.
- Breaker timeout uses `Instant` (monotonic).

## Result

- Exit code: n/a (static inspection)
- Summary:

1. **Wait primitive**: every retry/backoff sleep is `tokio::time::sleep`
   (drop-cancellable). No `std::thread::sleep` in any retry path (breaker tests
   at `circuit_breaker.rs:321,357` use thread::sleep only to let the timeout
   elapse in tests — not production).
2. **Explicit token responsiveness**:
   - echo-orchestration: exemplary — `tokio::select! { biased; cancel.cancelled() → cancelled; sleep → retry }` (`executor.rs:1204-1213`) plus `checked_add(1)` attempt counter (`:1203`), plus per-iteration `cancel.is_cancelled()` check (`:966`). No cancellation window.
   - echo_core `with_retry_if` / engine `retry_llm_call`: no CancellationToken parameter; retry is interrupted only by dropping the surrounding task. The run engine's token checks are at phase boundaries (tools.rs:177-178,348-349; think.rs:321 passes the token into the streaming ChatRequest), and the non-streaming path even hardcodes `cancel_token: None` (react_loop.rs:60). A token-signalled cancel therefore completes the current backoff sleep before the next phase check. Bounded: with defaults (500ms base, exponent cap 5, max_retries 3) the worst remaining sleep ≈ 2-3s; with maxed retries ≈ 24s. Impact: delayed (not lost) cancellation — observation, not a finding.
3. **Clock usage**: breaker timeout uses `Instant` (`circuit_breaker.rs:21,123,219,230,235` — monotonic, correct for timeouts); `utils/time.rs` `now_secs/now_millis` use `SystemTime` (wall clock) for display/audit only — appropriate; `unwrap_or_default` (0 on pre-epoch) per doc.
4. **Probe-slot lifecycle (breaker)**: slot take is inside the state mutex (no double-take race between concurrent `try_advance`); release is via `record_success/record_failure` `fetch_update` — but there is **no RAII guard**: a probe future dropped mid-flight (task cancel) never calls `record_*` → `probes_in_flight` stays 1 → every subsequent `try_advance` rejects forever (permanent wedge). Latent today because the gate is never called (P1-01); must be fixed when the gate is wired (P3-02).

## Deviations

None.

## Conclusion

Supports: cancellable waits everywhere (no blocking sleeps); monotonic clock for
breaker timeouts; orchestrator retry is fully token-responsive; engine/core
retries are drop-cancellable only (bounded delayed-cancellation observation);
breaker probe-slot leak on cancellation is latent (P3-02). Does not prove:
test execution (V04).
