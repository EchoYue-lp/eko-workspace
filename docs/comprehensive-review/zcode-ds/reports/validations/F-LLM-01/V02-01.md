## Claim

The streaming contract (`LlmClient::chat_stream` → `BoxStream<Result<ChatChunk>>`)
merges to the same semantic result as the non-streaming `chat()` with no
information loss on well-formed provider data, and every loss path on
malformed/edge input is identified and attributed.

## Method

1. Traced chunk flow: `stream_post` (`echo-integration/src/providers/client.rs:182-354`)
   → `parse_sse_chunk` (`:76-107`) → adapter mapping to `ChatChunk`
   (`openai.rs:369-375`, `adapter_client.rs:170-176`) → core loop merge
   (`src/agent/react/run/processor.rs:16-98` `process_stream_chunk` and
   `think.rs:110-120`).
2. Compared with non-streaming `post()` (`client.rs:110-172`) and
   `OpenAiClient::chat` (`openai.rs:264-318`).
3. Checked delta merge semantics: content `push_str`, reasoning `push_str`,
   tool-call fragments keyed by `index` with id/name replace + arguments
   `push_str` (`processor.rs:56-98`); tool-arg repair `parse_tool_args`
   (`processor.rs:104-136`).
4. Checked usage-in-stream: `last_usage` captured from any chunk carrying
   usage (`think.rs:112-114`, `stream_channel.rs:402-404`); final chunk
   only when `stream_options.include_usage` honored (doc `mod.rs:239-241`).
5. Searched for a contract-level streaming==non-streaming equivalence test
   (grep `non.stream|equiv|same` in echo-core llm + providers): none exists.

## Expected Result

Deltas merge losslessly when all chunks parse; any residual loss path is
documented or surfaced as an error; no divergence between streaming and
non-streaming error handling.

## Result

- Well-formed data: lossless. Content/reasoning concatenate, tool-call
  fragments assemble by index (arguments concatenated), usage flows through
  `ChatChunk.usage` when the provider honors `include_usage`. `finish_reason`
  is carried per chunk but not consumed by the core loop (only the structured
  path reads it, `react_loop.rs:101`).
- Malformed chunk: **silent drop**. `parse_sse_chunk` returns `None` on a
  serde failure and logs at `warn` (`client.rs:99-105`); the stream continues
  and terminates normally; the caller merges nothing and sees no error.
  The non-streaming `post()` fails with `LlmError::InvalidResponse` for the
  same malformed body (`client.rs:163-164`) — the two paths diverge.
  → F-LLM-01-P1-01.
- Type-level loss inside an otherwise-parseable chunk: `MessageContent::deserialize`
  maps unknown JSON shapes to `Empty` silently (`types.rs:69-88`); an array
  containing an unsupported part type loses the whole content array
  (same P1-01 class; part of the lenient-parse mechanism).
- Cancellation: `stream_post` returns silently on a cancelled token
  (`client.rs:251-256`) — no terminal chunk/error; documented at
  `mod.rs:173-175` ("stop at the next SSE boundary"). Consumers cannot
  distinguish cancel from normal end via the stream contract alone.
  → F-LLM-01-P3-01.
- End-of-stream sentinel: `[DONE]` is converted into an error whose payload
  is a marker string (`client.rs:81-86`) and later matched by string
  containment (`client.rs:329,347`) — text-based protocol signalling.
  → F-LLM-01-P3-01.
- Usage-in-stream is conditional: when the provider ignores
  `stream_options.include_usage`, no chunk carries usage; the contract
  signals this via `usage_reported: false` downstream (see V03), not by an
  error. This is an explicit, documented contract property.
- Chunk-vs-response asymmetry: `ChatCompletionChunk` lacks `model`/`created`
  (present in `ChatCompletionResponse`), so streamed calls cannot correlate
  a chunk to response metadata without the request context. Minor; recorded
  in V01, no finding.
- No equivalence test exists at the contract level (step 5); equivalence is
  asserted indirectly by F-RCT-02/03 loop tests (out of scope here).

None.

## Conclusion

Supports: streaming is lossless on well-formed data; the only identified
loss path on the stream is the silent chunk drop (`parse_sse_chunk` → None,
client.rs:99-105), which diverges from non-streaming error handling
(P1-01); cancellation and timeout produce no typed signal (P3-01).

Does not prove: loop-level cancellation recovery ordering (F-RCT-03) or
adapter-level delta fidelity for OpenAI/Anthropic (F-LLM-02/03).
