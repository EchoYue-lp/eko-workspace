## Claim

Discovery precedence is deterministic; malformed frontmatter and path edge cases behave per the documented contract; the documented input formats actually parse.

## Method

Static inspection of `loader.rs` (parse/discover/scope precedence), `types.rs` (path matching, tool matcher), `run_script_tool.rs`/`resource_tool.rs` (path safety), plus empirical probe executions against the real `echo_execution` crate (probe source in `/tmp/fskl-probe/src/main.rs`):

cd /tmp/fskl-probe && cargo build

## Expected Result

- Earlier discovery scope wins on name collision (doc: "Project-level skills override user-level skills", `loader.rs:14`).
- Missing `description` rejects the skill; name issues warn; malformed YAML rejects with warning; closing `---` must be on its own line.
- `requires-binaries` YAML-list metadata parses into the descriptor's metadata map (per `dependency_probe.rs:52-65` comment).

## Result

- Exit code: 0 (probes); not-applicable (static part)
- Summary:
  - **c-precedence**: earlier scope wins — `[probe] precedence winner: project-scope (expected project-scope)`. Deterministic for distinct scopes.
  - **d-frontmatter-edge**: trailing content after closing `---` on same line is rejected (`[probe] trailing-content REJECTED`); a block-scalar description containing an indented `---` line parses correctly (closing-separator heuristic works for indented YAML content).
  - **b-yaml-list**: `metadata:\n  requires-binaries: [soffice, pdftoppm]` FAILS to parse — `[probe] yaml list PARSE FAILED: SKILL.md YAML parse error: metadata.requires-binaries: invalid type: sequence, expected a string`. The comma-string form parses fine. Consequence: a skill using natural YAML list syntax for a documented metadata key is silently dropped from discovery (warn log only, `loader.rs:270-276`), and `dependency_probe.rs:52-65`'s claim that lists "come through as `[soffice, pdftoppm]`" is empirically false. Finding F-SKL-01-P2-03.
  - Static findings:
    - Within one directory, `scan_directory` uses `tokio::fs::read_dir` (filesystem order, `loader.rs:194-214`); two skills with the same name at different nesting depths (flat vs `category/name/`) resolve to a nondeterministic winner (shadow warning order also nondeterministic). Cross-scope precedence remains deterministic. Recorded as P3 (covered in F-SKL-01-P3-01 context).
    - Path safety: `run_skill_script` rejects absolute/`..` paths and verifies canonicalized containment (`run_script_tool.rs:178-258`); `read_skill_resource` same (`resource_tool.rs:91-166`); `is_path_safe` rejects `..`, absolute, and non-resolvable paths (`echo-core/src/tools/skill.rs:75-95`). Symlink escape is prevented by canonicalization. No violation found.
    - `parse_frontmatter` byte slicing (`loader.rs:417-450`) only slices at ASCII `---`/`\n---` boundaries; no UTF-8 panic path found.

## Deviations

- The YAML-list failure contradicts the in-code documentation (recorded as finding, not treated as pass).
- Nested same-name duplicates were not exercised dynamically (would need controlled read_dir ordering); the nondeterminism is derived from `read_dir` semantics.

## Conclusion

Supports: scope precedence deterministic; strict frontmatter terminator handling works; path containment checks are sound; YAML-list metadata is a silent skill-dropping input (F-SKL-01-P2-03). Does not prove: behavior under OS-level dir ordering races (documented as derived).
