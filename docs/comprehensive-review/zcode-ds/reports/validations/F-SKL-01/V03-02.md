## Claim

Tool-name collision from skill registration is observable (or at least not silently destructive in a way unique to skills); reload after content change refreshes runtime state; unload removes all group-owned state; script execution cancellation/timeout bounds are honored consistently.

## Method

Static inspection:

```text
grep -n "fn register\b|fn unregister\b" echo-execution/src/tools.rs
grep -n "is_installed|skip duplicate" src/agent/react/capabilities.rs
grep -rn "kill_on_drop|timeout(" echo-execution/src/skills/external/{prompt_exec,run_script_tool}.rs echo-execution/src/skills/hooks.rs
grep -rn "unregister_by_source|remove_descriptor" echo-execution/src/skills/registry.rs echo-agent-cli/echo-agent-app-core/src/plugin_runtime.rs
sed -n '55,80p' echo-agent-cli/src/cli/cmd_impls/skills.rs   # /skills sync reload path
```

## Expected Result

- Colliding tool names are detected or the replacement is at least logged.
- Re-running `load_skills_from_dir` after a SKILL.md content change refreshes descriptors, hooks, and catalog.
- Unload removes descriptors, hooks, projections, and tool instances for the source.
- Script/inline-command timeout and cancellation kill the spawned process (and its tree) deterministically.

## Result

- Exit code: not-applicable (inspection)
- Summary:
  - **Tool-name collision**: `add_skill` (`capabilities.rs:563-612`) dedups by skill name only; each skill's tools go through `tool_manager.register` (`:583-585`), which is silent last-wins (`echo-execution/src/tools.rs:529-536`). Two skills supplying the same tool name silently replace each other — same class as F-EXT-01-P1-02, skill-specific entry point. Finding F-SKL-01-P3-04.
  - **Reload staleness**: `discover_skills_inner` skips any descriptor whose name is already installed (`capabilities.rs:687-695` — "Skill already installed, skipping duplicate") with no content comparison; frontmatter hooks are registered only for new names (`:702-711`); when no new names arrive the catalog projection is not refreshed either (`:734-736` early return). The CLI `/skills sync` then calls `load_skills_from_dir(root)` (`cmd_impls/skills.rs:61-71`) expecting a reload — it is a no-op for existing skills. Plugin skills avoid the issue because disable runs `unregister_skills_by_source` first (`plugin_runtime.rs:1167`). Finding F-SKL-01-P2-01.
  - **Unload completeness**: `unregister_skills_by_source` (`capabilities.rs:915-958`) removes from both registries, unregisters the `HookSource::Skill(name)` hooks, clears per-skill projections, replaces the catalog, and re-registers the three skill tools; `remove_descriptor` (`registry.rs:208-232`) also purges legacy instructions, plugin variables, activation and sandbox-policy bookkeeping; source reverse index is maintained (`register_descriptor` :103-123, `tag_source` :161-190). Verified complete. Test `source_group_unload_returns_exact_skill_names` pins it.
  - **Script cancellation**: `run_skill_script` implements `execute` (no `ToolContext`), so `ctx.cancel` is not observable; the only bound is the timeout. Both the sandbox path and the direct fallback use `tokio::time::timeout` + `kill_on_drop(true)` (`run_script_tool.rs:319,332`; `prompt_exec.rs:426,436`; `hooks.rs:1178,1222`), which kills only the direct child — a process tree (e.g. `bash -c "sleep 100 &"`) leaves orphaned grandchildren after timeout. The skill's declared `SkillSandboxPolicy.timeout_secs` is applied in the sandbox path (`run_script_tool.rs:287-295`) but **not** in the direct fallback (`:313-354` uses `self.timeout_secs` only) — policy contract "tool execution within this skill's context is constrained according to the policy" (`types.rs:139-143`) is not honored without a sandbox. Findings F-SKL-01-P3-05 (one finding covering both arms).
