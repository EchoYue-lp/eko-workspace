## Claim

Approval cache identity honors the documented granularity: `Once` = no cache,
`Session` = same tool + same args (approval_cache.rs:6, policy.rs:24-25),
`SessionAllTools` = same tool, any args (policy.rs:27-28, approval_cache.rs:7);
all scope→cache/rule conversions in the service produce the same semantics.

## Method

Trace of every `record_approval` / `is_approved` / `add_session_rule` call and
the scope inference:

```text
1. approval_cache.rs — is_approved (100-125), record_approval (128-169),
   args_key (270-277), TTL (259-264)
2. service.rs — check_with_handler cache write (735-738),
   infer_scope_from_updates (791-807), DynProviderHandler response_with_scope (892-908)
3. permission.rs — DefaultPermissionRequestHandler + permission_response_with_scope (691-713),
   build_matcher (536-543)
4. RuleMatcher::Pattern("*") match (echo-core/src/tools/permission.rs:253-255)
5. Reachable scope producers: console provider 's'/'a' keys (console.rs:66-77),
   EKO providers returning ApprovedWithScope
```

## Expected Result

`Session` approvals cache per (tool, args); `SessionAllTools` approvals cache
per tool; the two bridges agree; the rule installed matches the chosen scope.

## Result

- Exit code: 0
- Summary:
  - `infer_scope_from_updates` (service.rs:791-807) maps ANY session-source
    allow rule to `ApprovalScope::SessionAllTools`, and any session deny rule
    to `Session`. Because every `ApprovedWithScope`/`Approved`+rule_updates
    response from the bridges produces a session `AddRule`, the cache stores a
    per-tool global entry (`global_approvals[tool_name]`, approval_cache.rs:151-167)
    in every case where the user chose a session scope — the args-keyed
    `Session` branch (approval_cache.rs:133-150) is unreachable through the
    service flow.
  - Consequence 1 (Session): "allow for this session" (intended same tool +
    same args per policy.rs:24-25 and docs/zh/05-human-loop.md:92) in fact
    auto-approves ALL argument values of that tool name for the session.
  - Consequence 2 (SessionAllTools): the two bridges disagree on the rule:
    `DefaultPermissionRequestHandler` installs `add_session_rule(tool_name)`
    (permission.rs:706-711 — this tool only), while the live EKO-used bridge
    `DynProviderHandler::response_with_scope` installs `add_session_rule("*")`
    (service.rs:901-906 — ALL tools). `RuleMatcher::Pattern("*")` matches
    every tool (echo-core:253-255), and rules are evaluated before cache
    (service.rs:561-573), so one "approve all" on any tool permits every tool
    for the rest of the session, bypassing cache/denial/handler.
  - The framework's own `ConsoleHumanLoopProvider` can produce
    `SessionAllTools` ('a' key, console.rs:72-77), so the wildcard path is
    reachable without any EKO involvement.
  - Cache key details: `args_key` is the exact `serde_json::to_string` of the
    args (approval_cache.rs:270-277) — JSON key order matters, so
    semantically identical args with different key order miss the cache
    (safe direction: re-ask). `sha256_hex` (approval_cache.rs:280-290) is not
    SHA-256 (it uses `DefaultHasher`) and the hash mode is never enabled
    through the service (service constructs caches with `hash_args: false`,
    service.rs:191-193, 979).
  - `PermissionServiceBuilder::build()` (dead code, service.rs:974-992)
    creates the cache without TTL, dropping `config.cache_ttl`.

## Deviations

All three documented granularity semantics diverge from observed behavior on
the service path; the two bridges disagree with each other on `SessionAllTools`.

## Conclusion

Supports finding F-HITL-01-P1-03 (scope→rule/cache conversion widening:
session approvals collapse to per-tool global approval, and
`SessionAllTools` becomes a session-wide wildcard allow through the live
bridge), plus P3 material on `args_key` ordering and the misnamed hash.

Does not prove: which specific UI button on EKO's GUI emits which scope
(A-HITL-01); the framework contract itself is the finding.
