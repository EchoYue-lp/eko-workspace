## Claim

On the live execution path (streaming and non-streaming wrapper), every tool
call passes through `PermissionStage` → `AgentRunSnapshot::check_tool_approval`
→ `PermissionService::check_with_permissions_in_mode`; the human ask happens
only inside the service's handler invocation; the framework's direct provider
ask path is dead; EKO wires the framework service with a real handler.

## Method

Static call-graph trace with grep verification of each hop:

## Expected Result

One live approval chain with the service as decision engine; provider asks
either via the service-internal handler or a direct provider call on the live
path.

## Result

- Exit code: 0 (all greps returned the traced call sites)
- Duration: ~10 min
- Summary:
  - Live chain confirmed: `PermissionStage` (pipeline.rs:277-346) runs the
    permission hook first, then calls `snapshot.check_tool_approval`
    (pipeline.rs:329-332). It honors only `Allow` (Ok(None)) and blocks on
    `Deny`; `RequireApproval`/`Ask` are returned as `Err(...)`
    (snapshot.rs:841-852) — the stage never requests human input itself.
  - The human ask on the live path happens exclusively inside
    `check_with_handler` (service.rs:707-754), which is reached only by mode
    dispatch for `Default`/`AcceptEdits`/`StrictConfirm` when the permission
    set requires confirmation and a real handler is configured
    (service.rs:587-632). `Ask`-rule decisions (step 4, service.rs:561-568)
    and `RequireApproval` from Bubble mode (service.rs:643), denial-tracker
    fallback (service.rs:575-585), Auto-without-classifier (service.rs:700-703)
    bypass the handler and return to the caller as errors.
  - EKO main path: `runtime.rs:130-141` wires `HitlDispatcher` as provider and
    calls `build_permission_service()` → `from_provider` → `DynProviderHandler`
    (the live bridge). GUI per-run transport swaps use the cache-preserving
    variant (agent_pool.rs:928-932).
  - Dead branch: `process_steps` has zero callers; its approval entry points
    (`run/approval.rs`) are the ONLY code that maps `RequireApproval` to a
    real `HumanLoopRequest` through the provider (request_human_approval,
    run/approval.rs:295-455).
  - `would_request_human_for_permissions` (batch split) consults rules and
    mode only — never the cache or the handler; Auto returns false there but
    `check_with_permissions_in_mode` maps Auto-without-classifier to
    `RequireApproval` (prediction/execution inconsistency, minor).
  - `HumanInLoop` builtin tool is registered only when
    `config.enable_human_in_loop` is true (react/mod.rs:442-445; default
    false at src/agent/config.rs:220, true at root src/config.rs:472).

## Deviations

None observed; trace is static (no runtime instrumentation in this read-only
review).

## Conclusion

Supports: the live path's only ask mechanism is the service-internal handler
call; `RequireApproval`/`Ask` semantics ("ask the human") are not fulfilled by
the live consumer; EKO's wiring uses the live bridge (`DynProviderHandler`);
the direct-provider ask implementation is dead code. These facts feed
F-HITL-01-P1-01/P1-02 and P2-03.

Does not prove: whether EKO's own surface arbitration handles these cases
(A-HITL-01 scope), or actual user-visible behavior without a live run.
