## Claim

The framework's approval timeout configuration is consulted by the approval
pipeline, and the documented default (`TimeoutStrategy::Reject`) matches
observed default behavior.

## Method

Grep for every read of `timeout_strategy` and `enable_classifier` in
`echo-agent` (excluding tests), plus branch inspection of the timeout paths:

```text
1. grep -rn "timeout_strategy" echo-agent --include="*.rs" (excl. tests)
2. grep -rn "enable_classifier" echo-agent --include="*.rs" (excl. tests)
3. HumanLoopManager::request timeout branch (human_loop/mod.rs:424-437)
4. HumanLoopRequest::approval/approval_with_timeout (mod.rs:628-684) — default timeout value
5. DynProviderHandler / DefaultPermissionRequestHandler — whether req.timeout is ever set
   (permission.rs:660, service.rs:864: HumanLoopRequest::approval without timeout)
6. ConsoleHumanLoopProvider timeout behavior (console.rs:275-289)
7. ApprovalResponder Drop default (mod.rs:168-177)
```

## Expected Result

`TimeoutStrategy` (default `Reject`) is applied when a handler/provider
exceeds the configured timeout; the framework default is documented and
bounded.

## Result

- Exit code: 0
- Summary:
  - `timeout_strategy` is WRITTEN in three places (config field service.rs:112,
    default service.rs:126, setters service.rs:221-226, 949-950) and READ
    NOWHERE. The pipeline never applies any timeout strategy.
  - `enable_classifier` is likewise written (service.rs:110,125,944-945) and
    never read; `check_with_classifier` keys only on `Option<Arc<dyn Classifier>>`
    (service.rs:689).
  - Framework default approval behavior: `HumanLoopRequest::approval(...)`
    sets `timeout: None` (mod.rs:638); both bridges forward it without a
    timeout (permission.rs:660, service.rs:864). `HumanLoopManager` waits
    indefinitely when timeout is None (mod.rs:433-437). The console provider
    blocks on stdin indefinitely (console.rs:287-288). Therefore the default
    is an unbounded wait; the only implicit default rejection is responder
    Drop → `Rejected { "No response provided" }` (mod.rs:168-177).
  - A timeout occurs only when a consumer sets `req.timeout` explicitly:
    `HumanLoopManager` then returns `HumanLoopResponse::Timeout`
    (mod.rs:424-432); the console provider instead returns
    `Err("Approval timeout")` (console.rs:275-289) — an error, not the
    `Timeout` variant; the webhook provider uses its own fixed 300 s HTTP
    timeout and maps a missing/`timeout` decision to
    `HumanLoopResponse::Timeout` (webhook.rs:130-141).
  - EKO compensates at the dispatcher level with a single 5-minute shared
    deadline and fail-closed rejection (hitl/dispatcher.rs) — application
    policy (A-HITL-01), not framework.

## Deviations

`TimeoutStrategy` and `enable_classifier` are dead configuration; the
documented default `Reject` is not the effective default (effective default =
unbounded wait + drop-deny). Console provider maps timeout to `Err` while the
manager maps it to `HumanLoopResponse::Timeout` — provider-inconsistent
timeout signaling.

## Conclusion

Supports finding F-HITL-01-P2-01 (dead `TimeoutStrategy` knob, misleading
public API, unbounded default wait). Also records the provider-level
timeout-signaling inconsistency (console `Err` vs manager/webhook `Timeout`
variant) as supporting evidence; every consumer that handles the `Timeout`
variant is bypassed when the console provider is in use.

Does not prove: whether the EKO dispatcher's deadline covers all surfaces
correctly (A-HITL-01).
