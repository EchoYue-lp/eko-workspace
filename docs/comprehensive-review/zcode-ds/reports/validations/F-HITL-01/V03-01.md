## Claim

The framework separates decision types (`PermissionDecision`), policy
(`PermissionMode` + rules + cache + protected paths + denial tracker), and
provider (`HumanLoopProvider` → `PermissionRequestHandler` bridges) into
generic framework primitives, without imposing EKO interaction policy; the
mapping between the three layers is single-valued for each decision path.

## Method

Field-by-field / branch-by-branch mapping inspection of:

```text
1. echo-core/src/tools/permission.rs — PermissionDecision (135-171),
   PermissionMode (57-115), RuleMatcher (220-292), RuleBehavior (308-332),
   RuleRegistry::check deny-first (437-461), PermissionPolicy (507-602)
2. echo-orchestration/src/human_loop/service.rs — pipeline (484-681),
   check_with_handler (707-754), would_request_human_for_permissions (371-405),
   DynProviderHandler (855-908), from_provider (215-218)
3. echo-orchestration/src/human_loop/permission.rs — PermissionRequest (271-436),
   DefaultPermissionRequestHandler (643-689), permission_response_with_scope (691-713)
4. echo-orchestration/src/human_loop/policy.rs — ApprovalScope (21-29), PolicyDecision (81-99)
5. Boundary: EKO hitl/ module + runtime.rs:130-141 (providers only), web-frontend
   ApprovalCard.tsx (rendering only), src/tauri/error.rs IpcAuth (EKO-only gate)
```

## Expected Result

Each decision path maps one-to-one to a policy rule and one provider outcome;
generic framework code does not reference EKO concepts; EKO code does not
re-implement decisions.

## Result

- Exit code: 0
- Summary:
  - Decision type: single `PermissionDecision` (Allow/Deny/RequireApproval/
    Ask) in echo-core; single `RuleBehavior` (Allow/Deny/Ask). No EKO-side
    redefinition (grep over echo-agent-cli found no `PermissionDecision`
    re-declaration).
  - Policy: single authority `PermissionService` + `RuleRegistry`; mode
    dispatch table in one place (service.rs:602-648). `PermissionMode` doc
    at echo-core:44-82 matches service behavior except `Bubble` (documented
    "sub-agent permissions bubble up to parent process"; observed: Bubble →
    `RequireApproval` → hard error on the live path — see V02 and P1-01).
  - Provider mapping: two bridges exist and diverge on scope→rule conversion
    (see V03-03/P1-03). Both bridges map `Timeout`→denied("请求超时") and
    `Deferred`→denied consistently (permission.rs:678-683, service.rs:879-884).
  - `RequireApproval`/`Ask` → provider mapping is NOT single-valued: the
    service-internal handler is reached only in three of the eight modes; all
    other `RequireApproval`/`Ask` producers map to opaque errors in the live
    consumer (snapshot.rs:841-852) while the dead consumer maps them to a
    provider ask (run/approval.rs:159-165, 295-455). See P1-01.
  - Boundary classification:
    - Generic mechanism (framework, correctly placed): PermissionDecision/
      PermissionMode/RuleRegistry/cache/classifier/denial-tracker/
      ProtectedPathChecker/audit sinks in echo-core + echo-orchestration;
      HumanLoopManager/Console/Webhook/WebSocket providers; HumanLoopHandler;
      BatchApprovalProvider; HumanInLoop tool.
    - EKO product policy (application): HitlDispatcher multi-provider
      arbitration with single 5-minute shared deadline and fail-closed
      rejection (hitl/dispatcher.rs); TUI/GUI/channel providers; frontend
      ApprovalCard rendering; permission_mode state (agent_pool.rs:467-483);
      runtime wiring (runtime.rs:130-141). Owned by A-HITL-01/A-SRF-03.
    - Adapter boundary: DynProviderHandler + DefaultPermissionRequestHandler
      are thin bridges but carry the divergent scope→rule conversion (P1-03)
      — a boundary defect, not EKO policy.
  - The framework does NOT gate direct user interactions: the only
    enforcement point is `PermissionStage` inside the agent tool pipeline
    (pipeline.rs:268-346); `require_full_auto` exists only in EKO's Tauri IPC
    layer (src/tauri/error.rs) — framework side is clean of product gates
    (V01). AGENTS.md over-gating lesson is not regressed in echo-agent.
  - PermissionService default state (no service configured) performs no
    checks at all (snapshot.rs:854-856) — opt-in generic behavior, acceptable
    for a framework.

None.

## Conclusion

Supports: decision/policy/provider separation is architecturally correct and
EKO-neutral (framework imposes no interaction policy; EKO adds only
providers/arbitration); the mapping is single-valued EXCEPT for the
`RequireApproval`/`Ask` consumer mapping (P1-01) and the two scope-converting
bridges (P1-03); `Bubble`'s documented semantics are unimplemented (P1-01).

Does not prove: EKO multi-surface arbitration correctness (A-HITL-01) or
frontend rendering correctness (A-SRF-03).
