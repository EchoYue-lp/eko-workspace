## Claim

All four interactive surfaces (TUI, GUI, CLI REPL, IM channel) reach the single
`drive_chat` at runtime, each through one thin adapter constructing
`PreparedUserTurn` + `ChatResources`; `drive_chat` owns the turn lifecycle
(run_id scoping, task-mode run creation/finalization, cancel registration,
execution-path observation) and routes every event to the per-mode sink; the
task runtime's subagent/background loops are a separate envelope consumer, not
a second chat driver.

## Expected Result

Four reachable production call sites; the driver forwards exactly the
envelope-normalized agent stream plus `Execution`/`ExecutionPath` events to the
sink; `TurnStatus` produced only by the GUI wrapper; `Interrupt` produced
nowhere; steer reaches the framework mailbox directly.

## Deviations

- `TurnStatus` has exactly one producer (GUI wrapper) but every sink and the
  REPL consume it; TUI's `TurnStatus` terminal handler and the channel's
  `TurnStatus` arm are dead on those paths.
- `ChatDriverEvent::Interrupt` has zero producers (see V01-01).
- GUI interrupt detection does not go through the shared sink.
- No surface except GUI/TUI has a cancel wiring; REPL/channel create a fresh
  token that is never fired.

## Conclusion

Supports: one runtime-reachable chat driver with four thin adapters; the
driver, not the sinks, owns turn lifecycle, task-mode run transitions, cancel
registration, and path observation; sinks are transport/render adapters with
surface-local projection state only. Supports: the task runtime is a separate
envelope consumer, not a parallel chat driver. Identifies: `drive_chat`'s
`Result` is decoupled from the agent stream terminal (the envelope yields only
Ok items — `Err` branch at chat_driver.rs:548 is unreachable today), which
feeds the GUI's terminal-status derivation; detailed in V03-01 and findings.
