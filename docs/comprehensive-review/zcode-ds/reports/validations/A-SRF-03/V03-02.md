## Claim

Reconnect/reload and late/duplicate event handling: (a) late chat events from
a previous turn are dropped, not applied to the current turn; (b) after a
webview reload the chat/tool/subagent stores are rebuilt from persisted facts
without duplicate or stale rows; (c) listener re-registration and unmount
cannot leak or double-register.

## Expected Result

- Events whose `message_key` differs from the current turn's are ignored.
- Reload rebuilds messages (deterministic ids), tool rows (identity-deduped),
  and subagent cards (from durable TaskRuntime events) with no duplicates.
- Listener setup is idempotent per mount and fully cleaned on unmount.

## Result

- Exit code: not-applicable (static trace)
- Summary:
  - (a) PASSES: `isCurrentRunEvent` (useTauriChat.ts:50-58) drops every
    `chat://event` whose `message_key` does not match the active turn; since
    the backend injects `message_key` into every payload (chat.rs:137-149),
    stale turns' late tokens/terminals never reach the store. Terminal
    handlers additionally null the refs (chatEventHandler.ts:106/147/154/211)
    so post-terminal stragglers are dropped too.
  - (b) PASSES for the reload path: `loadConversation` fetches
    `conversationApi.get` + `toolExecutionApi.list`; messages are rebuilt
    with deterministic ids (`restoredMessageId`,
    conversationStore.ts:194-200, 327); tool rows are merged identity-wise
    (`hydrateConversation` → `mergeHydratedToolExecutions`,
    toolExecutionStore.ts:106-117); subagent cards are re-projected from
    durable TaskRuntime events by `taskRuntimeSubagentExecutionEvents`
    (subagentRunStore.ts:330-405), invoked from live refresh/poll paths
    (taskRuntimeStore.ts:196-197, 246). No duplicate rows on the hydration
    path — unlike the live ingest path (V03-01, P2-01).
  - (c) PASSES: listener setup uses an `aborted` flag + `pendingCleanup`
    array (useTauriChat.ts:84-167) covering three unmount races (import
    pending, between the two `listen()` calls, after registration);
    re-mount re-registers fresh refs, so a reload mid-turn cannot double-
    subscribe.
  - Caveat (backend, not frontend): after a reload mid-turn, the backend's
    `active_chat_turns` still holds the old key, so the next send returns
    `chat_turn_busy` until the old turn finishes (chat.rs:536-549) — a
    backend recovery behavior in A-SRF-02/A-TSK scope, noted for Q-E2E-01.

None.

## Conclusion

Supports: late/duplicate chat events are dropped at the boundary; reload
rebuilds from persisted facts with identity dedupe on the hydration path;
listener lifecycle is race-safe. Does not prove: dynamic behavior under real
reload mid-turn (Q-E2E-01).
