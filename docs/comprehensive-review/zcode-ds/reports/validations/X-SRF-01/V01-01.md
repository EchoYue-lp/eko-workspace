## Claim

Every product surface (GUI, TUI, CLI REPL, channels, cron, background) can be
classified per capability (chat / task / subagent / tool / HITL / attachment /
browser / MCP / memory / workspace / research) at three levels: definition,
registration, and runtime reachability — and the classification reveals which
capabilities are shared-core, which differ only in trigger/rendering, and
which are genuinely missing on a surface.

## Deviations

- The channels row for "subagent/tool/browser/MCP/memory" is `full` only in
  the sense that per-sender pool agents carry the full bootstrap-equivalent
  surface (`modes.rs:112-116` doc comment); channels have no slash/management
  surface by design (NL-only). Whether that constitutes acceptable
  "trigger/rendering difference" is the task's own verdict; the task-report
  parity table records it as a gap for task management and steer.
- Concurrent turns from one sender on the same pool agent (two spawned
  `drive_chat` on the same acquired agent, `channels.rs:135-265`) were not
  resolved: no busy-guard found in the channel adapter. Recorded as residual
  uncertainty (A-SUB-01/A-CHAT-01 territory), not a finding.
- The `channel_papers_response` routing (`channels.rs:171-179`) makes the
  research row "partial" on channels even though no slash surface exists —
  noted for the parity verdict.

## Conclusion

The matrix supports: (a) the shared-core claim — every interactive surface
enters the same `drive_chat` + TaskRuntime + pool + PreparedUserTurn core;
(b) the systematic-asymmetry claim — management surfaces (workspace,
research, evolution, browser, task, steer, cancel) are unevenly distributed;
(c) three gaps not previously filed (REPL browser management, channel task
management, REPL/channel steer) are anchored by this validation. It does not
prove runtime event-flow equivalence — that is V02.
