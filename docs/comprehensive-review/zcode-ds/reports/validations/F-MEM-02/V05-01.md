## Claim

`SqliteStore`/`SqliteConversationStore` behave semantically equivalently to
`FileStore`/`FileConversationStore` on the shared `Store`/`ConversationStore`
trait methods for identical inputs (the F-MEM-01 semantic-alignment question,
extended to the sqlite backends).

## Method

Field-by-field comparison of both Store impls and both ConversationStore impls:

```text
1. Store trait (echo-core/src/memory/store.rs) vs FileStore/InMemoryStore
   (echo-state/src/memory/store.rs) vs SqliteStore (sqlite_store.rs):
   put (metadata handling, created_at/updated_at), get, search (ordering,
   scoring), delete, list_namespaces (encoding, prefix), list, prune_expired,
   dedup_by_content, search_with.
2. ConversationStore trait (echo-core/src/memory/conversation.rs) vs
   FileConversationStore (file_conversation.rs) vs SqliteConversationStore
   (sqlite_conversation.rs): save_messages (id assignment/preservation),
   get_messages (ordering), delete_conversation (cascade), search_conversations,
   timestamps.
3. Cross-check the framework's own write path: remember tool
   (echo-agent/src/tools/builtin/memory.rs:101-117) — what metadata is embedded
   in the JSON value passed to Store::put.
4. Verify test coverage for each divergence point in both backends.
```

## Expected Result

Both backends return equivalent StoreItem/StoredMessage data and ordering for
the same trait calls; any divergence is either documented by the trait or
filed as a drift finding.

## Result

- Exit code: not-applicable (read-only comparison)
- Duration: ~10 min
- Summary of compared dimensions:

  | Dimension | FileStore / FileConversationStore | SqliteStore / SqliteConversationStore | Verdict |
  |---|---|---|---|
  | put metadata (importance/expires_at) | struct-based only; JSON value content ignored (store.rs put/and_modify, StoreItem::new) | JSON-value-based (sqlite_store.rs:509-516 put; apply_json_metadata :935-945 read) | DRIFT -> F-MEM-02-P2-01 |
  | prune_expired trigger | struct field expires_at (is_item_valid) | json_extract(value,'$.expires_at') (sqlite_store.rs:918-925) | DRIFT (consequence of P2-01) |
  | save_messages ids | preserves Some(id), advances next_id (file_conversation.rs:363-370); comment claims it "matches the SQLite autoincrement" | discards supplied ids, always autoincrement (sqlite_conversation.rs:332-345) | DRIFT -> F-MEM-02-P2-02 |
  | get_messages order | file order, no sort (file_conversation.rs:378-386; F-MEM-01-P3-02) | ORDER BY id ASC (sqlite_conversation.rs:381) | sqlite conforms; file deviates |
  | search result order | sorted by score desc (store.rs:388-396) | row order of `WHERE key IN (...)` (sqlite_store.rs:271-321, 338-393); no final sort | DRIFT -> F-MEM-02-P2-03 |
  | dedup_by_content | implemented (store.rs:300-345 area) | trait no-op (not overridden) | DRIFT -> F-MEM-02-P3-02 |
  | namespace encoding | join("/") + split("/") + starts_with prefix (store.rs:59,153 etc.) | join("/") + split("/") + LIKE 'prefix%' (sqlite_store.rs:401,766-777) | shared flaw — F-MEM-01-P3-01 applies to sqlite too (not re-filed) |
  | timestamps | RFC3339 strings (file_conversation.rs now_rfc3339) | datetime('now','localtime') "YYYY-MM-DD HH:MM:SS" (sqlite_conversation.rs:72-73) | format divergence; both lexicographically sortable; consumers parsing RFC3339 would break on sqlite — noted, not filed (no documented RFC3339 contract) |
  | delete cascade | file removal per conversation (file_conversation.rs:338-346) | FK ON DELETE CASCADE + foreign_keys=ON PRAGMA (sqlite_conversation.rs:41,80) | equivalent |

- Framework write-path evidence: the `remember` tool embeds
  `"importance": N` into the JSON value before Store::put
  (echo-agent/src/tools/builtin/memory.rs:104-117), so the P2-01 drift is live
  on the framework's own path: SqliteStore returns `item.importance = N`,
  FileStore/InMemoryStore always return 5.0.
- Test coverage: FileConversationStore has extensive tests including id
  handling (F-MEM-01 V04); SqliteConversationStore has zero tests
  (V03-01 deviation 1).

## Deviations

None beyond the drifts listed (each filed as a finding).

## Conclusion

Supports: the sqlite backends are NOT semantically equivalent to the file
backends on four trait dimensions (metadata handling, message-id preservation,
search ordering, dedup), plus one shared namespace-encoding flaw already filed
by F-MEM-01-P3-01. Also confirms one place where sqlite is the conforming
implementation (get_messages id-ASC ordering) while the file backend deviates.

## Follow-Up

F-MEM-02-P2-01, P2-02, P2-03, P3-02. The trait contract itself may need
clarification (which convention is authoritative) — candidate for the
framework-contract iteration.
