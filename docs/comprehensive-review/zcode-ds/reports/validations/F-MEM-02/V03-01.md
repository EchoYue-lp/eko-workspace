## Claim

The sqlite test suite passes under `--all-features`, rusqlite errors propagate
as `MemoryError` (never panic), and concurrent access is handled: single
in-process connection serialized by a Mutex, cross-process via WAL +
busy_timeout.

## Method

```text
1. Execute: cd echo-agent && cargo test -p echo_state --all-features --lib --locked sqlite
   (expect exit 0; workspace parallel compilation may queue on file locks).
2. Static inspection of concurrency handling:
   - sqlite_store.rs:62-68 (single Mutex<Connection> rationale), :111-117
     (PRAGMA journal_mode=WAL, synchronous=NORMAL, busy_timeout=5000), :124-128
     (poisoned-lock error path), :478-497 (embedding computed BEFORE taking the
     connection/lock so no await while holding std MutexGuard), :454-456
     (semantic path drops conn before re-acquiring).
   - sqlite_conversation.rs:14,21 (tokio::sync::Mutex), :313-318 (BEGIN IMMEDIATE),
     :326-350 (ROLLBACK on delete/insert failure), :364-365 (COMMIT).
3. Static inspection of error propagation: memory_io_error (echo-state
   src/util.rs:24-26) wraps rusqlite errors into MemoryError::IoError;
   serde failures -> MemoryError::SerializationError (sqlite_store.rs:474,587);
   QueryReturnedNoRows -> Ok(None) (sqlite_store.rs:602, sqlite_conversation.rs:171);
   delete of missing key -> Ok(false) (sqlite_store.rs:743).
4. Panic-safety scan of the two sqlite files for unwrap/expect/byte-index on
   untrusted data.
```

## Expected Result

Exit 0 with all sqlite tests green; no panic-capable unwrap/expect on
error/DB-data paths; concurrency design serializes writes in-process and relies
on WAL + busy_timeout cross-process.

## Result

- Exit code: 0
- Duration: ~6 s (after incremental build)
- Summary: `cargo test -p echo_state --all-features --lib --locked sqlite`
  -> "test result: ok. 15 passed; 0 failed; 0 ignored; 0 measured; 131 filtered
  out". All 15 tests live in sqlite_store.rs (put/get/upsert/delete, FTS5
  search, LIKE-fallback, persistence across instances, namespace isolation,
  semantic-without-embedder error, with-embedder search, vector
  serialization, cosine similarity, extract_searchable_text).
- Concurrency: in-process access fully serialized (std Mutex for SqliteStore,
  tokio Mutex for SqliteConversationStore); the std MutexGuard is never held
  across `.await` (embedding computed before lock acquisition, sqlite_store.rs
  :478-497; the semantic path drops the guard and re-acquires, :454-456), so
  the BoxFuture stays Send; poison is mapped to MemoryError::IoError (:124-128).
  Cross-process: WAL + synchronous=NORMAL + busy_timeout=5000 (PRAGMA block,
  :111-117) gives multi-process readers and serialized writers with a 5 s busy
  wait — acceptable single-writer-plus-readers behavior for a local assistant
  framework option.
- Error propagation: every rusqlite error site is mapped via memory_io_error or
  an explicit IoError/SerializationError; no `unwrap`/`expect` exists in
  production code of either file (only test code and the guarded
  `partial_cmp(...).unwrap_or(Ordering::Equal)` at :451,896-901; `chunk[0..3]`
  in bytes_to_vec :234 is safe because `chunks_exact(4)` guarantees length 4;
  expand_tilde's `&s[2..]` at util.rs:8 is guarded by `starts_with("~/")` and
  cannot hit a mid-character boundary).
- Log/artifact: /tmp/fmem02_v03.log

## Deviations

1. `SqliteConversationStore` has zero tests (no `#[cfg(test)]` in
   sqlite_conversation.rs — grep verified). The 15-run sqlite suite covers only
   SqliteStore. (Finds expression in F-MEM-02-P3-05.)
2. `save_messages` (sqlite_conversation.rs:313-365) uses a manual
   BEGIN IMMEDIATE / COMMIT / ROLLBACK; on insert/delete failure the ROLLBACK
   error is ignored (`let _ = conn.execute("ROLLBACK", [])`), so a failed
   rollback leaves the shared pooled connection inside an open transaction that
   subsequent operations inherit. Low probability (rollback fails only on
   I/O errors) — robustness note folded into F-MEM-02-P3-05.
3. Cross-process contention was assessed statically only; no concurrent
   multi-process test exists in the repo.

## Conclusion

Supports: the sqlite feature test suite passes (exit 0); error propagation and
in-process serialization are sound and panic-safe. Does not prove: cross-process
behavior under contention (static only), SqliteConversationStore correctness
(untested — a coverage gap, not a failing behavior).
