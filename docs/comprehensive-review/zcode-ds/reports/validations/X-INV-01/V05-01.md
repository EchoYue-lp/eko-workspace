## Claim

No live production code byte-slices a `&str`/`String` at a non-char-boundary
offset (`&s[..n]` / `&s[n..]` truncation without `char_indices()` /
`floor_char_boundary()` / ASCII-delimiter guarantee). Two suspected live
violations (found by static scan) are reproduced with standalone snippets
to prove the panic.

## Method

```text
# 1. static scan: all range-slice patterns in production regions (above the
#    first #[cfg(test)] per file), excluding comment lines
python3 - <<'EOF'  # patterns: var[..x], var[x..], var[..=x], &var[..]
...
EOF
# 2. classification: Vec/array slices (safe), ASCII-delimiter find() offsets
#    (safe: find() always returns a char boundary), floor_char_boundary /
#    char_indices (safe by design), or candidate violation
# 3. reproduction of the two live candidates with standalone rustc programs
cd /tmp && cat > t_eval.rs <<'EOF' ... EOF && rustc -O t_eval.rs -o t_eval && ./t_eval
cd /tmp && cat > t_pdf.rs  <<'EOF' ... EOF && rustc -O t_pdf.rs  -o t_pdf  && ./t_pdf
```

## Expected Result

Either zero live violations, or a reproduced panic for each violation found.

## Deviations

## Conclusion

The UTF-8 safety invariant **fails** on two live framework paths
(`echo-tools` pdf tool under the `research` feature; `src/eval` runner
under the `eval` feature), both deterministic panics on abnormal input —
see task report findings X-INV-01-P1-01 / X-INV-01-P1-02. The CLI is clean.
