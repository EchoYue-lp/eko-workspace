## Claim

Every permission-sensitive operation is classifiable as either an
agent-automated path (which passes through the framework permission pipeline)
or a direct user interaction (which must carry no permission-mode gate); the
classification is complete for tool calls, interactive terminal, file picker,
MCP configuration, and browser interactions.

## Method

Static call-path tracing at the current commits. For each operation the
definition -> registration -> live-caller chain was followed in source:

1. Agent tool call (any tool): `ToolExecutionPipeline` default composition
   (`echo-agent/src/agent/react/run/pipeline.rs:268-346` `PermissionStage`,
   `:1004-1018` `PlanModeStage`) -> `AgentRunSnapshot::check_tool_approval`
   (`echo-agent/src/agent/snapshot.rs:798-870`) ->
   `PermissionService::check_with_permissions_in_mode`
   (`echo-orchestration/src/human_loop/service.rs:484-681`).
2. Interactive terminal: `create_terminal` / `write_terminal` /
   `confirm_terminal_consent` (`echo-agent-cli/src/tauri/terminal.rs:281-375`).
3. File picker: `web-frontend/src/lib/tauri-bridge.ts:85-95`
   (`@tauri-apps/plugin-dialog` `open()`), capability grants
   `echo-agent-cli/src-tauri/capabilities/default.json:10-14`.
4. MCP connect/configure: `connect_mcp_server` (`src/tauri/commands/mcp.rs:211-258`),
   `update_mcp_config` (`mcp.rs:476-559`), `validate_ipc_mcp_url` (`mcp.rs:169-208`),
   `validate_ipc_mcp_stdio` (same file).
5. Browser: agent tool path (1) plus `BrowserRuntime::confirm_action`
   (`echo-agent-cli/echo-agent-app-core/src/browser/mod.rs:978-1018`).
6. Agent `run_code`: `echo-tools/src/code.rs:305-345` (sandbox floor) vs the
   interactive terminal (2) — separation verified.
7. Subagent/task automation: EKO factory construction
   `echo-agent-cli/echo-agent-app-core/src/infra.rs:881-966` /
   `:968-1010`, pool agent construction `agent_pool.rs:824-975`,
   shared-resource extraction `agent_pool.rs:120-150,224,928-932`.

## Expected Result

- Agent tool calls pass through `PermissionStage`; direct user commands
  (terminal, file picker, MCP) contain no `permission_mode` read.
- Subagent/pool construction either inherits the permission service or is
  explicitly documented as not doing so.

Key reachability facts confirmed at the current commits:

- Primary agent service wiring: `runtime.rs:130-141`
  (`set_human_loop_provider(HitlDispatcher)` then `build_permission_service`);
  pool agents share the same `PermissionService` Arc
  (`agent_pool.rs:136,224,928-929`); pool agents get an empty `HitlDispatcher`
  as handler (`agent_pool.rs:955-975`).
- TaskRuntime subagent factories wire no permission service/provider/mode
  (grep: zero `build_permission_service` / `set_human_loop_provider` /
  `permission` hits inside `build_writer_subagent_agent` /
  `build_readonly_subagent_agent`, infra.rs:881-1040); they do call
  `subagent.set_plan_mode(true)` (infra.rs:963) which blocks write
  tools/shell/delete_file via visibility filter (snapshot.rs:227-236) and
  `PlanModeStage` (pipeline.rs:1004-1018) — but `run_code`/network/browser/
  git/data tools are not in the blocklist.
- Protected-path checks (.git/.ssh/.env) live inside `PermissionService`
  (service.rs:505-521) and therefore do not run for agents without a service.

## Deviations

None — the classification is complete. Two consequences of the trace are

## Conclusion

Supports: the direct-user surfaces (terminal, file picker, MCP configuration)
carry no permission-mode gate and remain usable; primary/pool agent automation
is gated by the single framework enforcement point (`PermissionStage`).
Does NOT support: that the same control applies to TaskRuntime subagent
automation — the permission boundary is not reachable there (P1-01).
