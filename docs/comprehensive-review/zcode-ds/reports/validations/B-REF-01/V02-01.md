## Claim

Codex exposes a typed, append-only **JSONL event stream** for non-interactive
execution (`codex exec --experimental-json`), with event/item types defined
in `codex-rs/exec/src/exec_events.rs`, durable per-turn rollout recording
(JSONL + SQLite index), and a sandbox + approval-policy model
(read-only / workspace-write / danger-full-access; approval Never in exec).

## Method

Lookup: `openai/codex` repository docs via zread search (doc pages
`22-protocol-and-type-definitions`, `9-thread-manager-and-rollout-recording`,
`10-tool-orchestrator-and-approval-flow`, `19-python-and-typescript-sdks`,
`18-app-server-protocol`) on 2026-08-12; plus web search confirming
`--sandbox workspace-write --full-auto` usage and workspace-write writable
roots (cwd, /tmp, $TMPDIR; protected `.git/`, `.codex/`). Official docs at
`developers.openai.com/codex/automation/non-interactive-mode` were not
fetchable (403/network) — limit noted.

## Expected Result

Concrete event type names, rollout persistence ordering, and sandbox policy
names.

## Result

- **Event stream**: newline-delimited JSON events from `codex exec
  --experimental-json`; the TypeScript SDK mirrors the Rust
  `exec_events.rs` types; observed event shapes include
  `item.started`, `item.agentMessage/delta`, `thread/started`,
  `turn/completed`, and terminal thread/rollout events (`record_ended`
  emits `ThreadEnded` + root-only `RolloutEnded`).
- **Durable rollout**: every turn (model response, tool call, user message,
  compaction) is durably recorded as an **append-only JSONL rollout file**
  on disk, indexed by a SQLite state database; `next_seq` counter gives
  monotonic event ordering; **payload files are written before the event
  that references them** so a replay interrupted after an event append never
  points at a missing payload.
- **Sandbox policies**: `read-only`, `workspace-write` (writable roots cwd,
  /tmp, $TMPDIR; protected subpaths `.git/`, `.codex/`), `danger-full-access`;
  approval policies include `Never` (used by non-interactive `codex exec`)
  and `AskForApproval` variants; tool orchestrator resolves
  sandbox+approval policy chains; exec policy + command canonicalization
  feed approval requirements.
- **Items vs events**: items are the conversation-level unit projected both
  onto the event stream and into the model context; terminal states flow
  through typed events (no text scraping).

## Deviations

Exact `item.in_progress/completed/failed` naming from the task card's
memory was not found verbatim in this lookup; the authoritative set lives in
`exec_events.rs`, and the observed names are `item.started`,
`item.agentMessage/delta`, `thread/started`, `turn/completed`. The naming
difference is recorded, not treated as an error in the referenced system.

## Conclusion

Supports: typed JSONL event stream as the external contract; append-only
durable rollout with payload-before-event ordering and monotonic sequence
(crash-safe recovery); sandbox/approval policy separation. Directly relevant
to EKO's `events.jsonl` recovery authority and typed terminal event kinds.

Does not prove: current official-doc phrasing (unreachable) or the complete
exec_events.rs variant list.
