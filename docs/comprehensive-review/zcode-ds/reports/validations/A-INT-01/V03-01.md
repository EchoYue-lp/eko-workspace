## Claim

MCP connect/disconnect/reconnect and invalid-config handling on the EKO side
behave as documented: reconnect removes stale tools and is bounded; invalid
config entries are handled without taking down healthy servers or stalling
startup.

## Method

Static inspection of the EKO boot and GUI reconnect paths plus framework
semantics:

```text
1. Reconnect: capabilities.rs:1149-1162 (connect_mcp_from_config disconnects
   same-name client and removes stale tools first), McpManager::connect
   (echo-integration/src/mcp/mod.rs:73-97, same-name replace).
2. GUI reconnect: mcp.rs:502-553 — disconnect-all then reconnect each with
   CONNECT_TIMEOUT=15 s, per-server skip on error/timeout; invalid entry
   skipped with warn (mcp.rs:526-531).
3. Boot load: infra.rs:1069-1108 — load_mcp_from_file with NO per-server
   deadline; framework to_server_configs (config_loader.rs:194-201) returns
   Err on the first invalid entry (all-or-nothing, `?` propagation);
   connect_mcp_from_config per-server errors are skipped
   (capabilities.rs:1251-1262).
4. Transport timeouts: stdio send timeout 120 s (stdio.rs:209-211); client
   initialize handshake goes through transport.send with no extra deadline.
5. Health/recovery: state.rs:750-797 marks healthy = client && !tools().is_empty();
   no auto-reconnect anywhere for dropped stdio servers (grep "reconnect"
   in echo-agent-cli -> only mcp.rs:502-553 config-save path and browser
   call_mcp restart).
6. Agent-level tool registry: disconnect_mcp removes registered tools by
   exposed name (capabilities.rs:1315-1331).
```

## Expected Result

- Reconnect is non-destructive on failure and bounded in time on the GUI path.
- One invalid config entry does not disable all other servers.
- Startup with a hung-but-alive server is bounded.
- A dropped MCP server either auto-recovers or is clearly reported.

## Result

- Exit code: not-applicable (static)
- Summary:
  - Reconnect at agent level: correct (stale tools removed before
    re-registration).
  - GUI reconnect: bounded per server (15 s), skip-on-failure; but it first
    disconnects ALL servers, holds the agent write lock for the whole loop,
    and runs detached in `tokio::spawn` (mcp.rs:502-553) — worst-case agent
    lock hold N x 15 s after a config save, and an app exit mid-loop can
    leave servers disconnected.
  - Boot path: NO per-server deadline (a stdio server that spawns but never
    answers `initialize` stalls boot up to the 120 s stdio transport timeout
    per server), and `to_server_configs` is all-or-nothing — one entry
    without `command`/`url` rejects the entire file, so zero servers connect
    at boot while the GUI path skips that same entry individually. Task
    report finding P2-02.
  - Recovery: no auto-reconnect for user-configured MCP servers; after a
    server dies (stdio EOF drains pending with -32000, client stays alive
    but dead), tools remain registered and fail until the user manually
    reconnects via GUI toggle or config save; the 30 s health loop only
    paints status. Task report finding P2-04.
  - Agent-level disconnect removes tools (healthy path verified).
- Log/artifact: none

## Deviations

- Findings P2-02 (boot all-or-nothing + unbounded) and P2-04 (no
  auto-recovery) are the deviations from the expected result.

## Conclusion

Supports: the reconnect/registry-sync invariant holds at the agent level;
GUI reconnect is bounded; boot-time invalid/hung config handling violates the
expected invariant (all-or-nothing, unbounded). Does not prove timing
behavior dynamically (no hung server was spawned; read-only review).
