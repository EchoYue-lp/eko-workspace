## Claim

Direct user operations (connecting MCP servers, opening the terminal,
browser interactions) are not gated by agent `permission_mode`
(`require_full_auto`/`IpcAuth` etc.) — the historical over-gating is not
reintroduced; only light input validation remains. Browser consequential-
action confirmations route through the EKO HITL dispatcher.

## Expected Result

- Zero `require_full_auto`/`IpcAuth` call sites on the interactive MCP,
  terminal, and browser paths (AGENTS.md historical lesson holds).
- The only guards are input validation and the browser HITL confirmation.
- The same MCP server configuration is treated consistently by the dialog,
  the config editor, and the on-disk file.

## Result

- Exit code: not-applicable (static)
- Summary:
  - No permission-mode gate on `connect_mcp_server` (mcp.rs:217-221 comment
    documents the local-model rationale), terminal (A-TOOL-01 V03-01), or
    browser commands. `IpcAuth`/`IpcPermission` have zero callers (A-HITL-01
    V01-01). The hard rule ("用户配置 MCP/开终端被 agent 权限门控 = P1") is
    NOT triggered — no such gate exists.
  - Input validation on `connect_mcp_server`: stdio executable allowlist
    (npx/node/uvx/…), https-only + private/loopback-range rejection for
    HTTP/SSE URLs (mcp.rs:169-208). The URL validator BLOCKS
    localhost/127.x/10.x/192.168.x/172.16-31.x and requires https — this is
    SSRF-style over-gating for a local assistant: the config-file path
    (boot load and `update_mcp_config` -> `McpConfigFile` -> framework
    `to_server_config`, config_loader.rs:109-152, doc example
    `http://localhost:8080/mcp` at config_loader.rs:26) accepts the same
    endpoints, and EKO's own network policy (MASTER-PLAN:74) allows
    loopback/private plain HTTP for web tools. A user cannot connect a local
    MCP server from the GUI dialog, only from the config file. Task report
    finding P2-03.
  - Browser confirmations route through the dispatcher (default provider),
    i.e., the REPL provider (runtime.rs:130-131). Consequences:
    (a) piped/scripted CLI runs auto-approve consequential browser actions
    (purchase/send_message/…, risk-driven, browser/mod.rs:465-522) once stdin
    hits EOF (A-HITL-01-P1-02 chain); (b) GUI windows before the
    per-conversation provider is set hit the same REPL provider (EOF at
    /dev/null auto-approves). "Approve all" -> SessionAllTools -> "*"
    wildcard (A-HITL-01-P1-03) also covers browser tools. Task report
    cross-reference finding P2-05.
  - Consistency: the dialog, the config editor, and the on-disk file apply
    different validation rules to the same server definition (dialog strict,
    editor/file lenient) — asymmetry feeding P2-03.
- Log/artifact: none
