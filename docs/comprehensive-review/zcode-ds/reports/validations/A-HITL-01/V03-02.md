## Claim

Direct user interactions (terminal, file picker, MCP configuration) are not
gated by agent permission modes (AGENTS.md hard invariant), while automated
agent actions are gated through `PermissionService`; default permission-mode
scenarios (no rules, default mode) ask for Write/Execute/Network/Sensitive
tools through the EKO provider, and mode changes propagate everywhere.

## Expected Result

- create_terminal / connect_mcp_server / file commands carry no
  `require_full_auto` or permission-mode check; only lightweight input
  validation and the write-consent mechanism exist.
- In `default` mode with no rules, tools carrying Write/Execute/Network/
  Sensitive go through the handler (EKO provider); Read-only tools run
  without asking; protected paths deny in all modes.
- `full-auto` maps to `BypassPermissions` (with the loud warning),
  `strict` → StrictConfirm, `auto-edit` → AcceptEdits, legacy aliases
  `auto`/`plan` → Default; changing mode clears the approval cache.
- GUI rule management (add/remove/list) does not affect decisions because the
  stored rules have no consumer (V01-01); this must be confirmed as behavior.

## Result

- Exit code: not-applicable (static inspection)
- Duration: ~30 minutes
- Summary:
  - Direct-user surfaces: no permission-mode gate on create_terminal
    (terminal.rs:286-289 comment documents the local-threat-model rationale),
    connect_mcp_server (mcp.rs:217-221 comment; input validation only),
    or any files command. `write_terminal` requires per-session user consent
    (`confirm_terminal_consent`, terminal.rs:366) + size cap + audit log —
    a consent/audit guard, not a permission-mode gate. `IpcAuth` has zero
    callers (V01-01). AGENTS.md over-gating invariant holds on the
    application side.
  - Default-mode behavior: `default_confirmation_required` = Write|Execute|
    Network|Sensitive (service.rs:167-172); with EKO's real handler, these
    ask via `check_with_handler` → provider; otherwise Allow (service.rs:589-594).
    Protected paths deny before modes (service.rs:526-541). No default rules
    are installed by EKO (state.rs:482 empty rules; no add_rule calls in EKO).
  - Mode propagation: GUI panels.rs:59-77 (state + primary agent +
    pool.apply_permission_mode), TUI events.rs:3585-3605, CLI
    coding.rs:665-681; framework set_permission_mode normalizes and calls
    `service.set_mode_sync` + `service.clear_cache` (react/mod.rs:2063-2080).
    Pool agents get the mode at creation (agent_pool.rs:931-932) and on
    apply (agent_pool.rs:467-483).
  - Mode values: "default" is the boot default (state.rs:481,
    agent_pool.rs:249); "auto"/"plan" normalize to "default" on all three
    surfaces (panels.rs:50, tui events, coding.rs:665).
  - GUI rules: `add_permission_rule`/`remove_permission_rule`
    (panels.rs:102-151) only mutate `AppState.config.permission_rules`;
    `list_permission_rules` only reads it; nothing converts
    `PermissionRuleConfig` into framework rules; `matches_tool`,
    `to_permission_decision`, `parse_permission_flag` (state.rs:145-201)
    have zero callers (V01-01). A GUI-configured `deny tool:shell` or
    `ask tool:write_file` rule therefore never affects any tool call —
    the rules panel is a non-functional policy surface. (Finding P1-01.)
  - Denial escalation: after 3 consecutive denials the denial tracker returns
    `RequireApproval` (service.rs:575-585); on the live path
    `check_tool_approval` maps `RequireApproval` to a hard error
    (snapshot.rs:841-846) — the user is not asked. EKO-reachable in default
    mode (user rejecting 3 times in a row) and in background runs whose pool
    agents auto-reject every approval (empty dispatcher, V02-01): three
    auto-rejections upgrade later tools to opaque errors. (Finding P2-03.)
  - "Approve all" scope: TUI 'a' (events.rs:242-244), REPL 'a'
    (repl_provider.rs:77-79), channel "a"/"全部同意" (channel_provider.rs:158-160),
    GUI "本会话同意" → scope `"session_all_tools"` (ChatPanel.tsx:321-322 →
    chat.rs:336-339) all send `ApprovedWithScope { SessionAllTools }`; the
    framework bridge `response_with_scope` maps that scope to a `"*"` session
    allow rule (service.rs:898-908), and `RuleMatcher::Pattern("*")` matches
    every tool (echo-core permission.rs:253-255) — one "approve all" unlocks
    ALL tools for the session on every surface. (Finding P1-03; framework
    defect F-HITL-01-P1-03, EKO is its primary consumer.)
  - Modified-args (F-HITL-01-P1-02): all EKO surfaces treat "modify" as a
    feedback rejection (TUI events.rs:53-81 Rejected-with-reason; GUI
    ChatPanel.tsx onModify → `sendApproval(false, "修改意见: ...")`;
    REPL/channel "m" → Rejected). No EKO surface emits `ModifiedArgs`, so
    the framework's discarded-args side channel is NOT triggered by EKO —
    EKO mitigates that specific defect by not using the feature.

## Deviations

- None beyond the findings listed (P1-01, P1-02, P1-03, P2-03); the channel
  provider's cross-sender isolation issue (P2-02) and the GUI bypass of the
  dispatcher (P2-01) were confirmed in V01/V02/V03-01.

## Conclusion

Supports: direct-user surfaces are free of permission-mode gating (the
AGENTS.md invariant holds); default mode asks for Write/Execute/Network/
Sensitive via the EKO provider; mode propagation is complete and consistent
across surfaces; GUI rule management is behaviorally dead; the denial-escalation
path degrades to opaque errors on the EKO path; "approve all" widens to a
session-wide `*` rule on every EKO surface.
