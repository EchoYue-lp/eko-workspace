## Claim

Every approval transport and permission-mode wiring is either registered on a
live runtime path (with the entry-point map below) or provably unreachable;
the per-surface provider map matches the claimed arbitration model.

## Expected Result

- TUI and CLI share one `HitlDispatcher`; GUI uses a per-conversation handler;
  channels use a per-handler channel provider; the map is consistent with the
  code comments and docs.
- GUI permission-mode changes propagate to agents and the framework service.
- Direct-user command surfaces (terminal, MCP, files) carry no permission-mode
  gate.

## Result

- Exit code: not-applicable (static trace)
- Duration: ~45 minutes
- Summary (verified wiring):
  - Runtime bootstrap (`runtime.rs:128-146`): one `HitlDispatcher` created,
    "repl" registered, set as primary-agent provider, `build_permission_service()`
    called (service built from provider via `DynProviderHandler`), dispatcher
    also set as browser-runtime default approval provider.
  - TUI (`main.rs:250-257`): unregisters "repl", registers "tui"; TUI renders
    the provider's `pending` handle. CLI/REPL keeps "repl".
  - GUI: primary agent keeps the dispatcher-with-repl (never unregistered);
    every chat turn (`chat.rs:570-582`) installs a per-conversation
    `TauriHumanLoopHandler` on the pool agent via
    `set_human_loop_provider_preserving_approvals`, and installs the same
    handler as the browser per-conversation provider (`chat.rs:583-589`);
    at turn end the agent's provider is replaced with an EMPTY
    `HitlDispatcher` (`chat.rs:712-719`).
  - Pool agents: created with an empty `HitlDispatcher`
    (`agent_pool.rs:960-975`, comment: approval requests auto-reject instead
    of blocking on stdin). Channels re-inject the shared
    `ChannelHumanLoopProvider` on every inbound message (`channels.rs:141-146`).
  - Background/cron runs (`tasks/service.rs:418-430`) run on pool-acquired
    agents → empty dispatcher → every approval-worthy tool call is auto-rejected
    with `Rejected { "No HITL provider available" }` (dispatcher.rs:82-87).
  - Permission mode: GUI `set_permissions_mode` (panels.rs:43-77) writes
    state and calls `agent.set_permission_mode` + `pool.apply_permission_mode`;
    framework `set_permission_mode` (react/mod.rs:2047-2084) normalizes and
    propagates to `PermissionService::set_mode_sync` and clears the approval
    cache. TUI (events.rs:3580-3605) and CLI (coding.rs:645-675) mirror this.
  - Decision pipeline: `PermissionStage` (pipeline.rs:268-347) →
    `snapshot.check_tool_approval` (snapshot.rs:798-857) →
    `service.check_with_permissions_in_mode` (service.rs:484-681); Default
    mode asks via handler when the tool carries
    Write|Execute|Network|Sensitive (service.rs:167-172); `Allow` returns
    `Ok(None)` (snapshot.rs:834) — the `last_modified_args` side channel
    (service.rs:729-731) is never read on the live path (F-HITL-01-P1-02).
  - Direct-user surfaces: `create_terminal` (terminal.rs:278-297),
    `connect_mcp_server` (mcp.rs:211-258), files commands: no permission-mode
    gate anywhere; `IpcAuth` has zero callers (V01-01).
  - GUI scope mapping: only `"session_all_tools"` is recognized
    (chat.rs:335-342); all four surfaces + browser map "approve all" to
    `ApprovedWithScope { SessionAllTools }`.

## Deviations

- GUI does not participate in the shared dispatcher's arbitration; the
  dispatcher is documented as the "HITL unification module" but the Tauri
  surface never registers on it (P2-01).
- GUI turns replace the provider with an empty dispatcher at turn end; the
  browser per-conversation provider is NOT cleared at turn end (browser
  approvals after a turn still reach the Tauri handler).
- Whether TaskRuntime plan subagents inherit the primary agent's
  provider/permission service is not resolvable from this slice (framework
  subagent construction; F-SUB-02 owns it) — recorded as uncertainty.

## Conclusion

A-HITL-01 findings P1-01, P1-02, P1-03, P2-01, P2-02, P2-03; confirms direct
user command surfaces are free of permission-mode gates and that mode changes
propagate end-to-end. Does not prove runtime behavior (V03), and does not
resolve subagent-provider inheritance.
