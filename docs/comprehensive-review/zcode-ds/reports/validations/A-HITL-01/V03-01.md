## Claim

Provider arbitration and cancellation behave as documented: one shared
deadline bounds the total wait; the first substantive response wins and the
remaining provider futures are cancelled; a single provider failure does not
fail the request; all-provider failure fails closed; provider timeout
signaling is consistent; and the TUI provider cleans up its pending state on
cancellation.

## Method

Full read and line inspection of `echo-agent-cli/echo-agent-app-core/src/hitl/dispatcher.rs`
(167 lines), `tui_provider.rs` (351 lines), `repl_provider.rs` (183 lines),
`channel_provider.rs` (292 lines), plus the framework bridge
`echo-orchestration/src/human_loop/service.rs:855-925` (DynProviderHandler
response mapping) and framework `HumanLoopResponse` variant semantics.

## Expected Result

- Dispatcher: parallel broadcast, first Ok-response wins, shared 5-minute
  deadline computed once, remaining futures dropped on return, fail-closed
  `Rejected` when all providers err/time out, `Rejected` when no providers
  are registered.
- TUI provider: publishes a `PendingApproval`, waits on oneshot with
  `req.timeout` fallback 300 s, returns `Timeout` variant, clears pending on
  response/timeout/drop (PendingCleanup).
- Channel provider: supersedes a previous pending request with an explicit
  rejection, returns `Timeout` after 300 s.
- REPL provider: blocks on stdin; dispatcher deadline is expected to bound it.
- Timeout responses map to denial in the service (fail-closed).

## Result

- Exit code: not-applicable (static behavior inspection; the TUI/channel
  provider tests were executed separately in V04-01)
- Duration: ~30 minutes
- Summary:
  - Dispatcher (dispatcher.rs:63-166): snapshot-before-await implemented
    (:74-80); empty-provider auto-reject (:82-87); parallel broadcast +
    first-response-wins (:89-155); single shared deadline
    `TIMEOUT_DURATION = 5*60s` computed once (:101-102); per-future
    `timeout_at(deadline, ...)` (:121); returning drops `pending` and cancels
    the remaining futures (:134-137); all-failed → `Rejected` with joined
    reasons (:157-163). Matches the documented contract.
  - TUI provider: pending published under lock (:191-194); `PendingCleanup`
    drop spawn clears only the matching `request_id` (:83-105); timeout
    returns `Timeout` variant (:217-222); channel-drop returns `Rejected`
    (:209-216); the `cancelling_request_clears_pending_approval` test proves
    the cleanup path (passed, V04-01).
  - Channel provider: supersede-with-rejection on new request (:95-101);
    timeout → `Timeout` (:113-119); clears pending only if request_id still
    matches (:120-127).
  - GUI Tauri handler (chat.rs:330-354,378-389,417-430): per-kind
    `tokio::select!` with a hard-coded 300 s sleep; timeout → `Timeout`;
    response → mapped; entries removed from the global `PENDING_RESPONSES`
    map on all exits.
  - Service bridge (service.rs:855-925): `Timeout` → `denied("请求超时")`
    (:892-894) — consistent fail-closed; `Rejected` → denied; `ApprovedWithScope`
    → rule updates (see V03-02 for the wildcard mapping).
  - REPL provider (repl_provider.rs:68-72): synchronous `std::io::stdin()
    .read_line()` inside the async request; the dispatcher's `timeout_at`
    cannot fire while a worker thread is blocked inside `read_line`, so the
    shared deadline is NOT enforceable when the REPL provider is awaiting
    stdin. The dispatcher comment's claim "the total wall-clock wait is
    bounded by TIMEOUT_DURATION regardless of how many providers are
    registered" (dispatcher.rs:96-100) is therefore false for this provider.
  - REPL provider approval parsing (repl_provider.rs:74-77): `""` (EOF or
    empty line) maps to `Approved` — the fail-open branch. `handle_input`
    rejects empty text (:130-135) but `handle_approval` approves it.

## Deviations

- Two REPL-provider defects against the arbitration/timeout invariant:
  deadline ineffectiveness while stdin blocks, and empty-input auto-approval
  (EOF in piped/non-interactive contexts). Recorded as A-HITL-01-P1-02.
- The GUI handler's 300 s timeout is per-request hard-coded (bypasses the
  dispatcher — P2-01); total wait for the GUI surface is 300 s, matching the
  shared deadline in practice, but the deadline is not shared across
  surfaces.

## Conclusion

Supports: dispatcher arbitration/cancellation semantics as documented for
non-blocking providers; TUI/channel cleanup-on-cancel correctness (with test
evidence); consistent fail-closed mapping of `Timeout` in the service bridge.
Does not prove the dispatcher's bounded-wait claim for the REPL provider —
it is disproved statically (blocking read defeats `timeout_at`); dynamic
confirmation is a Q-E2E item.
