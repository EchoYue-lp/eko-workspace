## Claim

The claim/revision protocol rejects stale-revision operations: a `claim_task`
carrying an old plan revision returns `ReloadSnapshot`, a completion write
whose claim no longer matches (task removed by a revision commit, or task
reset after a spec change) returns `Superseded`, and terminal task state is
never regressed by any stale write.

## Method

Standalone probe driving the REAL `TaskRuntimeStore` over a temp shadow root
(`/tmp/qflt02-probe/src/bin/s1_stale_revision.rs`, built with the real
`echo-agent-app-core`). The initial plan is committed by appending the same
`PlanRevisionCommitted` event payload the store's own `attach_plan_for_test`
helper writes (that helper is `#[cfg(test)]`, so the probe reproduces its
event shape through the public `FileTaskShadow` API). Raw revision commits are
followed by store re-creation (restart shape) so seq numbering stays
consistent.

Steps: (1) claim t1 at rev 1 -> `Claimed`; (2) re-claim while Running ->
`ReloadSnapshot`; (3) external revision bump 1->2 that removes t2 (event
payload mirrors `compare_and_commit_revisioned_task_graph`, store.rs:867-880);
(4) claim with stale rev 1 -> `ReloadSnapshot`, claim of removed t2 ->
`ReloadSnapshot`; (5) completion of the still-live rev-1 claim -> `Applied`;
(6) stale completion on the removed task -> `Superseded`; (7) revision bump
1->3 changing t1's spec WITH `reset_task_ids` (the patch engine's Reset
effect) -> t1 back to Pending with claim cleared, old-claim completion ->
`Superseded`; (8) duplicate completion after terminal -> `Superseded`.

Static side (code-path analysis of fault propagation):
- `claim_task` CAS: revision check first, then Pending + spec equality
  (`echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/store.rs:992-1028`).
- `set_claimed_task_status`: accepts only while the exact claim is still
  Running (`store.rs:1040-1062`).
- Tool layer: `task_execute` requires the exact latest revision and hard-errors
  on mismatch (`task_execute_tool.rs:277-282`); `task_update` CAS rejects stale
  base revisions (`store.rs:786-792`).
- Framework safe point reloads and tracks `active_revision`
  (`echo-agent/echo-orchestration/src/tasks/runtime_executor.rs:211-230`).
- Patch engine refuses to modify Running tasks
  (`echo-agent/echo-orchestration/src/tasks/revisioned.rs:525-541`), which
  closes the "replace spec at same id while Running" window (negative result).

## Expected Result

Every stale-revision/stale-claim operation returns `ReloadSnapshot` or
`Superseded`; terminal status is preserved; a live claim's completion after a
non-spec revision bump is still accepted (revision commits do not abort
in-flight work).

## Deviations

None. Step 5's acceptance of the live rev-1 claim after the rev-2 bump is the
documented semantics (revision commits preserve in-flight execution; the
run-level completion gate re-checks the latest revision), not a stale-write
acceptance — the claim object still matched the durable Running claim.

the claim CAS and the tool boundary; stale claims (removed task, spec reset)
