## Claim

Attempt identity gates terminal writes: after a claim is requeued
(retry_count bump), the OLD attempt's completion is `Superseded` and cannot
regress the Running state; after the current attempt completes, any further
completion (old or current attempt) is `Superseded` and the terminal state is
preserved; a late completion after a run-level cancellation is `Superseded`
(the pause-as-cancel regression anchor, A-TSK-04-P1-01, keeps its durability
properties at the claim layer).

## Method

Standalone probe (`/tmp/qflt02-probe/src/bin/s2_old_attempt.rs`) driving the
real `TaskRuntimeStore`: (1) claim t1 -> attempt 1; (2) `requeue_claimed_task`
with a failure fingerprint -> `Applied`, task Pending with retry_count 1 and
claim cleared (no unclaimed window — requeue is the only Pending transition);
(3) re-claim -> attempt 2 (`retry_count+1`); (4) old attempt-1 completion ->
`Superseded`, task still Running with claim.attempt=2; (5) attempt-2
completion -> `Applied`, terminal Completed; (6) post-terminal writes with BOTH
attempts -> `Superseded`, status stays Completed; (7) variant: run cancelled
while t2 has a live claim, finalize writes Cancelled via `set_task_status`,
late completion with the live claim -> `Superseded`, task stays Cancelled.

Static side (fault propagation trace):
- Requeue path `store.rs:1066-1105` (Running + claim equality checked before
  the Pending transition), claim rebuild `attempt = retry_count+1`
  (`store.rs:1010-1013`), claim-guarded terminal writes
  `set_claimed_task_status` (`store.rs:1032-1062`), hard-terminal
  `Cancelled | Completed => false` in `can_transition_to`
  (`types.rs:521-523`).
