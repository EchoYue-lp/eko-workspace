## Claim

If the process dies between `request_pause` (run durably Paused, task still
Running with a live claim) and the executor's Paused-branch reset
(`executor.rs:551` sets Running->Pending only after the executor returns), the
stranded state must still be recoverable. Current code cannot recover it:
`recover_incomplete` only processes `Running` runs (`store.rs:1632`), so the
Paused run is skipped at boot; resume re-enters the framework executor which
classifies the Running task as in-flight and polls
`external_progress_poll_interval` forever (`runtime_executor.rs:276-285`);
`retry_blocked_task` rejects the state; `task_update` rejects Running tasks
(`revisioned.rs:525-541`); there is no `SetStatus` op
(`types.rs:1257-1272`). This is a distinct recovery hole from canonical
A-TSK-04-P1-02 (which boot recovery heals because the run is Running).

## Method

Standalone probe (`/tmp/qflt02-probe/src/bin/s9_pause_crash_strand.rs`)
driving the real store: claim t1, `request_pause`, drop the store (crash),
restart with a fresh store over the same root, `recover_incomplete()`, resume,
then attempt every in-process repair surface.

## Expected Result

The invariant demands that restart recovery (or resume) clears the strand.
Given the code under test, the strand is expected to persist and no surface to
repair it is expected to exist.
