## Claim

A process crash while a writer holds a fork worktree must not permanently
block the logical task: the stale `git worktree lock` must be repairable
in-process (or auto-detected against `is_run_active`), and leaked `eko-fork-*`
worktrees/branches must have a lifecycle sweep. Current code: `acquire_fork`
hard-errors on any locked existing worktree (`worktree.rs:381-391`); unlock
happens only in `finalize`/`preserve_error`/`cleanup_managed_worktree`; boot
recovery never touches git locks; cleanup covers only `eko-unattended-*`.

## Method

Standalone probe (`/tmp/qflt02-probe/src/bin/s7_worktree_lock.rs`) against a
real temp git repo (GPG signing disabled, same as the project's commit rule):
create fork worktree via the REAL `RunWorktree::create_fork` (locked),
simulate a crash (lock persists), retry `RunWorktree::acquire_fork` (twice),
manually `git worktree unlock`, re-acquire (reuse), dirty the worktree,
unlock+retain (finalize semantics), re-acquire (reuse across retries), list
`eko-fork-*` branches.

## Expected Result

Happy path (reuse, retention, manual unlock) works; the crash lock is expected
to block `acquire_fork` permanently with no in-process repair.

## Deviations

The framework-side finalize (which normally unlocks on graceful exits) is not
invoked — the probe mirrors finalize's unlock+retain semantics manually; the
crash path (lock persists) is exactly what finalize never runs on. Git lock
files persist across the probe process, matching real crash behavior.
