## Claim

Every EKO plugin/skill/hook discovery, activation, and reload path is
registered and reachable from a live product surface (or demonstrably dead),
and each mutation reaches the live agent's framework registrations.

## Method

the framework registration calls.

   :499-592), PluginRuntimeService (:279-281, new -> reload -> apply_candidate)

## Expected Result

All surfaces reach one shared `PluginRuntimeService`; each mutation is applied
to the live agent and unloads exactly the previous set; hooks reload through
one loader; hub commands reach the live registry.

## Result

- Exit code: not-applicable (static trace)
- Summary:
  - One `PluginRuntimeService` constructed at bootstrap and shared by GUI
    (AppState.plugin_runtime), TUI (TuiApp.plugin_runtime), and CLI
    (CommandContext.plugin_runtime); channels-only mode (main.rs:357-403
    without run_cli) has no plugin surface (no runtime passed to
    run_channels_mode) — informational.
  - `apply_candidate` (plugin_runtime.rs:551-802) runs under `state` Mutex;
    every mutation rebuilds a scanned candidate, validates enabled
    dependencies, prepares app components, validates Subagent collisions,
    prepares LSP, then swaps with rollback on any failure.
  - Plugin skills tagged `plugin:{id}` in BOTH registries (capabilities.rs:719-730);
    hooks under `HookSource::Plugin(id)` (plugin.rs:294, hooks.rs:610-645);
    MCP recorded in `components_by_plugin`; subagents registered with
    def+factory (plugin_components.rs:471-472). Unload keys symmetric
    (unload_agent_components plugin_runtime.rs:1157-1176).
  - Hook reload parity: CLI/TUI/GUI all call `HookConfigLoader`; watcher
    reloads hooks+webhooks only; plugin/skill-sourced hooks are never touched
    by `clear_user_hooks` (UserConfig slot only).
  - Skill hub surfaces reach the runtime only via `load_skills_from_dir`
    (CLI sync skills.rs:64, GUI enable/sync panels.rs:531/:566/:616, TUI
    :3352/:3385); no hub-to-runtime unload path exists (see P2-02).
  - Dead surfaces checked: `discover_config` plugin inventory (F-PLG-01-P2-01,
    zero frontend callers), REPL `/mcp connect/disconnect` (skills.rs:255-270,
    print-only — MCP surface, A-INT-01 scope, noted only).
- Log/artifact: none

## Deviations

- `switch_workspace` (state.rs:844-1032) and `exit_workspace` (state.rs:1053-1185)
  never call any plugin-runtime or hook-reload path — project-scope plugin
  components stay live across workspace boundaries (finding P1-01).
- `apply_candidate`'s swap base uses the boot-frozen `self.lsp.project_root`
  (plugin_runtime.rs:608) while candidate scans use the live `self.project_root()`
  (:986-991) — root-source divergence inside one transaction (evidence of
  P1-01).

## Conclusion

Supports: all plugin/hook surfaces reach one runtime owner and the live agent;
registration/unload keys are symmetric and reachable; hook reload is single-
authority; hub enablement reaches the runtime only additively (no unload path);
workspace switch does not touch the plugin runtime. These facts feed
A-PLG-01-P1-01, P2-01, P2-02, P3-01.
