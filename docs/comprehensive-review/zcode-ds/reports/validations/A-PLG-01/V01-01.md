## Claim

EKO-side discovery/activation/reload of plugins, skills, and hooks has exactly
one runtime authority per semantic; there is no parallel lifecycle, registry,
or dispatcher implemented in `echo-agent-cli` that duplicates a framework
primitive (framework lifecycle primitives vs EKO activation policy).

## Method

Repository-wide grep across both repositories for definition, registration,
and construction sites of every plugin/skill/hook lifecycle symbol.

```text
1. PluginRegistry::new / PluginRegistry::with_paths constructions (all repos)
2. scan_all / scan_scopes callers (framework authority vs EKO call sites)
3. PluginIntegrator::wire_all / wire_skills / wire_hooks / wire_mcp callers
4. unregister_skills_by_source / unregister_by_source callers
5. register_plugin_hooks / HookSource::Plugin / clear_user_hooks callers
6. SkillsHub (EKO) vs SkillRegistry (framework): construction + role
7. HookConfigLoader callers; run_lifecycle_hooks / fire_lifecycle_hook callers
8. HookEventDispatcher / HookBridge constructions (task-runtime queue)
9. set_loaded_skills / enable_skill / disable_skill callers (hub projection)
10. `.eko/plugins` vs `.echo-agent/plugins` path sites
```

## Expected Result

One framework plugin authority (`echo-core::plugin::PluginRegistry` +
`PluginLifecycleManager` + facade `PluginIntegrator`) with one EKO runtime
owner (`PluginRuntimeService`); one skill runtime authority (`SkillRegistry`)
with EKO `SkillsHub` as a marketplace index only; one user-hook loader
(`HookConfigLoader`) over the framework `HookRegistry`; the task hook queue
(`HookEventDispatcher`) as the only queued hook path.
