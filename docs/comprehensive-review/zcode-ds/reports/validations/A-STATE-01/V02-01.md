## Claim

Every conversation-persistence capability (save, load/restore, list, search,
delete, export) is reachable from live entry points: the framework saves the
transcript projection per turn when a store is injected, and Tauri/TUI/CLI
commands reach the same injected store through one shared instance.

## Expected Result

All capabilities live-reachable through the one store instance; the framework
per-turn save makes the record the single automatic writer; TUI/GUI/CLI
restore paths load the record back into the runtime context via
`restore_messages` + `load_messages`.

## Deviations

Store-instance roots differ across lifecycle: boot = `~/.eko/conversations/`
(infra.rs:1215 + framework `new()` appends `conversations`); workspace switch
= `{ws}/.eko/conversations/conversations/` (state.rs:905 passes the leaf dir);
workspace exit = `~/.eko/sessions/conversations/` (state.rs:1078 passes
`Persistence::base_dir()` = `~/.eko/sessions`). See V03-01 and findings
A-STATE-01-P1-01 / P2-01. TUI /delete-session omits the ToolExecutionRepository
cleanup that the GUI delete performs (finding A-STATE-01-P3-02).

## Conclusion

Supports: single store instance per process scope, all capabilities wired to
live commands, framework per-turn save reachable on every terminal path,
restore reachable on all three surfaces. Does not prove runtime behavior of the
documented flows (Q-E2E-01 scenarios); store-root consistency is assessed in
V03-01.
