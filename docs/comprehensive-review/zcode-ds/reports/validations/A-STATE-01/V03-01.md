## Claim

Conversation persistence invariants hold at the EKO boundary: (a) one
canonical store root per scope and one identity per conversation across store
switches; (b) corrupt files surface errors and are never overwritten by EKO;
(c) message/tool/thinking round-trip is lossless on the EKO adapter path;
(d) deletion cascades to dependent artifacts on every surface; (e) concurrent
writes cannot lose or duplicate data.

## Method

Static inspection of construction sites, delete paths, merge logic, and
concurrency boundaries; framework facts cross-checked against F-MEM-01
(which reviewed `FileConversationStore` robustness: corrupt errors, atomic
writes, path-safe ids, in-process Mutex serialization).

## Expected Result

Per invariant: (a) store root identical between boot and workspace-exit, and
consistent with the record layout every reader uses; (b) `FileConversationStore`
surfaces corrupt JSON as errors and EKO handles them without data loss;
(c) project/restore round-trips roles, tool calls/results, multimodal parts and
reasoning on the EKO path; (d) deleting a conversation removes its JSON record
plus tool-output, user-input, upload, and tool-execution artifacts on every
surface; (e) no read-modify-write window loses an accepted save, and message
ids stay unique.

## Result

- Exit code: 0 (all greps; no dynamic run in this validation)
- Summary:
  - (a) **Violated.** Three store roots: boot `FileConversationStore::new(user_data_dir())`
    -> `~/.eko/conversations/` (infra.rs:1215-1227, desktop.rs:174-177);
    workspace switch passes `WorkspaceLayout::conversations(root)` =
    `{ws}/.eko/conversations` as the *base* (state.rs:905-907) -> files at
    `{ws}/.eko/conversations/conversations/` (framework appends
    `conversations`, file_conversation.rs:70-75) — one level deeper than the
    migration target `{ws}/.eko/conversations/<id>.json`
    (migration.rs:157-189) and than the canonical layout; workspace exit
    passes `Persistence::base_dir()` = `~/.eko/sessions` (state.rs:1078-1083,
    persistence.rs:204) -> `~/.eko/sessions/conversations/` — different from
    boot root. Same conversation_id therefore lives in different stores
    depending on when it was written; the active conversation keeps its id
    across a switch, so one id can exist in two stores with split transcripts.
  - (b) Framework corrupt-record behavior is explicit error, tested
    (`corrupt_record_surfaces_as_error_not_empty`); EKO surfaces propagate
    errors (CLI bails, TUI system message, GUI `IpcError`). No EKO path
    overwrites a corrupt record; the framework atomic_write protocol
    (uuid tmp + fsync + rename + parent sync) is intact.
  - (c) Framework round-trip is lossless for system/user/assistant/tool,
    tool_calls, tool results (id+name+text), multimodal `Parts`, and
    `reasoning_content` (project_message/restore_message,
    echo-state/src/memory/conversation.rs:35-191; test
    `round_trip_messages_via_project_and_restore`). EKO adapter
    (conversations.rs `project_saved_messages` + `pack_ui_projection` +
    `merge_projection_json`) merges UI metadata (message_id, display_content,
    thinking_segments, execution_steps, execution_rounds, attachments) into
    the canonical projection without overwriting framework keys; three unit
    tests cover alignment (V04-05). One divergence: TUI `/fork` persists the
    *unfiltered* runtime context (`agent.get_messages()` at events.rs:4888
    returns the full context, react/mod.rs:1260-1263) while the per-turn save
    filters system/internal messages (snapshot.rs:65-71) — forked records can
    contain system/internal prompts (finding A-STATE-01-P3-03).
  - (d) GUI delete_conversation removes: store record, tool-execution
    repository entry (conversations.rs:600-607, disk-backed
    tool_execution.rs), tool-output scope and user-input scope
    (conversations.rs:609-637). TUI /delete-session removes: store record,
    tool-output scope, user-input scope (events.rs:3069-3095) — **omits** the
    tool-execution repository cleanup (finding A-STATE-01-P3-02). Neither
    surface cleans the uploads directory (`~/.eko/uploads/` /
    `{ws}/.eko/uploads/`; A-INP-01-P3-01). Delete of a conversation whose id
    exists in another store scope (see (a)) removes only the file in the
    current store.
  - (e) In-process: `FileConversationStore` serializes each trait call with a
    Mutex, and `save_messages` is a single lock-scoped read-modify-write
    (file_conversation.rs:350-376) — atomic per call. The GUI
    `save_conversation`/`update_conversation` sequences
    (get_messages -> merge -> save_messages, conversations.rs:433-444,
    566-579) span multiple lock acquisitions, so a concurrent framework
    per-turn save can interleave; the merge design (tail UI messages beyond
    the canonical transcript are dropped until the framework saves the next
    turn) bounds the practical loss to UI metadata until the next turn.
    Cross-process: GUI and CLI are separate processes writing the same
    `~/.eko/conversations/` with no file locking; each keeps its own
    `_meta.json` counter (read_meta at open, persist_meta on mutation), so
    concurrent GUI+CLI use can assign duplicate message ids and last-writer
    wins on whole records (finding A-STATE-01-P2-02). The framework documents
    the SQLite backend for multi-process use (file_conversation.rs:43-45),
    which EKO cannot use (AGENTS.md).

## Deviations

See findings: A-STATE-01-P1-01 (exit-workspace store root), A-STATE-01-P2-01
(workspace-switch nested root + migration mismatch), A-STATE-01-P2-02

A-STATE-01-P3-02 (TUI delete misses tool-execution cleanup),
A-STATE-01-P3-03 (fork persists unfiltered transcript).

## Conclusion

Supports: robust corrupt-file behavior and atomic single-call writes
(framework, confirmed by tests), lossless framework round-trip with a
merge-tested EKO adapter, deletion cascade present on GUI and mostly on TUI.
Does not support: store-root stability across workspace enter/exit, cross-process
write safety, or TUI-side cascade completeness — those invariants are violated
and registered as findings. No dynamic runs; concurrency claims are static
proofs (Q-E2E-01 / Q-FLT scenarios should add GUI+CLI concurrent chat).
