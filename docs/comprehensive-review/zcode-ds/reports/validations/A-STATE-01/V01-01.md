## Claim

File-backed conversation persistence has exactly one authoritative storage
implementation (the framework `FileConversationStore`), EKO holds no second
conversation/session store and no SQLite dependency, and there is exactly one
on-disk record format shared by all readers and writers.

## Method

Repository-wide grep (both repos, excluding `target/` and `node_modules/`) for
definitions and production call sites of: `ConversationStore`,
`FileConversationStore`, `SqliteConversationStore`, `save_messages`,
`get_messages`, `list_conversations`, `delete_conversation`, `project_message`,
`restore_message`, `restore_messages`, `ensure_conversation`,
`search_conversations`, `SessionSearchEngine`, `index_session`,
`reindex_all`, `remove_session`, `SavedMessage`, `SavedSession`,
`AttachmentsPayload`, `conversations`, and the string `sqlite`/`Sqlite`.

```text
cd echo-agent-cli && grep -rn --include="*.rs" "FileConversationStore|ConversationStore" . | grep -v target
cd echo-agent-cli && grep -rn --include="*.rs" "sqlite|Sqlite" . | grep -v target
cd echo-agent && grep -rn --include="*.rs" "ConversationStore|save_messages|project_message" src echo-core/src echo-state/src echo-orchestration/src | grep -v target
cd echo-agent-cli && cargo tree --workspace --locked | grep -i "sqlite|rusqlite"
```

## Expected Result

One trait + one file implementation in the framework (`echo_core::memory`,
`echo_state::memory`); EKO consumes the trait only; zero SQLite references in
`echo-agent-cli` production code and dependency tree; one JSON record shape
(`{conversation, messages}` per `<base>/conversations/<safe_id>.json` plus
`_meta.json`) that every reader (store, reindex, migration) parses identically.
