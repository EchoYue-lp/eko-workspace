## Claim

The cron crate's `upcoming()` iterator returns only instants strictly after the
reference time, making the `SchedulerRunner` tick predicate
`next >= window_start && next <= now` unsatisfiable (echo-orchestration
`src/scheduler/runner.rs:82`).

## Method

Temporary cargo project `/tmp/croncheck` (outside both repositories; no repo
files modified):

```text
/tmp/croncheck/Cargo.toml: cron = "=0.12.1", chrono = "0.4"
/tmp/croncheck/src/main.rs: parse "0 */1 * * * *" (the exact 5-field padding
  CronTask::next_run uses: format!("0 {} *", expr)); now = Utc::now();
  next = schedule.upcoming(Utc).next().unwrap();
  print next > now; print in-window (next >= now-30s && next <= now);
  also print the second occurrence.
cd /tmp/croncheck && cargo run --offline
```

## Expected Result

`next > now` is true and `in_window` is false for a per-minute schedule sampled
mid-minute — proving the tick predicate can never hold.

## Conclusion

Empirically confirms the static analysis: `next_run()` always returns a
strictly future instant, so `tick()` can never fire any task. Supports
F-OPS-01-P1-01. The check is limited to cron 0.12.1 (the locked version); it
does not test the rest of the scheduler.
