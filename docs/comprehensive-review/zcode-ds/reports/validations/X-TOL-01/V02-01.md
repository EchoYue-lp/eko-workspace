## Claim

The framework error taxonomy (`ToolFailureCategory`, 7 values) is preserved
identically through the EKO error normalization and the frontend/TUI
rendering, so a consumer at any layer can recover the same classification and
terminal reason for a failed tool invocation.

## Expected Result

- A failed invocation that produced a `ToolError` shows the same 7-way
  category and recovery action in the EKO manifest, the GUI expanded detail,
  and the TUI metadata label.
- Kill paths that cannot produce a `ToolError` at the framework level are
  either distinguishable (timeout vs cancelled vs partial side effect) or
  explicitly documented as collapsed at every layer.

## Result

- Exit code: not-applicable (static trace)
- Duration: not-applicable
- Summary:
  - Normal path: the full 7-way taxonomy survives to every layer. The EKO
    manifest stores the framework `ToolFailure` unchanged
    (tool_execution.rs:84,341); the Tauri surface serializes it unchanged;
    the GUI renders `category · recovery`; the TUI renders
    `failure_category`/`recovery_action` strings derived from the same
    struct. TS `ToolFailureCategory` enumerates exactly the 7 snake_case
    values (types/api.ts:55-62). No renaming, no loss.
  - Partial side effect: `partial_file_failure` (files/files.rs:93-110)
    produces `PartialSideEffect` + `Possible` + idempotency_key +
    postcondition; this flows through the same chain; GUI shows
    "partial_side_effect · verify_then_retry".
  - Kill path (finding X-TOL-01-P2-01): when the framework abandons in-flight
    tools without emitting `ToolError` (batch timeout per
    phases/tools.rs:284-300, batch cancel per :295-300, subagent TimedOut,
    turn-end cleanup), EKO calls `cancel()` which has no failure parameter
    and can only set `ToolExecutionStatus::Cancelled`. The terminal reason is
    therefore always "cancelled" at the summary level with `failure: None`
    at the detail level — a timeout, a partial side effect, and a user cancel
    are indistinguishable, and no postcondition/idempotency metadata exists.
    Anchors: tool_execution.rs:360-392 (cancel signature), chat.rs:1106-1110,
    1325-1328, 1365-1368 (all kill paths route to cancel_active_tools).
    Framework side of the same gap is canonically F-RCT-04-P1-02 / P2-02.
  - Boot recovery additionally converts any Running execution to Cancelled
    without a failure record (tool_execution.rs:527-545) — same collapse.

## Deviations

- `AgentEvent::Error` (which carries no `ToolFailure`; produced by the
  envelope adapter from raw stream errors, echo-core/src/agent/event_envelope.rs:136-139)
  is the only signal of a batch timeout at the EKO boundary; the sink treats
  it identically to `Cancelled` (chat.rs:1325-1328).
- TUI collapses `ToolError` and `ToolComplete` both into its local
  `AgentEvent::ToolResult`/`ToolComplete` with the failure carried along
  (events.rs:2107-2132); no additional loss.

## Conclusion

This execution supports: the error taxonomy is preserved 1:1 across all four
layers on every path that carries a `ToolError`/`ToolResult.failure`; on the
kill paths (timeout/cancel/partial side effect caused by batch or subagent
abandonment) the taxonomy collapses to a bare 4-way "cancelled" status at the
EKO boundary with no failure metadata — finding X-TOL-01-P2-01. It does not
prove runtime behavior of a live timeout (no dynamic run executed; framework
side is canonically F-RCT-04-P1-02).
