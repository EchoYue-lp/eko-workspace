## Claim

`ChannelManager` start/stop, channel `start`/`stop`, and `SessionHandler`
session management terminate cleanly: after `stop()` no channel-owned task
keeps running or spinning, and sessions are bounded.

## Method

Static trace of `manager.rs` (full), `session.rs` (full), `qq/channel.rs`
(full), `feishu/channel.rs` (full), `feishu/long_poll.rs` (full), and the
EKO channel mode (`echo-agent-cli/src/cli/modes.rs:110-255`).

## Expected Result

`stop()` aborts all spawned tasks and closes channels; dropped
`ChannelManager` stops channels; session entries are reclaimed on timeout.

## Result

- QQ `start` spawns a detached send task whose JoinHandle is discarded
  (`let _send_task = tokio::spawn(...)`, qq/channel.rs:108) and a gateway
  reconnect loop stored in `gateway_handle`. `stop()` (qq/channel.rs:198-208)
  aborts only the gateway handle and drops `send_tx`. The send task is
  `loop { if let Some(msg) = send_rx.recv().await { ... } }` — when the
  last sender drops (wrapper dropped with the aborted gateway task),
  `recv()` returns `None` immediately and the loop **busy-spins forever**
  on one CPU core until process exit. Finding F-INT-02-P1-02.
- Feishu `start` uses `while let Some(msg) = send_rx.recv().await`
  (feishu/channel.rs:218) — after `stop()` drops the wrapper's sender, the
  loop exits cleanly. The long-poll `WsClient::run` reconnect loop
  (long_poll.rs:134-192) exits on task abort. Feishu teardown is clean.
- `ChannelManager::drop` (manager.rs:131-141) only logs "consider calling
  stop_all()"; doc at manager.rs:14-15 claims "Auto-stop all channels on
  Drop" — mismatch. Dropping the manager leaves QQ/Feishu reconnect loops
  running detached. Finding F-INT-02-P2-05.
- `SessionHandler`: sessions keyed `(channel_id, sender_id)`; timeout
  (session.rs:319-332) **replaces** `guard.handler` with a fresh factory
  instance but keeps the DashMap entry; entries are removed only on
  command reset (:298-312). Distinct senders accumulate entries (each
  holding an Agent) for the process lifetime — no eviction, no TTL sweep.
  Finding F-INT-02-P2-04. EKO's per-sender pool (`modes.rs`) duplicates
  this bookkeeping but is not the leak source.
- EKO channel mode stops all channels on SIGINT/SIGTERM
  (modes.rs:244-247) — for EKO the QQ spin ends with process exit.

## Deviations

QQ send-task spin after stop (P1-02); manager Drop does not stop channels
(P2-05); session entries never evicted (P2-04).

## Conclusion

Supports: Feishu teardown and gateway reconnect loops are well-formed;
EKO's stop path is invoked. Fails: QQ teardown (permanent CPU spin in
long-running consumers), manager Drop contract, and session eviction.
