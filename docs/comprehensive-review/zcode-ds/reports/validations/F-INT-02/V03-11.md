## Claim

A2A client operations complete or fail in bounded time (timeouts), and
`tasks/cancel` actually cancels the remote execution.

## Method

Static trace of `src/a2a/client.rs` (all five HTTP methods, SSE stream),
`src/a2a/server.rs` cancel paths, and `reqwest` client construction.

## Expected Result

`Client::new()` without `.timeout()` — expected: default reqwest behavior
(no overall timeout); cancel token wired into the agent run.

## Result

- `A2AClient::new()` (client.rs:25) builds `reqwest::Client::new()` with
  no connect/read/overall timeout. `discover` (client.rs:49-84),
  `send_task_with_session` (:108-157), `get_task` (:298-331),
  `cancel_task` (:334-367) all await `.send()` unboundedly; a
  dead-but-alive remote (e.g., SYN-accepted but never responding) blocks
  the caller until OS-level TCP timeouts (potentially minutes), with no
  recovery knob. Finding F-INT-02-P2-07.
- The streaming method (:205-295) reads the response body chunk by chunk
  with no idle timeout — a server that stops sending leaves the stream
  open forever (caller can drop the stream, but there is no protocol-level
  bound or heartbeat).
- Server-side cancel for `tasks/send` is cosmetic (execution continues,
  terminal state regresses) — F-INT-02-P1-03; the client-side
  `cancel_task` therefore cannot deliver a real cancel to a running sync
  task either.
- No retry logic in the client — each call is single-shot; the caller is
  responsible for retries.

## Deviations

None beyond the findings.

## Conclusion

Supports: none of retry/cancel is bounded — client hangs unboundedly on
unresponsive remotes, and server cancel does not stop execution.
