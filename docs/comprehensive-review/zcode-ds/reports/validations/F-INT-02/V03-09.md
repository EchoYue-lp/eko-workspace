## Claim

The A2A task lifecycle (`submitted → working → [input-required] →
completed/failed`, any non-terminal → canceled, terminal states final) is
enforced by the server, and in-memory task/cancel-token records are
eventually reclaimed.

## Method

Static trace of `src/a2a/server.rs` (full: `handle_task_send`,
`handle_request_stream`, `handle_task_cancel`, `update_task_state`,
`cleanup_completed_tasks`), `src/a2a/serve.rs`, and `grep` for
`cleanup_completed_tasks` callers.

## Expected Result

Transitions validated (terminal → anything rejected); cancel stops
execution; terminal state never regresses; task registry bounded.

## Result

- `update_task_state` (server.rs:588-602) rejects illegal transitions
  with a warn — the state machine is enforced for the streaming path.
- `handle_task_cancel` (server.rs:527-584) rejects cancel of terminal
  tasks (ERROR_CODE_TERMINAL_STATE) and marks the task Canceled.
- **Cancel does not stop execution for `tasks/send`**: the stored
  `CancellationToken` (server.rs:404-408) is never consulted by
  `handle_task_send`; `agent.execute(&input_text)` (server.rs:414) runs to
  completion, then the `completed_task` record overwrites the Canceled
  status (:439-442). A client polling `tasks/get` observes
  Canceled → Completed — a terminal-state regression, violating the A2A
  state machine. The framework offers `execute_stream_with_cancel`
  (echo-core/src/agent/mod.rs:560-568) but the server does not use it.
  Finding F-INT-02-P1-03.
- Streaming cancel (server.rs:225-235): between events the stream checks
  `is_cancelled` and emits a final Canceled event; the underlying
  `execute_stream` future is dropped when the stream ends, aborting the
  run — cancel works with up to one-event latency. On client disconnect
  the stream is dropped; the task record stays `Working`/`Submitted`
  forever.
- **Task registry unbounded**: `cleanup_completed_tasks`
  (server.rs:605-625) has zero production callers (V02-03); `serve_inner`
  runs no periodic cleanup. Every task and cancel-token entry persists for
  the server's lifetime. Finding F-INT-02-P2-09.
- `handle_request_stream` (server.rs:166-183) inserts a fresh
  `Submitted` record and overwrites any existing task with the same id —
  re-subscribe clobbers history (finding F-INT-02-P3-05).

## Deviations

See findings P1-03 (cancel/terminal regression), P2-09 (registry leak),
P3-05 (id overwrite).

## Conclusion

Supports: transition validation exists on the streaming path. Fails:
cancel semantics for sync tasks, terminal-state finality, and registry
reclamation.
