## Claim

External LSP wire names (`textDocument/didOpen`, `Content-Length`, LSP
method strings) appear only at the minimal wire boundary
(`echo-integration/src/lsp`), while internal APIs use framework naming;
no legacy `worker` terminology exists in the LSP stack.

## Method

1. `grep -rni "worker"` over `echo-core/src/lsp`, `echo-integration/src/lsp`,
   `echo-agent/src/tools/lsp.rs` — no hits.
2. Inspect wire-name locations: `client.rs` (method strings
   `"initialize"`, `"textDocument/definition"`, `"textDocument/didOpen"`,
   `"textDocument/publishDiagnostics"`), `jsonrpc.rs` (`Content-Length`
   framing, `JsonRpcRequest/Notification/Response`).
3. Check EKO consumption (`echo-agent-cli` plugin_runtime/runtime) for
   protocol leakage.

## Expected Result

Wire names confined to the JSON-RPC/framing boundary; internal API typed
with framework concepts; no worker naming.

## Result

- Wire names are confined to `echo-integration/src/lsp/client.rs` and
  `jsonrpc.rs`; the `LspClient` trait (`echo-core/src/lsp/client.rs:54-128`)
  is fully internal/typed (Position/Range/Diagnostic/etc. from
  `echo-core/src/lsp/types.rs`).
- Simplification is intentional and documented (`echo-core/src/lsp/types.rs:3-5`:
  "We define our own simplified versions rather than depending on the full
  `lsp-types` crate").
- EKO consumes only `LspConfig/LspManager/StdioLspClient` and the core
  types — no wire strings leak into the application.
- No `worker`/legacy naming; `subagent` terminology untouched by this
  stack.
- Doc drift: `echo-core/src/lsp/mod.rs:11-12` names `echo-tools/src/lsp/`
  as the tool module, which does not exist (tools are
  `echo-agent/src/tools/lsp.rs`) — a stale path, not a naming violation
  (finding F-INT-02-P3-03).
