## Claim

The framework detects corrupt/incomplete/version-mismatched checkpoints
and surfaces them as errors at the store layer
(`FileRuntimeStateStore::get_checkpoint` → `Err`) and at the validator
layer (`AgentCheckpoint::restore_messages` →
`RuntimeStateError::SerializationError`). However, the resume entry
point (`restore_thread_context`) catches ALL such errors and silently
falls back to `reset_messages` (empty context + system prompt) with
only a `warn!` log — the user is not alerted and the conversation
trajectory is lost. Additionally, `AgentCheckpoint` has no schema
version field, so a forward-incompatible checkpoint (older binary
reading a newer-shaped checkpoint, or a struct field promoted from
optional to required) fails opaquely inside serde with no actionable
diagnostic. This is the basis for F-RCT-05-P2-02.

## Method

Read-only static trace of the corrupt-checkpoint detection chain and
the resume fallback, plus a grep for any version/migration field,
anchored at:

```text
echo-agent/src/state/file.rs:151-168                (get_checkpoint: corrupt → Err, missing → None)
echo-agent/src/state/file.rs:66-74, 334-352         (read_nodes_file corrupt handling + test)
echo-agent/src/state/mod.rs:116-135                 (AgentCheckpoint struct — no version field)
echo-agent/src/state/mod.rs:157-237                 (restore_messages + validate_tool_message_pairing)
echo-agent/src/agent/react/run/context.rs:230-261   (restore_thread_context: Err → reset_messages)
echo-agent/src/agent/react/mod.rs:1680-1755         (resume_from_state_store error propagation)
```

## Expected Result

1. `FileRuntimeStateStore::get_checkpoint` returns `Err` for a corrupt
   `checkpoint.json` (not `None`), so the caller can distinguish
   "no checkpoint" from "unreadable checkpoint".
2. `AgentCheckpoint::restore_messages` returns
   `RuntimeStateError::SerializationError` for (a) malformed
   `messages_json`, (b) unpaired tool calls, (c) duplicate tool_call
   ids, (d) missing tool_call_id, (e) tool name mismatch.
3. `restore_thread_context` propagates the error to the caller OR
   alerts the user that resume failed and the context was reset.
4. `AgentCheckpoint` carries a schema version to enable migration.

## Result

- Exit code: not-applicable (static inspection) + cargo confirmation.
- Summary: claims 1 and 2 **pass**; claims 3 and 4 **fail**.

**(1) Corrupt-checkpoint detection at the store layer — PASS.**
`file.rs:158-167`:
```rust
match std::fs::read_to_string(&path) {
    Ok(s) => {
        let cp: AgentCheckpoint = serde_json::from_str(&s)
            .map_err(|e| ReactError::Other(format!("parse {}: {e}", path.display())))?;
        Ok(Some(cp))
    }
    Err(e) if e.kind() == std::io::ErrorKind::NotFound => Ok(None),
    Err(e) => Err(Self::to_react_err(e)),
}
```
Corrupt JSON → `Err(ReactError::Other("parse ..."))`. Missing file →
`Ok(None)`. The `corrupt_nodes_file_surfaces_as_error` test
(`file.rs:334-352`) proves the nodes-file analogue. So detection is
correct and distinguishes absent-vs-corrupt — better than the
`FileStore` silent-swallow pattern flagged in F-MEM-01-P1-01.

**(2) Validator-layer detection — PASS.**
`state/mod.rs:157-168`: `serde_json::from_str(&self.messages_json)`
failure → `SerializationError("Failed to deserialize checkpoint
messages: {error}")`. Then `validate_tool_message_pairing` (`:186-231`)
adds the four structural rejections (orphan, duplicate, missing id,
name mismatch) plus the end-of-walk "tool calls without results"
check. The `checkpoint_rejects_unpaired_or_duplicate_tool_results`
test (`state/mod.rs:336-359`) covers orphan and duplicate cases.

**(3) Resume fallback is silent — FAIL.**
`context.rs:230-261`:
```rust
if self.memory.state_store.is_some() {
    match self.resume_from_state_store().await {
        Ok(Some(_cp)) => { /* restored */ session_matcher = "resume"; }
        Ok(None) => { /* new session */ self.reset_messages().await; }
        Err(e) => {
            warn!(agent = %agent, error = %e, "⚠️ Failed to load RuntimeStateStore checkpoint, starting from empty context");
            self.reset_messages().await;
        }
    }
}
```
The `Err` arm logs `warn!` and calls `reset_messages` — which
(`context.rs:216-220`) clears the context and pushes only the system
prompt. There is:
- No `Err` propagated to the caller of `run_direct`/`run_chat_direct`.
- No user-visible signal (no event, no flagged turn, no UI state).
- No distinction between "checkpoint corrupt" and "no checkpoint" at
  the user layer — both produce an empty context, but the former is
  silent data loss while the latter is normal first-run behavior.
- No retention of the corrupt checkpoint for manual recovery. The next
  successful turn will `save_runtime_checkpoint` an empty-context
  checkpoint, **overwriting** the corrupt file (because
  `save_checkpoint` is an upsert/replace at `file.rs:170-187`). So the
  corruption is not just hidden — it is destroyed after the next turn.

This compounds F-MEM-01-P1-01's theme: the store layer correctly
surfaces corruption, but the resume consumer suppresses it. The
net user-visible behavior is identical to the `FileStore` silent
swallow that F-MEM-01 flagged as P1 — except here the overwrite makes
it unrecoverable.

**(4) No schema version — FAIL.**
`state/mod.rs:116-135` (`AgentCheckpoint` struct): fields are
`conversation_id, messages_json, current_plan, active_skills,
blocked_reason, working_dir, timestamp`. No `version`, no
`schema_version`, no `checkpoint_version`. `grep -rn "version\|schema"
echo-agent/src/state/mod.rs echo-agent/src/state/file.rs` returns no
version field.

Consequences:
- An older binary reading a newer checkpoint whose struct added a
  serde-required field fails inside `serde_json::from_str` with a
  generic "missing field" error → routed to the silent-fallback arm
  (claim 3). No "incompatible version" diagnostic.
- A newer binary reading an older checkpoint missing a field that was
  later promoted to required fails the same way. Only `working_dir`
  has `#[serde(default)]` (`:130`), so it is the single field that
  tolerates absence.
- Extra unknown fields are silently ignored (serde default), so a
  newer-written checkpoint read by an older binary loses the new
  fields without error — but the older binary's `restore_messages`
  will still validate the trajectory, so this direction is safer.
- There is no migration path: no `fn migrate(from_version)`, no
  version-gated deserializer. Under AGENTS.md's "no backward
  compatibility burden" rule for this project, the absence of
  migration is acceptable, but the absence of a version TAG means a
  future maintainer cannot tell which shape a given checkpoint has
  without inspecting the fields heuristically.

## Deviations

1. The destructive-overwrite claim (next successful turn replaces the
   corrupt checkpoint) is inferred from `save_checkpoint`'s
   unconditional `atomic_write` (`file.rs:181-184`). No executable test
   proves the sequence corrupt-load → empty-reset → next-turn-save →
   original-corruption-gone. The inference is strong (the code path is
   direct) but a regression test should accompany the fix.
2. Whether the application layer (echo-agent-cli) wraps
   `restore_thread_context` with any additional error handling or
   user alerting was not exhaustively audited — the framework
   `restore_thread_context` itself swallows the error, so any
   application-layer alert would have to be added downstream of a
   signal the framework does not currently emit. The grep for
   `restore_thread_context` callers
   (`direct.rs:11`, `context.rs:502,571`) shows only internal framework
   call sites; the application invokes `run_direct`/`run_chat_direct`
   which do not surface the resume result separately.

## Conclusion

The claim is **supported for claims 1-2 (detection works) and
contradicted for claims 3-4 (resume silently swallows the error; no
version field)**. This is the basis for F-RCT-05-P2-02: the store and
validator layers correctly surface corruption, but the resume consumer
suppresses it and the next turn destroys the corrupt file. The defect
is the silent, destructive fallback, not the detection. Severity is
amplified by the absence of a version tag, which makes the failure
mode opaque to users and maintainers.

## Follow-Up

The fix for F-RCT-05-P2-02 should: (a) propagate the resume error (or
emit a `ResumeFailed` event) so the application can alert the user;
(b) preserve the corrupt checkpoint under a `.corrupt` suffix before
overwriting; (c) add a `version: u32` field to `AgentCheckpoint` with
`#[serde(default)]` for forward-read compatibility. A new executable
test should assert the corrupt-load → preserve → alert sequence.
