## Claim

The repository has two distinct snapshot types. The in-memory
`StateSnapshot` (`echo-state`) captures only message history for
in-run rollback; the persisted `AgentCheckpoint` (`echo-agent::state`)
captures messages + plan + active skills + blocked reason + working dir
for cross-process resume. Neither fully reconstructs every agent
runtime field — resume is intentionally "trajectory + new turn"
(consistent with B-REF-01), not a byte-for-byte state restore. Budget
counters, iteration number, trace/run/turn IDs, TaskNode DAG, and
recently-read-files are deliberately NOT persisted.

## Method

Read-only static inspection of both snapshot structs and the resume
constructor, anchored at:

```text
echo-agent/echo-state/src/memory/snapshot.rs:20-35      (StateSnapshot struct)
echo-agent/echo-state/src/memory/snapshot.rs:56-166     (SnapshotManager — in-memory ring buffer)
echo-agent/src/state/mod.rs:116-184                     (AgentCheckpoint struct + restore_messages)
echo-agent/src/agent/snapshot.rs:329-406                (AgentRunSnapshot — live runtime holder)
echo-agent/src/agent/snapshot.rs:570-631                (save_runtime_checkpoint → AgentCheckpoint)
echo-agent/src/agent/snapshot.rs:1116-1141              (auto_snapshot → SnapshotManager)
echo-agent/src/agent/react/mod.rs:1680-1744             (resume_from_state_store)
echo-agent/src/agent/react/builder.rs:87-88,167-168,1006 (snapshot_policy default None)
```

Then diffed the persisted-fields set against the live
`AgentRunSnapshot` field set to enumerate what resume does and does not
restore.

## Expected Result

1. `StateSnapshot` (in-memory) carries only `id`, `iteration`,
   `messages`, `metadata`, `created_at` — it is a message-history
   rewind, not a full-state snapshot.
2. `AgentCheckpoint` (persisted) carries `conversation_id`,
   `messages_json`, `current_plan`, `active_skills`, `blocked_reason`,
   `working_dir`, `timestamp` — no schema version.
3. `resume_from_state_store` restores messages + plan + skills +
   working_dir + hydrates Running TaskNodes; it does NOT restore
   budget counters, iteration number, trace IDs, or recently-read-files.
4. The in-memory `SnapshotManager` is opt-in (builder default
   `snapshot_policy = None`), so `auto_snapshot` is a no-op for
   consumers that never set a policy.

## Result

- Exit code: not-applicable (static inspection) + cargo confirmation.
- Summary: the claim is **supported**, with the field-coverage matrix
  below.

**(1) In-memory `StateSnapshot` field set.**
`echo-state/src/memory/snapshot.rs:23-35`:
```rust
pub struct StateSnapshot {
    pub id: String,
    pub iteration: usize,
    pub messages: Vec<Message>,
    pub metadata: HashMap<String, String>,
    pub created_at: u64,
}
```
Five fields. No plan, no skills, no budget, no working_dir. The module
doc (`:1-13`) describes it as "对话历史快照" (conversation-history
snapshot) for "回滚到上一个 known-good 状态" (rollback to last
known-good). `SnapshotManager` (`:56-166`) is a pure in-memory
`Vec<StateSnapshot>` ring buffer with `capture`/`rollback`/`rollback_to`.
It is never serialized to disk; the module doc at
`echo-state/src/memory/mod.rs:11-13` (cited by F-MEM-01) explicitly
defers cross-restart recovery to `RuntimeStateStore`. So the in-memory
snapshot cannot survive a process restart by design.

**(2) Persisted `AgentCheckpoint` field set.**
`echo-agent/src/state/mod.rs:116-135`:
```rust
pub struct AgentCheckpoint {
    pub conversation_id: String,
    pub messages_json: String,
    pub current_plan: Option<String>,
    pub active_skills: Vec<String>,
    pub blocked_reason: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub working_dir: Option<std::path::PathBuf>,
    #[serde(with = "crate::utils::time::local_rfc3339")]
    pub timestamp: DateTime<Utc>,
}
```
Seven fields. No version field (relevant for V04). `working_dir` is the
only field with `#[serde(default)]`, so it tolerates older checkpoints
that predate it; all other fields are required by serde.

**(3) Resume restoration scope.**
`resume_from_state_store` (`react/mod.rs:1690-1744`) restores exactly:
- `messages` → `set_messages` (`:1694`) — full trajectory incl. tool
  hand-offs and internal projection messages.
- `current_plan` → `plan_state.write()` (`:1697-1700`).
- `active_skills` → `skill_registry.mark_activated` per name
  (`:1703-1705`).
- TaskNodes in `Running` → `Hydrated` via `hydrate_running_nodes`
  (`:1714-1715`, `snapshot.rs:763-796`).
- `working_dir` → `set_working_dir` (`:1718-1720`).
- `completed_tool_call_ids` → emitted as `CheckpointResumed` trace
  event (`:1731-1737`) — **informational only, not a gate** (see V02).

The following `AgentRunSnapshot` fields are NOT restored (verified by
diffing `snapshot.rs:329-406` against the resume body):

| Not-restored field | Source | Resume behavior |
|---|---|---|
| `config.run_budget` counters (reported_model_tokens, usage_complete, wind_down_emitted, final_only) | `phases/mod.rs` LoopState | Reset to defaults — resume starts a fresh budget envelope. Correct: resume = new turn. |
| iteration counter | `stream_channel.rs:528` for-loop | Restarts at 0 — the new turn gets a full `max_iterations` allowance. |
| `trace_run_id`, `current_run_id`, `current_turn_id`, `current_message_id`, `current_execution_id` | `snapshot.rs:362-371` | Regenerated by `prepare_turn` for the new turn. The old trace run stays in whatever status it was left in (F-RCT-02-P2-03 caveat). |
| `recently_read_files` | `snapshot.rs:357-358` | Reset (cleared at `prepare_stream_context` via `clear_read_files`, `context.rs:499`). A read-before-edit gate that fired pre-crash does not carry forward. |
| `cancel_token` | `snapshot.rs:353` | Fresh token per turn (`prepare_turn`). |
| `turn_steer_mailbox` pending | `steer.rs:40` | The mailbox is per-turn (`ActiveTurnLease` scoped); a steer enqueued pre-crash is lost. By design (steer is same-turn, not cross-turn). |

This is the "trajectory + new turn" model: the conversation history is
the authoritative context; everything else is recomputed for the new
turn. It matches B-REF-01's convergence finding (Claude Code:
checkpoint + rewind into a new turn, not event replay).

**(4) SnapshotManager is opt-in.**
`builder.rs:87-88, 167-168`: `snapshot_policy: Option<SnapshotPolicy>`
defaults to `None`; `max_snapshots` defaults to 10. The build path
(`builder.rs:1006-1008`) only calls `set_snapshot_manager` when
`snapshot_policy.is_some()`. So by default `snapshot_manager` is
`None` inside `AgentRunSnapshot` (`snapshot.rs:337`), and
`auto_snapshot` (`:1121-1126`) short-circuits on
`mgr.as_ref().is_some_and(...) == false`. The framework still
checkpoints to `RuntimeStateStore` regardless (that path does not
consult `snapshot_manager`), so cross-process resume works without the
in-memory snapshot being enabled.

`budget_counters_survive_async_pause_resume_boundary`
(`phases/mod.rs:167`) confirms counters survive an *async* pause/resume
boundary within one `LoopState` lifetime — i.e. across `.await` points
inside a single turn — NOT across a checkpoint reload (which creates a
fresh `LoopState`). This bounds the claim: counters survive async
suspension, not cross-process resume.

## Deviations

1. The in-memory `StateSnapshot` name is broader than its content. A
   reader expecting "state snapshot" to include plan/skills/budget will
   find only messages. This is the basis for F-RCT-05-P3-02 (naming
   oversells scope). Not a behavioural defect — the module doc is
   accurate, the struct name is the only misleading surface.
2. `working_dir` is the single forward-compatible field
   (`#[serde(default)]`); all other `AgentCheckpoint` fields are
   serde-required. There is no struct-level version tag. V04 covers the
   version-mismatch consequence.

## Conclusion

The claim is **supported**. Two snapshot types exist with cleanly
separated scopes: `StateSnapshot` (in-memory, message-only, opt-in,
never persisted) and `AgentCheckpoint` (persisted, messages+plan+skills+
working_dir+blocked_reason). Resume restores the trajectory and product
metadata; it deliberately does not restore per-turn runtime envelope
(budget/iteration/trace IDs) — consistent with the "trajectory + new
turn" recovery model from B-REF-01. The not-restored fields are a
design choice, not a defect. The findings filed under F-RCT-05 concern
(a) the chat-vs-execute asymmetry in *whether* restore runs at all
(F-RCT-05-P2-01), (b) silent fallback on corrupt/incompatible
checkpoints (F-RCT-05-P2-02), and (c) the `StateSnapshot` naming
mismatch (F-RCT-05-P3-02).
