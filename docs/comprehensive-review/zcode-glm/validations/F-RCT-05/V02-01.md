## Claim

On resume, completed tool calls are NOT re-executed because the
persisted trajectory already contains the `assistant_with_tools` →
`tool_result` pairs, and `AgentCheckpoint::restore_messages` enforces a
strict pairing invariant that rejects orphan/duplicate/mismatched tool
results. The framework has NO explicit idempotency gate keyed on
`completed_tool_call_ids` — that list is emitted as a trace event only.
Replay protection is therefore structural (trajectory + validation),
not a runtime gate, which is consistent with the prompt-driven design
rule in AGENTS.md.

## Method

Read-only static trace of the restore-validate path and the checkpoint
placement that guarantees pairing, anchored at:

```text
echo-agent/src/state/mod.rs:157-231                    (restore_messages + validate_tool_message_pairing)
echo-agent/src/state/mod.rs:170-183                    (completed_tool_call_ids)
echo-agent/src/agent/react/mod.rs:1731-1744            (CheckpointResumed trace event emission)
echo-agent/src/agent/react/run/phases/tools.rs:101-113 (assistant_with_tools push)
echo-agent/src/agent/react/run/phases/tools.rs:226-256, 382-412 (concurrent + serial tool_result pushes)
echo-agent/src/agent/react/run/phases/tools.rs:426-429 (post-batch checkpoint — "first point every call has a result")
echo-agent/src/agent/react/run/phases/compact.rs:34-35 (per-iteration checkpoint before think)
echo-agent/src/state/mod.rs:321-359                     (checkpoint_rejects_unpaired_or_duplicate_tool_results test)
```

Verified by following the message-ordering invariant: every
`save_runtime_checkpoint` site is positioned AFTER a fully-paired
trajectory, so an unpaired checkpoint cannot be written on the normal
or cancellation paths.

## Expected Result

1. `restore_messages` rejects a checkpoint whose trajectory has an
   assistant `tool_call` with no matching `tool_result` (orphan),
   a duplicate `tool_call_id`, a `tool_result` with no `tool_call_id`,
   or a `tool_result` whose `name` differs from the call's function
   name.
2. `completed_tool_call_ids` returns exactly the `tool_call_id`s of
   `Role::Tool` messages in the restored trajectory, in order.
3. Those IDs are consumed ONLY by the `CheckpointResumed` trace event
   (`react/mod.rs:1731-1737`); no tool-execution site consults them as
   a skip gate.
4. Every `save_runtime_checkpoint` call site that persists a paired
   trajectory is positioned after the batch completes; the mid-batch
   cancellation/timeout paths either checkpoint after pushing partial
   results or skip the post-batch checkpoint.

## Result

- Exit code: not-applicable (static inspection) + cargo confirmation.
- Summary: the claim is **supported**.

**(1) Pairing invariant is strict and four-way.**
`validate_tool_message_pairing` (`state/mod.rs:186-231`) walks the
message list once with a `HashMap<call_id, fn_name>` pending set:

| Condition | Rejected with |
|---|---|
| Assistant emits a `tool_call.id` already in `pending` | `duplicate in-flight tool call id {id}` (`:194-202`) |
| `Role::Tool` message with no `tool_call_id` | `tool result is missing tool_call_id` (`:206-209`) |
| `Role::Tool` message whose `tool_call_id` is not in `pending` | `orphan or duplicate tool result for {id}` (`:210-212`) |
| `Role::Tool` message whose `name` != pending fn name | `tool result name mismatch ...` (`:213-218`) |
| Non-empty `pending` at end of walk | `checkpoint has tool calls without results: {ids}` (`:221-229`) |

The last row is the key replay-protection invariant: a checkpoint that
ends with an unanswered assistant tool_call is rejected, so resume
never feeds the provider an unpaired trajectory (which OpenAI/Anthropic
reject with HTTP-400) and never re-runs the call blind.

**(2) `completed_tool_call_ids` shape.**
`state/mod.rs:170-183`: filters restored messages to `Role::Tool` and
collects `tool_call_id`. Pure projection over the validated trajectory.

**(3) IDs are trace-only, not a gate.**
`react/mod.rs:1731-1737`:
```rust
let completed_tool_call_ids = cp.completed_tool_call_ids()?;
self.record_trace_event(crate::trace::RunEvent::CheckpointResumed {
    conversation_id: conv_id.clone(),
    completed_tool_call_ids: completed_tool_call_ids.clone(),
    checkpoint_timestamp: cp.timestamp,
})
.await;
```
`grep -rn "completed_tool_call_ids" echo-agent/src` returns exactly two
hits: the `state/mod.rs` definition and this trace emission. No call
site in `phases/tools.rs`, `pipeline.rs`, or `execute_tool_with_policy`
consults the list to skip a tool. So if the model re-issues an
identical tool call (same name, same args, new `tool_call_id`) after
resume, the framework executes it again. This is the "no idempotency
gate" half of the claim — consistent with AGENTS.md's prompt-driven
design (verification belongs in the prompt/tool, not a framework gate).

**(4) Checkpoint placement guarantees pairing on the normal paths.**
Every `save_runtime_checkpoint` site that can produce a paired
trajectory:

| Site | Position | Pairing |
|---|---|---|
| `compact.rs:35` | Start of each iteration, before think | Paired: the previous iteration completed (post-batch checkpoint at `tools.rs:429` ran) or this is iteration 0 (only system+user). |
| `tools.rs:429` | After both sub-batches finish | Paired by construction — comment at `:426-428`: "first point where every assistant tool call in the batch has a matching result." |

The assistant_with_tools was pushed at `:110` with ALL calls, so a mid-batch cancel could leave some unpaired — but the cancellation checkpoint at `:203` runs only in the grace-elapsed arm AFTER the FuturesUnordered drained. See Deviation 1. |
| `tools.rs:258` (concurrent per-result cancel-observed) | After pushing the just-completed result | Paired for that call; other in-flight calls may still be pending — but this arm sets the grace timer and continues the loop, not an immediate checkpoint-and-exit. |

| `tools.rs:309, 336, 419` (serial cancel paths) | After the current serial tool's result/error push | Paired for completed serial calls. |
| `tools.rs:414` (serial tool error) | After pushing `[Error] ...` tool_result | Paired (errors are results too). |
| `finalize.rs:79, 164, 251` | At turn terminal | Paired (turn is over). |

## Deviations

1. **Mid-batch cancellation can persist a partially-paired trajectory
   to the in-memory `ContextManager`, but the on-disk checkpoint is
   protected.** The concurrent cancel-grace arm (`tools.rs:196-206`)
   and post-loop arm (`:278-300`) push the assistant_with_tools message
   (with ALL batch calls) at `:110` BEFORE any results, then push only
   the calls that completed during the grace window. If the grace
   elapses with N-k calls incomplete, the in-memory context has k
   `tool_result` messages for N tool_calls — an unpaired trajectory.
   However: (a) the cancellation checkpoint at `:203/:296` persists
   THIS in-memory state to the RuntimeStateStore, so the on-disk
   checkpoint can be unpaired; (b) the next `restore_messages` will
   then REJECT it via the end-of-walk "tool calls without results"
   check (`state/mod.rs:221-229`). So the worst case is: resume fails
   validation → falls back to the prior (clean) checkpoint or empty
   context (see V04 / F-RCT-05-P2-02). The unpaired mid-batch
   checkpoint is rejected, not silently loaded — the validation is the
   backstop. This is safe but means a cancelled batch can cost the user
   the iteration's work if the prior checkpoint is older. This is a
   consequence of the F-RCT-04 cancellation-grace design (5 s drain)
   combined with the strict pairing validator; it is not a new defect
   but is worth noting as a resume edge case.
2. The `completed_tool_call_ids` list is computed via a second full
   deserialize + walk (`restore_messages` inside
   `completed_tool_call_ids` at `state/mod.rs:172`), after
   `restore_messages` was already called once at `react/mod.rs:1691`.
   Minor redundant work (the messages are walked twice); not a
   correctness issue.

## Conclusion

The claim is **supported**. Replay protection is structural:
`validate_tool_message_pairing` rejects any trajectory that would let a
completed side effect be re-fed to the provider as an unanswered call,
and checkpoint placement keeps the on-disk trajectory paired on the
normal paths. The mid-batch cancellation edge case (Deviation 1) is
caught by the validator — the unpaired checkpoint is rejected, so no
replay occurs, though the user may lose the partial batch's progress.
`completed_tool_call_ids` is a trace-only projection; the framework
intentionally provides no idempotency gate, deferring retry-safety to
the prompt/tool layer (AGENTS.md prompt-driven design). This is the
basis for F-RCT-05-P3-01 (document the structural, non-gated nature of
replay protection).
