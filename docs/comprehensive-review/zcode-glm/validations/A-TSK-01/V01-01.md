## Claim

The TaskRuntime has an unambiguous file-authority model: `events.jsonl` is the
single write/read authority, while `plan.json` and `run-state.json` are
deterministic read projections regenerated from the event stream on every
mutation. There is no competing SQL/store authority and no overlapping writer.

## Method

Full read of the authority-bearing modules plus the write and read entry points.

```text
Read echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/store.rs (1-205, 676-885, 1123-1195, 1482-1530, 1778-1817)
```

## Expected Result

- One authoritative write primitive (`append_event_line`) feeding projections.
- `plan.json` and `run-state.json` derived (not independently writable).
- No SQL; no second store that mutates plan/run state outside the event append.
- A documented per-run write serialization.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **Authority declaration.** `store.rs:1-9` states the file system
    (`events.jsonl` plus deterministic `plan.json` and `run-state.json`
    projections) is the source of truth; `file_shadow.rs:1-7` reiterates
    "`events.jsonl` + `plan.json` is the read/write authority … SQL was retired".
    `TaskRuntimeStore` field doc (`store.rs:58-60`): "The event stream is
    authoritative; plan and execution files are deterministic read projections."
  - **File layout.** `{root}/{run_id}/` (`root` = `~/.eko/tasks/`,
    `file_shadow.rs:82-101`) holds exactly three files:
    - `events.jsonl` — append-only event stream (`append_event_line`,
      `file_shadow.rs:118-178`). Written via `O_APPEND` + `sync_all`
      (`append_line`, `file_shadow.rs:427-436`).
    - `plan.json` — `PlanRevision` snapshot = **spec only** (id/title/kind/
      depends_on/files/.../sort_order; NO execution status). Atomically
      rewritten by `rewrite_plan` (`file_shadow.rs:267-272`) via
      `atomic_write` (unique tmp + fsync + rename, `file_shadow.rs:405-422`).
    - `run-state.json` — `RunStateSnapshot` = run header +
      `Vec<EkoTaskExecution>` whose `status` field is the **framework
      `echo_agent::tasks::TaskStatus`** (types.rs:922-929). Atomically
      rewritten (`file_shadow.rs:273-278`).
  - **Write path (single authority).** Every `TaskRuntimeStore` mutator
    follows the same shape: hold per-run `plan_locks` mutex
    (`store.rs:77-82`) → `shadow.append_event_line(...)` →
    `shadow.rewrite_plan(run_id)`. Verified on `create_run`
    (`store.rs:336-356`), `transition_run` (`store.rs:387-425`),
    `compare_and_commit_revisioned_task_graph` (`store.rs:867-881`),
    `set_task_status` → `append_task_status_event`
    (`store.rs:1123-1186`). No mutator writes `plan.json` or
    `run-state.json` except through `rewrite_plan`.
  - **Projection rebuild.** `rewrite_plan` (`file_shadow.rs:208-280`) reads
    the full event stream, calls `rebuild_plan_from_events`, and rewrites
    only the projection(s) the latest event affects (`affects_plan` for
    `PlanRevisionCommitted`; `affects_run_state` for Run/Task status events).
    Events that affect neither (artifacts, reviews, notes) skip the rewrite.
  - **Read path.** `get_run`/`get_plan`/`list_todos` delegate to
    `FileTaskStore` (`store.rs:1482-1487, 1778-1788`). `FileTaskStore::load`
    (`file_store.rs:37-55`) reads `plan.json` + `run-state.json` + `events.jsonl`
    and merges. `FileTaskStore::get_plan` (`file_store.rs:125-160`) joins the
    spec snapshot with execution state and never rebuilds from events.
  - **Two store types, one authority.** `TaskRuntimeStore` (write authority,
    owns the `FileTaskShadow`) and `FileTaskStore` (read-only collection-query
    helper wrapping the same `FileTaskShadow`). No SQL, no second writer.
  - **Concurrency.** Same-run writes serialize on `plan_locks`
    (`store.rs:82`) AND `FileTaskShadow::run_write_locks`
    (`file_shadow.rs:30-34, 185-195`); different runs run in parallel.
- Log/artifact: none

## Deviations

None on the authority model. One caveat surfaced for the read path (not the
authority claim): `FileTaskStore::load` eagerly reads all three files, so a
corrupted `events.jsonl` breaks projection-only reads even though
`plan.json`/`run-state.json` are intact — audited under V04-01, not here.

## Conclusion

The file-authority model is unambiguous and implemented as documented:
`events.jsonl` is the sole write/read authority; `plan.json` (spec snapshot)
and `run-state.json` (execution snapshot) are deterministic projections
regenerated on every mutation via a single `append_event → rewrite_plan`
path. There is no SQL and no competing plan/run-state writer. Supports the
task report's primary conclusion and the V02/V04 read-path caveats.
