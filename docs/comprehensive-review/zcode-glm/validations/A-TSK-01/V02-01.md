## Claim

Conversion between EKO file/UI task types (`EkoTaskSpec`, `EkoTaskExecution`,
`PlanTask`, `TaskPlan`) and the framework task types
(`echo_agent::tasks::TaskSpec`, `TaskExecution`, `Task`,
`RevisionedTaskGraph`) is thin and field-by-field lossless in both directions,
with no dropped fields and no re-encoded scheduling/validation authority.

## Method

Field-by-field trace of every EKO↔framework conversion site in the adapter and
types layer.

```text
Read echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/revisioned_adapter.rs (full)
Read echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/types.rs (250-450, 800-1320)
Read echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/store.rs (676-885) [load/compare_and_commit graph conversion]
grep "fn to_task\b\|fn to_task_spec\|impl TryFrom<echo_agent::tasks::Task>\|fn to_task_plan_patch\|fn project_task_status\|fn try_from_task_status" types.rs
```

## Expected Result

- Every EKO spec field round-trips through framework `TaskSpec` without loss.
- The adapter (`EkoRevisionedTaskStore`, `EkoTaskToolPolicy`) performs only
  type conversion, metadata injection, and product policy — no patch logic,
  DAG validation, or ready-frontier computation.
- Execution state survives the round-trip for all framework `TaskStatus`
  variants.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **Adapter is thin (positive).** `EkoRevisionedTaskStore`
    (`revisioned_adapter.rs:26-76`) is a pure pass-through: `load` →
    `store.load_revisioned_task_graph`; `compare_and_commit` →
    `store.compare_and_commit_revisioned_task_graph`. The struct doc
    (`revisioned_adapter.rs:24-25`) states "It deliberately has no patch or
    validation logic; those remain authoritative in the framework service."
    `EkoTaskToolPolicy` (`revisioned_adapter.rs:80-296`) does product policy
    only: scope resolution, run bootstrap (`ensure_scope`), domain-default
    agent role, metadata round-trip, capability validation
    (`validate_candidate` delegates to `TaskCapabilityCatalog`). No DAG
    validation, no ready-frontier, no retry/cancel loop. Confirmed.
  - **Spec round-trip is lossless (positive).** `EkoTaskSpec::to_task_spec`
    (`types.rs:892-914`) maps all 13 fields 1:1 onto `echo_agent::tasks::TaskSpec`
    and packs EKO-only fields (`domain_profile`, `parallel_group`,
    `sort_order`) into `TaskSpec.metadata` as `EkoTaskMetadata` JSON. The
    inverse in `compare_and_commit_revisioned_task_graph`
    (`store.rs:804-832`) and `TryFrom<Task> for PlanTask`
    (`types.rs:1173-1199`) unpack the same JSON. `TaskPatch::to_task_spec_patch`
    (`types.rs:1236-1250`) and `TaskUpdateRequest::to_task_plan_patch`
    (`types.rs:1284-1316`) are 1:1 op-for-op mappings onto framework
    `TaskPlanPatchOp`. No spec field is dropped.
  - **Execution state round-trip is NOT lossless for two framework states
    (FAILURE).** `PlanTask::to_task` is documented "lossless"
    (`types.rs:1116`), but the inverse `TryFrom<echo_agent::tasks::Task> for
    PlanTask` (`types.rs:1162-1201`) calls
    `TodoStatus::try_from_task_status` (`types.rs:424-439`) which returns
    `Err` for `TaskStatus::Retrying { .. }` and `TaskStatus::Paused(_)`:
    `"framework task status {status:?} has no lossless EKO todo projection"`.
    A separate lossy helper `TodoStatus::project_task_status`
    (`types.rs:443-455`) collapses `Retrying → Running` and `Paused → Blocked`.
  - **The authoritative event stream encodes the lossy projection.**
    `append_task_status_event` (`store.rs:1123-1186`) writes
    `"status": status.as_str()` where `status: TodoStatus`. Therefore the
    event stream — the declared file authority (V01-01) — can never carry
    `retrying` or `paused` task states. `rewrite_plan` then regenerates
    `run-state.json` from that stream via
    `PlanTask::execution` → `TodoStatus::to_task_status`
    (`types.rs:1081-1089`), so the framework-typed
    `EkoTaskExecution.status` field in `run-state.json` is re-derived from
    the lossy `TodoStatus` and cannot hold `Retrying`/`Paused` after any
    `set_task_status`-driven rewrite.
  - **`commit_eko_task_plan` uses `DefaultTaskToolPolicy`, not
    `EkoTaskToolPolicy` (asymmetry).** `commit_eko_task_plan`
    (`revisioned_adapter.rs:344-388`) constructs
    `TaskRevisionService::new(..., DefaultTaskToolPolicy::new(run_id.clone()))`
    for the initial planner commit, bypassing `EkoTaskToolPolicy`. The
    comment (`revisioned_adapter.rs:342-344`) explains this is intentional
    ("Planning policy has already selected the EKO fields"), and the EKO
    metadata is pre-packed by the caller. Side effect: the planner path
    skips `validate_candidate` (capability validation) and
    `finalize_task_metadata` (sort_order normalization) that the task-tool
    path runs. Conversion itself stays lossless; the divergence is in
    policy hooks, not field mapping.
  - **`compare_and_commit_revisioned_task_graph` carries framework
    `TaskStatus` straight through (positive).** `store.rs:807-832` copies
    `task.execution.status` (framework type) into `EkoTaskSpec` only for
    spec fields; execution state is written into the `PlanRevisionCommitted`
    event payload's `plan` (spec only) while the live execution state flows
    through the separate `Task*` event path. The CAS, terminal-run guard,
    metadata decode, spec/execution id-match, and initial-pending invariant
    checks (`store.rs:764-844`) are EKO product policy, not a second DAG
    validator (V03-01 confirms no parallel validator).

## Deviations

The round-trip is lossy for framework `Retrying`/`Paused` task states. This
is documented in the type-layer docstring (`types.rs:917-920`: "The shared
`TaskStatus` remains authoritative and lossless. `TodoStatus` is derived only
when building UI-facing plan/todo projections.") — but that docstring is
inaccurate for the persisted authority path: because `rewrite_plan`
regenerates `run-state.json` from the `TodoStatus`-encoded event stream, the
persisted `EkoTaskExecution.status` is NOT the lossless framework value after
a status-event rewrite; it is the forward projection of a lossy encoding.

## Conclusion

The adapter is thin (no scheduling/validation authority) and the **spec**
round-trip is field-by-field lossless. The **execution-state** round-trip is
NOT lossless end-to-end: the authoritative event stream encodes status as
`TodoStatus`, which cannot represent the framework's `Retrying` and `Paused`
task states, and `rewrite_plan` regenerates the framework-typed
`run-state.json` from that lossy stream. Supports finding A-TSK-01-P2-02.
The `commit_eko_task_plan` policy asymmetry is recorded as P3-01.
