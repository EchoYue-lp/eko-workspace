## Claim

`HandoffManager::handoff` routes agent lookups through its own internal
`HashMap<String, Arc<dyn Agent>>` — a parallel path that never consults
`SubagentRegistry`. The LLM-facing `HandoffTool` (`tool name = "handoff"`)
is never constructed in production: `HandoffTool::new` has zero callers
across both repositories. The only live consumers of the handoff API are
two example demos (`demo21_handoff.rs`, `demo47_enterprise.rs`) that call
`HandoffManager::handoff` directly.

## Conclusion

Supports: the handoff module routes through a parallel
`HashMap<String, Arc<dyn Agent>>` and never consults `SubagentRegistry`.
The LLM-facing `HandoffTool` is unwired — no production or example code
constructs it. The entire live usage of the handoff API is two example
demos calling `HandoffManager::handoff` directly.

Does NOT support any claim that handoff and subagent dispatch share a
routing authority or that the `handoff` LLM tool is reachable from any
agent in the framework. They are siloed.

Findings using this validation: F-MAG-01-P2-01 (parallel authority with
no live consumer), F-MAG-01-P2-02 (the spawn-detach anti-pattern in the
routing path).
