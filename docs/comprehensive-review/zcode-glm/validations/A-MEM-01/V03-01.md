## Claim

When the memory protocol changes, the primary and pooled Agents are
refreshed immediately and consistently: MEMORY.md mutations refresh
`eko:hot-memory-context`, learned-rules.md mutations refresh
`eko:instruction-context`, and every surface (CLI/TUI/GUI/Dreaming) fans
the refresh out to both the primary agent and the pool.

## Expected Result

## Result

- Exit code: 0 (greps succeeded)
- Summary: **Claim is false.** Three defects found.

  **(P1-01) Wrong projection target on every MEMORY.md mutation.**
  `refresh_hot_memory_projection` has zero production callers outside
  `refresh_memory_projections`. The eight sites that mutate `MEMORY.md` all
  refresh `eko:instruction-context` instead:

  | Site | Mutates | Refreshes | Correct? |
  |---|---|---|---|
  | `infra.rs:1182` (Dreaming `promoted>0`) | MEMORY.md (`consider_promotion`) | instruction | no |
  | `tui/events.rs:2846` (`/remember` promoted) | MEMORY.md (`write_memory`) | instruction | no |
  | `tui/events.rs:2917` (`/forget` Hot) | MEMORY.md (`delete_memory` Hot) | instruction | no |
  | `tauri/commands/memory.rs:134` (add_memory promoted) | MEMORY.md | instruction | no |
  | `tauri/commands/memory.rs:227` (delete_memory Hot) | MEMORY.md | instruction | no |
  | `cli/cmd_impls/all.rs:130` (`/remember` promoted) | MEMORY.md | instruction | no |
  | `cli/cmd_impls/all.rs:201` (`/forget` Hot) | MEMORY.md | instruction | no |

  The two learned-rules.md sites are correct:

  | Site | Mutates | Refreshes | Correct? |
  |---|---|---|---|
  | `tauri/commands/panels.rs:1561` (promote_rule) | learned-rules.md | instruction | yes |
  | `cli/cmd_impls/evolution.rs:1489` (promote_rule) | learned-rules.md | instruction | yes |

  `get_instruction_suffix` (`instruction_provider.rs:141-163`) deliberately
  excludes `hot_memory`, so re-writing the instruction projection when only
  `MEMORY.md` changed is a no-op on the instruction marker and leaves the
  hot-memory marker stale.

  The only path that refreshes `eko:hot-memory-context` in production is
  `refresh_memory_projections` ← `refresh_dynamic_context`
  (`infra.rs:528-531`) ← workspace switch (`state.rs:883`, pool via
  `agent_pool.rs:553`). So the hot-memory stable prefix is frozen between
  workspace switches.

  **(P2-01) Pool helper cannot refresh hot memory.**
  `AgentPool::refresh_instruction_context` (`agent_pool.rs:686-710`) is
  documented as "Refresh hot-memory and instruction projections on every
  existing agent" but the body calls `refresh_instruction_projection` only
  (`:701`). Even if a caller wanted to fan a hot-memory refresh to the
  pool, no helper exists for it.

  **(P2-02) CLI surfaces do not fan out to the pool.**
  The three CLI call sites (`all.rs:130`, `all.rs:201`,
  `evolution.rs:1489`) refresh only `ctx.agent`. The TUI/GUI/panels/Dreaming
  sites all follow the primary-agent refresh with
  `pool.refresh_instruction_context()`. So a CLI-driven memory or rule
  change leaves every pooled/background agent (including the always-on
  `__background__` agent) on the stale projection until the next workspace
  switch or restart.

## Deviations

- The framework's per-turn `TURN_MEMORY_CONTEXT_PROJECTION`
  (`echo-agent/src/agent/react/run/context.rs:514-532`) re-injects
  query-recalled memories every turn. This partially masks P1-01: a
  promoted memory stored in the warm layer can still surface via recall
  when it matches the current query. It does **not** surface as the stable
  `## Active Memories (Hot Layer)` prefix, which is the surface Dreaming
  and `/remember` auto-promotion target. Severity rests on the stable
  prefix being defeated, not on total memory loss.
- The TUI/GUI add-or-delete paths refresh the pool only when
  `promotion.is_some()` / `layer == Some(Hot)` — i.e. only when `MEMORY.md`
  actually changed. That gating is correct; the defect is the wrong
  projection target, not the gating.

## Conclusion

The "immediate and consistent projection to primary and pooled Agents"
claim fails on three independent axes: wrong projection marker for MEMORY.md
mutations (P1-01), pool helper incapable of hot-memory refresh (P2-01), and
CLI pool-fan-out gap (P2-02). All three share one fix shape: route every
edit through a single helper that calls `refresh_memory_projections` on the
primary and a widened pool helper. Supports findings A-MEM-01-P1-01,
A-MEM-01-P2-01, A-MEM-01-P2-02.
