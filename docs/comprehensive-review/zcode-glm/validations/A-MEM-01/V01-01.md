## Claim

EKO owns exactly one instruction/memory file protocol (`InstructionProvider`
+ `UnifiedMemory`) with a deterministic tier precedence, and no parallel
authority for the instruction/memory suffix exists anywhere in the
application layer. The protocol is pure concatenation of every tier that
exists on disk (no override/merge semantics), in the fixed order
user → repository → project → learned-rules → local → hot-memory.

## Method

Static read of the loader, the wrapper, and every duplicate-search term
across both repositories.

```text
read echo-agent-cli/echo-agent-app-core/src/instruction_provider.rs:1-438
read echo-agent-cli/echo-agent-app-core/src/unified_memory.rs:1-268
read echo-agent-cli/echo-agent-app-core/src/auto_memory/mod.rs:1-72
grep -rn "InstructionProvider\|UnifiedMemory\|refresh_instruction_projection\|refresh_hot_memory_projection\|refresh_memory_projections\|get_instruction_suffix\|get_memory_suffix\|eko:instruction-context\|eko:hot-memory-context\|load_hot_memory\|agents_instructions_path" echo-agent-cli/ echo-agent/ --include='*.rs'
grep -rn "pub trait Store\b\|impl Store for" echo-agent-cli/ --include='*.rs'
```

## Expected Result

One `InstructionProvider` definition, one `UnifiedMemory` wrapper that
delegates to it, two projection markers, and a deterministic concatenation
order. No second loader, no second suffix builder, no second marker set.

## Result

- Exit code: 0 (all greps returned results consistent with the claim)
- Summary: Confirmed.
  - `InstructionProvider` is defined once at
    `echo-agent-cli/echo-agent-app-core/src/instruction_provider.rs:33`.
  - `UnifiedMemory` wraps it as `instructions: InstructionProvider` at
    `unified_memory.rs:59-62`; all four `UnifiedMemory::*_suffix` accessors
    delegate directly.
  - The two markers are module-private constants at
    `unified_memory.rs:28-29`:
    `eko:instruction-context` and `eko:hot-memory-context`.
  - Tier precedence is fixed in `get_instruction_suffix`
    (`instruction_provider.rs:141-163`):

    | Order | Header | Source file |
    |---|---|---|
    | 1 | `## User-level instructions` | `~/.eko/user.md` |
    | 2 | `## Repository instructions` | `AGENTS[.override].md` root→cwd chain (`agents_files_only` resolver) |
    | 3 | `## Project-level instructions` | `<root>/.eko/project.md` |
    | 4 | `## Auto-promoted rules` | `<root>/.eko/learned-rules.md` (legacy fallback `<root>/.eko/AGENTS.md`) |
    | 5 | `## Local directory instructions` | `<cwd>/.eko/local.md` |

    Hot memory is appended last as `## Active Memories (Hot Layer)` via
    `get_memory_suffix` (`:170-174`). `get_system_prompt_suffix`
    (`:121-134`) = `instruction_suffix ++ memory_suffix`. Every present
    tier contributes; absent tiers are silently omitted. There is **no
    override and no merge** — first-existing-wins applies only to the
    legacy `learned-rules.md`/`AGENTS.md` pair
    (`load_agents_instructions:267-284`).
  - `load_for(None)` deliberately ignores process cwd
    (`:54-56`), so the project/repository/local tiers disappear
    deterministically when a workspace is exited.
  - Duplicate search returned one canonical definition per term. The
    framework's per-turn `TURN_MEMORY_CONTEXT_PROJECTION`
    (`echo-agent/src/agent/react/run/context.rs:530`) and
    `WORKSPACE_CONTEXT_PROJECTION` (`:526`) are distinct runtime
    projections, not duplicates of the two EKO stable-prefix markers.
  - `auto_memory/mod.rs:17-71` routes observations into `EvidenceStore`
    (the review inbox), not into the instruction suffix — confirming the
    "static loader; dynamic memories handled separately" claim at
    `instruction_provider.rs:14`.

## Deviations

- The legacy `AGENTS.md → learned-rules.md` one-time migration
  (`instruction_provider.rs:90-113`) is a file-level rename, not a tier
  override; it converges to a single canonical filename. Tests at
  `:334-379` confirm it never overwrites a user-authored
  `learned-rules.md`.

## Conclusion

Single authority, deterministic concatenation precedence, no parallel
implementation. EKO's ownership boundary is clean: the application owns
the file protocol and the two projection markers; the framework owns the
projection survival and dynamic recall. Supports the Layering Decision and
Current Path "Instruction/memory protocol assembly". Establishes the
ground truth that V02 (compression survival of those two projections) and
V03 (refresh wiring) build on.
