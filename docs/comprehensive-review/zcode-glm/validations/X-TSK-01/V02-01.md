## Claim

There is exactly one authority for each task-graph concern:
one mutator (`TaskRevisionService`), one persistence contract
(`RevisionedTaskStore` trait), one patch engine
(`TaskPatchEngine::apply_operations`), one structural DAG validator
(`PlanValidator`), one kernel (`RuntimeDagExecutor`). The EKO
adapter (`EkoRevisionedTaskStore` / `EkoTaskToolPolicy`) is thin:
pure type conversion + metadata injection + product policy. No EKO
code re-implements patch semantics, DAG validation, ready-frontier
computation, retry loops, cancellation drains, or stall detection.

## Deviations

One intentional asymmetry: `commit_eko_task_plan` (the initial
planner commit path) constructs its own `TaskRevisionService` with
`DefaultTaskToolPolicy` instead of `EkoTaskToolPolicy`, skipping
the `validate_candidate` and `finalize_task_metadata` hooks for
that one path. Conversion itself stays lossless; the divergence is
in policy hooks, not authority. Already filed as A-TSK-01-P3-01;
not re-raised here.

## Conclusion

There is exactly one authority for each task-graph concern:
one `RevisionedTaskStore` trait (with one framework impl + one EKO
impl), one `TaskToolPolicy` trait (same), one `TaskRevisionService`
definition (framework; EKO only constructs it), one
`TaskPatchEngine::apply_operations`, one `PlanValidator`, one
`RuntimeDagExecutor`. The EKO adapter pair
(`EkoRevisionedTaskStore` + `EkoTaskToolPolicy`) is thin and
contains no patch/DAG/frontier/retry/cancel authority. The single
`commit_eko_task_plan` policy asymmetry is already tracked. AGENTS.md
rule 6 holds at the authority layer. Supports the task report's
primary conclusion.
