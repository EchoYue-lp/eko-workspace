## Claim

The framework `TaskSpec` (echo-agent) and EKO `EkoTaskSpec`
(echo-agent-cli) round-trip losslessly field-by-field in both
directions, and the only conversion asymmetry is the well-known
`Retrying`/`Paused` execution-state lossiness (already filed as
A-TSK-01-P2-02 / A-TSK-03-P3-02 and latent on the current executor
path). No spec field is dropped, re-encoded, or invented by the
adapter.

## Method

adapter and types layer.

## Expected Result

- Every one of the 13 framework `TaskSpec` fields has a 1:1 EKO
  counterpart on `EkoTaskSpec` (or is packed into `metadata` JSON as
  `EkoTaskMetadata`).
- Every framework `TaskPlanPatchOp` variant maps to one
  `TaskUpdateOperation` variant (or is intentionally disabled, e.g.
  `SetStatus`).
- The framework `TaskStatus` carries through `EkoTaskExecution.status`
  by identity, OR the lossiness is documented.
- No EKO code re-implements `TaskPatchEngine::apply_operations` or
  `apply_spec_patch`.

  ### Patch round-trip: framework `TaskPlanPatchOp` ↔ EKO `TaskUpdateOperation`

  EKO `TaskUpdateOperation` has 4 variants (`types.rs:1257-1272`):
  `Insert`, `Update`, `Skip`, `Reorder`. Framework
  `TaskPlanPatchOp` has 5 (adds `SetStatus`). The mapping
  (`TaskUpdateRequest::to_task_plan_patch`, `types.rs:1283-1316`)
  covers the 4 EKO variants 1:1; `SetStatus` is intentionally absent
  because `EkoTaskToolPolicy` does not override
  `allow_manual_progress_updates`, inheriting the trait default
  `false` (revisioned.rs:275-277). This matches EKO's product policy
  (no manual progress updates from the model). Verified consistent
  with A-TSK-02 V03-01.

  `TaskPatch::to_task_spec_patch` (`types.rs:1236-1250`) is a 1:1
  field-for-field copy onto framework `TaskSpecPatch` (12 `Option`
  fields). No field is dropped.

  ### Execution-state round-trip

  Framework `TaskStatus` has 10 variants (echo-agent
  `runtime.rs:90-107`): `Pending`, `Running`, `Blocked(String)`,
  `Completed`, `Failed(String)`, `Skipped`, `Cancelled`,
  `TimedOut { error }`, `Retrying { attempt, last_error }`,
  `Paused(String)`.

  EKO `TodoStatus` has 8 variants (`types.rs:367-377`): `Pending`,
  `Running`, `Blocked`, `Completed`, `Failed`, `Cancelled`,
  `TimedOut`, `Skipped`. No `Retrying`/`Paused`.

  - `TodoStatus::to_task_status` (`types.rs:409-421`) is total: every
    EKO variant maps to one framework variant.
  - `TodoStatus::try_from_task_status` (`types.rs:424-439`) returns
    `Err` for `Retrying`/`Paused` — the lossy edge.
  - `TodoStatus::project_task_status` (`types.rs:443-455`) is the
    lossy fallback: `Retrying → Running`, `Paused → Blocked`.

  The authoritative event stream encodes `TodoStatus`:
  `append_task_status_event` (`store.rs:1123-1176`) writes
  `"status": status.as_str()` with `status: TodoStatus`
  (store.rs:1163-1172). Therefore the persisted event stream cannot
  represent `Retrying`/`Paused`, and `rewrite_plan` regenerates
  `run-state.json` from that lossy stream.

  However — A-TSK-03-P3-02 (high confidence) established that the
  EKO executor never writes `Retrying`/`Paused` on the executor→store
  path. Retry is expressed as `Pending` + `retry_count`; pause is
  expressed as run-level `TaskRunStatus::Paused` (not task-level).
  The lossiness is therefore latent, not live.

  ### Adapter thinness (no patch/DAG re-implementation)

  `EkoRevisionedTaskStore` (`revisioned_adapter.rs:26-76`) is pure
  pass-through: `load` → `store.load_revisioned_task_graph`;
  `compare_and_commit` → `store.compare_and_commit_revisioned_task_graph`;
  both with only `store_error` mapping. No `TaskPatchEngine` call,
  no `apply_spec_patch`, no `PlanValidator` invocation.

  `EkoTaskToolPolicy` (80-296) does product policy only:
  `task_input_schema_extensions` adds `parallel_group`,
  `resolve_scope` / `ensure_scope` bootstrap a Run, `prepare_task`
  packs `EkoTaskMetadata`, `finalize_task_metadata` normalizes
  `sort_order`, `validate_candidate` delegates to
  `TaskCapabilityCatalog::validate_task_spec`. No patch/DAG/frontier
  logic.

  Verified zero `TaskPatchEngine::apply_operations` calls in
  `echo-agent-cli` outside `#[cfg(test)]` (`store.rs:915`, the
  `apply_task_patch_for_test` helper).

## Deviations

The execution-state round-trip is theoretically lossy for
`Retrying`/`Paused`, but the EKO executor never produces those
statuses (A-TSK-03-P3-02). The doc claim at `types.rs:917-920`
("shared `TaskStatus` remains authoritative and lossless") is
inaccurate for the persisted event-stream path; this is the same
drift A-TSK-01-P2-02 and A-TSK-03-P3-02 already recorded. Filed as
X-TSK-01-P3-01.

## Conclusion

The spec round-trip is field-by-field lossless end-to-end: all 12
direct fields + 1 `metadata` JSON bag (3 EKO-only fields) survive
both directions. The patch round-trip is intentionally 4-vs-5
variants (`SetStatus` disabled on EKO), consistent with EKO's product
policy. The execution-state round-trip is lossy for two framework
statuses that the EKO executor never produces — latent, not live.
The adapter is thin (no patch/DAG/validator authority). Supports the
task report's primary conclusion and X-TSK-01-P3-01.
