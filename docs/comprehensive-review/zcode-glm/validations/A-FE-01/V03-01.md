## Claim

The Option<T] ↔ TypeScript optional/null mapping is consistent: where
Rust serializes `None` as JSON `null`, the TS type is `T | null`; where
Rust uses `#[serde(skip_serializing_if = "Option::is_none")]` (so the
field is absent), the TS type is `T | undefined` (written as `?: T`).
No field has the wrong null/undefined contract in a way that would make
a strict-null-checked consumer fail at runtime.

## Method

For every Rust DTO field of type `Option<T>` that crosses IPC, classify
the serde convention (always-serialized-as-null vs
`skip_serializing_if = "Option::is_none"`) and compare against the
corresponding TS type annotation.

```text
1. Grep every Option<T> field in DTO structs that the Tauri command
   path returns:
   grep -n "pub.*Option<" echo-agent-app-core/src/types/response.rs \
                       echo-agent-app-core/src/tool_execution.rs \
                       echo-agent-app-core/src/persistence.rs \
                       echo-agent-app-core/src/model_config.rs \
                       echo-agent-app-core/src/evolution/evidence.rs \
                       src/tauri/commands/chat.rs \
                       src/tauri/commands/files.rs

2. For each occurrence, check whether the struct has
   #[serde(skip_serializing_if = "Option::is_none")] on the field.

3. Compare against the TS annotation in types/api.ts or generated/*.ts.

4. Spot-check consumer code for null-vs-undefined handling:
   grep -rn "\.task_id === null\|\.task_id === undefined\|\.task_id ?? "
           web-frontend/src --include="*.ts" --include="*.tsx"
```

## Expected Result

- Rust always-null Option ↔ TS `T | null` (not `?: T` alone).
- Rust skip-if-none Option ↔ TS `?: T` (not `T | null`).
- No field where TS forbids null but the wire sends null.

## Result

- Exit code: 0
- Duration: n/a
- Summary: most Option fields use the consistent pattern
  `always-null ↔ T | null` (with `?: ... | null` being a permissive
  superset that handles both). Three minor drifts found.

  Consistent (no finding):
  - `ToolExecutionSummary` (`tool_execution.rs:64-77`): all
    `Option<String>/Option<u64>` have no `skip_serializing_if`, so the
    wire always sends `null`. TS
    `conversation_id?: string | null`, `run_id?: string | null`,
    `finished_at?: number | null`, `duration_ms?: number | null` —
    consistent.
  - `ChatEvent::SelectionRequest` (`chat.rs:92-100`):
    `task_id/context/phase` are `Option<_>` with no skip; wire always
    sends `null`. TS `task_id?: string | null`, `context?: unknown`,
    `phase?: string | null` — consistent.
  - `emit_chat_event` routing metadata (`chat.rs:128-140`):
    `conversation_id` always inserted (as Null if None);
    `message_key` always inserted as String. TS both marked `?:` —
    permissive superset, not buggy.
  - `RuntimeTaskEvent.task_id` / `step_id`: no skip; wire always sends
    `null`. TS `string | null` — consistent.
  - `EvidenceCandidate.target`: `#[serde(default,
    skip_serializing_if = "Option::is_none")]` → wire absent when None.
    TS `target?: EvidenceTarget` — consistent.
  - `EvidenceRef.{source_run_id, source_role, source_turn,
    source_memory_key}`: all skip-if-none; TS all `?:` — consistent.
  - `ProviderTemplate` / `ConfiguredModelView.{base_url, temperature,
    max_tokens, context_window}`: no skip; wire always sends null.
    TS `string | null` / `number | null` — consistent.

  Drift (minor):
  - **`FileEntry` (`files.rs:12-20`) vs `endpoints.ts:745-752`**: Rust
    has `modified: Option<String>` and `extension: Option<String>`
    with NO `skip_serializing_if`, so the wire always sends
    `{modified: null, extension: null}` when absent. TS marks them as
    `modified?: string` and `extension?: string` (undefined-only,
    forbids null). Strict-null-checked consumer code that does
    `entry.modified === undefined` returns false (the wire value is
    `null`); code that uses truthiness checks (`if (entry.modified)`)
    still works. Cosmetic type-vs-runtime mismatch.
    A-FE-01-P3-03.**
  - **`DiffLine` (`files.rs:57-63`) vs `endpoints.ts:777-782`**: same
    pattern — `old_line: Option<usize>`, `new_line: Option<usize>`
    no skip; wire always null. TS `old_line?: number`,
    `new_line?: number` (forbids null). A-FE-01-P3-03.**
  - **`FileContent.mime_type` / `data_url` (`files.rs:23-32`) vs
    `endpoints.ts:761-770`**: in the SAME file as the drifts above,
    these two ARE typed as `string | null`, so the file is internally
    inconsistent — some Option fields include `| null`, others don't.
    The drift is only cosmetic in both directions (no runtime defect
    because consumers use truthiness). A-FE-01-P3-03.**

  Spot-check: the `subagentRunStore.taskRuntimeSubagentExecutionEvents`

  on `RuntimeTaskEvent`) into the `ExecutionEvent` shape
  (`task_id?: string`) via `jsonString` + `??` defaults. No
  null-vs-undefined hazard on this path.

## Deviations

The drifts in `FileEntry` / `DiffLine` are cosmetic — they would be
flagged by a strict round-trip test but do not produce runtime defects
on current consumer code (the file panels use truthiness checks). They
do indicate that no automated Option↔null/undefined linter or test
guards the contract.

## Conclusion

Supports the V03 claim: Option/null/undefined semantics are correct
for all load-bearing chat / tool-execution / task-runtime / evidence
DTOs (the high-traffic paths). The drift is confined to the file-panel
DTOs where the wire sends `null` and the TS declares `undefined`, a
cosmetic mismatch with no current runtime effect.
