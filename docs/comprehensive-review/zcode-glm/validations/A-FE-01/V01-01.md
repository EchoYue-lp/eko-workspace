## Claim

For every Rust DTO returned by a Tauri command, the wire field set
(Rust struct serialized by serde, or hand-built JSON in the command) and
the consuming TypeScript type (in `types/api.ts`, `api/endpoints.ts`, or
`generated/`) agree field-for-field: same field names, same presence, no
silent drift between hand-written and ts-rs-generated variants of the
same nominal type.

## Method

Static side-by-side comparison. Working directory:
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent`.

```text
1. Enumerate Rust DTO sources:
   - echo-agent-app-core/src/types/response.rs   (ts-rs exported DTOs)
   - echo-agent-app-core/src/tool_execution.rs   (manual DTOs)
   - echo-agent-app-core/src/persistence.rs      (SavedMessage, ConversationRecord)
   - echo-agent-app-core/src/model_config.rs     (ProviderTemplate, ConfiguredModelView)
   - echo-agent-app-core/src/evolution/evidence.rs (EvidenceCandidate, ...)
   - src/tauri/commands/chat.rs                  (ChatEvent enum)
   - src/tauri/commands/files.rs                 (FileEntry, FileContent, ...)
   - src/tauri/commands/conversations.rs         (hand-built wire JSON)
   - src/tauri/commands/panels.rs:346-386        (hand-built skill JSON)
   - src/tauri/commands/mcp.rs:60-86             (hand-built mcp JSON)

2. For each DTO, locate the consuming TS type:
   grep -rn "from.*types/api\|from.*generated" web-frontend/src \
       --include="*.ts" --include="*.tsx"

3. Compare field-by-field. Flag any:
   - Field present on the wire but absent from TS
   - Field present in TS but never sent on the wire
   - Same nominal type with different fields in manual vs generated

4. Trace consumer field access to confirm runtime impact of any drift:
   grep -n "tool.input_schema\|tool.parameters\|tool.need_approval" \
       web-frontend/src/components/tools/ToolsPanel.tsx
```

## Expected Result

- All Tauri command return shapes have a matching TS type.
- Manual TS and ts-rs-generated TS for the same nominal type agree.
- No consumer reads a field that the wire never sends.

## Deviations

The drift in `ToolInfo` is not just a typing issue: the consumer
(`ToolsPanel.tsx`) reads the manual-Typed field name (`input_schema`)
while the wire sends the Rust field name (`parameters`), so the runtime
payload is `undefined` and the rendered card silently omits parameters.
This is the load-bearing deviation that elevates the finding to P2.

## Conclusion

Supports the V01 claim with one significant caveat: most DTOs match, but
the manual `ToolInfo` type and the corresponding component field access
have drifted from the wire contract, with a user-visible effect. The
`SkillInfo` / `McpServerInfo` drift is currently masked because the
manual TS matches the hand-built wire and the generated TS is unused —
but the same-named manual-vs-generated collision is a maintainability
hazard (a developer importing from `generated/` would get the wrong
shape).

Findings using this validation: A-FE-01-P2-01, A-FE-01-P3-01.
