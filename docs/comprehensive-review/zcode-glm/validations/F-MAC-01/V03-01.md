## Claim

`#[derive(Tool)]` and `#[tool]` correctly handle struct generics, crate
rename, `echo_core`-vs-`echo_agent` crate-path fallback, and feature-gated
codegen.

## Method

Static inspection of `derive_tool.rs:226-415` (the derive expansion) and
`lib.rs:236-249` (the attribute expansion), plus
`resolve_echo_crate_path` (`derive_tool.rs:37-62`).

```text
1. Read derive_tool_impl: trace input.generics usage
2. Read resolve_echo_crate_path: trace crate-path resolution
3. grep for ::schemars and ::serde in generated code
4. Check echo_core-only consumer scenario (no echo_agent dep)
```

## Expected Result

- Struct generics are threaded through the generated `impl` and params struct
- Crate path is resolved via `resolve_echo_crate_path` (echo_agent or echo_core)
- All external crate references go through the resolved path
- Feature-gated codegen is handled correctly

## Result

- Exit code: 0 (static inspection)
- Summary: **FAILED** — two material gaps found.

### Gap 1: Generics silently dropped (P2-01)
`derive_tool_impl` at `derive_tool.rs:228-230` reads `input.ident` but
never reads `input.generics`. The generated `impl Tool for #struct_ident`
(line 358) and `<Self as ToolRunner<#params_ident>>::run` (line 387) omit
generic parameters. The generated `#struct_ident Params` struct (line 353)
also omits generics. A generic tool struct (`struct Tool<T>`) produces an
opaque post-expansion compiler error.

### Gap 2: Hard-coded ::schemars path (P2-02)
`lib.rs:236` and `derive_tool.rs:351` emit `::serde::Deserialize` and
`::schemars::JsonSchema` derives on the generated params struct.
`lib.rs:248` and `derive_tool.rs:363` emit `::schemars::schema_for!`.
The `::schemars` path is hard-coded and NOT routed through
`resolve_echo_crate_path`. `schemars` is not in `echo-core/Cargo.toml`
or `echo-macros/Cargo.toml`, so a consumer depending on only `echo_core`
gets "unresolved import: ::schemars".

### Crate-path resolution: CORRECT
`resolve_echo_crate_path` (`derive_tool.rs:37-62`) correctly tries
`echo_agent` first, falls back to `echo_core`, then to `crate`. It uses
`proc_macro_crate::crate_name` with proper error handling. This path is
used for all `echo_*` references in generated code.

## Deviations

The two gaps are real defects, not edge cases. Generics are a plausible
third-party use case. The schemars dependency leak affects every
non-workspace consumer.

## Conclusion

Crate-path resolution works correctly. But generics are silently dropped
(P2-01) and schemars is an undocumented hard dependency (P2-02). Both
should be fixed before the macros are advertised as production-ready.

## Follow-Up

Option (b) for P2-01: add `syn::Error::new_spanned` for generics.
For P2-02: route `::schemars` through `resolve_echo_crate_path` or
re-export from echo_agent/echo_core.
