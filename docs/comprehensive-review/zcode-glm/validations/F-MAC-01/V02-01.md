## Claim

The procedural macros emit clear diagnostics for invalid input: missing
required fields, wrong types, unknown attribute identifiers, and malformed
syntax.

## Method

Static inspection of `echo-macros/src/lib.rs` and `derive_tool.rs`,
checking every error-emitting path (`syn::Error::new`, `abort!`, `panic!`)
and documenting what happens with representative invalid inputs.

```text
1. grep -n 'syn::Error\|abort!\|panic!\|compile_error' echo-macros/src/*.rs
2. For each #[tool] attribute handler, trace the unknown-ident path
3. For #[derive(Tool)], trace the missing-name/description path
4. For #[callback]/#[guard]/etc., trace the wrong-signature path
```

## Expected Result

Every invalid-input path produces a `syn::Error` with a span pointing at
the user's code, not at the macro's internal expansion.

## Result

- Exit code: 0 (static inspection)
- Summary: Most attribute macros emit clear errors. `#[derive(Tool)]`
  uses `extract_tool_attrs` with proper error spans for missing name.
  `#[tool]` validates function signature. `#[callback]` validates the
  8 AgentCallback method names.

  **Notes:**
  - `#[derive(Tool)]` does NOT validate struct generics — they are
    silently dropped (see V03-01, finding P2-01). No error is emitted;
    the downstream compiler error is opaque.
  - `#[tool]` on a non-async function produces a clear error about
    missing `async`.
  - Unknown attribute identifiers in `#[tool(name = "...")]` produce
    "unknown attribute" errors.

## Deviations

The generics gap (P2-01) means one category of invalid input (generic
struct with `#[derive(Tool)]`) produces no macro-side diagnostic.

## Conclusion

Macro error handling is generally clear with proper spans. The generics
gap is a missing validation, not a misleading diagnostic.

## Follow-Up

Fix P2-01 by adding `if !input.generics.params.is_empty()` early
validation in `derive_tool_impl`.
