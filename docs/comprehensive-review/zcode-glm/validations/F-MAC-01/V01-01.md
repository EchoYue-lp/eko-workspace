## Claim

`echo_macros` exposes exactly eight procedural macros (`#[derive(Tool)]`,
`#[tool]`, `#[callback]`, `#[guard]`, `#[handler]`, `#[compressor]`,
`#[permission_policy]`, `#[audit_logger]`), each of which generates a
specific trait impl whose method signatures (lifetime, parameter, return
type) match the corresponding target trait definition in `echo-core` /
`echo-orchestration`. The macro-doc table at `echo-macros/src/lib.rs:1-31`
accurately describes the codegen.

### Codegen shape notes

- **`#[tool]` body inlining.** `tool_impl` does NOT route through
  `ToolRunner::run`. Instead it captures the user's fn body (`let body =
  &func.block;` at `lib.rs:220`) and splices it into
  `Box::pin(async move { let params = ...?; let #params_name { ... } =
  params; #body })` at `lib.rs:261-267`. The user's parameter bindings
  (`a`, `b`, ...) are in scope via the destructuring. This is a
  different codegen strategy from `#[derive(Tool)]`, which delegates to
  `ToolRunner::run`. Both strategies produce a valid `impl Tool`, but
  they are asymmetric — `#[derive(Tool)]` requires the user to write a
  separate `impl ToolRunner<...>` block (`echo-tools/src/git.rs:36`
  demonstrates), while `#[tool]` puts the body inline.

- **`extract_fn_params` (`lib.rs:615-648`).** Handles only
  `FnArg::Typed` whose `pat` is `Pat::Ident`. Patterns like `(_, ty)`,
  `(a, b): (f64, f64)`, or `mut x: f64` would hit the `Err` branch at
  `lib.rs:629` ("expected identifier pattern"). Acceptable for the
  documented examples; a forward-looking fix would handle tuple
  destructuring.

- **`lifetimed_params` + `add_lifetime_a` (`lib.rs:703-741`).** For each
  `FnArg::Receiver` the helper emits `&'a self`; for each `FnArg::Typed`
  it adds `'a` only if the type is a top-level `syn::Type::Reference`
  without an explicit lifetime. References already carrying a named
  lifetime (`&'b T`) are preserved as-is. See F-MAC-01-P3-07 for the
  shallow-rewrite limitation.

- **Visibility of generated items.** Both `#[tool]` (`lib.rs:237,241`)
  and `#[derive(Tool)]` (`derive_tool.rs:353,465`) emit `pub struct` for
  the params and the generated tool/struct. See F-MAC-01-P3-03.

- **`unwrap_or_default()` in `parameters()`.** `lib.rs:249` and
  `derive_tool.rs:364` use `::serde_json::to_value(schema)
  .unwrap_or_default()`. This does not panic (it falls back to
  `Value::Null`), but it silently produces a null schema if serialization
  fails — unlikely for `schemars::schema::RootSchema` but worth noting.

- **`to_pascal_case` (`lib.rs:777-790`).** Splits on `_` (and on `_`
  after replacing `-` with `_` in the `#[guard]` path at `lib.rs:400`).
  For `add` → `Add`; for `keep_recent` → `KeepRecent`; for
  `length-limit` (guard name) → `LengthLimit`. Correct for the
  documented examples. Non-ASCII inputs are not specifically handled.

- **Attribute-parser duplication.** `ToolAttrs` (`lib.rs:105-167`,
  used by `#[tool]`) and `ToolStructAttrs` (`derive_tool.rs:67-142`,
  used by `#[derive(Tool)]`) are near-identical hand-written
  `syn::Parse` impls. The derive variant adds `risk_level`. No
  shared parser — maintainability debt but not a contract defect.

- **`#[derive(Tool)]` unit-struct branch (`derive_tool.rs:419-495`).**
  Emits an empty params struct (`pub struct #params_ident {}`) and a
  `parameters()` returning a fixed
  `{"type":"object","properties":{},"required":[]}` JSON literal
  instead of using `schema_for!`. Correct for the no-arg case. Note
  the duplicate `#[allow(dead_code)]` at lines 467-468 (cosmetic).

## Deviations

- The signature matches are exact for the *trait-declared* shapes. They
  do not validate that the user's input fn (for `#[tool]`, `#[guard]`,
  `#[compressor]`, `#[permission_policy]`) actually returns the trait's
  expected return type — `tool_impl` accepts any non-`()` return type
  (`lib.rs:212-217`); `require_return_type` (`lib.rs:743-751`) used by
  `guard_impl`, `compressor_impl`, `permission_policy_impl` likewise
  only checks for non-`()`. The check is "has a return type", not
  "has the right return type". See F-MAC-01-P3-06.
- The lifetime injection in `lifetimed_params` is shallow; for the
  current `echo-core`/`echo-orchestration` trait shapes (all parameters
  are top-level `&T` or owned) this produces correct signatures. For
  hypothetical nested-reference parameters it would not. See
  F-MAC-01-P3-07.
- `messages!` accepts any `$role:ident` and expands to
  `Message::$role(...)`. If a user writes `messages![bogus("x")]` the
  error is "no associated item `bogus`" at the call site, not at macro
  expansion. Acceptable diagnostic; not a contract break.
- `tool_params!` and `chat_request!` use `stringify!($ty)` for the
  schema "type" field (`src/macros.rs:157,170,179,190`), so a user
  writing `tool_params! { "x" => (integer, ...) }` produces
  `{"type":"integer"}` (literally the string "integer"), not a
  JSON-Schema-validated type. The macro is a string templater, not a
  schema validator. Documented behaviour ("Quickly build tool parameter
  JSON Schema"); acceptable.
