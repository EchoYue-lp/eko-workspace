## Claim

Skill reload and unload behavior is deterministic at the framework
layer. There is NO framework-level filesystem watcher; reload is
explicit and application-driven. `unregister_skills_by_source` and
`remove_descriptor` clean up descriptors, source reverse-index,
legacy instructions, plugin variables, activation bookkeeping, sandbox
policies, hooks, and context projections. Running-script cancellation
on unload is NOT handled by the registry; it is handled by the runtime
owning the tool's BoxFuture (future-drop + `kill_on_drop(true)` on the
direct path) and by `SandboxManager` on the sandboxed path.

## Expected Result

Per-case expectation:
- `remove_descriptor(name)` purges descriptor, source reverse-index
  entry, `legacy_instructions[name]`, `plugin_variables[name]`,
  `activated[name]`, `active_sandbox_policies[name]`.
- `unregister_by_source(src)` looks up `by_source[src]`, removes each
  name via `remove_descriptor`, returns the sorted removed list.
- `unregister_skills_by_source` at the agent level mirrors cleanup on
  the shared progressive registry, the hook registry, and context
  projections, then refreshes the three progressive-disclosure tools.
- A skill descriptor registered with the same name *without* going
  through `remove_descriptor` first does NOT clear the previous
  occupant's `legacy_instructions`/`plugin_variables` (F-SKL-01-P2-02).
- No framework-level filesystem watcher for skills exists.
- A running `run_skill_script` subprocess started before unload is
  not killed by the registry; it is killed when the runtime drops the
  tool's BoxFuture (cancellation) thanks to `kill_on_drop(true)` on
  the direct path, or by `SandboxManager` cancellation on the
  sandboxed path.

## Result

- Exit code: not-applicable (static inspection).
- Duration: n/a
- Summary:
  - **`remove_descriptor` (registry.rs:208)** removes the descriptor,
    prunes the `by_source[src]` reverse index (deleting the entry when
    the set becomes empty), removes `legacy_instructions[name]`,
    removes `plugin_variables[name]`, removes `activated[name]`, and
    removes `active_sandbox_policies[name]`. Locks are taken with
    `unwrap_or_else(|error| error.into_inner())` to be poison-safe
    (consistent with the AGENTS.md no-panic rule). Returns
    `removed_descriptor.is_some()`.
  - **`unregister_names_by_source` (registry.rs:138)** removes the
    source entry from `by_source`, calls `remove_descriptor` for each
    name, sorts the result, and returns it. `unregister_by_source`
    returns just the count.
  - **`reconcile_skill_load_policy` (capabilities.rs:809)** walks
    descriptors, filters those disallowed by the current policy, and
    for each removal: calls `skill_registry.remove_descriptor`,
    unregisters `HookSource::Skill(name)` from the hook registry,
    clears the `echo-agent:skill:{name}` context projection, then
    refreshes the shared progressive registry, the catalog projection,
    and the three progressive-disclosure tools.
  - **`unregister_skills_by_source` (capabilities.rs:915)** mirrors
    the same cleanup for plugin-source group unload: catalog registry,
    shared progressive registry, hooks (`HookSource::Skill(name)`),
    context projections (per-skill + catalog), and tool refresh.
  - **`register_descriptor` overwrite branch (registry.rs:95-124)**
    updates the `by_source` reverse index when the previous occupant
    was source-tagged, but does NOT clear `legacy_instructions[name]`
    or `plugin_variables[name]` before `self.descriptors.insert(...)`.
    Confirmed by reading the method end-to-end: only the descriptor
    itself and the source reverse-index are touched. This is the
    F-SKL-01-P2-02 root cause.
  - **No filesystem watcher.** The grep returned only test fixture
    strings (skill bodies containing the word "notify" as an example
    command) — no `notify` crate, no `fs_watch`, no `reload_skills`,
    no `Watcher` type at the framework level. Re-discovery requires an
    explicit `discover_skills()`/`load_skills_from_dir()` call (or
    `reconcile_skill_load_policy` for policy-driven removal).
  - **Cancellation of running scripts.**
    - Direct fallback path (`run_script_tool.rs:319`):
      `cmd.kill_on_drop(true)` is set before
      `tokio::time::timeout(timeout, cmd.output()).await`. When the
      tool's BoxFuture is dropped (e.g. the agent's CancellationToken
      fires and the runtime drops the future), the inner
      `cmd.output()` future is dropped, which (with `kill_on_drop`)
      kills the child process. Same pattern in
      `prompt_exec.rs:426` (`run_command_direct`) and
      `hooks.rs:1178` (`execute_command_hook`).
    - Sandboxed path (`run_script_tool.rs:279-294`): execution goes
      through `manager.execute(sandbox_cmd).await` or
      `manager.execute_with_limits(...)`. Cancellation of the
      sandboxed subprocess depends on the `SandboxManager`
      implementation (F-SEC-01's scope). The skill tool does not
      impose a separate `kill_on_drop` here; it relies on
      `SandboxManager` honoring future-drop. The timeout itself is
      applied via `SandboxCommand::with_timeout` and
      `apply_sandbox_policy` (run_script_tool.rs:72).
  - **Registry vs. runtime ownership.** `SkillRegistry` does not
    track running tool futures or subprocess handles. The
    `activated: HashSet<String>` and `active_sandbox_policies` are
    bookkeeping only; they do not gate script cancellation. So
    removing a descriptor while a script is running will not
    proactively kill the subprocess — the runtime's ownership of the
    tool future is the sole cancellation path. This is the correct
    layering: the registry is a metadata authority, not a process
    supervisor.

## Deviations

- `register_descriptor`'s overwrite branch does not fully mirror
  `remove_descriptor`'s cleanup (legacy/plugin_variables leak).
  Recorded as task finding F-SKL-01-P2-02, not a validation failure:
  the canonical unload path goes through `remove_descriptor`/
  `unregister_by_source`, which is fully correct. The gap is only in
  the direct-overwrite edge case.

## Conclusion

Skill unload and reload behavior is deterministic and correctly
cleaned up at the framework layer through the canonical
`remove_descriptor` / `unregister_by_source` /
`reconcile_skill_load_policy` paths. There is no framework-level
filesystem watcher; reload is application-driven (CLI plugin runtime
calls unregister + load). Script cancellation on unload is owned by
the runtime (future-drop + `kill_on_drop(true)`), not the registry —
the correct layering. The F-SKL-01-P2-02 cleanup gap exists only on
the direct-overwrite path, which canonical callers avoid. Supports
the task report's "Current Path" items 9, 15, 16 and Findings
F-SKL-01-P2-02 and (cancellation claim) F-SKL-01-P3-02.
