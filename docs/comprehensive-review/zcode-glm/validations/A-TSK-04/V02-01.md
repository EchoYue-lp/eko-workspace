## Claim

Every optimistic-concurrency surface in the task-runtime store
rejects stale inputs **before** appending any event. Rejection never
silently overwrites durable state, and rejection never leaves a
partial event line on disk. Concretely:

1. `claim_task` rejects a stale plan revision (or a stale task spec,
   or a non-Pending task) with
   `RuntimeTaskClaimOutcome::ReloadSnapshot`, no event appended.
2. `compare_and_commit_revisioned_task_graph` rejects a stale
   `expected_revision` (or a terminal run, or an out-of-sequence next
   revision) with `Err(StoreError::PlanConflict)` or
   `Err(StoreError::InvalidPlan)`, no event appended.
3. `set_claimed_task_status` and `requeue_claimed_task` reject a
   stale claim (or a non-Running task, or a missing task) with
   `ClaimWriteOutcome::Superseded`, no event appended.
4. `transition_run` rejects an illegal run-status transition
   (including any transition out of terminal `Cancelled`/`Completed`)
   with `Err(StoreError::IllegalTransition)`, no event appended.
5. `attach_plan_for_test` (the seed helper used by the framework
   validator) rejects a structural DAG cycle with
   `Err(StoreError::InvalidPlan)`, no event appended.
6. The rejection-before-append invariant is observable: every test
   that exercises a rejection asserts both the error variant AND that
   the event count did not increase.

- Why "no event appended" is structurally guaranteed: every
  state-mutating method follows the pattern `with_run_lock(|| {
    read → validate → if invalid: return Err; append_event_line(...);
    rewrite_plan(...); Ok(...) })`. The `append_event_line` call is
  the **last** write side-effect before the `Ok`; every prior branch
  is a pure read + early-return. `append_event_line`
  (file_shadow.rs:118-178) itself holds the per-run write lock across
  seq-alloc → append → cache-bump, so a rejected call that never
  reaches it cannot advance the seq cache or be observed by a later
  call. (The seq cache is only bumped at file_shadow.rs:162-164,
  inside the locked section, after the line is durably appended.)

- Test evidence (rejection + "no event appended"):
  - `illegal_transition_is_rejected_and_leaves_no_event`
    (store.rs:2300-2324): transitions Pending → Running → Completed
    (legal), then attempts Completed → Running (illegal). Asserts
    `Err(StoreError::IllegalTransition)` and
    `list_events(...).len() == before_terminal` (unchanged).
  - `file_path_rejects_illegal_transition_and_appends_no_event`
    (store.rs:3374-3394): same scenario on the file path, asserting
    the file-authority branch rejects before writing.
  - `file_path_rejects_dependency_cycle_and_appends_no_event`
    (store.rs:3398-3454): creates t1 → t2, then patches t1 to depend
    on t2 (cycle). Asserts `Err(StoreError::InvalidPlan)` and
    unchanged event count. This exercises the `PlanValidator` call at
    store.rs:921-923 inside `apply_task_patch_for_test`.
  - `file_path_rejects_unknown_task_and_appends_no_event`
    (store.rs:3459-3468): `set_task_status("nope", ...)` returns
    `Err(TaskNotFound)` with unchanged event count.
  - `task_update_rejects_stale_revision_without_appending_event`
    (store.rs:3039-3057): patches with `base_revision: 0` against a
    plan at revision 1. Asserts `Err(PlanConflict)` and unchanged

## Deviations

One nuance is filed as a finding (P3-01) rather than treated as a
deviation from this validation's claim:

- The naked `set_task_status` (store.rs:953) is not in the rejection
  matrix above because it has **no** optimistic-concurrency guard to
  reject against. It writes whatever status the caller passes. This
  is A-TSK-04-P3-01: a defense-in-depth gap, not a violation of V02's
  claim (V02 only covers the surfaces that *have* a stale-input
  guard).

## Conclusion

Supports: the "stale write rejection" invariant. Every store API that
accepts an optimistic-concurrency input (`expected_revision`,
`claim`, run-status transition) validates it before any append, and
returns a typed rejection (`ReloadSnapshot` / `Superseded` /
`Err(PlanConflict)` / `Err(InvalidPlan)` / `Err(IllegalTransition)`)
without appending an event or advancing the seq cache. The file
authority therefore cannot be partially corrupted by a stale writer.

Supports: the AGENTS.md rule 6 ("任务关系只有一个权威 API") — there
is one revision commit surface (`compare_and_commit_revisioned_task_graph`,
wrapped by the framework `RevisionedTaskStore` impl) and one claim
surface (`claim_task`), both gated by optimistic concurrency.

Does NOT support (and is not asked to support): that the naked
`set_task_status` rejects illegal `TodoStatus` transitions. That is
the A-TSK-04-P3-01 gap.

Findings using this validation: A-TSK-04-P3-01 (for the contrast —
the claim-guarded surfaces are sound; the unguarded `set_task_status`
is the gap).
