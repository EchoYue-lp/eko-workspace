## Claim

Events are strictly ordered per run, every replay fold iterates them
in seq order, run-level terminal monotonicity is enforced, and the
typed-status → event-kind → hook-status mapping preserves terminal
distinction. Concretely:

1. `append_event_line` assigns seq under the per-run write lock
   (seq-alloc → append → cache-bump are atomic w.r.t. same-run
   writers); concurrent same-run appends produce strictly increasing
   per-run seqs.
2. `rewrite_plan` re-acquires the same per-run write lock and rebuilds
   the `plan.json`/`run-state.json` projection from the full event
   stream via `rebuild_plan_from_events`, which iterates events in seq
   order.
3. Every read-side fold (`rebuild_plan_from_events`,
   `recoverable_subagent_result`, `list_recovery_blockers`,
   `active_subagent_boundaries`, `active_tool_boundaries`) iterates
   `list_events(run_id, 0)` in seq order.
4. Run-level terminal monotonicity is enforced:
   `TaskRunStatus::can_transition_to` makes `Cancelled` and
   `Completed` refuse any further transition; `transition_run` checks
   this BEFORE any append and returns `Err(IllegalTransition)` with
   no event on rejection.
5. The typed `TodoStatus` drives the typed `RuntimeEventKind`
   (Failed → `TaskFailed`, Cancelled → `TaskCancelled`, TimedOut →
   `TaskTimedOut`), independent of the summary/status_detail text.
6. The `HookEventDispatcher` translates each typed event to its
   framework `HookEvent` counterpart preserving the terminal-status
   distinction (Cancelled → `SubagentStopStatus::Cancelled`, TimedOut
   → `TimedOut`, not collapsed to Failed/Skipped) and delivers them
   through a bounded single-consumer queue that applies backpressure
   rather than dropping.

## Expected Result

- Strict per-run seq ordering under the per-run write lock.
- `rewrite_plan` rebuilds from the full event stream under the same
  lock; the projection is deterministic.
- All read-side folds iterate in seq order.
- Run-level terminal monotonicity: Cancelled/Completed cannot

- Typed-status → event-kind mapping: status_detail text never changes
  the emitted event kind.
- Hook terminal distinction: Cancelled/TimedOut not collapsed.
- Bounded queue: backpressure, not drop.

## Result

- Exit code: 0 (static inspection; supporting test results in V04-01).
- Summary: Claim confirmed (with one P3 defense-in-depth gap noted).

### (1) Write ordering and seq allocation

- `append_event_line` (file_shadow.rs:118-178) holds the per-run
  `run_write_lock(run_id)` (file_shadow.rs:185-195 →
  `run_write_locks: std::sync::Mutex<HashMap<String,
  Arc<Mutex<()>>>>`) across:
  1. `next_seq(run_id)` (file_shadow.rs:141) — reads/initialises the
     in-memory `seq_cache` (file_shadow.rs:282-338);
  2. `serde_json::to_string(&event)` + `append_line(events_path,
     line)` (file_shadow.rs:156-159) — `O_APPEND` + `sync_all`
     (file_shadow.rs:427-436);
  3. `seq_cache.insert(run_id, next_seq)` (file_shadow.rs:162-164);
  4. event hook fire (file_shadow.rs:174-176).
- Because the lock wraps seq-alloc → append → cache-bump, two
  concurrent same-run writers cannot observe the same cached seq
  (the doc at file_shadow.rs:128-131 calls out the historical
  duplicate-seq bug this design closes). The test
  `concurrent_append_produces_unique_strictly_increasing_seq`
  verifies this directly.
- seq is per-run (the events file is per-run at
  `{root}/{run_id}/events.jsonl`, file_shadow.rs:91-93), so appending
  to run B does not advance run A's seq.
- `append_line` uses `O_APPEND` (file_shadow.rs:429-432), which
  guarantees that concurrent writes (if any) do not interleave within
  a single `write(2)` call on POSIX-local filesystems. Combined with
  the per-run lock, this gives strict per-run serialization.

### (2) Projection rebuild under the same lock

- `rewrite_plan` (file_shadow.rs:208-280) acquires
  `run_write_lock(run_id)` at file_shadow.rs:213-214 — the **same**
  lock instance used by `append_event_line`. The doc at
  file_shadow.rs:209-212 explains why: proceeding after `try_lock`
  would rebuild and rename `plan.json` without serialization.
- `rewrite_plan` calls `read_events(run_id)` (file_shadow.rs:216,
  defined at 362-379) which reads the entire `events.jsonl` and
  deserialises each non-empty line into a `RuntimeTaskEvent`, in
  file order = seq order (events are appended in seq order, so the
  file is naturally sorted).
- The rebuild then calls `rebuild_plan_from_events(&events)`
  (file_shadow.rs:245) — the deterministic fold defined in
  event_rebuild.rs:59-260 — and writes the result via
  `atomic_write(plan_path, ...)` and `atomic_write(run_state_path,
  ...)` (file_shadow.rs:267-278).
- `atomic_write` (file_shadow.rs:405-422) writes to a unique tmp file
  name (`{path}.tmp.{pid}.{ts}.{counter}`, file_shadow.rs:408-413),
  fsyncs, and renames over the target. The uniqueness is critical:
  the doc at file_shadow.rs:398-404 explains that a fixed `.tmp`
  suffix would race under concurrent `rewrite_plan` calls. The test
  `concurrent_atomic_write_no_tmp_collision` verifies this.
- The test `rewrite_plan_waits_for_same_run_write_lock` verifies
  that `rewrite_plan` blocks on a same-run writer rather than
  proceeding concurrently.
- The `shadow_parity_*` tests (file_shadow.rs tests) verify that the
  projection equals the event-fold after a full lifecycle, after
  reorder/remove patches, after run-status transitions, and across
  multiple isolated runs.

### (3) Read-side folds iterate in seq order

Every fold calls `list_events(run_id, 0)` (store.rs:1790-1798), which
delegates to `FileTaskStore::list_events` →
`FileTaskShadow::read_events` (file_shadow.rs:362-379) — returning
the events in file/seq order. Each fold iterates this `Vec` in order:

- `rebuild_plan_from_events` (event_rebuild.rs:66 — `for ev in events`);
- `recoverable_subagent_result` (store.rs:2046 — `for event in
  self.list_events(run_id, 0)?`);
- `list_recovery_blockers` (store.rs:2083 — `for event in
  self.list_events(run_id, 0)?`);
- `active_subagent_boundaries` (store.rs:1533 — `for event in
  self.list_events(run_id, 0)?`);
- `active_tool_boundaries` (store.rs:1562 — same).

The deterministic-order guarantee is what makes these folds
sound: `SubagentAssigned` clearing a prior `SubagentReleased`
(store.rs:2053), `RecoveryResolved` removing a prior
`RecoveryBlocked` (store.rs:2102-2106), `ToolCompleted` removing an
in-flight `ToolStarted` (store.rs:1587-1589), and the
`PlanRevisionCommitted` task-execution carry-over
(event_rebuild.rs:147-193) all rely on observing events in the order
they were appended.

### (4) Run-level terminal monotonicity

- `TaskRunStatus::can_transition_to` (types.rs:517-527):
  ```text
  Pending   → Running | Cancelled
  Running   → Paused | Failed | Completed | Cancelled
  Paused    → Running | Cancelled
  Failed    → Running | Cancelled
  Cancelled → (none)         ← terminal
  Completed → (none)         ← terminal
  ```
- `transition_run` (store.rs:387-428) reads the current run status
  under `with_run_lock`, checks `can_transition_to(next)` at
  store.rs:398, and returns `Err(StoreError::IllegalTransition)` at
  store.rs:399-404 **before** the `append_event_line` call at
  store.rs:406. The `rewrite_plan` call at store.rs:422 therefore
  never runs on rejection.
- Test evidence:
  - `illegal_transition_is_rejected_and_leaves_no_event`
    (store.rs:2300-2324): Pending → Running → Completed (legal), then
    Completed → Running (illegal). Asserts `Err(IllegalTransition)`
    AND `list_events(...).len() == before_terminal` (no new event).
  - `file_path_rejects_illegal_transition_and_appends_no_event`
    (store.rs:3374-3394): same scenario, explicitly targeting the
    file-authority branch.

### (5) Typed-status → event-kind mapping

- `append_task_status_event` (store.rs:1123-1176) maps the typed
  `TodoStatus` to the typed `RuntimeEventKind` at store.rs:1143-1152:
  ```text
  Running   → TaskStarted
  Completed → TaskCompleted
  Failed    → TaskFailed
  Cancelled → TaskCancelled
  TimedOut  → TaskTimedOut
  Skipped   → TaskSkipped
  Blocked   → TaskBlocked
  Pending   → TodoUpdated
  ```
- The `status_detail` (store.rs:1153-1157) and `summary`
  (store.rs:1166-1168) are payload fields; they do NOT influence the
  event kind. A `Failed` task whose `status_detail` happens to
  contain the word "cancelled" still produces `TaskFailed`, not
  `TaskCancelled`.
- Test evidence: `task_terminal_events_follow_typed_status_not_detail_text`
  (store.rs:2394-2449). The "failed" sub-test sets
  `Some("the report mentions timeout and cancelled behavior")` as
  the summary on a `TodoStatus::Failed` task, then asserts:
  - `events.iter().any(|e| e.event_type == TaskFailed)`;
  - `events.iter().all(|e| !matches!(e.event_type, TaskTimedOut |
    TaskCancelled))`.
  The "timed_out" and "cancelled" sub-tests analogously verify that
  their typed statuses produce their typed events.

### (6) HookEventDispatcher preserves terminal distinction and order

- `HookEventDispatcher` (hook_event_dispatcher.rs:49-215) is a
  bounded `std::sync::mpsc::sync_channel` (capacity 256,
  hook_event_dispatcher.rs:70, 88) consumed by a single dedicated
  thread (hook_event_dispatcher.rs:89-111). The module doc at
  hook_event_dispatcher.rs:14-18 explains the design choice:
  independent `tokio::spawn` calls are deliberately avoided because
  they can deliver Completed before Started.
- The translation table at hook_event_dispatcher.rs:273-353 maps:
  ```text
  TaskStarted                   → TaskStarted
  TaskCompleted                 → TaskCompleted(status=Completed)
  TaskFailed                    → TaskCompleted(status=Failed)
  TaskCancelled                 → TaskCompleted(status=Cancelled)
  TaskTimedOut                  → TaskCompleted(status=TimedOut)
  TaskSkipped                   → TaskCompleted(status=Skipped)
  SubagentAssigned (hook=true)  → SubagentStart
  SubagentReleased (hook=true)  → SubagentStop(status mapped from
                                  the "status" string field)
  PlanRevisionCommitted         → TaskCreated (one per new task id)
  ```
  The Cancelled/TimedOut statuses are NOT collapsed to Failed or
  Skipped — they map to distinct `TaskTerminalStatus` /
  `SubagentStopStatus` variants.
- The `dispatch` method (hook_event_dispatcher.rs:130-150) enqueues
  each translation under the persisted order; the bounded channel
  applies backpressure when full (`sender.send(...)` blocks). The
  doc at hook_event_dispatcher.rs:124-129 states this is deliberate:
  lifecycle delivery is never silently dropped merely because hooks
  are slower than the task event producer.
- Test evidence:
  - `task_cancelled_status_is_not_collapsed_to_skipped`
    (hook_event_dispatcher.rs:611-628): a `TaskCancelled` event with
    `status_detail="cancelled with parent run"` translates to
    `TranslatedKind::TaskCompleted{ status: Cancelled }`.
  - `task_timed_out_status_is_not_collapsed_to_failed`
    (hook_event_dispatcher.rs:631-645): a `TaskTimedOut` event
    translates to `TaskCompleted{ status: TimedOut }`.
  - `subagent_released_maps_status` (hook_event_dispatcher.rs:684-715):
    `SubagentReleased{status="timed_out"}` translates to
    `SubagentStop{status: TimedOut}`.
  - `bounded_queue_applies_backpressure_without_dropping`
    (hook_event_dispatcher.rs:759-809): pauses the consumer,
    dispatches one event past capacity, asserts the producer blocks
    (50ms timeout), then releases and asserts the event is delivered.
  - `flush_and_shutdown_are_explicit_and_idempotent`
    (hook_event_dispatcher.rs:747-756): flush waits for prior events;
    shutdown drains and is idempotent; post-shutdown dispatch errors.

## Deviations

One nuance is filed as a finding (P3-01) rather than treated as a
deviation:

- `TodoStatus` has no `can_transition_to` table (types.rs:367-457),
  so the **task-level** terminal monotonicity is not enforced at the
  store layer. The run-level monotonicity is enforced (part 4 above).
  See A-TSK-04-P3-01 for the defense-in-depth gap and the trusted-
  caller analysis that keeps current code paths sound.

## Conclusion

1), the "projection is a deterministic fold" invariant (part 2), the
"replay folds are order-sensitive and read in seq order" invariant
(part 3), the "run-level terminal monotonicity is enforced" invariant
(part 4), the "typed status drives typed event kind" invariant (part
5), and the "hook dispatch preserves terminal distinction and order"
invariant (part 6).

Supports: A-TSK-03-P3-02's "EKO never produces framework
`Retrying`/`Paused`" classification — the typed mapping at
store.rs:1143-1152 emits only the eight EKO `TodoStatus` variants;
framework `Retrying`/`Paused` are never produced.

Does NOT support (and is not asked to support): task-level terminal
monotonicity at the store layer. That is the A-TSK-04-P3-01 gap. The
claim-guarded writers (`set_claimed_task_status`,
`requeue_claimed_task`) enforce it indirectly via the Running+claim
guard, but the naked `set_task_status` does not.
