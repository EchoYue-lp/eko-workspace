## Claim

The `echo_state::compression` module defines a single canonical
`ContextCompressor` trait, and each concrete compressor (SlidingWindow,
Summary, IncrementalSummary, Hybrid, VisibilityHorizon, Adaptive) preserves
a documented, distinct set of invariants. No parallel compressor trait or
duplicate authority exists in the repository.

### Invariants enforced by the framework (not per-compressor)

These run in `ContextManager::prepare()` regardless of which compressor is
installed, and are the safety net that makes the "NOT aware" entries above
survivable:

| Invariant | Enforcement | Source |
|---|---|---|
| Protected markers survive | `split_protected` removes them before compression; `merge_protected` reinserts by relative position | `mod.rs:747-793` |
| Replaceable markers: latest-wins | `push()` retains only the newest message containing the marker | `mod.rs:380-388` |
| Canonical context re-injection | `reinject_canonical_context` restores system prompt / rules / skills with dedup | `mod.rs:877-929` |
| Tool-call pairing validity | `sanitize_tool_call_pairing` runs unconditionally after every compression + on session resume | `mod.rs:1448-1459, 1562-1709` |
| Summary P0 quality | `verifier::verify_compression` runs when a summary was produced; on P0 fail, SlidingWindow(40) fallback re-compresses from original | `mod.rs:1464-1523` |
| Memory promotion | evicted messages → `MemoryPromoter` (if configured) | `mod.rs:1358-1367` |

- Log/artifact: none.

## Deviations

- The matrix shows that only **VisibilityHorizon** is inherently tool-pair
  aware. All other compressors rely on `sanitize_tool_call_pairing` to repair
  orphaned calls/results after compression. This is a design choice (sanitize
  is the single choke point), not a defect — see V02 for the detailed
  correctness analysis of that safety net.
- IncrementalSummary's state is per-instance (`Mutex` inside the compressor
  struct), not per-session or per-ContextManager. This means a session
  restore that rebuilds the ContextManager loses the incremental summary
  state. Documented under V03.

## Conclusion

The claim is **supported**. There is one canonical `ContextCompressor` trait
with six implementations, each preserving a distinct, documented invariant
set, and no parallel authority. The framework-level invariants (protected
markers, canonical re-injection, sanitize, verifier) form a robust safety net
that compensates for the fact that most compressors are not individually
tool-pair-aware.

The compressor matrix, framework-invariant table, and duplicate-search
results here are stable inputs that downstream validations (V02–V04) and
downstream tasks (F-CTX-01 handoff, F-MEM-01 memory promotion) can rely on.
