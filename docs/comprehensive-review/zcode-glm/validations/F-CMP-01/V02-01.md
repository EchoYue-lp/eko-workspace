## Claim

Tool call/result pairs are kept together after compression. Orphaned tool
calls (assistant references a `tool_call_id` with no matching result) and
orphaned tool results (result without a matching assistant `tool_call`) are
detected and repaired so the final message sequence is protocol-valid for
OpenAI-compatible APIs.

## Expected Result

1. Every compressor path that can split a tool call/result pair is followed
   by `sanitize_tool_call_pairing`, which repairs the sequence.
2. Three repair cases are handled: orphaned results removed, fully-dangling
   calls cleared, partial-dangling calls get placeholder results.
3. The final sequence satisfies: every assistant `tool_calls` entry has a
   matching `tool` result, and every `tool` message has a matching preceding
   assistant `tool_call`.

### sanitize_tool_call_pairing repair matrix (mod.rs:1562-1709)

The function performs two passes:

**Pass 1** (`:1577-1588`): collect `assistant_tool_calls: HashMap<msg_index,
HashSet<tool_call_id>>` and `available_results: HashSet<tool_call_id>`.

**Pass 2** (`:1608-1708`): build the sanitized sequence:

| Case | Condition | Action | Fix type recorded |
|---|---|---|---|
| Assistant, ALL calls orphaned | `tc_ids.all(\|id\| !available_results.contains(id))` | `cleaned.tool_calls = None`; push as regular assistant | `DanglingCallCleared` per id |
| Assistant, SOME calls orphaned | at least one id in `available_results` | push as-is; collect missing ids into `pending_placeholders` | `PlaceholderResultInserted` (flushed before next non-Tool msg or at end) |
| Assistant, no orphaned calls | all ids in `available_results` | push as-is | none |
| Tool result, orphaned | `!all_referenced.contains(id)` or `tool_call_id` is None | **drop** the message | `OrphanedResultRemoved` |
| Tool result, referenced | id in `all_referenced` | push as-is | none |
| Non-tool/assistant (user/system) | — | push as-is; flush pending placeholders first | — |

Placeholder content (`:1618-1619`):
```text
"[Result unavailable — tool result was removed during context compression]"
```

This is a valid `Message::tool_result(id, "unknown", placeholder_text)` that
satisfies the OpenAI protocol requirement.

## Deviations

**L1 Fold ordering edge case (Adaptive only, not default).** When L1 Fold
collapses consecutive tool results (`levels.rs:364-403`), it inserts a
`Message::user("[L1 fold: ...]")` at the position of the first removed
result. If the owning assistant had calls `[tc1, tc2, tc3]` and `tc1` is
folded while `tc2, tc3` are kept, the post-fold sequence is:

```text
assistant(tc1,tc2,tc3) → user(fold) → tool(tc2) → tool(tc3)
```

After sanitize flushes the pending placeholder for `tc1` (triggered by the
non-Tool user message), the result becomes:

```text
assistant(tc1,tc2,tc3) → tool(placeholder tc1) → user(fold) → tool(tc2) → tool(tc3)
```

Every call now has a result (protocol-valid), but the tool results are split
by a user message. The OpenAI Chat Completions spec expects tool messages to
immediately follow the assistant message that issued the calls. Some provider
implementations may reject a user message between tool results. Impact is
low: this only occurs when `AdaptiveCompressor` with `l1_fold_consecutive_tools`
fires (not the default configuration; default is SlidingWindow or Summary),
and only when the fold boundary lands inside a multi-call result group.
Tracked as **F-CMP-01-P3-02**.

The claim is **supported**. Tool call/result pairs are kept protocol-valid
