## Claim

When compression runs multiple times (as it does every turn once the token
threshold is crossed), the system converges: re-compression does not lose
additional information beyond the first pass, and the context size stays
bounded.

## Expected Result

1. Re-running the same compressor on its own output does not evict
   additional messages (idempotent for count-based compressors).
2. No unbounded accumulation of metadata messages (summaries, fold markers,
   horizon compacts) across repeated compression cycles.
3. The token count of the compressed buffer stays bounded as the
   conversation grows.

## Result

- Exit code: 0 (the existing idempotency test passes)
- Summary: Claim **partially supported**. SlidingWindow, Horizon, and
  Adaptive count-based levels are idempotent. But **Summary and
  IncrementalSummary accumulate summary system messages across cycles** —
  each compression adds a new `[对话历史摘要]` system message without
  removing the previous one, causing unbounded growth in the system region.

### Per-compressor convergence analysis

#### SlidingWindow — CONVERGES (idempotent)

Cycle 1: `[sys] [m1..m50]` → evict m1..m10 → `[sys] [m11..m50]` (window=40).
Cycle 2 (no new messages): `conv_msgs.len() (40) <= window_size (40)` →
early return, no eviction (`sliding_window.rs:48-66`).

Confirmed by `invariant_compression_idempotent` (`invariants.rs:340-367`):
`count1 == count2` after re-compression.

#### Summary — DOES NOT CONVERGE (summary accumulation)

Trace of two cycles with `keep_recent=6`:

```text
Cycle 1 input:  [sys] [m1..m20]
  partition:    system_msgs=[sys], conv_msgs=[m1..m20]
  split_at=14:  to_summarize=[m1..m14], to_keep=[m15..m20]
  output:       [sys] [summary_S1] [m15..m20]                    ← summary.rs:346-348

Cycle 2 input:  [sys] [summary_S1] [m15..m20] [m21..m28]  (8 new msgs added)
  partition:    system_msgs=[sys, summary_S1], conv_msgs=[m15..m28]
  split_at=8:   to_summarize=[m15..m22], to_keep=[m23..m28]
  output:       [sys] [summary_S1] [summary_S2] [m23..m28]       ← S1 NOT removed

Cycle 3 input:  [sys] [S1] [S2] [m23..m28] [m29..m34]
  partition:    system_msgs=[sys, S1, S2], conv_msgs=[m23..m34]
  output:       [sys] [S1] [S2] [S3] [m29..m34]                  ← S1, S2 still present
```

Root cause (`summary.rs:292-297, 346-348`): the compressor partitions by
`role == Role::System`. The previous summary is a `Message::system(...)`
(`:347`), so it lands in `system_msgs` and is preserved verbatim. The new
summary is appended after `system_msgs`. Nothing in `prepare()`,
`merge_protected`, `sanitize_tool_call_pairing`, or
`reinject_canonical_context` removes old summary system messages.

The `reinject_canonical_context` dedup (`mod.rs:914-921`) only matches
canonical context (project rules, active skills) — it does not match
`[对话历史摘要]` envelopes.

After N compression cycles, the system region contains N summary messages.
At ~500–2000 tokens per structured summary, 20 cycles add 10K–40K tokens of
accumulated summaries — partially defeating compression's purpose and
growing without bound.

#### IncrementalSummary — SAME ACCUMULATION (despite field-level merge)

`IncrementalSummaryCompressor` was designed to avoid re-summarizing from
scratch: it keeps a `Mutex<Option<StructuredSummary>>` and merges field-by-
field (`summary.rs:497-585, 639-665`). This correctly prevents information
*drift* within the summary content.

But the output assembly is identical to Summary (`summary.rs:684-686`):

```rust
let mut messages = system_msgs;     // includes the PREVIOUS summary system msg
messages.push(Message::system(final_text));  // appends NEW summary
messages.extend(to_keep);
```

So the previous summary system message persists in `system_msgs` and a new
one is appended. After N cycles: N summary system messages in the buffer,
even though the Mutex-held `StructuredSummary` is a single merged object.

The Mutex state is also per-compressor-instance, not per-session: a session
restore that rebuilds the `ContextManager` (and re-creates the compressor)
loses the incremental state, falling back to a full first-time summary
(`summary.rs:639-646`).

#### Hybrid — depends on stages

`summary_buffer()` (`hybrid.rs:183-196`) = `[Summary, SlidingWindow]`. The
Summary stage accumulates as above. The SlidingWindow stage operates on the
Summary stage's output, but since summaries are system messages, SlidingWindow
preserves them all (system messages are partitioned out and kept).

Short-circuit (`hybrid.rs:66-83`) compares the compressor's internal
heuristic token count against `token_limit`. Once summaries accumulate, the
token count stays high, so short-circuit may not fire — but the Summary stage
keeps adding summaries regardless. Convergence depends on whether the
SlidingWindow stage's count-based eviction eventually removes enough non-
system messages to bring conv_msgs under `keep_recent`. It does not remove
summaries.

#### VisibilityHorizon — CONVERGES

`compact_horizon` (`horizon.rs:129-193`) replaces tool groups with symbolic
summaries and strips `tool_calls` from the assistant. Once a group is
compacted, re-running finds no `tool_calls` on that assistant → it is not
re-identified as a tool group → no double-compaction. The Global Objective,
if injected (`:313-330`), is deduplicated by the `[Global Objective]` marker
check (`:318-326`).

Confirmed by `test_30_round_integration` and `test_50_turn_token_stability`
(`horizon.rs:778-927`): token growth is sub-linear and compact summaries
count matches the expected group count.

#### Adaptive — MOSTLY CONVERGES

L1 Snip (`levels.rs:337-360`) is idempotent: already-short outputs are not
re-snipped. L1 Fold (`:364-403`) is idempotent: a folded sequence has a
user message breaking the tool run, so re-running finds a shorter run. L2
Micro (`:406-432`) is idempotent: already-truncated outputs have fewer lines.
L3 Collapse (`:436-475`) and L5 Reactive (`:590-635`) are count-based and
idempotent if no new messages arrive.

However, L3/L5 add marker system messages (`:464-470`, `:619-622`) —
`[Context compressed: N older messages removed]` and `[Emergency
compression: ...]`. These are system messages and accumulate across cycles
(same mechanism as the Summary accumulation). The volume is smaller (one
short sentence per cycle), but the pattern is the same.

### Existing idempotency test scope

`invariant_compression_idempotent` (`invariants.rs:340-367`) only tests
`SlidingWindowCompressor` directly (not via `ContextManager::prepare()`),
and only checks `count1 == count2` for message count. It does not catch
summary accumulation because:

1. It uses SlidingWindow, not Summary.
2. It calls `compressor.compress()` directly, bypassing `prepare()`'s
   system-message handling.
3. It checks message count, not the count of summary system messages.

- Log/artifact: none.

## Deviations

- The claim's third expectation ("token count stays bounded") fails for
  Summary-based compressors (the YAML default is `"summary"` per
  `src/config.rs:482`). The accumulation is slow (one summary per
  compression-triggering turn) but unbounded.
- SlidingWindow (the fallback and the hardcoded default when no LLM is
  configured, `src/agent/react/mod.rs:349-353`) does not have this issue.

## Conclusion

The claim is **not fully supported**. SlidingWindow, Horizon, and Adaptive
count-based levels converge. But **Summary and IncrementalSummary do not**:
each compression cycle appends a new summary system message without removing
the previous one, causing unbounded growth in the system region. This is a
P2 defect (**F-CMP-01-P2-01**) because:

- The YAML default is `compress_strategy = "summary"`.
- `prepare()` runs every turn, so compression can trigger every turn.
- The system region is never capped (no `max_messages` by default; even with
  it, `apply_hard_cap` only removes non-system messages).
- After ~20 compression cycles, accumulated summaries consume 10K–40K tokens
  that compression was supposed to free.

The existing idempotency test does not catch this because it tests
SlidingWindow in isolation, not Summary via `prepare()`.
