## Claim

Compressors handle multilingual (CJK) content without panics, large tool
schemas do not distort compression decisions, and token estimation is
consistent between the `ContextManager` (which decides when to compress)
and the compressors (which decide how to compress).

## Method

compressors, the `HeuristicTokenizer` algorithm, CJK-safe truncation
helpers, and the `current_query` plumbing. Cross-checked against the CJK
truncation tests and the tokenizer tests.

## Expected Result

1. No UTF-8 panic on CJK or emoji content (per AGENTS.md Rust constraint #1).
2. All truncation uses `chars()`-based iteration, never byte slicing.
3. Compressors use the same tokenizer as the `ContextManager` so compression

4. `current_query` is used to protect the active task/query from eviction

### CJK / UTF-8 safety — PASS

`HeuristicTokenizer` (`echo-core/src/tokenizer.rs:50-58`):

```rust
let weight: usize = text.chars().map(|c| if c.is_ascii() { 1 } else { 2 }).sum();
(weight / 4).max(1)
```

Uses `chars()` (Unicode scalar values), never byte slicing. ASCII weight 1,
CJK weight 2 — CJK-aware estimation (~40-60% more accurate than `bytes/4`
for Chinese per the docstring). Empty string returns 0.

`safe_truncate` (`levels.rs:23-35`) walks `char_indices` backwards to find
the nearest char boundary — never slices mid-character:

```rust
let end = s.char_indices()
    .map(|(i, c)| i + c.len_utf8())
    .take_while(|&end| end <= max_bytes)
    .last()
    .unwrap_or(0);
&s[..end]
```

Confirmed by `test_safe_truncate_cjk_no_panic` and `test_l1_snip_cjk_no_panic`
(`levels.rs:762-797`): CJK content that would fall mid-character is handled
correctly.

Horizon's error-preview truncation uses `content.chars().take(100).collect()`
(`horizon.rs:232`) and `errors[0].chars().take(60)` (`horizon.rs:280`) — both
CJK-safe.

Summary prompts are in Chinese (`COMPRESSION_PROMPT` at `summary.rs:18-35`),
so Chinese conversations get native-language summarization instructions.

Tokenizer tests: 12 passed, 0 failed at `9b0e0fa`.

### Tokenizer divergence — FAIL (F-CMP-01-P2-02)

Every compressor hard-codes `HeuristicTokenizer` for its internal token
counting:

| Compressor | Internal tokenizer | ContextManager's tokenizer |
|---|---|---|
| SlidingWindow | `HeuristicTokenizer` (`sliding_window.rs:32`) | `CalibratedTokenizer(HeuristicTokenizer)` (`mod.rs:1827`, wired at `react/mod.rs:333-335`) |
| Summary | `HeuristicTokenizer` (`summary.rs:284, 596`) | same |
| IncrementalSummary | `HeuristicTokenizer` (`summary.rs:596`) | same |
| Hybrid | `HeuristicTokenizer` struct field (`hybrid.rs:40, 166`) | same |
| VisibilityHorizon | `Box<HeuristicTokenizer>` (`horizon.rs:115-116, 122`) | same |
| Adaptive | `HeuristicTokenizer` struct field (`levels.rs:134, 143`) | same |

The `ContextManager` uses `self.tokenizer` (the configured, possibly-
calibrated tokenizer) for `estimate_tokens` (`mod.rs:1295, 1541-1547`),
which drives `needs_compression` and `effective_limit`. But once compression
fires, the compressor uses its own uncalibrated `HeuristicTokenizer` for:

- Checkpoint `token_before` / `token_after` (all compressors).
- Adaptive threshold comparisons (`levels.rs:186, 207, 216, 226, 301, 316` —
  `tokens > self.config.l1_snip_threshold_tokens` etc.).
- Hybrid short-circuit decision (`hybrid.rs:73` — `current_tokens <= token_limit`).

Consequences:

1. **Adaptive thresholds drift.** `tune_for_model` (`levels.rs:107-114`)
   sets thresholds as percentages of the context window (e.g. L1 at 60% of
   200K = 120K). These are real-token thresholds. But the comparison uses
   `HeuristicTokenizer` output, which may diverge from real tokens by
   ±30-50% (and is never calibrated by API feedback). So L1 may trigger too
   early (wasting detail) or too late (risking OOM).

2. **Hybrid short-circuit may misfire.** The short-circuit at `hybrid.rs:66-83`
   compares the uncalibrated heuristic count against `token_limit` (which
   came from the calibrated ContextManager path). If calibration factor is
   1.3 (real tokens are 30% higher than heuristic), the short-circuit fires
   too late — later stages run unnecessarily. If factor is 0.8, it fires too
   early — insufficient compression.

3. **Checkpoint token counts are inconsistent with `/context` observability.**
   The `ContextManager::token_estimate()` uses the calibrated tokenizer, but
   `CompressionCheckpoint.token_before/after` use the uncalibrated one. A
   user inspecting compression stats sees different numbers than the
   `/context` command reports.

### `current_query` is plumbed but unused — FAIL (F-CMP-01-P2-03)

`CompressionInput.current_query` is documented as:

> Current user query — used to protect active task context from eviction
> (`echo-core/src/compression.rs:45-46`)

But `prepare()` passes it through (`mod.rs:1342`), and **no compressor reads
it**:

| Compressor | Reads `current_query`? | Evidence |
|---|---|---|
| SlidingWindow | no | `sliding_window.rs` — field not referenced |
| Summary | no | uses `focus_instructions` instead (`summary.rs:323`) |
| IncrementalSummary | no | same (`summary.rs:635`) |
| Hybrid | only as checkpoint fallback | `hybrid.rs:118` — `.with_focus(focus_instructions.or(current_query))` (observability only, not eviction protection) |
| VisibilityHorizon | no | `horizon.rs` — field not referenced |
| Adaptive | no | `levels.rs` — field not referenced |

The `prepare()` docstring at `mod.rs:1239` even admits it: "`current_query`
is a reserved field; pass `None`."

The only protection for the active query is coincidental: SlidingWindow and
Summary both keep the LAST `window_size` / `keep_recent` messages, which
includes the most recent user turn. But there is no guarantee that earlier
turns relevant to the active task (e.g. "refactor auth module" stated 5
turns ago) survive — they fall into the evicted/summarized portion with no
query-aware priority.

The verifier's `check_last_query_presence` (`verifier.rs:134-190`) checks
that keywords from the last user message appear in the compressed output,
but only at 50% keyword threshold, only for keywords >3 chars (byte length,
not char length — see F-MEM-01-P3-01 for the same pattern), and only when
a summary was produced (SlidingWindow output is never verified).

### Horizon byte-length inconsistency — minor (F-CMP-01-P3-01)

`horizon.rs:295`:

```rust
let max_chars = self.config.compact_max_tokens * 4; // rough chars→tokens
if summary.len() > max_chars {                        // summary.len() = BYTES
```

For a CJK summary, `summary.len()` returns bytes (3 bytes per CJK char),
while the HeuristicTokenizer would estimate ~0.5 tokens per CJK char. So a
50-token CJK summary is ~150 bytes, and `max_chars = 50 * 4 = 200` — the
check passes (150 < 200), but the actual token cost is only ~25 tokens
(150 bytes / 6 bytes-per-token-heuristic). The comparison is semantically
inconsistent but not catastrophic: the fallback branch (`:297-306`) produces
a shorter summary, so the worst case is slightly over-aggressive truncation
of CJK summaries. No panic (it's a `>` comparison on `usize`, and the
fallback uses `tool_names.len()` not slicing).

## Deviations

- The tokenizer-divergence issue is structurally identical to the
  `ContextAssembler` divergence documented in F-CTX-01-P3-02 (different
  code paths using different estimators). F-CTX-01-P3-02 is off the hot
  path; this one is on every compression-triggering turn.
- `current_query` being unused is a pre-existing API-design gap, not a
  regression. The field was added with the right intent but never wired
  into eviction logic.

## Conclusion

The claim is **not fully supported**. Two defects exist:

1. **F-CMP-01-P2-02**: All compressors hard-code `HeuristicTokenizer`,
   diverging from the `ContextManager`'s calibrated tokenizer. This affects
   Adaptive threshold accuracy, Hybrid short-circuit correctness, and
   checkpoint/observability consistency.
2. **F-CMP-01-P2-03**: `current_query` is unused — no query-aware eviction
   protection exists despite the field's documented purpose.

CJK content is handled safely (no panics, char-aware truncation and counting
throughout — positive confirmation). The horizon byte-length inconsistency
(F-CMP-01-P3-01) is minor and CJK-safe.
