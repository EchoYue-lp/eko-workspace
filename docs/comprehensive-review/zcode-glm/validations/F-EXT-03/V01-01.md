## Claim

The data/research/media/database/web/rag/chart/statistics domain tools are
cleanly partitioned behind Cargo features, every feature maps to exactly one
module group in `lib.rs`, and `registry.rs` registers each tool under the
correct feature gate with a consistent read-only vs writer split. No tool is
registered under the wrong feature, and no two feature gates register
conflicting definitions of the same tool.

## Method

Static inspection of the feature manifest, the `lib.rs` cfg-gated module map,
and the two registration functions. Cross-checked each `pub use` / `use`
import against the module that defines the tool struct.

```text
1. Read echo-agent/echo-tools/Cargo.toml [features] table.
2. Read echo-agent/echo-tools/src/lib.rs module cfg-gates.
3. Read echo-agent/echo-tools/src/registry.rs::register_all_tools and
   register_readonly_tools.
4. Grep echo-tools/src for each tool struct name to confirm single definition.
```

## Expected Result

- 11 user-facing features (`web chart data database media git rag shell files
  research statistics`) plus the `full` aggregate and empty `default`.
- Each `pub mod` in `lib.rs` is gated by exactly one feature matching the
  manifest.
- `statistics` reuses `data` (per Cargo.toml `statistics = ["data"]`), so the
  exploratory-statistics tool depends on polars transitively.
- `register_all_tools` and `register_readonly_tools` reference only
  feature-gated modules and never construct a writer tool in the read-only
  function.

- Dependency notes:
  - `Cargo.toml:34` `statistics = ["data"]` — `statistics` enables `data`
    transitively; `lib.rs:13` documents this.
  - `Cargo.toml:31` `media` pulls in `encoding_rs` and `html2text`, which are
    also optional under `web`/`files` — shared deps, not shared gates.
  - `registry.rs:328-332` registers `ExcelLoadTool` only when both `media` and
    `data` are enabled (it bridges calamine → polars). Correctly
    double-gated.

- Read-only vs writer split (`registry.rs:21-193`):
  - `register_readonly_tools` excludes `run_code`, all write/edit/delete/move
    file tools, `git commit/branch/worktree-enter`, `ExcelWriteTool`, and
    `DataExportTool`. Confirmed by the two `#[test]`s at `registry.rs:426-463`
    asserting `run_code` presence in all and absence in readonly.
  - Note `registry.rs:76-80`: `SqlQueryTool` is intentionally kept in the
    read-only subset despite being capable of `INSERT/UPDATE`. The comment
    justifies this ("local analysis context, risk is low"); the actual
    write-protection is the `SET TRANSACTION READ ONLY` + keyword filter
    audited in V04.

- Duplicate search (names: `SqlQueryTool`, `WebFetchTool`, `ImageFetchTool`,
  `DataReadTool`, `RagSearchTool`, `ArxivSearchTool`,
  `ExploratoryStatisticsTool`, `GenerateChartTool`):
  - Each is defined exactly once in `echo-tools`.
  - One naming overlap: `media::web_fetch_enhanced::WebFetchToolEnhanced`
    (`registry.rs:96,311`) vs `web::WebFetchTool` (`registry.rs:85,299`). Both

  - `media::image_fetch::ImageFetchTool::new()` is fallible and registered

    `#[allow(dead_code)]`-tagged at the struct (`image_fetch.rs:16`) pending
    "media pipeline stable" (TODO v0.3), but it IS on the registered path
    when `media` is on.

## Deviations

- `ImageFetchTool` carries `#[allow(dead_code)]` on the struct and several
  methods (`is_image_url`, `download_image_as_base64` at `image_fetch.rs:46,
  70`), yet `execute` is live and the tool is registered. The `dead_code`
  allow is scoped to the unused helpers, not the tool itself — but the tag on
  the struct is broader than necessary. Recorded as task finding
  F-EXT-03-P3-03 (one of those dead helpers bypasses SSRF).
- `Cargo.toml:17` `full` deliberately omits `shell` and `files`:
  `full = ["web","chart","data","database","media","git","rag","shell",
  "files","research","statistics"]` — re-reading, `shell` and `files` ARE in
  `full`. Correction: all 11 features are in `full`. No deviation.

## Conclusion

The feature/capability map is coherent and honest. Every domain module is
behind exactly the feature its dependencies require; `registry.rs` constructs
each tool under the correct gate; the read-only/writer split is intentional
and tested. The only map-level concern is the `#[allow(dead_code)]` scope on
`ImageFetchTool` (followed up in V03 / F-EXT-03-P3-03), not a misregistration.
Supports the task's V01 claim and underpins the per-tool findings in V02–V04.
