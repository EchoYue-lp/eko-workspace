## Claim

The database and RAG tools (audit references 1.1 / 1.12 SQL-injection) handle
connections safely, prevent SQL injection through a layered defense,
validate connection URL schemes, preserve retrieval provenance, and bound
in-memory state. They do not panic on empty / single-row / oversized inputs.

## Method

Static inspection of `database.rs` (full file) and `rag.rs` (full file),
plus the shared pagination cursor (`echo-core/src/tools/pagination.rs`) that
`sql_query` depends on. For SQL injection, trace every site that builds a SQL
string and confirm each is either parameterized, validated, or quote-escaped.

```text
1. Read echo-agent/echo-tools/src/database.rs (full).
2. Read echo-agent/echo-tools/src/rag.rs (full).
3. Read echo-agent/echo-core/src/tools/pagination.rs (full) — cursor envelope
   + fingerprint binding.
4. For describe_table: confirm table_name validation + quote escaping.
5. For sql_query: enumerate the three defense layers.
```

## Expected Result

- `validate_db_url` rejects every scheme except `sqlite`, `mysql`,
  `postgresql`, `postgres` and null/newline chars in SQLite paths.
- `sql_query` blocks mutations through (a) statement-prefix allowlist, (b)
  dangerous-keyword denylist, (c) `SET TRANSACTION READ ONLY` for non-SQLite,
  and (d) sqlx single-statement execution semantics.
- `describe_table` parameterizes or escapes the table name.
- `sql_query` cursor is bound to the connection URL + query snapshot and
  refuses to advance when either changes.
- `rag_search` returns the source identifier with every chunk; cosine
  similarity is finite; `VectorStore` bounds memory.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:

  **Database (`database.rs`)** — three-layer write protection confirmed:
  - Layer 1 — statement-prefix allowlist (`database.rs:119-132`): only
    `SELECT`, `SHOW`, `DESCRIBE`, `DESC `, `EXPLAIN`, `WITH` accepted.
  - Layer 2 — dangerous-keyword denylist (`database.rs:134-170`): blocks
    `INSERT/UPDATE/DELETE/DROP/ALTER/CREATE/TRUNCATE/GRANT/REVOKE/REPLACE/
    EXECUTE/EXEC/INTO OUTFILE/INTO DUMPFILE/LOAD_FILE/DBLINK/LO_IMPORT/
    PG_TERMINATE_BACKEND/PG_CANCEL_BACKEND/PG_RELOAD_CONF/COPY/PRAGMA` even
    when embedded in a `SELECT`.
  - Layer 3 — `SET TRANSACTION READ ONLY` (`database.rs:432-458`): for MySQL
    and PostgreSQL, the query runs inside an explicit transaction that the
    database itself enforces as read-only; the transaction is rolled back
    (`database.rs:457`). SQLite skips this (it has no READ ONLY tx) but is
    protected by layers 1+2 and by `sqlx::query` executing a single prepared
    statement (no multi-statement injection).
  - Schema-validation safety: `describe_table` validates `table_name` to
    `[A-Za-z0-9_.]` only (`database.rs:306-314`) and additionally escapes
    single quotes via `replace('\'', "''")` (`database.rs:318, 325, 334`).
    Combined, this defeats SQL injection through the table-name parameter
    (audit 1.1/1.12 closed for this surface).
  - Connection URL scheme: `validate_db_url` (`database.rs:352-388`) accepts
    only the four documented schemes; for SQLite it also rejects `\0`/`\n`/
    `\r` in the path.
  - Pagination: cursor via `PageRequest` + `PageInfo` (`database.rs:107-114,
    178-189`); the cursor envelope is bound to the SHA-256 fingerprint of
    `{connection_url, query, limit, rows snapshot}` (`pagination.rs:120-169,
    198-216`), so a cursor from one query/connection is rejected with
    `CursorQueryMismatch` when replayed against another.
  - Oversized output spills to an artifact (`database.rs:494-537`); inline
    cells are truncated by `chars().take(MAX_INLINE_CELL_CHARS)`
    (`database.rs:586-592`) — UTF-8 safe.
  - `ensure_drivers_installed` (`database.rs:34-42`) installs sqlx drivers
    exactly once via `OnceLock`, avoiding the "No drivers installed" panic
    that sqlx 0.8 `any` mode would otherwise hit.

  **RAG (`rag.rs`)** — sound, with one contract-honesty caveat:
  - `cosine_similarity` (`rag.rs:79-91`) returns `0.0` for empty/mismatched
    vectors and for zero-norm vectors — no `NaN`, no division by zero.
  - `VectorStore::add_chunks` (`rag.rs:46-53`) evicts oldest chunks once
    `MAX_CHUNKS = 10_000` is exceeded — bounded memory, FIFO eviction.
  - Provenance: `DocumentChunk.source` (`rag.rs:26`) is carried from
    `rag_index` through to `rag_search` results (`rag.rs:402`), so every
    retrieved chunk reports its origin file/URL.
  - `rag_index` / `rag_chunk_document` handle empty content gracefully
    (`rag.rs:273-277, 475-477`).
  - Contract caveat (F-EXT-03-P3-04): the `overlap` parameter is accepted by
    `rag_index` and advertised in its description (`rag.rs:238-241`) but is
    passed to `chunk_by_sentences` where it binds to `_overlap`
    (`rag.rs:134`) and is discarded. `chunk_text` itself ignores overlap
    entirely. The tool produces non-overlapping chunks regardless of input.
  - Minor (not promoted to a finding): `chunk_size` has no lower clamp; a
    user-supplied `0` does not panic (sentence-end boundary logic absorbs
    it) but yields one chunk per sentence. The description does not promise a
    minimum, so this is a robustness niceness, not a contract violation.

- Log/artifact: none

## Deviations

- `execute_readonly_query` opens a fresh `AnyPool` per call
  (`database.rs:412-419`) with `max_connections(1)` and drops it on return.
  This is correct for a stateless per-call tool (no connection leak), but it
  pays the connect/handshake cost on every invocation. For a local analysis
  assistant this is acceptable; flagged as coverage/uncertainty, not a
  finding.
- The `connection_url` (which may embed `mysql://user:pass@host/db`) is placed
  into `query_identity` (`database.rs:174-177`) and fed to the pagination
  fingerprint. It is SHA-256-hashed inside `query_fingerprint`
  (`pagination.rs:198-216`) and never serialized into the cursor or the tool
  result, so the password is not leaked to the agent. No finding.

## Conclusion

The claim **passes**. The SQL-injection surface (audit 1.1/1.12) is defended
by three independent layers and the table-name path is additionally
validated and escaped. Cursor pagination is correctly bound to the query
identity and result snapshot. RAG is numerically safe and preserves
provenance. The only defect is the advertised-but-ignored `overlap`
parameter in `rag_index` (F-EXT-03-P3-04).
