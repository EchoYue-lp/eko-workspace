`GLOBAL_EVENT_BUS` is the live distribution hub it claims to be
(`echo-agent/src/event_bus.rs:42-45`).

## Method

Grep both repositories for every producer and consumer of `EventEnvelope`,
`envelope_event_stream`, `envelope_event_stream_after`, `EventEnvelope::new`,
`EventBus`, and `GLOBAL_EVENT_BUS`. Exclude test modules and the definition
file itself.

```text
grep -rn "GLOBAL_EVENT_BUS" --include="*.rs" echo-agent echo-agent-cli
grep -rn "envelope_event_stream|EventEnvelope::new|envelope_event_stream_after" --include="*.rs"
grep -rn "EventBus::new|EventBus::default|\.subscribe\(\)|\.subscriber_count" --include="*.rs"
```

## Expected Result

Producers exist in both repos; at least one subscriber to
`GLOBAL_EVENT_BUS` from the application layer; per-run streams route through

## Deviations

The doc comment at `event_bus.rs:1-4` and the comment at
`event_bus.rs:42-45` advertise a unified, multi-subscriber transport. Code
reality: never used. This contradicts the bus's stated purpose and
constitutes a misleading public API.

## Conclusion

`EventEnvelope`/`envelope_event_stream` itself has a healthy, reachable
producer-consumer graph (5 production call sites + tests). The
`GLOBAL_EVENT_BUS` / `EventBus` infrastructure is **not reachable at all**:
no producer, no consumer, no instantiation. Under AGENTS.md "code cleanup"
this qualifies as dead code that should be deleted, OR — if multi-sink
fan-out is genuinely needed — wired up. Used by finding
F-CORE-01-P2-01 (dead `GLOBAL_EVENT_BUS`/`EventBus`). Does not by itself
prove that all *intended* consumers receive every event, because no intended
multi-sink consumer exists in code today.
