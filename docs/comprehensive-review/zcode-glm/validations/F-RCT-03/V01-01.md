## Claim

The streaming event flow is a four-stage pipeline with a single
authoritative conversion path: provider SSE → `ChatCompletionChunk` →
`AgentEvent` (via `process_stream_chunk`) → `Result<AgentEvent>` on an
mpsc channel → consumer-wrapped `EventEnvelope`. Every `AgentEvent`
variant produced on the live path has exactly one production site, and
the framework streaming output is a raw `BoxStream<Result<AgentEvent>>`
— `EventEnvelope` wrapping is the consumer's responsibility, applied
outside the framework via `envelope_event_stream_after`.

## Expected Result

1. A single linear streaming pipeline with no parallel/sibling producer.
2. Each `AgentEvent` variant has exactly one production site reachable
   from `run_core_loop` (or its pre-loop short-circuits).
3. The framework returns `BoxStream<Result<AgentEvent>>`; the
   `EventEnvelope` layer is applied by the consumer, not the framework.

## Result

- Exit code: not-applicable (static inspection)
- Summary: the claim is supported.

### Stage 1 — Provider SSE → `ChatCompletionChunk`

`create_llm_stream` (`think.rs:261-393`) returns
`Pin<Box<dyn Stream<Item = Result<ChatCompletionChunk>> + Send>>`. Two
backends, both wrapped by `retry::retry_llm_call`:

- **LlmClient trait path** (`think.rs:285-351`): `llm_client.chat_stream`
  returns `Stream<Item = Result<ChatChunk>>`; mapped at `:334-344` back
  into the `ChatCompletionChunk` shape ("no information is lost" per the
  inline comment — both originate from the same OpenAI stream).
- **Legacy reqwest path** (`think.rs:353-392`): `crate::llm::stream_chat`
  returns `Stream<Item = Result<ChatCompletionChunk>>` directly.

### Stage 2 — `ChatCompletionChunk` → `AgentEvent`

Single conversion site: `process_stream_chunk` (`processor.rs:16-88`),
a pure function (`&self`-less, no I/O). Called once per chunk at
`think.rs:115-124`:

```text
for event in process_stream_chunk(
    &chunk, &mut content_buffer, &mut reasoning_buffer,
    &mut tool_call_map, &mut in_reasoning, /*emit_content_tokens=*/ false,
) {
    yield_event_or!(tx, event, ThinkOutcome::Abandoned);
}
```

`process_stream_chunk` returns `Vec<AgentEvent>` by inspecting
`chunk.choices.first()` (`processor.rs:26`):

- `delta.reasoning_content` non-empty → `ThinkStart` (on first) +
  `Token(reasoning)` (every chunk). Accumulated into `reasoning_buffer`.
- `delta.content` non-empty → `ThinkEnd` (when transitioning out of
  reasoning) + `Token(content)` only if `emit_content_tokens` is true.
  **On the live `run_think` path `emit_content_tokens=false`**
  (`think.rs:121`), so per-chunk content `Token` events are NOT emitted
  here; the full content is flushed as a single `Token` after the stream
  ends at `think.rs:241-245`. (DirectAnswer uses a different path — see
  below.) Accumulated into `content_buffer`.
- `delta.tool_calls` → accumulated into `tool_call_map: HashMap<u32,
  (id, name, args_buffer)>` by streaming-fragment index; **no event
  emitted here** (fragments are partial).

### Stage 3 — `AgentEvent` → `Result<AgentEvent>` on mpsc channel

Channel created at `stream_channel.rs:41`:
`mpsc::channel::<Result<AgentEvent>>(buffer)` where
`buffer = self.config.stream_buffer_size` (default 256,
`config.rs:235`). The `tx` end is moved into the spawned `run_core_loop`
task (`stream_channel.rs:302-312`); the `rx` end is returned as
`Box::pin(ReceiverStream::new(rx))` (`:314`).

Three send semantics (see V02 for the backpressure analysis):

- `yield_event_or!` (`stream_macros.rs:38-53`): `try_send`, drops on
  `Full` with a warn log. Used by 16 sites for non-terminal events
  (`ThinkStart`, `Token`, `ThinkEnd`, `LlmUsage`, `ToolBatchStart`,
  `ToolCall`, `ToolResult`, `ToolError`, `MemoryRecalled`,
  `ContextCompressed`, `BudgetDecision`).
- `yield_final_event!` / `yield_final_event_or!` (`:16-22, 56-62`):
  `send().await`, backpressure-aware. Used by 12 sites for terminal
  events (`FinalAnswer`) and tool-batch boundaries (`ToolBatchEnd`,
  `ToolStream`).
- `tx.try_send(Err(...))` (5 direct sites, see V03): error-forwarding,
  result discarded.

### Stage 4 — `Result<AgentEvent>` → `EventEnvelope` (consumer layer)

The framework's `Agent` trait streaming impls (`mod.rs:2780-2930`)
return the raw `BoxStream<'static, Result<AgentEvent>>` from
`run_stream_channel`. **No `envelope_event_stream` wrapping happens
inside the framework** — `ReactAgent` does not call
`envelope_event_stream` / `envelope_event_stream_after` anywhere
(grep: zero matches in `echo-agent/src`). The envelope layer is applied
by consumers (confirmed in F-CORE-01: `chat_driver.rs:538`,
`task_runtime/executor.rs:3743`, `a2a/server.rs:211-217` all call
`envelope_event_stream(raw_stream, event_identity)`).

### Pre-loop short-circuits (also produce terminal events)

`run_stream_channel` (`:35-316`) runs the same pre-flight checks as the
non-streaming `prepare_react_context` and may emit terminal events
without entering `run_core_loop`:

1. **Guard block** (`:141-179`): `tx.send(FinalAnswer("blocked…")).await`
   → finalize trace `Failed` → return `ReceiverStream`. No loop spawn.
2. **DirectAnswer shortcut** (`:185-246`): calls `direct_answer_stream`
   which streams `Token` + `LlmUsage` + terminal `FinalAnswer` via
   `send().await`, then finalizes the trace and returns.
3. **SkillRequired** (`:254-272`): activates a skill and falls through to
   the normal `run_core_loop` spawn.

The streaming test `stream_guard_block_yields_single_final_answer`
(`:874-913`) and `streaming_direct_answer_routes_through_projection_boundary`
(`:1327-1354`) pin (1) and (2). Both pass (V01 test run, exit 0).

## Deviations

1. `emit_content_tokens=false` on the live `run_think` path
   (`think.rs:121`) means per-chunk content `Token` events are suppressed
   inside the chunk loop; the full accumulated `content_buffer` is
   flushed as a single `Token` at `think.rs:241-245` after the stream
   ends. This is a **deliberate batching choice** (the inline comment at
   `processor.rs:51` documents the flag), not a defect — but it means the
   "streaming" UX for the full ReAct path delivers content as one
   post-stream burst rather than per-token. DirectAnswer
   (`stream_channel.rs:405-414`) does emit per-chunk content `Token`s,
   so the two streaming sub-paths differ in token granularity. Not a
   correctness issue; flagged for V04 conformance note.
2. `AgentEvent::Cancelled` is in the enum and `is_terminal()`
   (`mod.rs:331-336`) returns true for it, but **no code path in
   `run_core_loop` or `run_stream_channel` ever emits it**. See V03-01
   for the cancellation-terminal analysis.

## Conclusion

The claim is **supported**. The streaming event flow is a single
four-stage pipeline: SSE → `ChatCompletionChunk` → `AgentEvent` (one
pure converter) → `Result<AgentEvent>` on mpsc → consumer-wrapped
`EventEnvelope`. Every `AgentEvent` variant has exactly one production
site; no parallel/sibling producer exists. The framework returns raw
`Result<AgentEvent>` streams and leaves envelope wrapping to the
consumer, exactly as F-CORE-01 established.

The two deviations (content-token batching in full ReAct, and the
never-emitted `AgentEvent::Cancelled`) are real behavioural notes but do
not invalidate the single-pipeline / single-site claims. They feed V03
and V04.
