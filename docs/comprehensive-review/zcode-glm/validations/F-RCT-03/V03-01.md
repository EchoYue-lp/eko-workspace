## Claim

Terminal ownership on the streaming path is **split across two
mechanisms with different strength guarantees**:

1. **Success terminals** (`FinalAnswer`) use blocking `send().await` and
   are guaranteed to reach the consumer (or the loop exits gracefully if
   the receiver is gone). Exactly one success terminal per stream.
2. **Error terminals** (`Err(NoResponse)`, `Err(MaxIterations)`,
   intervention cancel/block) use non-blocking `try_send` and can be
   **silently dropped** when the buffer is full — the consumer then sees
   the stream end with `None` and **no terminal signal at all**.
3. **Cancellation via `CancellationToken`** (the `chat_stream_with_cancel`
   contract) produces **no terminal event** on ReactAgent's stream —
   `AgentEvent::Cancelled` is never emitted because ReactAgent overrides
   the trait default and does not wrap with `cancel_aware_stream`. The
   stream simply ends.

The success-terminal half is sound; the error-terminal and
cancellation-terminal halves violate the "exactly one terminal per
stream" expectation.

## Expected Result

- Exactly one terminal event per stream, regardless of success/failure/
  cancel.
- Terminal events are delivered (not droppable under backpressure).
- The cancellation contract (`AgentEvent::Cancelled`) is honoured by
  the concrete agent implementation, not just the trait default.

## Result

- Exit code: not-applicable (static inspection)
- Summary: the claim is supported on all three halves — and halves (2)
  and (3) are defects against the terminal-guarantee criterion.

### (1) Success terminals — sound, exactly-one

The three `FinalAnswer`-emitting arms (F-RCT-02 V02-01 T1/T2/T9, plus
the DirectAnswer and guard-block short-circuits) all use blocking sends:

| Arm | Site | API | Strength |
|---|---|---|---|
| T1 `finalize_completed_run` (tool success) | `finalize.rs:87` | `yield_final_event!` → `send().await` | guaranteed |
| T2 `emit_final_text` (text success) | `finalize.rs:179` | `tx.send().await` | guaranteed |
| T9 `prepare_turn` BlockedAndDone | `prepare.rs:68` | `yield_final_event_or!` → `send().await` | guaranteed |
| guard block (pre-loop) | `stream_channel.rs:163` | `tx.send().await` | guaranteed |
| DirectAnswer shortcut | `stream_channel.rs:478` | `tx.send().await` | guaranteed |

`send().await` blocks the producer until buffer space is available, so
the terminal is never dropped due to backpressure. If the receiver is
gone, `send()` returns `Err` and the macro/caller short-circuits
gracefully (`Ok(())` or `ControlFlow::Break`). Mutual exclusion is
inherited from the F-RCT-02 V02-01 analysis: the per-iteration branch
selects exactly one outcome, so no two success terminals fire in the
same iteration.

### (2) Error terminals — droppable under backpressure

The five `Err(...)`-forwarding arms all use non-blocking `try_send`:

| Arm | Site | API | On `Full` |
|---|---|---|---|
| T3 `finalize_no_response` | `finalize.rs:226` | `tx.try_send(Err(...NoResponse...))` | **DROP** (`let _ =`) |
| T4 `finalize_max_iterations` | `finalize.rs:267` | `tx.try_send(Err(...MaxIterations...))` | **DROP** |
| T6 intervention cancel | `think.rs:47` | `tx.try_send(Err(...cancelled...))` | **DROP** |
| T7 intervention block | `think.rs:65` | `tx.try_send(Err(...blocked...))` | **DROP** |
| top-level `run_core_loop` Err | `stream_channel.rs:310` | `tx.try_send(Err(e))` | **DROP** |

Every site discards the `try_send` result with `let _ =`. If the buffer
is full at the moment of terminal emission, the error event is silently
dropped. The function then returns `Ok(())`, the spawned task exits, the
channel's `tx` end is dropped, and the consumer's `ReceiverStream`
returns `None` — **the stream ends with no terminal item at all**.

The consumer cannot distinguish this from a clean cancellation or a
successful-but-empty stream. For the non-streaming collector
(`react_loop.rs:731-747`), this manifests as `rx.recv()` returning
`None`, the `while let Some(...)` loop exiting, and `answer` remaining
`String::new()` — so `run_react_loop` returns `Ok("")`, an empty
success string, **even though the turn actually failed with
`MaxIterationsExceeded` or `NoResponse`**.

#### Triggerability analysis

The buffer must be full at the exact moment the terminal `try_send`
fires. Sustained backpressure is required:

- For T3 (NoResponse): the LLM produced empty output. The preceding
  `run_think` emitted `LlmUsage` + possibly `ThinkEnd`/`Token` via
  `yield_event_or!` — if those filled the buffer and the consumer is
  still slow, the subsequent `try_send(Err(NoResponse))` at `:226` can
  hit `Full`.
- For T4 (MaxIterations): the loop ran `max_iterations` iterations,
  each emitting `LlmUsage` + think/tools events. The cumulative
  undrained events can easily exceed 256 if the consumer is slow across
  many iterations.
- For T6/T7 (intervention): these fire at think-start, before the LLM
  stream. The buffer is unlikely to be full unless prior iterations'
  events are undrained. Lower probability but not zero.

The `yield_event_or!` drops on intermediate events act as a pressure
relief (they prevent unbounded growth), so the buffer tends to
oscillate around full rather than stay permanently full. This makes the
terminal-drop a **race condition** rather than a sure thing — but race
conditions under load are exactly the failures that are hardest to
diagnose in production.

### (3) Cancellation produces no terminal event

`is_terminal()` (`mod.rs:331-336`) returns true for `FinalAnswer`,
`Cancelled`, and `Error`. The trait default
`execute_stream_with_cancel` / `chat_stream_with_cancel`
(`mod.rs:560-569, 606-626`) wraps the stream with `cancel_aware_stream`
(`mod.rs:896-917`), which yields `AgentEvent::Cancelled` and terminates
when the token fires.

**ReactAgent overrides both** (`mod.rs:2821-2842, 2844-2865`) and does
NOT wrap with `cancel_aware_stream`. Instead it stores the token on the
agent (`*self.cancel_token.lock().await = Some(cancel.clone())`) and
delegates to `run_stream_entry` → `run_stream_channel`. Cancellation is
then handled inside `run_core_loop` via:

- The LLM stream respecting the token (`create_llm_stream` passes
  `snap.cancel_token.clone()` into the LLM client).
- The tools-phase `select!` polling `cancel.cancelled().await`
  (`tools.rs:176-181, 278-283, 347-352`).

When cancelled mid-LLM-call (the common case), the LLM stream ends, the
`while let Some(cr)` loop exits, `run_think` returns
`ThinkOutcome::Continue(ThinkOutput{empty buffers})`, and the driver
hits `IterOutcome::NoResponse` → `finalize_no_response` → `try_send(
Err(NoResponse))`. So a cancelled stream surfaces as a `NoResponse`
error (which itself may be dropped per (2)), NOT as
`AgentEvent::Cancelled`.

When cancelled mid-tool-batch, the tools-phase `select!` observes the
cancel, enters the 5s grace period, then emits `ToolBatchEnd` via
`yield_final_event_or!` and returns `IterOutcome::Abandoned` → driver
returns `Ok(())`. No `AgentEvent::Cancelled` is emitted.

The test `test_run_stream_cancelled_mid_llm_call`
(`stream_channel.rs:1972-2038`) confirms this: it asserts the stream
terminates within 5s and that NO `FinalAnswer` is produced
(`:2030-2033`), but it does **not** assert that `AgentEvent::Cancelled`
IS produced — because it isn't. The consumer sees the stream end with
`None` (or with `Err(NoResponse)` if that `try_send` succeeded).

#### Downstream impact

- The non-streaming collector (`react_loop.rs:737-739`) has an arm for
  `Ok(AgentEvent::Cancelled)` that returns `Ok("Cancelled.")`. This arm
  is **dead for ReactAgent** — it can never fire because ReactAgent
  never emits `Cancelled`. A cancelled non-streaming turn returns
  `Ok("")` (empty) or `Err(NoResponse)` instead of `Ok("Cancelled.")`.
- Any consumer that switches on `is_terminal()` to detect end-of-stream
  will miss the cancellation case entirely for ReactAgent.
- The application `chat_driver` / `task_runtime` consumers that rely on
  the framework stream must implement their own cancellation detection
  (polling `cancel.is_cancelled()` separately, as noted in F-CORE-01)
  because the framework stream does not signal it.

### Post-terminal events

Within a single stream, no terminal arm emits events after the
terminal. Verified by inspecting each of the 5 error-terminal sites
(the `try_send` is the last statement before `Ok(())`) and the 5
success-terminal sites (`yield_final_event!`/`send().await` is followed
only by `fire_hook(SessionEnd)` which does not emit on `tx`).

The ONE exception is the Stop-hook continuation in `emit_final_text`
(`finalize.rs:182-201`): after emitting `FinalAnswer` via
`send().await`, it runs the Stop hook, and if the hook returns a
`continue_reason` and `!state.stop_hook_continued`, it sets the flag
and returns `ControlFlow::Continue(())` — letting the loop drive
another iteration, which may emit MORE events and a SECOND
`FinalAnswer`. The one-shot flag (`:199`) bounds this to at most one
continuation, so at most two `FinalAnswer` events per stream. This is
the only path where a terminal is followed by more events. See V04-01
for the streaming-vs-non-streaming divergence this creates.

## Deviations

None beyond the three defects documented above. The F-RCT-02 V02-01
terminal inventory (10 arms) remains accurate for the loop body; this
validation re-analyses those arms through the streaming-send-API lens
and finds the error-terminal half weaker than the success-terminal half.

## Conclusion

The claim is **supported**. Terminal ownership is split:

- **Success path is sound**: exactly-one `FinalAnswer`, delivered via
  blocking `send().await`, never dropped.
- **Error path is defective** (F-RCT-03-P2-01): the five `Err(...)`
  terminals use `try_send` and can be silently dropped on a full buffer,
  leaving the consumer with no terminal signal. The non-streaming
  collector turns this into a spurious `Ok("")`.
- **Cancellation path is defective** (F-RCT-03-P2-02): ReactAgent
  overrides `chat_stream_with_cancel` without wrapping
  `cancel_aware_stream`, so `AgentEvent::Cancelled` is never emitted.
  Cancellation surfaces as either `Err(NoResponse)` (itself droppable)
  or a silent stream end.

The "exactly one terminal per stream" expectation holds for the success
path and the Stop-hook-continuation edge (bounded to two). It does NOT
hold for the error/cancellation paths, where zero terminals is possible.
