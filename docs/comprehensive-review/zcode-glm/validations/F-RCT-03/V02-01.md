## Claim

The streaming channel has a bounded capacity (default 256) and three
distinct send semantics. Terminal events (`FinalAnswer`) and tool-stream
events use blocking `send().await` and are lossless under backpressure.
Non-terminal intermediate events (`Token`, `ToolCall`, `ToolResult`,
`ThinkStart/End`, `LlmUsage`, `MemoryRecalled`, `ContextCompressed`)
use `try_send` and are **silently dropped** when the buffer is full,
with only a `tracing::warn!` log. Terminal error events
(`Err(NoResponse)`, `Err(MaxIterations)`, intervention cancel/block)
also use `try_send` and are therefore **droppable** — see V03-01. The
config field is documented as intentionally lossy.

## Result

### Capacity

- Channel: `mpsc::channel::<Result<AgentEvent>>(buffer)` at
  `stream_channel.rs:41`, where `buffer = self.config.stream_buffer_size`.
- Default: `stream_buffer_size: 256` (`config.rs:235`).
- Documented contract (`config.rs:111-112`):
  > "Streaming channel buffer size (default 256). When full, events are
  > dropped with a warning."
- `DEFAULT_STREAM_BUFFER = 256` constant at `stream_macros.rs:11`, used
  only inside the `yield_event_or!` warn message.

Both the streaming (`run_stream_channel`) and non-streaming
(`run_react_loop`) entries use the same capacity
(`react_loop.rs:686`).

### Three send semantics

| Path | API | On `Full` | On `Closed` | Sites |
|---|---|---|---|---|
| `yield_event_or!` | `try_send` | **DROP** + warn log | short-circuit `Ok($bail)` | 16 (intermediate events) |
| `yield_final_event!` / `yield_final_event_or!` | `send().await` | **BLOCK** (backpressure) | short-circuit `Ok($bail)`/`Ok(())` | 12 (terminal + ToolStream + ToolBatchEnd) |
| direct `tx.send().await` | `send().await` | **BLOCK** | `Err` returned, handled | 8 (FinalAnswer, BudgetDecision, DirectAnswer tokens/usage) |
| direct `tx.try_send(Err(...))` | `try_send` | **DROP** (result discarded `let _`) | DROP | 5 (terminal errors: NoResponse, MaxIterations, intervention) |

### Backpressure asymmetry — the core finding

`yield_event_or!` (`stream_macros.rs:38-53`):

```rust
match $tx.try_send(Ok($event)) {
    Ok(()) => {}
    Err(TrySendError::Full(_)) => {
        tracing::warn!("Stream buffer full ({}), dropping event", DEFAULT_STREAM_BUFFER);
    }
    Err(TrySendError::Closed(_)) => { return Ok($bail); }
}
```

When the 256-slot buffer is full, the event is **dropped on the floor**
with only a warn log. The producer is NOT blocked — it continues
immediately. There is no retry, no swap-into-blocking-send, no
cooperative yield. The event is gone.

This affects every intermediate event:
- `Token(reasoning)` / `Token(content)` — the consumer (UI) sees
  garbled/truncated text because reasoning deltas are missing.
- `ToolCall` / `ToolResult` / `ToolError` — the consumer loses tool
  execution visibility; `ToolCall`/`ToolResult` pairs may become
  unbalanced (orphan `ToolResult` with no preceding `ToolCall`).
- `ThinkStart` / `ThinkEnd` — reasoning block boundaries become
  malformed (orphan `ThinkEnd` with no `ThinkStart`).
- `LlmUsage` — token-accounting observability loses a sample.
- `MemoryRecalled` / `ContextCompressed` — memory-projection UI gaps.

### Why the buffers do NOT rescue the consumer

The internal accumulation buffers (`content_buffer`, `reasoning_buffer`,
`tool_call_map` in `processor.rs:17-23`) are updated **unconditionally**
inside `process_stream_chunk`, regardless of whether the produced event
was later dropped by `yield_event_or!`. So:

- The **agent's own state** (context push, FinalAnswer) is always
  complete and correct — the dropped events do not corrupt the
  agent's reasoning.
- The **consumer's view of the stream** is lossy — the dropped `Token`
  events mean the consumer's rendered text has holes that can only be
  reconciled when the terminal `FinalAnswer` arrives (carrying the full
  text). Until then, the UI shows garbled content.

This is a real semantic gap for any consumer that renders `Token`
events as they arrive (the entire point of streaming) rather than
waiting for `FinalAnswer`.

### Is it triggerable?

Yes, under a slow consumer. The buffer (256) fills when the producer
emits faster than the consumer drains. Concretely:

- A long reasoning trace can emit hundreds of `Token(reasoning)` deltas
  in a tight loop (the LLM stream delivers them as fast as the network
  allows; `process_stream_chunk` + `yield_event_or!` is a pure-CPU
  hot path with no `await` between chunks except the LLM stream's own
  backpressure).
- If the consumer is blocked (e.g. UI render, network write to a remote
  client, GC pause) for the duration of >256 chunk emissions, the buffer
  fills and `yield_event_or!` starts dropping.

The drops themselves act as a pressure-relief valve (they prevent the
buffer from growing unboundedly), so the buffer tends to oscillate
around full rather than staying permanently full. This reduces (but does
not eliminate) the probability that a *terminal* `try_send` hits a full
buffer — see V03-01 for that analysis.

### Producer-side flow control

There is **no additional flow control** between the LLM stream and the
mpsc `tx`. The chunk loop at `think.rs:110-125` is:

```text
while let Some(cr) = llm_stream.next().await {
    let chunk = try_send_or!(tx, cr, ThinkOutcome::Abandoned);
    ...
    for event in process_stream_chunk(...) {
        yield_event_or!(tx, event, ThinkOutcome::Abandoned);  // try_send, drop on full
    }
}
```

The only backpressure on the producer is the LLM client's own stream
backpressure (which is network-bound, not consumer-bound). If the
consumer is slow but the LLM network is fast, the mpsc buffer fills and
`yield_event_or!` drops. There is no `await` point keyed to the mpsc
capacity for intermediate events.

### DirectAnswer path is different

`direct_answer_stream` (`stream_channel.rs:362-480`) uses
`tx.send(Ok(AgentEvent::Token(...))).await` (`:410`) — blocking. So the
DirectAnswer shortcut IS lossless for tokens (it backpressures on the
consumer). This is the opposite of the full-ReAct `run_think` path,
creating an inconsistency between the two streaming sub-paths (see V04).

### Slow-consumer / channel-close behaviour

- **Slow consumer, channel open**: intermediate events dropped (above).
  Terminal events (`FinalAnswer`) block the producer via `send().await`
  until the consumer drains — so the terminal is never lost, but the
  producer's spawned task is suspended indefinitely if the consumer
  never drains. The `execution_mutex` is held for the full stream
  lifetime (`stream_channel.rs:77, 304`), so a stuck consumer also
  blocks the next invocation on the same agent.
- **Consumer dropped (rx gone)**: every send path detects `Closed` and
  short-circuits (`yield_event_or!` → `Ok($bail)`;
  `yield_final_event!` → `Ok(())`; `send().await` returns `Err` which
  the caller turns into a `return`/`break`). The spawned task exits
  cleanly. This is correct and leak-free.

- Log/artifact: none.

## Deviations

The config doc-comment at `config.rs:111-112` explicitly documents the
drop-on-full behaviour as intentional ("events are dropped with a
warning"). This means the lossiness is a **deliberate design choice**,
not an oversight — but it directly conflicts with the "lossless" half
of the F-RCT-03 task question ("Are streaming deltas and terminal
events ordered, lossless, bounded, and semantically equivalent…"). The
finding is therefore classified as a real defect against the task's
lossless criterion, not as a bug against the implementer's intent.

## Conclusion

The claim is **supported**. The streaming channel is bounded (256) and
its close/cancel handling is clean (no leaks, no hangs on dropped
receivers). However, the backpressure policy is **asymmetric and lossy**
for the class of events the consumer most needs for streaming UX:

- Intermediate events (`Token`, `ToolCall`, `ToolResult`, `ThinkStart/End`)
  are silently dropped on full buffer — the consumer sees garbled text
  and unbalanced tool lifecycle pairs.
- Terminal error events (`Err(NoResponse)`, `Err(MaxIterations)`,
  intervention cancel/block) are also `try_send` and therefore
  droppable — see V03-01 for the terminal-guarantee analysis.
- Only success terminals (`FinalAnswer`) and tool-stream events
  (`ToolStream`, `ToolBatchEnd`) use blocking `send().await` and are
  lossless.

This feeds finding **F-RCT-03-P1-01** (intermediate-event loss) and
**F-RCT-03-P2-01** (terminal-error-event loss under backpressure). The
"bounded" half of the task question is satisfied (256-slot capacity,
no unbounded growth); the "lossless" half is NOT satisfied for
non-terminal events.
