## Claim

The streaming and non-streaming paths share the same loop body
(`run_core_loop`), the same tools, the same budgets
(`max_iterations` + `RunBudgetPolicy`), the same terminal partition,
and the same pre-flight checks (guard, IntentRouter). The semantic
equivalence holds at the **loop-body** level (inherited from F-RCT-02).
However, three **streaming-specific divergences** exist at the
collection/wrapping layer: (a) the Stop-hook continuation can emit two
`FinalAnswer` events on the streaming path but the non-streaming
collector returns after the first; (b) the streaming path exposes
per-token/per-tool events that the non-streaming collector discards;
(c) the cancellation terminal differs (`Err(NoResponse)` or silent end
vs the dead `Ok(AgentEvent::Cancelled)` arm).

### Shared machinery (equivalence)

Both `run_stream_channel` (streaming) and `run_react_loop`
(non-streaming) perform the same pre-flight sequence before spawning
`run_core_loop`:

| Step | Streaming (`stream_channel.rs`) | Non-streaming (`react_loop.rs`) |
|---|---|---|
| Execution mutex | `lock_owned().await` (`:77`) | `lock().await` (`:600`) |
| Trace run start | `start_scoped_trace_run` / `start_trace_run` (`:99-110`) | via `prepare_react_context` (`:603`) |
| Steer mailbox lease | `begin(turn_id)` + `set_steerable(true)` (`:122, 300`) | `begin(turn_id)` + `set_steerable(true)` (`:620, 685`) |
| Memory recall | `prepare_stream_context[_with_message]` (`:129-134`) | `prepare_react_context` (`:603`) |
| Guard input check | `check_all(Input)` → block yields `FinalAnswer` (`:141-179`) | `prepare_react_context` guard → returns `Ok(msg)` (`:603-613`) |
| IntentRouter | DirectAnswer shortcut / SkillRequired / Fallback (`:185-280`) | same three arms (`:623-682`) |
| Snapshot construction | `AgentSnapshot::from_agent[_with_invocation]` (`:197-299`) | `AgentSnapshot::from_agent` (`:687-706`) |
| Loop spawn | `tokio::spawn(run_core_loop(..., tx))` (`:302-312`) | `tokio::spawn(run_core_loop(..., tx))` (`:711-727`) |

The snapshot carries the **same** `config` (so the same `max_iterations`,
`run_budget`, `enable_tool`, `temperature`, etc.), the **same** `tools`
registry (so the same tool surface), and the **same** `cancel_token`.
The only difference is `StreamMode::Chat` vs the non-streaming
collector's mode (also `StreamMode::Chat` at `react_loop.rs:718` — the
mode flag affects only log labels and pre-loop audit text, not loop
behaviour; verified by `prepare_turn:31-34` which uses `mode` only in
`info!`).

The loop body (`run_core_loop`, `:494-756`) is byte-identical for both
callers — it does not branch on "am I streaming?". The `tx` it receives
is the same `mpsc::Sender<Result<AgentEvent>>` in both cases. So:
- Same tools.
- Same budgets (`max_iterations` ceiling, `iteration_wind_down_remaining`,
  `max_model_tokens`).
- Same terminal partition (the 10 arms from F-RCT-02 V02-01).
- Same compaction, same verification, same finalize helpers.

This is exactly the convergence F-RCT-02 handoff point #1 established,
and it holds.

### Divergence (a) — Stop-hook continuation: two `FinalAnswer` on streaming

`emit_final_text` (`finalize.rs:128-208`) emits `FinalAnswer` via
`tx.send().await` (`:179`), then runs the Stop hook. If the hook returns
a `continue_reason` and `!state.stop_hook_continued`, the flag is set
(`:199`) and `ControlFlow::Continue(())` is returned — the driver
continues the loop (`stream_channel.rs:694`), which may produce more
events and a **second** `FinalAnswer` on the next iteration's
`emit_final_text`.

- **Streaming consumer** sees: `[...events..., FinalAnswer("v1"),
  ...more events..., FinalAnswer("v2")]`. The consumer must treat the
  LAST `FinalAnswer` as authoritative (or merge).
- **Non-streaming collector** (`react_loop.rs:731-747`) breaks on the
  FIRST `FinalAnswer` (`break` at `:735`) and returns `answer = "v1"`.
  The second `FinalAnswer` is never collected.

So the two paths can return **different** final answers when the Stop
hook continues. The one-shot flag bounds this to at most two
`FinalAnswer` events, and the scenario requires a configured Stop hook
with a `continue_reason` (rare), so the practical impact is narrow — but
it is a genuine semantic divergence, not just an event-visibility
difference.

### Divergence (b) — Intermediate event visibility (expected/by-design)

The non-streaming collector at `react_loop.rs:745` does `_ => {}` for
every non-terminal event (`Token`, `ThinkStart/End`, `LlmUsage`,
`ToolCall`, `ToolResult`, `ToolError`, `ToolStream`, `ToolBatchStart/End`,
`MemoryRecalled`, `ContextCompressed`, `BudgetDecision`). It returns
only the `FinalAnswer` string. This is the entire point of having two
APIs: streaming exposes the per-step UX; non-streaming collapses to the
final result.

This is **not a defect** — it is the API contract. But it means
"semantically equivalent" must be scoped to the terminal outcome (same
`FinalAnswer` content), not to the event sequence. The agent's internal
state (context, tool results, trace events recorded via `record_event`)
is identical regardless of which collector drains the channel.

### Divergence (c) — Cancellation terminal (from V03-01)

Per V03-01: ReactAgent never emits `AgentEvent::Cancelled`. Cancellation
surfaces as:

- **Streaming**: the stream ends with `None` (if the buffer was full and
  the `Err(NoResponse)` `try_send` dropped) or with
  `Err(NoResponse)` (if the `try_send` succeeded). The consumer sees a
  failed/empty stream with no `Cancelled` marker.
- **Non-streaming**: the collector's `Ok(AgentEvent::Cancelled)` arm
  (`react_loop.rs:737-739`) is **dead** for ReactAgent. A cancelled
  non-streaming turn returns `Ok("")` (if `Err(NoResponse)` was dropped)
  or `Err(NoResponse)` (if it was delivered), never `Ok("Cancelled.")`.

So the non-streaming API does NOT return the documented
`Ok("Cancelled.")` outcome for ReactAgent. This is a contract divergence
between the trait's documented cancellation semantics and ReactAgent's
implementation.

### DirectAnswer sub-path: per-token streaming vs single string

The streaming DirectAnswer (`direct_answer_stream`,
`stream_channel.rs:362-480`) emits per-chunk `Token(content)` events via
`tx.send().await` (`:410`) — true token-by-token streaming with
backpressure. The non-streaming DirectAnswer (`react_loop.rs:755+`)
calls `call_llm_with_retry` and returns the full string. Both produce
the same final content, but the streaming path exposes the tokens.

Note (per V01-01 deviation 1): the full-ReAct `run_think` path does NOT
emit per-chunk content tokens (`emit_content_tokens=false`); it flushes
the whole `content_buffer` as one `Token` after the stream ends. So
DirectAnswer is actually MORE granular than full-ReAct on the streaming
path — an internal inconsistency, but both paths converge to the same
final `FinalAnswer` content.

## Deviations

The three divergences (a/b/c) are documented above. (b) is by-design.
(a) and (c) are real semantic divergences between the streaming and
non-streaming API contracts, but both are narrow:

- (a) requires a configured Stop hook returning `continue_reason`
  (uncommon).
- (c) is a cancellation-path weakness analysed in V03-01, not a
  loop-body behavioural difference.

Neither invalidates the core equivalence claim: the shared
`run_core_loop` produces the same terminal outcome for the same inputs
under the same budgets on both paths.

## Conclusion

The claim is **supported**. Streaming and non-streaming are
**semantically equivalent at the loop-body level**: same tools, same
budgets, same terminal partition, same pre-flight, same `FinalAnswer`
content for the same inputs. This is structurally guaranteed because
both entries spawn the same `run_core_loop` with the same snapshot
shape.

The three divergences are all at the collection/wrapping layer, not the
loop body:

- (a) Stop-hook double-`FinalAnswer` — feeds F-RCT-03-P3-01.
- (b) Intermediate event visibility — by-design, not a defect.
- (c) Cancellation terminal asymmetry — feeds F-RCT-03-P2-02 (from
  V03-01).

The "bounded" and "semantically equivalent" halves of the task question
are satisfied at the loop-body level. The "lossless" and "ordered"
halves have the caveats documented in V01-01 (content-token batching)
and V02-01 (intermediate-event drops).
