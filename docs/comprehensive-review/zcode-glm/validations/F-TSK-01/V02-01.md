## Claim

`TaskRevisionService` is the single authority for task create/update/list
transitions over a revisioned graph: every mutation flows through
`RevisionedTaskGraph` versioning and produces a `TaskGraphCommit`; the
transition table is coherent and has no parallel mutation path.

## Method

Read the revisioned task module and map each public mutation/query entry
point to its effect on graph versioning and commit recording.

```text
Read echo-agent/echo-orchestration/src/tasks/revisioned.rs (lines 1-700)
Read echo-agent/echo-orchestration/src/tasks/task_tools.rs (lines 1-220)
```

## Expected Result

A single service (`TaskRevisionService`) owns create/update/list; each
mutating op advances graph revision and yields a `TaskGraphCommit`; no second
mutator exists.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **Versioned graph container.** `RevisionedTaskGraph` (`revisioned.rs:42`)
    is the versioned state; `TaskGraphContext` (31) and
    `TaskGraphExecutionMode` (23) parameterize access. Version monotonicity is
    the revision invariant the service upholds.
  - **Create path.** Inputs: `TaskCreateInput` (67) → `TaskDraft` (49).
    `TaskRevisionService` applies the draft, assigns identity, and records a
    `TaskGraphCommit` (167) bumping the graph revision.
  - **Update path.** `TaskUpdateInput` (148) carries `TaskSpecPatch` (78)
    for scalar-field edits and `TaskPlanPatch` (117) with
    `TaskPlanPatchOp` (94) ops for plan/todo sub-edits. Result:
    `TaskPatchEffects` (156) + a new `TaskGraphCommit`.
  - **Plan-patch ops.** `TaskPlanPatchOp` (94) is the canonical plan/todo
    edit enum; `TaskPlanPatchInputOp` (125) is a parallel input-shaping enum
    used to deserialize tool arguments before normalization (see finding
    F-TSK-01-P3-01 — naming proximity is a readability concern, not a
    duplicate authority).
  - **List path.** Read-only over the current graph revision; no mutation,
    no commit.
  - **Store contract.** `RevisionedTaskStore` trait (`revisioned.rs:247`)
    is the persistence interface (`Send + Sync`); the service depends on it
    and on `TaskToolPolicy` (270, default `DefaultTaskToolPolicy` at 318) for
    permission/policy checks. Errors are typed:
    `RevisionedTaskStoreError` (175), `TaskPolicyError` (190),
    `TaskRevisionError` (200) — the last carries stale-revision/conflict
    semantics (see V04).
  - **Tool wiring.** `build_task_tools(service: Arc<TaskRevisionService>)`
    (`task_tools.rs:205`) constructs exactly three tools — `TaskCreateTool`
    (15), `TaskUpdateTool` (82), `TaskListTool` (143) — each holding an
    `Arc<TaskRevisionService>` and delegating to it. No tool performs direct
    store writes bypassing the service.
- Log/artifact: none

## Deviations

- `TaskPlanPatchOp` (94) and `TaskPlanPatchInputOp` (125) are two enums with
  overlapping names for related-but-distinct stages (canonical op vs. tool
  input deserialization). This is a readability/maintenance concern, not a
  duplicate authority — both feed the same `TaskRevisionService` update path.
  Recorded as finding F-TSK-01-P3-01.

## Conclusion

The transition/revision table is coherent and singular: one service, one
versioned graph, one commit record per mutation, one store contract. There is
no parallel mutation path. This supports the task's primary positive
conclusion (single canonical revisioned task model) and feeds finding
F-TSK-01-P3-01.
