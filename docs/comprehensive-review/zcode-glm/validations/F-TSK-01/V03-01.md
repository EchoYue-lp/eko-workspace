## Claim

The three task tools (`TaskCreateTool`, `TaskUpdateTool`, `TaskListTool`)
expose JSON Schema via the `Tool` trait and delegate every execution to
`TaskRevisionService`; argument shapes round-trip through
`TaskCreateInput` / `TaskUpdateInput` without lossy conversion at the tool
boundary.

## Method

Inspect the three tool structs and their `Tool` trait impls; verify each
tool holds an `Arc<TaskRevisionService>` and forwards arguments to the
matching service method.

```text
Read echo-agent/echo-orchestration/src/tasks/task_tools.rs (lines 1-220)
Read echo-agent/echo-orchestration/src/tasks/revisioned.rs (67, 148, 247-270)
```

## Expected Result

Each tool's `Tool::name`, `Tool::parameters_schema`, and `Tool::execute`
delegate to the service; no tool duplicates schema logic or store access.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **`TaskCreateTool`** (`task_tools.rs:15`): holds
    `Arc<TaskRevisionService>`. Its `Tool` impl declares a stable name and a
    JSON Schema for `TaskCreateInput` (`revisioned.rs:67`) fields.
    `execute` deserializes arguments into `TaskCreateInput` and calls the
    service create path; the service returns the new `TaskGraphCommit` /
    task id which the tool serializes back to the caller.
  - **`TaskUpdateTool`** (`task_tools.rs:82`): holds
    `Arc<TaskRevisionService>`. Schema covers `TaskUpdateInput`
    (`revisioned.rs:148`) including `TaskSpecPatch` (78) and the
    `TaskPlanPatch` (117) / `TaskPlanPatchOp` (94) family. Forwards to the
    service update path; returns `TaskPatchEffects` (156).
  - **`TaskListTool`** (`task_tools.rs:143`): holds
    `Arc<TaskRevisionService>`. Read-only; schema describes filter/view
    arguments; forwards to the service list path over the current graph
    revision.
  - **Schema source.** Schemas are produced via the framework `Tool` trait's
    `parameters_schema` (JSON Schema). The tool structs do not hand-roll a
    parallel schema; they reflect the same input types the service consumes,
    so argument shapes round-trip without an adapter mismatch.
  - **Registration.** `build_task_tools(service)` (`task_tools.rs:205`)
    returns `Vec<Box<dyn Tool>>` containing exactly these three tools, and
    `register_task_tools()` (`echo-agent/src/tasks.rs:18`) installs them on
    an agent. The only production caller is
    `echo-agent/src/agent/react/builder.rs:963`.
  - **No bypass.** No tool constructs a `TaskGraphCommit` or talks to a
    `RevisionedTaskStore` directly; all mutations go through
    `TaskRevisionService`, preserving the single-authority invariant from V02.
- Log/artifact: none

## Deviations

- The `TaskPlanPatchOp` (94) / `TaskPlanPatchInputOp` (125) pair means the
  wire argument enum and the canonical service enum are not literally the
  same type; the tool performs a normalization step between them. The
  conversion is lossless (input op → canonical op), but the two-type split is
  the source of finding F-TSK-01-P3-01.

## Conclusion

The tool layer is a thin, schema-driven adapter over `TaskRevisionService`.
JSON Schema is the wire contract, the service is the sole executor, and no
tool bypasses revision/versioning. Supports the task's primary positive
conclusion and feeds finding F-TSK-01-P3-01.
