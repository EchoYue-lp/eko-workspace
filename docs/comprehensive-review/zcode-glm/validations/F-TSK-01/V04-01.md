## Claim

Stale-update / concurrent-modification is handled typedly: the service
surfaces revision conflicts via `TaskRevisionError` and policy violations via
`TaskPolicyError`, and `RevisionedTaskStore` defines the error semantics the
store must honor.

## Method

Inspect the three error enums and the `RevisionedTaskStore` trait signature
to confirm stale-revision and conflict paths are typed (not stringly-typed)
and that the store contract mandates them.

```text
Read echo-agent/echo-orchestration/src/tasks/revisioned.rs (lines 175-270, 674-700)
```

## Expected Result

A dedicated stale-revision/conflict error variant exists; policy errors are
separable from store errors; the store trait's error type propagates the
distinction.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **`TaskRevisionError`** (`revisioned.rs:200`): the service-level error
    carrying revision-conflict / stale-update semantics. A caller that
    submits a `TaskUpdateInput` whose base revision does not match the
    graph's current revision receives this typed error rather than a
    silent overwrite or a stringly-typed message.
  - **`TaskPolicyError`** (`revisioned.rs:190`): policy-violation errors
    raised by the `TaskToolPolicy` (270) check (e.g. disallowed operation
    for the current caller/mode). Distinct from revision conflicts, so
    callers can branch on cause.
  - **`RevisionedTaskStoreError`** (`revisioned.rs:175`): the storage-layer
    error enum returned by `RevisionedTaskStore` implementations. The
    `RevisionedTaskStore` trait (`revisioned.rs:247`, `Send + Sync`) defines
    the persistence contract including its error type, so any store
    implementation (in-memory, file, sqlite-for-other-consumers) must honor
    these semantics.
  - **`TaskRevisionService`** (`revisioned.rs:674`) composes the store and
    the policy, converting store/policy errors into `TaskRevisionError` for
    its own callers. This keeps the stale-update path typed end-to-end:
    store conflict → service `TaskRevisionError` → tool result.
  - **Optimistic-revision shape.** Because every mutation produces a
    `TaskGraphCommit` (167) and the graph is versioned
    (`RevisionedTaskGraph` at 42), the stale-update check is a revision
    comparison, not a lock. This matches the B-REF-01 convergence: plan/task
    is a versioned artifact, approval is not a runtime state machine
    (B-REF-01-P1-01), and conflict resolution is by revision, not by an
    approval-state graph.
- Log/artifact: none
