## Claim

Workflows can be paused at interrupt points and resumed from checkpoints.
The `CheckpointStore` abstraction (`MemoryCheckpointStore` default,
`FileCheckpointStore` persistent) backs `run_until_interrupt` → `resume`
with typed approval decisions, state-injection, branching, and lineage.
The mechanism is coherent and live, but it has no schema-version field,
silently drops corrupt entries on list, exposes a filename-traversal
surface on user-supplied ids, and the streaming runner does not support
interrupts at all.

## Method

Static inspection of the checkpoint lifecycle: creation sites in the
graph runner, the `Checkpoint`/`CheckpointStore` types, both store
implementations, and the resume/branch/restore methods. Cross-checked
against the resume test and the F-RCT-05 checkpoint finding for
comparison.

## Expected Result

- Checkpoints are created at every configured interrupt point and saved
  before pausing.
- `resume()` honors `ApprovalDecision` (Approved continues; Rejected/
  Deferred abort with restored state) and deletes the checkpoint on
  completion.
- `FileCheckpointStore` writes atomically (temp + rename).
- A persisted checkpoint can be loaded back and its state restored.
- Gaps (anticipated): no schema-version field; no streaming-interrupt.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **Checkpoint creation.** Two interrupt points in `run_until_interrupt`
    (`graph.rs:738-906`): `should_interrupt_before` (`:768-785`) and
    `should_interrupt_after` (`:826-849`). Both build a `Checkpoint` via
    `Checkpoint::new(graph_name, current_node, &state, path, step_count,
    InterruptType)` and call `self.checkpoint_store.save(&checkpoint)`
    **before** returning `Interrupted`. The `*` wildcard is supported
    (`InterruptConfig::should_interrupt_*`, `:116-123`).
  - **`resume()` semantics** (`graph.rs:913-1092`):
    - `ApprovalDecision::Rejected { reason }` and `Deferred` return
      `Completed(GraphResult)` with `checkpoint.restore_state()?` and the
      recorded path/step_count — i.e. abort without executing further
      (`:919-946`). `Approved`/`ApprovedWithScope`/`Modified` continue.
    - State restored via `checkpoint.restore_state()?` (`:949`) →
      `SharedState::from_json(&self.state_snapshot)`
      (`checkpoint_store.rs:165-169`), a typed `Result`.
    - For a `BeforeNode` resume, the checkpoint's `current_node` is
      executed directly; the `should_interrupt_before` check is correctly
      skipped (comment `:978-979`). For `AfterNode`, the
      `should_interrupt_after` check (`:1013-1038`) runs and saves a new
      checkpoint, deleting the old one (`:1034`).
    - On completion (END / finish node / NextStep::End), the checkpoint is
      deleted (`:991`, `:1083`). ✓
  - **`resume_with_state`** (`graph.rs:1098-1118`) merges `state_updates`
    into the restored state and **reuses the original checkpoint id** for
    subsequent save/delete — so a `FileCheckpointStore` resume-in-place
    does not orphan the old file. Test
    `test_resume_with_state_reuses_checkpoint_identity` (`:1883-1933`)
    locks this (linear graph) and asserts the checkpoint store is empty
    after successful resume. ✓
  - **`branch_from`** (`graph.rs:1147-1178`) loads a checkpoint, applies
    state updates, creates a `Checkpoint::branch` carrying
    `parent_checkpoint_id` lineage (`checkpoint_store.rs:128-150`),
    saves the fork, and resumes it. `tag_checkpoint` (`:1181-1206`)
    mutates `label`/`tags` in place. `list_checkpoints_by_graph`
    (`:1219-1223`) filters server-side. ✓
  - **`CheckpointStore` implementations** (`checkpoint_store.rs`):
    - `MemoryCheckpointStore` (`:296-343`): `tokio::sync::RwLock<HashMap>`,
      straightforward CRUD. Default store used by `GraphBuilder::build`
      (`graph.rs:515`).
    - `FileCheckpointStore` (`:347-461`): atomic write via
      `path.with_extension("json.tmp")` then `tokio::fs::rename`
      (`:385-391`); `load` returns a typed error on parse failure
      (`:403-405`); `list` sorts newest-first (`:429`).
  - **Gaps confirmed:**
    - **No schema-version field on `Checkpoint`** (`:38-72`). Like the
      F-RCT-05 finding for ReAct snapshots, a `Checkpoint` struct
      evolution breaks `FileCheckpointStore::load` of older files with a
      serde error (`:403-405`) — no migration path, no version probe.
      Under AGENTS.md "no compatibility burden" this is low-severity for
      the CLI (which does not persist workflow checkpoints across
      versions), but the pub API advertises persistence.
    - **`FileCheckpointStore::list` silently skips unparseable entries**
      (`:420-425`: `if path.extension ... && let Ok(json) = ... && let
      Ok(cp) = ...`). So a corrupt file disappears from listings yet
      `load(id)` on the same id errors. Inconsistent failure mode. Low
      impact (local store, single user).
    - **Filename derived from raw `id`** (`:359-361`:
      `base_path.join(format!("{}.json", id))`). `load(id)`/`delete(id)`
      accept caller-supplied strings; an id like `../../etc/x` would
      traverse out of `base_path`. In the normal flow `id` is a UUID
      (`Checkpoint::new`, `:84`) and the threat model is local
      single-user (AGENTS.md), so reachability is low — but the pub API
      does not sanitize.
    - **`run_stream` has no interrupt/checkpoint support**
      (`graph.rs:1234-1369`). It runs to completion (or max-steps /
      cancel) and emits `WorkflowEvent`s; it never calls
      `should_interrupt_*` or `checkpoint_store.save`. So interrupt/
      resume is available only via `run_until_interrupt`, not the
      streaming runner. Feature gap, not a bug.
  - **`Checkpoint::restore_state`** (`checkpoint_store.rs:165-169`) maps
    a serde error to `ReactError::Other` (stringly-typed) rather than a
    dedicated variant — consistent with the F-CORE-01-P3-01 observation
    about `ReactError::Other` catch-all usage; not separately actionable
    here.

## Deviations

None for the core claim (resume works and is live). The four gaps are

## Conclusion

Checkpoint/resume is a coherent, live lifecycle:
`run_until_interrupt` → `Checkpoint` → `save` → `resume(decision)` →
`delete` (or branch/restore). Typed approval decisions, lineage via
`parent_checkpoint_id`, atomic file writes, and checkpoint-id reuse in
`resume_with_state` are all correct. The mechanism is usable as-is for
the `MemoryCheckpointStore` default and for single-version
`FileCheckpointStore` persistence.

Four lower-severity gaps identified (supporting findings
F-WFL-01-P2-04 no-version-field, F-WFL-01-P3-04 list-silent-skip +
traversal, F-WFL-01-P3-05 streaming-no-interrupt). The resume+parallel
correctness defect is owned by V03 / F-WFL-01-P1-01, not this validation.
