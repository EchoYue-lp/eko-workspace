## Claim

The workflow module offers two distinct "parallel branch" semantics, and
the `Graph` engine's `resume()` path diverges from its `run()` /
`run_until_interrupt()` paths: `resume()` executes parallel branches on
the **shared** state with no fork and no `deep_merge`, whereas the other
two paths fork each branch and merge via `deep_merge`. This makes a
parallel workflow resumed from a checkpoint behave differently than the
same workflow run straight through. Separately, the doc-comment rationale
for `Graph`'s sequential (non-spawned) parallelism is inaccurate: the
pipeline flavors prove `Arc<dyn Agent>` *can* be `tokio::spawn`ed.

## Method

Static inspection of all three parallel-execution sites in `graph.rs`,
the two `tokio::spawn`-based pipeline flavors, and the `SharedState`
merge primitives. Cross-checked against the unit tests for coverage of
the resume+parallel combination.

## Expected Result

- All parallel sites in `Graph` use the same fork+`deep_merge` semantics.
- Pipeline flavors (`ConcurrentWorkflow`, `DagWorkflow`) achieve true
  `tokio::spawn` concurrency.
- The doc comment on `add_parallel_edge` accurately states why `Graph`
  runs branches sequentially.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **`Graph::run()` parallel branch** (`graph.rs:686-706`): for each
    target, `branch_state = state.fork()?` (`:695`), execute on the fork,
    then `state.deep_merge(&branch_state)?` (`:701`). Each branch gets an
    isolated copy; results are recursively merged back. ✓
  - **`Graph::run_until_interrupt()` parallel branch** (`graph.rs:867-887`):
    identical fork+`deep_merge` pattern (`:876` fork, `:882` merge). ✓
  - **`Graph::run_stream()` parallel branch** (`graph.rs:1318-1350`):
    identical fork+`deep_merge` pattern (`:1329` fork, `:1344` merge). ✓
  - **`Graph::resume()` parallel branch** (`graph.rs:1064-1081`):
    **DIVERGENT.** For each target, `state.set_current_node(target_name)`
    (`:1074`) and `target_node.execute(&state).await?` (`:1075`) operate
    on the **shared** `state` directly. There is **no `state.fork()`** and
    **no `state.deep_merge()`**. The inline comment at `:1065` says
    `// Parallel branch execution, shared SharedState (sequential execution)`.
    Branches mutate the shared state in place, sequentially. Later
    branches see earlier branches' writes; there is no isolation and no
    merge. **This contradicts the other three sites.**
  - **Coverage gap confirmed:** the only resume test is
    `test_resume_with_state_reuses_checkpoint_identity` (`graph.rs:1883`),
    which uses a **linear** graph (`start -> finish`). No test exercises
    `resume()` + `add_parallel_edge`. The divergence is unverified by the
    test suite.
  - **Consequence:** a workflow that uses `add_parallel_edge` and is
    resumed from a checkpoint produces different state-merge semantics
    than the same workflow run straight through (or via
    `run_until_interrupt` then approved). A branch that reads a key
    before writing it may observe pollution from a prior branch only on
    the resume path. This is a latent correctness defect for any
    parallel+interrupt workflow.
  - **Pipeline flavors use true `tokio::spawn`:**
    - `ConcurrentWorkflow::run` (`concurrent.rs:99-111`) spawns one task
      per agent, collects `(name, input, result, elapsed)`, joins all
      (`:116-136`), then applies the user merge fn (`:138`). No shared
      mutable state between agents (each clones `input`). No race.
    - `DagWorkflow::run` (`dag.rs:134-163`) spawns one task per ready
      node per topological batch, joins the batch, then decrements
      successor in-degrees (`:189-198`). `node_results` is mutated only
      after join, in the driver task. No race.
  - **Doc-comment rationale is inaccurate.** `add_parallel_edge`
    (`graph.rs:361-366`) states branches run sequentially "Because `dyn
    Agent` nodes are not `Send + 'static`." But `SharedAgent =
    Arc<dyn Agent>` (`mod.rs:71`) and `Agent: Send + Sync`
    (`echo-core/src/agent/mod.rs`), so `Arc<dyn Agent>` is `Send + Sync`,
    and `ConcurrentWorkflow`/`DagWorkflow` successfully `tokio::spawn`
    exactly that type. The real blocker in `Graph::run()` is the borrowed
    `&self` + `&state` captured by a spawn inside the async loop (lifetime,
    not `Send`); the pipeline flavors own their `Vec<SharedAgent>` and
    clone the `Arc` out before spawning. The comment mis-describes the
    constraint.
  - **`SharedState::merge` dead code** (`state.rs:324-355`): the
    non-overwrite `merge()` acquires `self.inner.read()` twice, names the
    first guard `other_inner` (`:325`) while it locks `self.inner` (not
    `other.inner`), and drops both guards unused before doing the real
    read+write at `:338-353`. The first two lock acquisitions are dead
    and the `// SAFETY: need read both locks to prevent deadlock` comment
    (`:334`) is nonsensical. The actual merge logic (`or_insert_with`,
    no-overwrite) is correct. `merge()` has no production caller (only
    `state.rs:508` test) — retained as pub framework API per AGENTS.md;
    the dead lock code is cleanup, P3.
- Log/artifact: none

## Deviations

The validation **failed** against the primary claim: the four parallel
sites in `Graph` do NOT use uniform semantics. `resume()` diverges from
`run()`/`run_until_interrupt()`/`run_stream()`. The secondary observation
(inaccurate doc rationale) also failed.

The pipeline flavors (`ConcurrentWorkflow`, `DagWorkflow`) are clean:
true spawn-based concurrency, no shared mutable state across agents, no
race. The merge primitives (`deep_merge` recursive, `merge_overwrite`
wholesale) behave as documented.

## Conclusion

Two defects confirmed:

1. **F-WFL-01-P1-01 (resume parallel divergence):** `Graph::resume()`
   executes parallel branches on shared state with no fork/merge,
   contradicting the three other execution paths. Untested. Causes
   divergent state semantics for any `add_parallel_edge` workflow resumed
   from a checkpoint. P1 (concurrency/recovery correctness).
2. **F-WFL-01-P3-02 (inaccurate parallelism rationale):** the
   `add_parallel_edge` doc comment blames a `Send + 'static` bound that
   does not hold; the real constraint is `&self` lifetime. Misleads
   contributors. P3.

Plus positive confirmation: pipeline flavors' merge is race-free.
Supports F-WFL-01-P2-02 (parallelism asymmetry across flavors) and
F-WFL-01-P3-03 (`SharedState::merge` dead code).
