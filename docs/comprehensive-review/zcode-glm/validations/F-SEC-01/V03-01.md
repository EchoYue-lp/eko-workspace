## Claim

When a sandbox backend is unavailable (binary missing, isolation level
unsatisfiable), the framework either degrades with a logged warning or
returns a typed error. It does not silently execute untrusted code in a
less-isolated context without logging, and it does not panic.

## Method

Read `echo-execution/src/sandbox/manager.rs` (547 lines, full) and
`echo-execution/src/sandbox/local.rs` `is_available()` (lines 958-984) and
`select_executor()` (lines 344-403). Trace four scenarios:

```text
Scenario A — Docker unavailable, auto_detect default (allow_fallback=true):
  select_executor(required=Container):
    local.isolation_level() = Process (< Container)  -> skip
    docker = None (not detected at construction)     -> skip
    k8s = None                                        -> skip
    fall through to "no executor meets requirement":
      allow_fallback=true → return best available (local)
    execute_at_level sees actual=Process < required=Container:
      log warn!("Falling back to lower isolation executor")  [manager.rs:313-318]
    proceed on local

Scenario B — Docker unavailable, allow_fallback=false (local_only/local_sandbox):
  select_executor returns Err(SandboxError::Unavailable(...))
  caller receives typed error, no execution.

Scenario C — sandbox-exec missing on macOS (is_available=false):
  LocalSandbox::is_available returns false at local.rs:965-970
  (`Command::new("sandbox-exec")...status().unwrap_or(false)`).
  manager.is_available short-circuits to false; select_executor falls
  through to the no-executor branch.

Scenario D — execute_stream downstream failure:
  manager.rs:97-115: on executor.execute_stream error, emits
  SandboxStreamEvent::Complete with exit_code=-1 and stderr=error message;
  does not panic, does not silently drop.
```

## Expected Result

- Scenario A: warning logged, execution proceeds at lower isolation
  (documented auto-degrade behavior).
- Scenario B: typed `SandboxError::PermissionDenied` /
  `SandboxError::Unavailable`; no execution.
- Scenario C: `is_available() = false`; manager reports unavailable.
- Scenario D: graceful `Complete` event with error payload; no panic.
- No `unwrap()`/`expect()`/`panic!()` in non-test fallback code.

## Result

- Exit code: not-applicable (static inspection)
- Summary:
  - **Scenario A confirmed**: `manager.rs:303-319` checks
    `actual < required` and logs `warn!(required=..., actual=...,
    executor=..., "Falling back to lower isolation executor")` before
    proceeding. The downgrade is observable in logs.
  - **Scenario B confirmed**: `manager.rs:397-403` returns
    `Err(ReactError::Sandbox(Box::new(SandboxError::Unavailable(...))))`
    when `allow_fallback=false` and no executor meets the requirement;
    `manager.rs:304-311` returns `PermissionDenied` variant in
    `execute_at_level`. Both are typed errors; no panic, no silent run.
  - **Scenario C confirmed**: `local.rs:958-984` `is_available()` probes
    `sandbox-exec` (macOS) / `bwrap` (Linux) with `status().await.map(|s|
    s.success()).unwrap_or(false)`. Missing binary → false. The
    `unwrap_or(false)` is the correct safe fallback (not a panic).
  - **Scenario D confirmed**: `manager.rs:97-115` constructs an
    `ExecutionResult { exit_code: -1, stderr: message, ... }` and sends
    `SandboxStreamEvent::Complete(...)` to the channel. Downstream consumers
    see a normal completion event with failure metadata; no panic.
  - **Panic safety in fallback code**: grep of
    `manager.rs`/`policy.rs`/`local.rs` non-test code found zero
    `.unwrap()`/`.expect()`/`panic!`/`unreachable!`/`todo!`. All error paths
    use `?`, `unwrap_or`, `unwrap_or_default`, or typed `Result` returns.
  - **Cancellation path**: `echo-core/src/sandbox.rs:73-90`
    `execute_with_limits_and_cancel` default selects on
    `cancel.cancelled()` vs the inner future; on cancel returns
    `Err(Sandbox(Box::new(SandboxError::Cancelled(...))))`. Typed error, no
    silent drop. Local backend overrides for process-group cleanup
    (`local.rs:595-611`) logs warn on kill failure but still proceeds.

- Log/artifact: none created.

## Deviations

- On Windows, `LocalConfig::enable_os_sandbox` defaults to `true`
  (`local.rs:50-66`) but the Windows backend is just `cmd /C` with no real
  OS sandbox; `isolation_level()` correctly returns `Process` on Windows
  (`local.rs:948-956`). Not a fallback defect, but the config field name is
  misleading. Recorded as finding F-SEC-01-P3-03.

## Conclusion

Supports V03 (sandbox fallback safety): unavailability is surfaced as
either a logged warning (with `allow_fallback=true`) or a typed error
(without). No silent downgrade, no panic. Cancellation produces typed
`SandboxError::Cancelled`. Windows config naming is misleading but the
runtime isolation level is reported correctly.

Used by finding: F-SEC-01-P3-03 (Windows naming).
