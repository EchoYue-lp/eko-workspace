## Claim

The framework maps each LLM provider/model to its real context-window size and
feeds that size into the per-category budget allocations, so the budget
percentages are applied to the correct denominator. Unknown models degrade
safely (conservative window, explicit user-override path).

## Result

- Exit code: not-applicable (static inspection)
- Summary: **Claim not supported.** The resolver is (a) a single authority
  (good), (b) **not** per-provider despite its name and docstring, and (c) the
  fallback default `396_000` matches no real shipping model and silently
  over-allocates for the most common 128K/200K models.

### Single authority (positive)

One resolver: `infer_context_window(provider, model_name)` at
`echo-core/src/llm/capabilities.rs:197-217`. It is invoked from exactly two
sites — `ModelProfile::new` (`capabilities.rs:271`) and
`AppConfig::resolve_context_window` (`src/config.rs:101`). Duplicate search
across both repositories found no parallel resolver; the CLI does not
re-derive the window. The override path (`ModelProfileOverride::context_window`
applied via `ModelProfileResolver`, `capabilities.rs:296-317, 355-373`) is the
single extension point for consumer-supplied corrections.

### Not actually per-provider (negative)

```rust
// capabilities.rs:197
pub fn infer_context_window(_provider: &str, model_name: &str) -> Option<u32> {
    let lower = model_name.to_ascii_lowercase();
    if lower.starts_with("gpt-5.6")              { Some(1_050_000) }
    else if lower.starts_with("claude-fable-5")
        || lower.starts_with("claude-opus-4-8")
        || lower.starts_with("claude-sonnet-5")
        || lower.starts_with("deepseek-v4")
        || lower.starts_with("qwen3.7-max")
        || lower.starts_with("qwen3.7-plus")     { Some(1_000_000) }
    else if lower.starts_with("kimi-k2.7")
        || lower.starts_with("kimi-k2.6")        { Some(256_000)   }
    else if lower.starts_with("glm-5.2")         { Some(1_000_000) }
    else                                          { None            }
}
```

The `_provider` parameter is discarded — the function is pure model-name
pattern matching. The docstring (`:195-196` "根据厂商和模型名称推断上下文窗口大小")
and the call site (`src/config.rs:112-116` passes `&self.model.provider`) both
imply vendor awareness that the body does not deliver. For models hosted on
multiple backends with different windows (e.g. a Qwen model exposed via
DashScope vs. a self-hosted Ollama mirror), the resolver cannot distinguish
them.

Coverage of the table is narrow. The following common models all return `None`
and fall through to the default:

- OpenAI: `gpt-4o`, `gpt-4-turbo`, `gpt-4.1`, `gpt-4.5` (128K–200K real
  windows), `o3-mini` / `o4-mini` (128K–200K).
- Anthropic: `claude-opus-4.6`, `claude-sonnet-4.5`, `claude-3.7-sonnet`
  (200K real).
- DeepSeek: `deepseek-v3.2`, `deepseek-r1` (128K real).
- Alibaba: `qwen3-235b-a22b`, `qwen3-max` (256K real, only `qwen3.7-*` is
  listed).
- Zhipu: `glm-4.6`, `glm-4.5` (128K real, only `glm-5.2` is listed).
- Open-weight: `llama-3`, `llama-4`, Mistral, etc.

### Risky default for unknown models (negative)

When `infer_context_window` returns `None`, `resolve_context_window`
(`src/config.rs:99-104`) falls back to `396_000`:

```rust
fn resolve_context_window(explicit: Option<u32>, provider: &str, model_name: &str) -> usize {
    explicit
        .or_else(|| infer_context_window(provider, model_name))
        .unwrap_or(396_000)
        .clamp(1, 10_000_000) as usize
}
```

`396_000` matches **no** shipping model. It is larger than the 128K windows of
gpt-4o / gpt-4-turbo / deepseek-v3.2 / glm-4.6 / claude-3.x-small and larger
than the 200K windows of the Claude 3.7 / 4.x family. For those models, the
framework's `conversation_budget()` returns `0.65 × 396_000 ≈ 257K`, which
already exceeds a 200K model's *entire* window. Combined with the phantom
system/tool reservations (V01-01) and uncounted tool defs (V04-01), the
prepared request will exceed the real window and the provider will return a
400 / context-length-exceeded error.

The `unknown_model_uses_396k_default_context_window` test (`src/config.rs:855-862`)
codifies this default as intentional, but does not justify why 396K is safe for
a model whose real window is unknown. AGENTS.md's product-safety section
("本地个人助理" threat model) does not make this safe — the failure mode is a
hard API error that breaks the chat path, not a security issue.

Three-state mitigation in `to_agent_config` (`src/config.rs:120-137`): when the
user does not set `context_window` or `token_limit`, the budget's
`total_window` stays `None` and `token_limit` becomes `usize::MAX`, so
compression is effectively disabled (verified in V01-01: with
`total_window = usize::MAX`, `conversation_budget ≈ 0.65 × usize::MAX`, never
exceeded). So an unconfigured user does **not** hit the 396K trap. The trap
fires only when the user configures a strategy (`compress_strategy =
"summary"`, the YAML default per `src/config.rs:170-174`) without setting
`context_window` — in that path, `has_compressor()` returns true but the window
is still 396K.

### Clamp bounds

`.clamp(1, 10_000_000)` (`src/config.rs:103`) bounds the window to
[1, 10M]. Upper bound 10M is reasonable (no shipping model exceeds it as of
2026-08). Lower bound 1 lets a misconfigured user set `context_window: 1`,
which makes `conversation_budget = 0` and `token_limit / 2 = 0`, so
`effective_limit = 0` and the compressor would try to fit into 0 tokens. No
panic, but pathological. Not a separate finding (P3 at most, user-induced).

## Deviations

- The `ModelProfileResolver` override mechanism
  (`capabilities.rs:319-385`, tested at `:723-776`) is the correct, generic
  escape hatch: a consumer can register an exact `(provider, model) →
  context_window` override without forking the framework. EKO does not appear
  to use it today, but it exists and is tested.
- `infer_context_window` is `pub` and named generically; third-party consumers
  may rely on it. Per AGENTS.md ("框架 API 删了,复用方代码会断;留着至多多占一点
  编译时间"), do not delete — fix in place by either (a) honouring the
  `provider` parameter, or (b) renaming and updating the docstring to reflect
  model-name-only matching.

## Conclusion

The claim is **not supported** in two ways:

1. **F-CTX-01-P2-03**: `infer_context_window` ignores its `provider` argument
   despite the function name, signature, and docstring all implying per-vendor
   resolution. The body is model-name pattern matching only.
2. **F-CTX-01-P2-04**: the `396_000` fallback default is larger than the real
   windows of the most common 128K/200K models, so enabling compression
   without an explicit `context_window` produces a budget that can exceed the
   real model window and trigger provider 400 errors.

The override/resolver plumbing (`ModelProfileResolver`) is sound and is the
right place for a fix; the gap is in `infer_context_window`'s coverage and the
default choice.
