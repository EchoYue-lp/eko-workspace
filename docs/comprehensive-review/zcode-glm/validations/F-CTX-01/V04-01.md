## Claim

The framework's token estimate reflects what the model actually receives,
including (a) large tool-definition schemas and (b) multilingual / CJK content,
and the configured `Tokenizer` is used consistently across every context-assembly

### (a) Tool definitions are entirely uncounted (large-schema gap)

The request body (`echo-core/src/llm/types.rs:525-540`) carries tools out of
band:

```rust
pub struct ChatCompletionRequest {
    pub model: String,
    pub messages: Vec<Message>,
    #[serde(skip_serializing_if = "Option::is_none")]
    pub tools: Option<Vec<ToolDefinition>>,
    ...
}
```

`ContextManager::estimate_tokens` (`compression/mod.rs:1541-1547`) iterates
only `messages`:

```rust
fn estimate_tokens(messages: &[Message], tokenizer: &dyn Tokenizer) -> usize {
    messages
        .iter()
        .filter_map(|m| m.content.as_text())
        .map(|c| tokenizer.count_tokens(&c))
        .sum()
}
```

The `ContextManager` does not hold a reference to the `ToolManager`, so it has
no way to see `ToolDefinition`s. `prepare()` and `should_compress()` both call
`budget.allocate(0, 0, estimated_tokens)` (V01-01), passing `tool_defs_size =
0`. The 5% `tool_definitions_budget` reservation is therefore dead — it
protects no measured bytes.

**Concrete failure mode.** A 200K-window model with 30K tokens of tool
schemas (a few dozen MCP tools with non-trivial JSON schemas — easy to reach
in EKO's MCP-heavy product). Budget says: `conversation_budget = 0.65 × 200K =
130K`. Framework lets history grow to 130K. Real request body = 30K tools +
~8K system + 130K history = 168K, plus the 10% output reservation (20K) =
188K. Within 200K, but with no headroom for the per-message overhead
(provider role tags, packing) the actual request routinely exceeds the window
and the provider returns HTTP 400 / `context_length_exceeded`. The 10% safety
margin was supposed to absorb overhead, but it is computed from a budget whose
category inputs are zero, so the margin protects nothing it does not already
account for.

This compounds with the protected-token gap (V02-01) and the 396K default
(V03-01): each layer assumes the next layer is accounting for the bytes it
does not see, and the assumptions nest.

### (b) Multilingual token counting — safety and consistency

**Safety (positive).** No byte-slicing anywhere in the counting path:

- `HeuristicTokenizer::count_tokens` (`tokenizer.rs:50-58`) uses
  `text.chars().map(...).sum()` — Unicode-scalar-value-aware, no `&s[..n]`.
- `SimpleTokenizer::count_tokens` (`tokenizer.rs:63-71`) uses `text.len() / 4`
  — byte count, but no slice; AGENTS.md UTF-8 rule is about *truncation* panics,
  not byte-length arithmetic, so this is compliant.
- `CalibratedTokenizer::count_tokens` (`tokenizer.rs:188-194`) casts
  `(base as f64 * factor).round() as usize`. Since Rust 1.45 this cast
  saturates (NaN → 0, negative → 0, overflow → `usize::MAX`); no panic. The
  calibration `factor` is itself clamped via `observed_ratio.clamp(0.2, 5.0)`
  at `:152-154`, so wild factors are bounded.
- `CanonicalContext::to_reinjection_messages` truncates rules with
  `rules.chars().take(2000).collect()` (`echo-core/src/compression.rs:385`) —
  AGENTS.md-canonical pattern.

CJK accuracy: `HeuristicTokenizer` weights ASCII=1, non-ASCII=2, total / 4
(`tokenizer.rs:55`), so a single CJK char ≈ 0.5 tokens (heuristic) vs.
`SimpleTokenizer`'s 3 bytes / 4 = 0.75 tokens. The `test_heuristic_cjk`
(`tokenizer.rs:370-374`) and `test_heuristic_mixed` (`:377-381`) tests pin
these values. Acceptable approximation; the `CalibratedTokenizer` EMA
(`test_calibrated_tokenizer_calibration` at `:406-423`) closes the gap to real
token counts over time.

**Consistency (negative).** `ContextAssembler` (the parallel framework
building block, `src/context/mod.rs`) uses a *different* estimator from
`ContextManager`:

```rust
// src/context/mod.rs:208-211 (history) and :233-237 (tool results)
let t = m.content.as_text().map(|c| c.len() / 4).unwrap_or(0);
token_est += t;
```

This is byte-based (`c.len() / 4`), ignoring the configured `Tokenizer`
entirely — even though the assembler holds a `ContextBudget`, not a
`Tokenizer`. The docstring at `src/context/mod.rs:111-117` explicitly states
the default `ReactAgent` path does **not** use `ContextAssembler`, so this
inconsistency does not affect EKO today, but it means the same text produces
different token estimates depending on which framework API a third-party
consumer uses. Combined with the unchecked `token_est += t` (V01-01 site #5),
this is a latent footgun for reusers.

## Deviations

- `ContextAssembler` carries a parallel `ContextBudget` (10 fixed fields,
  `src/context/mod.rs:33-65`) with its own magic `396_000` default. Per
  AGENTS.md ("通用框架提供多个 Store/压缩器 是正常的框架设计"), a parallel
  building block with a different budget shape is acceptable *if* it is
  genuinely a different abstraction. Here it is documented as not used by the
  default runtime, so it does not create a second authority on the hot path —
  but its byte-based estimator and parallel `396_000` should at minimum be
  documented as divergent.
- Image `ContentPart::Image` bytes are not counted by `as_text()`
  (`echo-core/src/llm/types.rs:101-114` — only `ContentPart::Text` is
  collected). Multimodal message token cost is therefore under-estimated.
  Out of scope for this task (multimodal budgeting is a separate concern) but
  noted for the record.

## Conclusion

The claim is **not supported** in two of three sub-claims:

1. **F-CTX-01-P2-01** (full statement here, partial in V01-01): tool
   definitions are sent to the model but never counted by the framework's
   token estimate or budget. Large tool schemas silently consume window space
   the budget believes is free, producing provider 400 errors.
2. **F-CTX-01-P3-02**: `ContextAssembler` (a framework building block) uses a
   byte-based `len() / 4` estimator that diverges from the
   `HeuristicTokenizer` / `CalibratedTokenizer` used by `ContextManager`. Same
   text, different estimate, depending on path. Third-party reusers hit this;
   EKO's default ReactAgent path does not.

The UTF-8 safety sub-claim **is supported**: every counting path is
panic-free under multilingual / CJK / emoji input, and the
`CalibratedTokenizer` cast is saturating.
