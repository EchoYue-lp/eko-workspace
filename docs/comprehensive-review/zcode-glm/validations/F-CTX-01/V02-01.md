## Claim

Content that must survive compression — canonical system prompt, project rules,
skill injections, marker-protected messages, and active tool-call / tool-result
pairing — is deterministically preserved by `ContextManager::prepare()` and re-
injected after every compression pass, and its token cost is accounted against
the budget so the model window is not silently exceeded.

## Expected Result

- Protected content is excluded from compression and re-inserted at its original
  relative position.
- Canonical system prompt / rules / skills are restored after compression even
  if the compressor evicted them.
- Active tool-call ↔ tool-result pairs are kept valid.
- The token cost of protected content is deducted from the conversation budget
  so the model does not receive an over-long request.

## Result

- Exit code: not-applicable (static inspection)
- Summary: **First three expectations hold. The fourth fails.** Protected
  content survives compression correctly, but its token cost is **not** deducted
  from the budget, so enough protected content can push the real request past
  the model's window.

### What is protected

`is_protected` (`compression/mod.rs:679-691`) returns `true` when either:

1. The message is a framework projection (wrapped with the
   `PROJECTION_ENVELOPE_PREFIX` envelope by `wrap_projection_message`
   `:725-741`); or
2. The message's text content contains a substring listed in
   `protected_markers` (static, registered via `add_protected_marker`
   `:524-528`) or `replaceable_protected_markers` (latest-wins, registered via
   `add_replaceable_protected_marker` `:534-537`).

Marker examples in the framework: `[critical_policy]`, `<skill_content>`,
subagent brief markers. The set is consumer-extensible.

### How protected content survives compression

`split_protected` (`:747-773`) pulls protected messages out of the compressible
list before the compressor runs, recording each one's
`compressible_after` / `protected_after` offset. `merge_protected`
(`:781-793`) re-inserts them, iterating in reverse so each message reserves its
original trailing slot count. This preserves relative ordering. Verified by
`context_projection_preserves_unrelated_marker_text`
(`compression/mod.rs:2016-2037`) and the surrounding projection tests
(`:1944-2013`).

`apply_hard_cap` (`:402-446`) — the supplementary `max_messages` backstop —
also skips protected messages and system messages when selecting which
non-protected messages to discard.

### Canonical re-injection (system prompt, rules, skills)

`reinject_canonical_context` (`:877-929`) runs at the end of every `prepare()`
that performed compression (`:1528-1530`), and also at the end of every
`force_compress*` variant (`:1070-1072`, `:1143-1145`, `:1202-1204`).

- **System prompt**: if the canonical `system_prompt` is not present verbatim
  in any `Role::System` message, it is inserted at index 0 (`:884-893`).
- **Supplemental canonical messages**: `to_reinjection_messages()`
  (`echo-core/src/compression.rs:376-401`) produces a `[Canonical context —
  project rules restored]: …` message (rules truncated to 2000 chars via
  `rules.chars().take(2000).collect()`) and a `[Canonical context — active
  skills]: …` listing. These are inserted at the system/history boundary
  (`sys_end`, `:905-927`) with dedup against the existing system region, so
  repeated compressions do not accumulate duplicates. The insertion-point
  rationale (`:896-904`) is explicitly to preserve provider prefix caches
  (Anthropic explicit breakpoints, OpenAI automatic prefix caching).

### Active tool-call pairing

Compression can evict an assistant tool_call without its tool_result (or vice
versa). `sanitize_tool_call_pairing` (`:1660-1708`, invoked at `:1448-1459`
inside `prepare()`) repairs three cases after compression:
`OrphanedResultRemoved`, `DanglingCallCleared`, `PlaceholderResultInserted`
(`echo-core/src/compression.rs:62-76`). Tool-call pairing is therefore
structurally preserved even when the compressor itself is unaware of pairing.

### What is NOT protected

There is **no** "recent N messages always protected" mechanism. Protection is
strictly marker-based or projection-envelope-based. A recent assistant
tool_call that carries no protected marker is treated as ordinary compressible
history; if a compression pass fires mid-tool-flow, the tool_call/tool_result
pairing survives (via `sanitize_tool_call_pairing`) but the messages themselves
may be summarised away by `SummaryCompressor` / `IncrementalSummaryCompressor`.

### Token-cost accounting gap (expectation 4 fails)

`protected_token_estimate` exists (`:656-665`) and correctly sums the tokens of
protected messages — but it is **observability only**. Nothing on the
`prepare()` path subtracts `protected_token_estimate()` from
`conversation_budget` or `effective_limit`:

```rust
// compression/mod.rs:1299-1305
let effective_limit = if let Some(ref budget) = self.budget {
    let allocation = budget.allocate(0, 0, estimated_tokens);   // est INCLUDES protected
    (estimated_tokens.saturating_sub(allocation.conversation_excess))
        .max(self.token_limit / 2)
} else { self.token_limit };
```

`estimated_tokens` here is computed over **all** messages including protected
ones (`estimate_tokens` at `:1541-1547` iterates `self.messages` with no
filter). So protected content does inform the *trigger* (it contributes to
`estimated_tokens`), but when the compressor runs it is given
`effective_limit` tokens to fit the **compressible** subset, and the protected
messages are then merged back on top. The compressor has no knowledge that
protected messages will be re-added and will consume additional window space.

Concrete failure mode: a `replaceable_protected_marker` subagent brief of 30K
tokens + 130K conversation budget (200K window, 0.65) → compressor squeezes
history to 130K, then 30K protected is merged back → real request body ≈ 160K
messages, plus tool defs (see V04-01) and output reservation → can blow past
the 200K window. The 10% safety margin is supposed to absorb this, but it is
computed from a budget whose category inputs are always zero (V01-01), so the
margin is fictional.

### Rules-truncation inconsistency

`CanonicalContext::to_reinjection_messages` truncates `project_rules` to 2000
chars (`echo-core/src/compression.rs:385`) using the UTF-8-safe
`rules.chars().take(2000).collect()` (AGENTS.md-compliant). But the full rules
also live inside the canonical `system_prompt` (per F-RCT-01-P3-02), which is
re-injected untruncated. The 2000-char cap therefore does not bound total
rules footprint; it only bounds the supplemental copy. Already tracked as
F-RCT-01-P3-02; not a new finding here.

## Deviations

- `push()` (`:380-397`) applies `replaceable_protected_marker` semantics
  **before** appending the new message: it `retain`s only messages that do
  not contain the marker, then appends. This correctly implements latest-wins
  for dynamic protected content (e.g. a refreshed subagent brief replaces the
  prior one). Confirmed by `tail_projection_replaces_dynamic_context_near_latest_turn`
  (`:1970-1992`).
- The merge order in `merge_protected` (reverse iteration, `:787`) is subtle
  but correct: restoring from the tail lets each protected message reserve
  exactly its original trailing slot count. No finding.

## Conclusion

The claim is **partially supported**. Protected-content *survival* is
correctly and deterministically implemented (marker + projection + canonical
re-injection + tool-pair sanitisation). The claim's *budget-accounting* half is
**not** supported: protected-token cost is computed (`protected_token_estimate`)
but never deducted from the compressor's `effective_limit`, so the budget
system under-counts what the model will actually receive. This feeds
**F-CTX-01-P2-02**.
