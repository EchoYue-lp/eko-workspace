## Claim

The token-budget arithmetic path (model window → `TokenBudget` →
`ContextManager::prepare()` effective limit / `needs_compression`) is computed
without overflow risk and uses checked/saturating arithmetic as mandated by
`AGENTS.md` (Rust hard constraint #1/#2). The per-category reservations
(system / tool / output / safety) are wired to real measurements.

## Expected Result

1. All `usize` additions on the budget path use `checked_add` / `saturating_add`
   (per `AGENTS.md` Rust constraint #1/#2 and the workspace Clippy gate
   `-D clippy::arithmetic_side_effects` spirit).
2. `budget.allocate()` receives real per-category sizes so the 10% system /
   5% tool reservations actually protect those categories.

## Result

- Exit code: not-applicable (static inspection)
- Summary: **Both expectations fail.** Five unchecked `usize` arithmetic sites
  sit on the budget path, and `allocate()` is always called with
  `(system_size=0, tool_defs_size=0, conversation_size=estimated_tokens)`.

### Budget wiring (correctly resolves a window)

This part is correct: the window is resolved, clamped, and turned into a
`TokenBudget` with the documented 10/5/10/10 split.

### Overflow sites (unchecked `usize` arithmetic)

| # | Site | Code | Risk |
|---|------|------|------|
| 1 | `budget.rs:106` | `let total_used = system_size + tool_defs_size + conversation_size;` | `usize + usize + usize`. Public API of `allocate()`; a future caller passing three near-`usize::MAX` values panics in debug. Currently called with `(0, 0, est)` so not reached today. |
| 2 | `compression/mod.rs:1546` | `estimate_tokens`: `.map(\|c\| tokenizer.count_tokens(&c)).sum()` | `Iterator::sum::<usize>()` is plain `+=`. Drives `needs_compression` / `effective_limit`. Summing many large messages can wrap in debug. |
| 3 | `compression/mod.rs:664` | `protected_token_estimate`: `.map(...).sum()` | Same pattern; observability-only. |
| 4 | `compression/mod.rs:1003` | `let total = system + user + assistant + tool + summary + memory;` | Six-way `usize` chain; observability-only. |
| 5 | `src/context/mod.rs:209,234` | `ContextAssembler::assemble`: `token_est += t;` where `t = c.len() / 4` | Plain `+=` in the parallel building-block assembler (not on the ReactAgent hot path). |

None of these is a likely trigger on EKO's local single-user threat model
(messages are bounded by what one user types). But they violate the letter of
`AGENTS.md` Rust constraint #2 ("禁止任何会导致系统 panic 的 API … 整数运算可能溢出
→ `checked_add` / `saturating_*`"). The workspace Clippy gate that would catch
new instances (`-D clippy::arithmetic_side_effects`) is **not** in the
configured lint set — `AGENTS.md` lists `unwrap_used`/`expect_used`/`panic`/
`unreachable` only — so the pattern is silently accreting.

### Phantom per-category reservations (allocate always gets zeros)

`prepare()` calls the budget like this:

```rust
// compression/mod.rs:1300
let allocation = budget.allocate(0, 0, estimated_tokens);          // effective_limit
// compression/mod.rs:1311
let allocation = budget.allocate(system_tokens=0, tool_tokens=0, estimated_tokens);  // needs_compression
// compression/mod.rs:474  (should_compress)
let allocation = budget.allocate(0, 0, estimated_tokens);
```

The inline comments admit it: `// system prompt tokens already counted in
messages` and `// tool defs not in messages`. Consequences:

- `system_fits = (0 <= system_prompt_budget())` is always `true`. The 10%
  system reservation is never tested. The system prompt actually lives inside
  the conversation bucket (it is the first `Message` with `role=System` and is
  counted by `estimate_tokens`), so the conversation bucket is silently
  short-changed by the system-prompt size while 10% of the window sits empty.
- `tool_defs_fit = (0 <= tool_definitions_budget())` is always `true`. The 5%
  tool reservation is dead. Tool definitions are never measured at all
  (see V04-01).
- `conversation_budget()` returns `0.65 * window`, which must in reality hold
  system + history; the real free space for history is `0.65*window − system −
  tools`, which the framework never computes.

## Deviations

- The window-resolution and `TokenBudgetConfig::build` plumbing is correct and
  was verified against `default_budget_uses_396k_context_window`
  (`budget.rs:276-279`) and `infers_current_frontier_context_windows`
  (`capabilities.rs:603-638`).
- `apply_hard_cap` at `compression/mod.rs:402-446` does `self.messages.len() -
  target` (plain subtraction) but is gated by an upstream `len() > cap` check
  at `:392-396`, so it cannot underflow. Acceptable.

## Conclusion

The claim is **not supported**. Two distinct defects exist:

1. **F-CTX-01-P3-01**: five unchecked `usize` arithmetic sites on the budget
   path violate the `AGENTS.md` checked-arithmetic rule. Low realistic impact
   (local single-user threat model) but non-compliant.
2. **F-CTX-01-P2-01** (partial — full evidence in V04-01): the budget's
   `system_prompt_budget` and `tool_definitions_budget` reservations are
   phantom — `allocate()` is always called with `(0, 0, est)`, so the
   per-category fit checks are no-ops and the 10%+5% reservations sit empty
   while the conversation bucket silently absorbs the system prompt.

The core arithmetic (window → percentages → `conversation_budget`) is
mathematically sound; the defects are in the wiring of measurements into the
budget and in the choice of integer operators.
