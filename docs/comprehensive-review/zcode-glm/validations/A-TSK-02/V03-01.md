## Claim

EKO task schemas (`EkoTaskSpec`, `EkoTaskExecution`, `TaskPatch`,
`TaskUpdateOperation`, `TaskUpdateRequest`, `PlanTask`) match the
framework's `TaskSpec` / `TaskExecution` / `TaskSpecPatch` /
`TaskPlanPatchOp` / `TaskPlanPatch` field-by-field. EKO-only fields
(`domain_profile`, `parallel_group`, `sort_order`) ride through
`TaskSpec.metadata` as `EkoTaskMetadata` JSON without loss. The tool
schema exposed to the LLM (via `task_create_schema` /
`task_update_schema`) matches the EKO IPC `TaskUpdateOperation` shape,
including the deliberate omission of `set_status` on the EKO path.

## Method

Field-by-field comparison of the framework and EKO types at the
conversion sites, plus the JSON schema exposed by the framework tools.

```text
Read echo-agent/echo-orchestration/src/tasks/runtime.rs (1-260) [framework TaskSpec/TaskExecution/TaskStatus/TaskKind]
Read echo-agent/echo-orchestration/src/tasks/revisioned.rs (40-152, 247-340, 670-900) [TaskDraft/TaskCreateInput/TaskSpecPatch/TaskPlanPatchOp/TaskToolPolicy]
Read echo-agent/echo-orchestration/src/tasks/task_tools.rs (220-400) [task_create_schema/task_update_schema/task_input_schema/task_kind_schema]
Read echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/types.rs (800-1320) [EkoTaskSpec/EkoTaskExecution/PlanTask/TaskPatch/TaskUpdateOperation/TaskUpdateRequest]
Read echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/revisioned_adapter.rs (214-296) [prepare_task/validate_candidate]
```

## Expected Result

- 1:1 mapping between EKO `EkoTaskSpec` fields and framework `TaskSpec`
  fields, with EKO-only fields packed into `metadata`.
- 1:1 mapping between EKO `EkoTaskExecution` fields and framework
  `TaskExecution` fields.
- 1:1 mapping between EKO `TaskPatch` and framework `TaskSpecPatch`.
- The EKO `TaskUpdateOperation` enum variants are a subset of (or equal
  to) the framework `TaskPlanPatchOp` variants, and the tool schema
  exposed via `task_update_schema` matches the EKO IPC enum.
- The `task_kind_schema` exposed by the framework tool matches the
  `PlanTaskKind::to_task_kind()` round-trip (8 variants).

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **Spec parity (positive).** Framework `TaskSpec`
    (`echo-orchestration/src/tasks/runtime.rs:179-195`) has 13 fields:
    `id`, `title`, `description`, `kind`, `agent_role`, `depends_on`,
    `files`, `allowed_tools`, `required_artifacts`, `execution_checks`,
    `acceptance_criteria`, `max_retries`, `metadata`. EKO `EkoTaskSpec`
    (`echo-agent-app-core/src/tasks/task_runtime/types.rs:870-889`) has
    15 fields: the same 12 fields above (excluding `metadata`) plus
    `domain_profile`, `parallel_group`, and `sort_order`. The conversion
    `EkoTaskSpec::to_task_spec` (`types.rs:892-914`) maps the 12
    shared fields 1:1 and packs `domain_profile + parallel_group +
    sort_order` into `TaskSpec.metadata` as `EkoTaskMetadata` JSON
    (`revisioned_adapter.rs:228-235` does the same from `prepare_task`).
    The inverse `TryFrom<Task> for PlanTask` (`types.rs:1162-1201`)
    unpacks `metadata` via `serde_json::from_value::<EkoTaskMetadata>`.
    No spec field is dropped. (Carry-over from A-TSK-01 V02-01.)
  - **Execution parity (positive).** Framework `TaskExecution`
    (`runtime.rs:228-235`): `task_id`, `status`, `retry_count`,
    `failure_fingerprint`, `claim`. EKO `EkoTaskExecution`
    (`types.rs:921-929`): the same 5 fields, with `status` typed as the
    framework `echo_agent::tasks::TaskStatus` directly (no projection).
    `PlanTask::execution` (`types.rs:1081-1089`) and
    `PlanTask::from_parts` (`types.rs:1091-1114`) carry the framework
    status by identity at the type layer. (Persistence-side lossiness
    for `Retrying`/`Paused` is recorded as A-TSK-01-P2-02; not in scope
    here.)
  - **Patch parity (positive).** Framework `TaskSpecPatch`
    (`revisioned.rs:78-90`): 11 `Option<…>` fields. EKO `TaskPatch`
    (`types.rs:1221-1233`): the same 11 `Option<…>` fields.
    `TaskPatch::to_task_spec_patch` (`types.rs:1236-1250`) maps every
    field 1:1, including `kind: Option<PlanTaskKind>` →
    `Option<TaskKind>` via `PlanTaskKind::to_task_kind`.
  - **Op parity — tool path (positive, deliberate asymmetry).**
    Framework `TaskPlanPatchOp` (`revisioned.rs:94-113`) has 5
    variants: `Insert`, `Update`, `Skip`, `Reorder`, `SetStatus`.
    Framework `TaskPlanPatchInputOp` (`revisioned.rs:125-144`) mirrors
    those 5 (input-shape variant). The tool schema `task_update_schema`
    (`task_tools.rs:251-334`) emits 4 base operations and adds
    `set_status` only when `service.allow_manual_progress_updates()`
    returns true (`task_tools.rs:309-320`). `DefaultTaskToolPolicy`
    returns true (`revisioned.rs:338-340`); the trait default is false
    (`revisioned.rs:275-277`). `EkoTaskToolPolicy` does NOT override
    `allow_manual_progress_updates` (verified by reading the full
    `impl TaskToolPolicy for EkoTaskToolPolicy` at
    `revisioned_adapter.rs:105-296`: only `task_input_schema_extensions`,
    `resolve_scope`, `ensure_scope`, `prepare_task`,
    `prepare_initial_context`, `finalize_task_metadata`,
    `validate_candidate`). Therefore the EKO `task_update` tool schema
    OMITS `set_status`.
  - **Op parity — IPC path (matches the tool path).** EKO's own
    `TaskUpdateOperation` (`types.rs:1254-1272`) has exactly 4
    variants: `Insert`, `Update`, `Skip`, `Reorder`. No `SetStatus`.
    `TaskUpdateRequest::to_task_plan_patch` (`types.rs:1284-1316`)
    maps those 4 variants to the framework `TaskPlanPatchOp` 4 matching
    variants. The IPC path therefore cannot produce a `SetStatus` op,
    consistent with the tool schema.
  - **Kind parity (positive).** Framework `TaskKind`
    (`runtime.rs:22-39`) has 8 variants; `task_kind_schema`
    (`task_tools.rs:395-400`) exposes the same 8 string values:
    `implementation`, `debugging`, `verification`, `review`,
    `investigation`, `test_plan`, `summary`, `read_only_review`. EKO
    `PlanTaskKind` maps 1:1 onto this via `to_task_kind` / `from_task_kind`
    (verified in A-TSK-01 V02-01; the `task_kind_schema` strings match
    `TaskKind::as_str()`).
  - **Schema-extension parity.** The framework tool schema includes
    `task_input_schema_extensions` injected by the policy
    (`task_tools.rs:336-393`, particularly line 384).
    `EkoTaskToolPolicy::task_input_schema_extensions`
    (`revisioned_adapter.rs:107-112`) returns exactly one extension:
    `parallel_group: { "type": "string" }`. This appears in the
    `task_create` and `task_update` schemas exposed to the LLM. The IPC
    `EkoTaskSpec`/`TaskPatch` DTOs model `parallel_group` as
    `Option<String>` (`types.rs:880, 873`), so the same field round-trips
    through both surfaces.
  - **Required-fields parity.** Framework `task_input_schema` requires
    `["id", "title", "description", "kind"]` (`task_tools.rs:391`); the
    EKO DTOs' TS annotations and `Default::default` for `PlanTask`
    (`types.rs:1033-1058`) treat the same fields as required at the
    product layer. `parse_task_draft` (`task_tools.rs:527-575) enforces
    the same four as required when parsing tool input.
- Log/artifact: none

## Deviations

None on schema parity. The deliberate omission of `SetStatus` from the
EKO path (tool + IPC) is by design — `EkoTaskToolPolicy` chooses not to
enable manual progress updates, matching the EKO DTO. The framework
keeps the op available for `DefaultTaskToolPolicy` consumers.

## Conclusion

EKO task schemas match the framework's `TaskSpec` / `TaskExecution` /
`TaskSpecPatch` field-by-field, with the EKO-only metadata fields
packed losslessly into `TaskSpec.metadata`. The `TaskUpdateOperation`
enum is consistent across the tool and IPC surfaces (4 ops, no
`SetStatus`); the framework tool schema reflects the same set via the
`allow_manual_progress_updates()` gate. Supports the task report's
primary conclusion. No finding raised from this validation.
