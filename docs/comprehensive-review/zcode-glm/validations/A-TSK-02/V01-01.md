## Claim

The set of task-relationship tools registered on an EKO agent is exactly
`task_create` + `task_update` + `task_list` (framework defaults, replaced
in-place by name with EKO-backed store/policy) plus four EKO-owned
orchestration tools (`task_execute`, `create_complex_task`,
`check_run_status`, `cancel_run`). No `todo_write` / `plan_create` /
`plan_patch` / `plan_execute` tool is registered, and no global todo state
is held outside the `TaskRuntimeStore` projection.

## Method

Full read of the registration module and the EKO-owned tool module, plus
the framework's default-registration site and the `ToolManager::register`
mechanics, plus a name inventory of every tool defined in the
`echo-agent-cli` tree.

## Expected Result

- Framework default agent installs `task_create`/`task_update`/`task_list`
  (in-memory store, default policy).
- EKO post-hoc registration swaps those three tools by name and adds four
  EKO-owned tools; no name collision, no parallel task-authoring API.
- The `TASK_TOOLS` constant on the policy/mode layer lists exactly
  `task_create`, `task_update`, `task_list`, `task_execute`.
- Zero `todo_write` / `plan_create` / `plan_patch` / `plan_execute` tool
  registrations anywhere in `echo-agent-cli`.

## Result

- Exit code: 0
- Duration: <3s
- Summary:
  - **Framework default registration.** `ReactAgent::new`
    (`echo-agent/src/agent/react/mod.rs:386-400`) builds an
    `InMemoryRevisionedTaskStore` + `DefaultTaskToolPolicy::default()`,
    constructs a `TaskRevisionService`, and calls
    `tool_manager.register_tools(echo_orchestration::tasks::build_task_tools(task_revision_service))`.
    `build_task_tools` (`echo-orchestration/src/tasks/task_tools.rs:205-211`)
    returns exactly `TaskCreateTool` / `TaskUpdateTool` / `TaskListTool`,
    whose `fn name()` return `"task_create"` / `"task_update"` /
    `"task_list"`. So every ReactAgent starts with those three names
    registered.
  - **EKO replacement is name-based and atomic.** The TaskRuntimeStore is
    not available at agent construction, so EKO registers task tools
    post-hoc. `register_task_tools_on_agent`
    (`echo-agent-cli/echo-agent-app-core/src/tasks/task_runtime/register.rs:45-130`)
    builds the EKO revision service via
    `build_eko_task_revision_service` and calls
    `echo_agent::tasks::register_task_tools(agent, revision_service)`
    (`register.rs:65`). That framework function
    (`echo-agent/src/tasks.rs:18-23`) calls
    `agent.add_tools(build_task_tools(service))`.
    `ReactAgent::add_tools` (`capabilities.rs:43-58`) calls
    `ToolManager::register_tools` (`echo-execution/src/tools.rs:534-539`),
    whose body is `for tool in tools { self.tools.insert(tool.name().to_string(), tool); }`.
    The insertion is keyed by `tool.name()`, so the three EKO-backed
    tools replace the three default in-memory ones atomically — no second
    `task_create` API is exposed. The docstring on
    `echo_agent::tasks::register_task_tools`
    (`echo-agent/src/tasks.rs:15-17`) explicitly states this:
    "Tool registration is name-based, so this atomically selects the
    supplied store/policy adapter without exposing a second task API."
  - **EKO-owned orchestration tools (additive).** After the framework
    swap, `register_task_tools_on_agent` adds:
    - `CreateComplexTaskTool { subagent_catalog }` (`register.rs:69-71`)
      → `fn name() = "create_complex_task"` (`task_tools.rs:801-804`).
    - `CheckRunStatusTool` (`register.rs:72`) → `fn name() =
      "check_run_status"` (`task_tools.rs:1041-1044`).
    - `CancelRunTool` (`register.rs:73`) → `fn name() = "cancel_run"`
      (`task_tools.rs:1102-1105`).
    - `ExecuteTaskTool::new(store, agent_handle)` (`register.rs:88-94`)
      → `fn name() = "task_execute"` (`task_execute_tool.rs:202-205`).
    None of the four is a task/plan/todo CRUD: `create_complex_task`
    bootstraps a Run (UUID + `store.create_run` + spawn
    `drive_run_async`); `check_run_status` is read-only; `cancel_run`
    calls `store.request_cancel` (run-level); `task_execute` dispatches
    `execute_run` against a committed revision.
  - **Pool path adds the same `task_execute`.** `bind_task_execute_to_pool`
    (`register.rs:136-154`) constructs
    `ExecuteTaskTool::new(store, handle).with_agent_pool(Weak<AgentPool>)`
    and calls `agent.add_tool(Box::new(tool))`. Same `task_execute` name;
    only the agent-resolution strategy differs (pool vs primary).
  - **Policy/mode layer lists exactly the canonical four.**
    `echo-agent-cli/echo-agent-app-core/src/tool_exposure.rs:69`:
    `const TASK_TOOLS: &[&str] = &["task_create", "task_update", "task_list", "task_execute"];`
    — and the visibility tests at lines 219-267 assert exactly these
    four appear in the registered tool set after EKO registration.
  - **Registration entry points.** Both product entry points call the same
    function: TUI at `echo-agent-cli/src/main.rs:177` and GUI at
    `echo-agent-cli/src/tauri/desktop.rs:201`. AGENTS.md TUI/GUI parity
    holds at the tool layer.
  - **Negative assertion in the framework.** The framework test
    `default_agent_uses_one_task_relation_api`
    (`echo-agent/src/agent/react/builder.rs:1170-1183`) asserts that
    `task_create`/`task_update`/`task_list` ARE registered and that
    `todo_write` is NOT. The application layer inherits this guarantee.
- Log/artifact: none

`task_create` / `task_update` / `task_list` trio, swapped in-place to

operate on run lifecycle (not on the task graph). No banned parallel
CRUD tool name is registered. Supports the task report's primary
conclusion and the V04 forbidden-CRUD result.
