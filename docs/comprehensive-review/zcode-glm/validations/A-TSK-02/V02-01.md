## Claim

Each of the three framework task tools (`task_create` / `task_update` /
`task_list`) and the IPC Tauri `update_tasks` command forwards to the
single framework `TaskRevisionService` through the EKO adapter pair
(`EkoRevisionedTaskStore` + `EkoTaskToolPolicy`). No EKO code path
mutates the task graph directly through `TaskRuntimeStore`; the EKO-owned
tools (`task_execute`, `create_complex_task`, `check_run_status`,
`cancel_run`) operate strictly on run state, not on the task graph.

## Method

Read of every framework tool's `execute_with_context` body, the framework
`TaskRevisionService` API surface, the EKO adapter, and the IPC Tauri
command; cross-checked each tool's direct calls into `TaskRuntimeStore`.

## Expected Result

- `task_create`/`task_update`/`task_list` (framework) call
  `service.create_from_tool` / `update_from_tool` / `load`; no direct
  `TaskRuntimeStore` mutation.
- The IPC `update_tasks` command reaches the same service via
  `apply_eko_task_update` → `service.apply_patch`.
- The EKO-owned `task_execute` / `create_complex_task` /
  `check_run_status` / `cancel_run` touch only run state (`create_run`,
  `transition_run`, `request_cancel`, `get_run`, `get_plan`), never the
  task graph mutators (`set_task_status`, `compare_and_commit_*`,
  `attach_plan*`).
- The only `commit_eko_task_plan` callers are the initial-plan paths
  (planner, background service), not the agent tools.

## Result

- Exit code: 0
- Duration: <3s
- Summary:
  - **`task_create` is a thin wrapper.**
    `TaskCreateTool::execute_with_context`
    (`echo-orchestration/src/tasks/task_tools.rs:42-79`) parses input
    locally (`parse_task_create_input`, lines 402-439) then forwards to
    `self.service.create_from_tool(input, context).await`
    (`task_tools.rs:56`). The branch handles only result formatting.
    `TaskRevisionService::create_from_tool`
    (`echo-orchestration/src/tasks/revisioned.rs:713-823`) is the
    authority: it resolves scope via `EkoTaskToolPolicy::resolve_scope`,
    bootstraps a Run via `ensure_scope`, prepares drafts via
    `prepare_task`, calls `validate_candidate`, and commits via
    `EkoRevisionedTaskStore::compare_and_commit`. The framework tool
    holds no `TaskRuntimeStore` handle. V01-01 confirms.
  - **`task_update` is a thin wrapper.**
    `TaskUpdateTool::execute_with_context`
    (`echo-orchestration/src/tasks/task_tools.rs:109-141`) parses input
    (`parse_task_update_input`, lines 441-525) and forwards to
    `self.service.update_from_tool(input, context).await`
    (`task_tools.rs:123`). The service normalizes input ops to canonical
    `TaskPlanPatchOp` (`revisioned.rs:825-892`) and applies via
    `apply_patch_to_loaded` → `compare_and_commit`. The `set_status` op
    is schema-gated by `service.allow_manual_progress_updates()` and
    rejected by the parser otherwise (`task_tools.rs:497, 309`).
  - **`task_list` is a thin wrapper.**
    `TaskListTool::execute_with_context`
    (`echo-orchestration/src/tasks/task_tools.rs:166-203`) calls
    `self.service.resolve_scope(context).await` then
    `self.service.load(&scope_id).await`, formatting the tasks as text.
    No store handle; pure service-mediated read.
  - **IPC `update_tasks` reaches the same service.**
    `echo-agent-cli/src/tauri/commands/task_runtime.rs:399-427` builds
    the EKO revision service via `task_revision_service_for_agent` and
    calls `apply_eko_task_update(&service, &store, &run_id, request)`.
    `apply_eko_task_update`
    (`echo-agent-app-core/src/tasks/task_runtime/revisioned_adapter.rs:321-339`)
    converts `TaskUpdateRequest` → framework `TaskPlanPatch` via
    `to_task_plan_patch` (`types.rs:1284-1316`) and calls
    `service.apply_patch(run_id, patch).await`
    (`echo-orchestration/src/tasks/revisioned.rs:920-…`). The IPC and
    tool paths share one mutator.
  - **`task_execute` is a dispatcher (not a CRUD).**
    `ExecuteTaskTool::execute`
    (`task_execute_tool.rs:236-490`) has schema `{revision: integer ≥ 1}`
    (lines 222-234). It reads `store.get_plan(&run_id)` and
    `store.get_run(&run_id)`, rejects on revision mismatch
    (line 277), runs unattended preflight, acquires a per-run execution
    lock, and dispatches `execute_run(...)` (line 401). The only
    `store.*` writes from the tool are run-level:
    `store.transition_run(&run_id, TaskRunStatus::Failed)` on preflight
    rejection (line 306) and `store.register_run_cancellation`
    (line 380) / `store.note` (line 308). No call to
    `compare_and_commit_*`, `set_task_status`, or `attach_plan*`. The
    task graph is mutated only by `execute_run`'s internal controller
    (out of scope, A-TSK-03).
  - **`create_complex_task` mutates run state only.**
    `CreateComplexTaskTool::do_create`
    (`task_tools.rs:842-1033`) reads chat resources, then calls
    `store.create_run(&run_id, …, "agent_autonomous", attended)`
    (line 957), `store.set_run_attachments` (line 972),
    `store.transition_run(&run_id, Running)` (line 976), and spawns or
    awaits `drive_run_async(payload)` (lines 1010, 1028). No
    task-graph mutator is called; the spawned agent is expected to call
    `task_create` itself.
  - **`check_run_status` and `cancel_run` are read/cancel run helpers.**
    `CheckRunStatusTool::do_check` (`task_tools.rs:1071-1096`) calls
    `store.get_run(&run_id)` only. `CancelRunTool::do_cancel`
    (`task_tools.rs:1131-1153`) calls `store.request_cancel(&run_id)`.
    Neither touches the task graph.
  - **`BackgroundTaskService` is run-lifecycle, not task CRUD.**
    `echo-agent-app-core/src/tasks/service.rs` write paths:
    `create_run` (lines 281, 322), `record_trigger_metadata`
    (lines 291, 347), `transition_run` (lines 400, 484, 528, 584, 808,
    836, 846), `request_cancel` (line 459), `request_pause` (line 464),
    `resume_task_run` (lines 481, 583), `retry_blocked_task`

    834, 842). For DAG submission it calls
    `super::task_runtime::commit_eko_task_plan` (line 332), which is
    the planner commit adapter that routes through
    `TaskRevisionService::create_prepared` (revisioned_adapter.rs:379).
    The unified-list helpers (`list_unified`, `get_unified`,
    `get_progress`) only call `list_runs_in` / `get_run` / `list_todos`

## Deviations

One caveat surfaced for `create_complex_task` (not the thin-wrapper
claim): when `chat_resources` exists but `conv_id` is `None`, the tool
synthesizes `conversation_id = format!("message:{run_id}")`
(`task_tools.rs:953-955`) and forwards whatever `root_message_id` is
present (possibly empty). The synthetic id does not match the
`background:` prefix that `BackgroundTaskService::list_unified` filters
on, so such runs are unreachable from the background-listing API. This
is recorded as A-TSK-02-P3-01; it does not affect the thin-wrapper
conclusion (the tool still does not mutate the task graph).

## Conclusion

All four task-relationship surfaces (framework `task_create` /
`task_update` / `task_list` / IPC `update_tasks`) forward to the single
framework `TaskRevisionService` via the EKO adapter pair; no EKO code
path mutates the task graph directly. The four EKO-owned orchestration
tools operate strictly on run state. Supports the task report's primary
conclusion. The single finding (A-TSK-02-P3-01) is a run-state
robustness caveat, not a thin-wrapper violation.
