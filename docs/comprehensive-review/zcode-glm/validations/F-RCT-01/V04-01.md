## Claim

When a Cargo feature (`human-loop`, `subagent`, `mcp`, `tasks`, etc.) is
disabled, calling the corresponding builder method
(`enable_human_in_loop()`, `enable_subagent()`, `register_agent_dispatch_tool()`,
etc.) either (a) fails to compile, (b) returns an error at `build()` time,
or (c) at minimum leaves the `AgentConfig` flag matching the runtime state
(flag is `false` if and only if the capability is absent). The agent does
not silently advertise a capability it does not have.

## Method

Two-phase executable inspection.

### Phase 1 — compile and run a probe under `--no-default-features`

Created a temporary integration test at
`echo-agent/tests/f_rct_01_probe.rs` containing two cases:

```rust
#[test]
fn feature_gated_builder_flags_are_true_but_tools_absent() {
    use echo_agent::prelude::ReactAgentBuilder;
    let agent = ReactAgentBuilder::new()
        .model("probe")
        .system_prompt("p")
        .enable_tools()
        .enable_human_in_loop()       // sets config.enable_human_in_loop = true
        .enable_subagent()            // sets config.enable_subagent = true
        .build()
        .unwrap();
    assert!(agent.config().is_human_in_loop_enabled());
    assert!(agent.config().is_subagent_enabled());
    let names = agent.tool_names();
    assert!(!names.iter().any(|n| n == "human_in_loop"),
        "without human-loop feature the tool should NOT be registered");
    assert!(!names.iter().any(|n| n == "agent_tool"),
        "without subagent feature agent_tool should NOT be registered");
}

#[test]
fn register_agent_dispatch_tool_flag_is_silent_noop_without_subagent_feature() {
    use echo_agent::prelude::ReactAgentBuilder;
    let agent = ReactAgentBuilder::new()
        .model("probe")
        .system_prompt("p")
        .enable_tools()
        .register_agent_dispatch_tool()
        .build()
        .unwrap();
    let names = agent.tool_names();
    assert!(!names.iter().any(|n| n == "agent_tool"),
        "without subagent feature the explicit register_agent_dispatch_tool() \
         is a silent no-op");
}
```

## Expected Result

For the claim to hold, at least one of:

- Phase 1 fails to compile (builder method is itself `#[cfg(feature = ...)]`
  gated), or
- Phase 1 returns `Err` from `build()`, or
- The `AgentConfig` flags end up `false` after `build()`.

Otherwise, the agent silently misrepresents its capabilities.

## Deviations

- `enable_subagent()` requires `enable_tools()` to be set first; the
  builder enforces this with a hard error at `builder.rs:864-870`
  (`"Enabling sub-agent dispatch (enable_subagent) requires enabling tool
  calls (enable_builtin_tools)"`). This guard fires regardless of the
  `subagent` feature flag. The probe was adjusted (added `.enable_tools()`)
  to get past this guard and reach the actual silent-noop behaviour. The
  guard itself is good — it catches one real mis-configuration — but it
  does not catch the more important case (feature flag off).

## Conclusion

The claim is **NOT supported** — this is a failed validation. With
`--no-default-features`, the builder silently accepts
`enable_human_in_loop()`, `enable_subagent()`, and
`register_agent_dispatch_tool()`, sets the corresponding `AgentConfig`
flags to `true`, and returns a working agent that lacks the requested
capability. The flags and the runtime state diverge with no diagnostic.

This produces finding **F-RCT-01-P3-01**: feature-gated builder methods
silently no-op when their Cargo feature is disabled, leaving misleading
`AgentConfig` state. Priority is P3 (not P1/P2) because:

1. The affected capabilities (HITL, subagent dispatch, MCP) are opt-in
   extensions, not the core ReAct path; their absence does not crash the
   agent or corrupt data.
2. The divergence is observable through `agent.tool_names()` and through
   runtime behaviour, so a careful caller can detect it.
3. Most production consumers (including EKO) build with the relevant
   features enabled; the trap fires mainly for downstream framework
   consumers who trim features.

The validation confirms the *positive* direction (with features on,
behaviour is correct) and the *negative* direction (without features,
behaviour is silently wrong), so the finding is high-confidence.

## Follow-Up

None. The corresponding finding F-RCT-01-P3-01 records the recommended

build-time consistency check that clears the flag when the feature is
