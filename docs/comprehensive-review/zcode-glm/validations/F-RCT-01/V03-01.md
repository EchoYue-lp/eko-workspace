## Claim

`ReactAgent::build_system_prompt` assembles the canonical system prompt
deterministically: given the same `AgentConfig` and the same on-disk
project-rules files, the assembled string is byte-identical. The ordering
of sections is well-defined and documented. The separately-stored
`CanonicalContext.project_rules` is a post-compression re-injection
mechanism, not a parallel live prompt.

## Expected Result

## Result

- Exit code: not-applicable (static inspection)
- Summary:

### Deterministic ordering observed

`build_system_prompt(&config)` (`mod.rs:676-723`) composes the prompt in
this fixed order:

```text
[ project_rules ]\n\n           (PREPENDED, only when feature=project-rules
                                 AND config.auto_project_rules; via
                                 inject_rules_with_root at mod.rs:715-719)
[ config.system_prompt ]         (the user/base prompt)
\n\n[ COT_INSTRUCTION ]          (only when enable_tool AND enable_cot;
                                 mod.rs:683-691 — appended)
\n\n[ model_profile.prompt_suffix ]  (only when present and non-empty;
                                     mod.rs:693-701 — appended)
```

Final layout with every option enabled:

```text
<project_rules>

<base system_prompt>

Before calling any tool, briefly describe your analysis and execution plan.

<model_profile.prompt_suffix>
```

The composition uses only `format!`, `push_str`, and the helper
`inject_rules_with_root`. No iteration over unordered collections, no
thread/async races — all reads are over `&AgentConfig` fields or Mutex
guards held briefly and synchronously. The result is byte-identical for
identical inputs.

### Canonical context — separate concern, not parallel live prompt

`new_inner` (`mod.rs:358-382`) builds a `CanonicalContext` that stores:

- `system_prompt: Some(sp_for_canonical)` where `sp_for_canonical` is the
  full output of `build_system_prompt` (i.e. **includes** the prepended
  project rules). Anchor: `mod.rs:328, 360-361`.
- `project_rules: rules_injection_with_root(&wd, project_root)` — the raw
  rules content as a `Option<String>` (`mod.rs:371`).

The `ContextManager` is initialised with the same `system_prompt` via
`ctx_builder.with_system(system_prompt)` (`mod.rs:337`). So at construction
time the live system prompt and `canonical.system_prompt` are identical
strings, and `canonical.project_rules` redundantly stores the same content
that is already embedded in the system prompt string.

### Post-compression re-injection — partial duplication

`CanonicalContext::to_reinjection_messages` (`compression.rs:376-401`)
docs at `:373-375` state: "The base system prompt is restored directly by
`ContextManager`; this method returns only supplemental canonical context
so the prompt is not represented twice." The implementation honours that
for the *system prompt string* (it is never pushed into `msgs`), but the
*project rules content* — which is part of the restored system prompt —
IS pushed again as a supplemental message:

```rust
// compression.rs:383-390
if let Some(ref rules) = self.project_rules {
    let truncated: String = rules.chars().take(2000).collect();
    msgs.push(format!(
        "[Canonical context — project rules restored]:\n{}",
        truncated
    ));
}
```

Therefore, after a compression cycle, the LLM context contains the project
rules twice: once inside the restored system prompt, once inside the
supplemental canonical message. The duplication is bounded (the
supplemental copy is truncated to 2000 chars via UTF-8-safe
`chars().take(2000).collect()`) and is silent (no warning logged). See
finding F-RCT-01-P3-02.

### Runtime mutation paths

`ReactAgent::set_system_prompt` (`capabilities.rs:1348-1355`) updates
`config.system_prompt` and the live `ContextManager` system message, but
does **not** rebuild `CanonicalContext`. After a runtime `set_system_prompt`
call followed by compression, the canonical context would restore the
*old* system prompt. This is a known limitation of the sync
`set_system_prompt` path; `install_canonical_context`
(`mod.rs:1204-1210`) exists as the async-safe variant but is not called
by `set_system_prompt`. Out of scope for this task — flagged for F-RCT-02
(ReAct loop) or whichever task owns runtime prompt mutation.

## Deviations

1. Project-rules duplication after compression (see finding
   F-RCT-01-P3-02). Does not affect pre-compression determinism.
2. `set_system_prompt` does not refresh `CanonicalContext` (potential
   drift). Out of scope here; recorded for handoff.

## Conclusion

The claim is **supported with one caveat**. The system prompt assembly is
deterministic and well-ordered for the *initial* construction. The
`CanonicalContext.project_rules` field is a re-injection mechanism, not a
parallel live prompt — but its content overlaps with the rules already
embedded in `canonical.system_prompt`, producing a bounded duplication
after compression. F-RCT-01-P3-02 captures that observation.
