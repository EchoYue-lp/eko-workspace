## Claim

There is exactly one tool registry per `ReactAgent` instance. All tool
registration paths (presets, builder, post-build setters, MCP, skills,
subagent dispatch, runtime mutation) converge on the same
`ToolManager`. No parallel registry accumulates tools behind the agent's
back, and name-collisions resolve deterministically.

## Method

Read-only static inspection plus targeted `grep`.

1. Located the `ToolManager` definition and its `register`/`register_tools`
   semantics.
2. Enumerated every `tool_manager.register*` / `tool_manager.register_tools`
   call site reachable from `ReactAgent` construction and runtime APIs.
3. Verified the public capability API (`add_tool`, `add_tools`,
   `remove_tool`, `replace_tool`, `register_mcp_tools`) on
   `ReactAgent` all route through the same `tool_manager`.
4. Confirmed name-collision semantics are replacement, not accumulation.

## Result

- Exit code: not-applicable (static inspection)
- Summary:

### Single owner

`ToolExecutionSubsystem.tool_manager` is an `Arc<ToolManager>`
(`echo-agent/src/agent/react/subsystems/tool_exec.rs` via
`mod.rs:503-517`). Every registration path — whether invoked from
`new_inner`, the builder, the public capability API, or async MCP/skill
discovery — dereferences this single `Arc`. There is no second
`DashMap`/`HashMap`/`Vec` of tools on the agent.

### `ToolManager::register` semantics

```rust
// echo-agent/echo-execution/src/tools.rs:529-532
pub fn register(&self, tool: Box<dyn Tool>) {
    self.tools.insert(tool.name().to_string(), tool);
    self.invalidate_cache();
}
```

`self.tools` is a `DashMap<String, Box<dyn Tool>>` (`tools.rs:56`).
`DashMap::insert` **replaces** any existing entry with the same key and
returns the old value (which is dropped here). Therefore duplicate-name
registrations are idempotent replacement, never accumulation.

### Convergence of all registration paths

| Caller path | Where it lands |

| `new_inner` core tools (`FinalAnswerTool`, default `build_task_tools`) | `tool_manager.register*` (`mod.rs:393-400`) |

### Task-tool single-API invariant

`register_task_tools`'s docstring states it "atomically selects the
supplied store/policy adapter without exposing a second task API"
(`tasks.rs:16-17`). The default `build_task_tools` registered in
`new_inner` (`mod.rs:398-400`) uses an `InMemoryRevisionedTaskStore`;
when the builder supplies an application revision service, `register_task_tools`
calls `agent.add_tools(build_task_tools(service))`, which **replaces** the
default `task_create`/`task_update`/`task_list` tools by name. The result
is one task tool surface, never two.

This is verified by the unit test
`default_agent_uses_one_task_relation_api` (`builder.rs:1170-1183`): a
default-constructed agent has `task_create`, `task_update`, `task_list`
and **not** the historical `todo_write`.

## Deviations

Two related observations, neither invalidating the single-registry claim:

1. Memory tool registration has three textually-duplicated blocks
   (`setup_memory_store` at `mod.rs:767-776`, `set_memory_store` at
   `:1095-1111`, `install_memory_store` at `:1158-1173`). They are not
   concurrent code paths for the same agent — `setup_memory_store` runs
   only when `enable_memory` is true and no external store is supplied,
   while `set_memory_store`/`install_memory_store` run only when the
   caller supplies a store (the builder forces `config.enable_memory =
   false` at `builder.rs:948-951` precisely to keep these mutually
   exclusive). The duplication is a maintainability smell, not a parallel
   registry.
2. `set_memory_store` chooses between `Layered*Tool` and `Legacy*Tool`
   based on `self.memory_layer_manager` (`mod.rs:1080`), but
   `setup_memory_store` always registers the `Legacy*` variants
   (`mod.rs:767-776`). At construction time `memory_layer_manager` is
   always `None` (`mod.rs:574`), so the two paths register the same tool
   variants. The divergence would matter only for a caller that calls
   `install_memory_layer_manager` then `setup_memory_store` — but the
   former can only run after `new_inner`, by which time
   `setup_memory_store` has already executed.

## Conclusion

The claim is **supported**. There is exactly one tool registry
(`Arc<ToolManager>` in `ToolExecutionSubsystem`) per `ReactAgent`. All
registration paths — including the builder, the capability API, skill
discovery, MCP, and subagent dispatch — funnel through
`tool_manager.register`/`register_tools`. Duplicate-name registrations
replace rather than accumulate. The task-tool "single authority"
invariant is explicitly designed and unit-tested.

This is a positive confirmation: no finding arises from V02.
