## Claim

Cancellation propagates into every dispatched Subagent (via the cancel
token in `TaskSubagentContext`), applies a grace period before aborting,
drains the whole wave before honoring the stop outcome, and propagates
partial failure to the next safe point rather than failing mid-wave.
One gap: aborted tasks' claims are silently dropped and not resolved,
which can orphan `Running` rows (F-TSK-03-P2-02).

## Expected Result

- `cancel.clone()` is passed into each `TaskSubagentContext`
  (`with_cancel(task_cancel)` at runtime_executor.rs:345-346), so every
  dispatched Subagent can observe parent cancellation.
- The wave-drain `select!` is `biased` with three arms: `join_next`,
  `cancel.cancelled() if !cancellation_observed`, and
  `cancellation_grace if cancellation_observed`.
- On cancel: set `cancellation_observed = true`, reset grace to
  `now + cancellation_grace_period`. Do NOT abort immediately.
- After grace: `join_set.abort_all()`, then drain remaining joins.
  Aborted tasks (`Err(cancelled)`) are silently dropped — NOT resolved.
- Completed siblings that finished before the abort ARE resolved
  (`Ok(Some(result)) => wave_results.push`).
- `pending_outcome` starts as `Cancelled` if cancellation was observed
  (line 416). The wave is fully resolved before returning the outcome
  (comment at 443-447).
- A `Failed` resolution does NOT set `pending_outcome` — it is recorded
  in `failure_errors` and surfaces at the next safe-point iteration's
  terminal detection (line 235-265).

Resolution (416-447):
  pending_outcome = cancellation_observed ? Some(Cancelled) : None
  for (task, claim, dispatch) in wave_results:       ← only NON-aborted results
    resolution = controller.resolve_dispatch(...)
    Completed|Pending|Skipped|Superseded → {}
    Failed{error}    → failure_errors.insert(task.id, error)   ← deferred, NOT pending
    Blocked{error,d} → pending_outcome ||= stop_outcome(d,...)

- Cancel-token propagation confirmed (line 343-346): `task_cancel =
  cancel.clone()`; `context.with_cancel(task_cancel)`. Every dispatched
  Subagent receives the parent's cancel token. This mirrors the
  F-SUB-02 Sync/Fork/Teammate pattern (`execution_cancel =
  req.cancel.child_token()`).
- Grace-then-abort confirmed: the cancel arm (line 390-395) only sets
  the flag and resets the timer; the actual `abort_all` is in the
  separate grace arm (line 396-411) gated on `cancellation_observed`.
  So a Subagent that finishes its durable terminal writes within
  `cancellation_grace_period` (default 5 s) completes normally and is
  resolved as a sibling result; only non-cooperative dispatches are
  aborted after the grace.
- Wave-drain-before-stop confirmed: the resolution loop (417-441) runs
  to completion before `if let Some(outcome) = pending_outcome` (445).
  Comment at 443-444 ("Resolve the whole wave before honoring a stop
  request so completed siblings are never replayed after resume") is
  honored for the result set that reaches `wave_results`.
- Partial-failure deferral confirmed: a `Failed` resolution
  (line 427-429) enters `failure_errors` but does NOT set
  `pending_outcome`. The wave completes; the next outer-loop iteration
  reloads the snapshot and the terminal-detection block
  (line 235-265) catches the failed task (now persisted by
  `resolve_dispatch`), blocks downstream, and returns the stop outcome.
  This means a wave with mixed Completed + Failed resolves all
  Completed siblings before the Failed surfaces — no mid-wave abort on
  partial failure.
- Blocked/Cancelled priority: `Blocked` and `Cancelled` resolutions DO
  set `pending_outcome` (line 430-439). If a wave has both Failed and
  Blocked, the Blocked outcome is returned first; the Failed's
  persisted status surfaces on resume. This is priority ordering, not
  data loss.
- The `cancellation_drains_wave_and_preserves_completed_siblings` test
  (runtime_executor.rs:837-894):
  - Two tasks (`fast` with 10 ms delay, `slow` waiting on cancel).
  - 200 ms grace period.
  - Dispatches both, waits for both to start, sleeps 25 ms, cancels.

    `slow == Cancelled`.

    preserved as Completed; (2) the slow sibling that observed cancel

## Deviations

- **Aborted claims are silently dropped** (runtime_executor.rs:403,
  `Err(error) if error.is_cancelled() => {}`). They are NOT added to
  `wave_results`, so `resolve_dispatch` is never called for them. Their
  `Running` status (persisted by the controller's `claim_task`) is left
  unreconciled by the kernel. This is the root of F-TSK-03-P2-02 and is
  NOT covered by the existing cancellation test (which uses a slow task
  that itself observes cancel and returns `Err(Cancelled)` via the
  dispatch result path — that path DOES go through `resolve_dispatch`
  and resolves to `Cancelled`. The abort path is different: it drops
  the future before `dispatch_task` returns). The existing test does
  not distinguish "Subagent observed cancel and returned Cancelled"
  from "kernel aborted the Subagent's future."
- **Err in the closure aborts the whole execute** (line 379-381,
  402-403): a dispatch closure returning `Err` (e.g. semaphore closed
  at line 349-351) causes `execute` to return `Err` immediately,
  dropping any already-collected `wave_results` without resolving them.
  This is a hard-failure path (runtime shutdown), low severity, but it
  shares the orphan-claim mechanism.

## Conclusion

Supports: cancellation-token propagation, grace-then-abort, wave-drain-
before-stop, and partial-failure deferral. The kernel mirrors the
F-SUB-02 cancellation-grace pattern at the wave level. The
`cancellation_drains_wave_and_preserves_completed_siblings` regression
test covers the happy-path cancel.

Does NOT support (and identifies the gap): the abort path silently drops
aborted claims without resolving them, orphaning `Running` rows
(F-TSK-03-P2-02). The existing cancellation test does not exercise
this — it uses a Subagent that observes cancel cooperatively, not one
that is hard-aborted.

Findings using this validation: F-TSK-03-P2-02, F-TSK-03-P3-03 (the
abort-drain branch is untested).
