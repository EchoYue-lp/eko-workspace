## Claim

`RuntimeDagExecutor` is the single authority for runtime DAG execution:
it owns the ready frontier, bounded-wave dispatch, claims, cancellation,
failure propagation, and stall detection. The only production entry is
`TaskExecutor::execute_all`, and the `ManagedTaskDagController` adapter
is thin (no frontier, no DAG loop, no second validator). Two legacy
scheduling paths (`execute_ready_tasks`, `execute_all_async`) exist on
`TaskExecutor` but have zero production callers.

## Deviations

The ownership table reveals two ownership nuances that are filed as
findings, not deviations from the validation method:

- Stall detection is **partial** — it fires only when `in_flight` is
  empty (runtime_executor.rs:308-313). The in-flight poll branch
  (277-285) has no stall timeout. This is F-TSK-03-P2-01.
- Retry is **controller-owned**, not kernel-owned. `Retrying` is
  treated as externally in-flight, so a controller that does not
  re-dispatch a retrying task will stall via F-TSK-03-P2-01's
  mechanism. The kernel's design deliberately delegates retry/backoff/
  verification to `dispatch_task`.

## Conclusion

Supports: the "single kernel authority" invariant. `RuntimeDagExecutor`
is the one production owner of DAG traversal, bounded waves, claims,
cancellation, failure propagation, and (partial) stall detection.
`TaskExecutor::execute_all` is the sole production entry;
`ManagedTaskDagController` is a thin adapter that holds no frontier,
DAG loop, or validator. No parallel scheduler/executor/validator exists
in `verifier.rs`, `hooks.rs`, or `revisioned.rs`.

Supports (with caveat): the AGENTS.md rule 6 "one task-relationship
authority" — true for production. The legacy `execute_ready_tasks`
and dead `execute_all_async` are violations but are out of production
reach (F-TSK-03-P3-01).

Does NOT support (and partially refutes): the module doc's claim that
the framework "owns … stall detection." Stall detection is partial —
the in-flight branch can poll indefinitely (F-TSK-03-P2-01).

F-TSK-03-P3-02.
