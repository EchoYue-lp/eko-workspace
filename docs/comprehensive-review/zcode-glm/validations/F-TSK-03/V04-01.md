## Claim

The kernel reloads the snapshot at every safe point (loop iteration),
honors revision changes by re-deriving `DagExecutionState`, and detects
stalls — BUT only when `in_flight` is empty. When `in_flight` is
non-empty (externally running or orphaned tasks), the kernel polls
`external_progress_poll_interval` indefinitely with no stall timeout
and no `note_stalled` callback, so the executor can stall forever for
any task that never resolves. The cancel token is the only escape.

## Expected Result

- Each loop iteration calls `controller.load_snapshot(run_id)` and
  rebuilds `DagExecutionState::from_tasks(&tasks)` — so a mid-execution
  revision (e.g. a new task inserted by `resolve_dispatch`) is seen at
  the next safe point.
- A revision change is logged (line 222-228) and `active_revision` is
  updated.
- When `ready` is empty and `in_flight` is empty: a `Blocked` task
  yields its stop outcome; otherwise `note_stalled` + `Failed("DAG
  stalled...")`.
- When `ready` is empty and `in_flight` is non-empty: the kernel polls
  `external_progress_poll_interval` and loops — with NO stall timeout.
- No test covers the stall backstop, the in-flight poll, or
  resume-after-orphan.

Safe-point revision handling (runtime_executor.rs:213-233):

```text
213:  let snapshot = self.controller.load_snapshot(run_id).await?;
214:  if let Err(errors) = self.validator.validate_task_snapshot(&snapshot.tasks) { return Err(...) }
220:  if active_revision != Some(snapshot.revision) {
221:      if let Some(previous) = active_revision {
222:          tracing::info!(... "runtime DAG executor applied a plan revision at a safe point");
        }
229:      active_revision = Some(snapshot.revision);
    }
232:  let tasks = snapshot.tasks;
233:  let state = DagExecutionState::from_tasks(&tasks);   ← full re-derive each iteration
```

- Full reload per iteration confirmed. The kernel does NOT cache
  `tasks` or `state` across iterations — `from_tasks` runs every loop.
  This means a revision that inserts/removes/rewrites tasks is fully
  picked up at the next safe point. `refresh_in_flight` (runtime.rs:395)
  is NOT used — it is dead (F-TSK-03-P3-02).
- Revision logging confirmed (line 222-228): a `tracing::info!` fires
  on revision change. `active_revision` is updated. The kernel does
  NOT reject stale work mid-wave — it fully drains the current wave's
  JoinSet first (the spawn closure captures `expected_revision =
  snapshot.revision` at line 344, and the controller's `claim_task`
  enforces it). So mid-wave revisions are deferred to the next safe
  point, which is the documented safe-point semantics (comment at
  line 211-212).

Ready/stall block (runtime_executor.rs:275-314):

```text
275:  let ready_task_ids = state.ready_task_ids(&tasks);
276:  if ready_task_ids.is_empty() {
277:      if !state.in_flight.is_empty() {
278:          tokio::select! {
279:              _ = cancel.cancelled() => { return self.controller.interruption_outcome(run_id).await; }
282:              _ = tokio::time::sleep(self.config.external_progress_poll_interval) => {}
             }
284:          continue;                                     ← NO stall timeout, NO note_stalled
         }
287:      if let Some(blocked_task) = tasks.iter().find(|t| matches!(t.execution.status, Blocked(_))) {
             ... return stop_outcome(disposition, blocked_task.spec.id, error);
         }
308:      let reason = "DAG stalled with unfinished tasks (cycle or blocked)";
309:      self.controller.note_stalled(run_id, reason).await?;
310:      return Ok(RuntimeDagOutcome::Failed { failed_task_id: "<none>".to_string(), error: reason });
       }
```

- Three sub-branches confirmed:
  1. **In-flight poll** (277-285): `select!` between cancel and
     `sleep(poll_interval)` (default 250 ms). On cancel →
     `interruption_outcome` (default `Cancelled`). On sleep →
     `continue`. **No max-poll count, no max-duration, no
     `note_stalled`.** This is the F-TSK-03-P2-01 gap.
  2. **Blocked task** (287-306): the first `Blocked` task yields its
     persisted error + `failed_task_disposition` → `stop_outcome`.
     Returns `Failed` or `Paused`.
  3. **Stall backstop** (308-313): `note_stalled` + `Failed("DAG
     stalled with unfinished tasks (cycle or blocked)")`. This is the
     only `note_stalled` invocation in the codebase (confirmed by grep).
     It fires ONLY when `ready` is empty AND `in_flight` is empty AND
     no `Blocked` task exists — i.e. a cyclic/deadlocked graph that
     escaped the validator, or a fully-drained graph with no ready
     tasks.
- The stall backstop correctly catches the case a structural validator
  would normally prevent (cycles). It is the defense-in-depth backstop
  for validator misses.

## Deviations

- The stall backstop returns `failed_task_id: "<none>"` (line 311) — a
  synthetic placeholder rather than a real task id. Callers that
  pattern-match on `failed_task_id` to look up the task will not find
  it. This is a minor API ergonomics issue, not a correctness bug; it
  signals "the stall is a graph-level condition, not a task-level
  one." Not filed separately; mentioned here for completeness.
- The stall reason is hardcoded as "DAG stalled with unfinished tasks
  (cycle or blocked)" (line 308). A real cyclic graph that escapes the
  validator and a real "blocked with no Blocked task" condition share
  the same message, making diagnosis harder. Minor; not filed
  separately.

## Conclusion

Supports: safe-point revision reload (regression-tested via
`executor_follows_dependencies_and_safe_point_revision`), the stall
backstop's existence (code at line 308-313), and the blocked-task stop
outcome (regression-tested).

Does NOT support (and is the central gap): the module doc's claim that
the framework "owns … stall detection" is only half-true. The stall
backstop fires only when `in_flight` is empty. The in-flight poll
branch (line 277-285) loops indefinitely for any task that never
resolves — orphaned claims from cancellation abort (F-TSK-03-P2-02),
dead external workers, or `Retrying` tasks the controller does not
re-dispatch. The `note_stalled` callback is NOT invoked for this case,
so the controller/UI gets no stall signal. Only the cancel token
breaks the loop. This is F-TSK-03-P2-01.

F-TSK-03-P3-03 (stall/in-flight/resume branches untested).
