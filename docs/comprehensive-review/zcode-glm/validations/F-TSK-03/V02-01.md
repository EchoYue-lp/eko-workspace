## Claim

Stale claim/attempt scenarios are handled without dispatching stale work
or persisting contradictory state: (a) a stale revision at claim time
returns `ReloadSnapshot` and the task silently drops out of the wave;
(b) a stale claim at resolve time returns `Superseded`; (c) concurrent
claims are guarded by the controller's atomic claim flip; (d) `Retrying`
tasks are not re-dispatched by the kernel (controller-owned).

## Expected Result

- `claim_task` returning `ReloadSnapshot` → the spawned closure returns
  `Ok(None)`; the join loop skips it (`Some(Ok(Ok(None))) => {}` at
  runtime_executor.rs:378); no `resolve_dispatch` is called; no error.
- The next outer-loop iteration reloads the snapshot, so the task is
  reconsidered against the fresh revision.
- `resolve_dispatch` compares the claim identity; a mismatched claim
  returns `RuntimeTaskResolution::Superseded`, which the kernel treats
  as a no-op (runtime_executor.rs:423-426).
- `claim_pending_task` is atomic within a single `TaskManager` (DashMap
  shard lock) and rejects spec mismatch.
- `Retrying` is in-flight, not ready; the kernel does not re-dispatch
  it.

## Deviations

- The in-tree `ManagedTaskDagController` adapter always returns
  `revision: 0` from `load_snapshot` (executor.rs:1618, comment:
  "TaskManager is an in-memory authority without revision commits").
  This means the kernel's revision-tracking log at
  runtime_executor.rs:220 never fires for this adapter, and the
  `expected_revision != 0` guard in `claim_task`
  (executor.rs:1629-1637) is never tripped by the kernel's own
  revision increment. The staleness guard for this adapter rests
  entirely on `claim_pending_task`'s status+spec check
  (manager.rs:140-143). This is an adapter limitation, not a kernel
  bug; a real revisioned store adapter would exercise the kernel's
  revision path.
- Scenario (c) "concurrent claims" is guarded at the
  single-`TaskManager` level. Cross-process concurrency (two OS
  processes sharing a persistent store) is NOT guarded by the kernel —
  that is the persistence layer's responsibility (durability +
  compare-and-set on the revision). The kernel's `expected_revision`
  is the hook for such CAS, but the in-tree adapter does not use a
  real revision.

## Conclusion

Supports: the stale-claim/attempts invariant. Stale revisions at claim
time → silent reload (scenario a, regression-tested). Stale claims at
resolve time → Superseded (scenario b). Concurrent claims within one
TaskManager → atomic guard via `claim_pending_task` (scenario c).
`Retrying` is not re-dispatched by the kernel (scenario d, by design).

Does NOT prove: cross-process claim safety (that is the persistence
layer's job, not the kernel's). Does NOT prove: that the in-tree
adapter exercises the kernel's revision CAS (it does not — adapter
always returns revision 0).

Findings using this validation: F-TSK-03-P3-02 (notes that
`refresh_in_flight` is unused — the kernel rebuilds state from
`from_tasks` each iteration, so stale in-flight detection is
full-snapshot, not incremental).
