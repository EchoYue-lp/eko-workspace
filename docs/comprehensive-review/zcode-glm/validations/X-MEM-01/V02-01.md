## Claim

When the EKO memory protocol changes, the primary and pooled Agents observe
the change immediately and consistently: `MEMORY.md` mutations refresh
`eko:hot-memory-context`, `learned-rules.md` mutations refresh
`eko:instruction-context`, and every surface (CLI/TUI/GUI/Dreaming) fans the
refresh out to both the primary agent and the pool. (This is the "without lost
updates" half of the X-MEM-01 task question.)

### (P1-01) Wrong projection target on every MEMORY.md mutation

Seven production sites mutate `MEMORY.md` but refresh
`eko:instruction-context` (rows 1–7 above). `get_instruction_suffix`
(`instruction_provider.rs:141-163`) deliberately excludes `hot_memory`, so
re-writing the instruction projection when only `MEMORY.md` changed is a no-op
on the instruction marker (instruction content is unchanged) and leaves the
`eko:hot-memory-context` marker stale.

The only production path that refreshes `eko:hot-memory-context` is
`refresh_memory_projections` ← `refresh_dynamic_context` (`infra.rs:528-529`)
← workspace switch (`state.rs:883`) and bootstrap (`infra.rs:444`). So the
hot-memory stable prefix is frozen between workspace switches / restarts.

This is a **lost update**: the write to `MEMORY.md` is durable on disk but
never reaches the agent's stable `## Active Memories (Hot Layer)` prompt
prefix. The `eko:instruction-context` projection is needlessly re-written with
identical content, masking the omission.

### (P2-01) Pool helper cannot refresh hot memory

`AgentPool::refresh_instruction_context` (`agent_pool.rs:686-710`) is
documented as "Refresh hot-memory and instruction projections on every
existing agent" but the body calls `refresh_instruction_projection` only
(`:701`). Even if a caller wanted to fan a hot-memory refresh to the pool, no
helper exposes that capability.

### (P2-02) CLI surfaces do not fan out to the pool

The three CLI call sites (`all.rs:130`, `all.rs:201`, `evolution.rs:1489`)
refresh only `ctx.agent`. The TUI/GUI/panels/Dreaming sites all follow the
primary-agent refresh with `pool.refresh_instruction_context()`. So a
CLI-driven memory or rule change leaves every pooled/background agent
(including the always-on `__background__` agent) on the stale projection until
the next workspace switch or restart.

## Deviations

- The framework's per-turn `TURN_MEMORY_CONTEXT_PROJECTION`
  (`echo-agent/src/agent/react/run/context.rs:514-532`) re-injects
  query-recalled memories every turn from the warm store. This partially masks
  P1-01: a promoted memory stored in the warm layer can still surface via
  recall when it matches the current query. It does **not** surface as the
  stable `## Active Memories (Hot Layer)` prefix, which is the surface
  Dreaming and `/remember` auto-promotion target. Severity rests on the stable
  prefix being defeated, not on total memory loss.
- The TUI/GUI add-or-delete paths refresh the pool only when
  `promotion.is_some()` / `layer == Some(Hot)` — i.e. only when `MEMORY.md`
  actually changed. That gating is correct; the defect is the wrong projection
  target, not the gating.
- Bootstrap (`infra.rs:444`) and workspace switch (`state.rs:883`) both call
  `refresh_dynamic_context` → `refresh_memory_projections`, which refreshes
  BOTH projections correctly. So at agent creation and at switch time the
  hot-memory prefix is correct; it only goes stale after subsequent
  MEMORY.md edits.

## Conclusion

The "immediate and consistent projection to primary and pooled Agents" claim
fails on three independent axes: wrong projection marker for MEMORY.md
mutations (P1-01), pool helper incapable of hot-memory refresh (P2-01), and
CLI pool-fan-out gap (P2-02). All three share one fix shape: route every edit
through a single helper that calls `refresh_memory_projections` on the primary
and a widened pool helper.

This validates the "lost updates" half of the X-MEM-01 task question:
**lost updates do occur** on the hot-layer refresh path. The framework's
compression and persistence are not at fault — the defect is entirely in the
application refresh wiring. Supports findings X-MEM-01-P1-01, X-MEM-01-P2-01,
X-MEM-01-P2-02 (which re-affirm A-MEM-01-P1-01 / P2-01 / P2-02 at the X-MEM-01
commits).
