## Claim

EKO-specific instruction/memory layers flow to the framework via a single path
with no duplicate persistence: one file protocol loader
(`InstructionProvider`), one wrapper (`UnifiedMemory`), two distinct
projection markers, and one framework seam (`ContextManager::replace_projection`).
The framework's per-turn recall (`TURN_MEMORY_CONTEXT_PROJECTION`) is a
distinct tail projection, not a duplicate of the two stable-prefix projections.
No store/layer/concept has a parallel authority.

## Method

## Expected Result

1. Exactly one file-protocol loader (`InstructionProvider`) feeding one wrapper
   (`UnifiedMemory`).
2. `get_instruction_suffix` excludes hot memory; `get_memory_suffix` returns
   hot memory only — no overlap, no second source for either.
3. Two distinct projection markers (`eko:instruction-context`,
   `eko:hot-memory-context`) both flowing through the single framework seam
   `replace_projection`.
4. The framework's `TURN_MEMORY_CONTEXT_PROJECTION` recall is a tail
   projection (via `replace_tail_projection`), distinct from the two
   stable-prefix projections (via `replace_projection`).
5. No parallel `Store` / loader / projection authority in either repo.

## Result

- Exit code: 0 (greps and reads succeeded)
- Summary: **Claim supported on all five points.**

### (1) Single loader, single wrapper

`InstructionProvider::load_for(working_dir)` (`instruction_provider.rs:61-82`)
is the only constructor that reads the six file tiers. It populates six
`Option<String>` fields. `UnifiedMemory` (`unified_memory.rs:59-62`) wraps an
`InstructionProvider` and adds no second loader — grep confirms no other type
constructs these fields.

### (2) Suffix builders are non-overlapping

```text
get_instruction_suffix()    → user + repository + project + learned-rules + local
                              (instruction_provider.rs:141-163; hot_memory EXCLUDED)
get_memory_suffix()         → "## Active Memories (Hot Layer)\n" + hot_memory body
                              (instruction_provider.rs:170-174; ONLY hot_memory)
get_system_prompt_suffix()  → instruction_suffix ++ memory_suffix
                              (instruction_provider.rs:121-134; aggregation only)
```

`get_instruction_suffix` iterates `user_level`, `repository_level`,
`project_level`, `agents_level`, `local_level` — `hot_memory` is never
referenced. `get_memory_suffix` references only `hot_memory`. The two suffixes
are disjoint by construction; no tier is emitted by both.

### (3) Two markers, one framework seam

```text
INSTRUCTION_CONTEXT_PROJECTION = "eko:instruction-context"  (unified_memory.rs:28)
HOT_MEMORY_CONTEXT_PROJECTION  = "eko:hot-memory-context"   (unified_memory.rs:29)
```

Both `refresh_instruction_projection` (`:138-151`) and
`refresh_hot_memory_projection` (`:154-167`) call the same framework method:

```rust
agent.context().lock().await.replace_projection(MARKER, message);
```

`ContextManager::replace_projection` (`compression/mod.rs:605-611`) delegates
to `apply_projections(&[ContextProjection { marker, message }])` (`:546-573`),
which wraps the message in the framework-reserved
`<echo-agent-context-projection-v1>` envelope (`PROJECTION_ENVELOPE_PREFIX`,
`mod.rs:30`) and inserts it at the system/history boundary. One seam, two
markers — no parallel projection API.

### (4) Per-turn recall is a distinct tail projection

`run/context.rs:514-532`:

```rust
context.replace_projection(WORKSPACE_CONTEXT_PROJECTION, ...);   // system boundary
context.replace_tail_projection(TURN_MEMORY_CONTEXT_PROJECTION, memory_context.map(...));
```

`replace_tail_projection` (`mod.rs:617-632`) calls `push` (appends at tail),
not `apply_projections` (inserts at system/history boundary). The doc at
`:613-616` states tail placement "preserves the longest stable prompt prefix
for provider KV caches." So `TURN_MEMORY_CONTEXT_PROJECTION` is query-dependent
recall that sits at the tail, refreshed every turn; it is not a duplicate of
`eko:hot-memory-context` (stable prefix, refreshed on memory edits). The two
coexist with distinct placement and refresh semantics.

## Deviations

- `get_system_prompt_suffix` (`instruction_provider.rs:121-134`) concatenates
  both suffixes for legacy callers that need one string. It is an aggregation
  helper, not a parallel authority — it delegates to `get_instruction_suffix`
  + `get_memory_suffix`. The runtime context path uses the two independent
  projections, not this aggregation (verified: the only production caller of
  `get_system_prompt_suffix` is `UnifiedMemory::system_prompt_suffix`, which
  is itself only used in non-runtime paths).
- The legacy `AGENTS.md → learned-rules.md` one-time migration
  (`instruction_provider.rs:90-113`) renames the old auto-promoted rules file.
  This is a correctness mechanism (prevents rule loss on upgrade), not a
  duplicate source — `load_agents_instructions` (`:267-284`) reads the new name
  with legacy fallback, never both simultaneously.

## Conclusion

The claim is **supported**. EKO's instruction/memory layers flow to the
framework via a single path: `InstructionProvider` → `UnifiedMemory` → two
distinct projection markers → one framework seam (`replace_projection`). No
duplicate persistence exists: the hot/warm file split is intentional and
single-authority per layer, and the framework's per-turn recall projection is
a distinct tail projection, not a duplicate of the two stable-prefix
projections. This validates the "without duplicate persistence" half of the
X-MEM-01 task question. Supports the X-MEM-01 Layering Decision and Current
Path; no finding is produced by V01 (the duplicate-persistence question is
clean). The "without lost updates" half is validated by V02.
