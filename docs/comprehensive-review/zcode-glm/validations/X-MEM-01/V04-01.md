## Claim

On workspace switch, EKO performs a clean memory-store replacement with no
duplicate promotion: the primary and pooled agents are rebound to the new
workspace's store, layer manager, and both projections consistently, with
`memory_store_override` ensuring future pool agents bind to the new store.
There is no duplicate-store or split-brain defect. The hot (`MEMORY.md`) and
warm (`store.json`) layers share one `echo_agent_dir` per workspace and remain
single-authority per layer.

## Expected Result

1. `switch_workspace` refreshes both projections on the primary (via
   `refresh_dynamic_context`) and propagates to the pool (via
   `apply_working_dir`).
2. Memory store is replaced (not duplicated): `ReviewIntegration::rebind` →
   `create_layer_manager` → `install_memory_store` +
   `install_memory_layer_manager` on the primary; `apply_memory_store` on the
   pool.
3. `memory_store_override` is recorded so future pool agents bind to the new
   store.
4. Hot and warm layers share one `echo_agent_dir` per workspace (no path
   divergence).
5. No second `Store` trait or parallel KV is constructed.

### (1) & (2) Both projections refreshed on primary; both layers swapped

`refresh_dynamic_context` (`infra.rs:528-531`) calls
`refresh_memory_projections` (both markers) — this is the ONLY production
helper that refreshes both. It is invoked at `state.rs:883` (primary) and
inside `apply_working_dir` (pool). So switch refreshes both projections on
both populations. This is why workspace switch is the ground-truth refresh
path noted in A-MEM-01: it is the only path that exercises
`refresh_memory_projections` in production.

A pool agent created post-switch reads `memory_store_override` first
(consumed at `agent_pool.rs:906-911` per A-MEM-01 V04-01), so it binds to the

## Deviations

- `AgentPool::create_agent` (`agent_pool.rs:850-913`) first builds a pool
  agent via `infra::create_agent`, which itself constructs a `FileStore` at
  the resolved path. That store is immediately replaced by
  `install_store(effective_store)` (`agent_pool.rs:912-913`), where
  `effective_store = memory_store_override.or(shared.store)`. The transient
  bootstrap store is never read or written between build and replace (the
  agent is not running yet), so two `FileStore` instances never race on the
  same path. This is a minor inefficiency (one wasted `FileStore::new` per
  pool agent creation), not a duplicate-store defect; not promoted to a
  finding. (Same observation as A-MEM-01 V04-01.)
- The switch path does NOT call `refresh_hot_memory_projection` explicitly —
  it calls `refresh_memory_projections` (which refreshes both). So switch is
  the one path that correctly refreshes the hot-memory projection. This is
  consistent with the V02 finding that switch is the ground-truth refresh.
- Global vs workspace path layout asymmetry (global warm store at
  `~/.eko/store.json` vs workspace at `<root>/.eko/memory/store.json`) is
  noted in A-MEM-01-P3-02. It is a cleanliness observation, not a
  duplicate-promotion defect: each path is internally consistent and the
  resolution functions return matching pairs. Not re-litigated here.

## Conclusion

The claim is **supported**. Workspace switch is a clean, fully-consistent
rebind path: it refreshes both projections on primary and pool, rebinds the
store via `ReviewIntegration::rebind` → `install_memory_store` +
`install_memory_layer_manager`, records `memory_store_override` for future
pool agents, and keeps the hot/warm layers under one `echo_agent_dir`. No
duplicate-store authority, no split-brain, no duplicate promotion. The
hot/warm file split is single-authority per layer. This validates the
"workspace switch" half of the X-MEM-01 task question and re-confirms the
A-MEM-01 Handoff conclusion that switch is the ground-truth refresh path.
Supports the X-MEM-01 Current Path and Findings (switch is the only path
that refreshes `eko:hot-memory-context` correctly, which is why P1-01's
lost-update is confined to non-switch edit surfaces).
