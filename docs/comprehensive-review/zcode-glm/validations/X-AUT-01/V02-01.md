## Claim

The permission-mode matrix is exactly as X-AUT-01 describes: each
user-facing mode (`default`, `auto-edit`, `full-auto`, `strict`) maps
to a framework `PermissionMode`, and the per-mode dispatch in
`PermissionService::check_with_permissions_in_mode` produces a specific
allow/handler/deny decision for each `ToolPermission` (Read/Write/
Network/Execute/Sensitive). In particular:

- In `default` mode, Read auto-allows; Write/Network/Execute/Sensitive
  require handler approval.
- In `full-auto` (BypassPermissions), every tool auto-allows **except**
  protected paths (`.git/.ssh/.env/.aws/...`), which are denied at
  STEP 0 before the Bypass short-circuit.
- `Default` and `StrictConfirm` have identical confirmation surfaces.
- No direct-user command is affected by any mode (modes apply only to
  the agent-automation path; see V01).

## Expected Result

- `default_confirmation_required(permissions)` returns true for
  Write/Execute/Network/Sensitive; false for Read-only.
- `accept_edits_confirmation_required(permissions)` returns true for

- `strict_confirmation_required(permissions)` returns the same as
  `default_confirmation_required` (identical surface).

  short-circuit), so protected paths deny even in BypassPermissions.
- The user-facing `full-auto` maps to `BypassPermissions` and emits
  `tracing::warn!` on activation.

does not affect the boundary question.

## Conclusion

Supports X-AUT-01 Current Path §2 ("The permission-mode matrix"). The
matrix is exactly as the task report describes:

- `default`: Read auto-allow; Write/Execute/Network/Sensitive → handler.
- `auto-edit`: Read+Write auto-allow; Execute/Network/Sensitive → handler.
- `strict`: same as `default`.
- `full-auto`: everything auto-allows **except protected paths**, which
  override at STEP 0. Activation is loud (`tracing::warn!`).

No mode affects any direct-user command (the modes dispatch only inside
`check_with_permissions_in_mode`, which is reachable only from
`PermissionStage` on the agent path; see V01).
