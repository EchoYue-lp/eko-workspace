## Claim

Every tool/action in the EKO boundary falls into exactly one of two
disjoint categories, and the classification is correct:

- **Agent automation** — reached via `execute_tool_with_policy` →
  `ToolExecutionPipeline` → `PermissionStage` →
  `PermissionService::check_with_permissions_in_mode`. This is the only
  path that consults `permission_mode`.
- **Direct-user** — Tauri IPC commands and TUI key/slash handlers that
  bypass `execute_tool_with_policy` entirely and use input validation
  only (path validator, executable allowlist, URL scheme, per-session
  consent, size caps). These never read `permission_mode` as a gate.

If any direct-user command calls `execute_tool_with_policy`, or if any
direct-user command reads `permission_mode` to decide whether to run,
that falsifies the "correctly separated" half of the X-AUT-01 question.

## Conclusion

Supports X-AUT-01 Current Path §1 ("The two canonical paths"). The
agent-automation path and the direct-user path share no code, and
`permission_mode` is read only by the two mode-management IPC commands.
This is the load-bearing invariant for the X-AUT-01 question's
"automated Agent actions controlled" half (yes — via `PermissionStage`)
and its "direct user ... remain usable" half (yes — none of them is
gated by `permission_mode`).

The finding X-AUT-01-P2-01 is about the *justifying narrative* in the
comments of some of these commands, not about a path-separation
violation. The separation itself is clean.
