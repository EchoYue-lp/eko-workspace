## Claim

The A2A integration (`src/a2a/`) isolates the JSON-RPC + SSE protocol
behind a typed `TaskState` state machine with monotonic terminals,
correctly enforces JWT Bearer authentication on protected endpoints,
publishes a spec-compliant Agent Card, and honors `tasks/cancel` for
both sync and streaming task invocations.

## Expected Result

- Agent Card fields match A2A spec (camelCase serialization,
  per-field optionality).
- `TaskState.can_transition_to` enforces the spec state machine and
  is the single authority for transitions.
- `tasks/cancel` aborts both sync and streaming task executions.
- JWT middleware rejects missing/invalid tokens; agent-card endpoint
  is auth-protected when auth is enabled; health endpoints are not.
- Terminal states are monotonic: once Canceled/Completed/Failed, the
  state cannot regress.

## Result

- Exit code: not-applicable (static review)
- Duration: n/a
- Summary: Agent Card, JWT middleware, and the state machine enum are
  correct. But `handle_task_send` bypasses `update_task_state`'s
  transition check on its terminal write, and never checks the cancel
  token during `agent.execute()`. Together these break terminal
  monotonicity when `tasks/cancel` races a late completion — a P1
  defect.

  **Agent Card** (`types.rs:39-209`):
  - `#[serde(rename_all = "camelCase")]` on `AgentCard`
    (`types.rs:43`), with per-field `skip_serializing_if = Option::
    is_none` and `default` markers — spec-compliant.
  - `default_input_modes` / `default_output_modes` default to
    `["text/plain"]` (`types.rs:75-77`).
  - `AgentCard::from_agent` (`types.rs:97-116`) auto-derives skills
    from `agent.tool_definitions()` — useful, framework-only.
  - `AgentSkill`, `AgentProvider`, `AgentAuthentication`,
    `AgentCapabilities` all serialize to camelCase; capabilities use
    `#[serde(default)]` so older clients can omit them.

  **TaskState state machine** (`types.rs:329-391`):
  - Enum variants: `Submitted`, `Working`, `InputRequired`,
    `Completed`, `Failed`, `Canceled` (`types.rs:340-353`), with
    `#[serde(rename_all = "kebab-case")]`.
  - `is_terminal` (`types.rs:357-359`) returns true for Completed /
    Failed / Canceled.
  - `can_transition_to` (`types.rs:362-378`) encodes the documented
    state machine (`types.rs:322-327`): terminal states cannot
    transition; valid edges are Submitted→Working, Submitted→Canceled,
    Working→{Completed,Failed,InputRequired,Canceled}, InputRequired
    →{Working,Canceled}. Tests at `types.rs:692-735` cover every
    edge and several rejected edges.
  - `update_task_state` (`server.rs:588-602`) is the only path that
    **enforces** this matrix via `can_transition_to`; illegal
    transitions are logged-and-skipped.

  **JWT middleware** (`auth.rs`):
  - `JwtConfig::hs256` / `rs256` / `disabled` constructors
    (`auth.rs:60-118`). `Debug` impl redacts the secret
    (`auth.rs:120-130`, with a test at `auth.rs:315-321`).
  - `validate_token` (`auth.rs:221-252`) sets `validate_exp = true`,
    `validate_nbf = true`, leeway 30 s; honors configured issuer and
    audience.
  - `extract_bearer_token` (`auth.rs:215-218`) handles `Bearer <tok>`
    only — Basic/digest returns None.
  - **Note on algorithm restriction**: when
    `JwtConfig::algorithms.len() <= 1`, only the first algorithm is
    passed to `Validation::new` (`auth.rs:222-228`). When more than
    one is configured, all are passed (`auth.rs:231-233`). The
    default `HS256` constructor sets exactly one algorithm, so the
    well-known JWT "alg confusion" attack is not possible by default.
    However, if a user constructs `JwtConfig::rs256(...)` and the
    underlying `jsonwebtoken` `Validation` accepts HS256 with the
    public key as HMAC secret, an attacker could forge tokens. The
    `jsonwebtoken` crate rejects this mismatch by default (its
    `Validation` only accepts the algorithms in `algorithms`), so
    this is **not exploitable** with current `jsonwebtoken` versions.
  - Tests cover header extraction, disabled config, redaction
    (`auth.rs:283-352`).

  **Routing** (`serve.rs:97-165`):
  - `/health` and `/ready` are outside the auth-protected group
    (`serve.rs:142-143`).
  - `/.well-known/agent.json` and `/` (POST JSON-RPC) are inside the
    protected group, and `route_layer(jwt_middleware)` is applied
    only when `jwt_enabled` (`serve.rs:131-138`). Correct.
  - A non-loopback bind without auth logs a prominent warning
    (`serve.rs:104-117`) — good defense-in-depth.
  - `DefaultBodyLimit::max(max_body_bytes)` (default 1 MB) protects
    against oversized bodies.
  - Graceful shutdown on SIGINT / SIGTERM
    (`serve.rs:158-160, 168-200`).

  **handle_request** (sync) (`server.rs:81-125`):
  - Parses the JSON-RPC request; on parse failure returns
    `ERROR_CODE_PARSE = -32700` with `id: None` — JSON-RPC spec
    compliant.
  - Dispatches on `method`: `tasks/send`, `tasks/get`,
    `tasks/cancel`, with `tasks/sendSubscribe` rejected (must use
    `handle_request_stream`). Unknown methods return
    `ERROR_CODE_METHOD_NOT_FOUND = -32601`.

  **handle_task_send** (sync) (`server.rs:378-485`):
  - Generates a UUID task id if none provided; inserts an `A2ATask`
    with state `Submitted`.
  - Creates a `CancellationToken` and stores it in `cancel_tokens`
    (`server.rs:403-408`).
  - Calls `update_task_state` to move to `Working`
    (`server.rs:410`).
  - **`agent.execute(&input_text).await` is awaited with no
    cancellation hook** (`server.rs:414`). If `tasks/cancel` fires
    during this await, the cancel_token is set but no one polls it.
  - On success/failure, the code writes directly to `tasks` via
    `tasks.insert(task_id.clone(), ...)` (`server.rs:440-442,
    468-470`), **bypassing `update_task_state`'s transition check**.
    The status object is set to `Completed` or `Failed` regardless of
    what current state is.
  - The cancel_token is removed from the map on completion
    (`server.rs:444, 472`).

  **handle_request_stream** (SSE) (`server.rs:140-347`):
  - Same Submitted→Working flow, then iterates the agent's event
    stream.
  - **Cancels properly**: at the top of each iteration,
    `if cancel_token.is_cancelled()` → sets state to `Canceled`,
    yields the final event, removes the token, returns
    (`server.rs:224-235`). This path **does** honor cancellation.
  - Maps `AgentEvent::Token` to `ArtifactUpdate` events with
    `append = !first_chunk` — incremental streaming semantics.
  - Maps `AgentEvent::ToolCall` / `ToolResult` to status / artifact
    events.
  - On stream error or agent execution failure, sets state to
    `Failed`, yields the final event, returns
    (`server.rs:279-292, 330-343`).
  - On normal completion, sets state to `Completed`, pushes
    accumulated text into artifacts if no artifact was streamed
    (`server.rs:296-328`).
  - Removes the cancel_token on every terminal path
    (`server.rs:233, 320`).

  **handle_task_cancel** (`server.rs:527-584`):
  - Returns `ERROR_CODE_INVALID_PARAMS = -32602` if id is missing.
  - Returns `ERROR_CODE_TERMINAL_STATE = -32002` if the task is
    already terminal.
  - Sets state to `Canceled` via direct `tasks.get_mut(task_id).
    status = ...` (`server.rs:560`), bypassing `update_task_state`.
  - Looks up the cancel_token and calls `.cancel()` on it
    (`server.rs:563`). The lookup uses `cancel_tokens.read().await`
    nested inside `tasks.write().await` (`server.rs:543`). No
    deadlock risk because no other path takes the locks in reverse
    order.

  **The critical race** (F-INT-02-P1-01):

  1. Caller A invokes `tasks/send` for a long-running task. The
     server sets state Working and enters `agent.execute().await`.
  2. Caller B invokes `tasks/cancel` for the same task id. The
     server: acquires `tasks.write()`, sees state Working (not
     terminal), writes `status = Canceled`, calls
     `cancel_token.cancel()`, returns `Canceled` to caller B.
  3. `agent.execute()` eventually returns to caller A's path. The
     server: acquires `tasks.write()`, `tasks.insert(task_id,
     completed_task)` — overwrites `Canceled` with `Completed`.
     Removes the cancel_token.

  Net effect: caller B sees `Canceled`; a subsequent `tasks/get`
  sees `Completed`. The terminal state has regressed. The
  `can_transition_to` matrix would reject `Canceled→Completed`, but
  the terminal write bypasses it.

  In the streaming path this race does not occur, because the
  cancellation is checked every iteration and the iteration's
  `update_task_state(Canceled, ...)` is followed by an early
  return — there is no late `tasks.insert` to overwrite it.

  **handle_task_get** (`server.rs:489-523`): returns the task
  snapshot or `ERROR_CODE_TASK_NOT_FOUND = -32001`. No issues.

  **cleanup_completed_tasks** (`server.rs:605-625`): retains tasks
  whose non-terminal state OR whose timestamp falls within
  `max_age_secs`. Tasks without a parseable timestamp are kept —
  conservative, no leak. Caller is expected to invoke this
  periodically (not wired in this crate; the application must
  schedule it).

  **No `Drop` for `A2AServer`** — the `tasks` and `cancel_tokens`
  maps simply drop. In-flight tasks are not cancelled on server
  shutdown; the agent futures are dropped (which propagates as
  dropped streams for SSE clients).

  Application reachability: `serve` / `serve_with_auth` /
  `serve_from_config[_with_auth]` are the framework's only HTTP
  server entry points; `echo-agent-cli/src/cli/modes.rs` is the
  only EKO caller of these.

- Log/artifact: none.

## Deviations

Agent Card, JWT, state-machine enum, and the streaming cancellation
path all match expectations. The **sync `tasks/send` path does not
honour cancellation** and **bypasses the transition check on its
terminal write**, breaking terminal monotonicity under race.

## Conclusion

The A2A integration correctly isolates the JSON-RPC + SSE protocol
behind a typed state machine and enforces JWT on protected endpoints.
The streaming `tasks/sendSubscribe` path honours cancellation.
However, the **sync `tasks/send` path has a P1 race**: a late
`agent.execute()` completion overwrites a `Canceled` state, so
terminal monotonicity is violated. The same bypass affects Failed
writes after a cancel. The fix is to route the Completed/Failed
writes through `update_task_state` (which already enforces
`can_transition_to`) and to poll `cancel_token.is_cancelled()` before
writing the terminal state.

Supports findings F-INT-02-P1-01 (sync-send cancel race),
F-INT-02-P3-04 (no Drop / in-flight task cancel on shutdown).
