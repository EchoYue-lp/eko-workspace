## Claim

The LSP lifecycle (`StdioLspClient` + `LspManager`) starts language
servers cleanly, isolates the JSON-RPC protocol behind a typed `LspClient`
trait, cleans up the child process on shutdown / drop, and propagates
process death back to callers so they can recover or restart.

plus tracing the live application caller in
`echo-agent-cli/echo-agent-app-core/src/runtime.rs` and `plugin_runtime.rs`.

## Expected Result

- `LspClient` trait defines a typed, panic-free surface (per AGENTS.md
  no-panic rule and F-CORE-01).
- Start: spawn child + JSON-RPC handshake (`initialize` → `initialized`).
- Stop / Drop: child process killed; pending requests drained with an
  error; manager entry removed.
- Process death mid-session: surfaced to callers; no deadlock.
- Status report (`LspServerStatus.restart_count`, `last_error`) reflects
  observed reality.

## Result

- Exit code: not-applicable (static review)
- Duration: n/a
- Summary: Mixed. The protocol is isolated behind the typed `LspClient`
  trait and JSON-RPC framing is correct, but cleanup is best-effort,
  cancellation is absent, and the `restart_count` / `last_error` status
  fields are dead.

  Lifecycle in `echo-integration/src/lsp/client.rs`:
  - **Spawn** (`client.rs:67-122`): `tokio::process::Command` with
    `kill_on_drop(true)` (`client.rs:79`). Stdin/stdout pipes are taken
    and given to two `tokio::spawn` tasks (writer `client.rs:98-108`,
    reader `client.rs:113-116`). Neither `JoinHandle` is stored, so
    neither task can be cancelled explicitly.
  - **Initialize** (`client.rs:272-309`): sends `initialize` request
    with capabilities, then `initialized` notification. Sets
    `initialized.store(true, SeqCst)`.
  - **Send request** (`client.rs:202-236`): assigns a `u64` id via
    `AtomicU64`, registers a `oneshot::Sender` in `pending`, encodes
    and writes the request, awaits the response. **No per-request
    timeout.**
  - **Read loop** (`client.rs:125-199`): parses Content-Length framed
    messages, dispatches responses by id, stores
    `textDocument/publishDiagnostics` notifications in
    `diagnostics_cache`. On stdout EOF (`Ok(0)`) or read error, the
    `pending` map is cleared under the mutex (`client.rs:139, 144,
    166`), which drops every `oneshot::Sender` → waiting requests get
    `Err(RecvError)` and `send_request` returns
    `LspError::CommunicationError("Response channel closed")`.
  - **Shutdown** (`client.rs:311-329`): if `is_running()`, sends
    `shutdown` request and `exit` notification (errors ignored),
    `child.kill().await`, sets `running=false`, `initialized=false`.
  - **Drop**: no `impl Drop for StdioLspClient`. Relies on
    `kill_on_drop(true)` for the child and on the writer task exiting
    when `writer_tx` (held in `self.writer_tx`) is dropped. The reader
    task exits naturally when the child's stdout closes after kill.

  Manager in `echo-integration/src/lsp/manager.rs`:
  - **start_server** (`manager.rs:64-89`): wraps `client.initialize` in
    a 15 s `tokio::time::timeout`. On success stores
    `Arc<RwLock<StdioLspClient>>`. On failure the client is dropped
    (kill_on_drop fires).
  - **stop_server** (`manager.rs:92-102`): removes the entry, calls
    `client.shutdown()`.
  - **restart_server** (`manager.rs:105-108`): stop then start.
  - **shutdown_all** (`manager.rs:168-173`): iterates and stop_server,
    errors logged-and-discarded.

  Application reachability (single live caller, single source):
  - `echo-agent-cli/echo-agent-app-core/src/runtime.rs:499-590`
    `register_lsp_tools` calls `LspConfig::discover` →
    `LspManager::start_server` per language.
  - `echo-agent-cli/echo-agent-app-core/src/plugin_runtime.rs:27`
    stores `Arc<RwLock<LspManager>>` and calls `shutdown_all()` on
    reload/rollback paths (`plugin_runtime.rs:583, 596, 639, 691,
    707, 721`).
  - No other definition of `StdioLspClient` / `LspManager` exists in
    either repository; the integration is single-source.

  **Defects observed (details in task report):**
  1. `restart_count: u32` and `last_error: Option<String>` fields
     (`client.rs:40, 42`) are initialized to `0` / `None` at
     `client.rs:60-61` and read by `status()` at `client.rs:528-529`,
     but **no code path ever updates them** (grep across
     `echo-integration/src/lsp/` confirms zero assignments). They are
     dead fields; every `LspServerStatus` reports `restart_count: 0,
     last_error: None` forever, even after crashes and restarts.
  2. `send_request` (`client.rs:202-236`) has no per-request timeout.
     If the server hangs without closing stdout (deadlocked LSP server,
     kernel-paused process), the request awaits `rx` forever. Only
     start-up has a 15 s timeout (`manager.rs:76`); all later
     goto-definition / hover / completion calls can hang indefinitely.
  3. No `CancellationToken` is threaded into the LSP client (grep
     confirms zero `CancellationToken` references under
     `echo-integration/src/lsp/`). When the parent agent run is
     cancelled, the future is dropped, but the spawned reader/writer
     tasks keep running until the child dies (which only happens via
     explicit `shutdown()` or `kill_on_drop` on client drop).
  4. `parse_content_length` (`jsonrpc.rs:90-97`) is byte-index safe
     only because `"content-length:"` is ASCII and is the matched
     prefix — UTF-8 safe by virtue of ASCII prefix, **not a defect**.
  5. `JsonRpcResponse.id: Option<u64>` (`jsonrpc.rs:50`) plus the
     id extraction in `client.rs:176` (`value.get("id").and_then(|
     v| v.as_u64())`) silently drops responses whose id is a string
     (e.g. `"1"`). The pending entry is never matched, the oneshot
     never fires, the request hangs until the reader exits. (Not a
     panic; correctness bug.)

- Log/artifact: none.

## Deviations

The protocol-isolation and start/stop happy path match expectations.
The five defects above are not failures of isolation; they are
lifecycle/cleanup/recovery gaps.

## Conclusion

The LSP integration isolates the JSON-RPC protocol behind a typed
`LspClient` trait and starts servers safely. It does **not** satisfy
the "preserving typed internal lifecycle and cleanup" half of the
task question:

- `restart_count` / `last_error` are dead status fields (F-INT-02-P2-01).
- No per-request timeout (F-INT-02-P2-02).
- String-id JSON-RPC responses are silently dropped (F-INT-02-P3-01).
- No cancellation propagation (F-INT-02-P3-02).

Supports findings F-INT-02-P2-01, F-INT-02-P2-02, F-INT-02-P3-01,
F-INT-02-P3-02.
