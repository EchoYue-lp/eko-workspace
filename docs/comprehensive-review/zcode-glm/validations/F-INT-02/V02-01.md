## Claim

The IM channel layer (`ChannelManager` + `FeishuChannel` + `QqChannel`)
isolates platform protocols behind a single typed `ChannelPlugin` /
`MessageHandler` trait, manages connections (WebSocket long-poll,
webhook, QQ gateway) with bounded reconnect, and cleans up background
tasks on `stop()` / drop without leaking spawned tasks or subprocesses.

## Expected Result

- Single typed trait (`ChannelPlugin`) covers all platforms; no
  platform type leaks into the framework agent layer.
- Each channel's `start` registers a cancellable background task;
  `stop` aborts it.
- Reconnect logic is bounded (max retries, exponential backoff with
  reset after stable connection) and surfaces permanent failure.
- `Drop` for `ChannelManager` performs cleanup or warns loudly.
- Token managers handle expiry, concurrent refresh, and redaction in
  logs.
- Webhook signature verification is constant-time and challenge
  passthrough is correct.

## Result

- Exit code: not-applicable (static review)
- Duration: n/a
- Summary: Mostly correct. Trait isolation, reconnect math, HMAC
  verification, and dedup are sound. But cleanup is best-effort with
  task-leak windows, and `ChannelManager::Drop` only logs.

  **ChannelManager** (`manager.rs`):
  - Owns `HashMap<String, Box<dyn ChannelPlugin>>` (`manager.rs:17`).
  - `start_all` / `stop` / `stop_all` iterate per-plugin; `start_all`
    returns `Vec<Result<()>>` so one failure doesn't poison others
    (`manager.rs:53-76`).
  - `Drop for ChannelManager` (`manager.rs:131-141`) **only logs** if
    any channels remain; no async `stop_all` is invoked (Drop cannot
    await). Channels that weren't `stop_all`'d may leave their
    background tasks running.

  **FeishuChannel** (`feishu/channel.rs`):
  - `start` (`channel.rs:194-300`) creates a `TokenManager`, validates
    it, spawns a send-task (`channel.rs:217-239`, fire-and-forget —
    `JoinHandle` discarded), wraps the handler, and dispatches on
    `FeishuMode`:
    - **LongPoll** (`channel.rs:253-269`): spawns `WsClient::run`.
      `JoinHandle` stored in `self.task_handle`.
    - **Webhook** (`channel.rs:270-296`): spawns `run_webhook_server`.
      `JoinHandle` stored in `self.task_handle`.
  - `stop` (`channel.rs:302-312`): `task_handle.take().abort()` and
    `self.send_tx = None`.
  - `health_check` (`channel.rs:329-339`): checks
    `task_handle.is_finished()` and `token_manager.get_token()`.
  - `running_cards: DashMap<String, (String, Instant)>` has a 1-hour
    TTL reaper (`channel.rs:358-359`) — bounded memory.

  **WsClient (Feishu long-poll)** (`feishu/long_poll.rs`):
  - `run` (`long_poll.rs:134-192`): main loop with **bounded
    exponential backoff** (`backoff_secs: u64` doubled up to
    `MAX_BACKOFF_SECS = 300`, `long_poll.rs:188`), **reset to 1 after
    a stable connection** (`STABLE_THRESHOLD_SECS = 60`,
    `long_poll.rs:163-167`), and **bounded retry count** when
    `reconnect_count >= 0` (`long_poll.rs:173-182`). `reconnect_count
    = -1` (default, `long_poll.rs:41`) means unlimited. This is a
    **better-designed reconnect** than MCP's SSE transport (cf.
    F-INT-01-P2-02) — backoff resets on stability.
  - `connect` (`long_poll.rs:216-282`) starts a ping task
    (`long_poll.rs:262-276`) that holds a `running` clone; on
    `message_loop` return the ping task is explicitly aborted
    (`long_poll.rs:280`).
  - **stop** (`long_poll.rs:211-213`) sets `running = false`. But
    `WsClient::stop` is **never called by `FeishuChannel::stop`** —
    the channel just aborts the outer `task_handle`. So `running`
    stays `true` after abort; the ping task will keep looping (sleep →
    check `running` → still true → attempt `sink.send(ping)` → fails
    because the WebSocket sink was dropped with the outer task →
    break). Worst-case window: one ping interval (default 120 s,
    `long_poll.rs:32`) of lingering ping task.
  - **Dedup**: `processed_events: DashMap<String, Instant>` with
    5-minute TTL reaper (`long_poll.rs:29, 460-463`) — bounded.
  - **Fragment reassembly**: `fragment_cache: DashMap<String,
    (Instant, FragmentParts)>` with 5-minute TTL reaper
    (`long_poll.rs:475-479`) — bounded, panic-free
    (`seq`/`sum` validated as `seq >= 0 && seq < sum` at
    `long_poll.rs:490`).

  **Feishu Webhook** (`feishu/webhook.rs`):
  - HMAC-SHA256 signature verification uses `subtle::ConstantTimeEq`
    (`webhook.rs:53-61`) — timing-safe.
  - Length mismatch returns false early (`webhook.rs:54-56`); the
    `ct_eq` is only called on equal-length slices (its only safe
    input shape).
  - Challenge passthrough at `webhook.rs:86-89`.
  - `verification_token` check at `webhook.rs:92-98` uses
    `actual_token != Some(...)`, which is **not** constant-time but
    the token is a published configuration value, not a secret, so
    timing-leak impact is negligible.
  - Dedup `processed_events` (`webhook.rs:69-71`) with 5-minute TTL
    reaper (`webhook.rs:158-159`) — bounded.
  - Event processing is `tokio::spawn`'d after returning 200
    (`webhook.rs:191-211`) — Feishu's recommended pattern to avoid
    retry storms.

  **Feishu TokenManager** (`feishu/api.rs:186-291`):
  - `refresh_lock: Arc<Mutex<()>>` + double-check after lock
    (`api.rs:227-231`) — prevents concurrent duplicate refresh.
  - `expires_at: AtomicU64` compared to `now`
    (`api.rs:210-213`); refresh 5 minutes before expiry
    (`api.rs:282`).
  - Debug logs use the raw JSON (`api.rs:debug!` calls in
    `get_ws_endpoint` etc.) — these contain only endpoint URLs /
    non-secret fields. Token values themselves are not logged.
    Note: `info!("Feishu: token refreshed, expires in {}s",
    expires_in)` (`api.rs:288`) does not log the token itself.

  **QqChannel** (`qq/channel.rs`):
  - `start` (`channel.rs:83-196`):
    - Creates a `TokenManager`.
    - Spawns `_send_task` (`channel.rs:108-132`): **handle is
      discarded with `let _send_task`**, so this task cannot be
      aborted explicitly. It exits only when `send_rx.recv()` returns
      None, which happens after all `Sender`s drop. On `stop()`,
      `self.send_tx = None` drops one sender; the other
      (`send_tx_clone` moved into `QqMessageHandler`, which is held
      by `wrapper`, which is held by the gateway task) is dropped
      when `gateway_handle.abort()` tears down the gateway task.
      Net: send_task eventually exits.
    - Spawns `gateway_handle` (`channel.rs:136-190`): a loop that
      fetches the gateway URL and calls `connect_to_gateway`. The
      loop has its own **bounded exponential backoff** with
      reset-on-stable (`channel.rs:137-189`, identical pattern to
      Feishu WsClient). `JoinHandle` stored in `self.gateway_handle`.
  - `stop` (`channel.rs:198-208`): `gateway_handle.take().abort()`,
    `self.send_tx = None`. Same task-leak window as Feishu: the
    heartbeat task spawned inside `connect_to_gateway`
    (`gateway.rs:73-99`) is only aborted on explicit error / close /
    reconnect branches inside that function
    (`gateway.rs:175, 202, 208, 216`). When the outer gateway task
    is `abort()`'d by `stop()`, the heartbeat task continues until
    either the next tick's `sender.send(...)` fails (because the
    WebSocket sink was dropped with the parent) or the heartbeat
    interval elapses with no consequence. Worst-case window: one
    heartbeat interval (server-negotiated, default 30 s).
  - `health_check` (`channel.rs:225-239`) checks
    `gateway_handle.is_finished()` and `token_manager.get_token()`.

  **Qq TokenManager** (`qq/api.rs:28-179`):
  - Same `refresh_lock + double-check` pattern as Feishu.
  - **Explicit token redaction** in debug logs (`api.rs:103-125`) —
    `accessToken` / `access_token` replaced with
    `***REDACTED***` before `debug!`. Error messages also redact
    sensitive keys (`api.rs:134-150`). This is a **better secret-
    handling practice** than Feishu's.
  - `expires_in` field accepts both `u64` and string `"7200"`
    (`api.rs:158-164`) — robust to QQ API variability.

  **SessionHandler** (`session.rs`):
  - `SessionConfig::is_reset` uses `to_lowercase()` (Unicode-safe,
    not `eq_ignore_ascii_case`) for keyword matching — correctly
    handles non-ASCII reset keywords (`session.rs:133-162`).
  - `SessionHandler::get_or_create` uses DashMap entry API — atomic,
    race-free insertion per session key (`session.rs:260-271`).
  - Timeout reset replaces the handler under a per-session
    `Mutex<Session>` guard, so a slow handler cannot be replaced
    while it's mid-call (`session.rs:316-334`).

  Application reachability (single live caller):
  - `echo-agent-cli/src/cli/modes.rs:130-231` is the only EKO
    channel launcher: builds a `ChannelManager`, registers
    `QqChannel` and/or `FeishuChannel`, `start_all`s them, then
    `stop_all()` on shutdown.
  - No duplicate definition of `ChannelManager` / `FeishuChannel` /
    `QqChannel` exists.

  **Defects observed (details in task report):**
  1. `ChannelManager::Drop` (`manager.rs:131-141`) only logs — it
     cannot `await` on `stop_all`, so dropping without `stop_all`
     leaks the per-channel background tasks. The log message says
     "consider calling stop_all() before drop" but this is the
     framework's responsibility to make ergonomic.
  2. `FeishuChannel::stop` and `QqChannel::stop` abort the outer
     task but never call `WsClient::stop` / never explicitly abort
     the heartbeat / ping sub-tasks. The sub-tasks linger until
     their next I/O fails. Window: one ping/heartbeat interval
     (up to 120 s for Feishu, 30 s for QQ).
  3. Both TokenManagers create a new `reqwest::Client` via
     `http_client()` / `reqwest_client()` per `TokenManager::new`
     instance, and `FeishuChannel::new` also creates one
     (`channel.rs:152`). This isn't a defect per se, but
     `QqChannel::start` then reuses `self.http` for the gateway
     task (`channel.rs:106, 135`) — connection pool reuse is good.

- Log/artifact: none.

## Deviations

The protocol-isolation, reconnect math, dedup, HMAC verification,
and token-redaction expectations are met. Cleanup has the two
task-leak windows noted above and the `Drop` warning-only behavior.

## Conclusion

The IM channel layer isolates external protocols behind one typed
`ChannelPlugin` / `MessageHandler` trait and reconnects with bounded
exponential backoff that resets after stable connections — better
discipline than MCP's SSE transport. Cleanup is **best-effort**: the
`ChannelManager` `Drop` cannot run async cleanup, and per-channel
`stop()` leaks the heartbeat/ping sub-task for up to one interval
until its next I/O fails. No data-integrity or panic-safety defect
was found in this layer.

Supports findings F-INT-02-P2-03 (ChannelManager Drop), F-INT-02-P3-03
(channel stop sub-task leak).
