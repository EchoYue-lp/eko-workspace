## Claim

Each non-GUI trigger propagates `conversation_id`, `run_id`, and
`turn_id` (as appropriate for its lane) into the framework's
`AgentInvocationContext.runtime` (`ExternalRunContext`), so tools
called during the turn / run see consistent identity. Specifically:

- REPL chat: `conversation_id` from CLI flags; `turn_id` fresh per
  turn; `run_id = taskrun:{turn_id}` only in Task mode.
- Channel chat: `conversation_id = channel:{channel_id}:{sender_id}`
  (stable per sender); `turn_id` fresh per turn; `run_id` Task-mode
  only.
- Cron: `conversation_id = cron:{task_id}:{fire_id}`;
  `run_id` = persisted uuid; `turn_id` empty.
- Background: `conversation_id = background:{source}:{uuid}`;
  `run_id` = persisted uuid; `turn_id` empty.

## Expected Result

- Each trigger constructs `conversation_id` per its documented rule.
- `turn_id` is fresh per chat turn (REPL and channels); absent for
  cron/background (no chat message).
- `run_id` is persisted for cron/background (via `create_run`); for
  chat it is derived as `taskrun:{turn_id}` only in Task mode.
- The downstream `AgentInvocationContext.runtime` carries the same
  values into the framework, so tools see them via `ToolContext`.

## Conclusion

Supports V02's claim: identity propagation is consistent within each
lane and matches the documented conventions. The chat lane carries
`turn_id` (and derives `run_id` for Task mode); the task lane carries
a persisted `run_id` and a synthetic `conversation_id`. Both lanes
thread the values into `ExternalRunContext`, so framework-side tools
read the same identity.

The chat-lane identity matches what A-CHAT-01 V01 / A-INP-01
established for `PreparedUserTurn` consumption. The task-lane
identity matches what A-TSK-03 V01 established for the controller's
`load_snapshot` / `claim_task` flow.

Used by:

- The task report's Current Path identity table.
- The task report's Layering Decision (single derivation rule).

The cron `root_message_id = ""` (empty) is a deliberate design
choice (cron has no chat message to bind to) and is consistent with
how `executor.rs:3669-3722` rebuilds the in-scope identity from the
persisted run.
