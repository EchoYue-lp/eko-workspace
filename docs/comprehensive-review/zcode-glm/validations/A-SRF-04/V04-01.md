## Claim

Every non-GUI trigger has a reachable cancellation handle, every run
recovers cleanly on restart, and every recovered run auto-resumes.
Specifically:

- REPL / channel chat turns can be cancelled mid-flight.
- Cron runs are registered for cancellation via
  `TaskRuntimeStore::register_run_cancellation`.
- Background runs are registered for cancellation via the same path.
- `recover_incomplete` reconciles every `Running` run to `Paused`
  on restart.
- `BackgroundTaskService::resume_pending` re-dispatches every
  recovered run.
- Channels-only mode starts the same services as TUI/CLI.

## Expected Result

- Every trigger's CancellationToken is registered in
  `TaskRuntimeStore::run_cancel_tokens` (or held by an accessible
  surface field like TUI's `app.active_cancel`).
- Every shutdown path cancels in-flight runs (or the runtime drop is

- `recover_incomplete` + `resume_pending` cover every run regardless

- Channels-only mode starts the scheduler and the background service.

## Result

- Exit code: 0 (test runs — but the static inspection reveals the
  gaps the tests do not cover)
- Duration: ~1 minute (incremental cache)
- Summary: the claim FAILS on three independent counts.

  **Failure 1 — A-SRF-04-P2-01: Chat/Auto turns on REPL and channels
  have no externally reachable cancel handle.**

  Chat-lane cancellation registration is conditional on Task mode
  (`chat_driver.rs:240-252`):

  ```rust
  let _cancel_registration =
      if interaction_mode == InteractionMode::Task {
          match store.as_ref() {
              Some(store) => Some(
                  store
                      .register_run_cancellation(&formal_run_id, cancel.clone())
                      ...
              ),
              None => None,
          }
      } else {
          None
      };
  ```

  For Chat/Auto (the default at `channels.rs:60` and the REPL default
  at `repl.rs:192`), the registration is skipped. The token built at
  `repl.rs:533` (`cancel: CancellationToken::new()`) and at
  `channels.rs:244` (`let cancel =
  echo_agent::agent::CancellationToken::new();`) is held only by the
  spawned `drive_chat` future.

  Contrast with TUI (`tui/events.rs:1147-1153, 1410, 1937-1958`):
  `app.active_cancel = Some(cancel.clone())` is set before spawning,
  and `handle_esc` / the `q` key call `cancel.cancel()`. TUI therefore
  CAN cancel an in-flight turn; REPL and channels cannot.

  The REPL `Ctrl+C` handler at `repl.rs:239-241` only prints a hint
  and is only reached between turns (since `chat_with_agent` is
  awaited inline at `:234`). During an in-flight REPL turn, Ctrl+C
  falls through to the process default (SIGTERM → terminate) and
  forcible-aborts the turn.

  No `/cancel` slash command exists in the command registry
  (`grep -rn "cancel_chat\|/cancel" echo-agent-cli/src/cli/` returns
  only the test fixture at `channels.rs:840`).

  **Failure 2 — A-SRF-04-P2-02: Cron runs are recovered to Paused on
  restart but never auto-resumed.**

  `recover_incomplete` (`store.rs:1631-1760`) transitions every
  `Running` run to `Paused` regardless of conversation prefix — this
  half is correct.

  But `BackgroundTaskService::resume_pending`
  (`service.rs:556-589`) filters on
  `conversation_id.starts_with("background:")` at `:563`. The same
  filter appears at `:474, 516, 541, 552`. Cron runs have
  `conversation_id = "cron:{task_id}:{fire_id}"`
  (`executor.rs:3581-3582` with `source_kind = "cron"`), which fails
  the filter.

  No other component scans for paused cron runs. The scheduler's
  `FireFn` (`scheduler/runner.rs:47-130`) always creates a fresh
  `fire_id` and never consults previously-interrupted runs.

  `/cron resume <id>` (`cmd_impls/cron.rs:296-302, 301`) re-enables a
  CronTask SCHEDULE (the `CronTaskStatus`), not an interrupted RUN.

  Result: a cron run interrupted by a restart becomes Paused forever.
  Its partial work is preserved on disk but never re-dispatched. The
  next cron tick fires a NEW run, potentially duplicating the work.

  **Failure 3 — A-SRF-04-P2-03: Channels-only entry skips
  SchedulerRunner and BackgroundTaskService (imported from
  A-BOOT-01-P2-02).**

  `main.rs:357-403` (the `--channels` branch) spawns
  `cli::run_channels_mode(...)` and exits without calling
  `start_headless_services`. `start_headless_services`
  (`modes.rs:32-64`) is the only starter of both services for
  headless. `run_channels_mode` (`modes.rs:118-235`) does not start
  them either.

  Result: a user running `echo-agent-cli --channels` as a long-running
  IM bot gets no scheduled cron fires and no
  `BackgroundTaskService::submit` pathway. (`create_complex_task`
  still works because it goes through `drive_run_async`, not the
  service.)

  - `cargo test -p echo-agent-app-core --lib scheduler::` → 3 passed.
    These tests pin the routing (`launch_cron_run`) but do NOT
    exercise cancel or resume of cron runs.
  - `cargo test -p echo-agent-app-core --lib launch_unattended` →
    1 passed. Pins run_id return value; does not exercise cancel or
    recovery.

  No test in the repository asserts:
  - cancelling an in-flight Chat/Auto turn on REPL or channels.
  - resuming a Paused cron run after restart.
  - the presence of SchedulerRunner / BackgroundTaskService in
    channels-only mode.

## Deviations

The static inspection surfaced three gaps that the existing test
suite does not cover. The validation is failed not because any test
errored, but because the claim's three clauses are violated by the
source code at the cited lines.

## Conclusion

The claim is FALSIFIED on three independent counts:

1. Chat/Auto cancellation is unreachable from REPL and channels
   (A-SRF-04-P2-01). TUI has `app.active_cancel`; REPL and channels
   have nothing equivalent.
2. Cron runs do not auto-resume after restart (A-SRF-04-P2-02). The
   `background:` filter in `BackgroundTaskService::resume_pending`
   excludes the `cron:` prefix; no other component covers cron.
3. Channels-only mode does not start the scheduler or the background
   service (A-SRF-04-P2-03, imported from A-BOOT-01-P2-02).

The chat-lane terminal invariant (A-CHAT-01 V03) still holds — when
a turn IS cancelled (e.g. by process exit), the sink receives
exactly one terminal `AgentEvent::Error` via the
`envelope_event_stream` synthesis. The defect is not in the terminal
contract; it is in the cancel-handle reachability and the resume
coverage.

The task-lane reconciliation (`recover_incomplete` → Paused) is
correct; the defect is in the post-recovery resume filter for cron.

The positive half of the claim (every run reconciles on crash via
`recover_incomplete`) is supported by V04's evidence — `recover_incomplete`

happens AFTER reconciliation, not in reconciliation itself.
