## Claim

The trace layer redacts secrets only at `RunEvent::ToolCall.args` and leaves
all other persisted fields (`Run.input`, `Run.final_output`, `Run.error`,
`RunEvent::ToolResult.output_preview`, `RunEvent::ToolError.message`,
`RunSummary.input_preview`) verbatim. Separately, neither `JsonlRunStore` nor
`InMemoryRunStore` apply any size bound, retention, eviction, or compaction.
This validation confirms the static facts that underlie F-OPS-01-P1-03 and
F-OPS-01-P2-01.

## Conclusion

Supports F-OPS-01-P1-03 (secret leakage into trace store) and
F-OPS-01-P2-01 (no size bound on trace stores). The cleanest fix for both
is at the `JsonlRunStore::save` boundary: run the serialized JSON line
through `redact_secrets` before write (covers all current and future
fields), and enforce a `max_file_bytes` / `max_runs` cap with oldest-first
eviction. Field-level redaction is an alternative if nested-JSON validity
must be guaranteed char-for-char, but the persistence-boundary approach is
simpler and catches every field including future additions.

Does not prove the CLI currently persists traces in production — grep
confirms `with_run_store` is only attached in tests/examples today. The
finding is a latent framework defect that becomes live the moment any
consumer (EKO or third-party) enables the trace store.
