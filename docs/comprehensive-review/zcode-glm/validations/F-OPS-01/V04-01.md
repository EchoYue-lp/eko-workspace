## Claim

The `telemetry` feature is cleanly gated at the module, prelude, optional
dependency, and CLI consumer levels (positive). However, the gated module
is functionally inert: the five `Metrics::record_*` helpers have zero
callers anywhere in `echo-agent` or `echo-agent-cli`, and
`shutdown_telemetry` is never invoked, so OTLP spans/metrics are not
flushed on exit. This validation confirms the static facts that underlie
F-OPS-01-P2-02 and confirms the positive gating claim required by V04.

## Method

Read-only static inspection of feature gating plus a repository-wide
caller inventory for `Metrics::record_*`, `init_telemetry`, and
`shutdown_telemetry`. No commands were executed.

## Conclusion

Supports the positive half of the V04 claim ("telemetry-disabled behavior
cleanly gated") and F-OPS-01-P2-02 ("metrics wiring is missing; telemetry
is dead-on-arrival"). The feature gate itself is exemplary — consumers
opting out get zero code. The defect is that consumers opting in get an
empty collector: the framework ships the OTLP plumbing but never connects
the LLM/tool pipelines to the `Metrics` instruments, and never hooks
shutdown flush.

Direction (consumed by the task report):

- Wire `record_llm_call` / `record_llm_tokens` / `record_llm_latency` at
  the neutral LLM provider boundary (or in the OpenAI / Anthropic
  adapters) so every provider benefits, and `record_tool_execution` /
  `record_tool_latency` in `echo-execution/src/tools.rs` around tool
  dispatch. Each call site is a 2-3 line addition guarded by
  `#[cfg(feature = "telemetry")]` (or by `Metrics::get().map(|m| ...)`,
  which is already feature-transparent via the `Option` return).
- Hook `shutdown_telemetry` into the application's shutdown sequence
  (e.g. `AppState` Drop or a dedicated `shutdown()`).

Does not prove the OTLP exporter works against a real collector — that
requires a dynamic test with a local OTLP collector or an in-process
`MeterProvider` test harness. Out of scope for this static review.
