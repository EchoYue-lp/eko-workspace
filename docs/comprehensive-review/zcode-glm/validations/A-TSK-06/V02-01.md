## Claim

`execution_checks` and `acceptance_criteria` are kept as **distinct
fields with distinct enforcement gates** — they are never conflated
into a single check. This obeys AGENTS.md's adapter-boundary rule
("语义不同的字段…不得为了迁就旧结构而压平成一个字段").

1. **Schema separation.** `PlanTask` (types.rs:985-1031) declares
   `execution_checks: Vec<String>` (line 1007) and
   `acceptance_criteria: Vec<String>` (line 1011) as **separate**
   `#[serde(default)]` fields. The field-level doc comments
   (types.rs:1003-1010) state the semantic boundary explicitly:
   - `execution_checks`: "可执行验证项(命令类). …每个 execution_check
     必须有 `observed + passed` 才能通过 execution 门禁."
   - `acceptance_criteria`: "语义验收标准(描述类). 由 Reviewer 基于
     Subagent 输出判定,不要求工具事件证据."
2. **Hard-evidence gate** (`assess_task_execution`, executor.rs:695-765).
   This gate runs FIRST, immediately after the Subagent completes. It
   verifies:
   - `execution_checks` were observed with `Observed + Passed`
     verification (executor.rs:726-735). A missing observed pass →
     `CompletionAssessment::AcceptancePending` (block, not retry).
   - `required_artifacts` exist with `sha256 (64 chars) +
     producer_execution_id` (executor.rs:738-755). A missing artifact
     → `AcceptancePending`.
   - This gate NEVER judges `acceptance_criteria` (the comment at
     executor.rs:688-689 says so explicitly: "Acceptance criteria are
     intentionally NOT judged here — they are reviewer-judged in the
     ReviewGate, never auto-passed").
3. **Reviewer-judged gate** (`run_review_gate` → `review_task`,
   executor.rs:1773 + review.rs:82). This gate runs SECOND, only when
   `assess_task_execution` returned `Executed` (all hard evidence
   satisfied). It sends the task's `acceptance_criteria` to the
   reviewer LLM (review.rs:313-317 in `build_review_prompt`) along
   with the execution_checks (for context only — the LLM does not
   re-judge them). `requires_review` (review.rs:49-55) gates entry:
   either `acceptance_criteria` is non-empty OR the task kind is
   `Implementation`/`Debugging`.
4. **`required_artifacts` is a third, distinct gate.** It is also
   hard-evidence (hash + producer id) but bound to file artifacts
   rather than command verifications. Lives inside the same
   `assess_task_execution` function but tracked as a separate list
   (`missing_artifacts`) so the block reason names the exact missing
   piece.

**Schema proof** (types.rs:1003-1011):

```text
/// 可执行验证项(命令类)。Subagent 运行这些命令时,Runtime 从工具事件
/// 记录 `observed` 证据;每个 execution_check 必须有 `observed + passed`
/// 才能通过 execution 门禁。示例:`cargo test --lib`、`npm run build`。
#[serde(default)]
pub execution_checks: Vec<String>,
/// 语义验收标准(描述类)。由 Reviewer 基于 Subagent 输出判定,不要求
/// 工具事件证据。示例:`模块边界清晰`、`前端组件层级合理`。
#[serde(default)]
pub acceptance_criteria: Vec<String>,
```

**Hard-evidence gate** (executor.rs:695-765, key branches):

| Check | Failure outcome | Retriable? |
|---|---|---|
| `result.status != Completed` | `ExecutionFailed{reason}` | yes (within retry budget) |
| `result.summary` empty | `ExecutionFailed` | yes |
| `result.remaining_work` non-empty | `ExecutionFailed` | yes |
| any `verification.status != Passed` | `ExecutionFailed` | yes |
| any `execution_checks[i]` lacking `Observed + Passed` match | `AcceptancePending{missing_checks}` | NO — block |
| any `required_artifacts[i]` lacking `available + sha256(64) + producer_execution_id` | `AcceptancePending{missing_artifacts}` | NO — block |

The hard-evidence gate never consults `acceptance_criteria`. Its
comment (executor.rs:686-689) explicitly defers: "Acceptance criteria
are intentionally NOT judged here — they are reviewer-judged in the
ReviewGate, never auto-passed."

**Reviewer-judged gate** (review.rs:298-337, the prompt):

```text
Task under review:
  …
  execution checks: {execution_checks.join("; ") or "(none specified)"}
  acceptance criteria: {acceptance_criteria.join("; ") or "(none specified)"}
… Return JSON: { outcome: "pass" | "needs_fix" | "blocked", … }
Mark 'pass' only if the claimed outcome is supported and every
applicable required verification is addressed.
```

The prompt includes BOTH lists but the verdict semantics are
acceptance-driven (the reviewer is told to mark `pass` only if the
claimed outcome is supported AND every applicable required
verification is addressed — the latter being a re-statement of the
hard-evidence invariant, not a re-judgment of the observed-tool-event
proof).

**Order of enforcement** (executor.rs:1396-1530):

```text
match assess_task_execution(&task, &result) {
    ExecutionFailed { .. }     → retry or fail
    AcceptancePending { .. }   → block (NOT retryable)
    Executed                   → run_review_gate (the LLM gate)
                                  Pass → integrate_reviewed_task → Completed
                                  NeedsFix → block (review-stopped)
                                  Suspend → block (circuit-breaker)
                                  Skipped → block (no reviewer LLM)
}
```

The reviewer gate is reached only after `Executed` returns; therefore
the hard-evidence gate is a strict precondition. The reviewer never
sees a task whose `execution_checks` or `required_artifacts` lack
observed evidence.

**Subagent prompt also separates them** (subagent_prompt.rs:346-361):

```text
append_list("Execution checks:", &task.execution_checks, …);
append_list("Acceptance criteria:", &task.acceptance_criteria, …);
append_list("Required artifacts:", &task.required_artifacts, …);
```

So the executing Subagent itself sees three distinct sections and
knows: it must run the execution_checks as commands (which the runtime
will observe), it must produce the required_artifacts (which the
runtime will hash), and it will be judged by the reviewer against the
acceptance_criteria prose.

## Conclusion

Supports: the "acceptance/check separation" invariant. The two fields
have distinct schemas, distinct enforcement gates, distinct orders
(hard evidence first, reviewer second), and distinct failure modes
(hard-evidence failure blocks without retry; reviewer NeedsFix also
blocks but with a circuit breaker). The executing Subagent sees them
as separate prompt sections; the reviewer LLM sees them as separate
sections in the review prompt.

Supports: AGENTS.md's "don't conflate semantically distinct fields"
invariant — `execution_checks` (machine-judged from tool events) and
`acceptance_criteria` (reviewer-judged from prose) are kept apart at
every layer.

Does NOT support (and is not asked to support): that the
`required_artifacts` gate is also fully separated from the
`execution_checks` gate. They share the same `assess_task_execution`
function and the same `AcceptancePending` outcome, distinguished only
by the `missing_checks` vs `missing_artifacts` field. This is a
minor stylistic point — they are still tracked separately, and the
block reason names which is missing.

Findings using this validation: none directly. The separation is clean.
