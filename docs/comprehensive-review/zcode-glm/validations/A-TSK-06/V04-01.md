## Claim

The review gate's input — task spec + acceptance criteria + execution
checks + subagent output — can be reconstructed to the **exact same
form** after a crash/restart, so a re-run of the review produces a
verdict over the same evidence (not a degraded one). Specifically:

1. The task spec is durable: `PlanTask` lives on `plan.json`
   (rebuilt from `PlanRevisionCommitted` events by
   `rebuild_plan_from_events`).
2. The subagent output is durable: `record_subagent_released`
   persists `full_output` and `result` on the `SubagentReleased`
   event keyed on `(task_id, execution_id)`. The
   `recoverable_subagent_result` fold reads them back.
3. The `run_review_gate` call site in `execute_task`
   (executor.rs:1462-1474) prefers `full_output` over the bounded
   `result.summary`:

   ```rust
   let review_output = if full_output.trim().is_empty() {
       summary.as_str()
   } else {
       full_output.as_str()
   };
   ```

   On restart, the kernel's re-dispatch path re-runs `execute_task`,
   which re-acquires the claim and re-fetches the same task spec from
   `plan.json`. The subagent output is reconstructed from the
   durable event stream by `recoverable_subagent_result` BEFORE the
   re-dispatch is attempted (so the durable result is the one re-used
   without re-dispatch — A-TSK-04 V04).

4. The review prompt itself is deterministic in `(task,
   subagent_output, template)` — the same inputs always produce the
   same prompt string. The `ProfileTemplate::for_profile(task.domain_profile)`
   lookup is also deterministic.
5. The review result is **idempotently re-runnable**: a second
   `review_task` invocation after a restart produces a fresh
   `ReviewResult` with a new `id` and `created_at`, but the inputs to
   the verdict are identical.

**Review-prompt determinism:**

`build_review_prompt` (review.rs:298-337) constructs the prompt by
formatting:

- `task.title`, `task.description`, `task.files`,
  `task.execution_checks`, `task.acceptance_criteria` — all from
  the `PlanTask` read off `plan.json` (rebuilt from events);
- `subagent_output` — the `&str` argument;
- a fixed JSON-shape instruction and the固定 preamble.

No `chrono::Utc::now()`, no `uuid::Uuid::new_v4()`, no random IDs in
the prompt body. The only nondeterministic field on `ReviewResult`
is `id` (a new UUID) and `created_at` (now), both of which are
metadata on the persisted review — they do not affect the verdict.

The reviewer's `ChatRequest` (review.rs:94-102) does include
`user_id: Some(cache_user_id)` for caching, but no timestamp or
session-id. The two messages (`Message::system(preamble)` +
`Message::user(prompt)`) are deterministic in the inputs.

**`review_output` selection (executor.rs:1462-1466):**

```rust
let summary = result.summary.clone();
let review_output = if full_output.trim().is_empty() {
    summary.as_str()
} else {
    full_output.as_str()
};
```

`full_output` here is the `TaskDispatchSuccess.full_output` field —
the post-thinking output stream assembled by the dispatch path. On
the success path (executor.rs:2303-2407), it is the same string
passed to `record_subagent_released(full_output = Some(&full_output))`
at executor.rs:2341. Therefore the persisted `full_output` is the
same string the review gate saw.

**Crash-recovery reuse path:**

`recover_incomplete` (store.rs:1631-1776) walks each Running todo:

```text
let execution_id = task.claim.execution_id(run_id, task.id);
let completed_subagent = execution_id.as_deref().and_then(|id| {
    self.recoverable_subagent_result(run_id, &todo.task_id, id)
});
match (completed_subagent, active_mutating) {
    (Some(_), _) => (Pending, "Subagent completed before interruption; pending review"),
    (None, Some(_)) => (Blocked, "mutating side effect is indeterminate"),
    (None, None) => (Pending, "interrupted; pending resume"),
}
```

The durable result is queried BEFORE the task status is reset to
Pending. The execution_id is derived from the persisted claim on the
task (task.claim.as_ref().map(|c| c.execution_id(run, id))), so it
matches the execution_id the Subagent was originally dispatched
under.

When the kernel re-dispatches the now-Pending task on resume
(`execute_runtime_plan` → `execute_task`), it acquires a new claim
with `attempt = retry_count + 1`. **This produces a different
execution_id.** However, the dispatch path itself short-circuits:
the framework `RuntimeDagExecutor` checks for a durable result with
the new execution_id, does not find one, then re-dispatches.

Wait — that contradicts the test
`boot_recovery_reuses_completed_subagent_without_redispatch`. Let me
re-read.

The test (store.rs:2738) sets up:

- A task with `retry_count = 0`, `claim.attempt = 1`, so
  `execution_id = "r1:t1:1:1"`.
- A `SubagentReleased` with `step_id = "r1:t1:1:1"` and
  `status = "completed"`.
- Calls `recover_incomplete`, which transitions the run Running →
  Paused and the task Running → Pending. The task's claim is **not
  reset** — it is the projection's `claim` field that is cleared
  when the task transitions out of Running. The persisted event
  stream still carries the original `TaskStarted` event with the
  original claim.

On resume, the dispatcher's `claim_task` reads the persisted plan
(this is rebuilt from events). The persisted task's last status
event is the recovery-reset `TodoUpdated{status=Pending, claim=null}`,
so the new claim has `attempt = retry_count + 1 = 1` (retry_count
was 0). The new execution_id is `r1:t1:1:1` — **the same as the
original**, because `attempt` is `retry_count + 1`, and
`retry_count` is 0 both times (no retry happened; this is a
recovery reset, not a retry).

This is the key subtlety: recovery does NOT bump `retry_count`
(unlike `retry_blocked_task` or `requeue_claimed_task`), so the
re-claim produces the same `(revision, attempt)` and therefore the
same `execution_id`. The durable result for that execution_id is
still on the event stream and is reused. The test asserts this.

Therefore: on recovery-with-completed-subagent, the kernel re-uses
the durable result without re-dispatch. The review gate sees the
same `full_output` it would have seen pre-crash.

**`recoverable_subagent_result` fold (store.rs:2039-2078):**

Reads `full_output` from the event payload (or falls back to
`result.summary` when `full_output` is empty/missing). Returns
`RecoverableSubagentResult { result, full_output }`. This is the
struct the dispatcher uses to short-circuit dispatch on resume.

The fold is keyed on `(task_id, execution_id)` and clears on
`SubagentAssigned` (store.rs:2053) — so a confirmed retry (which
appends a new `SubagentAssigned`) does invalidate the prior result.
This was verified by A-TSK-04 V01
(`patched_spec_uses_new_execution_identity_without_retry_bump`).

## Deviations

One caveat: the durable result is reused **only** when the task's
`execution_id` matches on resume. The execution_id is
`{run_id}:{task_id}:{revision}:{attempt}`. A revision bump (e.g.
the user edits the plan during the crash window) invalidates the
durable result; the task re-dispatches with a new execution_id and
the review sees fresh output. This is the intended behavior
(A-TSK-04 V01) — it prevents stale-output reuse — but it means the
review input is "restart-equivalent" only when the plan is also
stable across the restart.

## Conclusion

Supports: the "restart-equivalent review input" invariant. When the
plan revision is stable across the crash:

- The task spec is read from the rebuilt `plan.json`.
- The subagent output (`full_output`) is read from the durable
  `SubagentReleased` event by `recoverable_subagent_result`.
- The review prompt is deterministic in `(task, subagent_output,
  template)`.
- The recovery sweep reuses the durable result without re-dispatch
  (because `retry_count` is not bumped by recovery, the
  `execution_id` matches).
- Therefore a re-run of the review gate sees the same inputs and
  produces a verdict over the same evidence.

Supports: the "full output preferred" sub-invariant. The
`review_output` selection prefers `full_output` over the bounded
`summary`, so the review sees the complete Subagent output stream
(excluding thinking tokens — see V01) rather than the 2 000-char
truncated summary.

Caveat (does not invalidate the claim): a plan revision between
crash and resume correctly invalidates the durable result. This is
the intended behavior, not a regression.

Findings using this validation: none directly (the invariant holds).
