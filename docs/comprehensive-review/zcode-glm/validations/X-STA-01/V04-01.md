### On-disk leak characterization

After deleting a conversation, the following persist on disk:

1. **`~/.eko/tasks/<run_id>/events.jsonl`** — the full event stream
   for every run attached to the conversation. Contains:
   - `RunCreated` payload with goal, conversation_id, mode_hint
   - `PlanRevisionCommitted` payload with the full plan (task specs,
     acceptance criteria)
   - `TaskStarted`/`TaskCompleted` payloads with summaries
   - `SubagentAssigned`/`SubagentReleased` payloads with subagent
     outputs, verification results, touched files
   - `ToolStarted`/`ToolCompleted` payloads with tool names + args
   - `RecoveryBlocked` payloads (if any)
   - `Note` payloads with summaries
2. **`~/.eko/tasks/<run_id>/plan.json`** — the latest plan snapshot.
3. **`~/.eko/tasks/<run_id>/run-state.json`** — the latest run +
   task execution state.
4. **`~/.eko/runtime_state/<safe(id)>/checkpoint.json`** — the
   framework resume checkpoint containing the full `messages_json`
   (the entire message history including user goal text, assistant
   responses, tool results) + `current_plan` + `active_skills`.
5. **`~/.eko/runtime_state/<safe(id)>/nodes.json`** — the TaskNode
   DAG state.

### Stale-data risk on id reuse

If a new conversation reuses a previously-deleted conversation_id
(very unlikely for the frontend's `conv-{Date.now()}-{6-char rand}`
but theoretically possible for explicit ids, and definitely possible
for REPL/channels which use `Uuid::new_v4()` only as a fallback when
no id is configured):

- `latestRunForConversation(id)` would return the OLD run.
- The frontend would render the old plan/todos/subagents.
- `restore_thread_context` would load the OLD checkpoint's messages
  into the new conversation's context.

This is the "stale overwrite" risk the task spec asks about. The
probability is low under the current id-generation policy, but the
structural possibility exists because the cascade does not remove
the orphaned files.

### Why tool-execution cascade is correct but TaskRuntime is not

The tool-execution cascade (`tool_execution.rs:464-506`) was
implemented as a `remove_conversation(conversation_id)` method on
`ToolExecutionRepository`, then wired into Tauri `delete_conversation`
at conversations.rs:600-607. The implementation:

1. Computes the per-conversation scope dir from `conversation_id`.
2. Renames it to a tombstone under `.trash/`.
3. Drops the index entries (summaries/details/active) whose
   `conversation_id` matches.
4. Async-removes the tombstone.

The TaskRuntime side was never given an analogous
`delete_runs_for_conversation(conversation_id)` method. The
`TaskRuntimeStore` has `recover_incomplete` (boot sweep),
`request_cancel` (single-run cancel via driver token), and
`transition_run(Cancelled)` (single-run terminal transition), but
no per-conversation directory removal.
