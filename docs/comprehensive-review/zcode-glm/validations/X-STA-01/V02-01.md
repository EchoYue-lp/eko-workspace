## Claim

For every meaningful crash point in the persistence pipeline (mid-
write, mid-event, mid-task, mid-recovery), the system either (a)
self-heals on the next operation, (b) fails safe with the prior
state intact, or (c) fails loud with an error the consumer can
recover from. No crash point silently corrupts data or bricks the
run without a documented recovery path.

### Atomic-write recipe comparison

```text
                     uuid temp   fsync temp   rename   parent-dir fsync
FileConversationStore   YES          YES        YES          YES           ✅ canonical
FileRuntimeStateStore   YES          YES        YES          YES           ✅ canonical
file_shadow (TaskRuntime)  unique(*)   YES        YES          NO            ❌ P2-02
tool_execution (write_json_atomic)  (not inspected in this task — A-SRF-02 / A-CHAT-01 territory)

(*) file_shadow uses tmp.{pid}.{ts}.{counter} suffix instead of uuid,
    but the uniqueness guarantee is equivalent for single-process use.
```

The three framework + application atomic-write routines did not
converge. F-MEM-01-P2-01 already documented this for `FileStore` and
`EmbeddingStore`; X-STA-01-P2-02 extends it to `file_shadow::atomic_write`.

## Deviations

Two:
1. P2-02 — the file_shadow atomic_write omits parent-dir fsync. This
   is the same class of inconsistency F-MEM-01-P2-01 flagged for
   `FileStore`/`EmbeddingStore`; the file_shadow instance was not
   noted in F-MEM-01 because file_shadow is application code (out of
   F-MEM-01's framework scope).
2. P2-01 (recorded under V03) compounds: the partial-tail recovery
   gap means a mid-append crash (#4) makes the run unwritable. So
   the crash-point #4 outcome is "fail silent then brick" rather
   than "fail loud with recovery path".

## Conclusion

Supports: the crash-point recovery characterization. Ten of eleven
crash points have a defined recovery path (self-heal, fail-safe, or
fail-loud). The single non-self-healing case (#9, mid-recovery) is
the A-TSK-04-P3-02 prior; the single silent-corruption case (#11,
checkpoint load) is the F-RCT-05-P2-02 prior.

Supports: the "events.jsonl is the authority; plan/run-state are
projections" invariant. Crash points #2, #5, #6, #7, #8 all rely on
this — the projection is disposable, the event stream is durable.

Does NOT support: the "atomic-write recipes converge" claim. The
TaskRuntime file_shadow atomic_write omits parent-dir fsync (P2-02).
The crash-point #2 outcome is still self-healing because plan.json
is a disposable projection — but the inconsistency is a robustness
gap.

Findings using this validation: P2-02 (atomic-write parent-dir fsync
gap on file_shadow).
