## Claim

A single composition root (`AgentRuntime::bootstrap` in
`echo-agent-app-core/src/runtime.rs`) constructs the process-wide services
shared by every entry point (TUI, GUI, CLI, channels). A second composition
root (`AppState::from_shared` in `echo-agent-app-core/src/state.rs`) builds
the per-process state container that owns TaskRuntimeStore, scheduler,
background-task service, conversation store, tool-execution repo, workspace
registry, and skills hub. The two roots plus the `AgentPool` form a layered
ownership DAG that is constructed exactly once per process for the shared
parts.

## Expected Result

- One shared bootstrap that returns an `AgentRuntime` with all cross-mode
  services wired once.
- An `AppState` that owns the per-process state containers, with
  `task_runtime_store` constructed either inside `AppState::from_shared`
  (for GUI) or via `build_task_runtime_store_for_headless` (for TUI/CLI/
  channels).
- Recovery logic on the TaskRuntime store that runs once at startup.
- Identifiable "shared once" vs "per-session/per-conversation" services.

### TaskRuntimeStore construction and recovery

Two parallel construction paths exist. Both call the same factory:

1. **Headless path (TUI/CLI/channels):** `build_task_runtime_store_for_headless()`
   in `src/main.rs:35-57`. Calls `TaskRuntimeStore::new()`, falls back to
   `new_in_memory()` on error (logged warn), then calls
   `store.recover_incomplete()` at line 52. The resulting
   `Option<Arc<TaskRuntimeStore>>` is threaded into `register_task_tools_on_agent`,
   `AgentPool::from_runtime`, and `bind_task_execute_to_pool`. The store is
   NOT installed on AppState because the headless path never builds AppState
   (it uses the agent + pool directly).
2. **GUI path:** `AppState::from_shared` builds it inline at
   `state.rs:547-566`: `TaskRuntimeStore::new()` → fallback
   `new_in_memory()` → `store.recover_incomplete()` → wrap in `Arc`. The
   `tasks.runtime` field on AppState is `Option<Arc<TaskRuntimeStore>>`
   (`state.rs:389`). It is then read by `desktop.rs:200-206` to call
   `register_task_tools_on_agent` and by `init_pool` (`desktop.rs:210-215`).

`recover_incomplete()` is invoked exactly once per process in both paths.
The framework's TaskRuntimeStore is a file-backed store (no SQLite, per
AGENTS.md) — see `tasks/task_runtime/` for the implementation. A separate
V should audit that store in detail (out of scope for B-PATH-01).

### Composition root 3 — `AgentPool::from_runtime`

Path: `echo-agent-app-core/src/agent_pool.rs:219-275`. Extracts
`SharedResources` from the primary agent (`SharedResources::extract_from` at
`agent_pool.rs:120-`), copies `browser_runtime`, `task_runtime_store`,
`skill_descriptors`, `tool_output_artifacts`, `working_dir` from the runtime,
and pre-creates a `__background__` agent if `enable_background_agent`.

Per-conversation agents are constructed lazily by `acquire(conversation_id)`
(`agent_pool.rs:293-`) and `__task__:`-prefixed task subagents via the task
runtime. Pool capacity only counts conversation agents
(`is_conversation_agent` at `agent_pool.rs:286-288`).

## Deviations

None for the claim itself. Two observations that may matter downstream:

1. The headless path's `start_headless_services` builds an `AppState`
   purely to call `start_task_service` and `start_scheduler_with_store`
   (`modes.rs:57-63`), then returns `(task_service, scheduler)` and lets
   `AppState` drop. The `connection`, `storage`, `webhook`, etc. sub-states
   are constructed and immediately discarded — wasted work, and a
   confusing pattern (the call site looks like it's just starting two
   services but actually constructs the full 14-field AppState). This is
   not a bug, but is a maintainability concern (see B-PATH-01-P3-01).
2. The headless path constructs `TaskRuntimeStore` via
   `build_task_runtime_store_for_headless` and the GUI path constructs it
   inside `AppState::from_shared`. Both call the same factory and
   `recover_incomplete`. The two paths are duplicated (see
   B-PATH-01-P2-03).

## Conclusion

The composition roots are exactly as claimed. `AgentRuntime::bootstrap` is
the single shared composition root; `AppState::from_shared` is the per-process
state container; `AgentPool::from_runtime` is the per-concurrency factory.
`TaskRuntimeStore` recovery runs exactly once per process via either of two
parallel paths. All shared services are constructed once per process;
per-session/per-conversation services are correctly identified.

This result does not prove:
- that any service actually works end-to-end (no execution attempted);
- that all 14 sub-states of AppState are exercised (some may be dead — out
  of scope here, see A-* tasks).

Findings using this report: B-PATH-01-P2-03 (duplicated TaskRuntimeStore
construction), B-PATH-01-P3-01 (wasteful AppState construction in headless
path).
