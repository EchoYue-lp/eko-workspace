## Claim

The five entry modes (TUI, GUI, CLI, channels, cron/background) have
asymmetric service coverage. Two services are started in GUI but not in
other user-facing modes (MCP health check, BackgroundTaskService in pure
channels mode), violating the TUI/GUI parity rule in AGENTS.md.

## Method

Static mode-to-service matrix construction. Procedure:

1. Inventoried all "long-running services" that can be started at boot:
   `AgentRuntime::bootstrap`, `AgentPool`, `SchedulerRunner`,
   `BackgroundTaskService`, `TaskRuntimeStore`, MCP health check,
   Dreaming task, config watcher, conversation store, workspace registry,
   plugin runtime bind_scheduler, browser runtime.
2. For each mode (TUI, GUI, CLI, channels-only, channels+CLI), traced
   whether the service is started, using the call graphs from V01 and V02.
3. Cross-referenced AGENTS.md parity rule: "TUI/GUI/CLI 必须功能对等"
   and "禁止以'某模式不需要'为由拒绝给该模式接入能力".
4. Flagged every asymmetry as a candidate parity gap.

No code was executed.

## Expected Result

Per AGENTS.md, TUI/GUI/CLI should have functional parity. Asymmetries are
gaps, not design choices. I expected to find:
- The "TUI doesn't use the task runtime" comment flagged in AGENTS.md as a
  historical gap — now fixed (V02 confirmed `task_runtime_store` is built
  in all headless modes).
- The Dreaming parity gap (historical) — now fixed in all 3 user-facing
  modes.

I expected to possibly find new asymmetries in MCP health, background
service, or workspace routing.

### Parity gaps identified

#### GAP-1: MCP health check is GUI-only (P2)

- **Service:** `infra::spawn_mcp_health_check` (`infra.rs:1111-1130`).
- **Started in:** GUI only (`desktop.rs:243`).
- **NOT started in:** TUI, CLI, channels, channels+CLI.
- **Effect:** GUI shows live MCP server health in the panels UI; TUI/CLI
  users have no equivalent — a server that goes down is invisible until a
  tool call fails. The `AppState::run_mcp_health_check` method
  (`state.rs:751`) and the in-memory `mcp_health` map
  (`state.rs:358`) exist but are not fed by any background loop outside
  GUI.
- **AGENTS.md parity rule violated:** "TUI、GUI(以及 CLI/channel)必须功能
  对等" / "禁止以'某模式不需要'为由拒绝给该模式接入能力".
- **Fix direction:** call `spawn_mcp_health_check` from
  `start_headless_services` (modes.rs) so TUI/CLI/channels+CLI all run it.
  Channels-only mode would need its own call site since it skips
  `start_headless_services`.

#### GAP-2: Channels-only mode skips `SchedulerRunner` and `BackgroundTaskService` (P2)

- **Services:** `state.start_scheduler_with_store` and
  `state.start_task_service` — both inside `start_headless_services`
  (`modes.rs:61-62`).
- **Started in:** TUI, CLI, GUI.
- **NOT started in:** pure channels mode (`run_channels_mode` at
  `modes.rs:117-235` does not call `start_headless_services`; main.rs:357-405
  spawns `run_channels_mode` and awaits shutdown_signal).
- **Effect:** IM channel users cannot schedule cron tasks, and
  `create_complex_task` runs do not benefit from the unified
  BackgroundTaskService (though the TaskRuntimeStore itself IS passed in,
  so direct task tools still work).
- **Mitigating observation:** channels reach the TaskRuntimeStore through
  `AppChannelMessageHandler.store` (`channels.rs:37`), so ad-hoc
  task_create/task_execute works. But the scheduler UI (`/cron` slash
  command) is unavailable, and `BackgroundTaskService.submit_run` /
  `submit_dag` (which the GUI exposes through `commands::tasks::submit_task`)
  is not wired in.
- **AGENTS.md parity rule violated:** same as GAP-1.
- **Fix direction:** either (a) call `start_headless_services` from
  `run_channels_mode`, or (b) refactor `start_headless_services` so its
  side effects (scheduler + background service spawn) are reusable without
  the transient `AppState`.

#### GAP-3: Dreaming is not spawned in channels-only mode (P3)

- **Service:** `infra::spawn_dreaming_task` (`infra.rs:1143-1201`).
- **Started in:** TUI (`tui/mod.rs:1999`), CLI (`repl.rs:106`), GUI
  (`desktop.rs:247`).
- **NOT started in:** pure channels mode.
- **Effect:** the daily memory promotion/demotion pass does not run for
  IM-channel-only sessions. Since channels typically run as long-lived
  background processes, this is the mode that would benefit MOST from
  Dreaming.
- **AGENTS.md parity rule violated:** same.
- **Note:** the historical doc `memory-evolution-full-audit.md` says this
  was a known gap for TUI/CLI and was fixed; the same fix was not extended
  to channels mode.

#### GAP-4: GUI does not run session-end memory review (P3)

- **Service:** `ReviewIntegration::on_session_end` (called only at
  `main.rs:308-309` for TUI).
- **Started in:** TUI only.
- **NOT started in:** GUI (window close → `tauri_result` returned at
  `desktop.rs:258-268`, no review hook), CLI (`repl.rs` session exit at
  line ~250+ does not call `on_session_end`), channels.
- **Effect:** the session-end memory review report (scanned/stale/conflicts/
  proposals) is printed only in TUI. GUI users get no equivalent
  end-of-session summary; the Dreaming daily pass compensates partially
  but is not the same trigger.

### Previously-documented gaps now fixed

The historical `memory-evolution-full-audit.md` (lines 576, 805)
documents that `spawn_dreaming_task` was previously GUI-only. Confirmed
fixed:

- TUI: `tui/mod.rs:1996-2007` (spawned before event loop, cancelled
  after).
- CLI: `repl.rs:100-114` (spawned after banner, cancelled on exit).
- GUI: `desktop.rs:246-253` (spawned after task service start).

The "TUI doesn't use the task runtime" comment from `main.rs` history
(flagged in AGENTS.md as a parity violation) is also fixed: the current
`main.rs:172-182` comment explicitly states "Every headless surface is a
full Agent surface" and `build_task_runtime_store_for_headless` is called
unconditionally for headless modes. `runtime.rs:120-126` documents that
both TUI and GUI call `register_task_tools_on_agent` post-hoc.

### Background/cron-specific observations

- Cron runs route through `launch_cron_run` (Phase 3.1 unification,
  `scheduler/runner.rs:101`), which uses a pool-acquired per-run agent
  keyed `__cron__:{task_id}:{fire_id}` (`runner.rs:88`).
- The previous `runtime_store=None` fallback (`BackgroundTaskService::submit`
  + `execute_direct`) was removed (`runner.rs:36-39`) — `AppState` always
  constructs a `TaskRuntimeStore` at boot.
- Webhook emitter is shared: `runner.rs:53` clones the emitter so cron
  runs emit `CronTaskCompleted` on the same endpoints as chat.
- Per-run pool agents are released immediately after the run completes
  (`runner.rs:106-109`), avoiding the 5-minute idle eviction lag that
  `drive_run_async` has.

## Conclusion

The mode-to-service matrix reveals four parity gaps (GAP-1 through GAP-4).
The two most material are GAP-1 (MCP health check GUI-only) and GAP-2
(channels-only mode skips scheduler + background service). GAP-3 and GAP-4
are lower-impact but still violate the strict parity rule.

Previously-documented gaps (Dreaming TUI/CLI, TaskRuntime TUI) are now
fixed in code.

This result does not prove:
- that any of these services actually function (no execution attempted);
- that the gaps have user-visible impact in practice (e.g., MCP health may
  be queried on-demand elsewhere — out of scope here).

Findings using this report: B-PATH-01-P2-01 (MCP health parity),
B-PATH-01-P2-02 (channels skips headless services), B-PATH-01-P3-02
(Dreaming not in channels), B-PATH-01-P3-03 (session-end review TUI-only).
