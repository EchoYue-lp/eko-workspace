## Claim

The framework `FileConversationStore` writes conversations atomically
(uuid temp + fsync + rename + parent-dir fsync). The application
`Persistence::write_json` and `Sessions::reindex_all` paths either match
this recipe or are flagged as deviations.

This is the application-side recurrence of the framework defects
F-MEM-01-P2-01 and F-MEM-01-P2-02 (which found the same recipe drift in
`FileStore` and `EmbeddingStore`).

## Expected Result

The framework `atomic_write` is the canonical recipe. The application
should either reuse it (via a shared helper) or replicate all four
properties: unique temp name, temp fsync, rename, parent-dir fsync.

## Result

- Exit code: 0
- Duration: ~5 min code read
- Summary:
  - **Framework `FileConversationStore::atomic_write`** (file_conversation.rs:494-523)
    is correct and matches F-MEM-01's canonical recipe:
    - Unique temp name `.{file}.{uuid}.tmp` (502-506).
    - `File::create` + `write_all` + `sync_all` on temp (507-512).
    - `fs::rename(temp, path)` (517).
    - `sync_parent_directory(parent)` on Unix (521, 525-528).
    - Cleanup of temp on any intermediate error (514, 518).
  - **Application `Persistence::write_json`** (persistence.rs:350-361)
    fails the recipe on three counts:
    1. Static temp name `path.with_extension("json.tmp")` (persistence.rs:357)
       — collides across two `Persistence` instances pointed at the same
       path. Same defect as F-MEM-01-P2-02.
    2. No temp-file `fsync` (`fs::write(&tmp, &json)?` is the standard
       library helper that does not call `sync_all`, persistence.rs:358).
       A crash after `fs::write` returns but before the OS flushes the
       temp's bytes leaves the temp empty and the subsequent rename
       replaces the original with a zero-byte file.
    3. No parent-directory `fsync` after rename (persistence.rs:359).
       Same defect as F-MEM-01-P2-01.
  - **`SessionSearchEngine::reindex_all`** (conversation_file.rs:138-167)
    is read-only and does not write; no atomic-write concern.
  - **`ToolExecutionRepository`** (`tool_execution.rs`) defines its own
    `write_json_atomic` helper used for manifest persistence — out of
    scope for this task, owned by A-TSK-04 / F-RCT-05.
  - **Cross-call sequence in Tauri `save_conversation`**
    (`src/tauri/commands/conversations.rs:411-444`):
    `get_conversation` → `update_conversation` → `get_messages` →
    `project_saved_messages` → `save_messages`. Each call independently
    acquires and releases the framework `Mutex<StoreMeta>`; there is no
    transaction spanning the sequence. Concurrent saves of the same
    conversation race (the framework `save_messages` replaces
    `record.messages` wholesale).

## Deviations

- The framework `atomic_write` correctly uses `File::create` + `write_all`
  + `sync_all`, not the `fs::write` convenience helper; the application
  uses `fs::write` which skips `sync_all`. This is an additional
  difference beyond the F-MEM-01 framework findings.
- The cross-call sequence (Tauri `save_conversation`) is not strictly an
  "atomic write" concern — it is a multi-call sequence non-atomicity. It
  is recorded here because the same validation inspects the durability of
  the application's save path end-to-end and is promoted separately as
  P3-01.

## Conclusion

The framework `FileConversationStore` is fully durable. The application
`Persistence::write_json` is a third recurrence of the F-MEM-01 P2-01/P2-02
recipe drift (after `FileStore` and `EmbeddingStore`). Because
`Persistence` is dead code (per V01-01), the practical risk is low, but
the defect should be removed with the dead code (P2-01) rather than
silently inherited by any future resurrected caller.

The cross-call sequence in Tauri `save_conversation` is a separate,
lower-priority race (P3-01).

Supports findings: P2-01 (delete `Persistence` and its
sub-`write_json`), P3-01 (Tauri save_conversation non-atomicity).

## Follow-Up

None. The framework `atomic_write` should be factored into a shared
`echo-state::util` helper per F-MEM-01 P2-01's direction; if
`Persistence::write_json` is resurrected rather than deleted, it should
call that helper.
