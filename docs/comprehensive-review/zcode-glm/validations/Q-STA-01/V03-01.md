## Claim

All `unsafe` blocks in production source are confined to
`std::env::set_var` / `std::env::remove_var` calls (required `unsafe` under
Rust edition 2024) and are guarded by single-threaded semantics
(`call_once`, `EnvGuard` mutex, or init-time only). Numeric `as` casts
(`as u32`, `as usize`, etc.) are not checked by any clippy lint in the
mandatory gate, but sampled inspection shows they operate on values whose
magnitude cannot overflow the target type on a 64-bit platform.

## Method

**Unsafe search:** grepped for the `unsafe` keyword in production `src/`
(excluding test/comments), then filtered out string literals containing
"unsafe" (e.g., `"unsafe command"` in test data) and read each real
`unsafe {` block in context.

```text
grep -rn 'unsafe' echo-agent/echo-*/src/ echo-agent/src/ --include='*.rs' \
    | grep -v target | grep -v worktrees | grep -v '///'
grep -rn 'unsafe' echo-agent-cli/src/ echo-agent-cli/echo-agent-app-core/src/ \
    --include='*.rs' | grep -v target | grep -v worktrees | grep -v '///'
```

**Cast search:** grepped for `as (u8|u16|u32|u64|usize|i8|i16|i32|i64|isize)`
in production `src/`, then sampled the `as u32` (potential truncation) and
`as usize` (potential indexing) subsets for magnitude analysis.

## Expected Result

Per AGENTS.md "禁止任何会导致系统 panic 的 API": integer overflow and
unsafe operations that can panic or cause UB must be avoided. `unsafe`
blocks must have SAFETY comments justifying why they are sound.

### Numeric `as` casts

| Repo | Total casts | Sampled subset |
|---|---:|---|

Sampled findings — all low-risk:

- `as u32` on token counts, page counts, retry counts, concurrency config,
  array indices, image dimensions — all values bounded well below 2^32.
  Representative: `echo-core/src/tokenizer.rs:414` (`actual as u32` token
  count), `echo-tools/src/pdf.rs:238` (`max_pages as u32`),
  `echo-orchestration/src/tasks/task.rs:879` (`attempts.len() as u32`).
- `as usize` from `f64` for token-budget math
  (`echo-core/src/budget.rs:66-85`): `(total_window as f64 * pct) as usize`.
  Inputs are positive bounded token-window sizes; NaN/infinite cannot arise
  from sane config. Low risk.
- `fragments[seq as usize]` at
  `echo-integration/src/channels/channels/feishu/long_poll.rs:491`:
  direct index from network `seq`, **but guarded** by `seq >= 0 && seq < sum`
  (line 490). Safe.
- `i64 -> usize` from SQLite row counts
  (`echo-state/src/memory/sqlite_conversation.rs:231,418`): values are
  message counts, small and non-negative.

**No clippy coverage**: `clippy::cast_possible_truncation`,
`clippy::cast_possible_wrap`, `clippy::cast_precision_loss` are pedantic
lints, not enabled by the mandatory `-D warnings` gate. There is no
automated guard against a future risky cast being introduced.

- Log/artifact: none.

## Deviations

The `as` cast audit is a sample, not an exhaustive review of all 318 casts.
Full coverage would require enabling pedantic clippy lints or manual review
of every site. The sample was selected to cover the highest-risk patterns
(truncation to u32, indexing via usize, network-sourced values).

## Conclusion

Supports the finding that **unsafe and overflow risk is low**. The two
production `unsafe` blocks are edition-2024 `env::set_var` with appropriate
single-threading guards and SAFETY comments. Numeric casts operate on
bounded values; the one network-facing direct index is bounds-checked.

The residual risk is the absence of a clippy guard for future casts
(pedantic lints not in the gate). This is a P3 maintainability observation,
not a current defect.

Findings using this report: Q-STA-01-P3-02 (no clippy guard for numeric
casts).
