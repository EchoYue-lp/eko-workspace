## Claim

Recorded events can be replayed through every consumer's reducer, and
each reducer either correctly handles out-of-order / duplicate events
or refuses to replay them. The replay paths are symmetric across
event families (chat, subagent, tool execution, task runtime).

## Method

For each live consumer, identify its replay / hydrate entry point
(if any) and classify its out-of-order / duplicate tolerance. Then
identify which event families are recorded at all and which are
fire-and-forget.

read echo-agent-cli/web-frontend/src/stores/toolExecutionStore.ts:50-254

## Expected Result

Every event family that crosses the IPC boundary has a corresponding
hydrate/replay entry point. Reducers are monotone on the replay path
(late or duplicate events do not corrupt terminal state). Replay
coverage is symmetric: chat events are as replayable as task-runtime
events.

## Result

- Exit code: 0 (static read)
- Duration: n/a
- Summary: **asymmetric replayability.** Subagent / tool-execution /
  task-runtime event families all have dedicated hydrate paths that
  replay durably-persisted events through the same reducer as the
  live path. **Chat AgentEvents have no replay path** — they are
  fire-and-forget at every sink. Of the reducers that DO replay,
  subagentRunStore is monotone; toolExecutionStore is monotone only
  on the hydrate path, not the live ingest path (A-SRF-03-P2-01).

### Chat events are fire-and-forget at every sink

`chat_driver.rs:540-564` drains the envelope stream and forwards each
envelope to `sink.on_event`. The sink implementation then:

- `TuiChatSink` (`events.rs:2031-2210`): forwards a local `AgentEvent`
  to a per-turn mpsc; the TUI render loop consumes and discards.
  Nothing is persisted.
- `TauriChatSink` (`chat.rs:1341-1417`): emits `ChatEvent`s to
  `chat://event`. The frontend `chatEventHandler` consumes live; the
  only persistence is what `chatStore.scheduleAutoSave` writes via
  `save_conversation` (final assistant content, not the streaming
  trace).
- `ChannelChatSink` (`chat_driver.rs:575-591`): forwards to the
  channel's mpsc; `aggregate_by_sentence` renders and discards.
- `WebhookTurnObserver` (`chat_driver.rs:106-176`): emits webhook
  events for `LlmUsage`/`ToolCall`/`ToolResult`/`ToolError`/`Error`/
  `FinalAnswer`; these are external HTTP calls, not a replayable
  store.

The only chat-level persistence on the backend is for **Task-mode
runs**: `chat_driver.rs:323/361/377` writes three `ExecEvent::run`
boundary events (`RunStarted`, `RunCancelled`, `RunFailed`) to
`trace_sink` → `TaskRuntimeStore.events.jsonl`. These are run-level
lifecycle markers, not chat streaming events. The granular
`AgentEvent`s (`Token`, `ToolCall`, `ThinkStart`, etc.) are never
written.

### Frontend consequence

A page reload during or after a chat turn:

- Recovers: the final assistant message content (via
  `get_conversation` → `chatStore.replaceAll`).
- Recovers (if GUI + tool-using turn): tool execution history (via
  `ToolExecutionRepository` → `toolExecutionStore.hydrateConversation`).
- Recovers (if Task-mode run was active): the run, plan, todos,
  subagent records (via `taskRuntimeStore.loadByConversation`).
- **Does NOT recover**: streaming trace — thinking segments (`Token`
  events routed to `thinkingSegments`), budget notices, guard
  notices, parameter errors, context-compressed notices. These are
  live-only; the user who reloads sees a finalized assistant message
  with no record of the model's reasoning or any safety/budget
  events that fired during the turn.

### Subagent reducer monotonicity (replay path)

`subagentRunStore.ingest` at `:446-521` is the same entry point for
both live events and replayed `taskRuntimeSubagentExecutionEvents`.
The terminal lock at `:458-460` (`if (prev && prev.status !==
'running') return s;`) makes it monotone:

- A late `started` after `completed` → dropped (prev.status=
  `completed` ≠ `running`).
- A duplicate `completed` → dropped (prev.status already =
  `completed`).
- An out-of-order terminal (terminal arrives before some
  intermediate events) → intermediate events dropped (prev.status
  terminal).
- Retries use a new `subagent_run_id` key (`{run_id}:{task_id}:
  {plan_revision}:{attempt}` per A-FE-02 V01), so they never touch
  the old terminal record.

Tests: `subagentRunStore.test.ts:65-90` (duplicate-started-after-
terminal), `:92-108` (retry isolation).

### Tool-execution reducer monotonicity (replay path vs live path)

The hydrate path is monotone via `mergeToolExecution`
(`toolExecutionStore.ts:58-86`): status-rank (terminal=1 > running=0)
+ activity-timestamp tiebreaker. Tested at `toolExecutionStore.test.ts:147-192`.

The live ingest path is NOT monotone (`toolExecutionStore.ts:206-
217`): direct overwrite by `tool.id`, no rank guard. A late `started`
clobbers a terminal. This is the A-SRF-03-P2-01 / A-FE-02-P3-03
defect, not re-audited here — but it means **replay through the
hydrate path is safe, replay through the live ingest path is not**.
The two paths are asymmetric; a future fix that routes live ingest
through `mergeToolExecution` would unify them.

### ChatStore: no replay, no monotonicity guard

`chatStore.ts` has no hydrate entry that re-drives `AgentEvent`s.
`replaceAll` (used by conversation load) overwrites the message array
and resets `runStatus` to `idle`; it does not restore any streaming
state. `setRunStatus` (`chatStore.ts:391`) is unconditional — no
terminal lock. The structural monotonicity for chat relies entirely
on:

1. `message_key` filter at `useTauriChat.ts:50-58` (drops events
   whose message_key doesn't match the current turn), AND
2. `envelope_event_stream_after`'s break-on-terminal (framework
   level), AND
3. `TauriChatSink::on_event` emitting `Done` after the terminal
   (which clears `currentMessageKeyRef`, closing the filter window).

A reload destroys (1) and (3); the framework's (2) does not help
because there is no stream to drain after reload. The reloaded state
is whatever `get_conversation` returned, with no replay.

## Deviations

Three deviations from the symmetric-replay expectation:

1. **Chat AgentEvents have no recorded-replay path** (X-EVT-01-P3-01).
   Streaming trace is lost on reload. The other three event families
   (subagent, tool execution, task runtime) all replay correctly.
2. **ToolExecutionStore live ingest is not monotone** (confirmed
   A-SRF-03-P2-01 / A-FE-02-P3-03 from this angle). Replay via
   `hydrateConversation` IS monotone; replay via live `ingest` is not.
3. **ChatStore.setRunStatus has no terminal lock**
   (X-EVT-01-P3-03). Today's monotonicity is indirect via the
   `message_key` filter; a future change to that filter could reopen a
   finalized chat.

## Conclusion

The framework's terminal-monotonicity primitives (`envelope_event_stream`'s
break, `subagentRunStore`'s terminal lock, `mergeToolExecution`'s
status-rank) are sound where applied. The asymmetric finding is that
**chat-level events are not recorded for replay**, while subagent /
tool / task-runtime events are. Used by findings X-EVT-01-P3-01
(no chat replay), X-EVT-01-P3-03 (no chatStore terminal lock), and
cross-references A-SRF-03-P2-01 (live ingest overwrite).

Does not prove: that the durable replay paths produce byte-identical
state to the original live run (they produce *semantically-equivalent*
state per A-FE-02 V01/V02, but the streaming-only fields like
`thinkingSegments` are by construction unrecoverable).
