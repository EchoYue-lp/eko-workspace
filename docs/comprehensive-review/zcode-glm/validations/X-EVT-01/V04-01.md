## Claim

Across framework, EKO persistence, Rust surfaces, and TypeScript
reducers, the four terminal scenarios agree:

1. **Duplicate terminals**: only one terminal is observed downstream.
2. **Out-of-order terminals**: late non-terminal events after a
   terminal do not reopen the run.
3. **Cancelled vs Error**: the two terminal kinds are distinguishable
   end-to-end on every surface, or the collapse is documented and
   compensated.
4. **Synthesized terminal on stream-end-without-terminal**
   (`envelope_event_stream_after`): the synthesized `Error` is
   distinguishable from a real `AgentEvent::Error` when the
   distinction matters.

## Method

For each terminal scenario, trace the event through the framework
envelope, the EKO persistence (TauriChatSink), the Rust surfaces
(TuiChatSink, aggregate_by_sentence), and the TS reducers
(chatEventHandler, chatStore, subagentRunStore, toolExecutionStore).
Verify monotonicity at each layer.

## Expected Result

All four scenarios are handled correctly at every layer. No layer
reopens a finalized run. Cancelled and Error are distinguishable on
every surface that renders a status label.

## Result

- Exit code: 0 (static read)
- Duration: n/a
- Summary: scenarios 1 and 2 hold. Scenario 3 **fails on 3 of 4
  surfaces** (only GUI recovers the Cancelled vs Error distinction,
  via a post-`drive_chat` `TurnStatus` poll). Scenario 4 holds at the
  type level but the synthesized Error's `source:"agent_stream"` is
  indistinguishable from a real stream-level error to the chat
  frontend.

### Scenario 1: duplicate terminals

Framework envelope: `envelope_event_stream_after` at
`event_envelope.rs:174-177` breaks after the first terminal payload
(`is_terminal() == true`). Verified by
`normalizes_missing_and_duplicate_terminals`
(`event_envelope.rs:352-379`): a stream of `[FinalAnswer("first"),
Cancelled]` yields exactly one envelope, the `FinalAnswer`. ✓

Downstream consumers receive one terminal by construction; no
duplicate handling needed. Belts-and-braces defenses that exist:

- `TauriChatSink::handle_tool_event` `Cancelled | Error` arm
  (`chat.rs:1325-1328`) calls `cancel_active_tools`, which
  `drain()`s `active_tool_ids` (`chat.rs:1174`). A second call finds
  an empty set — idempotent.
- `chatEventHandler` `final_answer` arm (`chatEventHandler.ts:97-109`)
  clears `assistantIdRef.current = null`. A second `final_answer`
  finds `id = null` and skips `finalizeAssistantMessage`. Idempotent.
- `subagentRunStore.ingest` terminal lock
  (`subagentRunStore.ts:458-460`) drops any event after a terminal.
- `chatStore.finalizeAssistantMessage` (`chatStore.ts:354-362`)
  unconditionally sets `runStatus='completed'`; a second call is
  harmless (same state).

✓ All layers safe.

### Scenario 2: out-of-order (late non-terminal after terminal)

Framework envelope: impossible within one stream — once `break` fires
at `event_envelope.rs:176`, no further events are wrapped.

Across streams (e.g. a subagent fork that emits events after the
parent's terminal): each fork has its own `EventIdentity`
(`execution_id` is forced unique at `subagent/executor.rs:802-825`)
and its own sequence space. There is no cross-stream ordering
invariant; each stream's terminal is independent.

For the chat path, a late `Token` after `FinalAnswer` cannot arrive
through `drive_chat` (the wrapper broke). For subagent runs, a late
event after the terminal is dropped by the `subagentRunStore`
terminal lock.

The one place out-of-order CAN bite is the **toolExecutionStore live
ingest** path (A-SRF-03-P2-01): a late `started` for the same
`tool.id` clobbers a terminal `succeeded`/`failed`. This is a known
defect, not re-audited here. ✓ for terminal conformance, ✗ for
tool-ingest monotonicity (cross-reference).

### Scenario 3: Cancelled vs Error — **FAILS on TUI / REPL / channels**

This is the cross-surface failure that X-EVT-01 was scoped to find.

**Framework type contract** (`mod.rs:330-336`): `Cancelled` and
`Error{..}` are distinct terminal variants.

**Concrete agent reality** (F-RCT-03-P2-02): `ReactAgent` overrides
`chat_stream_with_cancel` / `execute_stream_with_cancel`
(`react/mod.rs:2821-2865`) without wrapping `cancel_aware_stream`. On
cancel, the in-loop handling exits via `IterOutcome::NoResponse` or
`IterOutcome::Abandoned`; the underlying stream returns `None` to the
envelope wrapper; **no `AgentEvent::Cancelled` is emitted**.

**Envelope wrapper** (`event_envelope.rs:180-191`): on stream-end
without terminal, synthesizes exactly one
`Error{source:"agent_stream", message:"agent stream ended without a
terminal event"}`. The wrapper cannot tell whether the stream ended
because of cancellation or because of a bug; it always emits `Error`.

**Net upstream contract**: every surface's `Cancelled` arm in the V01
matrix is **dead code for `ReactAgent`-driven turns**. The actual
terminal delivered is `Error`.

**Per-surface recovery**:

| Surface | Cancelled arm live? | How cancel is surfaced | Effect |
|---|---|---|---|
| GUI (TauriChatSink → chatEventHandler) | NO (dead) | **post-`drive_chat` `TurnStatus{status:"cancelled"}`** at `chat.rs:704-712`: `cancel.is_cancelled() ? "cancelled" : outcome.is_ok() ? "completed" : "failed"`. Sent as `ChatEvent::RunStatus{status:"cancelled"}` after `drive_chat` returns. `chatEventHandler.run_status` arm sets `runStatus='cancelled'`. | ✓ User sees "cancelled". |
| TUI (TuiChatSink) | NO (dead — `events.rs:2071` Cancelled arm never fires for ReactAgent) | The synthesized `Error` arrives, mapped to local `AgentEvent::Error(message)` at `events.rs:2144`. TUI main loop displays the error message text. **No `TurnStatus{cancelled}` post-emission.** | ✗ User sees "agent stream ended without a terminal event" as an error. |
| REPL (ChannelChatSink → aggregate_by_sentence) | NO (dead — `channels.rs:566` Cancelled arm never fires) | The synthesized `Error` arrives, propagates as `ReactError::Channel(...)` at `channels.rs:570-575`. REPL surfaces a channel error. **No `TurnStatus{cancelled}` post-emission.** | ✗ User sees a channel error. |
| Channels (IM) | NO (dead — same path as REPL) | Same as REPL — IM user receives `agent stream error: agent stream ended without a terminal event`. | ✗ IM user sees an error message. |
| Webhook (WebhookTurnObserver) | NO (no Cancelled arm at all; `Observer::observe` does not match `Cancelled`) | `Error{message}` triggers `WebhookEvent::AgentError`. No compensating signal. | ✗ Webhook consumer sees `AgentError`, not a cancel. |

The GUI is the only surface that recovers the distinction, and only
because `send_chat` polls `cancel.is_cancelled()` after `drive_chat`
returns and emits a separate `TurnStatus{status:"cancelled"}` event
through `TauriChatSink::on_event`'s `TurnStatus` arm
(`chat.rs:1365-1388`). The TUI / REPL / channels entry points
(`send_to_agent`, `run_repl_turn`, `channels handle`) do not emit any
post-`drive_chat` status event (verified at `events.rs:2222-2228`,
`repl.rs:541-545`, `channels.rs:262-270`).

**This is a multi-mode parity violation under AGENTS.md**: "TUI、
GUI(以及 CLI/channel)必须功能对等". Cancel is rendered as error on
3 of 4 surfaces.

**Persistence impact**: `TauriChatSink::handle_tool_event`'s
`AgentEvent::Cancelled | AgentEvent::Error { .. }` arm
(`chat.rs:1325-1328`) calls `cancel_active_tools` for both. Tool
cancellation is correct (the call is idempotent and the result is the
same whether triggered by Cancelled or Error). But the
`ToolExecutionRepository.cancel` is called via the Error arm on
ReactAgent; the Cancelled arm is dead. Tools are cancelled correctly;
only the *semantic label* in the chat stream is wrong.

### Scenario 4: synthesized terminal distinguishability

The synthesized terminal is `Error{source:"agent_stream", message:
"agent stream ended without a terminal event"}`. The
`source:"agent_stream"` discriminator is preserved through:

- `TauriChatSink::agent_event_to_chat_event` Error arm
  (`chat.rs:1563-1565`): formats as `format!("{source}: {message}")`
  → the wire payload is `agent_stream: agent stream ended without a
  terminal event`. Distinguishable from a real `Error{source:"llm"}`
  by the prefix.
- `TuiChatSink` Error arm (`events.rs:2144`): forwards only
  `message`, dropping `source`. The TUI user cannot tell a
  synthesized stream-end from a real agent error.
- `chatEventHandler` Error arm (`chatEventHandler.ts:140-150`): sets
  `runStatus='failed'` and finalizes the assistant message with
  `[Error] ${event.message}`. The GUI user sees the full
  `agent_stream: ...` text and could in principle distinguish, but
  the store treats it as a generic failure.
- `subagentRunStore`: not applicable — subagent runs go through
  `executor.rs` which emits explicit `DispatchCompleted` /
  `DispatchFailed` / `DispatchCancelled` events; the envelope
  synthesis path is not the typical subagent terminal path.

✓ at the type level, ✗ at the UX level — the TUI drops `source`
and the GUI flattens it to a generic failure status.

### Trajectory validator is unused

`validate_event_trajectory` (`event_envelope.rs:197-295`) verifies:
schema version, contiguous sequences, identity stability, no
duplicate `event_id`, parent-before-child tool lifecycle, exactly one
terminal, terminal is last, no unfinished tool calls. It is
re-exported via `echo-core/src/agent/mod.rs:18` and
`echo-agent/src/lib.rs:143`.

`grep -rn "validate_event_trajectory" --include="*.rs"` outside the
definition module and its tests returns **zero production callers**.
No consumer — not `chat_driver`, not `task_runtime/executor`, not
`a2a/server`, not `subagent/executor` — calls it on the envelopes
they produce. The terminal monotonicity invariant is enforced only
by `envelope_event_stream_after`'s `break`; if that `break` were
ever removed or weakened, no validator would catch the regression in
production. The validator is exercised only by its own unit tests.

## Deviations

1. **Cancelled-vs-Error collapse** (X-EVT-01-P2-01). The framework
   type contract has distinct terminals; ReactAgent collapses them;
   only GUI recovers via post-`drive_chat` polling. 3 of 4 surfaces
   render cancel as error.
2. **Synthesized terminal `source` is dropped on TUI** (sub-finding
   of P2-01). The TUI's `TuiChatSink` Error arm forwards only
   `message`, not `source`; the TUI user cannot distinguish a
   synthesized stream-end from a real agent error.
3. **`validate_event_trajectory` is dead in production** (X-EVT-01-
   P2-03). The trajectory invariants are checked only in unit tests;
   no live consumer enforces them.

## Conclusion

Scenarios 1 (duplicate) and 2 (out-of-order within a stream) are
handled correctly at every layer. Scenario 3 (Cancelled vs Error)
**fails cross-surface**: only GUI recovers, via a separate post-hoc
`TurnStatus` channel that the other three surfaces do not implement.
Scenario 4 holds at the type level but the synthesized-error
discriminator is partially dropped on TUI. Used by findings
X-EVT-01-P2-01 (Cancelled-vs-Error collapse) and X-EVT-01-P2-03
(unused trajectory validator).

Does not prove: that the GUI's post-`drive_chat` `TurnStatus`
compensation is itself race-free (it polls `cancel.is_cancelled()`
synchronously after `drive_chat` returns, so there is no race — but
the cancel token must still be the same one passed into
`drive_chat`'s `ChatResources.cancel`; this is verified in
A-CHAT-01-V01).

## Follow-Up

The cross-surface Cancelled-vs-Error collapse (P2-01) is the headline
finding. A framework-side fix for F-RCT-03-P2-02 (wrap
`cancel_aware_stream` in ReactAgent's overrides) would emit
`AgentEvent::Cancelled` natively, making every surface's Cancelled
arm live and eliminating the need for GUI's post-hoc compensation.
Until then, TUI / REPL / channels need their own post-`drive_chat`
status emission to match GUI's behavior.
