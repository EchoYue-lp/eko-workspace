## Claim

Every `AgentEvent` variant produced by the framework reaches every
declared consumer (framework event bus, EKO persistence, TUI reducer,
GUI store, CLI output, channel renderer) through a single, traceable
path, and the consumers can be enumerated in a producer-to-consumer
matrix.

### Producer-to-consumer matrix

Framework produces 20 `AgentEvent` variants. The framework
`GLOBAL_EVENT_BUS` is **not a consumer** — it has zero producers and
zero subscribers (F-CORE-01-P2-01). The actual consumer graph is
single-producer-single-consumer per stream: `envelope_event_stream`
wraps the raw stream once (`chat_driver.rs:538`,
`task_runtime/executor.rs:3743`, `a2a/server.rs:219`,
`subagent/executor.rs:1182`) and feeds exactly one `ChatSink` /
stream-draining caller. There is **no fan-out** at the framework layer.

The five live consumers of `AgentEvent` variants are:

| Consumer | File:line | Surface | Identity input |
|---|---|---|---|
| `WebhookTurnObserver` | `chat_driver.rs:106-161` | EKO persistence (webhook fan-out) | `&AgentEvent` from inside `drive_chat_inner` |
| `TauriChatSink::handle_tool_event` | `chat.rs:1193-1331` | EKO persistence (`ToolExecutionRepository`) | `&AgentEvent` via `ChatDriverEvent::Agent(envelope)` |
| `TauriChatSink::on_event` + `agent_event_to_chat_event` | `chat.rs:1341-1417, 1449-1572` | GUI emit | `ChatDriverEvent::Agent(envelope)` |

| `aggregate_by_sentence` (channels) | `channels.rs:539-626` | CLI / IM channel output | `ChatDriverEvent::Agent(envelope)` |

`ChannelChatSink` (`chat_driver.rs:575-591`) is a pure forwarder; the
real variant dispatch happens in its renderer `aggregate_by_sentence`.

## Deviations

Three conformance gaps surfaced from the matrix; full evidence is in
the corresponding task-report findings:

1. **Channel silent-drop catch-all** (`channels.rs:625`). The channel
   renderer's `_ => {}` arm swallows `ThinkStart`, `ThinkEnd`,
   `LlmUsage`, all five tool-lifecycle variants, `ToolBatchStart/End`,
   and `ContextCompressed` without any log or notice. Every other
   surface surfaces unknown variants (TUI/Tauri via `Notice`; GUI via
   the typed `Notice` bucket). This is the only consumer that can
   silently lose information about a turn's progress. See X-EVT-01-P2-02.
2. **Cancelled terminal is dead on every surface except GUI.**
   `ReactAgent` never emits `AgentEvent::Cancelled` (F-RCT-03-P2-02);
   `envelope_event_stream_after` synthesizes `Error` on stream end.
   The `Cancelled` arm of every consumer in the matrix above is
   reachable only for non-ReactAgent implementations. GUI compensates
   via post-`drive_chat` `TurnStatus{status:"cancelled"}`
   (`chat.rs:704-712`); TUI / REPL / channels do not. See X-EVT-01-P2-01.
3. **Chat-level events are not durable.** `WebhookTurnObserver`,
   `TauriChatSink`, `TuiChatSink`, and `aggregate_by_sentence` all
   consume `AgentEvent` in-flight and discard. Only the
   `ToolExecutionRepository` (GUI) and `TaskRuntimeStore`
   (Task-mode `ExecEvent::run`) persist anything; chat streaming
   history (tokens, thinking segments, budget notices) is not
   replayable. See X-EVT-01-P3-01.

## Conclusion

The matrix is complete and the producer-to-consumer graph is single
producer → `envelope_event_stream` → single sink per stream (no
fan-out, framework bus dead). Three cross-surface conformance gaps
are documented; the most material is the Cancelled-vs-Error collapse
that only GUI recovers from. Used by findings X-EVT-01-P2-01,
X-EVT-01-P2-02, X-EVT-01-P3-01.

Does not prove: that the synthesised "ended without terminal" Error
message is correctly *interpreted* by end users on each surface (that
is a UX claim, not a structural one); nor that no future variant will
be added without updating every consumer (that is the V02 exhaustiveness
claim).
