## Claim

Every `AgentEvent` variant is handled by every live consumer; no
variant is silently dropped at any surface. New variants added to the
framework enum would be detected (logged, surfaced, or compile-
rejected) at each consumer.

## Method

For each of the five live consumers identified in V01, read its
variant-dispatch site and classify it as: (a) **explicit** — every
variant named; (b) **catch-all-visible** — unmatched variants routed
to a visible sink (`Notice`, `Notice{unknown_agent_event}`, etc.);
(c) **catch-all-silent** — unmatched variants dropped with no log;
(d) **typed-via-adapter** — the consumer sees a different typed enum
and is exhaustiveness-checked on that enum, not on `AgentEvent`
directly.

Verify framework `#[non_exhaustive]` on `AgentEvent`
(`mod.rs:140`) so future variants cannot be silently ignored by
out-of-tree consumers without an explicit catch-all.

```text
read echo-agent/echo-core/src/agent/mod.rs:140-446      # enum + non_exhaustive
read echo-agent-cli/src/tui/events.rs:2031-2210         # TuiChatSink match

                                                        # TauriChatSink handle_tool_event + agent_event_to_chat_event

```

## Expected Result

All consumers fall into (a), (b), or (d). Zero (c) silent
catch-all-silent consumers. The TS side has either an exhaustive
match (compiler-enforced via `: never`) or a default branch.

### Channel silent-drop detail

The channel renderer's match at `channels.rs:545-626` has the
following arms:

- Explicitly handled: `Token`, `FinalAnswer`, `Cancelled`, `Error`,
  `BudgetDecision`, `GuardTriggered`, `MemoryRecalled` (debug log
  only, no outbound), `Chart`, `SafetyNotice`, `ParameterError`.
- Catch-all-silent: `_ => {}`. This swallows:
  - `ThinkStart`, `ThinkEnd` — a channel user gets no signal that the
    model is thinking (the `Token` events arrive anyway, but the
    `Thinking` phase boundary is invisible).
  - `LlmUsage` — silent. Acceptable for IM (no UI indicator), but
    there is no audit trail of token spend on the channel surface.
  - `ToolCall`, `ToolResult`, `ToolError`, `ToolStream`,
    `ToolBatchStart`, `ToolBatchEnd` — silent. The channel user
    sees only the final answer; intermediate tool activity is
    invisible. This is **partly intentional** (IM surfaces should not
    be flooded with tool chatter) but it also means a long-running
    turn with many tool calls produces no progress signal until the
    final answer.
  - `ContextCompressed` — silent. A channel user whose context was
    just compacted (potentially degrading answer quality) gets no
    indication. This is the most consequential silent drop: it
    hides a signal that materially affects the answer.

### TypeScript exhaustiveness gap

`chatEventHandler.ts:25-220` is a `switch (event.type)` over the
`ChatEvent` discriminated union. It has:

- 17 explicit case arms covering all 19 current `ChatEvent` variants
  (verified against `types/api.ts:125-177`; the count "17" includes
  combined arms like `tool_batch_start`/`tool_batch_end` separately).
- **No `default` case** and **no `const _exhaustive: never = event`**
  assertion at the end.

Implications:

- Today, every variant is handled (the union is small and stable).
- Tomorrow, if `ChatEvent` gains a variant (e.g. someone wires the
  `Chart` payload as a typed `chart` case instead of routing through
  `Notice`), TypeScript would NOT flag the missing case — the switch
  falls through and the event is silently dropped. The user would see
  no chart, no error, no log.
- Contrast: the Rust consumers (`TuiChatSink`, `TauriChatSink`) use
  `other =>` catch-alls that surface unknown variants. The TS switch
  has no equivalent backstop.

`grep -n "default\|never" chatEventHandler.ts` returns zero hits —
confirms no exhaustiveness guard.

## Deviations

Two structural gaps:

1. **Channel catch-all-silent** (`channels.rs:625`). The only live
   consumer that can lose `AgentEvent` information without any trace.
   See X-EVT-01-P2-02.
2. **TS chatEventHandler non-exhaustive switch**
   (`chatEventHandler.ts:25-220`). No compiler guard against future
   `ChatEvent` variant additions. See X-EVT-01-P3-02.

The Rust `#[non_exhaustive]` on `AgentEvent` (`mod.rs:140`) prevents
out-of-tree consumers from constructing every variant, but does NOT
force them to handle every variant in a `match` — the `_` arm
satisfies exhaustiveness. The framework's defense is therefore the
*convention* that consumers route `_` to a visible sink (TUI/Tauri
do; channel does not).

## Conclusion

4 of 5 consumers are robust against variant addition; 1 (channel) is
not. The TS side is exhaustive today but has no compiler-enforced
guarantee. Used by findings X-EVT-01-P2-02 (channel silent drop) and
X-EVT-01-P3-02 (TS non-exhaustive switch).

Does not prove: that the existing explicit arms are *semantically
correct* (V01 covers that); nor that a future contributor adding a
variant will remember to update each consumer (the AGENTS.md
multi-mode parity rule is the policy backstop, not a code backstop).
