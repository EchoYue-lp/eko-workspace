## Claim

The three non-happy terminal classes — LLM/stream error, cancel, and
steer mid-turn — are handled coherently by `drive_chat` / the framework:
each results in exactly one terminal reaching the sink (or, for steer,
no new terminal at all because it injects into the running turn). There
is no path that hangs, double-terminates, or silently swallows the turn
on these inputs.

## Expected Result

- LLM/stream error: stream-setup error forwards one `Error` terminal to
  the sink; mid-stream errors are normalized by `envelope_event_stream`
  into one `Error` terminal. No hang, no double-terminal.
- Cancel: the shared `CancellationToken` aborts the framework stream;
  the raw stream ends, `envelope_event_stream` synthesizes one `Error`
  terminal. The sink sees one terminal (labelled `Error`, not
  `Cancelled` — inherited from F-RCT-03-P2-02).
- Steer: `agent.steer_input` injects into the running turn's mailbox;
  `run_core_loop` drains it at iteration boundaries. No new
  `drive_chat` call, no new terminal — steer is part of the same
  lifecycle.
- App-level fixtures for the three classes: none expected to exist
  (this is what A-CHAT-01-P3-02 addresses).

## Result

- Exit code: not-applicable (static inspection)
- Duration: not-applicable
- Summary: claim confirmed at the static level. No app-level fixture
  exists for any of the three classes (A-CHAT-01-P3-02).

  Step 1 — LLM/stream error:
  - stream-setup error (`execute_stream_message_with_invocation_context`
    returns `Err`): `drive_chat_inner` emits one synthetic
    `AgentEvent::Error { source: "chat_driver", message: e }` to the
    sink (`chat_driver.rs:526-534`), emits webhook `AgentError`, returns
    `Err`. One terminal.
  - mid-stream error (raw stream yields `Err`): normalized by
    `envelope_event_stream` into `AgentEvent::Error` before reaching
    `drive_chat_inner`'s loop; the loop's own `Err(e)` arm
    (`:548-560`) is dead today (V03-01). One terminal.

  Step 2 — cancel:
  - `ChatResources.cancel: CancellationToken` (`chat_resources.rs:38`)
    is cloned into `drive_chat` (`chat_driver.rs:218`) and passed as
    the second arg to `execute_stream_message_with_invocation_context`
    (`chat_driver.rs:513`).
  - consumer triggers:
    - TUI: `app.active_cancel = Some(cancel.clone())` at
      `events.rs:1410`; `handle_esc` / `Ctrl-C` while processing calls
      `cancel.cancel()` (`events.rs:1940`, `:1149`).
    - Tauri: token stored in `session.cancel_token[message_key]`;
      `cancel_chat` removes and calls `token.cancel()`
      (`chat.rs:805-830`).
    - REPL / channels: `CancellationToken::new()` created per turn
      (`repl.rs`, `channels.rs`); no user-facing cancel wired in the

## Deviations

None in the traced behavior. The lack of an app-level fixture for the
three classes is itself the finding A-CHAT-01-P3-02 — the
one-terminal-on-cancel/error invariant is currently unguarded at the
`drive_chat` layer and relies on (a) the framework tests above and
(b) the `envelope_event_stream` contract read in V03.

## Conclusion

Supports A-CHAT-01's error/cancel/steer conclusions (task report
Current Path "One-terminal invariant" and Handoff items 2 and 3). All
three non-happy classes are handled coherently:

- **LLM/stream error** → one `Error` terminal (synthesized on setup
  failure; normalized by the envelope on mid-stream failure).
- **Cancel** → one `Error` terminal synthesized by
  `envelope_event_stream` (semantic label downgrade inherited from
  F-RCT-03-P2-02; Tauri compensates with `TurnStatus`).
- **Steer** → no new terminal; injects into the running turn via
  `agent.steer_input`, drained at iteration boundaries. Steer is part
  of the same `drive_chat` lifecycle, not a second one.

The validation does NOT prove these paths with an executable
app-level test — that gap is A-CHAT-01-P3-02. The static trace +
framework-test cross-reference is sufficient to classify the behavior
as correct-by-construction, with the caveat that an `envelope_event_stream`
regression would currently go undetected by the app suite.
