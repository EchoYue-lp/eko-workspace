## Claim

Components contributed by a plugin (skills, hooks, MCP servers, Subagents) are
registered under a per-plugin source tag (`"plugin:<id>"` for skills,
`HookSource::Plugin(<id>)` for hooks) so they can be removed as a group on
disable/uninstall. The source identity is distinct from skill and user-config
sources. Registration is reversible: each component type has a matching
unregister path.

## Expected Result

- Skills loaded via `load_plugin_skills_from_dir` carry `source =
  "plugin:<id>"` in both the catalog and progressive skill registries.
- Plugin hooks are filed under `HookSource::Plugin(<id>)`, NOT
  `HookSource::Skill("plugin:<id>")` (the comment at hooks.rs:599-603
  documents this was a prior bug).
- `components_by_plugin` in `PluginWiringResult` records exactly which
  skills/hooks/MCP-servers each plugin contributed, enabling grouped unload.
- `unload_agent_components` removes each category by its source key.
- A disabled plugin's skills cannot be activated through the progressive
  disclosure tools (tagging is mirrored to the shared registry).

## Result

- Exit code: not-applicable (static inspection)
- Summary: All expectations confirmed.
  - **Skills**: `wire_all` (`plugin.rs:262`) builds `source_tag =
    format!("plugin:{plugin_id}")` and calls
    `agent.load_plugin_skills_from_dir(dir, &source_tag, variables)`.
    Inside `discover_skills_inner` (`capabilities.rs:698`),
    `desc.source = Some(source.to_string())` is set before
    `register_descriptor_with_legacy`, then
    `tag_source_with_variables` is called on BOTH
    `self.tools.skill_registry` (catalog) AND the `shared` progressive
    registry (`capabilities.rs:720-729`). This mirrors F-SKL-01's handoff
    note that disabled plugin skills must not be reachable through the
    progressive tools.
  - **Hooks**: `wire_all` (`plugin.rs:294`) calls
    `hook_reg.register_plugin_hooks(plugin_name, source_dir, def)`.
    `register_plugin_hooks` (`hooks.rs:610`) stores under
    `HookSource::Plugin(plugin_name.to_string())` — distinct from
    `HookSource::Skill`. The comment at hooks.rs:599-603 documents the prior
    P0-2 bug where plugin hooks were misfiled under
    `HookSource::Skill("plugin:…")`.
  - **MCP**: `wire_all` (`plugin.rs:332`) calls `agent.load_mcp_config(config)`
    and records each connected server name in
    `components_by_plugin[plugin_id].mcp_servers`.
  - **Subagents**: `wire_all` reports `agent_files` to the application layer
    (`plugin.rs:380`); `register_plugin_agents` (application-owned) registers
    the definition + factory atomically. `components_by_plugin` does NOT track
    agents — the application's `PreparedApplicationComponents.agents` is the
    unload authority (see `unload_agent_components`).
  - **Unload**: `unload_agent_components` (`plugin_runtime.rs:1157`) iterates
    `framework: HashMap<String, WiredPluginComponents>` and for each plugin:
    `unregister_skills_by_source("plugin:{name}")`, `hook_registry.unregister(&HookSource::Plugin(name))`
    if `hooks_registered`, `disconnect_mcp(server)` per server. Subagents are
    unloaded from the separate `application.agents` list via
    `unregister_subagent(plugin_agent.name())`.
- Reverse-index consistency: `SkillRegistry::register_descriptor`
  (`registry.rs:95`) updates `by_source` when replacing a same-named occupant
  (removes old name from previous source set). `unregister_names_by_source`
  (`registry.rs:138`) removes the source entry then calls `remove_descriptor`
  per name, which purges `legacy_instructions`, `plugin_variables`,
  `activated`, `active_sandbox_policies`.
- `tag_source_with_variables` (`registry.rs:166`) only tags descriptors whose
  `source` is `None`, avoiding cross-plugin contamination when two plugins
  share a skill name (first-wins; second is skipped by `is_installed` in
  `discover_skills_inner`).

## Conclusion

Per-plugin source identity is correctly established and reversible for all
four live component categories (skills, hooks, MCP, Subagents). The
`components_by_plugin` map is the authoritative unload manifest and is the
same map used by the rollback path (V03). No leaked registrations are
possible through the normal disable/uninstall path. This supports the "no
leaked registrations" half of the task question for the steady-state case;
V03 covers the failure-rollback case.
