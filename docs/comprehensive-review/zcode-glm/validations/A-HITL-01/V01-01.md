## Claim

EKO routes approval requests through one canonical `HitlDispatcher`
per process, and that dispatcher arbitrates across TUI / GUI / channel
providers under a single shared 5-min deadline. Every surface either
registers its provider into the dispatcher or calls it via the agent's
installed `HumanLoopProvider`. If a surface bypasses the dispatcher,
that falsifies the "shared deadline across surfaces" half of the
A-HITL-01 question and becomes a finding.

## Method

Static reachability trace of the dispatcher + provider install graph
across all four entry points. Working directory:
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent`.

```text
1. Enumerate every HitlDispatcher construction site:
   grep -rn "HitlDispatcher::new\|HitlDispatcher{" \
       echo-agent-cli --include="*.rs" | grep -v test

2. Enumerate every register / unregister call against the dispatcher:
   grep -rn "hitl_dispatcher\.\(register\|unregister\)\|dispatcher\.\(register\|unregister\)" \
       echo-agent-cli --include="*.rs" | grep -v test

3. Enumerate every set_human_loop_provider* call (the bypass path):
   grep -rn "set_human_loop_provider\b\|set_human_loop_provider_preserving_approvals" \
       echo-agent-cli --include="*.rs" | grep -v "test\|fn set_human_loop"

4. For each entry point, follow the dispatcher from construction to
   the agent that drives the chat turn:
   - REPL/TUI: main.rs → runtime.rs:136 → dispatcher in agent.
   - Channels: channels.rs:149 → per-sender pooled agent.
   - GUI:      chat.rs:575-582 → per-conversation pooled agent.

5. Verify the dispatcher's parallel fan-out is single-provider in
   practice: cross-reference the registration calls against the
   "currently registered" set at any point in time.
   grep -n "register.*repl\|register.*tui\|unregister.*repl" \
       echo-agent-cli/src/main.rs
   grep -n "hitl_dispatcher\|register" \
       echo-agent-cli/src/tauri/desktop.rs \
       echo-agent-cli/src/cli/channels.rs | grep -v test
```

## Expected Result

- One canonical `HitlDispatcher` construction in the bootstrap path
  (`runtime.rs`), plus the empty-dispatcher fallback at
  `agent_pool.rs:966` and the post-turn reset at `chat.rs:715`.
- REPL/TUI register their provider into the dispatcher; the
  dispatcher is the live path for them.
- GUI and Channels install per-session providers directly via
  `set_human_loop_provider_preserving_approvals`, bypassing the
  dispatcher. **This falsifies the "shared deadline across surfaces"
  half of the claim.**
- No entry point registers more than one provider simultaneously, so
  the dispatcher's parallel fan-out always contains one future.

  | Channels entry | `["repl"]` (never used by channel agents) |

  At no point does the dispatcher contain more than one provider.
  The `FuturesUnordered` parallel fan-out (`dispatcher.rs:114-124`)
  therefore always races exactly one future.

## Deviations

The validation's claim ("every surface routes through the
dispatcher") is falsified by GUI (`chat.rs:579`) and Channels
(`channels.rs:149`). These are themselves the findings
(A-HITL-01-P2-01 multi-surface bypass; A-HITL-01-P3-01
single-provider dispatcher), not environmental deviations.

## Conclusion

Supports A-HITL-01's surface → provider wiring map (task report
Current Path "Verified surface → provider wiring") and Handoff item
3 ("multi-surface approval arbitration is per-session, not cross-
surface"). The REPL/TUI path uses the dispatcher with a single
shared 5-min deadline. GUI and Channels bypass the dispatcher and
install per-session providers with their own 300s timeout. The
"single shared deadline across TUI/GUI/channel" framing in the task
question is **not implemented in practice** — each surface is
isolated. This is correct for the local-assistant positioning
(AGENTS.md) but should be documented; see A-HITL-01-P2-01.

The dispatcher's parallel fan-out logic is correct as written but
operationally degenerates to single-provider pass-through; see
A-HITL-01-P3-01.
