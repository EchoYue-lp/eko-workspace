## Claim

All four EKO HITL provider paths converge on a 300-second (5-minute)
default timeout, and every path maps a timeout to fail-closed Deny
(either directly via `HumanLoopResponse::Timeout` or via
`HumanLoopResponse::Rejected`), which the framework seam
(`DynProviderHandler` / `DefaultPermissionRequestHandler`) further
maps to `PermissionDecision::Deny`. There is no surface whose
on-timeout behaviour is fail-open.

`HumanLoopRequest::timeout` field flow, and the on-timeout branch.

## Expected Result

- All four providers default to 300s (5 min) when
  `HumanLoopRequest::timeout` is `None`.
- Every provider's on-timeout branch returns either
  `HumanLoopResponse::Timeout` or `HumanLoopResponse::Rejected { .. }`.
- The framework's `DynProviderHandler` and
  `DefaultPermissionRequestHandler` map both to
  `PermissionResponse::denied` → `PermissionDecision::Deny`.
- No provider returns `HumanLoopResponse::Approved` on timeout.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not-applicable
- Summary: claim confirmed. All four paths fail-closed on timeout
  with a 300s default.

  Step 1 — per-provider timeout:

  | Provider | Code site | Default timeout | Source |
  |---|---|---|---|
  | `HitlDispatcher` | `dispatcher.rs:101` `const TIMEOUT_DURATION = Duration::from_secs(5 * 60)` | 300s | Hardcoded single shared deadline |
  | `TuiHumanLoopProvider` | `tui_provider.rs:201` `req.timeout.unwrap_or(Duration::from_secs(300))` | 300s | Per-request override or fallback |
  | `ChannelHumanLoopProvider` | `channel_provider.rs:110-112` `request.timeout.unwrap_or(Duration::from_secs(300))` | 300s | Per-request override or fallback |
  | `TauriHumanLoopHandler` | `chat.rs:350, 385, 426` `tokio::time::sleep(Duration::from_secs(300))` | 300s | Hardcoded literal in each `select!` arm (Approval / Input / Selection) |

  Convergence on 300s across all four paths. The literal value is
  duplicated four times; no shared `const` is extracted (a minor DFT
  observation, not a finding — the value is stable and small).

  Step 2 — on-timeout return value:

  | Provider | On-timeout return | Code site |
  |---|---|---|
  | `HitlDispatcher` | `Ok(HumanLoopResponse::Rejected { reason: "All HITL providers failed or timed out (...)" })` | `dispatcher.rs:158-163` (after the `while pending.next()` loop exhausts) |
  | `TuiHumanLoopProvider` | `Ok(HumanLoopResponse::Timeout)` | `tui_provider.rs:221-222` (`Err(_) =>` arm of `tokio::time::timeout`) |
  | `ChannelHumanLoopProvider` | `Ok(HumanLoopResponse::Timeout)` | `channel_provider.rs:118` (`Err(_) =>`) |
  | `TauriHumanLoopHandler` (Approval) | `Ok(HumanLoopResponse::Timeout)` | `chat.rs:351-353` (`_ = tokio::time::sleep(300s) =>`) |
  | `TauriHumanLoopHandler` (Input) | `Ok(HumanLoopResponse::Text(String::new()))` | `chat.rs:386-388` |
  | `TauriHumanLoopHandler` (Selection) | `Ok(HumanLoopResponse::Timeout)` | `chat.rs:427-429` |

  Every timeout branch returns either `Timeout` or `Rejected`. The
  Input-arm special case returns `Text("")` (empty) rather than
  `Timeout` — semantically a "no input" denial; downstream the
  framework treats empty input as a rejection. No arm returns
  `Approved` or `ApprovedWithScope`.

  Step 3 — `HumanLoopRequest` default `timeout`:

  - `HumanLoopRequest::approval(name, args)`
    (`echo-orchestration/src/human_loop/mod.rs`) constructs the

    `mod.rs:628-642`). The framework never imposes a timeout; each
    provider applies its own fallback. Confirmed consistent with

  Step 4 — framework timeout → `PermissionDecision` mapping

  - `DynProviderHandler::handle` (`service.rs:879-881`) maps

    `PermissionResponse::denied(Some("请求超时"))` →

  - `DefaultPermissionRequestHandler::handle`

  - The dead `TimeoutStrategy` knob (`service.rs:84-96`, including

  Step 5 — drop-without-respond: `ApprovalResponder::Drop` sends

None. The Tauri Input-arm returns `Text("")` instead of `Timeout`

## Conclusion

Supports A-HITL-01's timeout behaviour conclusion (task report

fail-closed, and the convergence on 300s across all four is
consistent. No finding arises from this validation.

remains dead at the application layer — no provider reads it.
