## Claim

For V04 (default-permission interactive use): the MCP, browser, and LSP
interactive surfaces do not gate on agent `permission_mode` (no
`require_full_auto` / `default` gate) — the historical lesson from
AGENTS.md holds. However, the IPC MCP command path applies a separate
allowlist + private-range URL rejection that goes beyond the AGENTS.md
"lightweight validation only" rule and effectively re-introduces
over-gating under a different name. This makes some user-configured
local MCP servers unreachable from the GUI panel while remaining
reachable from the on-disk config path.

## Expected Result

- No `permission_mode` / `require_full_auto` / `full_auto` reference in
  any of `mcp.rs`, `browser.rs`, or the LSP startup path.
- IPC `connect_mcp_server` validates input only (not permission).
- On-disk `validate_stdio_command` is a lightweight denylist
  (metacharacters + dangerous commands + traversal) — matches
  AGENTS.md.
- IPC `validate_ipc_mcp_stdio` / `validate_ipc_mcp_url` apply a
  stricter allowlist + private-range block than the on-disk path.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not-applicable
- Summary: confirmed — V04 fails on the over-gating dimension.

  **No permission_mode gate (core AGENTS.md rule holds):**
  `grep -n "permission_mode\|require_full_auto\|full_auto" mcp.rs
  browser.rs` returns zero hits in the IPC command bodies. The comment
  at `mcp.rs:217-222` explicitly documents the design:
  ```
  // MCP is a user-driven capability extension: the user explicitly
  // configures servers they trust. EKO is a local personal assistant
  // with no online / multi-user threat model, so we don't gate it
  // behind a permission mode.
  ```
  Browser commands (`browser.rs:9-22 execute(...)`) call
  `browser_runtime.execute_main(...)` directly — no permission check.
  LSP startup (`runtime.rs:499-592`) constructs `LspManager` directly —
  no permission check. TUI `/mcp` (`tui/events.rs:3425-3477`) calls
  `load_mcp_from_file` / `disconnect_mcp` directly — no permission
  check.

  **IPC over-gating — stdio allowlist** (`mcp.rs:117-160`):
  `ALLOWED_MCP_STDIO_BASES = ["npx", "node", "uvx", "uv", "python",
  "python3", "pipx", "docker", "java"]` (`:117-119`). Any command whose
  base-name is not in this list is rejected with `IpcError::Validation`
  ("not in the allowed executable list"). The doc-comment at
  `mcp.rs:110-119` explicitly invokes the online XSS-RCE threat model:
  ```
  // The frontend must not be able to spawn an arbitrary process (any
  // XSS would then be a one-hop RCE: invoke('connect_mcp_server',
  // { Stdio: { command: '/bin/sh', args: ['-c', '...'] } })).
  ```
  AGENTS.md product-positioning section: "不要套用线上 Web 服务的威胁
  模型:诸如'防 XSS→RCE''防 SSRF 内网穿透'...这类线上服务的安全闸,
  **默认不适用于 EKO**."

  Concrete impact: a user with a custom MCP server binary at
  `/usr/local/bin/my-mcp-server` cannot configure it through the GUI
  panel. The same binary in `~/.eko/mcp.json` is accepted by the
  startup loader (on-disk `validate_stdio_command` at
  `config_loader.rs:229-261` applies only a denylist + metacharacter +
  traversal guard, not an allowlist).

  **IPC over-gating — URL private-range rejection** (`mcp.rs:169-208`):
  requires `https://`, then rejects `localhost`, `127.0.0.1`, `::1`,
  `169.254.*`, `10.*`, `192.168.*`, `172.16.*`-`172.31.*`
  (`:188-200`). The doc-comment at `mcp.rs:162-168` invokes the online
  SSRF threat model:
  ```
  // ... rejects obvious private/loopback/link-local hosts to deny the
  // SSRF pivot where a compromised page forces the app to issue
  // authenticated POSTs to internal services.
  ```

  Concrete impact: a user running a local MCP server on
  `http://localhost:8100/mcp` (a very common local-dev port) cannot
  configure it through the GUI panel. The framework's own
  `config_loader.rs:24-42` documentation examples use
  `"url": "http://localhost:8080/mcp"` and `"url":
  "http://localhost:3000"` — URLs the IPC path refuses.

  **Test suite locks in the over-gating** (`mcp.rs:591-613`):
  - `test_url_requires_https`: asserts `http://example.com/mcp` is
    rejected. This part is reasonable (catching the typo case
    AGENTS.md allows).
  - `test_url_rejects_private_ranges`: asserts `https://127.0.0.1`,
    `https://localhost`, `https://169.254.169.254`, `https://10.0.0.5`,
    `https://192.168.1.1`, `https://172.16.0.1` are all rejected. This
    is the over-gating — a regression-test rewrite is part of the fix
    direction.
  - `test_url_allows_public_https`: asserts only public HTTPS URLs pass.

  **On-disk validator is correctly lightweight**
  (`config_loader.rs:213-261`): doc-comment explicitly notes "this does
  **not** whitelist executables — MCP servers are legitimately arbitrary
  interpreters (`npx`, `uvx`, `python -m …`); the real trust boundary
  is 'where did this mcp.json come from', enforced by the caller."
  This matches AGENTS.md "用户自扩展的能力由用户自己负责."

  **Asymmetry summary:**
  | Path | stdio check | URL check | AGENTS.md alignment |
  |---|---|---|---|
  | On-disk `mcp.json` (`config_loader.rs`) | denylist + metachar + traversal | none | aligned |
  | IPC `connect_mcp_server` (`mcp.rs`) | allowlist (9 binaries) + metachar + traversal | https-only + private-range block | over-gated |
  | TUI `/mcp load` (`tui/events.rs`) | delegates to framework on-disk | delegates to framework on-disk | aligned |

## Deviations

The validation confirms the claim. Two side observations:

1. The `require_full_auto` gate (the historical lesson AGENTS.md calls
   out) is genuinely gone — no permission_mode references anywhere. The
   over-gating is a *parallel* gate under a different name
   (allowlist + SSRF block), not a reintroduction of the same gate.

2. The `test_url_requires_https` test (rejecting plain `http://` for
   external hosts) is defensible under AGENTS.md's "URL 用了明文 http"
   typo-catch allowance. Only the private-range rejection and the
   executable allowlist cross the line into permission-level
   interception.

## Conclusion

Supports finding A-INT-01-P1-01: the literal `require_full_auto` gate
is removed (AGENTS.md historical lesson holds), but the IPC MCP path
re-introduces permission-level interception through an executable
allowlist + private-range URL rejection. The on-disk config path and
the TUI `/mcp` slash command remain correctly aligned with AGENTS.md.
The asymmetry makes some legitimate local MCP servers unreachable from
the GUI panel. The existing test suite (`mcp.rs:591-613`) locks the
over-gating in and would need to be updated as part of the fix.
