## Claim

EKO's worktree integration refuses to merge into a dirty main checkout.
Three independent guards protect the user's uncommitted changes, and
the preflight catches merge conflicts before any mutation reaches the
main checkout. Specifically:

1. `reject_active_git_operation` (worktree.rs:949-972) refuses
   integration if any of `MERGE_HEAD`, `CHERRY_PICK_HEAD`,
   `REVERT_HEAD`, `rebase-merge`, `rebase-apply` is present.
2. The staged-files guard (worktree.rs:706-713) refuses if the main
   checkout has ANY staged file (so the user's staged work is never
   captured by an EKO merge commit).
3. The dirty-overlap guard (worktree.rs:714-726) refuses if the main
   checkout has uncommitted changes in any path the writer declares
   ownership of.
4. The non-mutating preflight `git merge-tree --write-tree --name-only
   --messages HEAD <branch>` (worktree.rs:728-754) detects conflicts
   before the actual `git merge` runs.

The three tests `local_dirty_owned_path_blocks_integration`,
`staged_user_change_is_never_captured_by_merge_commit`, and
`conflicting_worktree_fails_without_dirtying_main_index` exercise
these guards end-to-end.

## Expected Result

## Deviations

Two nuances that do not invalidate the claim:

- **No test for `reject_active_git_operation` specifically.** The
  guard is exercised indirectly by `conflicting_worktree_fails_without_dirtying_main_index`
  (which would also fail if a stale MERGE_HEAD were left behind by a
  prior test), but no test seeds a `MERGE_HEAD` directly and asserts
  the rejection. The guard logic is simple (`path.exists()` over five
  markers), so the gap is low-risk.
- **The dirty-overlap check uses writer-declared ownership, not the
  actual changed-files list, to determine overlap.** Wait — re-reading
  worktree.rs:716-720, the overlap is `changed_files.iter().filter(|p|
  dirty.contains(p))`, where `changed_files` is the writer's actual
  staged changes (from guard #4) and `dirty` is the main checkout's
  dirty paths. So the check is "writer's actual changes ∩ main's
  dirty paths", which is correct: a writer can declare ownership of
  `a.txt` but only touch `b.txt`, and the dirty-overlap check would
  flag `b.txt` if the main has uncommitted changes there. Good — this
  is the correct, conservative check. No deviation.

## Conclusion

Supports: the "dirty-tree protection is layered and tested" invariant.
The three guards (active-operation, staged-files, dirty-overlap) run
in sequence before any mutating git operation. The user's uncommitted
changes — whether staged, unstaged, or untracked-but-not-ignored —
are preserved. A failed merge never leaves the main checkout dirty:
the preflight catches conflicts without mutation, and the actual
`git merge` failure path calls `git merge --abort` (verified by code
at worktree.rs:777-783). The failed worktree is preserved (via
`preserve_error`) for later review or retry.

Does NOT support (and is not asked to support): that the *in-worktree*
writes are atomic. The writer subagent uses the framework's
`WriteFileTool` / `EditFileTool` etc., which F-EXT-02-P1-02 found to
be non-atomic (plain `tokio::fs::write`, no temp-file-then-rename).
A crash mid-write inside the worktree can truncate a worktree file.
This corruption would then be committed by `git add -A` and propagated
by the merge. However, this is a framework-level defect owned by
F-EXT-02-P1-02, not an EKO worktree-policy issue — and its blast
radius is bounded to files the writer is actively editing when the
crash occurs, not the entire main checkout.

documented under V01, V03, V04).
