## Claim

EKO detects file-ownership conflicts at two layers (plan-time wave
narrowing + dispatch-time per-file locks), uses a single ownership
authority (`planner::FileOwnership`), and fully mitigates F-EXT-02-P1-01
(worktree path traversal) by computing worktree paths deterministically
from sanitised internal labels. The framework's broken worktree tool
surface (`enter_worktree` / `exit_worktree` / `merge_worktree`) is not
reachable from EKO's task runtime.

Concretely:

1. `select_ownership_safe_wave` (executor.rs:1127-1145) is the sole
   wave-narrowing site; `Unknown` ownership conflicts with every writer;
   `ReadOnly` never consumes ownership.
2. `file_write_locks` (executor.rs:1154, 2020-2029) is the sole
   per-file mutex table; locks are acquired in sorted order to prevent
   deadlock.
3. `integrate_fork_worktree` (worktree.rs:569) is the sole merge
   authority; `EkoRuntimeDagController::resolve_dispatch`
   (executor.rs:1522) is the sole caller.
4. The worktree path is always computed by `default_worktree_path`
   (worktree.rs:218) from a `safe_branch_id`-sanitised label
   (worktree.rs:61-89) and verified by `validate_worktree_target`
   (worktree.rs:245-267).
5. `enter_worktree` / `exit_worktree` are listed in
   `UNATTENDED_DIRECT_MUTATION_TOOLS` (executor.rs:247-248) precisely so
   they can be disabled in unattended-Fork mode; no call site in
   `echo-agent-cli` reaches the framework's `merge_worktree`.

- `select_ownership_safe_wave` (executor.rs:1127-1145):
  - ReadOnly tasks are always included.
  - Known/Unknown writers are included iff `selected_writers.iter().all(|s| !ownership.conflicts_with(s))`.

    chosen subset depends on the order of `ready`. This is a
    determinism caveat (see Deviations), not a safety defect.

    `sorted_files.is_empty()` → no per-file lock acquired. This is
    correct: Unknown writers are kept out of mixed waves by
    `select_ownership_safe_wave`, and within their own wave they run

## Deviations

Two nuances are noted but do not invalidate the claim:

- **Wave-selection order-dependence.** `select_ownership_safe_wave`
  iterates `ready` in the order supplied by the framework kernel. If
  the kernel's order is non-deterministic across runs, the chosen
  subset may differ. The *safety* property (no two conflicting writers
  in the same wave) is preserved either way; only the *which*
  conflicting writer goes first may vary. This is filed as an
  observation, not a finding — the framework kernel's
  `ready_task_ids` is itself deterministic (sorted by task id in the
  current implementation), and any non-determinism would be a framework
  concern.
- **`Unknown` writers acquire no per-file lock.** This is correct
  (they are isolated in their own worktree), but it means the
  per-file lock table is empty for tasks with `files = []` or with
  glob/parent-traversal scopes. The plan-time wave narrowing ensures
  `Unknown` writers never run with other writers in the same wave, so
  the lock absence is not a hazard.

## Conclusion

Supports: the "single ownership authority + mitigated path traversal +
unreachable framework worktree tools" invariants. EKO's writer
isolation has exactly one of each authority
(`FileOwnership`, `select_ownership_safe_wave`, `file_write_locks`,
`integrate_fork_worktree`, `repo_merge_lock`, `EkoWorktreeFactory`).
The path-traversal attack vector from F-EXT-02-P1-01 is closed at three
layers (`safe_branch_id` normalisation, `default_worktree_path`
sanitisation, `validate_worktree_target` canonicalisation). The
framework's broken worktree surface is not registered as an active
tool in EKO's task runtime.

Does NOT support (and is not asked to support): that the framework
tools themselves are correct — they are not (F-EXT-02 findings stand
for any other consumer). This validation only establishes that EKO
does not reach them.
