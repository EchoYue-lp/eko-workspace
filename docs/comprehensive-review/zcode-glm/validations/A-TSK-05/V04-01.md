## Claim

EKO's worktree-merge site handles merge conflicts, merge failures, and
cancellation deterministically. Specifically:

1. The non-mutating preflight `git merge-tree --write-tree --name-only
   --messages HEAD <branch>` (worktree.rs:728-754) catches conflicts
   BEFORE the actual `git merge` runs. Exit code 1 means "conflict
   detected, no tree written"; the main checkout is left untouched.
2. If the actual `git merge --no-ff --no-edit -m ... <branch>` fails
   (worktree.rs:757-784), `git merge --abort` is invoked before the
   error is returned, restoring the main checkout to its pre-merge
   state.
3. The failed worktree is preserved: the `preserve_error` helper
   (worktree.rs:630-636) unlocks the worktree and embeds its path and
   branch in the error message.
4. Cancellation BEFORE the merge starts is checked twice (select on
   `merge_lock.lock_owned()` + explicit `cancel.is_cancelled()` at
   executor.rs:926-933). The integration aborts cleanly with no side
   effects.
5. Cancellation DURING the merge runs to completion: `spawn_blocking`
   is uninterruptible (executor.rs:961-971). This is correct — a
   half-finished `git merge` would leave `MERGE_HEAD` set and conflict
   markers in working files, breaking the main checkout for every
   other worker.
6. Repeated integration of the same execution id is idempotent:
   `find_integration_commit(trailer)` (worktree.rs:928-947) detects
   the prior merge commit and short-circuits to `AlreadyIntegrated`.

  Every error path inside `integrate_existing_worktree` calls

- Preflight evidence (worktree.rs:728-754): the call is
  `git merge-tree --write-tree --name-only --messages HEAD <branch>`.
  `merge-tree --write-tree` (git >= 2.38) writes a tree object but
  does NOT touch the working tree, index, or HEAD. Exit 0 = clean
  merge possible; exit 1 = conflict; the conflict markers and messages
  are printed to stdout (captured in `preflight.stdout`). On exit 1,
  the function returns `Err("worktree merge conflict: <diagnostic>")`
  via `preserve_error`. The main checkout is untouched.
- Actual merge + abort evidence (worktree.rs:756-784):
  ```rust
  let merge = git_output(repo_root, &[
      "-c", "commit.gpgsign=false",
      "-c", "user.name=EKO TaskRuntime",
      "-c", "user.email=eko@local",
      "merge", "--no-ff", "--no-edit", "-m", &message, &branch,
  ])?;
  if !merge.status.success() {
      let diagnostic = bounded_output(&merge, 4_000);
      let abort_error = abort_own_merge(repo_root).err();

  }
  ```
  `abort_own_merge` (worktree.rs:974-987) checks `MERGE_HEAD` and
  runs `git merge --abort` only if it exists. If the abort itself
  fails, the suffix is appended to the error (so the user knows the
  repo may still be in MERGE state). This is the correct
  defense-in-depth: a clean abort is preferred, but a failed abort is
  surfaced rather than hidden.

## Deviations

One nuance filed as a finding (P3-02) rather than a deviation from
this validation's claim:

- No executor-level test exercises cancellation arriving during the
  `spawn_blocking { integrate_fork_worktree }` window. The design is
  correct (the merge runs to completion because `spawn_blocking` is
  uninterruptible; the result is applied via the post-spawn outcome
  match), but the property is enforced only by code inspection, not
  by a regression test. See A-TSK-05-P3-02.

A second observation that is NOT a deviation:

- If cancel arrives AFTER the merge completes but BEFORE
  `set_claimed_status(Completed)` runs (executor.rs:1535-1543), the
  task is marked Completed (the CAS writes through because the task
  is still Running with the right claim). `finalize_cancelled_run_state`
  (executor.rs:643-661) only touches `Pending | Running | Blocked`
  tasks, so a Completed task that the run later cancels keeps its
  Completed status — and its merge commit stays in the main checkout.
  This is the correct outcome: the work was already merged; reverting
  it would require a separate `git revert`, which is outside
  `finalize_cancelled_run_state`'s responsibility. No data loss, no
  inconsistency between the task status and the checkout state.

## Conclusion

Supports: the "merge failure / cancellation is deterministic"
invariant. Merge conflicts are caught by a non-mutating preflight;
failed merges trigger `git merge --abort`; the main checkout is never
left dirty by a failed integration. Cancellation before the merge
aborts cleanly; cancellation during the merge runs to completion (the
correct design for a non-cancel-safe mutation). Repeated integration
is idempotent via the `EKO-Execution-Id:` trailer lookup.

Does NOT support (and is not asked to support): that the
`spawn_blocking` cancellation-during-merge behaviour is regression
-tested. It is not (A-TSK-05-P3-02). The design is sound; the gap is
in test coverage, not correctness.

Also does NOT support: that the framework's `merge_worktree`
(F-EXT-02-P2-04) has been fixed. It has not. EKO routes around it by
using its own `integrate_fork_worktree`. The framework tool remains
broken for any other consumer.

Findings using this validation: A-TSK-05-P3-02 (mid-merge cancel test
gap).
