## Claim

`ToolFailureCategory`'s 7 variants map exhaustively to
`ToolRecoveryAction`'s 5 actions, with `PartialSideEffect -> VerifyThenRetry`
as the key safety pattern for tools that may have committed a side effect
before failing. No category lacks a defined recovery mapping.

## Method

Read the three enums and the default recovery mapping in `mod.rs`. Enumerate
each category variant and confirm its mapped action.

```text
Read echo-agent/echo-core/src/tools/mod.rs lines 1-130
(enum definitions + ToolFailure struct + default mapping)
```

## Expected Result

A deterministic, exhaustive mapping from every `ToolFailureCategory` variant
to a `ToolRecoveryAction`, with the partial-side-effect case routed to a
verification gate rather than blind retry.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - `ToolFailureCategory` (`mod.rs:20`): 7 variants — `InvalidArguments`,
    `Unavailable`, `Timeout`, `Cancelled`, `Transient`, `Permanent`,
    `PartialSideEffect`.
  - `ToolRecoveryAction` (`mod.rs:47`): 5 variants — `CorrectArguments`,
    `Retry`, `RestoreThenRetry`, `VerifyThenRetry`, `Stop`.
  - `ToolSideEffect` (`mod.rs:70`): `None`, `Possible`, `Confirmed`.
  - **Default mapping** (used by `ToolFailure` construction / `ToolFailure::new`):
    | Category | Recovery |
    |---|---|
    | `InvalidArguments` | `CorrectArguments` |
    | `Unavailable` | `RestoreThenRetry` |
    | `Timeout` | `VerifyThenRetry` |
    | `PartialSideEffect` | `VerifyThenRetry` |
    | `Transient` | `Retry` |
    | `Cancelled` | `Stop` |
    | `Permanent` | `Stop` |
  - All 7 categories are covered; no variant falls through to a default/
    catch-all arm.
  - **Safety pattern.** `PartialSideEffect -> VerifyThenRetry` is the
    critical case: when a tool may have committed a side effect (file write,
    shell mutation) before failing, the framework does not blind-retry
    (which would double-apply the effect); it routes through verification
    first. `Timeout` is mapped the same way because a timeout may leave a
    side effect in an unknown state.
  - `idempotency_key` (`ToolFailure` field) cooperates with retry actions:
    a tool that provides an idempotency key can be retried safely even after
    a partial side effect, because the key deduplicates the effect on the
    target system.
- Log/artifact: none

## Deviations

The default category-to-recovery mapping is hardcoded in a single `match` in
`mod.rs`. It is not configurable per-tool — a tool whose semantics warrant a
different mapping (e.g. a tool that is always safe to blind-retry despite
`PartialSideEffect` because it carries an idempotency key) cannot override
the default without constructing `ToolFailure` with an explicit `recovery`
field. This is a flexibility observation, recorded as task finding
F-EXT-01-P3-02, not a validation failure: the mapping is exhaustive and
deterministic.

## Conclusion

The error classification is exhaustive and safety-oriented. Every category
has a defined recovery; the partial-side-effect and timeout cases correctly
route through verification rather than blind retry. This satisfies the
"complete error classification" portion of the task question. Supports task
finding F-EXT-01-P3-02 (mapping is hardcoded, not per-tool configurable).
