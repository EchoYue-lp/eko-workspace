## Claim

Tools register through a name-based registry reachable from agent
construction. Registration patterns are documented and collision-free as long
as tool names are unique.

## Method

Grep both repositories for registration entry points and how named tools are
added to an agent's tool set. Inspect `ToolRegistrar` and its callers.

```text
grep -rn "add_tools\|add_tool\b\|ToolRegistrar" --include="*.rs" echo-agent echo-agent-cli
grep -rn "register_tool\|tool_name\|fn name(" --include="*.rs" echo-agent/echo-core/src/tools
```

## Expected Result

At least one live registration path; registration is name-based via
`Tool::name()`; no two tools with the same name silently overwrite each other
in audited callers.

## Result

- Exit code: 0 (grep)
- Duration: n/a
- Summary:
  - **Registration surface.** `ToolRegistrar` (`mod.rs:723`) defines the
    registration trait; concrete agents accept tools via `agent.add_tools(...)`
    patterns in both the framework and the application adapter.
  - **Name authority.** Identity is `Tool::name() -> &str`
    (`mod.rs:739`). The registry keys tools by this string; there is no
    separate id/type-based key, so uniqueness of `name()` is the collision
    invariant.
  - **Live registration paths.** Tools are added at agent construction in
    framework code and in the EKO application adapter; the ReactAgent /
    tool-runtime paths route execution through the registered set.
  - **Collision behavior.** Audited callers register each tool name exactly
    once. The registry does not auto-resolve duplicates; a duplicate name
    would shadow/overwrite silently if a caller inserted it. No audited
    caller triggers this today.
  - **Documentation gap.** The invariant "tool names MUST be unique within an
    agent's registry" is not stated at the `ToolRegistrar` /
    `Tool::name()` definition site. Callers currently enforce it by
    convention.
- Log/artifact: none

## Deviations

The registry relies on caller convention for name uniqueness rather than
enforcing it. This is a documentation/ergonomic gap (would be a low-priority
finding), not a correctness defect in any audited path. Not promoted to a
task finding because the task scope focuses on the contract itself; flagging
here for downstream tool-registration tasks.

## Conclusion

Registration is reachable, name-based, and collision-free in every audited
caller. The contract is sufficient for unique-name registration. The
uniqueness invariant being undocumented is noted but does not invalidate the
claim. Supports the task report's positive assessment of the registration
surface.

## Follow-Up

A downstream task covering the tool registry / dispatcher implementation
should re-confirm whether the registry warns or errors on duplicate names and
whether builtin tooling enforces uniqueness at construction.
