## Claim

`spawn_config_watcher` hot-reloads only user hooks, the `ConfigChange`
lifecycle hook, and webhook endpoints. Model selection, MCP topology, runtime
limits, providers, and the central `AppState.app_config` are **not** reloaded —
the freshly loaded `new_config` is consumed only by the webhook emitter and then
discarded; those domains require a restart.

## Method

Static read of the watcher spawn path, the debounce loop, the reload handler,
and the call sites that start it.

```text
read echo-agent-cli/echo-agent-app-core/src/config_watcher.rs:1-278 (full module)
grep spawn_config_watcher echo-agent-cli/src/main.rs:231-233
grep spawn_config_watcher echo-agent-cli/src/tauri/desktop.rs:165-167
read echo-agent-cli/echo-agent-app-core/src/state.rs:339 (AppState.app_config: RwLock<AppConfig>)
```

## Expected Result

A precise partition of which domains are live-reloadable versus
restart-required, with evidence that the reload handler does not mutate state it
claims to skip.

## Result

- Exit code: not-applicable
- Summary: Watch targets (`config_watch_targets`, `config_watcher.rs:199-211`):
  the resolved loaded config file, `~/.eko/hooks.yaml`, and
  `<cwd>/.eko/hooks.yaml`. The debounce loop (`:137-154`) collapses a burst into
  one reload via a resettable 500 ms quiet window (robust against atomic-save
  rename, per module docs `:13-26`).

  `handle_config_change` (`:227-278`) performs exactly three actions on settle:
  1. Fires `HookEvent::ConfigChange` with the changed path as matcher context
     (`:236-247`).
  2. Reloads merged user hooks via `HookConfigLoader::load_merged_from_disk_at`;
     on success swaps `agent.hook_registry()` (clear + register); on parse error
     it logs a warning and **keeps the last-known-good hooks** (`:258-274`).
  3. Calls `webhook_emitter.reload_from_config(&new_config)` (`:275-277`).

  `new_config` (`:254-257`) is built by re-running `echo_agent::config::load_config`
  but is consumed by **only** the webhook emitter. It is never written back to
  `AppState.app_config` (the `RwLock<AppConfig>` at `state.rs:339`), never
  propagated to the agent's `LlmConfig`, never to MCP, never to runtime limits.
  The handler does not even receive an `AppState` handle — only `AgentHandle`
  and an optional `WebhookEmitter`.

  Therefore the restart-required set (confirmed by absence of any write path):
  - `model` / `model_providers` / provider auth / base_url (wired once at
    `infra.rs:307-320`).
  - `mcp.*` topology (loaded once in `bootstrap` via `infra::load_mcp_config`,
    `runtime.rs:110`).
  - `agent.token_limit` / `system_prompt` (baked into the prompt assembler at
    `infra.rs:215-225`).
  - `sandbox.*`, `web.*`, channel credentials.

## Deviations

None. The module-level doc (`config_watcher.rs:1-11`) explicitly states the
intentional scope ("Hooks and webhook endpoints are reloaded live. Other config
domains ... require a restart") — observed behavior matches the documented
intent. The defect is not a divergence from intent, it is that the intent leaves
`AppState.app_config` permanently stale relative to disk after the first edit
(see finding A-CFG-01-P2-03).

## Conclusion

Hot-reload scope is exactly {user hooks, ConfigChange hook, webhook endpoints}.
Everything else requires restart, and the watcher does not even refresh the
in-memory `app_config` snapshot that IPC handlers read. This validates the
restart-required side of the task question and feeds finding A-CFG-01-P2-03
(stale app_config) and A-CFG-01-P3-01 (reload scope is undocumented at the IPC
layer — clients cannot tell which edits took effect).
