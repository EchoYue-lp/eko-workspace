## Claim

Invalid or partial config is handled by **silent fallback**: an unparseable
explicit file falls back to `AppConfig::default()` with only an `error!` log; an
unparseable search-path file is skipped to the next path with a `warn!`. A
missing provider API key produces no startup error — the agent is built without
an `LlmConfig` and fails later at the first LLM call. There is no fast-fail
validation gate at bootstrap.

## Method

Static read of the loader error paths, the auth resolution path, and the agent
build site that consumes the resolved auth token.

```text
read echo-agent/src/config.rs:681-757  (load_config_file + load_config error handling)
read echo-agent-cli/echo-agent-app-core/src/model_config.rs:278-293 (auth_token resolution)
read echo-agent-cli/echo-agent-app-core/src/infra.rs:303-320 (LlmConfig injection, skip when None)
read echo-agent/src/config.rs:687-722  (save_config 0600 permission mitigation)
grep -rn "bail!\|return Err" echo-agent-cli/echo-agent-app-core/src/infra.rs (validation gates)
```

## Expected Result

Either a fast-fail gate (startup refuses to bootstrap without a usable model
config) or a clearly documented deferred-fail policy with a user-facing message.

## Result

- Exit code: not-applicable
- Summary:

  **Invalid YAML, explicit `--config`** (`config.rs:726-738`): on parse failure
  logs `error!("Failed to load config ...")` then `info!("Using default
  config")` and **returns `AppConfig::default()`**. The process continues
  bootstrapping with an empty config. The user's explicit config file is
  silently ignored.

  **Invalid YAML, search path** (`config.rs:741-753`): on parse failure logs
  `warn!("Failed to load config ...")` and **falls through to the next path**,
  ultimately to `AppConfig::default()` if all fail. Two failure modes are
  conflated: "file not present" (normal) and "file present but corrupt"
  (operator error). A corrupt `./echo-agent.yaml` silently downgrades to
  `~/.eko/config.yaml` or to defaults with no surfaced error.

  **Missing API key** (`model_config.rs:287-293`): `resolve_runtime_model`
  returns `auth_token = None, auth_source = "none"`. At the agent build site
  (`infra.rs:307-320`) the entire LlmConfig-injection block is gated on
  `if let Some(auth_token) = ...`, so with `None` the block is skipped and the
  builder receives no `LlmConfig`. The inline comment (`infra.rs:304-305`)
  acknowledges the fallback: "the agent falls back to env vars +
  echo-agent-models.yaml, which may not exist (especially in GUI apps where
  shell env vars aren't inherited)." There is **no `bail!`/`return Err`** in
  `create_agent_with_diagnostics` for the no-auth case — bootstrap succeeds and
  the failure surfaces as an opaque provider HTTP 401 / "no model configured"
  error on the user's first message.

  **Partial config / unknown provider** (`infra.rs:2005-2025`,
  `build_llm_config`): an unknown provider string falls through to the
  `LlmConfig::new(url, auth_token, model)` catch-all arm — no validation that
  the provider is recognized.

  **Positive finding** (`config.rs:708-720`): `save_config` explicitly documents
  the plaintext-secret risk and restricts the file to `0600` on Unix — the
  correct local-app mitigation, consistent with AGENTS.md's threat model.

## Deviations

The 0600 mitigation in `save_config` only covers files written by `save_config`
itself (Web API / CLI self-edit). A user-authored `~/.eko/echo-agent.yaml` (or
the loader's `config.yaml`) is not normalized to 0600 on read; its permissions
are whatever the user/editor left. Minor, given the local-single-user threat
model in AGENTS.md.

## Conclusion

The error-handling posture is uniformly **silent fallback to defaults**, never
fast-fail. For corrupt YAML this masks operator error; for a missing API key it
defers the failure to the first LLM call with a much worse user experience
(especially in GUI where env vars are absent). This is the load-bearing
evidence for finding A-CFG-01-P1-02 (missing API key should fail fast at
bootstrap) and A-CFG-01-P2-05 (corrupt explicit config file should not silently
downgrade to defaults).
