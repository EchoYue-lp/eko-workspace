the atomic-write primitive has one canonical implementation; the framework

All six implement the same primitive (unique tmp → `File::create` →
`write_all` → `sync_all` → `rename`, with tmp cleanup on failure). They
differ only in tmp-naming scheme, error type, and — critically — whether
the parent directory is fsynced after rename. **Only 1 of 6** (the
framework's own `src/state/file.rs`) calls `sync_parent_directory`. This
is the concrete mechanism behind the A-STATE-01 recurring "missing
parent-dir fsync" concern: it is a duplicate-authority problem (no
canonical helper) expressed as a durability defect.

## Deviations

The framework `src/state/file.rs:210` atomic_write is the ONLY site that
fsyncs the parent directory. All other sites (including the framework's own
`echo-state/src/memory/file_conversation.rs:494`) omit it. The durability
gap is therefore not merely a CLI issue — the framework itself is
inconsistent across its two copies.

## Conclusion

Three behaviors are duplicated or dead:

1. **`atomic_write` is implemented 6 times with drifting durability
   semantics.** This is a P2 duplicate-authority finding (X-BND-01-P2-01)
   and the root mechanism behind A-STATE-01's parent-dir fsync concern.
2. **The framework `TaskSubagent` contract path is dead.** The production
   path is `RuntimeDagController`. The CLI's adapter converters to the
   `TaskSubagent` return types are test-only. This is a P2 framework
   deletion candidate (X-BND-01-P2-02) and a V03/V04 concern.
3. **The CLI task-runtime worktree reimplements the git-invocation
   primitive** rather than reusing `echo_tools::git_worktree`. P3
   (X-BND-01-P3-02).

The workflow-execution path is correctly single-authority (framework
engine) — no finding. Supports X-BND-01-P2-01, P2-02, P3-02.
