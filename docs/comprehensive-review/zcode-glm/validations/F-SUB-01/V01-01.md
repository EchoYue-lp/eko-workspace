## Claim

Every `SubagentDefinition` field has a runtime effect (is read by some
production dispatch/registration path), every definition is registered through
one canonical registry, and no parallel identity/catalog authority exists.
Terminology is Subagent-only (no Worker).

## Method

Read-only static inspection. Enumerated all 22 fields declared on
`SubagentDefinition` (`echo-agent/src/agent/subagent/types.rs:130-197`) and
traced each one to its read site. Searched both repositories for each field
name and for the parallel concepts (`compile_system`, `tool_filter`,
`lightweight`, `SubagentKind::Custom`, `ContextBuilder`, `SubagentOutput`).

## Expected Result

(1) All `SubagentDefinition` fields are read somewhere on the dispatch path.
(2) One registry (`SubagentRegistry`) owns identity; the dispatch catalog is a
    projection, not a second authority.
(3) No `Worker` terminology in the subagent module.

## Result

- Exit code: not-applicable (static inspection)
- Summary: fields partition into three categories — live, partially-live, dead.

### Category A — fields read on the dispatch path (live)

`name` (registry lookup, catalog key, event payload), `description` (catalog
text + LLM schema), `execution_mode` (executor mode selection,
executor.rs:449-453), `model` (used by factory authors building the agent; not
read by the executor itself — passed through the factory closure),
`max_iterations` (applied inside the built agent, not by the executor),
`token_limit` (same), `timeout_secs` (executor.rs:1475-1478),
`inherit_history` (executor.rs:1481-1485 → `compile_invocation` →
`filter_history`), `inherit_memory` (via `ContextInheritance::fork_default`,
context.rs:74-81, applied by `ParentContextFactory`), `can_delegate`
(catalog/constraint surface; nested depth guarded separately by
`NestedDelegationPolicy`), `tags` (registry `list_by_tag`), `isolate_worktree`
(agent_dispatch.rs:248 forces Fork + executor worktree path),
`isolate_workspace` (same, executor.rs workspace path), `team` (executor
`dispatch_team`), `is_background` (agent_dispatch.rs:251 → background
dispatch), `kind` (metadata only — see Category C).

### Category B — declared, settable, but NEVER read by production (dead)

- **`tool_filter`** (`types.rs:144`). Settable via `SubagentBuilder::tools`
  (`builder.rs:126`). Grepped across both repos: zero production read sites.
  Tool restriction at dispatch actually uses `SubagentContext.allowed_tools`
  (executor.rs:1672-1676, Fork only) and `ContextInheritance.inherit_tools`
  (context.rs:236-252) — two *separate* mechanisms. See F-SUB-01-P2-01.
- **`lightweight`** (`types.rs:164`). Doc promises "shares the parent's LLM
  client, ToolManager, and GuardManager." No `SubagentBuilder` setter exists;
  no production read site. See F-SUB-01-P2-04.
- **`system_prompt`** (`types.rs:142`). Stored and carried to
  `compile_system`'s `role_prompt` input (prompt.rs:51), but
  `compile_system` itself has zero production callers (see V03-01). The
  subagent's actual system prompt is whatever the pre-built agent instance
  carries. The field is metadata that the framework compiler path ignores.

### Category C — variant/field with incomplete implementation

- **`SubagentKind::Custom { path }`** (`types.rs:86-89`). Doc says "Loaded
  from a `.md` definition file (similar to skills)." Settable via
  `.custom(path)` (`builder.rs:73-76`). No loader opens or parses the file.
  See F-SUB-01-P3-01.

### Registry authority — single, with a projection

- One registry: `SubagentRegistry` (`registry.rs:72-85`) owns
  `agents` / `definitions` / `factories` maps. All registration entry points
  (`register`, `register_sync`, `register_factory`, `register_factory_sync`,
  `register_definition`, `register_definition_sync`) write to the same
  `definitions` map keyed by name. Name collisions are last-write-wins
  (`HashMap::insert`).
- The dispatch catalog (`AgentDispatchTool.catalog`,
  `agent_dispatch.rs:75`) is a `Vec<SubagentCatalogEntry { name, description }`
  — a projection of the registry's definitions, NOT a second authority. It is
  refreshed by `update_dispatch_catalog` (`capabilities.rs:377-401`) on every
  register/unregister call that goes through `ReactAgent`. The catalog is
  mutable post-build (updated at registration time), not immutable; this is
  intentional so plugin/runtime-discovered subagents appear in the schema.
- **Projection gap**: `SubagentRegistry::register_definition` /
  `from_subagent_map` (registry.rs:204-225, 115-134) write to the registry
  directly and do NOT touch any `AgentDispatchTool` catalog (the registry has
  no catalog reference). Consumers using a shared registry across multiple
  agents must call `sync_subagent_dispatch_catalog`
  (`capabilities.rs:434-438`) per-agent or the LLM schema will be stale. This
  is documented in the method docstring.
- **Terminology**: grep for `Worker`/`worker_` in
  `echo-agent/src/agent/subagent/` returned zero hits. Module is
  Subagent-only. (A separate `executor.rs` concurrency concept uses
  "subagent" naming throughout — semaphore permits are acquired for subagent
  dispatch, not "worker slots.")

- Log/artifact: none.

## Deviations

Three observations that do not invalidate the "single registry" claim but
narrow it:

1. The catalog is a *per-agent* projection, not a registry-level projection.
   When a shared `SubagentRegistry` is reused across agents (the
   `new_with_subagent_registry` path, `mod.rs:314-320`), only the registering
   agent's catalog updates. This is the documented behavior but creates a
   stale-schema risk for multi-agent shared-registry deployments.
2. `register_factory_sync` (`registry.rs:247-272`) can partially fail:
   definitions written, then factories write fails → returns `false` with the
   definition already inserted. The capabilities-layer caller
   (`capabilities.rs:366-373`) skips the catalog update on `false`, so the
   definition exists in the registry but not in the catalog.
3. `model`, `max_iterations`, `token_limit` are not read by the executor —
   they are consumed by whoever builds the agent instance (factory closure or
   direct construction). This is by design (the definition describes, the
   factory builds), but it means a definition registered via
   `register_definition` (no instance) carries fields the framework never
   enforces until an instance is supplied.

## Conclusion

The claim is **partially supported**. One canonical registry exists, no Worker
terminology leaks, and the catalog is a projection rather than a second
authority. However, **three definition fields are dead**
(`tool_filter`, `lightweight`, and effectively `system_prompt` on the compiler
path) and one variant (`SubagentKind::Custom`) has no loader. These feed
findings F-SUB-01-P2-01, F-SUB-01-P2-02, F-SUB-01-P2-04, and F-SUB-01-P3-01.
