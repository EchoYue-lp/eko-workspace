## Claim

The `agent_tool` dispatch entry selects the target subagent by name from a
catalog snapshot that is consistent with the registry, and the schema exposes
only currently-registered names to the LLM. The catalog is not a second
identity authority — it is a projection updated on every register/unregister.

## Method

Read-only static inspection of the dispatch tool's parameter generation and
catalog update path, plus a targeted test run to confirm the schema reflects
registrations at runtime.

## Expected Result

(1) `parameters()` reads the catalog under its `RwLock` and emits an `enum`
    of names when non-empty, so the LLM cannot invent a name.
(2) Registering a subagent through `ReactAgent` updates the catalog before
    the next tool-definition read.
(3) Dispatch resolves the name through the registry (`executor.registry().get`),
    not through the catalog — so a stale catalog cannot cause a wrong-agent
    dispatch, only an LLM-visible schema lag.

## Result

- Exit code: 0 (executable tests)
- Duration: ~0.05s
- Summary:

### How the LLM sees the catalog

`AgentDispatchTool::parameters` (`agent_dispatch.rs:388-443`) reads
`self.catalog` (an `Arc<std::sync::RwLock<Vec<SubagentCatalogEntry>>>`) under
a read lock, clones the entries, and builds the JSON schema:

- Empty catalog → `agent_name` is a free-form `string` with description
  "No SubAgents are currently registered."
- Non-empty catalog → `agent_name` is a `string` with an `enum` array of
  names, plus a human-readable "Available SubAgents: name: desc; ..." line.

Each catalog entry carries only `name` and `description`
(`agent_dispatch.rs:78-83`). Other definition fields (tools, model, mode) are
NOT exposed in the schema — the LLM picks by name+description only, matching
the Claude Code single-tool pattern.

### How dispatch resolves the target

`dispatch_with_context` (`agent_dispatch.rs:196-264`) extracts `agent_name`
from parameters, then at `:246` calls `executor.registry().get(agent_name)`
to read the definition (for `isolate_worktree`/`isolate_workspace`/
`is_background` checks). The actual agent instance comes from
`SubagentExecutor::isolated_dispatch_agent` (`executor.rs:1455-1466`) which
calls `registry.create_fresh_agent` / `registry.get_agent`. **The catalog is
never consulted at dispatch time** — only the registry. So even if the
catalog is stale, dispatch resolves correctly; the worst case is the LLM
seeing an outdated `enum`.

### How the catalog stays in sync

`ReactAgent::register_subagent_with_definition` /
`register_subagent_definition` / `register_subagent_factory`
(`capabilities.rs:305-374`) each call `update_dispatch_catalog(&def)`
(`capabilities.rs:377-401`) after a successful registry write.
`update_dispatch_catalog` acquires a write lock on the catalog handle,
upserts the entry by name (update description if name exists, else push),
sorts the vec by name, then calls
`self.tools.tool_manager.invalidate_definition_cache()`
(`echo-execution/src/tools.rs:480`) so the next `get_tool_definitions` call
rebuilds the cached schema with the new enum. `unregister_subagent`
(`capabilities.rs:406-424`) retains only entries whose name differs and
invalidates the cache the same way.

### Cache invalidation mechanism

`ToolManager::cached_definitions` (`echo-execution/src/tools.rs:65`) is a
`RwLock<Option<(u64, Vec<ToolDefinition>)>>` keyed by a version counter.
`invalidate_definition_cache` (`:480-499`) bumps the version, forcing the
next `get_tool_definitions` (`:577`) to rebuild. This makes the schema
enum update visible to the LLM on the next tool-list call without restarting
the agent.

## Deviations

Two consistency gaps that do not break dispatch correctness but can produce
a stale LLM-visible schema:

1. **Per-agent catalog, shared registry.** The catalog handle is captured
   per-`AgentDispatchTool` instance at construction (`mod.rs:486-495`). When
   `new_with_subagent_registry` shares one registry across N agents
   (`mod.rs:314-320`), only the agent whose `register_subagent_*` was called
   updates its own catalog. The other N-1 agents keep stale enums until
   `sync_subagent_dispatch_catalog(definitions)` (`capabilities.rs:434-438`)
   is called on each. This is documented but easy to miss.
2. **Direct registry writes bypass the catalog.** Code that calls
   `SubagentRegistry::register_definition` / `register_factory` directly
   (e.g. plugin integrators that collect into the registry first) does not
   update any `AgentDispatchTool` catalog. The registry has no back-reference
   to the tool. The capabilities-layer `register_subagent_definition` exists
   precisely to bridge this, but nothing forces integrators to use it.
3. **`register_factory_sync` partial-failure.** As noted in V01-01: if
   `definitions` writes but `factories` write fails
   (`registry.rs:253-272`), the function returns `false`, the caller
   (`capabilities.rs:366-373`) skips `update_dispatch_catalog`, and the
   definition exists in the registry but is absent from the catalog — the
   LLM cannot name it even though dispatch would succeed if it could.

## Conclusion

The claim is **supported**. The catalog is a projection (name+description
only), the schema enum is regenerated through cache invalidation, and
dispatch resolves through the registry rather than the catalog — so catalog
staleness degrades LLM ergonomics, never correctness. The three deviation
scenarios are documented or edge-case paths; they do not constitute a second
identity authority.
