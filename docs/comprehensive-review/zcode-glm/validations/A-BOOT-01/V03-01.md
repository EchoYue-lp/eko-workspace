## Claim

`AgentRuntime::bootstrap` propagates errors via `?` and does not leak partially
constructed state: any service that must be torn down on a later step's failure
is either not yet constructed or is owned by a value whose `Drop` performs the
cleanup. There is no explicit cleanup-on-failure block because construction is
linear and short-lived.

## Method

Static inspection of error paths in `bootstrap`. Working directory:
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent`.

```text
1. Read echo-agent-cli/echo-agent-app-core/src/runtime.rs:73-369.
2. Identify every early-return point (?, bail, Err return).
3. For each, determine what resources have already been constructed and whether
   their Drop is sufficient (no leaked tasks, file handles, or spawned
   background work).
4. Confirm the browser_runtime (an async-started resource) is either cleaned up
   or not yet live at each ?.
```

## Expected Result

- Bootstrap uses `?` for fatal errors; the only explicit `Err` mapping is
  `create_agent_with_diagnostics` (`runtime.rs:104-105`).
- No background task is spawned before the last `?` that could leak.
- `BrowserRuntime` is the only resource with async `start`; confirm it is
  Drop-cleaned if a later step fails.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not-applicable
- Summary: claim holds.

  Error-return points inside `bootstrap`:

  1. `runtime.rs:103-105` — `infra::create_agent_with_diagnostics(...).await.map_err(|e| anyhow::anyhow!("{e}"))?`.
     At this point only the `state_store`, conversation id, and `browser_runtime`
     have been created (`runtime.rs:80-100`). The browser runtime has been
     `start`ed; its `Drop` must shut it down (relies on `BrowserRuntime`'s own
     Drop impl — see Deviations). No agent yet, no HITL, no hooks, no spawned
     tasks. Return propagates cleanly.

  No other `?` appears in the body. All subsequent steps (`load_mcp_config`,
  `apply_compressor`, HITL wiring, skill loads, hook loads, review integration,
  LSP tools, plugin runtime, research tools, startup hook, intent router) either
  swallow errors into `tracing::warn!` (skills `runtime.rs:160-163`, LSP server
  start `register_lsp_tools` `runtime.rs:568-570`, methodology baseline is
  best-effort) or are infallible synchronous wiring. `load_mcp_config` and
  `load_user_hooks` return `()` (best-effort). `fire_startup_hook` returns `()`.
  `PluginRuntimeService::new` is infallible (returns `Self`, not `Result`).

  Implications:
  - Because the only `?` is at the very first service construction, a bootstrap
    failure leaves essentially nothing to clean up: no agent, no HITL
    dispatcher, no skills, no hooks, no spawned scheduler. The caller
    (`run_tui_or_cli_entry` / `run_desktop`) receives `Err` and propagates to
    `main`, which prints and exits. No partial-state recovery is needed.
  - `BrowserRuntime` is the one resource live before the `?` would fire on a
    *re-call* — but on the failing path it is created *after* `create_agent`
    succeeds... wait, ordering: `browser_runtime` is created at `runtime.rs:93-99`
    **before** `create_agent_with_diagnostics` at `runtime.rs:103`. So if
    `create_agent` fails, `browser_runtime` is live and would be dropped when
    the local goes out of scope on the `?` return. Correctness depends on
    `BrowserRuntime`'s `Drop` shutting down its driver. This is the only
    leak-sensitive ordering point.
  - On success, `BrowserRuntime` is moved into the returned `Self` and the
    caller is responsible for calling `browser_runtime.shutdown()` at process
    exit (confirmed in V04: every entry does so).

- Log/artifact: none

## Deviations

- `BrowserRuntime::Drop` behavior was not read in this review (its definition
  lives in `echo-agent-app-core/src/browser/`). The claim assumes Drop shuts
  down the driver. If Drop does not, a `create_agent` failure could leak the
  browser process until process exit. This is a low-severity residual
  uncertainty, not a bootstrap-logic defect — process exit reclaims the
  resource regardless.

## Conclusion

Supports the A-BOOT-01 Layering Decision and Current Path: bootstrap is a
linear construction with a single fatal `?` near the top, so failure cannot
leave the agent in a partially-wired state. No explicit cleanup-on-failure
block exists because none is needed. This also means the double-construction
finding (A-BOOT-01-P2-01) is not a *failure-safety* problem — it is purely a
construction-counting / duplication problem.
