## Claim

Every entry's shutdown path calls `TaskRuntimeStore::shutdown_hook_events`,
`BrowserRuntime::shutdown`, and cancels its `CancellationToken`, but the
**ordering** differs between headless (flush -> browser -> drop runtime ->
cancel) and GUI/channels (cancel first or no explicit runtime drop). This
validates A-BOOT-01-P3-02.

## Method

Static inspection + grep of shutdown paths. Working directory:
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent`.

```text
1. grep -n "shutdown_hook_events\|browser_runtime.shutdown\|cancel_token.cancel\|drop(runtime)" \
     echo-agent-cli/src/main.rs echo-agent-cli/src/tauri/desktop.rs
2. For each of the 4 exit branches (TUI, CLI, channels-only, GUI), record the
   ordered sequence.
3. Read TaskRuntimeStore::shutdown_hook_events (store.rs:261) to confirm it
   does not depend on a CancellationToken-gated task.
```

## Expected Result

- All four entries call `shutdown_hook_events` and `browser_runtime.shutdown`.
- All four call `cancel_token.cancel()`.
- Headless (TUI/CLI) does `drop(runtime)` explicitly; GUI and channels do not.
- Ordering diverges as described in A-BOOT-01-P3-02.

- Summary: claim holds.

  Shutdown sequences (in source order):

  - **TUI** (`main.rs:329-336`):
    1. `task_runtime_store.shutdown_hook_events()` (`main.rs:330-333`)
    2. `runtime.browser_runtime.shutdown()` (`main.rs:334`)
    3. `drop(runtime)` (`main.rs:335`)
    4. `cancel_token.cancel()` (`main.rs:336`)

  - **CLI** (`main.rs:438-445`, runs after `run_cli_mode` returns):
    1. `shutdown_hook_events()` (`main.rs:439`)
    2. `browser_runtime.shutdown()` (`main.rs:443`)
    3. `drop(runtime)` (`main.rs:444`)
    4. `cancel_token.cancel()` (`main.rs:445`)

  - **Channels-only** (`main.rs:394-400`):
    1. `shutdown_hook_events()` (`main.rs:395`)
    2. `browser_runtime.shutdown()` (`main.rs:399`)
    3. `cancel_token.cancel()` (`main.rs:400`)
    - No explicit `drop(runtime)` (implicit at scope end of `run_tui_or_cli_entry`).

  - **GUI** (`desktop.rs:261-267`):
    1. `cancel_token.cancel()` (`desktop.rs:261`)
    2. `shutdown_hook_events()` (`desktop.rs:262-266`)
    3. `browser_runtime.shutdown()` (`desktop.rs:267`)
    - No explicit `drop(runtime)` (implicit at scope end of `run_desktop`).

  `shutdown_hook_events` (`store.rs:261`) returns `Result<(), String>` and
  operates on the store's own hook-dispatcher state; it does not await any
  `CancellationToken`-gated task. Therefore GUI's cancel-before-flush ordering
  is not a live bug today, but it is a divergence: headless flushes while
  background tasks are still alive (safer), GUI flushes after cancelling.

  Additional observations:
  - No entry explicitly stops `SchedulerRunner` or `BackgroundTaskService`.
    Both rely on their own internal `CancellationToken` and process exit. The
    process-wide `cancel_token` cancelled in each entry is the config-watcher's
    token, **not** the scheduler/bg-task tokens (those are separate
    `SchedulerState::cancel_token` / `TaskState::cancel_token`).
  - The throwaway `AppState` built inside `start_headless_services`
    (`modes.rs:57`) is dropped at end of `start_headless_services` — its
    `SchedulerState` / `TaskState` `CancellationToken`s are NOT cancelled by
    that drop (they are just dropped). The escaping `Arc<SchedulerRunner>` and
    `Arc<BackgroundTaskService>` keep the background tasks alive via their own
    internal handles. This is consistent with the headless design but worth
    noting for any future shutdown-correctness task.

## Conclusion

Supports A-BOOT-01-P3-02: shutdown ordering is inconsistent across entries
(headless flushes before cancel; GUI cancels before flush). The divergence is
not currently exploitable because `shutdown_hook_events` is self-contained, but
a future hook that depends on a token-gated task would break under GUI's
ordering. The recommended fix is a shared `shutdown(...)` helper with a
documented order. Also documents that scheduler / bg-task shutdown relies on
process exit, not explicit stop, in all entries.

## Follow-Up

None for A-BOOT-01. A future task chartered for shutdown correctness could
assert that `SchedulerRunner` / `BackgroundTaskService` stop cleanly on token
cancel rather than relying on process exit.
