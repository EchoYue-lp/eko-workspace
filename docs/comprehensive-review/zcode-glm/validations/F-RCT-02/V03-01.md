## Claim

`max_iterations` is enforced as a hard ceiling by the loop driver, and
two soft budgets (`RunBudgetPolicy::iteration_wind_down_remaining` and
`max_model_tokens`) steer the model toward convergence. However, the
dedicated `LoopDetector` advertised by `loop_detector.rs` and
`AgentConfig::loop_detector_config` is **dead infrastructure**: it is
never instantiated on the live loop, so no exact-duplicate,
failure-streak, or no-progress loop detection actually runs.

## Expected Result

- `max_iterations` bounds the loop and fires `finalize_max_iterations`
  on exhaustion.
- Wind-down and final-only budgets inject exactly-once nudges.
- `LoopDetector` is wired into the loop (record_tool_call /
  record_iteration / check) — OR, if not wired, is clearly marked as
  unused scaffolding.

## Result

- Exit code: 0 for all three cargo invocations.
- Summary:

**`max_iterations` enforcement — VERIFIED.**
`stream_channel.rs:521-527` rewrites `max_iterations == 0` to
`usize::MAX` (the "unlimited" sentinel) while preserving for-loop
semantics. The `for iteration in 0..max_iterations` (`:528`) therefore
always terminates after at most `max_iterations` iterations (default
100). When the loop falls through, `:754-755` calls
`finalize_max_iterations`, which emits `Err(MaxIterationsExceeded)`,
marks the trace `Failed`, and fires `StopFailure` + `SessionEnd`
hooks. The test
`finalize_max_iterations_sends_error_and_marks_trace_failed`
(`finalize.rs:336-361`) asserts the trace status and error string.

**Soft budgets — VERIFIED.**
- `iteration_wind_down_remaining`: when
  `remaining <= threshold`, a one-shot `BudgetDecision::WindDown` event
  is emitted and a context note is pushed (`stream_channel.rs:540-573`),
  gated by `state.budget.wind_down_emitted` so it fires exactly once.
  The test `iteration_wind_down_is_injected_once`
  (`stream_channel.rs:1714-1752`) asserts `wind_down_count == 1` with
  `max_iterations=2, threshold=1`.
- `max_model_tokens`: once cumulative reported tokens cross the limit,
  `state.budget.final_only = true` (`:622-641`), a
  `BudgetDecision::FinalOnly` event fires, and subsequent iterations
  strip tools from the request (`think.rs:395-398`,
  `tools_for_request`). If the model still emits tool calls, they are
  blocked and the loop continues (`:643-651`). The test
  `model_token_budget_blocks_tools_and_forces_final_only_request`
  (`stream_channel.rs:1811-1857`) asserts the tool never runs.
- `missing_provider_usage_does_not_fake_token_budget_exhaustion`
  (`:1899`) guards the no-usage edge case.

**`LoopDetector` — NOT WIRED (dead infra).**
`LoopDetector::new()` is called **only** inside `loop_detector.rs`
`#[cfg(test)]` (`:159, 168, 180, 193, 206`). Zero production call sites
exist in `echo-agent` or `echo-agent-cli`. The runtime never invokes
`record_tool_call`, `record_iteration`, or `check`. The advertised
"three types of loop detection" (exact-duplicate at threshold=3,
failure-streak at threshold=3, no-progress at threshold=8 —
`loop_detector.rs:1-7, 22-28`) do not run. The config field
`AgentConfig::loop_detector_config` (`config.rs:176`), the builder
method `.loop_detector(...)` (`:1025`), and the accessor
`.get_loop_detector_config()` (`:1031`) are all carry-along plumbing
for the dead struct.

Consequence: the only loop-protection actually enforced is the hard
`max_iterations` ceiling plus the two optional soft budgets. An agent
that calls the same read-only tool with identical args 99 times (under
the default `max_iterations=100`) will burn 99 LLM rounds with no
detection or nudge — `LoopDetector`'s exact-duplicate `Break` would
have stopped it at 3.

- Log/artifact: none (test output captured inline; no separate log
  file created).

## Conclusion

The claim is **supported on both halves**.
- `max_iterations` + the two soft budgets work as designed and are
  covered by tests. This is the loop-protection mechanism that actually
  runs.
- `LoopDetector` + `LoopDetectorConfig` + the `loop_detector_config`
  field + builder method + accessor are dead infrastructure. They
  advertise loop-detection capabilities the runtime does not perform.

The dead-infra half feeds finding **F-RCT-02-P2-01**. The finding is
classified P2 (not P0/P1) because the missing detection does not cause
data loss or core-path failure — `max_iterations` still bounds the run
— but it is misleading infra that violates the AGENTS.md "code cleanup:
no compatibility burden" rule and is structurally identical to the
dead-bus finding F-CORE-01-P2-01.
