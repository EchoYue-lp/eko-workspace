## Claim

One non-streaming turn transitions through a single, explicit state
machine `prepare_turn → [compact → think → (tools | verify_final_text |
NoResponse)]* → finalize_*`. Every transition is driven by a typed
outcome enum, and there is exactly one ReAct loop body shared by the
streaming and non-streaming entry points.

## Expected Result

A single linear state machine with:
1. One pre-loop `prepare_turn` call.
2. One `for iteration in 0..max_iterations` loop.
3. Per-iteration order: callbacks → budget flags → compact → think →
   branch on (tool_call_map, content_buffer) → match IterOutcome.
4. Every terminal arm calls exactly one `phases::finalize::*` helper or
   returns `Ok(())` for the Abandoned short-circuit.
5. No second/sibling loop body.

Transition triggers:
- prepare → loop: `PrepareOutcome::Continue { task_node_id }`.
- prepare terminal: `BlockedAndDone` (hook block, FinalAnswer already
  yielded), `Abandoned` (channel closed via `yield_final_event_or!`).
- compact → think: `CompactOutcome::Continue(Vec<Message>)`.
- think → branch: contents of `ThinkOutput` (`tool_call_map`,
  `content_buffer`).
- tools/text/noresponse branch: `think.tool_call_map.is_empty()` and
  `think.content_buffer.is_empty()`.
- verifier gate: `verify_answer` (Critic); fail → `IterOutcome::Continue`
  + injected feedback (self-correction), pass → FinalText or Finish.
- iteration → next: `IterOutcome::Continue`.
- Stop-hook continuation: `emit_final_text` returns
  `ControlFlow::Continue` once (one-shot `stop_hook_continued` flag,
  `finalize.rs:199`); next termination cannot continue again.

`run_core_loop` is documented and verified as the single loop body:

the same loop body." The non-streaming `run_react_loop` confirms this by

## Deviations

1. The task brief lists `pipeline.rs (1722 lines)` as a primary path
   for this review. `pipeline.rs` is the **tool-execution pipeline**
   (13-stage per-tool-call middleware; see `run/mod.rs:19` and
   `pipeline.rs:1-6`), not the turn-level state machine. The actual
   turn state machine lives in `stream_channel.rs::run_core_loop`.
   `pipeline.rs` is still on the live path — it is reached via
   `snap.execute_tool_with_policy` (`snapshot.rs:1189`) called from
   `phases/tools.rs:154` — but it governs individual tool invocations,
   not turn transitions. This validation covers the turn-level machine;
   the tool-pipeline internals are a separate concern.
2. `ReactAgent::process_steps` (`react_loop.rs:177-502`) carries an
   `#[allow(dead_code)]` attribute and is not on any live path. It is
   the pre-unification non-streaming tool-batch implementation. See
   finding F-RCT-02-P2-02.

## Conclusion

The claim is **supported**. The turn state machine is a single explicit
`run_core_loop` body with typed outcome-enum transitions, shared by the
streaming and non-streaming entries. No parallel/sibling loop exists on
the live path. The `process_steps` and `pipeline.rs` clarifications
above feed findings F-RCT-02-P2-02 (dead `process_steps`) and the
scope note in the task report, but do not invalidate the transition
trace.
