## Claim

Spawned child processes are cleaned up on cancel/timeout/stream-drop (good),
but the ReAct core-loop driver task is detached without a tracked
`JoinHandle`, so cancellation of the *stream consumer* (dropping `rx`) is
cooperative and best-effort rather than guaranteed — the spawned task and
its held execution mutex rely on every await point noticing a send error.

## Method

Static trace of every `tokio::spawn` / `Command::spawn` / `CancellationToken`
site on the critical execution paths, reading the cancel/cleanup branches.

```text
# Child process: cancel/timeout/stream-drop handling
sed -n '396,449p' echo-agent/echo-execution/src/sandbox/local.rs   # spawn + kill_on_drop
sed -n '595,655p' echo-agent/echo-execution/src/sandbox/local.rs   # cleanup_child_process + select

# ReAct core loop driver: detached spawn
sed -n '302,315p' echo-agent/src/agent/react/run/stream_channel.rs # tokio::spawn, handle dropped

# Task/subagent executor: cooperative cancel
sed -n '1386,1407p' echo-agent/echo-orchestration/src/tasks/executor.rs
sed -n '496,518p'   echo-agent/echo-orchestration/src/tasks/background_task.rs  # select on cancel

# EKO agent pool: idle eviction
sed -n '744,770p' echo-agent-cli/.../agent_pool.rs
```

## Expected Result

For each spawned task/process there is a reachable cleanup path on
(cancel | timeout | consumer-drop). At least one path should lack a
guaranteed abort (the validation's falsifiable claim).

## Result

- Exit code: not-applicable (static trace)
- Summary:

  **Child processes — robust (no finding).** The sandboxed command stream
  (`echo-execution/src/sandbox/local.rs`) sets `command.kill_on_drop(true)`
  (`:406`) and the streaming driver `run_streaming_child` runs a
  `tokio::select!` (`:637`) over three arms: `tx.closed()` (consumer
  dropped → `cleanup_child_process` kills the child, `:638-641`), the
  timeout deadline (`:642-655`), and pipe reads whose `send` errors also
  trigger `cleanup_child_process` (`:666-683`). So stream-drop, timeout,
  and send-failure all reach a kill. `cleanup_child_process` (`:595-611`)
  additionally sends a process-group kill as a belt-and-suspenders.

  **Task/subagent executor — cooperative but tracked (no finding for
  cancel; the registry leak is separate, V01).** `cancel_task`
  (`executor.rs:1386-1392`) removes the per-task `CancellationToken` from
  the `running_tasks` DashMap and calls `token.cancel()`; the spawner's
  per-task future runs under a `tokio::select!` on `cancel.cancelled()`
  (`background_task.rs:498-518`), so a token cancel reaches the future.
  Concurrency is bounded by a semaphore (executor `max_concurrent: 5`,
  `executor.rs:69,376`), so even an unresponsive future cannot spawn
  unbounded work. `cancel_all` (`:1395-1407`) clears all tokens.

  **Agent pool — bounded & evicted (no finding).** `AgentPool` enforces
  `max_agents` (default 10, `agent_pool.rs:51,61`), evicts the oldest idle
  agent on pressure (`:302-340`), and runs a periodic idle-eviction task
  gated by a `CancellationToken` (`:744-765`, idle_timeout default 30 min,
  `:53,62`).

  **ReAct core-loop driver — detached, cooperative cleanup only
  (finding Q-PERF-01-P3-02).** `run_stream_channel`
  (`stream_channel.rs:302-312`) spawns the core loop with
  `tokio::spawn(async move { … })` and **drops the returned `JoinHandle`**
  — it is not stored, awaited, or abortable. The owned execution mutex
  guard (`execution_guard`) and the active-turn lease are moved into the
  task and released only when `run_core_loop` returns. Termination when the
  consumer drops `rx` is therefore **cooperative**: the loop must notice a
  `tx.send(...).await.is_err()` (e.g. the Token branch at `:410-411`,
  comment `"Receiver dropped — caller cancelled the stream"`) and return.
  Explicit run-cancel is stronger — it is delivered via the agent's
  `cancel_token`, honored by the think/tool phases (test
  `test_run_stream_cancelled_mid_llm_call` at `:1974`). The residual risk:
  a future await point that neither awaits a cancellable future nor checks
  `tx` would keep the spawned task (and the execution mutex) alive past
  consumer drop. This is a robustness gap, not an observed deadlock.

## Deviations

No live cancel was triggered in this environment (requires a running model
+ stream). The cleanup reachability is established statically from the
`select!` arms and the `kill_on_drop`/token-cancel wiring, which are
deterministic. The "no observed deadlock" qualifier for the detached
core-loop task is therefore a static-reachability limit, not a measured
non-occurrence.

## Conclusion

Supports Q-PERF-01-P3-02 (detached core-loop driver task; cleanup on
stream-drop is cooperative, not guaranteed via `JoinHandle::abort`). The
higher-risk cancellation surfaces (child processes, subagent executor,
agent pool) are well-handled and do **not** produce findings. This also
narrows V01's unbounded-registry finding: the *concurrency* is bounded, so
leaked registry entries are a memory issue (P2), not a runaway-process
issue.

## Follow-Up

A fault-injection suite (Q-FLT-01) should drive a real mid-stream drop +
cancel against a long-running tool/LLM call to confirm the detached task
actually exits and releases the execution mutex within bounded time.
