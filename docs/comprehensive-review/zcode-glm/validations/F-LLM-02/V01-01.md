## Claim

The OpenAI adapter's `OpenAiClient::chat` and `OpenAiClient::chat_stream`
faithfully map every neutral `ChatRequest` field onto the OpenAI Chat
Completions wire body (`ChatCompletionRequest`): `messages` are normalized
for OpenAI's content schema, `temperature`/`max_tokens`/`tools`/`tool_choice`/
`response_format`/`user_id` are forwarded unchanged, `thinking` is translated
into the correct vendor-specific wire field, `stream`/`stream_options` are set
correctly per path, and `cache_hints` is the only field silently dropped.

## Method

Static inspection of the two `LlmClient` impls that route OpenAI-compat
traffic, plus the wire-body type and the thinking translator. Confirmed the
executable compiles and the existing provider tests pass.


## Expected Result

Every neutral `ChatRequest` field maps 1:1 to a wire-body field or has a
documented translation step; `cache_hints` is the only documented no-op for
OpenAI; no neutral field is silently lost; the crate compiles clean and tests
pass.

## Deviations

- `cache_hints` is silently dropped on every OpenAI-compat path
  (`openai.rs:280-300, 336-355`; `adapter_client.rs:83-102, 138-157`). The
  wire body has no field for it and there is no log. Acceptable for OpenAI
  (automatic cache) but undocumented. See finding F-LLM-02-P3-02.
- The `ProviderAdapter::prepare_request` hook exists only on `AdapterClient`,
  which has no implementor. `OpenAiClient` does not invoke it. The hook is
  therefore never executed. See finding F-LLM-02-P2-01.

## Conclusion

The OpenAI adapter faithfully maps every forwardable neutral `ChatRequest`
field onto the OpenAI wire body, with correct thinking-protocol translation,
correct `stream`/`stream_options` per path, and a documented `normalize_messages`
transformation for content parts. The two deviations — `cache_hints` silent
drop and the dormant `prepare_request` hook — do not break the live OpenAI path
but are noted as findings. Supports V02, V03, V04. Used by findings
F-LLM-02-P2-01, F-LLM-02-P3-02.
