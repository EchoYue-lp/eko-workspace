## Claim

The OpenAI adapter correctly maps both response paths onto the neutral
contract: the non-streaming `ChatResponse { message, finish_reason, raw }`
preserves the first choice's message, finish reason, and the full raw body
(including usage); the streaming `BoxStream<Result<ChatChunk>>` preserves
every SSE chunk's delta, finish reason, and usage — including the final
usage-only chunk whose `delta` is `null`. `reasoning_content` flows through
both paths unchanged.

## Method

Static inspection of the two response mappers, the SSE parser, and the
streaming chunk types. Verified the deserializer's null-delta handling and the
`[DONE]` terminator path. Ran the existing client/OpenAI test suites.

```text

cargo test -p echo_integration --lib providers::openai
```

## Expected Result

Both paths round-trip content, reasoning, tool-call deltas, finish reason, and
usage without silent loss; the final usage-only chunk is not dropped; the
`[DONE]` marker terminates the stream cleanly; reasoning_content is preserved.

## Result

- Exit code: 0 (both commands)
- Duration: <1s each (3 client tests; 4 openai tests; 0 failed)
- Summary:
  - **Non-streaming response mapping** (`openai.rs:302-316`):
    ```rust
    let raw = post(...).await?;
    let choice = raw.choices.first().ok_or(LlmError::EmptyResponse)?;
    Ok(ChatResponse {
        message: choice.message.clone(),
        finish_reason: choice.finish_reason.clone(),
        raw,
    })
    ```
    - `choice.message` is a fully-populated `Message` including `content`,
      `tool_calls`, `reasoning_content`, and `name` — all cloned verbatim
      from the wire-format `Choice`. No field is dropped at this layer.
    - `raw: ChatCompletionResponse` is the **entire** deserialized body, so
      `raw.usage` (`types.rs:633-634`) survives even though `ChatResponse`
      has no top-level `usage` field. Consumers reach in via `response.raw.usage`
      (e.g., `react_loop.rs:100`). See finding F-LLM-02-P2-04.
    - Empty `choices` array → `LlmError::EmptyResponse`. Correct.
    - Non-first choices silently ignored (`choices.first()`). The framework
      never sends `n>1` (no `n` field on `ChatCompletionRequest`), so no live
      data loss. See finding F-LLM-02-P3-03.
  - **Streaming response mapping** (`openai.rs:366-375`):
    ```rust
    Ok(Box::pin(futures::StreamExt::map(stream, |result| {
        result.map(|chunk| {
            let choice = chunk.choices.first();
            ChatChunk {
                delta: choice.map(|c| c.delta.clone()).unwrap_or_default(),
                finish_reason: choice.and_then(|c| c.finish_reason.clone()),
                usage: chunk.usage.clone(),
            }
        })
    })) as BoxStream<...>)
    ```
    - When `chunk.choices` is non-empty: `delta` is cloned from the first
      choice's `DeltaMessage`, which carries `role`, `content`,
      `reasoning_content`, and `tool_calls` fragments (`types.rs:833-847`).
      `reasoning_content` flows through verbatim — verified by the React
      engine's `process_stream_chunk_accumulates_reasoning_for_protocol_replay`
      test (`processor.rs:245-270`).
    - **When `chunk.choices` is empty (usage-only final chunk)**:
      `choice = None`, `delta = DeltaMessage::default()` (empty), and
      `finish_reason = None`, BUT `usage = chunk.usage.clone()` preserves the
      usage object. The chunk is emitted, not dropped. This is the correct
      handling of OpenAI's terminal `include_usage` chunk.
    - **When `chunk.choices[0].delta` is `null`** (some providers send
      `{"delta":null,"finish_reason":"stop"}` on the terminal chunk): the
      `#[serde(deserialize_with = "deserialize_null_as_default")]` on
      `ChunkChoice.delta` (`types.rs:822`) converts null to
      `DeltaMessage::default()`, so the chunk parses successfully. Without
      this, the entire terminal chunk would fail to deserialize and `usage`
      would be silently lost. The doc-comment at `types.rs:813-821` documents
      this exact scenario.
  - **SSE parsing pipeline** (`client.rs`):
    - `split_sse_event` (`:36-49`): splits on `\n\n` or `\r\n\r\n`, preferring
      the earlier match — handles both LF and CRLF servers.
    - `parse_sse_data` (`:51-72`): strips `data:` prefixes, joins multi-line
      data, ignores `event:`/`id:`/`retry:`/`:` comment lines. Tested by
      `parse_data_without_space` and `parse_data_with_crlf_and_keepalive`
      (`:367-386`).
    - `parse_sse_chunk` (`:76-107`): trims, treats `[DONE]` as the stream
      terminator (returns `Err(LlmError::NetworkError(SENTINEL))` — see
      finding F-LLM-02-P3-01), parses other data as `ChatCompletionChunk`.
      **On serde failure: logs `warn!` and returns `None`** (`:99-105`) — the
      malformed chunk is silently dropped and the stream continues. See
      finding F-LLM-02-P2-03.
    - Stream loop (`:244-351`): polls `bytes_stream`, appends to buffer,
      extracts complete SSE events, parses them, yields chunks. On the
      `[DONE]` sentinel error, returns (terminates stream cleanly). Cancellation
      token checked between chunks (`:252-256`). Timeouts: first-chunk (30s
      default), idle (60s default), overall (off by default) — all env-tunable.
- Log/artifact: none

## Deviations

- Non-streaming `ChatResponse` exposes usage only via `raw.usage`, not a
  top-level field. Asymmetric with `ChatChunk.usage`. See finding
  F-LLM-02-P2-04.
- Malformed SSE chunks are silently dropped at the transport layer
  (`client.rs:99-105`); neither the OpenAI adapter nor the React engine is
  notified. See finding F-LLM-02-P2-03.
- The `[DONE]` marker is encoded as a sentinel string inside
  `LlmError::NetworkError` and detected by `err.to_string().contains(...)`.
  See finding F-LLM-02-P3-01.

## Conclusion

The OpenAI adapter faithfully maps both response paths onto the neutral
contract. Non-streaming preserves the full message + raw body; streaming
preserves every chunk including the terminal usage-only chunk (via the
null-delta deserializer). `reasoning_content` flows through on both paths for
OpenAI-family reasoning models. The four noted deviations are observational
or design-level (P2/P3), not semantic loss on the live path. Supports V01,
V03, V04. Used by findings F-LLM-02-P2-03, F-LLM-02-P2-04, F-LLM-02-P3-01,
F-LLM-02-P3-03.
