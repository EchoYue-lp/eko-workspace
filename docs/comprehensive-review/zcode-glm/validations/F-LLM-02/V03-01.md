## Claim

Tool calls are handled correctly across both paths: the non-streaming response
carries fully-assembled `ToolCall` objects in `Message.tool_calls`; the
streaming path relays `DeltaToolCall` fragments indexed by `index`, and the
downstream React-engine assembler (`processor.rs`) correctly aggregates
parallel tool calls, concatenates incremental argument fragments, repairs
trailing-character corruption from provider "fake-stream" artifacts, and
drops unparseable tool calls rather than echoing corrupt JSON back to the
provider.

## Method

Static inspection of the OpenAI adapter's tool-call handling on both paths
(none — it relays), the streaming chunk types, the React-engine assembler, and
its 7 unit tests. Ran the React-engine processor tests.


## Expected Result

Parallel tool calls aggregate by index; empty-args `{}` tool calls survive;
malformed args are repaired when possible and dropped when not; the OpenAI
adapter itself performs no assembly (correct — it relays fragments).

## Result

- Exit code: 0 (both commands)
- Duration: <1s each
- Summary:
  - **OpenAI adapter performs NO tool-call assembly** — by design. The
    streaming mapper (`openai.rs:366-375`) clones `choice.delta` verbatim
    into `ChatChunk.delta`, which carries `tool_calls: Option<Vec<DeltaToolCall>>`
    (`types.rs:846`). Each `DeltaToolCall` has an `index: u32` field
    (`types.rs:853`) that identifies which parallel call the fragment belongs
    to. Assembly is the consumer's responsibility. On the non-streaming path
    (`openai.rs:310-316`), OpenAI returns fully-assembled `ToolCall` objects
    in `choice.message.tool_calls` (`types.rs:451-460`), and the adapter
    clones them verbatim into `ChatResponse.message`. Correct.
  - **React-engine assembler** (`processor.rs`):
    - `process_stream_chunk` (`:16-88`): for each `DeltaToolCall` in
      `choice.delta.tool_calls`, looks up / creates an entry in
      `tool_call_map: HashMap<u32, (id, name, args)>` keyed by `dc.index`
      (`:64-67`). Updates `id` if present and non-empty (`:68-72`), updates
      `name` if present and non-empty (`:73-78`), and **concatenates**
      argument fragments via `entry.2.push_str(args)` (`:79-81`). This is
      correct incremental assembly: OpenAI streams args character-by-character
      across many chunks.
    - `build_tool_calls_from_map` (`:138-183`): sorts entries by index
      (`:141-142`) — preserves the model's emitted order even though HashMap
      iteration is unordered — then calls `parse_tool_args` for each.
    - **Parallel tool calls**: each call has a distinct `index`, so the
      HashMap correctly accumulates them in parallel. Confirmed by code path:
      two simultaneous calls with index 0 and 1 land in distinct entries.
    - **Empty-args `{}`**: `parse_tool_args("{}")` returns
      `Ok((Value::Object({}), "{}"))` — verified by `parse_tool_args_empty_object`
      test (`processor.rs:236-242`). The tool call survives with empty args.
      This is the OpenAI-server standard for no-arg tools.
    - **Empty-args `""` (empty string, not `{}`)**: `parse_tool_args("")`
      fails (empty string is not valid JSON), the repair loop trims to `""`
      and retries — still fails — so the call is **dropped** with a `warn!`
      (`processor.rs:165-178`). OpenAI servers do not send `arguments: ""`,
      but a non-conforming provider could trigger this. See finding
      F-LLM-02-P3-04.
    - **Trailing-character repair** (`parse_tool_args`, `:104-135`): on JSON
      parse failure, strips trailing `}`/`]`/`,`/whitespace one character at
      a time (up to 8 iterations) and retries. Handles the DeepSeek
      "fake-stream" extra-`}` artifact documented at vLLM issue #42878.
      Verified by 4 repair tests (`:201-227`). Uses `attempt.chars().last()`
      and `attempt.pop()` — UTF-8 safe (operates on `char`, not bytes).
    - **Genuinely broken args**: returns `Err`, and `build_tool_calls_from_map`
      drops the tool call entirely (`:165-178`). The comment at `:173-177`
      explains the policy: dropping avoids HTTP 400 "Invalid assistant message"
      on the next turn and avoids emitting a half tool_call with no matching
      tool_result. The model can retry the call cleanly next turn. Verified
      by `parse_tool_args_genuinely_broken_returns_err` (`:229-234`).
    - **Canonical args echo**: on successful parse, the **re-serialized**
      canonical form is what goes into `LlmToolCall.function.arguments`
      (`:160`), not the raw received string. This means the next-turn
      assistant message always carries valid JSON, even if the stream
      delivered slightly-corrupted fragments that were repaired.
  - **Test coverage** (`processor.rs:185-271`): 7 tests covering valid JSON,
    empty object, single extra `}`, trailing whitespace, multiple extra `}`,
    genuinely-broken, and reasoning accumulation. All pass.
- Log/artifact: none

## Deviations

- The OpenAI adapter does no tool-call assembly on the streaming path; a
  non-React consumer of `LlmClient::chat_stream` must do its own
  index-keyed aggregation. The neutral `ChatChunk` carries fragments, not
  assembled calls. This is a contract design choice (F-LLM-01 V01-01
  confirmed `ChatChunk.delta.tool_calls: Option<Vec<DeltaToolCall>>`), not
  a defect — but it means the "faithful implementation" guarantee is
  "faithful relay of fragments", not "faithful assembly".
- Empty-string args (`""`, distinct from `"{}"`) cause the tool call to be
  dropped. See finding F-LLM-02-P3-04.

## Conclusion

Tool-call handling is correct and well-tested on the live OpenAI path:
parallel calls aggregate by index, argument fragments concatenate correctly,
DeepSeek-style trailing-corruption is repaired, and unrepairable calls are
dropped with a clear policy. The OpenAI adapter faithfully relays both
assembled (non-streaming) and fragment (streaming) tool calls. The one edge
case — empty-string args being dropped — is low-probability (OpenAI servers
send `{}`) and noted as P3. Supports V01, V02. Used by finding
F-LLM-02-P3-04.
