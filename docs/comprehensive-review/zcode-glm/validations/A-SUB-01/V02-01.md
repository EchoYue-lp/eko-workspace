## Claim

Default subagent routes (DomainProfile × PlanTaskKind) are validated at
startup against the effective catalog snapshot. The validation is a hard
gate (failure aborts the agent build) and runs before the system prompt is
baked. Invalid routes surface as a typed error rather than silent
degradation.

## Expected Result

(1) `validate_default_subagent_routes` runs inside `create_agent_with_diagnostics`
    before the system prompt is finalized.
(2) The gate's `Err(...)` propagates as `Result<CreatedAgent, _>` failure
    (it does not silently fall back to defaults).
(3) The gate covers every (DomainProfile, PlanTaskKind) pair.
(4) The gate uses the SAME catalog snapshot that is baked into the system
    prompt, so the LLM's view and the gate's view agree at bootstrap.
(5) The unit test `every_default_route_resolves_in_the_effective_catalog`
    exercises the gate end-to-end.

## Deviations

Two observations that narrow the claim but do not invalidate it:

1. **The gate is structurally a no-op in practice today.** Every
   non-`primary` route in `default_subagent_for` resolves to a builtin
   name (`explorer` / `reviewer` / `summarizer` / `analyst` /
   `implementer`). Builtins are seeded by `discover_subagents` via
   `by_name.entry(name).or_insert(def)` (loader.rs:274) — they are always
   present unless a builtin source `.md` is corrupt. The
   `builtin_defaults_parse_cleanly` test guards against that at unit-test
   time. So in a normal bootstrap the gate cannot fail. Its real value is
   forward protection: if `default_subagent_for` is changed to reference a
   non-builtin name, the gate catches it.

2. **The gate runs once, on the snapshot, not on the live registry.**
   Plugin registration (`plugin_runtime.rs:844-867`) runs after the gate
   and after the system prompt is baked. There is no re-validation after
   plugin register/unregister. This feeds A-SUB-01-P3-01: a plugin that
   removes or capability-mismatches a default route target is not caught.

## Conclusion

The claim is **supported**. The startup gate is wired correctly: it runs
at the right point in bootstrap (before system-prompt baking), uses the
same snapshot that is baked into the prompt, propagates failure as a
typed error, covers the full (profile × kind) matrix, and is exercised by
three passing unit tests. The gate's limitation is that it is a one-shot
snapshot check, not a live invariant — that is filed as A-SUB-01-P3-01
and is not a violation of the claim as stated.
