## Claim

When subagent definitions change after bootstrap (via `.md` edit, plugin
install/uninstall, or workspace switch), the primary agent's subagent
registry is **not** refreshed, the system-prompt-baked catalog section is
**not** refreshed, and `AgentPool` has **no** subagent refresh analog to
`refresh_skill_descriptors`. Pool agents independently re-read `.md`
files from disk on each `acquire` (because they call
`infra::create_agent`), so they silently diverge from the primary agent
after any post-bootstrap definition change.

## Deviations

Two observations that narrow the claim:

1. **Pool agents DO pick up `.md` edits on creation.** This is a
   side-effect of (5), not an explicit reload mechanism. If a user edits
   `~/.eko/subagents/explorer.md` at runtime, the primary agent keeps the
   old prompt, but the next pool agent acquired (`pool.acquire("conv-N")`)
   reads the new prompt from disk. This produces silent primary-vs-pool
   divergence after any edit. The task report classifies this as the
   "split behavior" in A-SUB-01-P2-02.

2. **Workspace switch does not break pool agent discovery, just defers
   it.** `pool.apply_working_dir(new_wd)` (state.rs:890) updates
   `pool.working_dir`, so FUTURE pool agent creations resolve against the
   new workspace. Existing pool agents (already in the HashMap) are NOT
   re-registered — their subagent registries are frozen at their
   `acquire` time. This is consistent with the skill refresh pattern
   (where existing pool agents ARE re-staged via `refresh_skill_descriptors`)
   — subagents are the outlier with no equivalent refresh.

## Conclusion

The claim is **supported**. There is no reload mechanism for subagents:
the watcher ignores `.md` files, `switch_workspace` does not refresh the
registry, `AgentPool` has no subagent refresh method (in contrast to
skills/memory/working_dir/permission/workspace-routing, all of which have
one), and the primary agent's registry is frozen at bootstrap. Pool
agents independently re-read `.md` files on each `acquire`, creating
silent primary-vs-pool divergence. Plugin subagents (separate
registration path on the primary only) never reach pool agents.

This is the basis for the two highest-priority findings:
[A-SUB-01-P2-01](../../tasks/A-SUB-01.md#a-sub-01-p2-01-plugin-subagents-register-only-on-the-primary-agent--pool-agents-never-see-them)
and
[A-SUB-01-P2-02](../../tasks/A-SUB-01.md#a-sub-01-p2-02-subagent-definitions-have-no-reload-mechanism-no-watcher-no-switch_workspace-hook-no-pool-refresh-api).
The skill refresh pattern at `agent_pool.rs:495-528` is the documented
template for the fix direction.
