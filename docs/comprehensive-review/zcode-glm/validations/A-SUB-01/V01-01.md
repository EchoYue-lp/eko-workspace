## Claim

Subagent definitions are loaded from exactly three file-based scopes
(builtin / user / project) with a documented precedence (project > user >
builtin), plugins constitute a fourth source registered through a separate
path that bypasses the file-scope precedence, no parallel app-layer
registry/compiler/route-table exists, and the framework dispatch catalog
is the sole runtime authority.

## Deviations

Three observations that do not invalidate the claim but narrow it:

1. **Plugin precedence is undocumented.** The loader docstring
   (`subagent_loader.rs:7-16`) names three scopes and their precedence.
   Plugins are not mentioned, yet they register last and silently overwrite
   any same-named definition (last-write-wins in the framework registry).
   This feeds A-SUB-01-P3-02.

2. **`SubagentCatalogSnapshot` has two constructors over the same struct.**
   `from_definitions` (app-layer `SubagentDefinition`) and `from_registered`
   (framework `echo_agent::agent::subagent::SubagentDefinition`). They
   differ in how `readonly` / `isolation` are derived: `from_definitions`
   reads the app-layer fields directly (loader.rs:176-179), while
   `from_registered` parses framework tags
   (`capability:readonly`, `isolation:worktree`) back into the projection
   (loader.rs:194-201). The two paths agree if registration tags are set
   consistently — and `register_default_subagents` does set them
   (`infra.rs:736-742`), but `register_plugin_agents` does NOT set
   `prompt_source:`, `capability:`, or `isolation:` tags on plugin
   definitions (`plugin_components.rs:478-509` passes through
   `definition.tags` directly, which contains only the frontmatter tags).
   This means a plugin's catalog entry from `from_registered` will show
   `isolation = "context"` regardless of its actual `isolate_worktree` /
   `isolate_workspace` fields, because the framework definition's tags
   don't carry the `isolation:*` tag that `from_registered` looks for.
   This is a minor projection inconsistency.

3. **Each pool agent re-runs `discover_subagents`** (`infra.rs:242-245`
   reached via `agent_pool.rs:850`). This is not a duplicate definition —
   it is the same loader invoked per-agent — but it does mean plugin
   subagents never reach pool agents (A-SUB-01-P2-01), and `.md` edits
   silently take effect for new pool agents but not for the primary
   (A-SUB-01-P2-02).

## Conclusion

The claim is **supported**. The three file-based scopes have the
documented precedence (verified by passing tests), plugins are a fourth
source on a separate path, the loader/compiler/route-table/gate are each
singular, and the framework `SubagentRegistry` is the sole runtime
authority. The three deviations above are documented gaps (precedence
documentation, projection consistency for plugins, and pool/primary
divergence), not violations of the claim.
