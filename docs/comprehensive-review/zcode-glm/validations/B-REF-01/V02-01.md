## Claim

OpenAI Codex CLI (the `codex` Rust CLI, especially `codex exec --json`)
exposes a non-interactive JSONL event stream with a small, stable set of
event types (thread/turn lifecycle + per-item lifecycle), uses a layered
submission/handler/turn agent loop, gates automation through three
**sandbox** modes plus three **approval** policies at the kernel level, and
treats crash recovery as a known gap rather than a solved feature. These
behaviors constrain the `B-REF-01` event, recovery, and permission
findings.

## Expected Result

Before lookup, the expectation (from `AGENTS.md`) was that Codex CLI emits
non-interactive events of the shape `item.in_progress` / `item.completed` /
`item.failed`, and that it has a sandbox-based permission model. The
expected event taxonomy was confirmed and substantially expanded.

## Result

- Exit code: not-applicable (literature lookup, no command)
- Summary: claim substantiated across agent loop, events, permissions, and
  recovery. Codex exposes the most explicit, machine-readable event stream
  of any system in this matrix.

### 1. Architecture: event-driven three-layer state machine

From the Codex CLI Internals Survey (https://yage.ai/share/codex-cli-internals-survey-en-20260314.html,
accessed 2026-08-12):

- The loop is an "event-driven three-layer state machine" built on two
  async channels: a **Submission channel** (client → session) and an
  **Event channel** (session → client).
- Three nested layers:
  1. **Submission loop** — outer loop that waits for user operations.
  2. **Handler scheduling** — middle layer that starts a new dialogue
     round on each user input.
  3. **Turn loop** — innermost cycle managing a single conversational
     turn; "no hard limit on inference and tool-execution cycles," so a
     single turn can chain dozens of tool calls.
- **Stateless turn design.** The full conversation history is sent on
  every API call (Responses API), ignoring server-side state parameters.
  This simplifies the client and supports Zero Data Retention.
- Prompt assembly cascade: hard-coded system prompt → optional developer
  instructions → cascaded `AGENTS.md` files → configured skills →
  available tools → full conversation history.

### 2. State model

- State lives in two places: the in-memory session state machine
  (submission/handler/turn) and the JSONL session log on disk
  (`~/.codex/sessions`). The session state machine is **not** a published
  data structure; only the JSONL log is observable.
- `AGENTS.md` cascading is identical in spirit to Claude Code's
  `CLAUDE.md` model — first-party discovered files are merged into the
  prompt.

### 3. Plan mode

- Codex CLI does **not** document a "plan mode" equivalent to Claude
  Code's `plan` mode. There is no public concept of a plan artifact that
  the user approves before execution.
- The closest analogues are:
  - The `--ask-for-approval` flag (values: `never`, `on-failure`,
    `on-request`) which gates tool execution per turn, not per plan.
  - The `todo_list` event type, which surfaces a checklist that the agent
    maintains internally; this is a progress projection, not an approval
    gate.

### 4. Subagent / delegation

- Codex CLI is a **single-agent** runtime. There is no public `Task` tool
  or subagent primitive in Codex CLI's first-party surface as of the
  lookup date.
- Parallelism across tasks is achieved by running multiple `codex exec`
  processes (e.g., the agent-cockpit issue #135 pattern), not by an
  in-process subagent API.

### 5. Events: the canonical non-interactive stream

From the takopi.dev cheatsheet (https://takopi.dev/reference/runners/codex/exec-json-cheatsheet/,
accessed 2026-08-12), `codex exec --json` writes one JSON object per line
(JSONL) where each line is a top-level thread event with a `type` field.

**Top-level event types:**

| Event              | Payload                                              |
|--------------------|------------------------------------------------------|
| `thread.started`   | `thread_id`                                          |
| `turn.started`     | (none beyond `type`)                                 |
| `turn.completed`   | `usage.input_tokens`, `usage.cached_input_tokens`, `usage.output_tokens` |
| `turn.failed`      | `error.message`                                      |
| `error`            | `message` (transient; "Reconnecting…" is non-fatal)  |

**Item event types** (every item line has a stable `item.id`, plus
`item.type`, plus a per-item `item.status` of `in_progress`, `completed`,
or `failed`):

| `item.type`        | Lifecycle lines                              | Notable payload                                                |
|--------------------|----------------------------------------------|----------------------------------------------------------------|
| `agent_message`    | `item.completed`                             | `item.text`                                                    |
| `reasoning`        | `item.completed`                             | `item.text`                                                    |
| `command_execution`| `item.started`, `item.completed`             | `item.command`, `item.aggregated_output`, `item.exit_code`     |
| `file_change`      | `item.completed`                             | `item.changes[].path`, `item.changes[].kind` (`add`/`delete`/`update`) |
| `mcp_tool_call`    | `item.started`, `item.completed`             | `item.server`, `item.tool`, `item.arguments`, `item.result`, `item.error` |
| `web_search`       | `item.completed`                             | `item.query`                                                   |
| `todo_list`        | `item.started`, `item.updated`, `item.completed` | `item.items[].text`, `item.items[].completed`              |
| `error` (as item)  | `item.completed`                             | `item.message`                                                 |

**Stable identity:** `item.id` is stable for an item; updates and
completion lines reuse the same id. This is the critical property that
lets a downstream reducer update an in-flight row in place rather than
append.

**Lifecycle sequence:** `thread.started` → `turn.started` → (any number
of `item.started` / `item.updated` / `item.completed` lines) →
`turn.completed` (or `turn.failed`).

This is the **most explicit event schema** of any system in this matrix
and is the strongest single reference for `X-EVT-01` (event lifecycle
conformance) in this review.

### 6. Permissions: kernel-level sandbox + approval policy

From https://learn.chatgpt.com/docs/agent-approvals-security and the
Codex CLI Internals Survey (accessed 2026-08-12):

**Sandbox modes (where writes are allowed):**

| Mode                   | Write scope              | Approval behavior                                   |
|------------------------|--------------------------|-----------------------------------------------------|
| `read-only`            | None                     | Never asks (cannot write).                          |
| `workspace-write`      | Repo / project directory | Auto-edits files; **asks approval for untrusted shell commands.** |
| `danger-full-access`   | Anywhere on system       | Full autonomy; no approval prompts.                 |

**Approval policies** (the `--ask-for-approval` flag):

| Value         | Behavior                                                          |
|---------------|-------------------------------------------------------------------|
| `never`       | No approval prompts (suitable for non-interactive pipelines).     |
| `on-failure`  | Prompt only after a tool execution fails.                         |
| `on-request`  | Prompt when the agent itself asks for human input.                |

**Sandbox enforcement is at the kernel level**, not the application
layer:

- macOS: **Seatbelt** (Apple's native sandbox).
- Linux: **Landlock + seccomp** for filesystem access control and
  syscall filtering.

This is a stronger isolation boundary than application-layer hooks (as
Claude Code uses). It is also less flexible: the policy is enforced even
against the agent's own process.

### 7. Skills

- Codex CLI assembles skills into the system prompt via the cascade
  noted above. There is no public skill-loading API analogous to Claude
  Code's `Skill` meta-tool with progressive disclosure; skills are
  flattened into the prompt.
- `AGENTS.md` cascading is the primary user-extension surface.

### 8. Recovery

- Sessions are stored as JSONL under `~/.codex/sessions`. There is a
  first-party **`/fork`** command that branches a new session from an
  existing one.
- **Robust crash recovery is explicitly a known gap.** Open feature
  requests:
  - openai/codex#1991 — "Add /resume command to continue after errors"
    (when Codex hits an unrecoverable error, "the entire workflow context
    is lost").
  - openai/codex#28218 — "Automatic Session Checkpointing and Recovery
    for Interrupted Workflows."
- Community-built workarounds exist (saving the resume hash, the
  Codex Session History Manager MCP skill) but there is no first-party
  durable multi-step checkpoint feature as of the lookup date.

## Deviations

- The official `learn.chatgpt.com` docs site timed out repeatedly under
  WebFetch; the cheatsheet and the internals survey were used as
  authoritative substitutes. The two are mutually consistent.
- The exact semantics of `--ask-for-approval=on-request` are not
  precisely documented in the pages fetched; the description above
  ("prompt when the agent itself asks") is the consensus reading of
  community sources and may not match the implementation exactly.

## Conclusion

Codex CLI is the **canonical reference for the event-stream pattern**
(item-level lifecycle with stable ids, thread/turn envelope, terminal
`turn.completed` / `turn.failed`) and for **kernel-level sandbox
permissions**. Its main constraints on this review are:

- `F-CORE-01` and `X-EVT-01`: a stable, per-item event identity that
  survives update and completion is the right shape; echo-agent's
  event envelope should support this pattern.
- `F-HITL-01` and `X-AUT-01`: kernel-level sandbox + named approval
  policy (`never`/`on-failure`/`on-request`) is the mature pattern for
  gating automated execution; this is consistent with EKO's local
  threat model because the sandbox is the user's machine, not a
  multi-tenant service.
- `F-RCT-05` (steer/interrupt/snapshot/resume): Codex's gap here
  confirms that durable multi-step checkpointing is not a solved
  problem in the broader ecosystem. echo-agent's `Snapshot` design is
  ahead of the industry norm, not behind it; the bar should be
  correctness, not parity.
