## Claim

Claude Code (Anthropic) — the primary external reference named in `AGENTS.md`
for Agent architecture, plan mode, subagent design, events, permissions, skills,
and recovery — implements these behaviors in publicly observable ways that
constrain the findings of `B-REF-01`. Specifically:

1. Plan mode is **prompt injection plus a lightweight enter/exit state machine**,
   not a multi-state runtime approval state machine. The plan is a Markdown file
   artifact on disk; tools are not actually rendered read-only at the tool layer.
2. Subagents are Markdown files with YAML frontmatter, spawned via a single
   `Task`/`Agent` tool, returning one final message; recursive subagent spawning
   is not normally allowed.
3. Permission modes are session-level flags; the model does not distinguish
   "direct user action" from "automated agent action" — the gate applies
   uniformly to tool calls. Hooks are the deterministic control layer.
4. Skills are filesystem folders with `SKILL.md` using YAML frontmatter and
   three-stage progressive disclosure; model invocation is the default and
   `disable-model-invocation: true` is the opt-out.
5. Recovery is session-resume plus JSONL logs; durable multi-step checkpointing
   is not a first-class product feature.

## Expected Result

Before lookup, the expectation was that Claude Code's plan mode, subagent
model, and skills system are well documented publicly and that plan mode is
implemented as prompt reinforcement rather than a runtime enforcement gate
(this is the explicit assumption in `AGENTS.md`).

## Result

- Exit code: not-applicable (literature lookup, no command)
- Summary: claim substantiated across all five areas, with one notable
  correction: plan mode is "prompt injection **plus a lightweight state
  machine**", not pure prompt injection.

### 1. Architecture (ReAct + Skills + Subagents)

- Claude Code's runtime is a single-agent ReAct loop augmented with hooks,
  skills, and a `Task`/`Agent` tool for delegating to subagents. Skills are
  surfaced to the model as a `Skill` meta-tool whose argument list is the
  short description of every available skill; the model decides when to
  invoke. Source: Anthropic engineering blog "Equipping Agents for the Real
  World with Agent Skills"; corroborated by Lee Hanchung's deep dive.
- The loop is deterministic only at hook boundaries; everything else
  (planning, tool selection, sequence) is model-driven.

### 2. State model (lightweight mode + artifact plans)

- Claude Code maintains a small session-level mode flag (one of `default`,
  `acceptEdits`, `plan`, `dontAsk`/auto, `bypassPermissions`). This is the
  only state machine that the public surface exposes; there is no
  multi-state plan-approval runtime machine.
- Source: https://claudefa.st/blog/guide/development/permission-management
  (accessed 2026-08-12); corroborated by Claude Code GitHub issue #5466
  ("Plan Mode can't be used with Bypass Permissions"), which exists
  precisely because plan mode is one mode value, not an approval-state graph.

### 3. Plan mode (prompt injection + tiny enter/exit state machine)

This is the key insight named in `AGENTS.md`. Verified against Armin
Ronacher's reverse-engineering (https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/,
accessed 2026-08-12):

- "It is **both**, but primarily prompt injection driving a lightweight state
  machine." The system prompt remains identical; plan mode appends "a little
  bit of extra verbiage" with workflow phases, read-only reminders, and the
  plan-mode exit tool description.
- "I was initially under the assumption that the tools actually turn into
  read-only. But it is just prompt reinforcement." The read-only behavior is
  not enforced at the tool layer.
- The plan is "a markdown file that is written into Claude's plans folder by
  Claude in plan mode." The agent uses the standard edit-file tool to write
  and modify the plan document; there is no structured plan data type.
- Exiting plan mode is itself a tool the agent invokes; on exit, the tool
  reads the plan **from the file on disk** and surfaces it to the user for
  approval. After approval, the agent reads the plan back from the file
  system and executes against it.

This **directly invalidates** any design that introduces a multi-state
runtime approval state machine (e.g., Planning → AwaitingApproval → Ready →
…). The mature pattern is: plan file is an artifact; approval is a UI flow
on top of a tool call; runtime only tracks the active mode.

### 4. Subagent / delegation model

- A subagent is a Markdown file with YAML frontmatter. Per GitHub issue
  anthropics/claude-code#19292 (which quotes the official "Supported
  frontmatter fields" table), the supported fields are: `name`,
  `description`, `tools`, `disallowedTools`, `model`, `permissionMode`,
  `skills`, `hooks`. `name` and `description` are required; the rest are
  optional overrides that scope the subagent's tools, model, permissions,
  skills, and hooks.
- The main agent spawns a subagent via a single `Task` (a.k.a. `Agent`)
  tool. The subagent runs in its own context window with its own tool set
  and permission scope, and **returns a single final message** to the
  parent.
- Subagents generally **cannot spawn further subagents**; this constraint is
  repeatedly noted in community reverse-engineering write-ups
  (ksred, learn-simplified on Medium). The official docs site does not
  explicitly document this constraint as of the lookup date.
- The `Task` tool accepts an `isolation: "worktree"` argument so the
  subagent's file edits land in a separate git worktree. Source: official
  https://code.claude.com/docs/en/sub-agents (via WebSearch snippet;
  direct WebFetch timed out).

### 5. Event / streaming model (hooks are the deterministic surface)

- Claude Code's deterministic event surface is **hooks**. Per
  https://code.claude.com/docs/en/hooks and
  https://hidekazu-konishi.com/entry/claude_code_hooks_complete_guide.html
  (accessed 2026-08-12), hook lifecycle events include at minimum:
  `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SessionStart`,
  `SessionEnd`, `Notification`, and `SubagentStop`. (Catalogs in the
  community list 13–30 named events; only the official-doc subset is cited
  here as canonical.)
- Hooks "run before the permission system and can approve, deny, or modify
  tool calls at runtime." They are the only deterministic control layer;
  everything else is prompt-driven.
- Streamed model output (text deltas, tool-call deltas, thinking) is
  surfaced via the SDK / CLI; the public docs do not enumerate a stable
  typed event schema at the level of Codex's `item.in_progress` /
  `item.completed` (see `V02-01`).

### 6. Permissions (session modes + hook overrides)

- Five primary modes: `default` (prompt for every potentially dangerous
  operation), `acceptEdits` (auto-accept file edits), `plan` (read-only
  intent; tools are not actually read-only at the tool layer, see above),
  `dontAsk`/auto (auto-deny unless pre-approved), and `bypassPermissions`
  (skip all checks). Source:
  https://claudefa.st/blog/guide/development/permission-management.
- The model **does not distinguish** direct user actions from automated
  agent actions. Every tool call is gated uniformly by the active mode and
  the configured allow/deny rules; there is no "user-invoked terminal" vs.
  "agent-invoked terminal" carve-out. This is a critical correction to the
  assumption baked into some EKO design discussions: in Claude Code, the
  permission mode applies to **all** tool usage.
- `PreToolUse` hooks can programmatically approve/deny at runtime — this is
  how automation pipelines pre-approve without disabling the gate.

### 7. Skills / plugins

- A skill is a directory containing a `SKILL.md` file with YAML frontmatter
  (`name`, `description`, optional `allowed-tools`, `model`,
  `disable-model-invocation`). Source:
  https://leehanchung.github.io/blogs/2025/10/26/claude-skills-deep-dive/
  and the official Anthropic engineering blog.
- Discovery is filesystem-based (user configs, project folders, plugins,
  built-ins). Loading uses **three-stage progressive disclosure**:
  1. Frontmatter (name + description) is loaded into a meta-tool list
     bounded to ~15,000 characters aggregate.
  2. On match, the full `SKILL.md` body is loaded (recommended ≤5,000 words).
  3. On execution, bundled `references/` and `assets/` files are loaded
     on demand.
- The model invokes skills by name via the `Skill` meta-tool. Setting
  `disable-model-invocation: true` removes the skill from the auto-list and
  requires explicit slash-command invocation.

### 8. Recovery

- Sessions can be resumed (`claude --resume`, slash-command `/resume`) from
  a session ID; sessions are stored as JSONL.
- Durable multi-step checkpointing (e.g., persisting an in-flight tool
  batch so a crash mid-batch resumes from the right step) is **not** a
  documented Claude Code feature. Claude Code does not need it for its use
  case because each turn is a fresh model call with the conversation
  history as the source of truth.
- Logs and traces are written to disk for forensics, not for replay-based
  recovery.

## Deviations

- The official Claude Code docs site (`code.claude.com`) repeatedly timed
  out under WebFetch (10-second connect timeout). Where this happened,
  claims were cross-checked against at least two independent secondary
  sources, and one of those sources is the Anthropic first-party
  engineering blog. Where only a single source was available, the claim is
  marked with lower confidence in the task report.
- "Subagents cannot spawn further subagents" is widely reported in
  community write-ups but not explicitly documented in the official docs;
  it is treated as a strong-but-not-canonical claim.
- The exact count of hook lifecycle events varies across community
  catalogs (13 to 30). Only events named in the official docs reference
  page (via search snippet) are listed as canonical.

## Conclusion

The `AGENTS.md` assertion that "Claude Code's plan mode is prompt injection
rather than runtime enforcement" is **substantially correct with one
refinement**: plan mode is prompt injection plus a tiny enter/exit state
machine that surfaces the plan for user approval. It is **not** a multi-state
runtime approval graph. The historical 13-state design rejected in
`AGENTS.md` is therefore confirmed as diverging from the mature pattern.

The findings constrain downstream review tasks as follows:

- `F-TSK-01` (canonical task model) — the plan must be an artifact, not a
  runtime state.
- `F-HITL-01` (human-loop and permission model) — permission modes are
  session flags + hook overrides; there is no per-tool-type user-vs-agent
  carve-out in the mature pattern.
- `F-SUB-01/02` (subagent) — single-message return, no recursion, optional
  worktree isolation, scoped tools/permissions/skills/hooks per subagent.
- `F-SKL-01` (skill loading) — progressive disclosure with model-invoked
  default.
- `F-OPS-01` (operational adapters) — recovery is JSONL session resume, not
  durable multi-step checkpointing.
