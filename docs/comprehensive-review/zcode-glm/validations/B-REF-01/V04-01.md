## Claim

Devin (Cognition) implements a **two-part brain + devbox** architecture
in which a stateless reasoning coordinator drives an ephemeral cloud
Linux container, runs a continuous **plan-execute-observe-replan** loop,
parallelizes via a **parent-child agent fan-out** integration pattern,
and recovers from execution errors via an **autonomous self-correction
loop** rather than durable multi-step checkpoints. These patterns
constrain the `B-REF-01` plan, subagent, and recovery findings.

## Expected Result

Before lookup, the expectation was that Devin is a cloud-only autonomous
agent with a plan-then-execute loop and that it does not advocate
multi-agent architectures. Both expectations were partially refined.

## Result

- Exit code: not-applicable (literature lookup)
- Summary: claim substantiated. Notable refinements: (1) Devin does use
  parallelism via a parent-child fan-out, despite Cognition publicly
  arguing against "multi-agent architectures"; the apparent
  contradiction dissolves when "multi-agent" means "many equal peers
  with fragmented context" (which they reject) and "fan-out" means
  "parent retains plan, children do isolated subtasks" (which they
  endorse). (2) Recovery is autonomous self-correction, not checkpoint
  replay.

### 1. Architecture: brain + devbox

From https://fast.io/resources/cognition-devin-ai-architecture/
(accessed 2026-08-12):

- **The Brain** is "a stateless reasoning coordinator residing in
  Cognition's cloud infrastructure." It evaluates codebases, generates
  step-by-step plans, translates prompts into instructions, and
  dynamically scales compute. It does **not execute code** directly.
- **The Devbox** is "a fully-featured isolated Linux container running
  in the cloud to isolate code execution." It contains a shell
  (terminal), a code editor, and a sandboxed Chromium web browser. It
  safely executes the brain's commands and streams outputs back.

This is the **strongest separation of concerns** in this matrix:
planning and execution are physically separated processes. (Claude
Code, Cursor, Codex CLI all run agent loop and tool execution in the
same process; Devin does not.)

### 2. State model

- The Brain is **stateless**; per-task state lives in the prompt and
  the running plan.
- The Devbox is **ephemeral**: "designed to be torn down once a task is
  completed or when a session expires."
- Persistent state (files, audit logs, configurations) lives in
  **external workspaces** that survive devbox teardown.

### 3. Plan mode (plan-execute-observe-replan)

From https://fast.io/resources/cognition-devin-ai-architecture/
(accessed 2026-08-12) and the Cognition first-party blog:

- Plan: Devin "analyzes the task, searches the codebase, plans its
  approach" before acting. It "builds a mental map of dependencies and
  breaks the main goal into separate execution milestones."
- Execute & Observe: the brain generates instructions for the devbox;
  the devbox runs commands and "returns the console outputs or
  directory trees to the brain."
- Replan: "As Devin progresses, it updates its plan dynamically." On
  observed compilation errors, it appends troubleshooting subtasks.

This is a **runtime planning loop**, not a user-approved artifact plan
(contrast Claude Code `V01-01` and Cursor `V03-01`). The user can
review the plan but does not gate execution on plan approval — Devin's
core promise is autonomous execution.

### 4. Subagent / delegation: Devin Fusion + parent-child fan-out

- Devin operates as a multi-agent system internally via a hybrid
  strategy called **Devin Fusion**: a primary reasoning model handles
  complex system design and coordinates with smaller, specialized
  helper models for routine operations (e.g., syntax checks).
- For large tasks, Devin uses a **parent-child agent fan-out** pattern:
  - **Fan-out:** "The parent agent retains the primary plan" while
    spawning parallel child agents, each focused on an isolated
    subtask.
  - **Integration:** "Once the child agents complete their work, the
    parent agent aggregates the changes."
  - **Conflict resolution:** if child agents produce overlapping
    modifications, the parent "functions as an integration server,
    verifying builds and instructing children to resolve merge
    conflicts before final code commits."

Cognition's public "don't build multi-agents" stance (LinkedIn post by
Ricky Ho, capturing Cognition's argument) refers to **peer
multi-agents with fragmented context**, not to parent-child fan-out.
This is an important nuance for echo-agent's `F-SUB-02` (subagent
execution modes and teams) review.

### 5. Events

- Devin does **not** publicly document a typed event stream at the
  Codex/Claude-Code level. The observable surface is the Devin web UI
  (the live devbox shell, editor, browser) plus a session log.
- This is the same gap noted for Cursor (`V03-01`).

### 6. Permissions

- Devin does **not** document a per-tool-call approval gate. Its core
  value proposition is autonomous execution within the devbox
  sandbox.
- The devbox itself is the safety boundary: it is isolated from the
  user's machine by design (cloud container, separate filesystem,
  separate browser profile). This is the **cloud-analogue of Codex's
  kernel sandbox** (`V02-01`) — isolation by environment rather than
  by syscall filter.
- Devin does not face the "local desktop assistant" threat model that
  EKO does, so its permission model is not directly transferable.

### 7. Skills / plugins

- Devin does **not** publicly document a skill/plugin system comparable
  to Claude Code's `SKILL.md` + progressive disclosure.
- The cascade of `AGENTS.md`-style files is not publicly documented for
  Devin either; first-party docs focus on session prompts and
  knowledge instructions.

### 8. Recovery: autonomous self-correction, not checkpoint replay

From https://fast.io/resources/cognition-devin-ai-architecture/
(accessed 2026-08-12):

- Devin relies on an **autonomous self-correction loop**: on execution
  errors, it "reads the terminal traceback log, pinpoints the relevant
  file in its editor, and applies a code fix," then "reruns the test
  script, continuing this cycle until the errors are resolved."
- The devbox is torn down per-task. Persistent state lives in external
  workspaces, so cross-session recovery means reattaching to the same
  workspace, not replaying a checkpoint.
- Multi-step durable checkpointing (the Temporal pattern, see `V05-01`)
  is **not** part of Devin's public model.

## Deviations

- The brain/devbox split and the fan-out pattern come primarily from
  the fast.io architecture deep dive, which is a high-quality
  secondary source. The first-party Cognition blog corroborates the
  plan-then-execute workflow but does not detail the fan-out
  mechanics.
- "Devin Fusion" is named in the secondary source; the first-party
  blog does not use this term as of the lookup date.

## Conclusion

Devin's value to this matrix is its **plan-execute-observe-replan
runtime loop** and its **parent-child fan-out with parent-owned plan**.
These patterns are the strongest contrast to Claude Code's
prompt-injected plan mode:

- **Claude Code / Cursor:** plan is a user-approved artifact, agent
  executes against the artifact.
- **Devin:** plan is a runtime structure owned by the agent, updated
  dynamically; the user supervises rather than approves.

For echo-agent this means both patterns are mature and viable; the
choice is a product decision, not a correctness decision. The
fan-out-with-parent-owned-plan pattern is directly relevant to
`F-SUB-02` and `F-TSK-03` (runtime DAG execution).

Devin's permission model (none at the tool layer; isolation by
container) is **not** transferable to EKO's local-desktop model and
should not be cited as evidence for or against EKO permission design.
