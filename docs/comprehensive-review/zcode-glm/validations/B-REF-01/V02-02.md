### A. JSONL event stream (thread / turn / item) — confirms V02-01 §5

- "`codex exec --json` ... When you enable `--json`, `stdout` becomes a JSON
  Lines (JSONL) stream so you can capture every event Codex emits while it's
  running. Event types include `thread.started`, `turn.started`,
  `turn.completed`, `turn.failed`, `item.*`, and `error`." (non-interactive
  mode doc)
- "Item types include agent messages, reasoning, command executions, file
  changes, MCP tool calls, web searches, and plan updates." (non-interactive
  mode doc)
- Verbatim sample from the doc (exact item-state transition + terminal usage):
  ```
  {"type":"thread.started","thread_id":"0199a213-81c0-7800-8aa1-bbab2a035a53"}
  {"type":"turn.started"}
  {"type":"item.started","item":{"id":"item_1","type":"command_execution","command":"bash -lc ls","status":"in_progress"}}
  {"type":"item.completed","item":{"id":"item_3","type":"agent_message","text":"Repo contains docs, sdk, and examples directories."}}
  {"type":"turn.completed","usage":{"input_tokens":24763,"cached_input_tokens":24448,"output_tokens":122,"reasoning_output_tokens":0}}
  ```
  (non-interactive mode doc)
- This confirms `V02-01`'s lifecycle sequence
  (`thread.started`→`turn.started`→`item.*`→`turn.completed`/`turn.failed`)
  and the stable per-item `id` (the same `item.id` is reused across
  `item.started`/`item.completed`).

### B. Rollout persistence + resume — corrects V02-01 §8

- Persistence is the DEFAULT: "Use `--ephemeral` when you don't want to
  persist session rollout files to disk." (non-interactive mode doc)
- **Resume is now a documented subcommand** (issue openai/codex#1991, cited
  in `V02-01` as an open "Add /resume command" request, has shipped): "If you
  need to continue a previous run (for example, a two-stage pipeline), use the
  `resume` subcommand: `codex exec \"review the change for race conditions\"`
  then `codex exec resume --last \"fix the race conditions you found\"`. You
  can also target a specific session ID with `codex exec resume
  <SESSION_ID>`." (non-interactive mode doc)
- `thread.started`'s `thread_id` is the join key between the original run and
  the resumed run.

### C. Sandbox / permission = launch-time flags — confirms V02-01 §6

- "By default, `codex exec` runs in a read-only sandbox. In automation, set
  the least permissions needed for the workflow: Allow edits: `codex exec
  --sandbox workspace-write \"<task>\"`; Allow broader access: `codex exec
  --sandbox danger-full-access \"<task>\"." (non-interactive mode doc)
- "`codex exec --full-auto` [is] a deprecated compatibility flag ... Prefer
  the explicit `--sandbox workspace-write` flag in new scripts." (non-
  interactive mode doc)
- A required-MCP failure is a hard stop, not an interactive approval: "If you
  configure an enabled MCP server with `required = true` and it fails to
  initialize, `codex exec` exits with an error instead of continuing without
  that server." (non-interactive mode doc)

### D. Output shape — confirms V02-01 §1 streaming/non-streaming split

- "`codex exec` streams progress to `stderr` and prints only the final agent
  message to `stdout`." With `--json`, stdout becomes the JSONL stream.
  Structured final output via `-o`/`--output-last-message` and
  `--output-schema`. (non-interactive mode doc)

## Deviations

None for the claims. Limits:

- The primary doc gives one sample stream and an event-type list but does NOT
  publish a full JSON Schema for every item `type` (the per-type field tables
  in `V02-01` §5 come from the secondary cheatsheet, not the primary doc).
  The primary doc confirms the *envelope*; the *per-type payload* is still
  only secondarily documented.
- The primary doc does not state whether `item.failed` exists as a distinct
  item event (the sample shows `item.started`/`item.completed` only); failure
  surfaces as `turn.failed` + `error`. `V02-01` lists `failed` as an item
  status from the cheatsheet — not contradictable from the primary doc alone.

## Conclusion

Primary-source confirmation of the Codex event-stream, sandbox, and output
models, plus one correction: **rollout resume is a shipped, documented
feature** (`codex exec resume --last` / `codex exec resume <SESSION_ID>`),
so durable trajectory-resume is no longer an industry gap. The relevant
cross-system patterns:

1. **Typed, append-only JSONL event stream** with stable per-item ids and a
   thread/turn/item envelope — strongest reference for a scriptable,
   surface-agnostic event contract (supports TUI/GUI/CLI parity).
2. **Recovery = persisted rollout (trajectory) + resume-by-ID into a new
   turn**, NOT undo of file side effects. Matches Claude Code (V01) and
   contrasts with Temporal event-sourced replay (V05).
3. **Permission = launch-time `--sandbox` flag + deprecated `--full-auto`**,
   not a runtime approval state machine. Kernel-level enforcement detail
   (Seatbelt/Landlock) is from `V02-01` and is consistent.
4. **Plan is an item type** (`plan updates`), reinforcing plan-as-data.

What this result does NOT prove: the full per-item-type schema (primary doc
shows the envelope only), and Codex's subagent/delegation model (none
documented in `codex exec` — single-threaded surface).
