## Claim

This attempt re-verifies the Temporal claim against three first-party primary
sources and offers a **different analytical conclusion** from `V05-01` on the
same underlying facts. Both agree Temporal is event-sourced durable
execution with no-replay-of-completed-activities. They diverge on
*transferability*: `V05-01` frames Temporal's pattern as "the right shape for
echo-agent's `Snapshot` design"; this attempt argues, from the same primary
docs plus the determinism requirement they imply, that **event-sourced replay
is NOT transferable to an LLM coding agent** because the LLM step is
non-deterministic, and that the coding-agent convergence on the weaker
"trajectory + resume" model is a *consequence* of that non-determinism, not
an oversight. This matters because AGENTS.md explicitly warns against over-
engineering runtime state for an interactive local agent.

## Result

- Exit code: not-applicable (reference lookup).
- Duration: not-applicable.
- Summary: facts confirmed verbatim (consistent with `V05-01`). The
  transferability conclusion differs (see Conclusion).

### A. Durable execution = crash-proof via event-sourced state reconstruction (confirms V05-01 §1–2)

- "Durable Execution is crash-proof execution. ... it virtualizes execution,
  enabling it to take place across a series of processes ... If the current
  process happens to crash, Durable Execution ensures that work transparently
  resumes in a new process. The application state is recreated in that new
  process." (durable-execution blog)
- "Temporal is an event-sourced system and each Workflow has its own event
  history. Temporal will maintain the state of the Workflow and continually
  progress each Workflow to completion regardless of any failures."
  (idempotency blog)
- Local variables are durable: "all of the variables in your application,
  including local variables, are durable. They will have the same values
  after a crash as they did before it." (durable-execution blog)

### B. Activity retry = at-least-once; idempotency required (confirms V05-01 §4, adds the key)

- "Temporal recommends that Activities be idempotent. ... Because Activities
  may be retried, these functions may be executed more than once."
  (activity-definition doc)
- "For an Activity with a Retry Policy that allows retries, Temporal
  guarantees that the Activity will be observed as completed exactly once.
  However, the Activity may be executed multiple times and may even
  partially complete more than once during this process." (activity-
  definition doc)
- Default is at-least-once; at-most-once is opt-in: "By default, Activity
  retries are unlimited, meaning 'at least once' execution ... limiting
  `maximumAttempts` to 1 ... will guarantee 'at most once' execution,
  meaning zero times is also possible." (idempotency blog)
- Idempotency key: "you can use a combination of the Workflow Run ID and the
  Activity ID as an idempotency key since this is guaranteed to be consistent
  across retry attempts but unique among Workflow Executions." (activity-
  definition doc)

### C. Replay does NOT re-execute completed Activities — and this requires determinism (confirms V05-01 §3–4, sharpens the constraint)

- "By design, completed Activities will not re-execute as part of a Workflow
  Replay. ... Activities won't record to the Event History until they return
  or produce an error. If an Activity fails to report to the server at all,
  it will be retried." (activity-definition doc)
- "During replay, activities that have already been executed are not
  re-executed. Instead Temporal simply takes activity input and output from
  its event history while continuing with Workflow progression."
  (idempotency blog)
- **The non-obvious precondition:** for replay to skip a completed Activity,
  the re-executed Workflow code must *reach the same Activity call in the
  same order with the same arguments*. Temporal enforces this by requiring
  Workflow code to be **deterministic** (no wall-clock, no RNG, no IO in
  Workflow code — all of that goes in Activities). The activity-definition
  doc states the consequence directly: "In the event of failure, the
  function begins at its initial state when retried (except when Activity
  Heartbeats are established). Therefore, an Activity Definition has no
  restrictions on the code it contains." — i.e., determinism is required of
  the *Workflow*, while *Activities* may be non-deterministic (because their
  results are cached, not recomputed, on replay).

### D. The transferability gap (the analytical divergence from V05-01)

- An LLM-driven ReAct loop is the *Workflow* analogue (the orchestrator that
  decides which tool to call next), not the *Activity* analogue (the side-
  effecting unit whose result is cached). Temporal's no-replay property
  holds because the Workflow is deterministic, so re-running it reaches the
  same Activity calls in the same order. An LLM Workflow is non-deterministic:
  the same prompt + history can yield a different tool-call sequence on a
  second run. Therefore an LLM agent **cannot** safely skip "completed"
  tools by re-running the orchestrator — the re-run might choose different
  tools, or order them differently, making the cached results mismatch.
- This is why **every coding agent in this matrix (Claude Code V01, Codex
  V02, Cursor V03, Devin V04) converges on "persist the trajectory, resume
  into a new turn," NOT "re-run the orchestrator and skip completed tools."**
  The convergence is not a collective gap; it is forced by LLM non-
  determinism. Codex's `codex exec resume` (V02-02) and Claude Code's
  `--resume` (V01-02) both restore the *conversation/trajectory* and start a
  *new* turn; neither re-runs the orchestrator over recorded tool results.
- `V05-01`'s recommendation that Temporal's no-replay-of-completed-
  activities is "the right shape for echo-agent's `Snapshot` design" is
  therefore **too strong**. The transferable parts of Temporal are: (1) the
  retry/idempotency-key pattern for *individual* tool calls (Activities), and
  (2) the at-most-once escape hatch for non-idempotent tools. The *non-*
  transferable part is event-sourced orchestrator replay.

## Deviations

None for the factual claims. One analytical caveat: the determinism
requirement is stated in Temporal's encyclopedia pages (read by `V05-01`)
rather than in the three pages read here; the activity-definition doc states
only the consequence ("function begins at its initial state when retried").
The determinism framing here is consistent with `V05-01` §3 and is standard
Temporal doctrine.

## Conclusion

Temporal is the **contrast case** that explains why the coding-agent
patterns (V01–V04) are shaped the way they are. Cross-system-relevant
patterns:

1. **Trajectory-resume (agents) vs event-sourced-replay (Temporal)** are two
   different recovery tiers, and the gap is *forced by LLM non-determinism*,
   not by oversight. echo-agent should adopt the agent tier (trajectory +
   resume), not the Temporal tier, for its orchestrator recovery.
2. **Activity retry + idempotency key IS transferable** to tool-call retry:
   "at-least-once by default, idempotent tool, key by (run-id, call-id)" is
   the mature reference for echo-agent's tool-batch execution (F-RCT-04).
3. **At-most-once via `maximumAttempts=1`** is the right escape hatch for
   non-idempotent/destructive tools — directly relevant to EKO's
   full-auto/default distinction (a destructive shell command should not be
   auto-retried).
4. **The four-timeout decomposition** (Schedule-To-Start, Schedule-To-Close,
   Start-To-Close, Heartbeat — from `V05-01` §8) is a sound reference for
   per-tool timeout granularity, independent of the replay question.

What this result does NOT prove: that echo-agent should avoid *any* snapshot
mechanism. A `Snapshot` of conversation + tool results (à la Claude Code
checkpointing, V01) for *rewind*, and a persisted trajectory for *resume*
(à la Codex, V02), are both appropriate and are NOT the Temporal replay
pattern being cautioned against here.

Findings using this report: B-REF-01-P1-05 (Temporal as contrast case —
sharpens the transferability boundary), B-REF-01-P2-05 (Activity retry +
idempotency-key as the transferable tool-retry reference), B-REF-01-P3-04
(at-most-once for destructive tools). Reconciles with `V05-01`: facts agree;
`V05-01`'s "right shape for Snapshot" framing is narrowed to the retry/
idempotency primitives only.
