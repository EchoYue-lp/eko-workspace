## Claim

Cursor's plan-then-execute model and background (Cloud) Agents constitute a
cross-system reference for (1) plan-as-editable-artifact (a saved file the
user reviews and edits before building) and (2) delegation-via-isolation
(each background agent runs in its own sandboxed VM with its own repo clone,
producing a reviewable diff/PR). Specifically: Cursor treats the plan as a
persisted document, not a runtime state; and parallelism is achieved by
spinning isolated environments, not by a shared-context multi-agent mesh.

## Expected Result

The official docs should: describe Plan Mode as producing a reviewable,
editable plan the user approves before execution; state where plans are saved;
and describe Background Agents as isolated cloud VMs with their own repo
clone, sandboxed from the local machine, producing reviewable artifacts.

## Result

- Exit code: not-applicable (reference lookup).
- Duration: not-applicable.
- Summary: claim supported. Cursor's docs are terse but explicit on both
  points. Notably, the plan is described as a saved document and the workflow
  explicitly recommends reverting + re-planning over in-place fixing.

### A. Plan Mode = research, then a reviewable/editable plan, then build

- "Plan Mode creates detailed implementation plans before writing any code.
  Agent researches your codebase, asks clarifying questions, and generates a
  reviewable plan you can edit before building." (plan-mode doc)
- The plan is a persisted artifact, saved to a default location and movable
  into the workspace: "Plans are saved by default in your home directory.
  Click 'Save to workspace' to move it to your workspace for future
  reference, team sharing, and documentation." (plan-mode doc)
- The recommended failure-recovery flow is revert-and-replan, not patch-
  forward: "Sometimes Agent builds something that doesn't match what you
  wanted. Instead of trying to fix it through follow-up prompts, go back to
  the plan. Revert the changes, refine the plan to be more specific about what
  you need, and run it again. This is often faster than fixing an in-progress
  agent, and produces cleaner results." (plan-mode doc)
- Plan/Build separation is the product surface: "For quick changes or tasks
  you've done many times before, jumping straight to Agent mode is fine."
  (plan-mode doc)

### B. Background (Cloud) Agents = isolated VM per agent, own repo, reviewable diff

- "Background agents are coding agents that typically run for a very long
  time. In practice, that means moving a task from your local device to the
  cloud, where the agent takes it from start to finish without interruption
  and reports back with proof that the work is done. In Cursor, we call these
  Cloud Agents." (background-agents doc)
- Each agent gets its own full, isolated environment: "Each Cloud Agent runs
  on its own dedicated virtual machine with a full development environment:
  your repository, dependencies, secrets, and network access. It plans the
  task, edits code, runs commands, and tests its work over minutes or hours.
  Because it runs remotely, you can close your laptop and check the result
  later." (background-agents doc)
- Isolation is a security/containment boundary: "The VM is sandboxed and
  isolated from your local machine, so the agent's commands never touch your
  environment. Cursor wraps each run in secret redaction, network policies,
  and credential management, and you control which repositories, secrets, and
  network access an environment gets." (background-agents doc)
- Output is reviewable artifacts, not in-place edits: "Background agents
  produce artifacts to demo their changes. As an agent works, it tests its
  changes and attaches videos, screenshots, and logs to the pull request, so
  you can validate the work without checking out the branch. You can also take
  control of the agent's remote desktop to use the software it built and make
  edits yourself." (background-agents doc)
- Entry points span surfaces: "In Cursor, select Cloud by the agent input; On
  the web or mobile, go to cursor.com/agents; In Slack, GitHub, or Linear,
  mention @Cursor. You can also run them on a schedule or from events with
  Automations." (background-agents doc)

## Deviations

None for the claims. Limits:

- Cursor's docs are deliberately high-level and do NOT document the internal
  plan representation (whether it is a structured object or a markdown file),
  the event/state model, or the permission/sandbox flags at the same
  granularity as Codex/Claude Code. The *behavior* (reviewable editable plan,
  isolated VM per agent) is documented; the *mechanism* is not.
- The docs do not state how many background agents can run concurrently from a
  single user (a secondary guide claims "up to 8"; this is NOT in the primary
  doc and is not relied on here).
- The docs do not describe a subagent/delegation API within a single session;
  parallelism is at the *Cloud Agent* (whole-VM) granularity, not an in-
  process subagent tool.

## Conclusion

Cursor corroborates two cross-system patterns directly relevant to this
review:

1. **Plan is an editable, persistable artifact reviewed before execution** —
   the same convergence as Claude Code (V01) and Codex's `plan updates` item
   (V02). Cursor additionally makes the plan *shareable* (Save to workspace
   for team/docs), reinforcing plan-as-document over plan-as-state.
2. **Parallelism = isolated environments, not shared-context multi-agent** —
   each Cloud Agent is a full VM with its own repo clone, producing a
   reviewable PR. This is the same isolation-first delegation pattern as
   Devin's managed Devins (V04) and Claude Code's `isolation: worktree`
   subagents (V01), and it is the *opposite* of a shared-context parallel
   subagent mesh (which Cognition's "Don't Build Multi-Agents" essay argues
   against — see V04).
3. **Recovery from a wrong build = revert + replan**, not patch-forward. This
   is a product-level confirmation that plans are re-runnable artifacts and
   side effects are disposable via VCS.

What this result does NOT prove: Cursor's internal state/event model (not
documented), the exact concurrency limit (secondary source only), and any
in-process subagent tool (none documented — delegation is at VM granularity).

Findings using this report: B-REF-01-P1-01 (plan-as-artifact convergence),
B-REF-01-P1-03 (isolation-first delegation convergence), B-REF-01-P3-02
(revert-and-replan recovery).
