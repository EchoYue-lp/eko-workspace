## Result

- Duration: not-applicable.
- Summary: all five claims supported by primary documentation. One correction

### A. Plan mode is tool-mediated, produces an editable plan, and is NOT restored on resume

- Permission modes are part of session state, with explicit exceptions:
  "`plan` and `bypassPermissions` are never restored; bypassing permissions
  must be enabled again at launch." (sessions doc)
- `EnterPlanMode` and `ExitPlanMode` are *tools* the model calls; they are
  listed among tools filtered from subagents ("`EnterPlanMode`" and
  "`ExitPlanMode`, unless the subagent's `permissionMode` is `plan`"). Because
  transitions occur via tool calls, plan mode is a tool/prompt-driven mode,
  not a harness-internal state machine the model cannot affect. (sub-agents
  doc)
- A built-in `Plan` subagent serves plan-mode research: "A research agent used
  during plan mode to gather context before presenting a plan ... When you're
  in plan mode and Claude needs to understand your codebase, it delegates
  research to the `Plan` subagent so that exploration output stays in a
  separate context window while the main conversation remains read-only."
  (sub-agents doc)

### B. Sessions are JSONL transcript files, no database

- "By default, transcripts are stored as JSONL at
  `~/.claude/projects/<project>/<session-id>.jsonl`, where `<project>` is your
  working directory path with non-alphanumeric characters replaced by `-`.
  Each line is a JSON object for a message, tool use, or metadata entry. The
  entry format is internal to Claude Code and changes between versions ..."
  (sessions doc)
- Subagent transcripts are independent JSONL files:
  "find IDs in the transcript files at
  `~/.claude/projects/{project}/{sessionId}/subagents/`. Each transcript is
  stored as `agent-{agentId}.jsonl`. Subagent transcripts persist
  independently of the main conversation ... when the main conversation
  compacts, subagent transcripts are unaffected. They're stored in separate
  files." (sub-agents doc)

### C. Checkpointing = per-session file snapshots, explicitly best-effort

- "checkpointing automatically captures the state of your code before each
  user prompt ... Claude Code keeps file snapshots for the 100 most recent
  checkpoints in a session ... Claude Code saves checkpoints with the
  conversation, so you can still run `/rewind` after you resume a session ...
  deletes checkpoints along with sessions after 30 days." (checkpointing doc)
- Documented gaps (quoted exactly):
  - "Checkpointing does not track files modified by bash commands."
  - "A subagent makes edits with Claude's file editing tools, but Claude Code
    usually doesn't capture those edits in your session's checkpoints."
  - "External changes not tracked."
  - "Symlinked and hard-linked paths not restored."
  - "Not a replacement for version control." (checkpointing doc)
- The rewind menu separates code restoration from conversation restoration
  ("Restore code and conversation" / "Restore conversation" / "Restore code")
  and from compaction ("Summarize from here" / "Summarize up to here"), so the
  file-snapshot store and the conversation store are distinct.

### D. Subagents: isolated context, tool filtering, output scanning, configurable concurrency/depth — and recursion IS allowed (corrects V01-01)

- "Each subagent runs in its own context window with a custom system prompt,
  specific tool access, and independent permissions." (sub-agents doc)
- "As of v2.1.198, subagents run in the background by default." Background
  subagents keep a reduced built-in tool set: "`Read, Grep, Glob, Bash,
  PowerShell, Edit, Write, NotebookEdit, WebFetch, WebSearch, TodoWrite,
  Skill, ToolSearch, EnterWorktree, ExitWorktree, Monitor, TaskStop,
  SendMessage, and Artifact`". (sub-agents doc)
- Concurrency and depth are configurable caps: "By default, when 20
  subagents are running in a session, spawning another with the Agent tool
  fails with `Concurrent subagent limit reached` ...
  `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`" and "a subagent can spawn
  subagents of its own, up to three layers below the main conversation ...
  `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`". (sub-agents doc)
- **Correction to `V01-01` §4**: `V01-01` asserts "Subagents generally cannot
  spawn further subagents." The primary doc states the opposite: recursion is
  allowed and configurable, defaulting to 3 layers. Only at the depth limit
  is the `Agent` tool withheld: "At the depth limit, Claude Code withholds the
  `Agent` tool from every subagent except a fork." (sub-agents doc)
- Worktree isolation is opt-in per subagent: "To give the subagent an isolated
  copy of the repository instead, set `isolation: worktree`." (sub-agents doc)
- Output is scanned as untrusted: "Claude Code scans each subagent's final
  report before Claude reads it ... The scan never removes or rewords
  anything; it makes two kinds of change ... Backslash insertion ... Marker
  line ...". (sub-agents doc)

### E. Hooks are deterministic lifecycle gates with exit-code-2 blocking

- "Hooks are user-defined shell commands, HTTP endpoints, or LLM prompts that
  execute automatically at specific points in Claude Code's lifecycle." Five
  handler types: `command`, `http`, `mcp_tool`, `prompt`, `agent`. (hooks doc)
- Three cadences: "once per session: `SessionStart` and `SessionEnd`; once
  per turn: `UserPromptSubmit`, `Stop`, and `StopFailure`; on every tool call
  inside the agentic loop: `PreToolUse` and `PostToolUse`". (hooks doc)
- "Exit 2 means a blocking error. On events that can block, exit 2 blocks
  whether or not you print JSON: even a JSON `permissionDecision` of
  `\"allow\"` can't override it." (hooks doc)
- Hooks fire inside subagents with identifying fields: "the input carries the
  `agent_id` and `agent_type` common input fields that identify the
  subagent." (hooks doc)

## Deviations

None for the claims. Two limits recorded:

- The official docs describe plan-mode *behavior* (read-only main
  conversation, `Plan` subagent, transitions via `EnterPlanMode`/`ExitPlanMode`
  tools) but do NOT name the *internal implementation mechanism*. The
  characterization "prompt injection, not runtime enforcement" (cited in the
  project's AGENTS.md) is consistent with tool mediation but is not a verbatim
  official statement. The reverse-engineered system-prompts repo (source 5) is
  consistent with a prompt/tool implementation; treated as supporting only.
- Docs are versioned to v2.1.x releases; behavior reflects the latest
  documented version on the access date.

## Conclusion

The primary documentation substantiates all five reference claims and corrects
`V01-01`'s subagent-recursion error. Cross-system-relevant patterns:

1. **Plan is an artifact + tool-mediated mode, not a runtime approval state
   machine**, and the `plan` mode is explicitly non-durable across resume.
   Strongest external corroboration of AGENTS.md's rule that plan should be a
   versioned artifact driven by prompt/permission, not a run-state column.
2. **File-based JSONL persistence for both main and subagent transcripts**,
   no database. Supports the project's "echo-agent-cli does not need SQLite"
   positioning.
3. **Checkpointing is deliberately best-effort file snapshots** with
   documented gaps (bash, subagent, external, symlinks) — not a transactional
   recovery log.
4. **Subagent coordination via isolation + configurable caps + output
   scanning**, with bounded recursion (default 3) and bounded concurrency
   (default 20). No global scheduler state machine.
5. **Hooks are deterministic gates** with a single blocking signal (exit 2),
   firing inside subagents.

What this result does NOT prove: the exact binary implementation of plan mode
(no source access), and Claude Code's *skills* mechanism (only touched via the
`skills` subagent field and `Skill` tool — documented but under-sampled here;
`V01-01` covers skills more fully from secondary sources).

B-REF-01-P2-01 (file-based persistence convergence), B-REF-01-P2-02
(checkpoint best-effort model), B-REF-01-P2-03 (subagent recursion correction).
