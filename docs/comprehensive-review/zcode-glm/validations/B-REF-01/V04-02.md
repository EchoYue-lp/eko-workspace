### A. Managed Devins = coordinator + isolated-VM children (confirms V04-01 §4, primary)

- "Devin can break down large tasks and delegate them to a team of managed
  Devins working in parallel, each running in its own isolated VM. The
  coordinator session scopes the work, monitors progress, resolves conflicts,
  and compiles results." (Devin docs)
- Each child is a *full* Devin in its own VM: "Each managed Devin is a full
  Devin, running in its own isolated virtual machine with its own terminal,
  browser, and development environment. Each one can independently run shell
  commands, execute tests, and verify its own changes before reporting back.
  Each has its own session link, so you can inspect its work or message it
  directly." (Cognition blog 2026-03-19)
- The product rationale is exactly the context-accumulation problem from the
  "don't build multi-agents" essay: "when one agent tries to handle too many
  things in a single session, context accumulates, focus degrades, and the
  quality of each subtask suffers. Each managed Devin gets a clean slate, a
  narrow focus, its own shell, and its own test runner." (Cognition blog
  2026-03-19)

### B. Coordinator capabilities (primary, exact list)

- "What the coordinator can do: Spin up managed Devins — launch child
  sessions with specific prompts, playbooks, tags, and ACU limits; Message
  child sessions — send follow-up instructions or clarifications to running
  sessions; Monitor ACU consumption — track how much compute each child
  session is using; Put child sessions to sleep or terminate them — pause or
  stop sessions that are stuck or no longer needed; Schedule messages to
  itself — set reminders to check back on long-running child sessions."
  (Devin docs)
- The coordinator learns from children's full trajectories: "Devin can also
  read the full trajectories of its managed Devins to understand what worked,
  what didn't and where they got stuck, and use that to improve how it breaks
  down the next task." (Cognition blog 2026-03-19)
- **Approval gate on fan-out (nuance V04-01 missed):** "Devin analyzes your
  request and proposes the sessions for your approval before launching them."
  (Devin docs) So fan-out is not fully autonomous — the proposed session plan
  is user-approved, then execution within each child is autonomous.

### C. Cognition's architectural principles (first-party, supersedes V04-01's LinkedIn source)

The "Don't Build Multi-Agents" essay (Walden Yan, 2025-06-12) states two
principles verbatim:

- "Principle 1 — Share context, and share full agent traces, not just
  individual messages."
- "Principle 2 — Actions carry implicit decisions, and conflicting decisions
  carry bad results."
- Recommended default: "The simplest way to follow the principles is to just
  use a single-threaded linear agent ... Here, the context is continuous."
- For very long tasks: a dedicated compression model "whose key purpose is to
  compress a history of actions & conversation into key details, events, and
  decisions" (Cognition reports fine-tuning one).

### D. Reconciliation: "don't build multi-agents" vs Managed Devins (first-party)

The apparent contradiction dissolves on a precise reading:

- The essay (2025-06) rejects **peer multi-agents that split one coherent
  artifact** (the Flappy-Bird example: background + bird built in parallel
  with shared-but-incomplete context → inconsistent results). Its thesis is
  that *live shared context* across parallel workers on one task is fragile.
- Managed Devins (2026-03) delegate **independent work packages** (per-file,
  per-module, per-service), each with a *clean slate, narrow focus, own
  verification*. Children do NOT share live context; the coordinator reads
  full trajectories *after* they finish and compiles.
- This preserves Principle 2: each child's implicit decisions are scoped to
  its own independent package, so there are no conflicting cross-child
  decisions on a shared artifact. The essay's own Claude-Code example notes
  Claude Code subagents (as of 2025-06) "never does work in parallel with the
  subtask agent" — Devin's later managed Devins relax this *only* for
  independent packages with post-hoc trajectory reading, not for shared live
  context.

### E. Other surfaces (confirms V04-01)

- Skills/plugins: Devin's docs describe **playbooks** (reusable procedures
  derived from sessions) and a **knowledge base**, both manageable via the
  Devin MCP server. There is no `SKILL.md`-style filesystem progressive-
  disclosure system; extension is via MCP tools and playbooks. (Devin docs)
- Permissions: "These advanced capabilities require the `UseDevinExpert`
  permission, which is included in the default `org_member` and `org_admin`
  roles." Permission is RBAC over *capabilities*, not per-tool-call gating.
  The devbox/VM isolation is the safety boundary (consistent with `V04-01`
  §6). (Devin docs)
- Events: not documented at the Codex typed-stream level; the observable
  surface is the session UI + the MCP session-management tools ("Inspect any
  session's full event timeline — list event summaries, fetch detailed event
  contents, or search across events by text"). (Devin docs)

## Conclusion

Devin's first-party-primary contribution to the matrix:

1. **Isolation-first delegation is the dominant parallelism pattern.** Each
   delegated unit runs in its own VM with a clean slate, own verification,
   and own session link. The coordinator owns the plan and compiles results
   from full trajectories. This matches Cursor Cloud Agents (V03) and Claude
   Code `isolation: worktree` subagents (V01), and is the convergent
   counter-pattern to a shared-context parallel subagent mesh.
2. **Plan approval and execution approval are separable.** Devin approves the
   *proposed session plan* before launch, then each child executes
   autonomously. This refines the plan-as-artifact pattern (V01/V03): the
   *decomposition* is an approved artifact, while *per-step* execution inside
   a child is agent-driven.
3. **Cognition's two principles (share full traces; actions carry implicit
   decisions)** are the cleanest first-party articulation of *why*
   shared-context parallel agents are fragile. This directly informs when
   EKO should vs should not fan out subagents.
4. **Recovery = autonomous self-correction loop + external persistent
   workspace**, not checkpoint replay (consistent with V04-01 §8).

What this result does NOT prove: Devin's internal brain/devbox process
boundary (secondary only), its typed event schema (undocumented), and any
transferable permission model (RBAC-over-capabilities + VM isolation is
cloud-specific, not applicable to EKO's local-desktop model per AGENTS.md).

Findings using this report: B-REF-01-P1-03 (isolation-first delegation
convergence, now primary-sourced), B-REF-01-P1-04 (Cognition's two
principles as the cross-system anti-fragmentation rule), B-REF-01-P3-03
(plan-approval vs execution-approval separability).
