## Claim

Temporal (temporal.io) implements **event-sourced durable workflow
execution** in which the **event history is the durable checkpoint**,
workflow code is **deterministic** so it can be replayed after a crash,
activities are **never re-executed on replay** (their results are read
from history), and execution is bounded by **four orthogonal timeout
types** and a configurable retry policy. These patterns constrain the
`B-REF-01` state, event, and recovery findings, and provide the
strongest reference for echo-agent's `Snapshot`/resume work in
`F-RCT-05` and the DAG work in `F-TSK-03`.

## Result

- Exit code: not-applicable (literature lookup)
- Summary: claim substantiated across event sourcing, replay, timeouts,

  with a fully worked-out durable execution model.

### 1. Architecture: event-sourced durable workflow

From https://docs.temporal.io/encyclopedia/event-history/event-history-python
(accessed 2026-08-12):

- The Temporal Service records "a detailed log of Events that occur
  during the lifecycle of a Workflow Execution" — these are **History
  Events**, persisted to the database.
- Workers run workflow code and emit **Commands** to the service; the
  service records the corresponding **Events** in response.
- Commands enumerated in the docs include: `ScheduleActivityTask`,
  `StartTimer`, `CompleteWorkflowExecution`. (Additional commands
  exist; these are the canonical examples.)

This is a **server-authoritative event-sourcing model**: the service
owns the event log; workers are stateless executors that reconstruct
state by replaying the log.

### 2. State model: event history is the state

From https://blog.corneliadavis.com/temporal-what-does-preserving-state-really-mean-ebdca256526f
(accessed 2026-08-12):

- Temporal preserves "enough state to recreate the complete state of
  the workflow at any point." The full event history **is** the
  durable checkpoint; there is no separate snapshot mechanism
  (internal caching/optimizations aside).
- Workflow state is reconstructed by replaying the event history
  through the deterministic workflow code.

This is **different from all four agent systems** in this matrix
(Claude Code, Codex CLI, Cursor, Devin), none of which expose an
event-sourced workflow-state model. The implication for echo-agent is
that **Temporal is the reference for durable execution**, while the
agent systems are references for **interactive loop shape**.

### 3. Determinism: required for replay

From https://docs.temporal.io/encyclopedia/event-history/event-history-python
(accessed 2026-08-12):

- A workflow is deterministic iff "every execution of its Workflow
  Definition produces the same Commands in the same sequence given the
  same input."
- "When there's a mismatch between the expected sequence of Commands …
  Replay will be unable to continue." Non-deterministic workflows
  cause repeated workflow task failures.

The Medium "Replay Bugs Hide in Plain Sight" article
(https://medium.com/@Nexumo_/temporal-replay-bugs-hide-in-plain-sight-7e436f4b3ea4,
accessed 2026-08-12) enumerates **seven sources of nondeterminism**
that silently break replay:

1. Random number generation inside workflow code.
2. Reading wall-clock time inside workflow code (must use
   `Workflow.UtcNow`-equivalent).
3. Network/IO inside workflow code (must be in activities).
4. Iterating non-deterministic data structures.
5. Using language-native concurrency primitives instead of
   workflow-native ones.
6. Workflow code changes that alter the command sequence (versioning
   required).
7. Thread/global state leaks.

For echo-agent, the determinism requirement is a **direct constraint on
`F-RCT-05`** (steer, interrupt, snapshot, resume): any
`Snapshot`-based resume design must produce the same sequence of
tool-call side effects when replayed.

### 4. Activities: not re-executed on replay

From https://blog.corneliadavis.com/temporal-what-does-preserving-state-really-mean-ebdca256526f
(accessed 2026-08-12):

- "On replay, activities must not be re-executed — instead, results
  from previous activity executions (stored in history) are reused."

This is the **critical safety property** of durable execution:
side-effecting operations (API calls, file writes, shell commands) are
run once and their results are cached in the event log. On crash
recovery, the workflow code is re-executed, but when it reaches the
point of a previous activity invocation, the recorded result is
returned instead of re-running the activity.

For echo-agent's `F-RCT-05`, this is the rule that **completed tools
must not replay their side effects**. The corresponding invariant is
in `F-RCT-05`'s task card: "Can a running or interrupted Agent resume
without replaying completed side effects or losing canonical context?"

### 5. Events: history events are publicly exposed

From https://github.com/temporalio/temporal/blob/main/docs/architecture/history-service.md
(accessed 2026-08-12):

- "History Events are a publicly-exposed part of Temporal's internal
  event-sourcing model." The term "event" in Temporal means a
  **Workflow History Event** — the atomic unit of durable execution
  and recovery.

This is the **typed event surface** that agent systems generally lack.
Temporal's event types are well-defined and documented per command
class (`ActivityTaskScheduled`, `ActivityTaskStarted`,
`ActivityTaskCompleted`, `ActivityTaskFailed`, `TimerStarted`,
`TimerFired`, `WorkflowExecutionCompleted`, etc.).

### 6. Permissions

- Not applicable to Temporal in the agent-system sense. Temporal does
  not gate tool calls; it gates **worker identity** via mTLS and
  namespace-level ACLs. This is a server-to-server security model,
  not a local-execution model.
- Listed for completeness only; should not be cited as evidence for
  echo-agent permission design.

### 7. Skills / plugins

- Not applicable. Temporal has no skill/plugin concept; extensibility
  is via worker code in any supported language.

### 8. Recovery: replay + timeouts + retry

**Recovery via replay:**

- After a crash, a worker re-runs the workflow code from the
  beginning. The Temporal service feeds it the recorded history
  events. When the workflow code issues a command that matches the
  next recorded event, the service returns the recorded result
  instead of executing it. When the workflow catches up to the
  last recorded event, execution goes live.
- Source: https://www.linkedin.com/posts/ram-chavali_workflow-execution-engines-like-temporal-activity-7423606775981129728-iCN2
  and https://keithtenzer.com/temporal/temporal_time_travelling_replay/
  (accessed 2026-08-12).

**Four orthogonal timeout types** (from
https://temporal.io/blog/activity-timeouts, accessed 2026-08-12):

| Timeout               | Bounds                                                         |
|-----------------------|----------------------------------------------------------------|
| `Schedule-To-Start`   | Time a task waits in the queue before a worker picks it up.    |
| `Schedule-To-Close`   | Total time from scheduling to completion, including retries.   |
| `Start-To-Close`      | Time an individual activity execution takes once started.      |
| `Heartbeat`           | Periodic liveness signal for long-running activities.          |

**Retry policy** (from https://docs.temporal.io/encyclopedia/retry-policies,
accessed 2026-08-12): configurable per-activity and per-workflow;
includes initial interval, backoff coefficient, maximum interval,
maximum attempts, and a non-retryable error allowlist.

For echo-agent, the **four-timeout decomposition** is directly
applicable to `F-RCT-04` (tool batch execution: validation, concurrency,
timeout, cancellation, partial output, retry) and to `F-REL-01`
(retry, budgets, circuit breakers).

## Conclusion

Temporal is the **canonical reference for durable execution** in this
matrix. Its constraints on echo-agent are:

- `F-RCT-05` (steer/interrupt/snapshot/resume): the
  event-history-as-checkpoint pattern, with **no-replay-of-completed-
  activities** as the critical safety property, is the right shape for
  echo-agent's `Snapshot` design.
- `F-TSK-03` (runtime DAG execution): the four-timeout decomposition
  is the right granularity for DAG execution safety.
- `F-REL-01` (retry, budgets, circuit breakers): the retry-policy
  fields (initial interval, backoff coefficient, max interval, max
  attempts, non-retryable allowlist) are a tested design.
- `X-STA-01` (persistence, recovery, identity continuity): the
  identity-stability requirement (workflow ID + run ID + event ID)
  is a strong reference for echo-agent's identity model.

The determinism requirement is the strongest single constraint: any
`Snapshot`-based resume that produces a different sequence of tool-call
side effects on replay is a bug, by definition, in the Temporal model.
