## Claim

Across Claude Code, OpenAI Codex CLI, Cursor, Devin, and Temporal,
independent implementations converge on a small set of patterns strong
enough to constrain the architecture, state, Plan, Subagent, event,
permission, skill/plugin, and recovery findings of this review. This
report enumerates those convergences with the supporting sources and
records where the systems diverge.

## Method

Synthesis from `V01-01` (Claude Code), `V02-01` (Codex CLI), `V03-01`
(Cursor), `V04-01` (Devin), and `V05-01` (Temporal). Every claim below
cites at least the validation report that supports it; reports in turn
cite primary URLs accessed 2026-08-12.

For each topic, this report uses the following convergence scoring:

- **Strong convergence** — three or more independent implementations
  agree, with at least two of them being first-party or
  reverse-engineering-confirmed.
- **Weak convergence** — two implementations agree, or three agree but
  only via single-source secondary reports.
- **Divergence** — implementations visibly disagree.
- **No public pattern** — the implementations do not document a
  behavior at this level.

## Result

- Exit code: not-applicable (synthesis)
- Summary: strong convergence on plan-as-artifact (3 of 4 agent

### Strong-1: ReAct + tools + subagent delegation

Four of four agent systems (Claude Code `V01-01`, Codex CLI `V02-01`,
Cursor `V03-01`, Devin `V04-01`) implement an LLM-driven ReAct-style
loop that selects tools, observes results, and continues until a turn
completes. Three of four (Claude Code, Cursor, Devin) add an explicit
subagent/delegation mechanism; Codex does not expose one in-process.

**Constraint for echo-agent:** the React + tools + subagent shape is
the consensus. `F-RCT-02` (non-streaming ReAct loop), `F-RCT-03`
(streaming ReAct event flow), and `F-SUB-01/02` (subagent) should be
evaluated against this consensus, not against hypothetical alternative
topologies.

### Strong-2: Plan is an artifact, not a runtime approval state machine

Three of four agent systems (Claude Code `V01-01`, Cursor `V03-01`,
and Devin `V04-01` in the weaker "agent-owned runtime plan" form) do
**not** model plan approval as a runtime state machine.

- **Claude Code** (https://lucumr.pocoo.org/2025/12/17/what-is-plan-mode/):
  plan is a Markdown file; exiting plan mode is a tool the agent calls
  that reads the file and surfaces it for user approval; tools are not
  actually rendered read-only — the behavior is prompt-reinforced.
- **Cursor** (https://cursor.com/blog/plan-mode): plan is a Markdown
  file artifact with an inline interactive editor; "you're happy with
  the plan" gates execution as a UI flow.
- **Devin** (https://fast.io/resources/cognition-devin-ai-architecture/):
  plan is a runtime structure owned by the agent, updated dynamically
  via plan-execute-observe-replan. The user supervises but does not
  gate execution on plan approval.

Only Devin deviates from "artifact plan" toward "runtime plan," and
even then the plan is **not a runtime approval state machine** — it is
a working data structure, not a state graph.

**Constraint for echo-agent:** the historical 13-state design rejected
in `AGENTS.md` is confirmed as diverging from all observed mature
patterns. `F-TSK-01` (canonical task model) must keep the plan as an
artifact (or, at most, a versioned artifact — see `Weak-1` below).
`A-TSK-02` (EKO task authoring tools) must not introduce a parallel
plan-CRUD with its own state machine.

### Strong-3: Per-tool-call permission gating with named modes

All four agent systems implement some form of per-tool-call permission
gating with named, user-selectable modes:

- **Claude Code** (`V01-01`): `default`, `acceptEdits`, `plan`,
  `dontAsk`, `bypassPermissions`. Gate applies to **every** tool call;
  no carve-out for "direct user actions."
- **Codex CLI** (`V02-01`): sandbox modes (`read-only`,
  `workspace-write`, `danger-full-access`) × approval policies
  (`never`, `on-failure`, `on-request`). Enforcement at kernel level
  (Seatbelt / Landlock+seccomp).
- **Cursor** (`V03-01`): step limit (25 tool calls) + safe-operation
  auto-approve + destructive-operation human-confirm + action undoing.
  Different mechanism, same goal.
- **Devin** (`V04-01`): no tool-layer gate; isolation by container.

**Constraint for echo-agent:** the mature consensus is that the
permission gate applies to **automated agent execution**, and the
specific mechanism is a product decision (Claude Code's named modes
vs Codex's sandbox+approval matrix vs Cursor's step-limit+undo). For
EKO's local-desktop threat model (per `AGENTS.md`), the relevant
constraint is: do **not** apply the agent-permission gate to direct
user interactions (terminal, file picker, MCP configuration) — none
of the mature systems make this conflation, and Claude Code
explicitly does not have such a carve-out because it does not have
direct user interactions. Devin and Cursor handle the difference by
isolation (container/VM), not by gate carve-out.

### Strong-4: Durable execution = event history + replay (Temporal alone)

Temporal (`V05-01`) is the only system in this matrix with a fully
worked-out durable execution model. Its core invariants are:

1. **Event history is the durable checkpoint** — no separate snapshot.
2. **Workflow code must be deterministic** for replay to work.
3. **Activities are not re-executed on replay** — results are read
   from history.
4. **Four orthogonal timeout types** (Schedule-To-Start,
   Schedule-To-Close, Start-To-Close, Heartbeat).
5. **Configurable retry policy** (initial interval, backoff,
   max interval, max attempts, non-retryable allowlist).

None of the four agent systems has a comparable model. Codex CLI
explicitly lists durable multi-step checkpointing as a known gap
(`V02-01`, openai/codex#1991, openai/codex#28218).

**Constraint for echo-agent:** the Temporal model is the **only**
available reference for `F-RCT-05` (steer/interrupt/snapshot/resume)
and `X-STA-01` (persistence, recovery, identity continuity). The
critical safety property — **completed tools must not replay their
side effects** — is precisely Temporal's no-replay-of-activities rule.
echo-agent's `Snapshot` design is **ahead of the agent-system norm**
and should be evaluated against Temporal's correctness bar, not
against Claude Code or Codex's gap.

### Weak-1: Plan-as-versioned-artifact (Cursor single-source)

Cursor (`V03-01`, single-source) describes the plan as a Markdown
file the user can edit inline. Claude Code (`V01-01`) describes it as
a file in a `plans/` folder the agent writes to. Neither publicly
documents a **versioned** plan artifact (revision history).

**Constraint for echo-agent:** `F-TSK-01`'s task card asks "Is
`TaskSpec + TaskExecution + TaskStatus` the sole generic dynamic task
model with coherent revisioned `task_create/update/list` semantics?"
The revisioned-graph model is **more structured than any observed
mature pattern**. This is acceptable — it is a framework capability
not a product feature — but `F-TSK-01` should be reviewed against
this baseline so the revision model is not over-built.

### Weak-2: Typed event schema (Codex + Temporal)

Only Codex CLI (`V02-01`) and Temporal (`V05-01`) publicly document a
typed event schema. Claude Code exposes a hooks lifecycle (V01-01)
but not a per-item event stream; Cursor and Devin do not document
one.

**Constraint for echo-agent:** Codex's per-item lifecycle
(`item.started` / `item.in_progress` / `item.completed` / `item.failed`
with a stable `item.id` reused across updates) is the **strongest
single reference** for `X-EVT-01` (event lifecycle conformance) and
`F-RCT-03` (streaming ReAct event flow). Temporal's event ID + run ID
model is the reference for `X-STA-01` identity stability.

### Weak-3: Cascaded AGENTS/CLAUDE/rules markdown

Three of four agent systems (Claude Code `V01-01`, Codex CLI
`V02-01`, Cursor `V03-01`) implement cascaded markdown instruction
files (`CLAUDE.md`, `AGENTS.md`, `.cursor/rules/*.mdc`). Devin does
not publicly document this.

**Constraint for echo-agent:** cascaded-project-instructions is the
consensus; echo-agent's instruction provider (`A-MEM-01`) should
conform to this pattern.

### Weak-4: SKILL.md + progressive disclosure (Claude Code only)

Only Claude Code (`V01-01`) publicly documents a skill system with
three-stage progressive disclosure (frontmatter → body → bundled
references). Codex CLI, Cursor, and Devin do not document an
equivalent.

**Constraint for echo-agent:** the progressive-disclosure pattern is
a **single-vendor design**, not a cross-vendor consensus. It is still
a reasonable reference for `F-SKL-01` (skill loading and execution)
because it is well-documented and production-deployed, but it should
not be treated as the only valid shape.

### Divergence-1: User-approval gating of the plan

Claude Code and Cursor require explicit user approval of the plan
before execution begins. Devin does not — its value proposition is
autonomous execution.

**Constraint for echo-agent:** both patterns are mature and viable.
For EKO's "local personal superintelligence assistant" positioning
(`AGENTS.md`), the Claude Code / Cursor pattern (explicit approval)
is more aligned with the "user-in-control" framing; the Devin pattern
(autonomous) is more aligned with background/headless execution
(`A-SRF-04`, `F-OPS-01`). Both can coexist behind a per-run mode
flag, which is itself consistent with Claude Code's `--permission-mode
plan` flag.

### Divergence-2: Concurrency primitive

- **Claude Code** (`V01-01`): single agent per session; subagents via
  Task tool with optional `isolation: "worktree"`.
- **Codex CLI** (`V02-01`): single agent per process; parallelism via
  multiple processes.
- **Cursor** (`V03-01`): up to eight parallel agents in git worktrees;
  background agents in dedicated VMs.
- **Devin** (`V04-01`): parent-child fan-out with parent-owned plan;
  devbox isolation.
- **Temporal** (`V05-01`): child workflows + activities, server-scheduled.

**Constraint for echo-agent:** git worktree isolation is the
**strongest cross-vendor pattern** for file-editing concurrency
(Claude Code, Cursor, Devin-via-devbox all converge on isolated
working directories). This directly constrains `A-TSK-05` (worktree,
file ownership, merge policy) and `F-SUB-02` (subagent execution
modes and teams). The parent-child fan-out with parent-owned plan
(Devin) is the strongest pattern for `F-TSK-03` (runtime DAG
execution) and matches echo-agent's `TaskRun → PlanTask → SubagentRun`
model.

### Out-of-scope or undocumented

The following topics are **not publicly documented** at the level this
review requires, across multiple systems:

- **Claude Code internal state-machine** beyond enter/exit plan mode
  (only the lightweight mode flag is documented).
- **Cursor event schema** (none documented; editor UI is the surface).
- **Devin event schema and skill/plugin system** (none documented).
- **Claude Code, Codex CLI, Cursor, Devin durable multi-step
  checkpoint** (none has a Temporal-class model; Codex has open
  feature requests).

When a downstream task needs to make a claim in one of these areas,
it must either cite the single best-documented system or mark the
claim as under-evidenced.

## Conclusion

The strongest constraints for echo-agent, in priority order:

1. **Plan is an artifact or a runtime working data structure, never a
   multi-state approval state machine.** (`AGENTS.md` historical
   lesson is fully validated.)
2. **Durable execution = event history + replay + no-replay-of-
   completed-side-effects.** Temporal is the only mature reference;
   Codex CLI confirms the rest of the industry has not solved this.
3. **Per-tool-call permission gating applies to automated agent
   execution, not to direct user interaction.** For EKO's local
   threat model, this means: do not gate the user's own terminal,
   file picker, or MCP configuration by the agent permission mode.
4. **Git worktree isolation is the cross-vendor primitive for
   file-editing concurrency** (Claude Code, Cursor, Devin all
   converge here).
5. **Typed per-item event lifecycle with stable identity** (Codex
   `item.id`, Temporal event ID) is the right shape for streaming
   and persistence.

These five constraints will be cited from the `B-REF-01` task report
by downstream tasks `F-TSK-01`, `F-HITL-01`, `F-SUB-02`, `F-SKL-01`,
`F-RCT-03`, `F-RCT-05`, `F-OPS-01`, `F-TSK-03`, `X-EVT-01`,
`X-STA-01`, `X-AUT-01`, and `A-TSK-05`.
