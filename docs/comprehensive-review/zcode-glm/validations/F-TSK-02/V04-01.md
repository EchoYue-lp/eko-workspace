## Claim

Structural DAG validation is status-independent: it operates on the
pre-execution task shape (`&[TaskSpec]`) and does not consult any runtime
status, schedule state, or execution result as an input to the structural
rules. A plan can be validated before any task is scheduled or executed,
which is the property that makes `PlanSpec` a reviewable artifact rather
than a runtime approval gate.

## Method

Read the three public entry points of `PlanValidator` and confirm the
structural rules depend only on ids + dependency edges, not on
`TaskStatus`/schedule/executed-state; confirm `validate_task_specs`
accepts the pre-execution shape.

```text
Read echo-agent/echo-orchestration/src/planning/validator.rs
  (PlanValidator at 14, validate at 50, validate_task_snapshot at 184,
   validate_task_specs at 210)
```

## Expected Result

- `validate_task_specs(tasks: &[TaskSpec]) -> Result` at `validator.rs:210`
  — accepts the pre-execution task shape.
- The structural rules (cycle, missing-node, self-dependency — see V02)
  read only task ids and `Dependency` edges; none reads `TaskStatus`,
  schedule state, attempt/evidence/artifact fields, or any execution
  output.
- A `PlanSpec` can be converted to `TaskSpec[]` via `to_task_specs()`
  (`plan_spec.rs:359`) and fully validated without any task having run.

## Result

- Exit code: not-applicable (static inspection)
- Duration: n/a
- Summary:
  - **Pre-execution entry point.** `validate_task_specs(tasks: &[TaskSpec])`
    (`validator.rs:210`) takes the pre-execution shape directly. A caller
    can validate a plan immediately after `PlanSpec::to_task_specs()`
    (`plan_spec.rs:359`), before any task is scheduled.
  - **Status-independent rules.** The structural checks (V02) operate on
    task ids and `Dependency` (`plan_spec.rs:229`) / `DependencyType` (243)
    edges only. `TaskStatus`, `TaskAttempt`, `Evidence`, `Artifact`, and
    other execution-time fields are not inputs to the structural rules.
  - **Plan-artifact path.** `PlanValidator::validate(plan: &PlanSpec)`
    (`validator.rs:50`) consumes the versioned `PlanSpec` artifact (18) and
    produces a `ValidationReport` — no scheduling, no execution, no
    approval-state transition. This matches B-REF-01 C1: the plan is an
    artifact, not a runtime approval state machine.
  - **Snapshot re-validation.** `validate_task_snapshot(tasks: &[Task])`
    (`validator.rs:184`) accepts the runtime `Task` shape for re-validation
    of in-flight graphs, but the structural rules it runs are the same as
    the pre-execution path; runtime status is not consulted as an input.
- Log/artifact: none

## Deviations

None. Structural validation runs on `TaskSpec[]` before execution and does
not consult runtime status as an input. The plan-artifact path
(`validate(&PlanSpec)`) produces a `ValidationReport` without scheduling or
executing anything.

## Conclusion

on `&[TaskSpec]`. This supports the task report's positive conclusion that
