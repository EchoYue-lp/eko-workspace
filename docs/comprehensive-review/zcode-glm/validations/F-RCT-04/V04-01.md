## Claim

`ToolFailureCategory::PartialSideEffect` is handled conservatively and
correctly: it maps to `ToolRecoveryAction::VerifyThenRetry` and is
**never** automatically retried by `ToolManager` (because
`allows_automatic_retry()` returns false for this category). The
`from_error` classifier rewrites `Unavailable`/`Transient`/`Permanent`
to `PartialSideEffect` when the tool `may_have_side_effects` (i.e. is
not `ReadOnly`), so write/destructive tool failures are conservatively
treated as potentially-partial. The `VerifyThenRetry` action is
advisory metadata: the framework does not run a verification gate, nor
does it surface the failure taxonomy in the `tool_result` content the
model sees — the "verify" half is expected to happen via prompt-driven
model behaviour, not framework enforcement. Partial side effects are
not specially detected by the batch layer; they flow through as
ordinary tool errors.

## Expected Result

1. `PartialSideEffect` maps to `VerifyThenRetry` in the default
   `ToolFailure::new` constructor.
2. `allows_automatic_retry()` returns `false` for `PartialSideEffect`,
   even with `.retryable()` or `.with_idempotency_key(..)`.
3. `from_error` rewrites `Unavailable`/`Transient`/`Permanent` to
   `PartialSideEffect` when `may_have_side_effects` is true, and sets
   `side_effect = Possible`.
4. `may_have_side_effects` is computed as `risk_level() != ReadOnly` at
   both the pipeline `ExecuteStage` and the `execute_tool_with_policy`
   error mapper.
5. The `ToolManager` retry loop never retries a `PartialSideEffect`
   failure (neither the non-streaming nor the streaming variant).
6. The batch layer (`run_tools`) treats a `PartialSideEffect` failure
   identically to any other tool error: emit `ToolError` event, push
   `[Error] {message}` to context, save checkpoint, continue. No
   special partial-side-effect detection or verification gate runs.
7. The `ToolFailure` taxonomy (category, recovery, side_effect,
   postcondition) is attached to the `AgentEvent::ToolError` event but
   does NOT appear in the `Message::tool_result` content pushed to the
   conversation history — the model does not see the structured
   failure facts.

## Result

- Exit code: not-applicable (static inspection) + cargo confirmation.
- Summary: the claim is **supported**. Detailed evidence:

**(1) Mapping.**
`ToolFailure::new` (`echo-core/mod.rs:92-102`):
```rust
let recovery = match category {
    ToolFailureCategory::InvalidArguments => ToolRecoveryAction::CorrectArguments,
    ToolFailureCategory::Unavailable => ToolRecoveryAction::RestoreThenRetry,
    ToolFailureCategory::Timeout | ToolFailureCategory::PartialSideEffect => {
        ToolRecoveryAction::VerifyThenRetry
    }
    ToolFailureCategory::Transient => ToolRecoveryAction::Retry,
    ToolFailureCategory::Cancelled | ToolFailureCategory::Permanent => {
        ToolRecoveryAction::Stop
    }
};
```
`PartialSideEffect` → `VerifyThenRetry`. The `side_effect` field is
set to `Possible` for `PartialSideEffect` (`:103-107`).

**(2) Non-retryable.**
`allows_automatic_retry` (`echo-core/mod.rs:154-162`):
```rust
pub fn allows_automatic_retry(&self) -> bool {
    matches!(
        self.category,
        ToolFailureCategory::Unavailable
            | ToolFailureCategory::Timeout
            | ToolFailureCategory::Transient
    ) && self.recovery == ToolRecoveryAction::Retry
        && (self.side_effect == ToolSideEffect::None || self.idempotency_key.is_some())
}
```
`PartialSideEffect` is absent from the `matches!` list, so this always
returns `false` for that category — regardless of `.retryable()`,
`.with_idempotency_key(..)`, or any other builder. The test
`permanent_and_partial_failures_cannot_be_made_automatically_retryable`
(`echo-core/mod.rs:1201-1210`) asserts exactly this:
```rust
let partial = ToolFailure::new(ToolFailureCategory::PartialSideEffect)
    .with_idempotency_key("call-1")
    .retryable();
assert!(!partial.allows_automatic_retry());
```
This test passes (confirmed by cargo run).

**(3) Classifier.**
`from_error` (`echo-core/mod.rs:165-179`) defines a closure:
```rust
let possible_side_effect = |mut failure: Self| {
    if may_have_side_effects {
        if matches!(
            failure.category,
            ToolFailureCategory::Unavailable
                | ToolFailureCategory::Transient
                | ToolFailureCategory::Permanent
        ) {
            failure.category = ToolFailureCategory::PartialSideEffect;
        }
        return failure.with_side_effect(ToolSideEffect::Possible);
    }
    failure
};
```
So when a tool `may_have_side_effects`, any `Unavailable`/`Transient`/
`Permanent` classification is *upgraded* to `PartialSideEffect` and the
`side_effect` field is set to `Possible`. This is the key conservative
behaviour: a write tool that hits a transient IO error is treated as
"the write may have partially landed."

Note: `Timeout` is *not* rewritten by this closure — it passes through
`possible_side_effect` but the `matches!` guard excludes it. However,
`with_side_effect(Possible)` is still applied (`:176`), and
`with_side_effect` (`:135-141`) itself upgrades recovery to
`VerifyThenRetry` when `side_effect != None && idempotency_key.is_none()`.
So a timeout on a side-effecting tool ends up with
`category=Timeout`, `side_effect=Possible`, `recovery=VerifyThenRetry`
— and `allows_automatic_retry` returns false because
`side_effect != None` and no idempotency key. Correct.

**(4) may_have_side_effects source.**
Two computation sites:
- `ExecuteStage` (`pipeline.rs:572-576`): after execution, when the
  result is an `Err`, it constructs `ToolFailure::from_error(&e,
  may_have_side_effects)` where `may_have_side_effects = tool_manager
  .get_tool(name).is_none_or(|t| t.risk_level() != ReadOnly)`.
- `execute_tool_with_policy` error mapper (`snapshot.rs:1264-1271`):
  on a pipeline-level `Err`, the same expression computes
  `may_have_side_effects` for `ToolFailure::from_error`.

So an unknown tool (`get_tool` returns `None` → `is_none_or` returns
`true`) is treated as side-effecting — conservative. A `ReadOnly` tool
is treated as non-side-effecting.

**(5) ToolManager retry gate.**
Non-streaming loop (`echo-execution/tools.rs:700-724`):
```rust
match result {
    Ok(result) if result.success => return Ok(result),
    Ok(result) if attempt < max_retries
        && result.failure.as_ref().is_some_and(ToolFailure::allows_automatic_retry) => {
        // record retry_after_ms, continue loop
    }
    Ok(result) => return Ok(result),  // failure not retryable → return
    Err(error) if attempt < max_retries => {
        let failure = ToolFailure::from_error(&error, !is_read);
        if failure.allows_automatic_retry() { last_err = Some(error); }
        else { return Err(error); }
    }
    Err(error) => return Err(error),
}
```
A `PartialSideEffect` failure (whether from the tool's own
`result.failure` or from `from_error`) fails the
`allows_automatic_retry` gate and is returned immediately — no retry.
The streaming variant (`:877-902`) has the same gate with an
additional `!output_forwarded` condition (once output has been
streamed to the caller, no retry is attempted regardless — the
`streaming_output_prevents_automatic_retry` test confirms this).

Tests confirm:
- `retries_only_explicit_transient_failures` — only `Transient` with
  `Retry` recovery is retried; `PartialSideEffect` is not (passes).
- `invalid_arguments_are_not_retried` — `InvalidArguments` is not
  retried (passes; same gate mechanism).
- `streaming_output_prevents_automatic_retry` — output-forwarded
  failures are not retried (passes).

**(6) Batch-layer handling — no special partial-side-effect path.**
The concurrent error arm (`tools.rs:241-263`):
```rust
Err(error) => {
    yield_event_or!(tx, AgentEvent::ToolError {
        call_id: id.clone(), name: fname.clone(),
        error: error.error.to_string(),
        failure: error.failure.clone(),  // ← ToolFailure attached to event
    }, IterOutcome::Abandoned);
    context.lock().await.push(Message::tool_result(
        id, fname.clone(),
        format!("[Error] {}", error.error),  // ← only error string in history
    ));
    snap.save_runtime_checkpoint(context, Some(format!("Tool error: {fname}"))).await;
}
```
The serial error arm (`:397-416`) is identical. There is:
- No `match error.failure.category` dispatch.
- No `PartialSideEffect`-specific branch.
- No verification/postcondition check.
- No `if failure.side_effect != None { .. special handling .. }`.

Every tool error — whether `InvalidArguments`, `Timeout`,
`PartialSideEffect`, or `Permanent` — follows the same path: emit
`ToolError`, push `[Error] {message}`, checkpoint, continue. The
`failure` struct is attached to the *event* (for UI/trace/eval
consumers) but does not influence batch control flow.

**(7) Model visibility gap.**
The `Message::tool_result` content pushed to context is
`format!("[Error] {}", error.error)` — only the error message string.
The `ToolFailure` taxonomy (`category`, `recovery`, `side_effect`,
`postcondition`) is **not** included. The model on the next iteration
sees `[Error] {message}` but has no signal that:
- The category was `PartialSideEffect` (a write may have partially
  applied).
- The recovery action was `VerifyThenRetry` (it should verify before
  retrying).
- A `postcondition` string was set (a tool-specific check to run).

This is the basis of F-RCT-04-P3-02: the taxonomy is richer than what
the model sees. The framework's safety rests entirely on
`allows_automatic_retry() == false` (no blind retry) — which is
correct — but the "verify" half of `VerifyThenRetry` is not surfaced to
the agent.

## Deviations

1. `with_side_effect` (`echo-core/mod.rs:135-141`) has a subtle
   secondary effect: if `side_effect != None` and there is no
   idempotency key, it overwrites `recovery` to `VerifyThenRetry`
   regardless of the original category's default recovery. So a tool
   that explicitly calls `.with_side_effect(Possible)` on a
   `Transient` failure ends up with `recovery=VerifyThenRetry` (not
   `Retry`), and `allows_automatic_retry` then returns false (because
   `recovery != Retry`). This is correct and conservative but means
   the `category → recovery` table in `ToolFailure::new` is not the
   final word — `with_side_effect` can override it.
2. The `postcondition` field (`echo-core/mod.rs:148-151`) is
   serializable and settable via `.with_postcondition(..)`, but nothing
   in `run_tools`, the pipeline, or the ToolManager reads it. It is
   pure metadata. Whether any builtin tool populates it is deferred to
   F-EXT-02 (builtin tools inventory).

## Conclusion

The claim is **supported**. `PartialSideEffect` is classified and
gated conservatively: it maps to `VerifyThenRetry`, is never
automatically retried, and side-effecting tools' failures are upgraded
to `PartialSideEffect` by the `from_error` classifier. The batch layer
handles partial-side-effect failures identically to any other tool
error — no special detection or verification gate — which is consistent
with the prompt-driven design (AGENTS.md: verification is the model's
job, not the framework's). The gap is that the failure taxonomy is not
surfaced in the `tool_result` content the model sees, so the model has
no signal that a side effect may have partially occurred. This is the
basis of F-RCT-04-P3-02 (advisory metadata, not surfaced to the agent).
The conservative non-retry behaviour is correct and well-tested.

## Follow-Up

F-RCT-04-P3-02 proposes documenting `VerifyThenRetry` as advisory and
optionally surfacing `failure.category`/`side_effect` in the error
`tool_result` content so the model can act on it. F-EXT-02 should
confirm which builtin tools report `PartialSideEffect` with a
`postcondition` in practice.
