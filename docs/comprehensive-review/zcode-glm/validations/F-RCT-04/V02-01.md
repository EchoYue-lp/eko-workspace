## Claim

When multiple tools run concurrently in one batch, their results are
emitted as `ToolResult`/`ToolError` events and inserted into the
conversation history in **completion order** (the order in which the
underlying futures resolve), not in call/submission order. This makes
the event stream and the history tail nondeterministic across runs of
the same batch. Pairing remains correct (by `tool_call_id`) and the
request is API-legal, but the ordering is not reproducible.

## Method

Read-only static trace of the concurrent sub-batch loop, anchored at:

```text
echo-agent/src/agent/react/run/phases/tools.rs:142-160  (FuturesUnordered construction)

```

Confirmed the call side is deterministic (index-sorted) and the result
side is completion-ordered by reading the `FuturesUnordered::next()`
contract and the push site. Cross-checked that no buffering/reordering
layer sits between `futs.next()` and the `context.lock().await.push(..)`.

## Expected Result

1. The assistant message's `tool_calls` list is in ascending streaming-
   index order (deterministic) — calls are submitted in this order.
2. The concurrent futures are polled via `FuturesUnordered`, which
   yields results in completion order.
3. Each result is pushed to `context` immediately upon completion, with
   no deferral or re-sort.
4. Therefore, for a batch of calls `[call-0, call-1, call-2]` with
   overlapping latencies, the `tool_result` messages appear in the
   history in whatever order the tools finished — `call-2` may precede
   `call-0`, and the order differs across runs.
5. The `ToolResult`/`ToolError` events on the `tx` channel follow the
   same completion order (they are emitted in the same `futs.next()`
   arm, immediately before the context push).

## Result

- Exit code: not-applicable (static inspection).
- Summary: the claim is **supported**. Evidence:

**(1) Deterministic call side.**
`build_tool_calls_from_map` (`processor.rs:141-142`) sorts indices
ascending. The `msg_tool_calls` vector and the `steps` vector are both
built in this sorted order. The `assistant_with_tools(msg_tc)` message
(`tools.rs:104`) therefore carries `tool_calls` in index order. The
LLM/model sees a deterministic call sequence.

**(2) Completion-ordered result side.**
The concurrent loop (`tools.rs:142-160`) pushes all tool-execution
futures into a `FuturesUnordered`:
```rust
let mut futs = FuturesUnordered::new();
for (id, name, args) in conc {
    let snapshot = snapshot.clone();
    let event_tx = stream_tx.clone();
    futs.push(
        async move {
            // ... parse params ...
            let result = snapshot
                .execute_tool_with_policy(id.clone(), &name, &params, &args, Some(event_tx))
                .await;
            (id, name, result)
        }
        .instrument(info_span!("tool")),
    );
}
```
`FuturesUnordered` is documented (futures crate) to yield items in
completion order, not insertion order.

The select arm that consumes completions (`tools.rs:207-265`):
```rust
Some((id, fname, result)) = futs.next(), if !futs.is_empty() => {
    // ... drain stream_rx ...
    match result {
        Ok(output) => {
            yield_event_or!(tx, AgentEvent::ToolResult { call_id: id.clone(), .. }, ..);
            context.lock().await.push(Message::tool_result(id, fname.clone(), output.clone()));
            // ... final_answer verify ...
        }
        Err(error) => {
            yield_event_or!(tx, AgentEvent::ToolError { call_id: id.clone(), .. }, ..);
            context.lock().await.push(Message::tool_result(id, fname.clone(), format!("[Error] {}", error.error)));
            // ... checkpoint ...
        }
    }
}
```
The `yield_event_or!` and `context.lock().await.push(..)` happen
**immediately** in the completion arm — there is no buffering into a
`HashMap<call_id, result>` for later ordered replay, and no re-sort by
original index. The `tokio::select!` is `biased` (`:197`), but `biased`
only fixes the *priority* order of branch polling (top-to-bottom); it
does not change which `futs.next()` value is ready first.

**(3) Consequence — nondeterministic history tail.**
For a batch of three concurrent tools `[call-0, call-1, call-2]` with
latencies that overlap under system load, the `ContextManager` message
tail after the batch is:
```
[assistant_with_tools([call-0, call-1, call-2]),
 tool_result(<whichever finished first>),
 tool_result(<whichever finished second>),
 tool_result(<whichever finished third>)]
```
The order of the last three depends on tokio's scheduling, tool
latency, I/O contention, and host load. Two runs of the same prompt +
tools + model can produce different `tool_result` orderings, and
therefore different inputs to the next LLM request.

**(4) API legality.**
`Message::tool_result` (`llm/types.rs:421-430`) sets
`tool_call_id: Some(tool_call_id)`. Both OpenAI and Anthropic match
tool results to tool calls by this id (not by position), so the request
is accepted regardless of result order. No HTTP-400 risk from ordering.

**(5) Event stream is also completion-ordered.**
The `AgentEvent::ToolResult` / `ToolError` events are emitted in the
same `futs.next()` arm, immediately before the context push. A
streaming consumer (TUI/GUI) therefore sees tool results appear in
completion order too. This is desirable for latency-to-first-event
(the user sees the fastest tool's result immediately) but is the
source of the nondeterminism relative to the call order.

nondeterminism is unguarded.

## Deviations

1. The serial sub-batch (`tools.rs:303-424`) is deterministically
   ordered — it iterates `serial` in submission order and pushes each
   result before starting the next. The nondeterminism is specific to
   the concurrent path. If all tools in a batch are serial (e.g. all
   need approval), ordering is deterministic.
2. `biased` in the `tokio::select!` (`tools.rs:197`) ensures that once
   `cancellation_observed` is set, the cancellation-grace branch takes
   priority over result processing. This is deterministic w.r.t.
   cancellation handling but does not affect the completion-ordering of
   results during normal operation.

## Conclusion

The claim is **supported**. Concurrent tool results are emitted and
pushed to history in completion order via `FuturesUnordered::next()`,
making the event stream and conversation-history tail nondeterministic
across runs of the same batch. Pairing is correct (id-keyed) and the
request is API-legal, so this is not a correctness defect — it is a
reproducibility characteristic. The finding feeds F-RCT-04-P3-01, which
proposes buffer-and-order as the deterministic alternative.
