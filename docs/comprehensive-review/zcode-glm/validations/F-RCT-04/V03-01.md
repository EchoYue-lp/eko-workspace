## Claim

The tool batch has two distinct deadline mechanisms. (a) **Per-tool
timeout**: `ToolManager` wraps each `tool.execute()` in
`tokio::time::timeout(timeout_ms)` unless the tool
`manages_own_timeout()`; on expiry the tool result becomes a retryable
`ToolError::Timeout`. (b) **Per-batch timeout** (concurrent path only):
`compute_concurrent_tool_batch_timeout` scales the per-tool budget by
retry attempts and concurrency waves; on expiry the batch forwards
`Err(Timeout)` and returns Abandoned immediately. **Cancellation** is
a third, separate signal: on `CancellationToken::cancel`, the batch
enters a 5-second grace period during which in-flight tools may still
complete; only after the grace (or once all complete) does the batch
emit `ToolBatchEnd`, save a checkpoint, and return Abandoned. The
batch-timeout path is asymmetric: it skips both the `ToolBatchEnd`
emission and the checkpoint save that every cancellation and
normal-completion path performs.

## Expected Result

1. Two timeout layers exist and are distinct: per-tool (ToolManager)
   and per-batch (concurrent select arm).
2. Per-tool timeout produces a retryable `ToolError::Timeout` that
   flows through the retry loop; if not retryable, it becomes a
   `ToolResult` failure.
3. Per-batch timeout fires only on the concurrent path; the serial
   path has no batch timer.
4. `compute_concurrent_tool_batch_timeout` returns `None` (disabling
   the batch timer) when `timeout_ms == 0` or when any concurrent tool
   is `exempt_from_batch_timeout`.
5. Cancellation sets `cancellation_observed` and resets a 5-second
   grace timer; tools completing during grace are processed normally;
   after grace, the batch emits `ToolBatchEnd`, saves a checkpoint, and
   returns Abandoned.
6. Timeout does NOT enter a grace period — it forwards the error and
   returns Abandoned immediately.
7. The timeout arm is the only concurrent-batch terminal path that
   does not emit `ToolBatchEnd` and does not save a checkpoint.

## Result

- Exit code: not-applicable (static inspection) + cargo confirmation.
- Summary: the claim is **supported**. Detailed evidence:

**(1)+(2) Per-tool timeout in ToolManager.**
`execute_tool_inner` (`echo-execution/tools.rs:686-695`):
```rust
let result = if self.config.timeout_ms > 0 && !tool.manages_own_timeout() {
    match tokio::time::timeout(
        Duration::from_millis(self.config.timeout_ms),
        tool.execute_with_context(parameters.clone(), ctx),
    ).await {
        Ok(r) => r,
        Err(_) => Err(ToolError::Timeout(tool_name.to_string()).into()),
    }
} else {
    tool.execute_with_context(parameters.clone(), ctx).await
};
```
On timeout expiry, `ToolError::Timeout` is produced. The retry loop
(`:700-724`) then calls `ToolFailure::from_error(&error, !is_read)`
which classifies `ToolError::Timeout` as `ToolFailureCategory::Timeout`
with `retryable()` set (`echo-core/mod.rs:189-191`), and
`allows_automatic_retry()` returns true for `Timeout` with `Retry`
recovery and no side effect. So a per-tool timeout is retried (up to
`max_retries`) and, if still failing, returned as a `ToolResult` /
`Err(ToolCallFailure)` to the batch layer. The streaming variant
(`execute_tool_stream_with_context`, `:863-875`) applies the same
per-attempt timeout to the whole stream lifetime.

Tests confirm: `internally_timed_tool_bypasses_ordinary_execution_timeout`
and `internally_timed_tool_stream_bypasses_ordinary_execution_timeout`
pass — verifying `manages_own_timeout() == true` (which defaults to
`exempt_from_batch_timeout()`, `echo-core/mod.rs:827-829`) opts out of
the per-tool timeout.

**(3)+(4) Per-batch timeout — concurrent only.**
The concurrent sub-batch computes the batch timer (`tools.rs:167-175`):
```rust
let bt = if has_timeout_exempt_tool {
    None
} else {
    super::super::retry::compute_concurrent_tool_batch_timeout(
        &snap.config.tool_execution, tool_count, mc,
    )
};
```
`compute_concurrent_tool_batch_timeout` (`retry.rs:70-109`) returns
`None` if `tool_count == 0 || config.timeout_ms == 0`. Otherwise it
computes `per_wave_budget_ms = timeout_ms * attempts_per_tool +
retry_delay_total`, multiplies by `waves = ceil(tool_count /
max_concurrency)`, and adds `250ms * waves` grace. The test
`test_compute_concurrent_tool_batch_timeout_scales_by_waves`
(`retry.rs:117-133`) confirms the formula:
`timeout_ms=1000, retries=2, delay=200, concurrency=2, count=5` →
`Some((1000*3 + (200+400)) * 3 + 750)` ms. The
`test_compute_concurrent_tool_batch_timeout_disabled_when_per_tool_timeout_is_zero`
test confirms `timeout_ms == 0` returns `None`.

The serial sub-batch (`tools.rs:303-424`) has **no** batch-level
timer — each serial tool is bounded only by the per-tool
`ToolManager` timeout. The serial path's `tokio::select!` (`:326-358`)
has only: result-ready, cancellation-grace, stream-receive, and
cancel-token branches. No timeout branch.

**(5) Cancellation grace.**
On `cancel_token.cancelled().await` firing (`tools.rs:278-283`):
```rust
_ = &mut cancel, if !cancellation_observed => {
    cancellation_observed = true;
    cancellation_grace.as_mut().reset(
        tokio::time::Instant::now() + TOOL_CANCELLATION_GRACE_PERIOD,
    );
}
```
`TOOL_CANCELLATION_GRACE_PERIOD` is `Duration::from_secs(5)` (`:22`).
The `cancellation_grace` sleep starts at `Duration::ZERO` (`:190`) and
is reset to 5 s when cancellation is observed. During the grace
period, the `futs.next()` arm (`:207`) continues to process completing
tools normally — they get their `ToolResult`/`ToolError` events and
`tool_result` messages. Only when the grace elapses
(`:196-206`):
```rust
_ = &mut cancellation_grace, if cancellation_observed => {
    tracing::warn!(grace_ms = ..., "tool batch cancellation grace period elapsed");
    snap.save_runtime_checkpoint(context, Some("Tool batch cancelled".to_string())).await;
    yield_final_event_or!(tx, AgentEvent::ToolBatchEnd, IterOutcome::Abandoned);
    return Ok(IterOutcome::Abandoned);
}
```
Both `ToolBatchEnd` and checkpoint are present. The post-loop check
(`:295-300`) handles the case where all futures complete within the
grace — it also emits `ToolBatchEnd` + checkpoint.

The test `cancellation_drains_running_tool_before_abandoning_turn`
(`stream_channel.rs:2041`) confirms the grace: a `DelayedTerminalTool`
is allowed to finish and set its `finished` flag after `cancel.cancel()`,
and the test asserts `finished.load(Acquire)` is true. This proves
the grace period lets in-flight tools complete.

**(6) Timeout — no grace.**
The timeout arm (`tools.rs:284-292`):
```rust
_ = &mut timeout, if !cancellation_observed => {
    try_send_or!(
        tx,
        Err(ReactError::from(crate::error::ToolError::Timeout("batch timeout".into()))),
        IterOutcome::Abandoned
    )
}
```
`try_send_or!` (`stream_macros.rs:65-75`) always takes the `Err` path
(the value is constructed as `Err(..)`):
```rust
match $fallible {
    Ok(v) => v,
    Err(e) => {
        let _ = $tx.try_send(Err(e.into()));
        return Ok($bail);
    }
}
```
So: the error is forwarded to `tx` via `try_send` (non-blocking; may
silently drop if buffer `Full`), and the function immediately returns
`Ok(IterOutcome::Abandoned)`. The remaining `futs` are dropped,
cancelling in-flight tool futures. No grace period. No
`ToolBatchEnd`. No checkpoint.

**(7) Asymmetry — the defect.**
Enumerating every `ToolBatchEnd` emit site in `run_tools`:

| Line | Path | Checkpoint? |
|---|---|---|
| `:204` | concurrent — cancel-grace elapsed | yes (`:203`) |
| `:298` | concurrent — post-loop cancel-observed | yes (`:296`) |
| `:311` | serial — pre-iteration cancel check | yes (`:309`) |
| `:337` | serial — cancel-grace elapsed | yes (`:336`) |
| `:421` | serial — post-exec cancel-observed | yes (`:419`) |
| `:430` | normal completion | yes (`:429`) |

The timeout arm at `:284-292` is conspicuously absent from this table.
It is the only terminal exit from the concurrent batch that returns
`Abandoned` without emitting `ToolBatchEnd` and without calling
`save_runtime_checkpoint`. `grep -n "AgentEvent::ToolBatchEnd"
phases/tools.rs` confirms exactly the 6 sites above — the timeout arm
does not appear.

## Deviations

1. The serial sub-batch has no batch-level timeout. A serial tool that
   hangs beyond its per-tool timeout (because `timeout_ms == 0` or
   `manages_own_timeout() == true`) has no outer batch protection. This
   is by design (serial tools are either approval-gated or
   parallelism-opt-out, and the per-tool timeout is the configured
   bound), but it means the two sub-batches have different deadline
   surfaces.
2. `try_send_or!` uses `try_send` (non-async) for the error forward.
   Under a `Full` channel buffer, the `Err(Timeout)` event is silently
   dropped (`let _ = $tx.try_send(Err(e.into()))`) and the function
   still returns `Abandoned`. In that case the caller sees `Abandoned`
   → `Ok(())` with no error event at all — the timeout signal is lost.
   This compounds F-RCT-04-P2-01: not only is `ToolBatchEnd` missing,
   the error itself may not be delivered.

## Conclusion

The claim is **supported**. Two distinct timeout layers exist
(per-tool in `ToolManager`, per-batch in the concurrent select arm);
cancellation is a third mechanism with a 5-second grace. The
batch-timeout arm (`tools.rs:284-292`) is asymmetric with every other
terminal path: it does not emit `ToolBatchEnd` and does not save a
checkpoint, breaking the event-bracket contract and the
checkpoint-durability contract that the cancellation and
normal-completion paths establish. This finding is the basis of
F-RCT-04-P2-01. No test currently exercises the batch-timeout terminal
path, which is why the asymmetry has gone undetected.

## Follow-Up

F-RCT-04-P2-01 proposes the fix (mirror the cancellation-arm cleanup
sequence in the timeout arm) and the regression test (drive a
concurrent batch past the computed timeout; assert `ToolBatchEnd` and
checkpoint).
