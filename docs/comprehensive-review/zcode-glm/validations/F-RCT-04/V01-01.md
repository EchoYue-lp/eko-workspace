## Claim

Every tool call issued in one iteration's batch has a matching
`tool_result` inserted into the conversation history before the loop
continues, the batch is split into serial vs concurrent sub-batches by
a policy predicate, and the per-call `execute_tool_with_policy` routes
through the 16-stage `ToolExecutionPipeline`. Pairing is by
`tool_call_id`, not by position.

## Method

Read-only static trace of the batch construction, split, execution, and
result-insertion paths, anchored at:

```text
echo-agent/src/agent/react/run/phases/tools.rs:50-443   (run_tools — batch orchestrator)
echo-agent/src/agent/react/run/phases/tools.rs:24-38    (requires_sequential_execution)
echo-agent/src/agent/react/run/processor.rs:138-183     (build_tool_calls_from_map)

echo-agent/echo-execution/src/tools.rs:606-728          (ToolManager::execute_tool_inner)
```

Verified the pairing by following every tool-result push site and
confirming each carries the call's original `id`. Verified the split by
reading `requires_sequential_execution` and both sub-batch loops.
Verified pipeline reachability by following
`execute_tool_with_policy` → `pipeline.run` → `ExecuteStage` →
`ToolManager`.

## Expected Result

1. `build_tool_calls_from_map` produces a deterministic, index-sorted
   list of `(id, name, args)` triples; unparseable calls are dropped
   symmetrically from both the assistant message and the steps list.
2. The assistant message (`assistant_with_tools`) carries exactly the
   calls that will be executed; if all calls were dropped, a text
   fallback prevents an HTTP-400 from the provider.
3. `requires_sequential_execution` routes a call to serial iff the tool
   opts out of parallelism OR (under `human-loop`) needs approval.
4. Both the concurrent and serial paths push exactly one
   `Message::tool_result(id, name, output)` per executed call — success
   and error alike — using the call's original `id`.
5. `execute_tool_with_policy` constructs a `ToolExecutionContext` and
   runs `default_pipeline()` (16 stages); the `ExecuteStage` delegates
   to `ToolManager::execute_tool_with_context` or the streaming variant.
6. No second live batch orchestrator exists.

## Result

- Exit code: not-applicable (static inspection) + cargo confirmation.
- Summary: the claim is **supported**. Detailed findings:

**(1) Deterministic call construction.**
`build_tool_calls_from_map` (`processor.rs:141-142`):
```rust
let mut sorted_indices: Vec<u32> = tool_call_map.keys().cloned().collect();
sorted_indices.sort();
```
Indices are the streaming `delta_tool_calls[].index` values accumulated
in `process_stream_chunk` (`processor.rs:64-83`). The sort is ascending
and deterministic. For each index, `parse_tool_args` (`processor.rs:104-135`)
attempts JSON parse with a trailing-junk repair loop (up to 8 chars,
handling DeepSeek fake-stream artifacts). On success, the call is added
to both `msg_tool_calls` (for the assistant message) and `steps` (for
execution). On failure (`processor.rs:165-178`), the call is dropped
from **both** lists — the comment explicitly states this is critical to
avoid a half tool_call with no matching tool_result. The repaired
canonical args are echoed back to the provider.

**(2) Assistant-message consistency.**
`tools.rs:101-113`: if `msg_tc.is_empty()` (all calls dropped), the code
falls back to `Message::assistant("(流式工具调用参数解析失败,已跳过;请重新发起工具调用)")`
— a text-bearing assistant message. The comment (`:96-100`) explains
this prevents the HTTP-400 "content or tool_calls must be set" rejection.
When `msg_tc` is non-empty, `assistant_with_tools(msg_tc)` is used, with
`content_buffer` promoted into `content` if present.

**(3) Split predicate.**
`requires_sequential_execution` (`tools.rs:24-38`):
```rust
let tool_disallows_parallel_execution = snap.tools.tool_manager
    .get_tool(tool_name)
    .is_some_and(|tool| !tool.value().allows_parallel_batch_execution());
#[cfg(feature = "human-loop")]
{ tool_disallows_parallel_execution || snap.tool_needs_approval(tool_name).await }
#[cfg(not(feature = "human-loop"))]
{ tool_disallows_parallel_execution }
```
The split loop (`tools.rs:115-126`) partitions `steps` into `serial`
and `concurrent` by this predicate. Default `allows_parallel_batch_execution()`
is `true` (`echo-core/mod.rs:816-818`), so most tools are concurrent
unless they opt out or need approval.

**(4) Result pairing — every push uses the call's `id`.**
Four push sites, covering all four (path × outcome) combinations:

| Path | Success push | Error push |
|---|---|---|
| Concurrent | `tools.rs:226-230` `Message::tool_result(id, fname, output)` | `tools.rs:252-256` `Message::tool_result(id, fname, "[Error] {error}")` |
| Serial | `tools.rs:382-386` `Message::tool_result(id, fname, truncated)` | `tools.rs:408-412` `Message::tool_result(id, fname, "[Error] {error}")` |

`Message::tool_result` (`llm/types.rs:421-430`) sets
`tool_call_id: Some(tool_call_id)` and `role: Role::Tool`. The `id`
flows from the original streaming tool-call index → `build_tool_calls_from_map`
→ the `(id, name, args)` tuple → the `execute_tool_with_policy(id.clone(), ..)`
call → the `ToolExecutionContext.call_id` → the result push. No site
reassigns or drops the id. OpenAI/Anthropic match `tool_result` to
`tool_call` by this id, so pairing is positional-order-independent (see
V02 for the ordering characterization).

The normal-completion checkpoint (`tools.rs:429`) runs only after both
sub-batches finish — the first point where every assistant tool call has
a matching result. The comment (`:426-428`) states this explicitly:
"This is the first point where every assistant tool call in the batch
has a matching result."

**(5) Pipeline reachability.**
`execute_tool_with_policy` (`snapshot.rs:1199-1228`) constructs
`ToolExecutionContext` with `call_id`, `tool_name`, `params`, `input`,
`stream_tx`, then calls `pipeline.run(&mut ctx, self)`. The pipeline is
`default_pipeline()` (`pipeline.rs:935-956`) — 16 `Box<dyn PipelineStage>`
entries. The `run` method (`pipeline.rs:959-983`) iterates stages in
order, short-circuiting if `ctx.blocked`. `ExecuteStage` (`pipeline.rs:459-632`)
builds a per-call `ToolContext` (`:495-508`) carrying the snapshot's
`working_dir`, run/turn/message ids, artifacts config, and cancellation
token, then delegates to `tool_manager.execute_tool_with_context` (or
the streaming variant if `supports_streaming`).

**(6) Single live orchestrator.**
Duplicate search (`grep -rn "fn run_tools" echo-agent/src echo-agent-cli/src`):
exactly one definition (`phases/tools.rs:50`). The `process_steps`
variant in `react_loop.rs:177` carries `#[allow(dead_code)]` and is the
pre-unification implementation (F-RCT-02-P2-02). No other batch
orchestrator exists on the live path.

## Deviations

1. The task brief lists `pipeline.rs` as a "13-stage" middleware
   (carried over from F-RCT-02's description). `default_pipeline()`
   at `pipeline.rs:935-956` actually contains **16** stages
   (Intervention, ParseValidate, ToolVisibility, PlanMode,
   PreToolUseHook, Permission, ReadBeforeEdit, SkillPermission,
   CallbackStart, Audit, Execute, PostToolUseHook, OutputGuard,
   Truncation, TraceRecording, CallbackEnd). The `execute_tool_with_policy`
   doc comment at `snapshot.rs:1187` says "15 stages" — also stale.
   This is a documentation drift, not a behavioural defect; the stage
   count does not affect the pairing claim.
2. The `try_send_or!`-based error forward on the batch-timeout path
   (`tools.rs:284-292`) means a `Full` channel buffer silently drops the
   `Err(Timeout)` event. This is a reliability nuance of the timeout
   path specifically (see V03 / F-RCT-04-P2-01), not a pairing defect —
   the calls that did complete before the timeout are still paired
   correctly.

## Conclusion

The claim is **supported**. Every tool call in a batch is paired with
exactly one `tool_result` message (success or error) keyed by the
original `tool_call_id`; the split into serial/concurrent is
policy-driven; the per-call path runs the full 16-stage pipeline; and
`run_tools` is the single live orchestrator. The completion-order
nondeterminism of the concurrent path (V02) and the batch-timeout
asymmetry (V03 / F-RCT-04-P2-01) do not break pairing — they are
separate findings about ordering and terminal-path symmetry.
