## Claim

When EKO activates a plugin, real components are registered into the live
runtime — not metadata-only. Skills, hooks, and MCP servers are wired by the
framework `PluginIntegrator::wire_all`; Subagents are registered by the
application `register_plugin_agents` (definition + instance + factory); and
the application-owned discovery outputs (themes, output styles, monitors, LSP
configs) are prepared into `PreparedApplicationComponents` and applied to
their live subsystems (scheduler, LSP manager, system-context projection).
Activation also fires the `PluginLoaded` lifecycle hook.

- Themes/output-styles/monitors/LSP are applied to live subsystems

## Result

- Exit code: 0
- Summary: All expectations confirmed.

  **Subagent registration is real (definition + instance + factory).**
  `register_plugin_agents` (`plugin_components.rs:444-476`) builds a concrete
  `ReactAgent` instance via `build_plugin_agent` (`:459`), then calls
  `agent.register_subagent_with_definition(framework_definition.clone(),
  Box::new(instance))` (`:471`) AND
  `agent.register_subagent_factory(framework_definition, factory)` (`:472`).
  The factory (`FnAgentFactory`, `:463-470`) rebuilds the agent on each
  isolated dispatch. This is three framework registrations per plugin agent,
  not a metadata stub. The framework
  `register_subagent_with_definition` (`capabilities.rs:305-325`) writes into
  `subagent_registry` and updates the model-facing dispatch catalog.

  **Application-owned components reach live subsystems.**
  `prepare_application_components` (`plugin_components.rs:96`) returns
  `PreparedApplicationComponents { agents, lsp_configs, monitors, themes,
  output_styles }`. These are consumed by `apply_candidate`:
  - LSP: `prepare_lsp` (`plugin_runtime.rs:946-984`) builds a fresh
    `LspManager`, merges configs, and `start_server` per language; the manager
    is swapped into the live `self.lsp.manager`.
  - Monitors: `replace_plugin_monitors` (`:1178-1209`) removes previous and
    `add_task`s candidate monitors on the bound `SchedulerRunner`.
  - Output styles: on successful apply, `apply_candidate` re-injects the active
    style's instructions into the system context via
    `replace_system_context_projection(OUTPUT_STYLE_PROJECTION, instructions)`
    (`:741-752`).
  - Themes: tracked in `state.prepared.themes`; surfaced via `themes()` /
    `activate_theme()` to the UI.

  **Unload reverses all categories.** `unload_agent_components`
  (`plugin_runtime.rs:1157-1176`) iterates `application.agents` →
  `unregister_subagent(name)`, and `framework` entries →
  `unregister_skills_by_source("plugin:{name}")` +
  `hook_registry.unregister(&HookSource::Plugin(name))` +
  `disconnect_mcp(server)`. `unregister_subagent`
  (`capabilities.rs:406-424`) removes from the registry AND the dispatch
  catalog and invalidates the definition cache — a no-op (returns `false`) for
  names that were never registered, so exhaustive cleanup of a partially
  prepared set is safe.

  **PluginLoaded hook fires.** `fire_loaded_events` (`plugin_runtime.rs:1048`)
  reads the live `hook_registry` + session id + agent name from the agent and
  calls `run_lifecycle_hooks` with `HookEvent::PluginLoaded` per plugin
  (`:1063-1070`).

  **Test output:**
  ```text
  test plugin_runtime::tests::real_plugin_load_disable_and_unload_are_live ... ok
  test plugin_runtime::tests::scaffold_and_validate_cover_application_components ... ok
  ```
  The live-cycle test asserts: after reload — `agents_loaded=1`,
  `lsp_languages_loaded=1` (unix), `monitors_loaded=1`, `themes_loaded=1`,

## Deviations

None. One observation: `prepare_application_components` performs within-batch
deduplication via per-category HashSets (`agent_names`, `lsp_languages`,
`monitor_ids`, `theme_names`, `output_style_names`, `plugin_components.rs:
103-107`), so a duplicate within a single reload batch is a hard error. This
is correct because each reload builds a fresh `PreparedApplicationComponents`
(the previous set is fully unloaded), so cross-batch accumulation cannot
occur. See finding A-PLG-01-P2-01 for the granularity of this error handling.

## Conclusion

EKO activation registers real, live components across all eight categories
(skills, hooks, MCP, Subagents, LSP, monitors, themes, output styles), not
metadata-only. Subagents get the full definition+instance+factory triple;
application-owned components reach their live subsystems (scheduler, LSP
manager, system context); unload reverses every category. This supports the
"correctly apply product components" half of the task question.
