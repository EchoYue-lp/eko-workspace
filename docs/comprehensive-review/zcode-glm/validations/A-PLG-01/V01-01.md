## Claim

EKO plugin activation is owned by a single application-layer service
(`PluginRuntimeService`) that drives the framework lifecycle correctly:
`PluginLifecycleManager` callbacks are registered once, `init` fires exactly
once per plugin, `activate`/`deactivate` bracket each atomic swap, and the GUI
(Tauri), CLI, and TUI command surfaces all delegate to the same shared service
instance (no divergent enabled/loaded set).

## Expected Result

- Exactly one `PluginRuntimeService` constructed at bootstrap; stored as
  `Arc<PluginRuntimeService>` on `AgentRuntime` and cloned into
  `AppState.plugin_runtime: Option<Arc<...>>`.
- `register_lifecycle` uses the framework `PluginLifecycleManager` (register →
  init-once → activate-per-transition) and cleans up (unregister) if activation
  fails so the plugin can be re-registered.
- Tauri IPC, CLI slash commands, and TUI all resolve the SAME shared service
  instance; none constructs its own `PluginRegistry` or runs `wire_all`
  independently.
- No parallel plugin-activation authority exists in the application.

## Result

- Exit code: not-applicable (static inspection + grep)
- Summary: All expectations confirmed.
  - **Single service.** `PluginRuntimeService::new` is called exactly once at
    `runtime.rs:280` inside `AgentRuntime::bootstrap`. The resulting
    `Arc<PluginRuntimeService>` is held on `AgentRuntime.plugin_runtime`
    (`runtime.rs:51,367`) and cloned into `AppState` via
    `with_plugin_runtime(Some(self.plugin_runtime.clone()))`
    (`runtime.rs:386`). `AppState.plugin_runtime: Option<Arc<...>>`
    (`state.rs:449`) is the single IPC-facing handle.
  - **Lifecycle correctness.** `register_lifecycle`
    (`plugin_runtime.rs:387-410`) acquires the state mutex, looks up the
    plugin's `enabled` flag, calls `state.lifecycle.register(name, callbacks)`
    (framework `PluginLifecycleManager::register`), and — only if enabled —
    calls `state.lifecycle.activate(name)`. `activate`
    (`lifecycle.rs:98-118`) fires `init` once (guarded by `initialized` flag)
    then `activate` (guarded by `active` flag). On activation error,
    `register_lifecycle` calls `state.lifecycle.unregister(name)` which
    (`lifecycle.rs:153-179`) removes the entry BEFORE running
    deactivate/shutdown, so a failing cleanup cannot block re-registration
    (test `failed_native_lifecycle_registration_shuts_down_and_can_retry`).
  - **Atomic swap brackets.** `apply_candidate` (`plugin_runtime.rs:551`)
    calls `deactivate_all()` before any swap (`:575`) and
    `activate_enabled(candidate_plugins)` after the swap succeeds (`:655`).
    On any of the four failure checkpoints it re-activates the previous set
    (`activate_enabled(previous_plugins)`), preserving the bracket invariant.
  - **Tauri delegation.** `require_service(&state)`
    (`tauri/commands/plugins.rs:83-89`) returns
    `state.app_state.plugin_runtime.clone()` or a hard error when the service
    is absent (headless/channel mode). All 13 IPC commands call
    `service.{list,get,install,uninstall,enable,disable,configure,reload,
    themes,activate_theme,output_styles,activate_output_style}`. No IPC
    command constructs its own registry or calls `wire_all`.
  - **CLI delegation.** `/plugins` subcommands (`cli/cmd_impls/plugins.rs`)
    resolve `ctx.plugin_runtime.as_ref()` and call the same service methods.
    A missing runtime prints "Plugin runtime is not initialized." rather than
    constructing a fallback registry.
  - **Duplicate-authority search.** `PluginRegistry::new` appears only inside
    `PluginRuntimeService` (`registry_for`, `plugin_runtime.rs:993-1005`) and
    `#[cfg(test)]` helpers. `PluginIntegrator::new` appears only inside
    `replace_agent_components` (`plugin_runtime.rs:818,829,853`). No command
    surface builds its own registry or integrator. The pre-P0-4
    `build_registry()` helper (documented in the Tauri command header comment,
    `plugins.rs:1-9`) has been removed.

## Conclusion

EKO activation is owned by a single `PluginRuntimeService` that drives the
framework `PluginLifecycleManager` correctly: init-once, activate-per-swap,
remove-before-cleanup on unregister. The GUI/CLI/TUI surfaces are thin
delegates to the same shared `Arc`; no divergent enabled/loaded set exists.
This supports the "correctly apply product components" half of the task
question. The application owns the orchestration policy (atomic swap,
preferences, monitor/theme/style projection); the framework owns the lifecycle
primitives — the layering matches AGENTS.md's "uncertain ownership defaults to
application". Relates to finding A-PLG-01-P2-01 (reload granularity) but does
not affect ownership correctness.
