## Claim

Plugins can be reloaded, disabled, enabled, and uninstalled repeatedly; every
operation fully removes and re-registers all eight live component categories.
Hooks fire synchronously (no persistent queue to flush), and the
`PluginLifecycle::shutdown` callback runs via `PluginLifecycleManager::Drop`
on service drop. User hooks from the three config sources (inline +
`~/.eko/hooks.yaml` + `.eko/hooks.yaml`) are merged into one
`HookSource::UserConfig` slot by the single `HookConfigLoader`, so reloads do
not clobber one another. Preferences (active theme, active output style)
survive a runtime drop + recreate.

## Expected Result

- The full load→disable→enable→uninstall cycle removes and restores all
  component categories; repeated reloads are idempotent (init once).
- Lifecycle counts across reload→configure→uninstall match the init-once /
  activate-per-reload model.
- Hooks run synchronously (awaited inline); there is no background queue, so
  "flush" is a no-op for the registry. The only flush obligation is the
  plugin's sync `shutdown()` callback.
- `HookConfigLoader` merges the three user-hook sources into one
  `register_user_hooks` call, so reloads do not clobber one another.
- On service drop, `PluginLifecycleManager::Drop` runs sync `shutdown()` per
  plugin; async MCP disconnect only happens on explicit unload (not Drop).
- Preferences survive a runtime restart.
- All targeted tests pass.

  **Lifecycle-bracketing test
  (`native_lifecycle_brackets_reload_configure_and_unregisters_on_uninstall`).**
  Counts across reload→configure→uninstall: init=1, activate=3, deactivate=2
  (pre-uninstall); deactivate=3 + shutdown=1 (post-uninstall). Re-scaffold +
  re-register after uninstall succeeds (no stale-registration block).

  **Preferences test
  (`theme_and_output_style_preferences_survive_runtime_restart`).** Activate
  theme + output style, drop the runtime, recreate, assert preferences
  persisted and the output-style projection is re-injected. (Preferences are
  stored atomically: tmp+rename, 0o600 on Unix, `plugin_runtime.rs:1121-1135`.)

  **Hook execution is synchronous.** `HookRegistry::run_hooks`
  (`hooks.rs:792-836`) iterates sources and rules, calling `execute_action(
  ...).await` inline and `merge_result` per action; it short-circuits on
  `stop_propagation`/`block`. There is no `tokio::spawn`, no channel, no
  pending-task set — hooks are fire-and-await. `execute_command_hook`
  (`hooks.rs:1092`) runs the child via `manager.execute(sandbox_cmd).await` or
  the direct `tokio::time::timeout(...).await`, both awaited. Conclusion:
  there is no queue to flush; the only flush obligation is the plugin author's
  sync `shutdown()` callback.

  **HookConfigLoader single-slot merge.** `load_merged`
  (`hook_config_loader.rs:90-115`) takes inline `app_config.hooks`, then
  `merge_file_sources` (`:161-201`) adds `~/.eko/hooks.yaml` and
  `.eko/hooks.yaml` additively into one `HooksDefinition`. The caller does a
  single `clear_user_hooks()` + `register_user_hooks(merged)`. The module doc
  (`:1-28`) documents this was the P0-1 fix for the prior bug where each
  source separately called clear+register and clobbered the others. All 7
  `hook_config_loader` tests pass.

  **Shutdown path.** There is no explicit `plugin_runtime.shutdown().await`
  call at app exit (grep of `runtime.rs`/`state.rs` for shutdown calls
  returns nothing plugin-related). Shutdown relies on
  `PluginLifecycleManager::Drop` (`lifecycle.rs:254-260`), which calls
  `shutdown()` (`:241-251`), which calls `unregister` per plugin (sync
  deactivate + shutdown callbacks). The async `unload_agent_components`
  (MCP disconnect, hook unregister) only runs during explicit
  reload/disable/uninstall — NOT on Drop. For a local personal assistant this
  is acceptable (OS reclaims sockets/processes); plugin authors needing
  deterministic cleanup must use `deactivate()` (sync, fires on reload).
  See finding A-PLG-01-P3-01.

  **No plugin filesystem watcher.** Grep for `notify::`/`RecommendedWatcher`/
  `plugin.*watch` in `echo-agent-app-core/src` returns only the config watcher
  (`config_watcher.rs`), whose doc (`:1-11`) explicitly scopes it to user
  hooks + webhook endpoints and states other domains "require a restart".
  Plugin component files (SKILL.md, hooks.yaml, agents/*.md, themes/*.json)
  are NOT watched; edits require manual `/plugins reload`. See finding
  A-PLG-01-P2-02.

  **Steady-state unload paths inspected.**
  - `disable(name)` (`plugin_runtime.rs:242-264`): scans fresh candidate,
    `candidate.disable(name)`, `apply_candidate` swaps, fires `PluginDisabled`
    hook; on apply error `restore_enabled_state` rolls back the flag.
  - `uninstall(name, keep_data)` (`:287-343`): if enabled calls `disable(name)`
    first (unwires components), then `registry.uninstall(name, keep_data)`
    (removes dir before in-memory entry so a failed delete leaves the live
    registry truthful), then `lifecycle.unregister(name)` (deactivate +
    shutdown). `PluginDisabled` fires if it was not previously enabled.
  - `reload()` (`:201-207`): fresh candidate registry → `scan_registry` →
    `apply_candidate`. Because `apply_candidate` does full
    unload-previous/wire-candidate (not a diff), a no-op reload produces an
    equivalent live state; repeated reloads are idempotent.
