## Claim

The project index has two layers and only one of them is live:

1. `ProjectIndex` (`project/index.rs`) — a 488-line metadata-cache module
   advertised as persisting to `~/.eko/cache/{project_hash}.json` — has
   **zero production callers**. It is compiled into the crate (`pub mod
   index;` at `project/mod.rs:6`) but never built, loaded, saved, or
   queried by any runtime path. There is therefore no live index to
   invalidate and no stale-cache risk arising from it — only dead code
   (P2-01) and a misleading doc (P3-01).
2. `ProjectContext` (`project/context.rs`) + `PromptAssembler`
   (`project/prompt.rs`) — the live project-context path — read fresh from
   disk on every call. `generate_file_tree_summary` / `collect_dir_entries`
   walk the directory tree with no cache, and `load_git_context` shells
   out to `git status` / `git diff` with no cache. The
   `eko:project-context` projection is rebuilt on every workspace switch
   via `refresh_project_context_projection`.

So the task's V01 sub-question ("how is the index built / invalidated /
stale-cache risk?") resolves to: **in production there is no index; the
live path is cache-less and reads current files.**
