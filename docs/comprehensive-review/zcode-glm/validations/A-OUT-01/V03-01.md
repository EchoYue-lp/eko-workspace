## Claim

When an external document converter (pandoc / quarto / PDF engine) is
missing, EKO degrades gracefully: structured errors with actionable
messages, no panic, no silent fall-through to a degraded format, and the
"all formats" export omits the unavailable formats. The agent and the GUI
both see the same error classification.

## Expected Result

- Missing converter → structured `ResearchError::External` with an
  actionable message naming the required binaries and env vars.
- "All formats" export omits DOCX/PDF when the renderer is unavailable.
- No panic, no `unwrap` on `Option<DocumentRenderer>`.
- Both agent and GUI see the structured error.
- Stderr from the external renderer is captured and bounded safely.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not-applicable
- Summary: the claim holds at the Rust layer; one UX-layer observation
  (frontend does not pre-check availability).
  - **Discovery returns `Option<DocumentRenderer>`.**
    `resolve_document_renderer` (`research.rs:1215-1233`) tries, in order:
    `EKO_PANDOC` env → `pandoc` on PATH → `EKO_QUARTO` env → `quarto` on
    PATH → `None`. `executable_available` (`research.rs:1241-1249`) spawns
    `<bin> --version` with null stdio and returns `bool`. No `unwrap`; the
    `None` case is the documented "missing" state.
  - **Conditional "all formats".** `export_all_review_formats`
    (`research.rs:1171-1192`) always includes Markdown/JSON/CSV/BibTeX/RIS
    (pure-Rust renderers), adds DOCX iff
    `document_renderer_available()`, and adds PDF iff
    `pdf_renderer_available()` (`research.rs:1182-1187`). So a missing
    converter cannot produce a half-empty PDF file in the "all" bundle.
  - **Two structured error branches.**
    - `render_review_document` (`research.rs:1251-1257`): if
      `resolve_document_renderer()` is `None`, returns
      `ResearchError::External("PDF/DOCX export requires Pandoc or Quarto
      on PATH; EKO_PANDOC/EKO_QUARTO may point to a custom executable")`.
    - `render_review_document_with_renderer` (`research.rs:1285-1289`): if
      pandoc is present but `pdf_engine` is `None`, returns
      `ResearchError::External("Pandoc PDF export requires typst,
      weasyprint, wkhtmltopdf, xelatex, lualatex, or pdflatex; EKO_PDF_ENGINE
      may select another supported engine")`.
    Both name the required binaries and the override env vars.
  - **Renderer exit failure.** Non-zero renderer exit
    (`research.rs:1312-1322`) returns `ResearchError::External` with the
    status code and a UTF-8-safe, 2_000-char-bounded stderr excerpt
    (`String::from_utf8_lossy(&output.stderr).chars().take(2_000)`).
  - **Agent surface.** `research_tool.rs:189`
    `Ok(result.unwrap_or_else(|error| ToolResult::error(error.to_string())))`
    — every `ResearchError` becomes a `ToolResult::error`, so the LLM sees
    the actionable message and can retry / switch format. No panic.
  - **GUI surface.** `tauri/commands/research.rs:251-254` calls
    `export_review` / `export_all_review_formats` and maps errors via
    `ipc_error` (`ResearchError::External` falls into the
    `AnalysisError::Io | Json | Execution` arm pattern at
    `src/tauri/commands/analysis.rs:32-34`, returning
    `IpcError::Internal(error.to_string())`; the same mapping shape is used
    by the research command). The frontend's `exportReview` handler
    (`ReviewWorkbench.tsx:163-165`) catches the rejected promise and
    surfaces `error.message` to the user.
  - **UX-layer observation (not a Rust defect).** The frontend
    `ReviewWorkbench.tsx:354-362` hardcodes the `<option>` list
    (`all/markdown/pdf/docx/json/csv/bibtex/ris`) unconditionally. It does
    not call a `rendererAvailable` probe to grey out PDF/DOCX before the
    user clicks Export. So a user on a machine without pandoc sees PDF and
    DOCX as selectable, clicks Export, and only then receives the
    structured error. The error is correct; the discoverability is late.
- Log/artifact: none (no finding filed against the Rust path). The
  frontend late-discoverability is noted in the task Handoff for A-FE-02.
- Pandoc/Quarto happy path not executed (requires the binaries on PATH);
  the inspection covers command construction
  (`research.rs:1276-1309`) and the structured-error branches, which are
  deterministic from source.

## Deviations

The "happy path" (pandoc installed, DOCX/PDF produced end-to-end) was not
exercised. The validation covers the missing-converter branches, which is
the V03 claim's focus. Executing a happy-path run would require pandoc +
typst (or another PDF engine) installed in the review environment and is
not necessary to classify the fallback behavior.

## Conclusion

The missing-converter behavior is graceful at the Rust layer: structured
errors with actionable messages, no panic, conditional inclusion in the
"all formats" bundle, and identical error classification reaching both the
agent (`ToolResult::error`) and the GUI (`IpcError`). The single gap is a
frontend UX pre-check — PDF/DOCX appear selectable even when the renderer
is unavailable, so the user discovers the constraint only after clicking
Export. That is a discoverability defect owned by A-FE-02, not a V03
failure of the export path itself. Supports the "passed (with UX finding)"
status in the task Validation Matrix.
