Every output path that truncates or previews content uses UTF-8-safe
truncation (`chars().take(n)` / `chars().count() > n`) per AGENTS.md, with
no byte-length (`str::len()`) guards mixed in.

Every truncation/preview uses `chars()`. No `str::len()` (byte count)
guards. AGENTS.md's "判断长度用字符数" rule is honored everywhere in the
output paths.

## Deviations

The inspection is static; no runtime test was run that prints a long
Chinese tool result to the REPL. The conclusion follows from the source:
the suffix decision branches on `output.len()` (bytes), which AGENTS.md
explicitly flags as the wrong unit (`s.len() > 100 // ❌ 这是字节数`).

Note the blast radius is narrow: `print_tool_result` is called only from
`src/cli/repl.rs:787`, and the REPL is a hidden entry (`args.rs:26`
`--cli`). No panic is possible (no byte slicing is performed); the defect
is a misleading `"..."` suffix for multi-byte content in a narrow size
band.

## Conclusion

The output/export paths are almost entirely UTF-8 safe — the framework
truncation, the analysis capture bounding, the pandoc stderr capture, and
most of `OutputRenderer` all use `chars()`. The single exception is
`OutputRenderer::print_tool_result` at `output/mod.rs:225`, which mixes a
`chars().take()` preview with a `str::len()` suffix guard, violating the
AGENTS.md UTF-8 rule. The same file's `print_tool_call` at line 207 shows
the correct pattern, so the fix is a one-line change. Supports finding
A-OUT-01-P3-03.
