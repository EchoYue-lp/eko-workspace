## Claim

A non-EKO consumer can use `eval`, `improve`, and `evolution` against the
framework's own generic traits (`Agent`, `Store`, `RunStore`) with zero
coupling to EKO product types, Tauri, or app-core. The APIs are options on
the framework, not projections of EKO policy.

## Method

Read-only grep for product-coupling markers across all three modules, plus
inspection of public API signatures to confirm they take framework traits
and produce framework types.

```text
1. grep -rni "eko|echo.agent.cli|echo_agent_cli|app.core|app_core|tauri"
   echo-agent/src/eval echo-agent/src/improve echo-agent/src/evolution
   (expect 0 matches)
2. grep -rn "use crate::eval|use crate::improve" echo-agent/src/evolution
   (expect 0 — evolution must not depend on eval/improve features)
3. Inspect public entry points:
   - EvalRunner::new/run/with_grader/with_run_store (eval/runner.rs)
   - LlmGrader + grader prompt (eval/grader.rs)
   - generate_review_html (eval/server.rs)
   - TrajectorySaver (improve/trajectory.rs)
   - ImprovementLoop / Analyzer (improve/loop.rs, analyzer.rs)
   - MemoryLayerManager + MemoryRuntimeIntegrationBuilder (evolution/layer.rs,
     runtime_integration.rs)
   - Dreaming, Curator, SkillMerger, SkillPatcher, MemoryReviewer,
     BackgroundReviewer (evolution/*)
4. Confirm the EKO-specific types live only in echo-agent-cli and enter the
   framework exclusively via trait impls (MemoryTriggerSink, SkillLoadPolicy,
   EvolutionObserver).
```

## Expected Result

Zero product-coupling markers inside the three framework modules. Public
APIs reference only `crate::` framework modules and framework traits. Any
EKO-specific behavior enters via traits implemented in the application
layer, not via framework types.

### Public API signatures (framework traits only)

- `EvalRunner::run(&self, case: &EvalCase, agent: &dyn Agent)` — takes the
  framework `Agent` trait (`eval/runner.rs:52`). `with_run_store(Arc<dyn
  RunStore>)`, `with_grader(LlmGrader, Arc<dyn Agent>)`.
- `LlmGrader` wraps `crate::llm::LlmClient` (the framework client) — no
  provider lock-in (`eval/grader.rs:42`).
- `generate_review_html(report: &EvalReport, title: &str) -> String`
  (`eval/server.rs`) — pure function producing self-contained HTML; no
  server, no EKO UI dependency. "review" here = eval review, not EKO's
  Review Inbox.
- `TrajectorySaver` writes ShareGPT JSONL to a caller-supplied directory
  (`improve/trajectory.rs`) — generic fine-tuning dataset export.
- `ImprovementLoop` returns `LoopResult { suggestions:
  Vec<ImprovementSuggestion> }` (`improve/loop.rs`) — suggestions only;
  the doc explicitly says "does NOT automatically apply suggestions"
  (verified in V03).
- `MemoryLayerManager::new(echo_agent_dir: PathBuf, store: Arc<dyn Store>,
  change_log: Box<dyn ChangeLog>)` (`evolution/layer.rs`) — takes the
  framework `Store` and `ChangeLog` traits; `echo_agent_dir` is just a
  path string, not an EKO type.
- `MemoryRuntimeIntegrationBuilder::new(echo_agent_dir, store)` +
  `HookEvolutionObserver::new(hook_registry, session_id, agent_name)`
  (`evolution/runtime_integration.rs`) — generic wiring over the
  framework `HookRegistry`. Doc: "framework-level plumbing only ...
  Product lifecycle policy and scheduling remain in app code."
- `Dreaming::new(layer_manager, config)` / `Dreaming::run()` — the doc
  tells consumers "Call `Dreaming::run` on a cron/daily schedule"
  (`evolution/dreaming.rs:96`); the framework does not schedule it.
- `BackgroundReviewer::review_run(...)` takes `&dyn RunStore`, `LlmClient`,
  `MemoryLayerManager` (`evolution/background_review.rs`) — generic; the
  default is proposal-only.

### Where EKO coupling actually lives (application layer)

- `echo-agent-cli/echo-agent-app-core/src/evolution/review_integration.rs`:
  `ReviewIntegration` implements `echo_agent::evolution::MemoryTriggerSink`
  (returns `Captured`) and `echo_agent::skills::external::SkillLoadPolicy`.
  Both are thin trait impls; no framework type is modified.
- `echo-agent-cli/echo-agent-app-core/src/evolution/rule_promoter.rs`:
  `RulePromoter` produces `RuleProposal` — application policy on top of
  framework memory.
- `echo-agent-cli/echo-agent-app-core/src/infra.rs:1132-1209`: the daily
  Dreaming scheduler ("Spawn Dreaming after boot settles, then repeat it
  on a daily cadence") — application scheduling of a framework pass.
- `echo-agent-cli/echo-agent-app-core/src/evolution/evidence.rs`: the
  Evidence Store / Review Inbox types — application-only, no framework
  counterpart.

## Conclusion

Supports the V02 claim: `eval`, `improve`, and `evolution` are generic
framework options. A non-EKO consumer can construct an `EvalRunner` with
its own `Agent`/`RunStore`, export trajectories with `TrajectorySaver`,
run `ImprovementLoop` for suggestions, and install a `MemoryLayerManager`
for typed memory + audit — all without touching any EKO type. EKO product
policy (Review Inbox, RulePromoter, Dreaming scheduling) lives entirely in
`echo-agent-cli/echo-agent-app-core/src/evolution/` and enters the
framework exclusively via trait implementations. This is consistent with
AGENTS.md "删除框架代码的判定" (these are framework options, not EKO
projections) and with the F-FEAT-01 layering discipline.
