## Claim

Per AGENTS.md ("No self-evolution metric platform. Evolution = explicit
diagnostics and user-triggered review only."), the eval/improve/evolution
surface is diagnostics-only for rules and skills, and propose-before-apply
for semantic memory. The validation checks (a) that no framework path
auto-mutates rules or skills, (b) that semantic memory/skill mutations are
proposal-then-explicit-apply, and (c) characterizes every automatic
memory-write path in the framework react engine.

## Method

Read-only inspection of mutation entry points and their callers across
framework + app.

```text
1. Enumerate pub mutation fns in evolution/:
   grep -rn "pub fn write|pub async fn write|pub fn promote|pub fn apply|
   pub fn merge|pub async fn merge|pub fn patch|pub fn delete" src/evolution
2. For each, classify: proposal-producer (returns a Proposal/Report and has
   no side effect) vs explicit-apply (takes a proposal, consumer-invoked).
3. Confirm skill/rule auto-mutation is absent:
   - RulePromoter is app-layer (echo-agent-cli); framework has no rule write.
   - Skill promotion: Curator::promote_to_* are pub+explicit; no caller in
     the react engine auto-promotes skills.
4. Trace the framework react engine for auto memory writes:
   grep -rn "write_memory|detect_and_write_memory_triggers|pre_compaction_flush"
   src/agent/
5. Verify EKO's MemoryTriggerSink disposition (Captured vs Persist) and
   whether pre_compaction_flush is sink-interceptable.
6. Verify background review default (auto_persist_user_preferences) and that
   skills remain proposal-only.
7. Verify no background auto-scheduling loops in framework evolution:
   grep -rn "tokio::spawn|interval(|sleep(" src/evolution
```

## Expected Result

- Rules: no framework auto-mutation (RulePromoter is app + proposal-based).
- Skills: candidate/proposal only; promote/merge/patch are explicit apply.
- Semantic memory: propose (analyze_and_propose / scan_and_propose /
  review) separated from apply (apply_patch / execute_merge / merge_group).
- Any react-engine memory auto-write is opt-in (layer manager installed),
  security-scanned, audit-logged, and (for triggers) sink-interceptable.

## Result

- Exit code: 0 (inspection).
- Summary: rules and skills are confirmed diagnostics/proposal-only at the
  framework layer. Semantic memory has a clean propose→apply split. The
  framework react engine auto-writes memory in two paths when a
  `MemoryLayerManager` is installed; the trigger path is sink-interceptable
  (EKO routes to review), but the pre-compaction path is not. This is the
  finding F-EVO-01-P2-01.

### Rules — no framework auto-mutation (PASS)

- The framework has no rule-writing primitive. `RulePromoter` lives in
  `echo-agent-cli/echo-agent-app-core/src/evolution/rule_promoter.rs` and
  produces `RuleProposal`s consumed by the application.
- `instruction_provider.rs:265` (app) reads "auto-promoted rules
  (evolution)" from `.eko/learned-rules.md` — a file the app's
  `RulePromoter` writes after its own criteria. No framework path writes
  rules during a run.

### Skills — candidate/proposal only (PASS)

- `SkillCandidateDetector` produces `CandidateReport` (detection).
- `SkillDraftGenerator` produces `DraftResult` (analysis).
- `SkillMerger::scan_and_propose` → `Vec<SkillMergeProposal>`;
  `execute_merge(proposal)` is a separate explicit fn (`merge.rs:109,232`).
- `SkillPatcher::analyze_and_propose` → `Vec<SkillPatch>`;
  `apply_patch(patch)` is separate (`patch.rs:201,267`).
- `Curator::promote_to_draft`/`promote_to_active`/`apply_transitions` are
  pub+explicit; the only non-test caller of `apply_transitions` is the
  CLI command `evolution run` (`echo-agent-cli/src/cli/cmd_impls/evolution.rs:185`)
  and a Tauri panel (`panels.rs:1394`). The framework react engine only
  refreshes `last_used_at` telemetry (`execution.rs:137`), it does NOT
  call `apply_transitions`.
- `BackgroundReviewConfig::auto_persist_user_preferences = false` by
  default (`background_review.rs:111`); the doc states project facts,
  debugging lessons, and skills are **always** proposal-only
  (`background_review.rs:98-99`).
- No framework `tokio::spawn`/`interval` auto-schedules skill mutation
  (V03 grep). Dreaming is consumer-scheduled.

### Semantic memory — propose → apply split (PASS)

- `MemoryReviewer::review` produces `ReviewReport { conflict_proposals,
  ... }` (`review.rs:594`). `review.rs:277`: "Analysis-only proposal
  describing a conflict that needs an explicit choice." Default config
  `auto_generate_drafts = false` (`review.rs:534`). A test
  `review_defaults_are_manual_and_proposal_only` exists (`review.rs:831`).
- `MemoryMerger::merge_group(group)` is the explicit apply
  (`review.rs:390`), taking a `ConflictGroup` produced by detection.
- All writes flow through `MemoryLayerManager::write_memory`
  (`layer.rs:837`), which runs `EvolutionSecurityGuard::check_memory_write`
  (secret scan + injection detection + trust) and `record_change` (audit)
  before the store put (`layer.rs:843-882`).

### React-engine auto memory writes (FINDING — F-EVO-01-P2-01)

Two paths in `echo-agent/src/agent/react/run/context.rs` auto-invoke
`MemoryLayerManager::write_memory` during a run when a layer manager is
installed:

1. **Trigger path** (`context.rs:34-137`, called at `react_loop.rs:558`
   and `context.rs:509,579`):
   - `TriggerDetector::detect` runs on each user message.
   - For each `TriggerMatch`, if a `memory_trigger_sink` is installed and
     returns `Captured`, the framework **skips** its write
     (`context.rs:76-84`).
   - If there is **no sink** (framework default) or the sink returns
     `Persist`, the engine calls `layer_manager.write_memory(...)`
     directly (`context.rs:100-101`).
   - EKO installs `ReviewIntegration` as the sink
     (`agent_pool.rs:924`, `runtime.rs:256`) which **always returns
     `Captured`** and upserts an `EvidenceCandidateDraft` into the
     Review Inbox (`review_integration.rs:277-321`). Comment at
     `review_integration.rs:314-317`: "EKO treats inferred memory as
     review-only. Do not let an inbox storage failure fall through to
     the framework's direct durable write path." → EKO's trigger
     behavior is review-gated; the framework *default* (no sink) is
     auto-write.

2. **Pre-compaction flush** (`context.rs:676-798`):
   - Gated only by `self.llm_client` and `self.memory_layer_manager`
     being `Some` (`context.rs:681-683`) and
     `ContextManager::should_compress()` (`context.rs:692`).
   - Makes a bounded 15s LLM call to extract facts, then calls
     `layer_manager.write_memory(...)` directly for each fact
     (`context.rs:794`).
   - **NOT** intercepted by `memory_trigger_sink`. This path auto-writes
     in EKO's deployment too.

Mitigations common to both: writes go through the security guard + audit
log; they land in the warm typed-namespace; warm→hot promotion (which
would surface in `MEMORY.md` / the system-prompt prefix) still requires
`consider_promotion`'s deterministic confidence+stability gate
(`layer.rs:884-886`).

### Auto-scheduling check (PASS)

`grep -rn "tokio::spawn|interval(|sleep(" src/evolution` (non-test):
- `recall.rs:66` — fire-and-forget `recall_count` bump (counter, not a
  mutation loop).
- `audit.rs:281`, `curator.rs:311` — `std::thread::sleep(BACKOFF)` inside
  file-lock retry (not a scheduler).
- `background_review.rs:270,282,329,341` — `tokio::spawn` to run ONE
  review pass async and return a `JoinHandle`; invoked by the caller, not
  self-scheduling.
- `layer.rs:1040` — `tokio::time::sleep(BACKOFF).await` file-lock retry.

No `tokio::time::interval` auto-loop mutates memory or skills inside the
framework. The daily Dreaming scheduler is application code
(`echo-agent-cli/echo-agent-app-core/src/infra.rs:1132`).

## Deviations

The pre-compaction flush bypassing the `memory_trigger_sink` is the
deviation from a uniform "all auto-writes are sink-interceptable" model.
Recorded as F-EVO-01-P2-01 direction (b).

## Conclusion

Supports the V03 claim **for rules and skills** (no framework auto-
mutation; propose→apply). For **memory**, the framework react engine
auto-writes during runs (F-EVO-01-P2-01): triggers are sink-interceptable
and EKO review-gates them, but the framework default (no sink) auto-writes
and the pre-compaction path is not sink-interceptable at all. This is in
tension with the AGENTS.md "Evolution = explicit diagnostics and
user-triggered review only" / "no automatic memory mutation" statements.
The finding is recorded as P2 (bounded blast radius: warm layer only,
security-scanned, audit-logged, no auto-promotion, no rule/skill effect)
with three non-implemented remediation options for the user to choose
among.
