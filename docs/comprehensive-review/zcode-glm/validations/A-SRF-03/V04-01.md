## Claim

The frontend renders streaming tokens, tool calls, and results
correctly: (a) tokens route to either `message.content` (between
thinking_end and the next thinking_start) or the active thinking
segment (between thinking_start and thinking_end); (b) tool-batch
rounds (`tool_batch_start` → `recordToolStart` → `tool_batch_end`)
build `executionRounds` correctly and survive a round without
thinking; (c) tool detail is fetched lazily via the tool-execution
API and auto-refreshes while running; (d) subagent runs attach to
the correct message via `messageId` with conservative fallbacks for
legacy records; (e) the message bubble caps in-memory growth
(`MAX_MESSAGES = 500`); (f) `MessageBubble` is memoized so other
messages do not re-render on each token.

## Expected Result

- Tokens between thinking_start and thinking_end append to
  `thinkingSegments`; tokens outside append to `content`.
- `tool_batch_start` captures the current thinking segment into
  `currentRound.thinking`; `tool_batch_end` pushes the round onto
  the streaming message's `executionRounds`.
- `InlineToolCall` fetches detail only when expanded and auto-refreshes
  on a 500 ms interval while running, with a 256 KiB auto-load cap.
- `visibleSubagentRuns` matches by exact `messageId`, with fallbacks
  gated on the active run's `run_id` / `conversation_id`.
- `trimToMax` enforces `MAX_MESSAGES = 500` on every append/replace path.
- `MessageBubble` is wrapped in `memo`.
- All targeted tests pass.

## Deviations

The reducer is O(n) on every token (full message-array clone plus
content concat at `chatStore.ts:243-248`). For very long messages
(thousands of tokens), this is quadratic in message length. The
`memo` wrapper prevents other messages from re-rendering, so the
cost is bounded to the streaming message — but a single very long
final answer could still cause noticeable jank. This is a performance
characteristic, not a correctness defect; noted in Coverage but not
promoted to a finding.

## Conclusion

Supports the V04 claim. The streaming / tool / result rendering is
correctly layered: the chat-event handler owns token routing, the
chat-store reducers own message mutation, the tool-execution store
owns tool rows, the subagent-run store owns subagent lifecycles, and
the rendering components compose them via memoized selectors. The
lazy-detail-fetch pattern bounds memory; the message cap bounds
message-list growth; the visible-runs projection is conservative.

The one finding connected to V04 is the untyped `execution://event`
cast chain (A-SRF-03-P3-03): the rendering trusts that
`tool.owner.message_id` and `subagent_run_id` exist on the payload
because the cast declared them present. A malformed payload would
produce `toolExecutionOwnerKey === 'chat:undefined'`, making the
tool invisible in the rendering. This is a defensive-validation gap,
not a rendering bug per se.

Findings using this validation: A-SRF-03-P3-03 (receive-side cast
chain that the rendering trusts).
