## Claim

The frontend recovers correctly from window reload / Tauri restart /
listener remount: (a) the listener-setup race (mount → `await import()`
→ `await listen`) is handled so no listener leaks and no callbacks
fire on unmounted components; (b) reload rehydrates auth, conversation
list, and the active conversation's chat + tool + subagent + TaskRun
state; (c) `hydrateConversation` preserves tools from other
conversations; (d) interrupted loads (startNew during loadConversation)
do not leave stale state.

## Expected Result

- `useTauriChat` documents and implements abort handling covering
  three windows: abort during `import`, abort between the two
  `listen`s, abort after both `listen`s but before `push`.
- `useBrowserEvents` either uses the same pattern or has a documented
  reason not to.
- App mount triggers `conversationStore.init()` and an `activeId`-driven
  `taskRuntimeStore.loadByConversation`.
- Auth token rehydrates from `sessionStorage` at module load.
- `loadConversation` uses a generation counter; `startNew` increments
  it so in-flight loads early-return.
- `hydrateConversation` filters tools by `conversation_id` so other
  conversations' live tools survive.
- After reload, `activeId` is null until the user picks a conversation
  (or clicks Resume in WelcomeScreen).
- All targeted tests pass.

## Result

- Exit code: 0
- Duration: ~4 s
- Summary:
  - (a) **`useTauriChat` race handling confirmed**:
    `useTauriChat.ts:84-167` sets `let aborted = false` and collects
    `pendingCleanup: Array<() => void>`. The setup function
    early-returns if `aborted` is set after each `await`. Cleanup
    iterates `pendingCleanup.forEach((fn) => fn())`. All three race
    windows are covered. The `:76-83` comment documents the previous
    P0-4 bug and the fix.
  - (b) **`useBrowserEvents` lacks the same hardening** — claim
    PARTIAL. `useBrowserEvents.ts:6-25` uses a simpler pattern: a
    single `disposed` flag and `.then((cleanup) => disposed ?
    cleanup() : (unlisten = cleanup))`. The pattern is mostly
    equivalent for the single-listen case (the listener is either
    immediately unregistered or stored), but it lacks the explicit
    "abort during import" early-return and the `pendingCleanup`
    collection. If the listener chain ever grows a second `listen`
    (mirroring `useTauriChat`'s evolution), the current pattern would
    reintroduce the original bug. → A-SRF-03-P3-04.
  - (c) **Mount-time initialization confirmed**: `App.tsx:36-39`
    triggers `initWorkspaces()` + `initConversations()`. `App.tsx:54-56`
    fires `loadTaskRun(activeId)` whenever `activeId` changes.
    `authStore.ts:14-39, 107-122` rehydrates from `sessionStorage`
    synchronously at module load and runs periodic + focus-driven
    `checkAuth`.
  - (d) **`loadConversation` generation counter confirmed**:
    `conversationStore.ts:297-299` increments `loadGeneration`;
    `:307, :315` early-return when `generation !== loadGeneration`.
    `startNew` at `:436` increments the generation, suppressing the
    in-flight load. Backed by `conversationStore.test.ts:122-135`.
  - (e) **`hydrateConversation` preserves other conversations**:
    `toolExecutionStore.ts:223-235` filters `currentTools` by
    `tool.conversation_id !== conversationId` and re-merges only the
    in-conversation slice. Backed by
    `toolExecutionStore.test.ts:207-243` ("hydrates one conversation
    without deleting live tools from another conversation").
  - (f) **Manual resume UX confirmed**: `WelcomeScreen.tsx:36-73`
    queries `sessionApi.getLatest()` and surfaces a "Resume" button.
    `App.tsx:36-39` does not auto-load the latest conversation;
    `activeId` starts as null. The user must click.
  - All targeted tests pass: `conversationStore.test.ts` (4),
    `toolExecutionStore.test.ts` (10), `taskRuntimeStore.test.ts` (n).
- Log/artifact: none.

## Deviations

The `useBrowserEvents` divergence is the only deviation from the
claim. The implementation is functionally correct for the current
single-listen case but diverges from the documented-correct pattern in
`useTauriChat`. P3-04 documents this.

## Conclusion

Supports the V03 claim with one deviation. The recovery flow is
well-designed: generation counters protect against stale writes, the
hydration merge preserves cross-conversation state, and the auth
rehydration is synchronous at module load. The single gap
(`useBrowserEvents` divergence) is a maintainability / consistency
finding, not a correctness regression on the live path.
