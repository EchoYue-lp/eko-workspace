## Claim

The frontend reducers handle out-of-order, duplicate, and late events
monotonically: (a) `useSubagentRunStore.ingest` never reopens a
terminal record; (b) `useToolExecutionStore.ingest` uses a status-rank
merge so a late `running` cannot clobber a terminal; (c)
`useChatStore.recordToolStart` is idempotent; (d) `useChatStore.appendToken`
drops tokens for absent messages silently; (e) the chat-event handler
is resilient to `final_answer` / `done` / `cancelled` reordering;
(f) `taskRuntimeStore.refresh` and `conversationStore.loadConversation`
suppress stale writes via generation counters.

## Expected Result

- The subagent reducer contains an explicit terminal-lock guard and
  returns `s` unchanged when `prev.status !== 'running'`.
- The tool-execution reducer's live `ingest` uses `mergeToolExecution`
  when an entry already exists.
- `recordToolStart` short-circuits duplicates.
- `appendToken` returns state unchanged when the message id is absent.
- `taskRuntimeStore.refresh` and `conversationStore.loadConversation`
  have generation counters that early-return on stale generations.
- The vitest suite passes (no regression).
