## Claim

Each public item exposed by the `echo_agent` facade has exactly one
canonical path. No item is reachable through more than two facade paths
(prelude + a single thin-re-export module).

## Method

Static duplicate-path enumeration. For each "interesting" facade item,
resolved every path through which a consumer could import it by walking:

1. `echo_agent::prelude::*` (curated always-on surface).
2. `echo_agent::advanced::*` (curated optional-feature surface).
3. `echo_agent::<thin-module>::*` (e.g. `memory`, `tasks`, `mcp`,
   `llm`, `sandbox`).
4. `echo_agent::<thin-module>::<subcrate>::*` (the nested
   `pub mod state { … }` / `pub mod orchestration { … }` escape hatch
   inside thin-re-export files).
5. `echo_agent::workspace::<subcrate>::*` (crate-level alias).
6. `<subcrate>::*` directly (when the consumer adds the sub-crate as a
   Cargo dependency).

For each item, the canonical definition was located with
`grep -rn "pub (struct|trait|enum|fn|use)"` across the workspace, then
each re-export path was confirmed by reading the relevant `pub use`
statement. All paths below are compile-time-equivalent (Rust structural
identity) — this is not a name-collision bug, it is a maintenance/
coherence concern.

```text
cd /Users/ls/MyWork/code/ylp_agent_learn/lp-agent/echo-agent
grep -rn "pub trait Store\b" --include=*.rs .           # locate canonical def
grep -n "pub use echo_state::memory" src/memory.rs      # confirm thin re-export
grep -n "pub use echo_state as state" src/lib.rs        # confirm workspace alias
sed -n '54,90p' src/llm.rs                              # llm.rs nested submodules
grep -n "pub use echo_orchestration" src/tasks.rs src/human_loop.rs
grep -rn "pub struct McpManager" echo-integration/src
grep -rn "pub struct LocalSandbox" echo-execution/src
grep -rn "pub struct TaskRevisionService" echo-orchestration/src
grep -rn "pub struct ProviderFactory\|impl ProviderFactory" echo-integration/src
```

For each sampled item, at most two facade paths (prelude/advanced + the

## Deviations

- The duplicate-path count treats `echo_<subcrate>::*` (direct
  sub-crate import) as a distinct path. A consumer who added
  `echo_integration` as a Cargo dependency and imported
  `echo_integration::mcp::McpManager` would get the same item as
  `echo_agent::mcp::McpManager`. This is correct Rust semantics; it is
  counted as a separate path because the question is about facade
  coherence, not identity.
- All duplicate paths are compile-time-equivalent. There is no name
  shadowing, no type-mismatch bug, no ambiguous-resolution warning.
  The failure is coherence/maintainability, not correctness.

## Conclusion

The claim is falsified. Multiple high-traffic facade items (Store,
OpenAiClient, ProviderFactory, McpManager, LocalSandbox,
TaskRevisionService) are each reachable through 4-6 distinct facade
paths, not 1-2. This is the same observation B-ARCH-01-P2-02 made at
the architecture level; F-API-01 confirms it from the public-API
contract angle and supplies concrete item-level evidence with item
counts and canonical-definition anchors.

The duplication is structurally intentional: it is the documented
migration scaffold (`src/lib.rs:119-123` says `workspace` exists "during
migration"; thin-re-export files document their nested submodule as
"Direct re-exports from `echo_<crate>`"). It is not a regression. The
cost is maintenance overhead (changing a type's source crate requires
updating multiple re-export sites) and consumer-code inconsistency
(READMEs and examples import the same type through different paths).
