## Claim

File-based stores (a) prevent filesystem path traversal via untrusted ids,
and (b) use an atomic-write pattern that is crash-durable: temp file + fsync
the temp + rename + fsync the parent directory.

## Method

Static inspection of all atomic-write and id-to-path code in the memory
modules.

```text
cd /Users/ls/MyWork/code/ylp_agent_learn/lp-agent
grep -rn "atomic_write|fs::rename|.tmp|safe_segment|sync_all|sync_parent"
  echo-agent/echo-state/src/memory echo-agent/echo-core/src/memory --include='*.rs'
read echo-agent/echo-state/src/memory/file_conversation.rs (safe_segment 465-486,
  atomic_write 494-533)
read echo-agent/echo-state/src/memory/store.rs (FileStore::flush 254-278)
read echo-agent/echo-state/src/memory/embedding_store.rs (flush_index 181-208)
```

## Expected Result

- Every file-based store that incorporates an id into the filesystem path
  sanitizes it through `safe_segment` (or equivalent).
- Every atomic-write routine performs all four steps: tmp + fsync-temp +
  rename + fsync-parent-dir.

## Result

- Exit code: not-applicable (static inspection)
- Duration: <1s
- Summary: **Mixed. Path safety is correct; atomic-write durability is
  inconsistent across the three routines.**
  - **Path safety — OK.** Only `FileConversationStore` builds a path from an
    external id (`<base>/conversations/<id>.json`, file_conversation.rs:86-89),
    and it sanitizes via `safe_segment` (465-486): rejects empty, rejects
    `/`, `\`, `..`, `.`, and any char outside `[A-Za-z0-9\-_.:~]`. Verified by
    `safe_segment_rejects_traversal_and_accepts_typical_ids` (772) and
    `path_traversal_id_is_rejected` (644).
    - `FileStore` does NOT join ids into paths — namespace and key are
      flattened to a HashMap key (`namespace.join("/")`, store.rs:317 etc.)
      and the whole map is serialized to one configured file. No traversal
      vector.
    - `EmbeddingStore` similarly uses `namespace.join("/")` as a HashMap key
      (embedding_store.rs:223), not as a filesystem path.
  - **Atomic-write durability — inconsistent.**
    - `FileConversationStore::atomic_write` (file_conversation.rs:494-523):
      does all four steps correctly — unique uuid-suffixed tmp (502-506),
      `sync_all` on temp (511), rename (517), `sync_parent_directory` on
      Unix (521, 525-528). Correct.
    - `FileStore::flush` (store.rs:254-278): does tmp + `sync_all` + rename
      but **does NOT fsync the parent directory** after rename. On a crash
      the rename may not be durable even though the temp's contents are.
    - `FileStore::flush` also uses a **static** tmp name `format!("{}.tmp",
      self.path.display())` (store.rs:258), not a uuid-suffixed one. Two
      `FileStore` instances pointed at the same path would clobber each
      other's tmp file.
    - `EmbeddingStore::flush_index` (embedding_store.rs:181-208): same
      pattern as `FileStore::flush` — tmp + sync + rename, **no parent-dir
      fsync**, static tmp name (`path.with_extension("json.tmp")`).

## Deviations

Three atomic-write routines implement three slightly different subsets of
the durable-write recipe. Only `FileConversationStore` is fully correct.
The other two omit the parent-directory fsync (so the rename is not
guaranteed crash-durable on Linux ext4 with default mount options) and use
non-unique tmp names (collision risk if two stores share a path, even
within one process via misconfiguration).

## Conclusion

Supports findings:
- **F-MEM-01-P2-01** (FileStore/EmbeddingStore omit parent-dir fsync —
  less durable than FileConversationStore).
- **F-MEM-01-P2-02** (FileStore/EmbeddingStore use static tmp names —
  cross-instance collision risk).

Path safety itself is correct: the only file-from-id store
(`FileConversationStore`) sanitizes correctly and has tests proving it.
This validation does not prove runtime behavior; it inspects source.

## Follow-Up

Fixes should converge all three atomic-write routines on the
`FileConversationStore::atomic_write` helper (factor it out as a shared
`util::atomic_write` in `echo-state`). Add a regression test that asserts
the parent dir is synced.
