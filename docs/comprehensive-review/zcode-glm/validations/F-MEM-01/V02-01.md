## Claim

Both file-backed stores (`FileStore`, `FileConversationStore`) handle corrupt
JSON consistently: surface the error to the caller rather than silently
returning empty data, so callers can detect corruption instead of mistaking
it for "no data".

## Method

Read both implementations and their corrupt-handling code paths and tests.

```text
read echo-agent/echo-state/src/memory/store.rs (FileStore::new, lines 225-252)
read echo-agent/echo-state/src/memory/file_conversation.rs (read_record/read_meta/read_all_records, lines 100-242)
inspect tests: file_conversation.rs:623 (corrupt_record_surfaces_as_error_not_empty)
```

## Expected Result

Both stores propagate `MemoryError::SerializationError` on a malformed JSON
file, matching the module-level doc claim in `file_conversation.rs:18-22`
("Corrupt JSON is an error ... rather than silently returning None").

## Result

- Exit code: not-applicable (static inspection)
- Duration: <1s
- Summary: **Mismatch.** The two stores have divergent corrupt-file semantics.
  - `FileConversationStore` is correct: `read_record` (file_conversation.rs:149-166)
    returns `MemoryError::SerializationError` on parse failure;
    `read_meta` (100-138) does the same for `_meta.json`;
    `read_all_records` (215-242) surfaces the error rather than skipping.
    This is verified by the test `corrupt_record_surfaces_as_error_not_empty`
    at line 623.
  - `FileStore::new` (store.rs:232-241) does the opposite: it uses
    `serde_json::from_str(&raw).unwrap_or_else(|e| { warn!(...); HashMap::new() })`,
    swallowing the parse error and starting from an empty state with only a
    `warn!` log.
- Log/artifact: none.

## Deviations

The `FileStore` behavior directly contradicts the durability contract this
task is asked to verify ("durable, atomic ... semantically aligned"). A
corrupted main JSON file is indistinguishable from a fresh install: the next
`flush()` (store.rs:254-278) writes the now-empty map back over the corrupted
file via `tokio::fs::rename`, destroying any chance of manual recovery. The
silent overwrite turns a recoverable corruption into permanent data loss.

## Conclusion

Supports finding **F-MEM-01-P1-01** (FileStore silent corruption = data loss).
The `FileConversationStore` demonstrates the correct pattern; `FileStore`
should adopt the same fail-loud behavior. The fix is local:
replace `unwrap_or_else` at store.rs:235 with `.map_err(|e|
MemoryError::SerializationError(...))?`.

This validation does NOT test runtime behavior — it is a static code
inspection. A follow-up executable test (write garbage to a FileStore path,
call `FileStore::new`, assert `Err`) should accompany the fix.
