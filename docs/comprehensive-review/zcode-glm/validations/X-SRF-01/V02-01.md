## Claim

For each of three representative scenarios (chat turn, task run, tool
execution), every applicable mode produces **equivalent facts**:
same `turn_id` / `run_id` derivation, same tool results, same terminal
status, same recovery semantics. The differences are purely in
rendering policy.

The trace must show that the underlying `AgentEvent` /
`ChatDriverEvent` / `ExecEvent` stream is identical across modes; the
surface-specific sinks (`TuiChatSink`, `TauriChatSink`,
`ChannelChatSink`, the REPL print loop, the cron/background drivers)
are pure projections.

## Method

Static scenario trace at
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent`, both repos at the
pinned commits. For each scenario, walk the call graph from user input
to terminal event in every applicable mode and assert fact-equivalence.

```text
For each scenario:
  1. Identify the shared entry point (drive_chat for chat lane,
     execute_run / drive_agent_run for task lane).
  2. Walk the surface-specific pre-entry path for each mode:
     - TUI: handle_enter / start_tui_task_run_driver (events.rs)
     - GUI: send_chat_message / execute_run caller (tauri/commands)
     - CLI: chat_with_agent / drive_run_async (repl.rs / run_driver.rs)
     - channels: handle_stream / drive_run_async (channels.rs)
     - cron: launch_cron_run (scheduler/runner.rs)
     - background: start_run_driver (tasks/service.rs)
  3. Walk the sink path for each mode:
     - TUI: TuiChatSink::on_event (events.rs:2031)
     - GUI: TauriChatSink::on_event (chat.rs:1341) + execution://event
     - CLI: repl.rs:563-845 print loop
     - channels: aggregate_by_sentence (channels.rs:514-654)
     - cron: drive_agent_run outcome branch (executor.rs)
     - background: drive_agent_run outcome branch
  4. For each step, record the identity (turn_id / run_id /
     conversation_id), the data payload, and the terminal event.
  5. Assert: same identity, same payload, same terminal across modes.
```

## Expected Result

- **Scenario A (chat turn "What is 2+2?")**: All four chat-lane modes
  (TUI/GUI/CLI/channels) reach `drive_chat`, derive `turn_id = uuid`,
  emit `Token` chunks + `FinalAnswer`, terminate with `TurnStatus {
  status: "completed" }`. Identity is `turn_id`; Task mode also
  derives `taskrun:{turn_id}`.

- **Scenario B (task run "Build hello world in Python and verify")**:
  All four task-lane modes (TUI/GUI/cron/background, plus
  CLI/channels-via-create_complex_task) reach `execute_run` /
  `drive_agent_run`, persist a `TaskRun` with `run_id = uuid`, execute
  the plan, and emit `ExecEvent::RunCompleted` on success. Identity
  is `run_id`.

- **Scenario C (tool execution `read_file`)**: All six modes
  (TUI/GUI/CLI/channels/cron/background) register `read_file` on the
  agent, call it via the ReAct loop, receive `ToolResult::Success`
  with the file content (or an artifact spill if large), and return
  it to the next ReAct iteration. The tool result is identical across
  modes (subject to the `InteractionMode` visibility filter).

## Result

- Exit code: not-applicable (static inspection)

- Summary: claim confirmed. All three scenarios produce equivalent

(X-SRF-01-P2-03). A cron run interrupted by restart stays Paused
forever; a background run auto-resumes.

**Fact equivalence (Scenario C):**

| Fact | All six modes |
|---|---|
| Tool registered | framework `enable_tools()` at `infra.rs:280` (mode-agnostic) |
| Tool visibility | per `InteractionMode` filter at `chat_driver.rs:465-472` / `executor.rs:3084-3109` (chat) or `:3686-3710` (Auto) |
| Permission pipeline | `PermissionStage` (one entry: `execute_tool_with_policy`) |
| Output bounding | `process_tool_output_for_call` — 4000-token model budget, 32 KiB artifact threshold |
| Result returned to agent | identical `ToolResult::Success` payload |
| Tool execution persistence | GUI-only via `ToolExecutionRepository`; TUI/CLI/channels/cron/background drop on session exit (X-SRF-01-P3-03) |

**Caveat — tool visibility:** the *result* of a tool call is
identical, but the *visibility filter* differs by `InteractionMode`
(A-TOOL-01). Auto mode hides `run_code`; Chat and Task include it.
The capability row "tool" is ✅ across modes; the per-tool visibility
is per-mode policy, not a parity gap.

**Caveat — persistence:** the *agent* sees the same result in every
mode; the *user* sees persisted history only in GUI (X-SRF-01-P3-03).

None. The fact-equivalence claim holds across all three scenarios
with two documented caveats (cancel reachability in Scenario A;
