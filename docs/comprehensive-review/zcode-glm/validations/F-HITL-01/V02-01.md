## Claim

When an approval request times out (or the responder is dropped without
responding), the effective `PermissionDecision` is `Deny` (fail-closed),
and this behavior is hardcoded at the provider→handler seam — entirely
independent of the `TimeoutStrategy` config, which is write-only (stored
and settable but never read in any decision path).

## Conclusion

Supports finding F-HITL-01-P2-01 in full. The `TimeoutStrategy` knob
is dead: a consumer that sets
`with_timeout_strategy(TimeoutStrategy::AutoApprove { .. })` will still
get `Deny` on timeout, because the knob is never consulted and the
handler-to-decision mapping is hardcoded to deny. The effective default
(timeout = Deny, drop = Reject) is fail-closed and correct for the
local-assistant threat model (AGENTS.md); the defect is the unused,
misleading public API, not the runtime behavior.

The result does NOT prove what happens if a future change wires
`TimeoutStrategy` in — only that at commit `9b0e0fa` it is unwired. It
also does not cover provider-side timeout policy (e.g. EKO
`HitlDispatcher`'s 5-min deadline, `dispatcher.rs:101-102`), which is
application-owned and out of scope for the framework permission model.
