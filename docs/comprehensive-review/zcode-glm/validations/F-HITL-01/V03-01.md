## Claim

The approval cache identifies approvals by (a) `tool_name` only for
`SessionAllTools`, (b) `tool_name + args_key` for `Session`, and (c)
nothing (no cache) for `Once`. However, the per-args `Session` scope is
unreachable for approvals through the standard
`PermissionRequestHandler` path: `PermissionService::infer_scope_from_updates`
collapses every session-scoped *allow* to `SessionAllTools`, and
`build_matcher` discards args when constructing the rule matcher.
Additionally, `SessionApprovalCache::sha256_hex` is misnamed — it
computes `DefaultHasher` (SipHash), not SHA-256.

## Expected Result

1. `SessionAllTools` keys on `tool_name` only; `Session` keys on
   `tool_name + args_key`; `Once` does not cache.
2. `infer_scope_from_updates` returns `SessionAllTools` for any
   `{source:"session", behavior:"allow"}` update and `Session` only for
   a deny update; since `record_approval` runs only when the decision is
   `Allowed`, per-args `Session` is never selected for an approval.
3. `build_matcher` returns bare `tool_name` for null/empty args and
   `"{tool_name}(*)"` otherwise — args are never preserved in the
   matcher.
4. `test_session_all_tools_scope` asserts `Bash({})` → caches
   `Bash({"cmd":"rm -rf /"})`.
5. `sha256_hex` body uses `std::collections::hash_map::DefaultHasher`,
   not a SHA-256 implementation.
6. No live caller toggles `hash_args` on outside `approval_cache.rs`
   itself.

## Conclusion

Supports findings F-HITL-01-P3-01 (per-args `Session` scope unreachable
for approvals; session approvals collapse to tool-wide) and
F-HITL-01-P3-02 (`sha256_hex` misnaming). The cache *as implemented*
supports three granularities, but the cache *as driven by
PermissionService* delivers only two: `Once` and tool-wide
(`SessionAllTools`). The documented per-args granularity
(`policy.rs:23-29`, "相同工具 + 相同参数") is not delivered on the
approval path.

The behavior itself (session approval is tool-wide) matches Claude
Code's "allow for session" (B-REF-01 C4) and is acceptable for the
local threat model (AGENTS.md); the defects are the dead per-args
granularity and the misnamed hash function, both maintainability issues.

Cross-context note (not a finding, recorded for downstream): the cache
lives inside `PermissionService`, which is per-agent. EKO's per-
conversation pool agents (`agent_pool.rs:953-977`) get isolated caches,
but if the primary agent (`runtime.rs`) is reused across GUI
conversations, its `SessionApprovalCache` would accumulate approvals
across conversations. Whether that happens is an application-layer
question for A-CHAT-01.
