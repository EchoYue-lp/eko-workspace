## Claim

Large tool output is bounded at every layer by a named mechanism: the
framework spills oversized payloads to a sha256-tagged artifact file
(`ToolOutputArtifactWriter`); the EKO projection paginates output via a
cursor (`read_output(cursor, limit)`); the frontend pulls pages lazily and
caps live loading. The spill path's sha256 checksum and artifact path
reach the EKO projection either as structured metadata (streaming tools)
or as a textual pointer in the output string (all tools); the cursor
pagination is end-to-end continuous from `read_output` to the frontend.

## Expected Result

- The spill file's sha256 is computed by a real hasher (not text
  replacement) and is exposed both in the model-facing output and (for
  streaming tools) in the structured metadata that reaches the frontend.

  sha256 integrity: `ToolOutputArtifactWriter` (artifact.rs:145-156)
  constructs a `Sha256` hasher (`use sha2::{Digest, Sha256}` at
  artifact.rs:8) and feeds every written byte through it; the final
  digest is exposed as `ToolOutputArtifactRef.sha256` (artifact.rs:96).
  The same hash is then (a) interpolated into the model-facing output
  string (`snapshot.rs:970-974`: "...sha256 {hash}. Use read_artifact with
  this exact path and expected_sha256..."), and (b) added to the
  framework metadata as `artifact_sha256` via `extend_metadata`
  (artifact.rs:117). Both surfaces carry the identical hash, so the model
  and any metadata consumer see the same checksum. The model's
  `read_artifact` tool is the structured verifier (the user-facing
  checksum gate is the model being told the expected sha256 in the
  output text).

  Cursor continuity: `read_output` (tool_execution.rs:413-450) returns
  `ToolExecutionDetailPage { chunks, next_cursor, complete }`.
  `parse_cursor` (tool_execution.rs:668-676) accepts the prior
  `next_cursor` (an opaque string) and translates it to a byte offset.
  The frontend stores `next_cursor` in React state (`setCursor` at
  InlineToolCall.tsx:75) and passes it as `cursor` to the next
  `readOutput` call (InlineToolCall.tsx:71). The JSONL path
  (`read_jsonl_output_page` at tool_execution.rs:677) and the artifact
  path (`read_artifact_page` at tool_execution.rs:720) share the same
  opaque-cursor contract; both repair UTF-8 boundaries
  (`utf8_page_prefix` at :750). The existing test
  `artifact_pages_end_on_utf8_boundaries` (tool_execution.rs:957-997)
  drives a 3-character "你🙂好" file through 1-byte and 8-byte pages and
  asserts the boundaries land on character boundaries — passing per
  A-FE-02 V03 (run during that review).

  Asymmetric recovery (the X-TOL-01-P2-01 consequence for V03):

  | Tool family | Example tools | Streaming? | Spill metadata reaches EKO manifest? | Consequence |
  |---|---|---|---|---|
  | Stream-capable | shell, run_code | yes | yes (via `ToolStream::Complete` → `pending_completions` merge at chat.rs:1253-1278) | `read_output` paginates the spill file via `manifest.metadata["artifact_path"]`; `manifest.truncated` is true; sha256 visible in metadata |
  | Non-streaming | read_file (large), write_file, edit_file, git tools, web_fetch, sql_query, data/research/media tools | no | **no** (metadata dropped at snapshot.rs:1242) | `read_output` cannot reach the spill file (no `artifact_path` in metadata); falls through to JSONL output (which contains only the preview+pointer text); `manifest.truncated` is **false**; sha256 only in the output text, not in metadata |

  For non-streaming spilled tools, the spill file still exists on disk
  (the framework wrote it), the model can still call `read_artifact` with
  the textual pointer to retrieve bounded pages, and the output string
  carries the textual `path` + `sha256`. So the *content* is reachable
  via the agent loop. The GUI's `InlineToolCall` lazy reader, however,
  paginates only the EKO JSONL output (which holds the preview+pointer
  text) and has no path to the artifact — the user sees the pointer text
  but cannot page into the full payload from the lazy detail panel. The
  "Agent 上下文已截断" label is also missing for these tools
  (`manifest.truncated` is false).

  Framework in-tool cursor pagination (`PageRequest`/`PageInfo`,
  echo-core/tools/pagination.rs) is a separate channel used inside
  individual tool payloads (`web_search`, `sql_query` — verified by
  F-EXT-01 V03 and F-EXT-03). It binds the cursor to a SHA-256
  fingerprint of `{query, limit, items snapshot}` and rejects stale
  cursors (`CursorQueryMismatch`). This is a per-tool pagination
  contract exposed as JSON inside `ToolResult.data`, not a cross-layer
  output-pagination mechanism; it is correct and bounded but does not
  interact with the EKO `read_output` cursor.

## Conclusion

Supports V03 with a documented asymmetry. The framework computes a real
sha256 over the spilled payload, the EKO projection's cursor pagination is
UTF-8-safe and continuous, and the frontend lazy reader is bounded. The
non-streaming metadata drop (X-TOL-01-P2-01) degrades the GUI's reach
into spilled content for non-streaming tools specifically: the spill
file is on disk and model-reachable, but the EKO `read_output` API and
the `manifest.truncated` flag lose their structured handle to it. This
is the most concrete user-visible consequence of the cross-layer drop
documented in V01.
