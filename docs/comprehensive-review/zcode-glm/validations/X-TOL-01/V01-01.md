## Claim

A single tool invocation's fields are mapped field-by-field across five layers
— model-facing framework `ToolResult`, framework `AgentEvent`, EKO
`TauriChatSink` / `TauriExecutionProjector`, EKO `ToolExecutionRepository`
manifest, and the frontend TypeScript contract — and the mapping is
documentable as a strict table that exposes which fields survive every hop and
which are dropped (and where).

  Authoritative drop boundary: `execute_tool_with_policy`
  (`echo-agent/src/agent/snapshot.rs:1242`, commit `9b0e0fa`):
  ```rust
  if result.success {
      return Ok(ctx.output.unwrap_or(result.output));
  }
  ```
  The function's signature is `Result<String, ToolCallFailure>` — on success
  only `ctx.output` (a String) is returned. `ctx.result` (the full
  `ToolResult` that the `TruncationStage` at `pipeline.rs:743-745` enriched
  with `truncated` and the spill `metadata`) is in scope but **not read past
  this point by the batch layer**. The downstream `AgentEvent::ToolResult`
  enum variant (`echo-core/src/agent/mod.rs:203-210`) only has three fields
  (`call_id`, `name`, `output: String`), so the loss is structural at the
  framework event boundary, not an EKO-side bug.

  Compensating channel (streaming tools only): when `tool.support_streaming()`
  is true, `ExecuteStage` (`pipeline.rs:528-551`) forwards every
  `ToolStreamEvent` (including the terminal
  `ToolStreamEvent::Complete(ToolResult)`) through the batch's `stream_rx`.
  The batch then emits `AgentEvent::ToolStream { event: Complete(result) }`
  with the *full* `ToolResult` (`phases/tools.rs:223-225` and `:232-236` at
  `9b0e0fa`). The EKO `TauriChatSink` captures this in
  `pending_tool_completions[call_id]` (`chat.rs:1253-1260`) and merges
  `result.metadata` + `result.truncated` into the subsequent
  `AgentEvent::ToolResult` projection (`chat.rs:1267-1278`). The TaskRuntime
  subagent projector has the same pattern at `executor.rs:3420-3442` and
  `chat.rs:1034-1105`.

  Net effect: streaming tools (shell, run_code) preserve `truncated` and
  `metadata` end-to-end via the parallel `ToolStream::Complete` channel;
  non-streaming tools (file/git/data/web_fetch/sql_query) lose both at the
  `execute_tool_with_policy` boundary. The asymmetry is the load-bearing
  observation behind X-TOL-01-P2-01.

  Secondary observation: the EKO TaskRuntime path has TWO parallel
  projections of the same tool invocation, with different field names and
  truncation policies:
  - `store.record_tool_finished` (`store.rs:2002-2034`) writes
    `RuntimeEventKind::ToolCompleted` (success) or `ToolFailed` (failure)
    into `events.jsonl` with payload `{result_preview (bounded 500 chars),
    result_chars, failure}`.
  - `executor.emit_exec(...)` (`executor.rs:3326-3341, 3375-3391`) emits an
    `ExecEvent` with `RuntimeEventKind::ToolCompleted` (for BOTH success and
    failure) and payload `{result (full string), success, failure?}`.

  The GUI observer reads the **trace-sink** payload (`chat.rs:1034-1105`),
  not the store payload; the TaskRuntime `events.jsonl` is the durable
  audit trail. The two projections disagree on (a) event kind for failures
  (`ToolFailed` vs `ToolCompleted`) and (b) whether the result is bounded.
  This is not a per-field corruption — both carry `failure` losslessly — but
  it is a conformance complexity worth flagging for downstream tasks that
  consume either projection.
