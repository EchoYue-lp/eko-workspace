flattens or re-derives them. Any flattening is confined to clearly
secondary diagnostic consumers and is named.

## Conclusion

Supports V02. On the primary failure path (GUI chat sink and TaskRuntime
subagent projector → EKO manifest → frontend), `ToolFailure` with all six
fields survives every hop as a typed struct with no re-derivation. The
frontend TS mirror is identical variant-for-variant. The single flattening
consumer (`analysis.rs:run_status`) is a diagnostic surface, not the live
tool-execution view; it is filed as X-TOL-01-P3-01 (P3 — no impact on the
live tool-execution conformance).

The validation also confirms a secondary observation recorded for
downstream tasks: the tool-execution wire types (`ToolFailure`,
`ToolFailureCategory`, `ToolRecoveryAction`, `ToolExecution`,
`ToolExecutionDetailManifest`, `ToolExecutionDetailPage`,
`ToolExecutionSummary`) are **hand-written in TypeScript**
(`types/api.ts:49-116`), NOT generated via `#[derive(TS)]` from the Rust
source (no matching files exist in `web-frontend/src/generated/`). The
task-runtime family IS generated (`generated/RuntimeEventKind.ts`,
`SubagentTaskResult.ts`, etc.). Adding a new `ToolFailureCategory` variant
in Rust would serialize correctly at runtime (the frontend reads it as a
string), but the TS union would not flag the missing literal — drift is
caught only by inspection. This is recorded as X-TOL-01-P2-02.
