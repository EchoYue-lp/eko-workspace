## Claim

Tauri commands are lifecycle-safe under concurrency: no long-held async locks,
no `std::sync::Mutex` held across `.await`, no nested-lock deadlock cycle. One
minor lock-across-await smell is acceptable if non-deadlocking and bounded.

## Method

Static lock-pattern inspection across all command modules. Working directory:
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent`.

```text
1. Enumerate every async-lock acquisition in commands:
   grep -rc "\.write()\.await\|\.read()\.await\|\.lock()\.await" \
       echo-agent-cli/src/tauri/commands

2. For each write/read acquisition, inspect the guard's scope: is it
   block-scoped (`{ let g = …; … }`) or released via explicit `drop` before
   the next .await? Or is it held across .await?

3. Find nested-lock patterns (lock acquired inside another lock's scope):
   grep -rn -A8 "\.write()\.await\|\.lock()\.await" echo-agent-cli/src/tauri \
       | inspect for inner .await on a second lock

4. Find std::sync::Mutex held across .await:
   grep -rn "std::sync::Mutex\|Mutex::new\|\.lock()" echo-agent-cli/src/tauri \
       | classify each site

5. Confirm the conversation_store RwLock type and its writers:
   grep -rn "conversation_store:" echo-agent-app-core/src/state.rs
   grep -rn "conversation_store\.write()" echo-agent-app-core/src

6. Inspect the one candidate long-held lock (save_conversation) and the one
   nested-lock candidate (hooks reload):
   read echo-agent-cli/src/tauri/commands/conversations.rs:391-450
   read echo-agent-cli/src/tauri/commands/hooks.rs:149-163
```

## Expected Result

- All command-path async-lock guards are either block-scoped or explicitly
  dropped before the next `.await`.
- No `std::sync::Mutex` guard survives an `.await`.
- No nested-lock cycle.
- Any exception is identified and classified as deadlocking vs non-deadlocking.

## Result

- Exit code: not-applicable (static inspection)
- Duration: not-applicable
- Summary: claim **holds**. No deadlock cycle. One non-deadlocking
  lock-across-await identified (`save_conversation`) → P3-04. The nested-lock
  candidate (`hooks` reload) is clean.

  Step 1 — 76 async-lock acquisitions across command modules (panels 27,
  chat 10, mcp 8, conversations 8, config 8, providers 6, hooks 3, tools 2,
  workspace/session/research/analysis 1 each).

  Step 2 — dominant pattern is correct. Representative block-scoped sites:

  - `tools.rs:37-42` — `enable_tool`: `{ let mut states = …write().await;
    states.get_mut(&name).enabled = true; }` then `.await` at `:45` with the
    guard already dropped.
  - `tools.rs:58-63` — `disable_tool`: identical pattern.
  - `panels.rs:59-61` — `set_permissions_mode`: `let mut mode_lock =
    …write().await; *mode_lock = …; drop(mode_lock);` then further `.await`
    calls (agent `write_async`, pool `apply_permission_mode`) with the lock
    released.
  - `panels.rs:125-133` / `:140-153` — permission-rule list mutations,
    block-scoped.
  - `state.rs:908-911` — workspace-switch writer, block-scoped
    (`{ let mut guard = …; *guard = Some(new_store); }`).

  Step 3 — nested-lock candidate `hooks.rs:152-162`:

  ```text
  agent_handle.write_async(|a| {
      Box::pin(async move {
          let mut registry = a.hook_registry().write().await;  // inner lock
          registry.clear_user_hooks();                          // sync
          if !hooks_def.is_empty() { registry.register_user_hooks(hooks_def); }  // sync
      })
  }).await;
  ```

  The `hook_registry().write().await` guard is acquired and released inside
  the closure, with only **sync** calls between (`clear_user_hooks`,
  `register_user_hooks`). No `.await` on the inner guard, no third lock taken.
  The outer `write_async` holds the agent's write lock; the inner takes the
  registry lock. No cycle (the registry never re-enters the agent lock). Clean.

  Step 4 — `std::sync::Mutex` sites:

  - `chat.rs:22` — `use std::sync::{Mutex as StdMutex, …}`.
  - `chat.rs:1148-1156` — `TauriChatSink` holds
    `tool_completions: StdMutex<HashMap<…>>` and
    `active_tool_ids: StdMutex<HashSet<…>>`.

  The `ChatSink::on_event` impl (`chat.rs:1341-1415`) is a **sync `fn`** (the
  trait method is `fn on_event(&self, event) -> bool`, no `async`). The std
  Mutex guards are acquired and released within this sync function (and within
  `handle_tool_event`, also sync). No `.await` is reachable while a std Mutex
  is held → no runtime deadlock. Deliberate design (StdMutex chosen over
  tokio::Mutex because the sink is sync).

  Step 5 — `conversation_store: RwLock<Option<Arc<dyn ConversationStore>>>`
  (`state.rs:363`). Two writers: `state.rs:909` and `state.rs:1081`, both
  block-scoped.

  Step 6 — the one long-held lock, `save_conversation`
  (`conversations.rs:398-444`):

  ```text
  let store_guard = state.app_state.storage.conversation_store.read().await;  // :398
  let store = store_guard.as_ref().ok_or_else(...)?;
  let existing = store.get_conversation(&id).await.ok().flatten();            // :411 await under guard
  store.update_conversation(&conv.conversation_id, …).await…                  // :414 await under guard
  let existing_messages = store.get_messages(&conversation_id).await…         // :434 await under guard
  let stored = project_saved_messages(…);                                      // sync
  store.save_messages(&conversation_id, &stored).await…                       // :441 await under guard
  ```

  The read guard is held across four store I/O awaits. Non-deadlocking
  because: (a) RwLock permits concurrent readers, so parallel saves don't
  block each other on this guard (the inner store handles its own locking);
  (b) the only writers (`state.rs:909`, `:1081`) are short-scoped and never
  re-enter the read lock; (c) Tauri uses a multi-threaded tokio runtime, so
  one task holding the read guard cannot starve the writer's runtime entry.
  Contention surface: a workspace switch (writer) stalls until in-flight saves
  drain. Drives P3-04.

## Deviations

## Conclusion

Supports the A-SRF-02 lifecycle-safety conclusion. The Tauri command path
introduces no deadlock and no std-Mutex-across-await hazard. The convention
(block-scoped guards + explicit `drop` + StdMutex only in sync `fn`s) is
consistent. One bounded, non-deadlocking read-lock-across-await in
`save_conversation` is the sole smell (P3-04, one-line clone-out-of-guard
fix). The `TauriChatSink`'s deliberate StdMutex-in-sync-fn design is correct.
This validation is the evidence for the V02 claim and for P3-04.
