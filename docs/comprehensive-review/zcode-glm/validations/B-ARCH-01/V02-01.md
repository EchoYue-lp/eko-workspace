## Claim

The root `echo_agent` crate exposes one coherent facade made of `prelude`,
`advanced`, and `workspace` modules. Each public type has exactly one
canonical source crate reachable through the facade, and the facade does
not leak sub-crate internals in unexpected ways.

Note: this validation is `passed_with_notes` rather than `passed` because
the facade itself is structurally correct, but it deliberately exposes
**two parallel access paths** (facade modules + `workspace::*` direct
access) for the same items. This is documented migration debt and is
captured as a finding, not a deviation.

## Method

Read the root `src/lib.rs` end-to-end and enumerate every `pub mod`,
`pub use`, and direct re-export from a sub-crate. Then for each facade
module (`prelude`, `advanced`, `workspace`), categorize every item by its
source crate. Finally, list types reachable via multiple paths.

Procedure (working directory
`/Users/ls/MyWork/code/ylp_agent_learn/lp-agent/echo-agent`):

1. Read `src/lib.rs` (332 lines) in full.
2. For each facade module, record source crate for every re-exported item.
3. For each thin-re-export file (`src/memory.rs`, `src/audit.rs`, etc.),
   read the file to confirm it is a pure re-export vs a real implementation.
4. For root modules with their own implementation (`src/state/`,
   `src/agent/`, `src/event_bus.rs`, `src/hooks_bridge.rs`, `src/llm.rs`,
   `src/channels.rs`), record what is real code vs re-export.
5. Build the duplicate-path table.

## Expected Result

- A single canonical facade: `prelude::*` for the common case,
  `advanced::*` for opt-in features, `workspace::*` as a documented escape
  hatch for callers that need to bypass facade drift.
- Each sub-crate's public API reachable through exactly one facade module
  per concept.
- No type re-exported simultaneously from `prelude` and `advanced`.

### Duplicate / ambiguous paths

The same item is reachable from multiple paths. Examples:

- `TaskRevisionService`:
  - `echo_agent::tasks::TaskRevisionService` (root re-export)
  - `echo_agent::advanced::TaskRevisionService` (`src/lib.rs:321-324`)
  - `echo_agent::workspace::orchestration::tasks::TaskRevisionService`
  - `echo_orchestration::tasks::TaskRevisionService`
- `Store` trait:
  - `echo_agent::memory::Store` (root re-export)
  - `echo_agent::workspace::state::memory::Store`
  - `echo_core::memory::Store`
- `SlidingWindowCompressor`:
  - `echo_agent::compression::SlidingWindowCompressor`
  - `echo_agent::workspace::state::compression::SlidingWindowCompressor`
  - `echo_state::compression::SlidingWindowCompressor`
- `LocalSandbox`:
  - `echo_agent::sandbox::LocalSandbox`
  - `echo_agent::prelude::LocalSandbox` (same item, re-exported twice
    within the root crate)
  - `echo_execution::sandbox::LocalSandbox`
- `McpManager`:
  - `echo_agent::mcp::McpManager` (root re-export)
  - `echo_agent::advanced::McpManager`
  - `echo_agent::workspace::integration::mcp::McpManager`
  - `echo_integration::mcp::McpManager`

The duplicate paths are explicit and documented as migration debt
(`src/lib.rs:119-123` comment on `workspace` module). They do not produce
ambiguity inside a single `use` statement because Rust requires the user
to pick one path; they produce maintenance ambiguity because changing a
type requires touching multiple re-export sites.

### Inconsistent helper exposure inside the root

Each thin re-export file follows a convention of also exposing a nested
submodule named after the source crate's category:

```rust
// src/memory.rs:42-45
pub mod state { pub use echo_state::memory::*; }
pub use echo_state::memory::*;
```

The same pattern repeats in `compression.rs` (`pub mod state`),
`audit.rs` (`pub mod state`), `human_loop.rs` (`pub mod orchestration`),
`tasks.rs` (`pub mod orchestration`), `tokenizer.rs` (`pub mod core`),
`error.rs` (`pub mod core`), `retry.rs` (`pub mod core`), `mcp.rs`
(`pub mod integration`), `channels.rs` (`pub mod integration`),
`lsp.rs` (no extra submodule — different convention), `llm.rs`
(`pub mod core` AND `pub mod integration` AND `pub mod types` AND
`pub mod config` AND `pub mod providers`).

The convention is not uniform across files (`lsp.rs` and `llm.rs` deviate),
and the naming is not consistent with the `workspace` module's aliases
(`workspace::state` vs `memory::state` both refer to `echo_state`, but
only `workspace::state` gives the whole crate).

## Deviations

Structural facade correctness holds. The following are recorded as
findings, not deviations:

- The root crate contains substantial real implementation, not just
  re-exports (`agent/`, `state/`, `evolution/`, `event_bus.rs`,
  `hooks_bridge.rs`, etc.). Recorded as `B-ARCH-01-P2-01`.
- The `workspace` module deliberately provides parallel access paths
  during migration (`src/lib.rs:119-130`). Recorded as
  `B-ARCH-01-P2-02`.
- The thin re-export files use a non-uniform "nested submodule per source
  crate" convention. Recorded as `B-ARCH-01-P3-06`.
- `echo_tools` and `echo_macros` are not aliased under `workspace::*`,
  breaking the symmetry of the escape hatch. Recorded as
  `B-ARCH-01-P3-07`.

## Conclusion

Supports: the root crate exposes a working facade via `prelude` and
`advanced`. Every public item from every sub-crate is reachable through
the facade. The `workspace` module is the documented escape hatch.

Does not prove: that the facade is *minimal* or *canonical*. The root
crate owns real implementation that has not yet been pushed down into a
sub-crate, and the same item is reachable through up to four paths. These
are migration-debt findings, not violations of the dependency graph (V01)
or of cycle freedom (V03).

`B-ARCH-01-P3-07`.
