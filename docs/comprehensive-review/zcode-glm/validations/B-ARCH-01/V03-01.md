## Claim

No type is misplaced across the eight workspace crates in a way that
breaks the layering principle `core → {tools, integration, state,
orchestration} → execution → facade`. Specifically:

- No circular dependency patterns even when not expressed in `Cargo.toml`.
- The root crate does not define types that belong in sub-crates.
- No `extern crate` usage bypasses Cargo dependencies.
- Each concept has one authoritative definition (no parallel
  implementations of the same trait/type).

## Method

1. Search for every `extern crate` occurrence across the workspace.
2. Search sub-crate source code for any `use echo_agent::...` or
   `crate_name("echo_agent")` references (the cycle indicator that

### Misplaced types — root crate

The root crate defines entire domain subsystems that the architecture
documentation assigns to sub-crates:

1. **`src/state/`** defines `RuntimeStateStore`, `TaskNode`,
   `AgentCheckpoint`, plus file and SQLite implementations. The
   `echo_state` crate exists specifically for "State management ...
   memory, compression, audit" — runtime checkpointing would fit there
   naturally. Today `echo_state` does not know about `RuntimeStateStore`;
   the trait lives only at the facade layer.

   Evidence: `src/state/mod.rs:244` defines the trait; `src/state/file.rs`
   and `src/state/sqlite.rs` provide the only implementations. The
   `src/memory.rs` doc comment (line 12) cross-references
   `crate::state::RuntimeStateStore` as the third tier of the memory
   system, indicating these concepts are tightly coupled to memory but
   live in a different crate level.

2. **`src/event_bus.rs`** defines `EventBus` and `GLOBAL_EVENT_BUS` at the
   facade. There is no event-bus concept in `echo_core` or
   `echo_integration`. Because `EventBus` consumes
   `crate::agent::EventEnvelope` (which is itself defined in `echo_core`),
   the type could live in `echo_core` (or `echo_integration`).

3. **`src/workflow/`** is a *thin re-export* of
   `echo_orchestration::workflow` (`src/workflow/mod.rs:66` —
   `pub use echo_orchestration::workflow::*;`) **plus** two root-only
   modules: `dsl.rs` (372 lines) and `loader.rs` (442 lines). The
   `Graph`/`GraphBuilder`/`SequentialWorkflow`/`DagWorkflow` types all
   come from `echo_orchestration::workflow`; the root only adds the YAML
   loader and DSL helpers on top. This is acceptable layering
   (orchestration owns the engine; facade provides the loader that needs
   root-level types). **No parallel authority.**

4. **`src/llm.rs:116-178`** defines three compatibility wrappers
   (`assemble_req_header`, `chat`, `stream_chat`) at the facade. The
   doc comment at line 111-118 explicitly states these remain "so older
   call sites can stay on `echo_agent::llm::*` while the canonical
   implementation lives in `echo_integration::providers::openai`." This
   is acknowledged compat debt, not a misplaced *type*, but it is
   facade-level code duplicating sub-crate functions.

5. **`src/agent/`** is the largest real implementation in the root crate
   (`ReactAgent`, subagent, callbacks, critic, default_factory, snapshot,
   steer, turn). The architecture allows this — `echo_core::agent` only
   defines the `Agent` trait and event types, while the concrete
   `ReactAgent` engine is intentionally a facade-level composition. This
   is acceptable layering for a "framework facade with a default
   implementation" pattern and is not flagged as misplaced.

### Parallel authority check

For each duplicated concept, distinguish *re-export* from *parallel impl*:

- **`Store` trait + impls**: trait in `echo_core`, impls in `echo_state`.
  Root `src/memory.rs` is a pure re-export. **No parallel authority.**
- **`Skill` trait vs `SkillRegistry`**: trait in `echo_core::tools::skill`,
  registry in `echo_execution::skills`. Root `src/skills/mod.rs` re-exports
  both. **No parallel authority.**
- **`workflow` module**: root `src/workflow/mod.rs:66` is a thin
  re-export (`pub use echo_orchestration::workflow::*;`) plus a nested
  `pub mod orchestration` alias and two root-only modules (`dsl.rs`,
  `loader.rs`). The `Graph`/`GraphBuilder` etc. types all originate in
  `echo_orchestration::workflow`. **No parallel authority.**
- **`tasks` module**: root `src/tasks.rs` is a thin re-export of
  `echo_orchestration::tasks` plus a small `register_task_tools` helper
  that wires the framework task tools into a `ReactAgent`. The helper is
  an adapter, not a second task authority. **No parallel authority.**
- **`compression`/`audit`**: root modules are pure re-exports.
  **No parallel authority.**

### Cycle-by-other-means check

No sub-crate imports the root facade, but the root facade imports every
sub-crate. That is the expected one-way shape. The macro layer
(`echo_macros`) generates code that, when expanded inside the root crate,
refers back to `::echo_agent::...` paths — but this is a *compile-time
path* in the consuming crate, not a Cargo dependency from `echo_macros`
to `echo_agent`. `echo_macros` builds cleanly without `echo_agent` in its
dependency graph (verified by reading `echo-macros/Cargo.toml`).

No circular include path, no dev-dep cycle, no build-time cycle.
