## Claim

The provider adapter contract (`ProviderAdapter` trait + `ProviderFactory`)
is a thin, lossless customization surface: it lets each provider declare
identity, endpoint, auth, thinking protocol, cache policy, and a request
preparation hook, without re-introducing transport, scheduling, or state
authority at the adapter layer. The neutral-contract crate compiles clean and
its LLM unit tests pass.

## Deviations

- `ThinkingProtocolPreference` (`traits.rs:96-107`, transport layer) and
  `ThinkingProtocol` (`thinking.rs:270-296`, framework layer) model
  overlapping concepts with different variant sets. The transport enum lacks
  `AnthropicThinkingBudget` / `AnthropicAdaptive` (it only has
  `OpenAiReasoningEffort` / `EnableThinkingFlag` / `GlmReasoningEffort` /
  `DeepSeekDual` / `None`) because Anthropic has its own request builder and
  does not route through the shared OpenAI-compat transport. Not a defect —
  the two enums serve different code paths — but a contributor reading both
  could be confused about which is authoritative. See finding
  F-LLM-01-P3-02.
- `ProviderAdapter::prepare_request` takes `&mut ChatCompletionRequest`
    (the OpenAI-shaped wire body), not the neutral `ChatRequest`. This couples
    the hook to the OpenAI-compatible wire format. For the providers that use
    the shared transport (OpenAI, DeepSeek, DashScope, GLM) this is fine;
    Anthropic does not use `prepare_request` (it builds its own body). Not a
    loss, but the hook is transport-format-specific.

## Conclusion

The adapter contract is thin and lossless: declarations only, no scheduling or
state authority, and `ProviderFactory` boxes everything to the neutral
`LlmClient`. The crate compiles clean and the LLM test suite is green. The
two deviations are naming/layering observations (P3), not semantic loss.
Supports the task's positive answer: the neutral contract can be implemented
without providers having to reimplement transport or carry provider-specific
trait objects.
