## Claim

The diff/edit tools apply changes safely: they detect conflicting concurrent
writes, perform atomic (crash-safe) file replacement, handle ambiguous
(old_content) matches without silent corruption, and the result of an edit is
verified to match the requested change before reporting success.

## Method

Static inspection of `echo-tools/src/files/edit.rs` (EditFileTool),
`echo-tools/src/files/files.rs` (WriteFileTool, UpdateFileTool, MoveFileTool,
AppendFileTool, CreateFileTool, DeleteFileTool), and `echo-tools/src/files/diff.rs`
(DiffTool). Cross-checked against the existing regression suite:

```text
cd echo-agent
cargo test -p echo_tools --lib --features "shell files git" --locked
```

Procedures:

1. Read each tool's read-modify-write body and identify the durability /
   atomicity primitive used (`tokio::fs::write`, `tokio::fs::rename`,
   temp-file-then-rename, etc.).
2. Identify conflict-detection mechanisms (expected-hash, advisory lock,
   multi-occurrence gate, dry_run preview).
3. Compare `EditFileTool` and `UpdateFileTool` semantics to determine
   whether they are duplicate authorities with divergent safety.
4. Inspect `git_checkpoint` integration for backup/rollback correctness.
5. Execute the existing regression suite to confirm what is actually tested.

## Expected Result

- All mutating file tools use atomic temp-file-then-rename (or document
  why not) so a crash mid-write cannot corrupt the target file.
- All read-modify-write tools detect concurrent modification by default
  (or at least optionally, with the optional path correctly documented).
- No two tools implement the same edit/replace semantics with different
  safety invariants.
- Ambiguous multi-occurrence matches are always rejected before write.

## Result

- Exit code: 0 (test suite passed; the *claim* failed, not the commands)
- Summary:

1. **Atomic write — claim NOT supported.** Every mutating file tool uses
   in-place `tokio::fs::write(&path, content)`:

   | Tool | Path | Atomic? |
   |---|---|---|
   | `WriteFileTool` | files.rs:699 | No — in-place overwrite |
   | `UpdateFileTool` | files.rs:963 | No — in-place overwrite |
   | `EditFileTool` | edit.rs:231 | No — in-place overwrite (creates `.bak` first at edit.rs:222-228) |
   | `CreateFileTool` | files.rs:190 | No — but content is empty, low risk |
   | `AppendFileTool` | files.rs:834 | No — but append is naturally idempotent-ish |

   `tokio::fs::write` opens with `O_WRONLY|O_CREAT|O_TRUNC` and writes the
   payload in one (or a few) `write(2)` syscalls, then `fsync`. If the
   process is interrupted between `truncate` and the final `fsync`, the file
   is left truncated/partial — *not* a crash-safe write. The standard fix
   (write to `path.tmp`, `fsync`, atomic `rename(path.tmp, path)`) is not
   used. The `EditFileTool` mitigates this by creating a `{path}.bak`
   sidecar (edit.rs:222-228) that allows manual recovery, but the live file
   is still corrupted on crash, and the `.bak` is never cleaned up. The
   `WriteFileTool` does not even create a `.bak`.

   This is recorded as F-EXT-02-P1-02.

2. **Conflict detection — partial.** `WriteFileTool` accepts an optional
   `expected_hash` parameter (files.rs:608-611, 641-670) and rejects the
   write if the file's current SHA-256 differs from the hash the caller
   obtained from a prior `read_file`. The existing test
   `write_file_rejects_stale_content_hash` (files.rs:1348-1395) executes
   this path and passed in this validation run. **This is the only conflict
   guard in the file family, and it is opt-in.** `UpdateFileTool`,
   `EditFileTool`, and `AppendFileTool` perform no concurrent-write check;
   a read-modify-write race silently loses whichever side writes second.
   `EditFileTool` mitigates only by leaving a `.bak`.

3. **Ambiguous-match handling — divergent.** `EditFileTool` (edit.rs:167-178)
   rejects the call when `old_content` matches multiple locations and
   `replace_all` is not set, returning a helpful error with all occurrence
   line numbers. `UpdateFileTool` (files.rs:961) silently calls
   `content.replacen(old_content, new_content, 1)`, replacing only the first
   occurrence without warning. The two tools accept the same parameters
   (`path`, `old_content`, `new_content`) and perform the same operation,
   but with different safety invariants — see duplicate-authority finding
   F-EXT-02-P2-01.

4. **`UpdateFileTool` is a strict regression vs. `EditFileTool`.** Compared
   field-by-field:

   | Capability | `EditFileTool` | `UpdateFileTool` |
   |---|---|---|
   | Multi-occurrence rejection | yes | no |
   | `replace_all` mode | yes | no |
   | `dry_run` preview | yes | no |
   | Diff output | yes (unified) | no |
   | `.bak` backup | yes | no |
   | Git checkpoint | yes | no |
   | `expected_hash` guard | no | no |

   `UpdateFileTool` provides nothing `EditFileTool` does not, and lacks
   every safety feature. Per AGENTS.md "能复用就不新建,能扩展就不另起";
   per REPORTING.md duplicate-authority is P2.

5. **Edit success is not verified.** After `tokio::fs::write` succeeds,
   neither `EditFileTool` nor `UpdateFileTool` re-reads the file to confirm
   the bytes match `updated`. This is normally fine (write either succeeds
   or returns an error), but it means a partial write from a full-disk or
   quota condition is reported as success if `write(2)` returns Ok after a
   short write that the kernel later truncates. Low-impact in practice;
   noted here for completeness.

6. **Existing regression suite — passed.** All 118 tests in `echo_tools`
   with `--features "shell files git"` passed, including
   `write_file_rejects_stale_content_hash`, `read_file_is_utf8_safe_and_rejects_oversized_single_lines`,
   `test_create_file_lands_in_context_working_dir`, and
   `test_list_dir_uses_context_working_dir`. The tests corroborate V01
   (path confinement) and the optional hash guard, but **no test exercises
   crash-mid-write recovery, concurrent-write races on `EditFileTool` /
   `UpdateFileTool` / `AppendFileTool`, or `UpdateFileTool` first-match
   ambiguity** — the safety gaps identified above are uncovered.

## Deviations

- The `.bak` file is created with `format!("{}.bak", path.display())`
  (edit.rs:222), which places it next to the original without any uniqueness
  suffix. Two concurrent `EditFileTool` invocations on the same file would
  overwrite each other's `.bak` before the in-place write, defeating the
  backup. The git-checkpoint tag has a similar collision issue (see V04).
- `EditFileTool` invokes `crate::git_checkpoint::create_checkpoint(&path)`
  synchronously (edit.rs:216) inside an async body; this blocks the
  tokio worker thread for the duration of three `git` subprocess invocations
  (`git rev-parse`, `git tag`, `git tag -l`). Recorded as part of
  F-EXT-02-P3-03.

## Conclusion

The diff/edit safety claim is **not supported** in three of its four
sub-clauses:

- Atomic writes: not used; in-place `tokio::fs::write` everywhere. (P1)
- Concurrent-write detection: only `WriteFileTool`, only opt-in.
- No duplicate authority: `EditFileTool` vs. `UpdateFileTool` is a clear
  duplicate with divergent safety. (P2)

The claim is supported on one sub-clause: ambiguous multi-occurrence
matching is rejected by `EditFileTool` (but not `UpdateFileTool`).

Supports findings: F-EXT-02-P1-02 (atomic writes), F-EXT-02-P2-01
(duplicate edit tool), F-EXT-02-P3-03 (sync git in async path).
