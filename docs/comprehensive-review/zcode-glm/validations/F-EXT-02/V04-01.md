## Claim

The git worktree tools (`git_worktree.rs` + `worktree_tool.rs` wrappers)
create, list, merge, and remove worktrees safely: they confine the worktree
path under `.worktrees/`, cannot be tricked into writing or force-deleting
files outside that directory, do not race with concurrent writers, honor the
agent session's `working_dir`, and recover cleanly from merge conflicts and
missing worktrees.

## Method

Static inspection of `echo-tools/src/git_worktree.rs` (the low-level
helpers) and `echo-tools/src/worktree_tool.rs` (the agent-facing Tool
wrappers), plus one executable confirmation in a throwaway git repository.

Procedures:

1. Read `create_worktree` (git_worktree.rs:37) and trace how `path_suffix`
   flows from LLM input → `WorktreeConfig::path_suffix` →
   `git_root.join(".worktrees").join(suffix)` → the
   `git worktree add` argv.
2. Read `EnterWorktreeTool::execute` (worktree_tool.rs:78) and confirm
   whether it implements `execute_with_context` (and therefore honors
   `ctx.working_dir`) or only the context-free `execute`.
3. Read `remove_worktree` (git_worktree.rs:115) and `ExitWorktreeTool`'s
   fallback when the requested path is not in `git worktree list`
   (worktree_tool.rs:195-210).
4. Read `merge_worktree` (git_worktree.rs:193) for merge-conflict handling
   and checkout side effects.
5. Empirically verify the path-traversal hypothesis by running real
   `git worktree add` invocations with a `..`-containing path in a
   throwaway repo.

Executable confirmation:

```text
rm -rf /tmp/wt-escape-test && mkdir -p /tmp/wt-escape-test
git -C /tmp/wt-escape-test init -q
git -C /tmp/wt-escape-test config user.email t@t
git -C /tmp/wt-escape-test config user.name t
git -C /tmp/wt-escape-test config commit.gpgsign false
printf 'a\n' > /tmp/wt-escape-test/a.txt
git -C /tmp/wt-escape-test add .
git -c commit.gpgsign=false -C /tmp/wt-escape-test commit -qm init

# Reproduce path_suffix = "../evil-target/wt":
git -C /tmp/wt-escape-test worktree add -b evilbr2 \
    /tmp/wt-escape-test/.worktrees/../evil-target/wt
git -C /tmp/wt-escape-test worktree list
```

Environment: macOS 15.5, git 2.x.

## Expected Result

- A `path_suffix` containing `..` is either rejected by Rust-level
  normalization or confined by `git_root.join(".worktrees")` so that the
  final worktree path stays inside `.worktrees/`.
- All three worktree tools honor the agent's `working_dir` (use
  `execute_with_context`).
- Merge conflicts are reported and the repository is left in a clean state.
- `remove_worktree` on a missing worktree is rejected, not silently
  "constructed from path basename" and force-deleted.
- Branch-name flag injection (`-b <flag-shaped-name>`) is blocked by a `--`
  separator.

## Result

- Exit code: 0 (the executable reproduction succeeded; the *claim* failed)
- Summary:

1. **Path traversal via `path_suffix` — claim NOT supported.**
   `git_worktree.rs:44-51` computes the worktree directory as
   `git_root.join(".worktrees").join(path_suffix)`. `Path::join` does not
   normalize, so a `path_suffix` like `"../evil-target/wt"` yields the
   literal path `…/.worktrees/../evil-target/wt`. `git worktree add`
   accepts this and creates the worktree at the resolved location
   **outside `.worktrees/`**.

   Empirically confirmed:
   ```
   $ git -C /tmp/wt-escape-test worktree add -b evilbr2 \
       /tmp/wt-escape-test/.worktrees/../evil-target/wt
   Preparing worktree (new branch 'evilbr2')
   HEAD is now at bc69f74 init
   $ git -C /tmp/wt-escape-test worktree list
   /private/tmp/wt-escape-test                 bc69f74 [master]
   /private/tmp/wt-escape-test/evil-target/wt  bc69f74 [evilbr2]
   ```

   `EnterWorktreeTool` (worktree_tool.rs:88-91, 97-101) accepts
   `path_suffix` as a free-form string directly from LLM-supplied JSON and
   forwards it to `create_worktree` with no sanitization. The branch field
   is sanitized for path purposes (git_worktree.rs:47-50) but `path_suffix`
   is not.

   Recorded as F-EXT-02-P1-01 (P1). This is a concrete data-integrity
   risk: a malicious prompt or confused agent can write a worktree (and
   subsequently run `git worktree remove --force` on it) at arbitrary
   locations outside `.worktrees/`.

2. **Cleanup amplifies the traversal — `--force` + branch `-D`.** Even
   without a malicious caller, the cleanup path is destructive:
   `remove_worktree` (git_worktree.rs:119-146) always passes `--force` to
   `git worktree remove` and always force-deletes the branch with
   `git branch -D`. If the worktree at the escaped path contains user
   files (because the path was confused with an existing project dir),
   `--force` discards them. AGENTS.md explicitly calls out "防止用户无
   意中的数据丢失" as a legitimate safety concern — this qualifies.

3. **Worktree tools ignore `ctx.working_dir` — claim NOT supported.**
   `EnterWorktreeTool`, `ExitWorktreeTool`, and `ListWorktreesTool` all
   implement `fn execute` (worktree_tool.rs:78, :175, :278), *not*
   `execute_with_context`. The default `repo_path` is `"."` (e.g.
   worktree_tool.rs:92-95), interpreted relative to the *process* cwd, not
   the agent's session-bound working directory. This means an agent
   operating inside a worktree calling `enter_worktree` would create the
   new worktree under the wrong directory. Compare to `git.rs` which uses
   `effective_repo_path` (git.rs:552-569) to honor `ctx.working_dir` —
   the worktree tools are inconsistent with their sibling git tools.

   Recorded as F-EXT-02-P2-02.

4. **Missing-worktree fallback force-deletes an unrelated branch.**
   When `exit_worktree` is called with a `worktree_path` that is not in
   `git worktree list` (worktree_tool.rs:195-210), the code synthesizes a
   `ManagedWorktree { managed: true, branch: <basename-of-path> }` and
   proceeds to call `remove_worktree`. `remove_worktree` then runs
   `git branch -D -- <basename>` (git_worktree.rs:140). If the user has a
   real branch whose name matches the path's final component (e.g. the
   path ends in `/main`), that branch is force-deleted. Recorded as
   F-EXT-02-P2-03.

5. **Merge conflict handling leaves repo in MERGE state.**
   `merge_worktree` (git_worktree.rs:202-232) runs `git checkout
   <target>` then `git merge --no-edit <branch>`. If the merge conflicts,
   it returns `Err("Merge conflict or error: <stderr>")` with no rollback
   — the repository is left in the MERGE state with conflict markers in
   working files. The caller (an agent, or a user looking at the repo
   later) must manually `git merge --abort`. Recorded as
   F-EXT-02-P2-04.

   Side effect: `git checkout <target_branch>` (line 202) operates on the
   main worktree's HEAD. If another subagent or the user is working in
   that worktree concurrently, the checkout disrupts them. Concurrent
   merges to the same target branch are not serialized.

6. **Branch name flag-injection is partially possible.**
   `git_worktree.rs:67` passes `-b &config.branch` without a following
   `--`. Empirically, `git worktree add -b --force <path>` parses
   `--force` as the branch name (it printed `Preparing worktree (new
   branch '--force')`). Other flag-shaped branch names that match real
   `git worktree add` options (`--detach`, `--no-checkout`, `-B`) could
   silently change semantics. The `git_branch` tool in git.rs:436-441
   correctly defends with a `--` separator; the worktree helper does not
   match that pattern. Recorded as F-EXT-02-P2-05.

7. **Existing tests do not cover any of the above.** The only tests in
   `git_worktree.rs` and `worktree_tool.rs` are
   `test_find_git_root` / `test_find_git_root_non_repo` (git_worktree.rs:254-267),
   which verify the helper returns a path or an error. There is **no
   test** for: path-traversal rejection, missing-worktree fallback,
   merge-conflict recovery, concurrent-writer behavior, or `ctx.working_dir`
   honoring. The safety gaps are uncovered.

## Deviations

- The branch-name sanitizer (git_worktree.rs:47-50) prevents slashes and
  most punctuation from reaching the *path*, but is not applied to the
  *git command's* branch argument, so it does not defend against flag
  injection.
- `merge_worktree`'s `--` placement (git_worktree.rs:203, 219) correctly
  protects against pathspec injection — that part is sound; the defect is
  the missing conflict rollback, not arg injection.

## Conclusion

The worktree safety claim is **not supported**. The single most serious
defect (F-EXT-02-P1-01) is an executed path-traversal via `path_suffix`
that lets an LLM-influenced caller write (and later force-delete) a
worktree outside `.worktrees/`. Layered on top:

- All three worktree tools skip `execute_with_context`, ignoring the
  agent's `working_dir` (P2).
- `exit_worktree` synthesizes a "managed" entry from the path basename
  and force-deletes whatever branch matches it (P2).
- `merge_worktree` leaves the repo in a conflicted MERGE state on failure
  and disrupts concurrent workers in the main worktree (P2).
- `git_worktree add -b <branch>` lacks the `--` separator that sibling
  tools use to prevent flag-shaped branch names (P2).

Supports findings: F-EXT-02-P1-01 (path traversal), F-EXT-02-P2-02
(ignored `working_dir`), F-EXT-02-P2-03 (missing-worktree fallback),
F-EXT-02-P2-04 (merge conflict no-rollback), F-EXT-02-P2-05 (branch-name
flag injection).
