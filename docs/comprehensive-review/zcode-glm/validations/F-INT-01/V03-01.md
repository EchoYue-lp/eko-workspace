## Claim

Each transport (`Stdio`, `Http`, `Sse`) closes pending requests on
disconnect, retries transient failures, honors cancellation, and never
deadlocks; failures surface as structured `McpError` variants.

## Method

Static inspection of the three transport implementations, the
`McpTransport` trait, and `McpError`.

```text
1. Read echo-integration/src/mcp/transport/mod.rs (trait)
2. Read echo-integration/src/mcp/transport/stdio.rs (379 lines)
3. Read echo-integration/src/mcp/transport/sse.rs (434 lines)
4. Read echo-integration/src/mcp/transport/http.rs (270 lines)
5. Verify McpError variants vs echo-core/src/error.rs:230-249
6. Grep notification_tx.send usage across transports
```

## Expected Result

All three transports: (a) clean up pending requests on close,
(b) provide bounded timeouts, (c) reconnect or fail-fast on transient
errors, (d) honor a cancellation token, (e) feed the notification channel
when the transport advertises `notification_rx()`.

## Result

- Exit code: not-applicable (static review)
- Duration: n/a
- Summary: StdioTransport passes all five criteria. **SseTransport and
  HttpTransport fail** on discrete criteria — see Deviations.

  **StdioTransport — PASS**
  - Pending cleanup on stdout EOF (`stdio.rs:124-138`): every waiting
    request receives a synthetic `JsonRpcResponse` with `code = -32000`,
    message `"MCP transport closed: stdout reached EOF"`. No leak.
  - Bounded timeouts: 30 s per `tools/list` / `resources/list` /
    `prompts/list` page in `client.rs`, 120 s for general `send`
    (`stdio.rs:298`).
  - No retry (correct for stdio — child death is terminal).
  - `Drop` impl (`stdio.rs:362-372`) re-spawns a kill+wait task; if the
    runtime has already shut down the child may leak (best-effort, noted
    in F-INT-01-P3-02).
  - `notification_rx()` returns `None` (`stdio.rs:357-359`) — correct,
    server-push over stdio requires routing through stdout and is
    currently only logged, not exposed.

  **HttpTransport — FAIL on notification channel (criterion e)**
  - `notification_rx()` returns `Some(...)` (`http.rs:240-244`) and the
    request advertises `Accept: application/json, text/event-stream`
    (`http.rs:158`), but **`notification_tx.send(...)` is never called
    anywhere in `http.rs`** (verified by grep). The broadcast channel
    exists but is never fed.
  - Consequence 1: server-push notifications on Streamable HTTP (the GET
    SSE stream defined by MCP) are not implemented — `Accept:
    text/event-stream` is advertised but no GET listener runs.
  - Consequence 2: the 202-Accepted branch (`http.rs:195-211`) awaits a
    `oneshot::Receiver` for the request id, but the only thing that
    fulfills that receiver is the synchronous-response branch's path,
    which is *not* taken on 202. The async response that the server will
    eventually push has nowhere to arrive. **A 202 response therefore
    always blocks until the 60 s timeout** (`http.rs:201`) and then
    returns `McpError::ProtocolError("等待 HTTP 异步响应超时")`.
  - Retry: `MAX_RETRIES = 3`, exponential backoff with ±25 % jitter on
    retryable errors (`http.rs:170-194`); `is_retryable_error`
    (`http.rs:248-270`) covers timeout/connect/DNS/TLS/502/503/504 +
    message-pattern matching.
  - Cancellation: none — no `CancellationToken` field; in-flight `send`
    can only fail via the 60 s / 120 s timeouts.

  **SseTransport — FAIL on reconnect-after-clean-close + retry budget
  (criteria c, d)**
  - Outer reconnect loop (`sse.rs:74-94`):
    ```rust
    match Self::run_sse_loop(...).await {
        Ok(_) => { break; }            // !!! breaks on clean stream end
        Err(e) => { retry_count += 1; ... }
    }
    ```
    `run_sse_loop` returns `Ok(())` when the `bytes_stream` ends
    (`sse.rs:227-228`, the `while let Some(chunk)` falls through). A
    clean SSE close therefore **terminates the transport permanently** —
    the `MAX_RETRIES = 5` budget is only consumed by `Err` paths
    (network errors). Old-style SSE servers that close the connection
    periodically (e.g. behind a load balancer idle timeout) become
    unreachable until the user manually reconnects.
  - `retry_count` is never reset to 0 across successful reconnects
    (`sse.rs:67-94`). 5 lifetime transient errors — even spaced hours
    apart — permanently disable the transport.
  - Pending cleanup: not implemented — there is no `Err -> drain pending
    with synthetic responses` step; orphaned oneshots just time out
    individually.
  - Cancellation: `CancellationToken` correctly threaded into the SSE
    loop (`sse.rs:33, 54, 74, 105, 117, 184`) — this criterion passes.
  - Notification publish: `notification_tx.send(notif)` at
    `sse.rs:301` — passes criterion (e).

  **McpError coverage** (`echo-core/src/error.rs:230-249`): all
  transport failures map to one of `ConnectionFailed`,
  `InitializationFailed`, `ProtocolError`, `ToolCallFailed { code,
  message }`, `TransportClosed`. No transport invents undocumented
  errors.

- Log/artifact: none.

## Deviations

1. **HttpTransport `notification_rx()` is a lie** — advertises a channel
   that is never fed. This is Finding **F-INT-01-P1-01** (P1): the
   202-Accepted async path is unreachable in practice.
2. **SseTransport breaks on `Ok(_)`** — clean close = permanent
   disconnect. This is Finding **F-INT-01-P2-01**.
3. **SseTransport retry_count never resets** — 5 lifetime errors kills
   the transport. This is Finding **F-INT-01-P2-02**.
4. **No tool-call cancellation on any transport.** The framework
   `Tool::execute` does not accept a `CancellationToken` (per F-EXT-01
   V01-01), so this is a framework-level limitation, not unique to MCP.
   Recorded as **F-INT-01-P2-03** (the MCP-specific part: server-side
   `notifications/cancelled` only logs and does not track in-flight
   requests, so even a future client-side cancel hook could not abort an
   in-flight call).

## Conclusion

Validation **failed**: StdioTransport is robust, but HttpTransport
advertises a notification surface it never feeds (P1) and SseTransport
has two reconnect-budget defects (P2). The framework-contract claim
"MCP preserves framework contracts" holds for the lifecycle and tool
adapter (V01, V02) but **does not hold for transport resilience**.
