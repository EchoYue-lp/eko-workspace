## Claim

`McpConfigFile` parses mcp.json entries defensively: invalid JSON,
disabled entries, and ambiguous `command`-vs-`url` configurations produce
structured `McpError` variants rather than panics; the validator rejects
shell-meta injection, blocked commands, and path traversal in stdio
commands.

## Method

Static inspection of `config_loader.rs`, `server_config.rs`, and the
four stdio-command-validator tests.

```text
1. Read echo-integration/src/mcp/config_loader.rs (261 lines)
2. Read echo-integration/src/mcp/server_config.rs (164 lines)
3. Read echo-integration/src/mcp/transport/stdio.rs:345-379 tests
4. Walk each McpError construction site:
   - McpConfigFile::parse  (config_loader.rs:213-220)
   - McpConfigFile::from_file (config_loader.rs:227-237)
   - McpServerEntry::to_server_config (config_loader.rs:152-203)
   - validate_stdio_command (config_loader.rs:236-261)
   - StdioTransport::validate_mcp_command (stdio.rs:311-344)
5. Confirm no panic-prone API (.unwrap/.expect/byte slice) on user data
```

## Expected Result

- All error paths return `Result<_, ReactError::Mcp(McpError::...)>`.
- No `.unwrap()` / `.expect()` / byte-slice indexing on JSON or
  user-supplied strings.
- Disabled entries are silently skipped by `to_server_configs` but raise
  `McpError` if explicitly converted via `to_server_config`.
- Missing both `command` and `url` is rejected.

## Result

- Exit code: not-applicable (static review)
- Duration: n/a
- Summary: All four expectations hold.

  **JSON parse failure** (`config_loader.rs:213-220`):
  `serde_json::from_str(s).map_err(|e| ReactError::Mcp(McpError::ProtocolError(
     "mcp.json 格式解析失败: {e}")))` — structured error, no panic.

  **File-read failure** (`config_loader.rs:227-237`):
  `std::fs::read_to_string(path).map_err(...)` →
  `McpError::ConnectionFailed("读取配置文件失败 (...)")`.

  **Disabled handling** (intentional split):
  - `McpConfigFile::to_server_configs` (`config_loader.rs:222-232`)
    silently skips entries with `disabled: true` (just `tracing::debug`).
  - `McpServerEntry::to_server_config(name)` on a disabled entry
    (`config_loader.rs:158-164`) returns
    `McpError::ConnectionFailed("服务端 '...' 已禁用")`.
  - The application layer uses both paths correctly: state.rs stores the
    full config, `tauri/commands/mcp.rs:520` skips disabled before
    calling `to_server_config`, and the explicit-conversion error is a
    safety net.

  **Ambiguous / missing fields** (`config_loader.rs:166-203`):
  `command` wins over `url`; if neither is present, returns
  `McpError::ConnectionFailed("服务端 '...' 配置无效: stdio 模式需提供
  'command', HTTP 模式需提供 'url'")`. No silent fallthrough.

  **Transport selection** (`config_loader.rs:178-187`): `transport:
  Some("sse")` → `TransportConfig::Sse`; anything else (including
  `None`) → `TransportConfig::Http` (Streamable HTTP). Matches the
  documented contract.

  **Stdio command validation** — `validate_stdio_command`
  (`config_loader.rs:236-261`):
  - Rejects shell meta-chars `| ; & $ \` > < ( ) \n \r`
    (`DANGEROUS_SHELL_CHARS`).
  - Rejects blocked command prefixes: `sudo su dd chmod chown reboot
    shutdown halt` (`BLOCKED_COMMANDS`).
  - Rejects `..` (path traversal).
  All three return `McpError::ProtocolError` with a precise message.
  Uses `command.split_whitespace().next().unwrap_or("")` — `unwrap_or`
  is panic-safe (consistent with AGENTS.md no-panic rule).

  **Defense-in-depth at spawn time** —
  `StdioTransport::validate_mcp_command` (`stdio.rs:311-344`) adds a
  second layer: rejects empty command, bare shells
  (`sh/bash/zsh/fish/dash/cmd/powershell/pwsh`) with a warning, and
  argument-injection prefixes (`--upload-pack`, `-o`, `--config`). This
  catches anything the loader validator missed (e.g. when the transport
  is constructed directly via `McpServerConfig::stdio`).
  - **Note (not a finding):** `validate_mcp_command` warns but does not
    reject bare shells, and the `-o`/`--config` blocklist is best-effort.
    Consistent with AGENTS.md: MCP is user-configured locally, the real
    trust boundary is "who wrote mcp.json", so lightweight validation is
    the right level.

  **In-file test coverage** (`stdio.rs:350-378`): four `#[test]`s
  covering empty command, `--upload-pack=`, `ssh -o`, legitimate
  `npx -y @modelcontextprotocol/server` / `python -m`, and plain
  paths/`uvx`. All parse and assert `.is_ok()` / `.is_err()` without
  panic-prone APIs.

  **No panic-prone API** on user data: grep found no `.unwrap()` /
  `.expect()` / byte-slice indexing on JSON content, command strings, or
  args. The single `.unwrap_or("")` in `validate_stdio_command` is the
  safe form.

## Conclusion

mcp.json parsing is defensive and panic-free; invalid configurations
surface as structured `McpError` variants at the correct layer. The
two-stage validation (loader + spawn-time) matches the AGENTS.md
"lightweight validation, user-trusts-their-own-config" model and avoids
the historical over-gating anti-pattern. Supports the task report's
"configuration handling preserves framework contracts" claim.
