## Claim

For each of the four plugin-owned component types (skills, hooks, MCP,
Subagents), exactly one framework primitive owns the registration
mechanism and exactly one EKO adapter owns the activation policy. No
parallel registration authority exists in either repository. The
adapter (`PluginRuntimeService`) delegates every registration to a
framework primitive; it does not re-implement dependency resolution,
source tagging, hook validation, or subagent dispatch.

If any component type has two registration authorities, or if the
adapter re-implements a framework-owned mechanism, that falsifies the
"single authority" half of the X-PLG-01 question.

## Expected Result

- Skills: `SkillRegistry` (echo-execution) + `SkillLoader` (echo-execution)
  are the sole registration primitives. The adapter calls
  `load_plugin_skills_from_dir` → `discover_skills_inner` which registers
  into both the catalog and progressive registries. No application code
  constructs a `SkillRegistry` or calls `register_descriptor` directly.
- Hooks: `HookRegistry` (echo-execution) is the sole registration
  primitive. The adapter calls `register_plugin_hooks` via
  `PluginIntegrator::wire_all`. User hooks land in the same registry
  via `HookConfigLoader` → `register_user_hooks` under
  `HookSource::UserConfig`.
- MCP: `McpManager` + `connect_mcp_from_config`/`disconnect_mcp`
  (echo_agent) are the sole primitives. The adapter calls
  `load_mcp_config` via `wire_all`; `unload_agent_components` calls
  `disconnect_mcp`.
- Subagents: `SubagentRegistry` (echo_agent) +
  `register_subagent_with_definition`/`register_subagent_factory`/
  `unregister_subagent` are the sole primitives. The adapter calls
  `register_plugin_agents` which uses the first two; unload calls
  `unregister_subagent`.
- No parallel orchestrator: `PluginRegistry::new` appears only inside
  `PluginRuntimeService::registry_for` (+ `#[cfg(test)]`);
  `PluginIntegrator::new` only inside `replace_agent_components`.
- The two bootstrap paths (base MCP `runtime.rs:110`, built-in Subagent
  `infra.rs:847-851`) are one-time startup registrations, not plugin
  lifecycle operations.
- `register_lifecycle` has zero non-test callers.

## Conclusion

Supports X-PLG-01 Current Path §1 ("The adapter join"). For each of
the four component types, exactly one framework primitive owns
registration and exactly one EKO adapter owns activation policy. The
adapter is thin: it delegates every registration to a framework
primitive and does not re-implement any framework-owned mechanism. No
parallel registration authority exists. The two bootstrap paths are
not lifecycle operations.

This is the load-bearing invariant for the X-PLG-01 question's
"joined through ... adapters" half: the join exists, it is single-
threaded, and it respects the framework/application boundary.

The finding X-PLG-01-P3-01 (`register_lifecycle` zero production
callers) is about a pub API that bypasses the atomic swap, not about
a second registration authority for any component type.
