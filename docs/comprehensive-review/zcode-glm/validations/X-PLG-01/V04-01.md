## Claim

After `unload_agent_components` runs for a given plugin, no plugin-owned
tool, Subagent, hook, MCP-adapted-tool, skill-catalog entry, skill-hook
entry, progressive-skill entry, or context projection belonging to that
plugin survives in any framework registry. Framework-owned singletons
(the three progressive-disclosure tools, the `AgentDispatchTool`) are
refreshed (not removed), which is correct because they are not plugin-
owned.

If any plugin-owned registration survives `unload_agent_components`,
that falsifies the "no stale registrations" property implied by the
X-PLG-01 question's "source-scoped" and "reversible" halves.

## Conclusion

Supports X-PLG-01 Current Path §4 ("Stale-registration search") and
the "source-scoped" + "reversible" halves of the X-PLG-01 question.
After `unload_agent_components`, no plugin-owned tool, Subagent, hook,
MCP-adapted-tool, skill-catalog entry, skill-hook entry, progressive-
skill entry, or context projection survives in any framework registry.

Framework-owned singletons (the three progressive-disclosure tools and
the `AgentDispatchTool`) are correctly refreshed rather than removed —
they persist as framework singletons with state that reflects the
unload.

This validation, combined with V02 (reversibility) and V03 (failure
rollback), confirms the adapter join's core safety property: under
normal operation, unload is exhaustive; under failure, the rollback
unloads the candidate before restoring the previous (so no partial
candidate registration survives either).
