## Claim

The full plugin lifecycle (discover → prepare → activate → use →
reload → unload) is reversible at each step. Specifically:

- **Reload is a full unload+rewire**, not an in-place mutation of the
  live agent's tool set. `apply_candidate` `mem::replace`s the previous
  state out, then `replace_agent_components` unloads the previous from
  the live agent before wiring the candidate.
- **Unload is the exhaustive inverse of wire** for all four component
  types (skills, hooks, MCP, Subagents). Each wire operation has a
  corresponding unload operation that removes exactly what wire added.
- **No step leaves the live agent or the persisted state in an
  indeterminate intermediate state** under normal (non-failure)
  operation.

If reload mutates the live agent's tools in-place without unloading
the previous set first, or if any unload operation is not the inverse
of its wire operation, that falsifies the "reversible" half of the
X-PLG-01 question.

## Expected Result

- `scan_scopes` clears the plugins map before scanning (`registry.rs:
  126`), so re-discovery produces a fresh registry (idempotent).
- `prepare_application_components` is pure (returns `Ok(prepared)` or
  `Err(errors)`; no mutation of `state` or the live agent).
- `apply_candidate` performs unload-then-wire in that order, inside a
  single agent write lock.
- `reload()` → `apply_candidate` → full unload+rewire. No in-place
  shortcut.
- `unload_agent_components` calls the exact inverse of each wire
  operation, and each inverse is exhaustive:
  - `unregister_subagent` → `SubagentRegistry::remove` clears all three
    internal maps (agents + definitions + factories).
  - `unregister_skills_by_source` clears catalog + progressive +
    skill-hooks + projections + refreshes the 3 progressive tools.
  - `hook_registry.unregister(&HookSource::Plugin(name))` removes the
    single source entry.
  - `disconnect_mcp` enumerates adapted tools from the live client,
    removes each, then disconnects.

  wire for all four component types.

  Step 1 — DISCOVER (idempotent re-scan):

  | Site | Behaviour |
  |---|---|

  Re-discovery is idempotent: a second `scan_all` on the same dir set
  produces the same registry (modulo the collision non-determinism in
  X-PLG-01-P2-01).

  Step 2 — PREPARE (pure parse):

  | Site | Behaviour |

  Prepare is pure: it either produces a `PreparedApplicationComponents`
  or returns an error, without touching the live agent.

  Step 3 — ACTIVATE (unload-then-wire, not in-place):

  | Line | Operation |
  |---|---|
  | `plugin_runtime.rs:606` | `let previous_registry = mem::replace(&mut state.registry, ...)` — previous moved out |
  | `plugin_runtime.rs:610` | `let previous_framework = mem::take(&mut state.framework_components)` — previous moved out |
  | `plugin_runtime.rs:611` | `let previous_prepared = mem::take(&mut state.prepared)` — previous moved out |

  The order is strict: previous is fully unloaded from the live agent
  before candidate is wired. Both happen inside `agent_handle.
  write_async(...)`, so no concurrent tool call can observe the
  intermediate (unloaded) state.

  Step 5 — RELOAD (full unload+rewire, no shortcut):

  | Site | Behaviour |
  |---|---|
  | `plugin_runtime.rs:201-207` `reload()` | builds fresh candidate, `scan_registry`, `apply_candidate(&mut state, candidate)` |

  `enable`/`disable`/`install`/`uninstall`/`configure` all funnel

## Conclusion

Supports X-PLG-01 Current Path §2 ("The lifecycle trace"). The full
plugin lifecycle is reversible at each step:

- Discover is idempotent (fresh registry per scan).
- Prepare is pure (no live-agent side effect).
- Activate is unload-then-wire inside a single write lock (no
  observable intermediate state).
- Reload is a full unload+rewire (no in-place shortcut).
- Unload is the exhaustive inverse of wire for all four component
  types (verified by reading each framework primitive's removal logic).

This is the load-bearing invariant for the X-PLG-01 question's
"reversible" half: every registration has a matching, exhaustive
deregistration, and reload does not mutate the live agent in-place.

The collision non-determinism (X-PLG-01-P2-01) affects WHICH skill/
plugin loads, not the reversibility of the load itself — once a
particular skill/plugin is chosen, its wire/unload cycle is fully
reversible.
