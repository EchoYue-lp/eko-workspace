## Claim

`apply_candidate` has eight failure checkpoints, each with a defined
rollback that restores the previous state. Checkpoints 1-6 are exact
(no mutation has reached the live agent or persisted state before the
checkpoint, so the previous state is byte-identical). Checkpoints 7-8
are best-effort: the rollback re-runs `wire_all` on the previous
registry, which may produce a subset under transient failures (MCP
server down, skill file deleted), but the candidate is always fully
unloaded before the previous is restored — no partial candidate state
leaks into the live agent.

If any checkpoint fails to restore the previous state, or if a partial
candidate registration survives a rollback, that falsifies the
"failure-safe" half of the X-PLG-01 question.

## Deviations

One observation (not a deviation from the claim, but documented for
completeness): checkpoints 7-8 are best-effort because the rollback
re-runs `wire_all(previous_registry)` which may fail to reconnect a
transient MCP server or reload a deleted skill file. In that case,
`state.framework_components` is set to `restored.components_by_plugin`
(the actually-wired subset), and the `restored.errors` are surfaced in
the returned error message. This is the correct design: the state
reflects what is actually wired in the live agent; the alternative
(snapshotting live tool registrations) is infeasible for network
resources. The user sees the error and can retry.

This is NOT promoted to a finding because it is inherent to rolling
back live network resources, not a defect in the rollback logic.

## Conclusion

Supports X-PLG-01 Current Path §3 ("The failure-rollback checkpoints")
and the "failure-safe" half of the X-PLG-01 question. All eight
checkpoints have defined rollback paths:

- Checkpoints 1-6 are exact (no mutation reaches the live agent or
  persisted state before the checkpoint).
- Checkpoints 7-8 are best-effort (re-run `wire_all`), but the
  candidate is always fully unloaded before the previous is restored —
  verified in both `replace_agent_components`'s inner rollback (line
  823-828, 847-852) and the post-swap reverse swap (line 667-675).

No partial candidate state leaks into the live agent on any failure
path. The `PluginLifecycleManager`'s remove-before-cleanup ordering
ensures failed lifecycle cleanup does not block re-registration.

The finding X-PLG-01-P3-01 (`register_lifecycle` bypassing the atomic
swap) is about a separate entry point, not about a gap in
`apply_candidate`'s checkpoint coverage.
