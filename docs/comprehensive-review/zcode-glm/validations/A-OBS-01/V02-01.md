## Claim

Observability and webhook configuration is sourced from one canonical
`AppConfig`, applied identically across TUI / REPL / Tauri / channels
modes. The same per-process emitter feeds every chat turn; the same
`RunStore` and the same prompt-assembly report feed every diagnostics
surface. Live config reloads propagate to the in-process emitter without
restart.

## Expected Result

- All four production modes derive their webhook emitter from the same
  `AppConfig.webhooks` shape.
- One emitter per process; AppState's own construction is overridden by
  every production caller.
- The prompt-assembly report flows from `infra::create_agent_with_diagnostics`
  through `AgentRuntime` to AppState.observability and is consumed by all
  three Rust diagnostics surfaces.
- Live reload is wired for headless and GUI.
- The RunStore handle is shared by primary agent and pooled agents.

## Deviations

- Channels mode does not register a TUI/CLI-style `/trace` slash command
  surface (channels.rs:349-367 has a best-effort `/runs` / `/trace`
  handler that runs against the same shared emitter and run_store, but
  it is invoked by sending an IM message that starts with `/`, not by a
  local REPL). The wiring identity is the same; only the surface differs.
- AppState's own `WebhookEmitter::from_config` at state.rs:469 is
  defensive-only. Every production caller overwrites it before any chat
  turn runs, so the duplicate construction is harmless — but it is a
  subtle maintainability trap: a future caller that forgets to override
  would silently get a second emitter (no endpoints if AppConfig had
  none, or a duplicate fan-out if it did). Not promoted to a finding
  because no current caller forgets; flagged for completeness.

## Conclusion

Supports the V02 claim for TUI / REPL / Tauri: one canonical AppConfig
feeds one per-process emitter, one RunStore, one prompt-assembly report.
Channels inherits the same shared root resources but lacks a local slash
surface and is best treated as a renderer-only mode for observability
purposes. Live reload works through `reload_from_config` for any mode
that spawns the config_watcher.

No finding arises from this validation alone; the duplicate AppState
construction is a code smell worth a future cleanup but not a defect
today.
