## Claim

The observability and webhook pipelines have known misleading-success
gaps on failure paths, and the webhook delivery retry policy is best
-effort with no operator-visible failure signal. Specifically:

1. Cron task runs that FAIL or are CANCELLED emit no webhook event (only
   the `Ok` path emits `CronTaskCompleted`).
2. Background `TaskRun` lifecycle (Completed / Failed / Cancelled /
   Paused) emits no webhook event at all — only the foreground chat
   `ChatCompleted` and the cron `CronTaskCompleted` exist.
3. Cancelled foreground chat turns produce no terminal webhook event at
   all (the observer's `completed` flag stays false because
   `AgentEvent::FinalAnswer` never fires; the synthesized
   `AgentEvent::Error` from `envelope_event_stream` would route through
   `AgentError`, but per A-CHAT-01 the ReactAgent never emits
   `Cancelled`, so the actual stream-end yields an `Error` whose source
   is `"agent_stream"` — only that error event is emitted).
4. Webhook delivery: one retry after a 2-second sleep; both failures
   log `tracing::warn!` and drop the event. No persistent queue, no
   operator metric.

## Conclusion

Supports A-OBS-01-P2-02 (cron / background-task webhook gap) and
A-OBS-01-P3-01 (cancelled-chat terminal semantics — partial corroboration
of A-CHAT-01's analysis from the observability side). The webhook
delivery retry policy is acceptable for the local-assistant threat model
(AGENTS.md: "user-extended capability is the user's responsibility"), but
the misleading-success gaps are real product defects: an operator who
configures a webhook to monitor "is my agent done" will see chat
completions and cron successes, but never see cron failures or
background-task failures.

The RunStore remains authoritative for full lifecycle facts — the
operator can always query `/runs` or the GUI observability panel — but
the PUSH channel (webhooks) is incomplete while the PULL channel
(diagnostics) is complete. This asymmetry is the root cause of the
finding's "misleading success" framing.

Does not prove that webhook delivery actually retries correctly under
network failure — that would require a mock HTTP server and is owned by
the regression-validation requirement of any future fix.
