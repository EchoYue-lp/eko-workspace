## Claim

EKO's executor and tool surfaces contain no scheduling-loop duplicate of
the framework kernel. Specifically, none of the following live in
`echo-agent-cli`:

- ready-frontier computation (`ready_task_ids`, frontier walk);
- bounded-wave dispatch (`JoinSet`, `validate_selected_wave`,
  `subagent_semaphore`);
- a second stall detector (timeout / max-poll / `note_stalled` driver);
- a retry loop that re-dispatches in EKO outside the kernel's safe-point
  re-claim;
- a second DAG validator (structural cycle / topology check);
- a second cancellation `JoinSet`/abort drain.

The retry mechanism is a one-shot `Pending` resolution in
`resolve_dispatch` that lets the kernel re-claim — not a loop in EKO.

- Retry path confirmation (executor.rs:1396-1432):
  - On `CompletionAssessment::ExecutionFailed`, the controller checks
    `claim.attempt.saturating_sub(1) < task.max_retries`.
  - If the budget allows, it calls `store.requeue_claimed_task`
    (store.rs:1066-1105), which **atomically** appends one
    `TodoUpdated(status=Pending, retry_count+1, claim=null)` event and
    rewrites the projection. This is a single event write under the
    per-run `plan_locks` mutex — NOT a loop.
  - The controller then returns `RuntimeTaskResolution::Pending`
    (executor.rs:1418). The kernel sees a non-terminal resolution, ends
    the current safe point, and re-iterates: the next `load_snapshot`
    sees the task as `Pending`, the kernel's `ready_task_ids` includes
    it, the kernel re-claims via `claim_task` (which sets `attempt` =
    new `retry_count + 1` at store.rs:1012).
  - The retry **mechanism** (loop, backoff if any, attempt counter) is
    the kernel's safe-point loop + claim's `attempt` field. The retry
    **policy** (budget = `task.max_retries`) is EKO product policy in
    `resolve_dispatch`. This matches the layering F-TSK-03 prescribes:
    "retry + backoff + verification lives behind `dispatch_task`."
- `select_ownership_safe_wave` (executor.rs:1127-1145) contract:
  - First iteration: if first task is `ReadOnly` → selected
    (selected.len() ≥ 1). If first task is a writer →
    `selected_writers.iter().all(...)` is vacuously true → selected
    (selected.len() ≥ 1).
  - Therefore `select_ownership_safe_wave(non_empty)` always returns at
    least one id. The framework kernel's "must return at least one id
    when `ready_task_ids` is non-empty" contract
    (echo-agent `runtime_executor.rs:103-104, 319/467`) is honored.
  - The function is deterministic (input-order scan), so it cannot
    introduce its own starvation: a deferred writer will be first in the
    next iteration's input and will then be selected.

## Deviations

One orthogonal observation, not a deviation from the claim:

- The cycle-rejection test `invalid_cycle_is_rejected_before_scheduler_dispatch`
  (executor.rs:5785-5821) shows that EKO rejects cycles at plan-attach

  `PlanValidator` still re-validates every snapshot at
  `runtime_executor.rs:214`. The two checks have different scopes
  (commit-time vs every safe point) and do not duplicate authority.
