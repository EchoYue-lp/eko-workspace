## Claim

Every callback EKO provides to the framework's `RuntimeDagController`
trait is product policy / persistence / dispatch — never a recomputed
frontier, never a wave dispatcher, never a cancel-loop, never a retry
loop, never a stall timer. The eight callbacks collectively implement:
persistence (load/claim/resolve), product dispatch (write/shell/llm
semaphores, worktree integration, review gate), and product policy
(file-ownership wave narrowing, retry budget, attended/unattended
disposition, run-state cleanup). Two callbacks (`interruption_outcome`,
the post-cancel `finalize_cancelled_run_state` sweep) together mitigate
F-TSK-03-P2-02's framework-level orphan hazard at the application layer.

Returns `RuntimePlanSnapshot { revision, tasks }`. |
| `claim_task(run_id, task, expected_revision)` | 1254-1263 | persistence (delegation) | Delegates directly to `store.claim_task` (store.rs:986-1029), which CAS-checks `plan.revision == expected_revision` and `task.status == Pending`, then atomically appends a `Running` event with the new claim. | `select_ready_wave(tasks, ready_ids)` | 1265-1282 | product policy (file ownership) | Calls `select_ownership_safe_wave` (executor.rs:1127-1145): pass through read-only tasks and the first writer; defer writers that conflict with already-selected writers. Always returns ≥1 id when `ready_ids` is non-empty (verified in V02). **Does NOT recompute the frontier** — it only filters the ids the kernel passed in. |
| `dispatch_task(ctx, claim, task)` | 1284-1346 | dispatch + product policy | First consults `store.recoverable_subagent_result` to short-circuit a previously-completed durable result (restart resumption). Otherwise delegates to `dispatcher.dispatch(...)`, which for the production `RealTaskDispatcher` calls `execute_task` (executor.rs:855-887) with write/shell/llm semaphores + per-file locks threaded in. Returns `TaskDispatchSuccess { result, full_output }`. |
| `resolve_dispatch(run_id, claim, task, dispatch)` | 1348-1562 | product policy (review + retry + integration) | On error: maps to `Failed`/`Cancelled`/`TimedOut`. On success: runs `assess_task_execution`, then: (a) `ExecutionFailed` → if budget remains, `requeue_claimed_task` (one-shot Pending flip, returns `Pending`); else `Failed`. (b) `AcceptancePending` → `Blocked` (with attended/unattended disposition). (c) `Executed` → `run_review_gate`; on pass, `integrate_reviewed_task` (worktree merge for Implementation/Debugging); on `NeedsFix`/`Suspend`/`Skipped` → `Blocked`. |

| `interruption_outcome(run_id)` | 1595-1613 | persistence (state reflection) | Returns `Paused` if the run was externally paused during execution; otherwise `Cancelled`. Drives the outer drain loop's branch selection. |

- Forbidden-class check (zero hits expected):
  - No callback reads `DagExecutionState`, `ready_task_ids`,
    `failure_errors`, or any kernel-internal primitive. (These types are
    not even imported into executor.rs — confirmed by grep.)
  - No callback spawns a `JoinSet`, drives a wave, or implements its own
    cancellation abort. Cancellation cleanup lives in the post-outcome
    sweep below, not in a callback.
  - No callback constructs a `PlanValidator`. The single validator lives
    in the kernel (`runtime_executor.rs:178`).
- Orphan reconciliation (mitigates F-TSK-03-P2-02):
  - `finalize_cancelled_run_state` (executor.rs:643-661): after the
    kernel returns `Cancelled`, the outer `execute_run` sweeps over
    `list_todos(run_id)` and flips every task in
    `Pending | Running | Blocked` to `Cancelled`. This catches the
    orphaned `Running` rows the framework's abort drain left unresolved
    (F-TSK-03-P2-02 mechanism), then transitions the run to `Cancelled`.
  - Paused-state cleanup (executor.rs:546-559): after the kernel returns
    `Paused`, the outer loop sweeps every `Running` task back to
    `Pending` so a subsequent resume re-dispatches them. `Blocked` and
    `Failed` tasks are intentionally left alone (Blocked needs user
    action; Failed is terminal).
  - Together these close the orphan-claim hazard at the application
    layer for EKO. The framework-level gap (F-TSK-03-P2-02) remains for
    other consumers; A-TSK-04 should confirm recovery/resume paths also
    honor this reconciliation.
- `plan_tasks` cache (executor.rs:1157, 1244-1247): the in-memory
  `Mutex<HashMap<String, PlanTask>>` is fully overwritten on each
  `load_snapshot` call. Since the kernel calls `load_snapshot` at the top
  of every safe point (echo-agent `runtime_executor.rs:213`) and dispatch
  / resolve happen within that iteration, the cache is consistent within
  an iteration. It is a read-side convenience for `dispatch_task` /
  `resolve_dispatch` to look up the `PlanTask` (EKO's rich type) from the
  runtime `Task` (framework's neutral type) — not a parallel authority.

## Deviations

One nuance worth noting, not a deviation from the claim:

- The retry budget lives in `resolve_dispatch`, which is technically
  "controller-owned retry policy" rather than "dispatch-pipeline retry"
  (F-TSK-03 suggested retry lives behind `dispatch_task`). The shape is
  nevertheless correct: the controller returns a `Pending` resolution,
  the kernel re-claims, and the kernel's `claim.attempt` carries the
  retry counter (store.rs:1012). No retry loop exists in EKO; only the
  one-shot decision and the budget check. This matches AGENTS.md's
  allowance that the adapter owns product policy (retry budget) while
  the framework owns the mechanism (re-claim loop).
