## Claim

Both SQLite stores use a sound, consistent concurrency model: WAL journaling
for concurrent readers, a busy timeout to absorb cross-process write
contention, a single connection serialized through a mutex to avoid
`SQLITE_BUSY` storms within one process, and an async-safe mutex that does not
block tokio worker threads or risk `!Send` futures.

## Method

Read both PRAGMA batches, the connection/mutex fields, and every call site
that acquires the guard; compare the two stores and cross-reference the
sibling `SqliteRuntimeStateStore` pattern.

```text
read echo-agent/echo-state/src/memory/sqlite_store.rs (54-128, 395-462, 465-561, 710-745, 909-928)
read echo-agent/echo-state/src/memory/sqlite_conversation.rs (5-93, 97-141, 295-369)
read echo-agent/src/state/sqlite.rs (28-86)   # sibling pattern cross-ref
grep -n "PRAGMA\|Mutex\|busy_timeout\|spawn_blocking\|transaction" \
  echo-agent/echo-state/src/memory/sqlite_store.rs \
  echo-agent/echo-state/src/memory/sqlite_conversation.rs
```

Static inspection (no multi-process contention harness executed).

## Expected Result

- Both stores: WAL enabled, `synchronous=NORMAL`, `busy_timeout` set.
- Both stores: same mutex type (preferably `tokio::sync::Mutex` for async
  safety, or rusqlite wrapped in `spawn_blocking`).
- No `!Send` guard held across `.await`; no synchronous disk I/O on the tokio
  worker thread without `spawn_blocking`.
- Per-op transactions for multi-statement writes (`put`, `delete`,
  `save_messages`).

## Result

- Exit code: not-applicable (static inspection)
- Duration: <1s
- Summary: **Two divergences from the claim.**
  - **WAL + transactions: correct in both.** `SqliteStore::open_connection_at`
    (`sqlite_store.rs:108-120`) sets `journal_mode=WAL; synchronous=NORMAL;
    cache_size=10000; temp_store=MEMORY; busy_timeout=5000`.
    `SqliteStore::put` wraps main+FTS+vector writes in `conn.transaction()`
    (504-556); `delete` likewise (716-741).
    `SqliteConversationStore::new` (`sqlite_conversation.rs:36-42`) sets
    `journal_mode=WAL; synchronous=NORMAL; cache_size=5000; temp_store=MEMORY;
    foreign_keys=ON`. `save_messages` (317-365) wraps DELETE+INSERT+UPDATE in
    `BEGIN IMMEDIATE TRANSACTION` with explicit ROLLBACK on error. Both are
    atomic across their multi-statement bodies. **This part of the claim holds.**
  - **Divergence 1 — `busy_timeout` missing on the conversation store**
    (finding F-MEM-02-P2-02): `SqliteStore` sets `busy_timeout=5000`
    (`sqlite_store.rs:116`); `SqliteConversationStore` does **not** set any
    `busy_timeout` (`sqlite_conversation.rs:36-42`). Under cross-process write
    contention the conversation store returns `SQLITE_BUSY` (surfaced as
    `MemoryError::IoError`) where the memory store would wait up to 5 s and
    retry. WAL mitigates reader/writer contention but not writer/writer.
  - **Divergence 2 — inconsistent, async-unsafe mutex model**
    (finding F-MEM-02-P2-03): `SqliteStore` uses `std::sync::Mutex<Connection>`
    (`sqlite_store.rs:54, 67`); `open_connection` (124-128) returns a
    `std::sync::MutexGuard`, which is `!Send`. The code carefully avoids
    holding the guard across `.await` (embedder hoisted out of the transaction
    — comment 478-481; `semantic_search_impl` drops+reacquires at 454-455),
    but there is no compile-time enforcement: a future maintainer who adds an
    `.await` under the guard silently makes the future `!Send`, breaking
    multi-threaded tokio at runtime. `SqliteConversationStore` uses
    `tokio::sync::Mutex<Connection>` (`sqlite_conversation.rs:14, 21`) — await-
    aware, no `!Send` footgun. Neither store wraps rusqlite calls in
    `tokio::task::spawn_blocking`, so both block the worker thread for the
    duration of synchronous disk I/O; `SqliteStore` adds the `!Send`-guard
    hazard on top.
- Log/artifact: none.

## Deviations

The struct-doc justification at `sqlite_store.rs:62-64` ("single
`Mutex<Connection>` ... SQLite serialises all writes anyway, so a single
connection eliminates `SQLITE_BUSY` storms") optimises for write-serialisation
correctness within one process but does not address (a) the async-runtime
integration (`!Send` guard, executor blocking) and (b) cross-process contention
(the very thing `busy_timeout` exists for, and which the conversation store
then omits). So the documented rationale is partial; the two stores never
converged on a single model.

## Conclusion

The WAL + per-op transaction layer is sound and gives `SqliteStore` the crash-
durability `FileStore` lacks (confirming the F-MEM-01 Handoff hypothesis). But
the concurrency claim fails on two points: the conversation store's missing
`busy_timeout` (P2-02) and the inconsistent / executor-blocking / `!Send`-
prone mutex model (P2-03). Neither is an active crash today (single-process-
single-connection avoids contention; the await-avoidance currently holds), so
both are latent rather than live failures — hence P2, not P1. Supports
findings F-MEM-02-P2-02 and F-MEM-02-P2-03.

This validation does NOT execute a multi-process contention test; the
`busy_timeout` gap is established by PRAGMA inspection, and the mutex hazard
by reading the guard's `!Send` type and the await-avoidance comments.

## Follow-Up

Open findings F-MEM-02-P2-02 (add `busy_timeout=5000` to the conversation
PRAGMA batch) and F-MEM-02-P2-03 (converge on `tokio::sync::Mutex` for
`SqliteStore`, or wrap rusqlite in `spawn_blocking`). A dynamic `Send`-future
compile assertion and a two-process `SQLITE_BUSY` test should accompany the
fixes.
